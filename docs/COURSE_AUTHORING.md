# Как добавлять и проверять учебные главы

Учебный материал хранится в репозитории. Платформа загружает только ID, перечисленные в `internal/content/manifest.json`. Наличие файлов черновика не публикует главу и не подтверждает навык ученика.

## Файлы и контракт

Для главы `middle-26` используются:

- `internal/content/data/middle-26.json` — название, ранг, порядок, зависимости, версия Go, ожидаемые результаты обучения, словарь, самопроверка и три задания;
- `internal/content/data/middle-26.md` — самостоятельное объяснение и исполняемые примеры;
- `internal/grading/specs/middle-26-{easy,medium,hard}.json` — сигнатура, разрешённые импорты, доверенный driver и публичные/закрытые векторы;
- `internal/content/solutions/middle-26-{easy,medium,hard}/main.go` — приватные эталонные решения.

Сигнатуры в условии, starter, driver и эталоне должны совпадать. Поле `public_output` в metadata должно соответствовать `public_expected` production-grader. Не добавляйте произвольные поля в grading JSON: схема отклоняет неизвестные поля. Эталон не должен попадать в публичный API, bundle frontend или текст подсказки.

## Что должна объяснять глава

Начните с понятной проблемы и определите новые английские термины на русском. Для каждого заявленного результата укажите объяснение, пример и наблюдаемое доказательство. Не подменяйте предметный материал повтором общих абзацев. В M11 автоматический gate проверяет объём 1800–2200 слов и минимум три группы примеров; эти числа не доказывают качество объяснения.

Пример оформляется как fenced Go-блок с metadata, например `go group=middle-26-easy mode=run`. Файлы одной группы объединяются для запуска. `mode=build` используется для примера, который нужно только скомпилировать. Проверьте применяемые варианты metadata по существующим главам и `internal/content/examples_test.go`.

Easy, Medium и Hard должны добавлять наблюдаемую работу: новые состояния, обработку ошибки, композицию или проверяемый инвариант. Переименование одной функции и замена строкового ответа не создают новую сложность.

## Проверяемое поведение

Публичные примеры помогают понять контракт; закрытые векторы проверяют независимые ветви, приоритет ошибок, нулевые/предельные значения и неверные состояния. Для арифметики проверяйте переполнение до умножения или сложения; полезен независимый oracle на `math/big` и генерация входных данных через стандартный `testing/quick`.

Если условие обещает отсутствие записи, rollback или порядок публикации, grader должен наблюдать эти действия через счётчик или журнал fake-зависимости. Одна правильная итоговая строка не доказывает правильные побочные эффекты. Явно различайте результат функции и диагностический trace, который добавляет driver.

Проверьте несколько содержательно ошибочных решений: пропущенный rollback, ack до эффекта, игнорирование tenant, неверный приоритет, переполнение или повтор side effect. Они должны компилироваться и отклоняться production `Spec.Request` / `Spec.Check`; compile error не доказывает качество скрытого вектора. Запускайте только закреплённые доверенные fixtures по существующим test helpers. Пользовательский код остаётся в изолированном runner.

Fake проверяет локальный протокол. Он не подтверждает SQL isolation, долговечность брокера, производительность или безопасность развёрнутой системы. Такие результаты требуют отдельного проекта, интеграционного сценария и, где предусмотрено, ручного review. Связывайте skill только с реально наблюдаемой практикой; XP и helper-задание не выдают ранг.

## Команды проверки

Используйте `sh scripts/go.sh`, чтобы выбрать закреплённый toolchain, а не случайный системный Go.

```sh
sh scripts/go.sh test ./internal/content ./internal/grading
make test
```

Для scoped-проверки M11 нужен работоспособный локальный rootless runner и заранее подготовленные pinned images. Команда ниже сохраняет точные scope, отпечаток исходников, exit code и SHA-256 сырого лога:

```sh
python3 scripts/check_m11_acceptance.py \
  --lessons middle-26 \
  --report artifacts/m11-middle26-report.txt \
  --log artifacts/m11-middle26.log \
  --cache-dir /tmp/oga-m11-author-cache
```

Для полного gate опустите `--lessons` и выберите отдельные пути отчёта и лога. Scoped PASS не является PASS всех 88 глав. Если исходники изменились во время прогона, результат помечается `STALE`. Отпечаток включает содержание уроков, grading и runner, поэтому обычная смена файловых дат после checkout не отменяет доказательство неизменённого кода.

## Приёмка и публикация

Сначала согласуйте контракт и границу утверждений, затем проверьте примеры, стартеры, эталоны и неправильные решения. Нужен отдельный педагогический review: понятность для заявленного уровня, корректность терминов, постепенное усложнение и отсутствие обещаний, не подтверждаемых заданием. Исправьте замечания и повторите затронутые проверки.

После всех правок M11 повторяется полный 88-главный gate. Только после содержательной приёмки, проверки prerequisites/skills и проектных/rank criteria можно менять `published_lessons`. ИИ-наставник получает опубликованные материалы; черновики не должны становиться его учебным источником по одному факту наличия файла.

Опубликованный ID задания, его критерии и уже выданное evidence нельзя незаметно переопределять. Изменение контракта требует нового ID/версии либо явного плана миграции и регрессионных тестов. Обновите manifest, план, handoff и матрицу требований, сохранив точные команды и ограничения проверки.
