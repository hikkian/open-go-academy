# Интерфейс урока: карточка задания, ожидаемый вывод, «ждали / получили»

Спецификация для исполнителя кода (frontend `web/src`, API `internal/httpapi`). Цель: чтобы урок, написанный по `docs/LESSON_STYLE_GUIDE.md`, выглядел как задумано, а при «Не принято» ученик сразу видел, чего ждали и что получили. Ничего из этого не меняет проверку заданий, эталоны и grading-спецификации.

## 0. Что сейчас (разбор)

Страница урока: слева `lesson-pane` (результаты обучения → Markdown → слова урока → список «Практика» → «Проверь себя»), справа `ide-pane` (заголовок с `title` и одной строкой `prompt`, редактор, кнопки, «Результат», эталон).

Проблемы, из-за которых ученик «теряется»:

1. **Ожидаемый вывод не показывается нигде.** Поле `public_output` есть в JSON и в типе `Exercise` (`api.ts`), но `App.tsx` его не рендерит. Требование «ровно `Go готов!`» живёт только в середине фразы `prompt`.
2. **Условие над редактором — одна строка с обрезкой** (`.ide-heading span`: `max-width: 450px; text-overflow: ellipsis`). Длинные `prompt` (у функциональных заданий 250+ знаков) обрезаются на середине.
3. **Критерии (`criteria`) не показываются вообще.** Ученик не знает, что именно проверят.
4. **Список заданий — в самом низу левой панели**, после глоссария: до него надо пролистать весь текст. В тексте уроков задания повторяются прозой («Практика» в Markdown), условия — внутри предложений.
5. **«Не принято» — только названия галочек** («Публичный пример вывода ×»). Нет «ждали / получили», не видно, где именно разошлись строки, пробел это или перевод строки.
6. **Функциональные задания:** при «Проверить» stdout заменяется текстом «Проверены открытые и закрытые сценарии.», и ученик видит `закрытый пример 3 ×` без намёка, какой класс входов упал (граница, пустая строка).
7. **Отказ до запуска** (например, `import "fmt"` там, где импорты запрещены) приходит как HTTP 422 и показывается красным баннером «Не удалось выполнить действие: …» — выглядит как сбой системы, а не как ответ на код.
8. **Нет визуальных блоков**: Markdown без выносок, таблиц и раскрывашек (CommonMark, без `rehype-raw`/GFM); цитаты не стилизованы. Урок — сплошной текст одного цвета.
9. **Самопроверка — абзацем** в тексте и ещё раз списком под уроком; в тексте вопросы слиты в одну строку.
10. **Галочки не привязаны к критериям**: названия проверок («Обязательная структура задания») не объясняют, что нарушено.

## 1. Компоненты

### 1.1 Карточка задания (`TaskCard`) — в `ide-pane`, над редактором

Источник данных на этапе 1 — Markdown урока: раздел от заголовка `### Задание N · <title>` (где `<title>` = `exercise.title`) до следующего заголовка того же или более высокого уровня. Frontend находит его по `exercise.title`, рендерит тем же `ReactMarkdown` с теми же `components`, плюс:

- первый абзац, начинающийся с `**Цель.**` → строка заголовка карточки (вместо нынешнего `prompt`; `prompt` остаётся запасным вариантом, когда карточки в тексте нет);
- блок после `**Ожидаемый вывод**` → секция «Ожидаемый вывод» моноширинным шрифтом с видимыми `⏎` в конце строк (переключатель «показать невидимые»); для `kind: function` рядом — входы публичных примеров, если frontend получит их из API (см. 2.3), иначе — только блок из текста;
- цитаты с меткой `**Подсказка.**` → `<details>` «Подсказка», свёрнуто; раскрытие не влияет на прогресс и не логируется как попытка;
- `**Шаги.**`, `**Как проверить себя.**`, `**Если не принято.**` → подзаголовки карточки (стиль `eyebrow`).

Карточка сворачивается в одну строку (Цель) кнопкой «Свернуть», состояние запоминается в `localStorage` на уровне урока. На экране ≤ 980 px карточка стоит над редактором и свёрнута по умолчанию; на десктопе — развёрнута, высота ограничена 40 % панели с прокруткой.

Этап 2 (после миграции контента): те же блоки из структурированных полей JSON `goal`, `expected_output`, `steps[]`, `self_test`, `not_accepted[]`, `hints[]`; тогда карточка в Markdown становится необязательной. Поля добавляются в `internal/content/content.go` и `api.ts`; `go` структура игнорирует неизвестные поля, но публиковать поля без рендера нельзя.

### 1.2 Критерии как чеклист

В карточке — список `criteria` с иконками состояния, которые обновляются после «Проверить»: каждая проверка сервера сопоставляется с критерием по индексу `criterion` (см. 2.1), несопоставленные показываются ниже как есть. До первой проверки — серые кружки.

### 1.3 Блок «ждали / получили» в «Результате»

При `passed: false`:

- заголовок «Не принято — вот что разошлось»;
- для каждой проваленной проверки с `expected`/`actual` — две колонки на десктопе (одна под другой на мобильном): «Ждали» и «Получили», моноширинно, построчное сравнение; первая отличающаяся строка подсвечена; пробелы и переводы строк показываются как `·` и `⏎` при включённом переключателе; лишние/недостающие строки помечены `+`/`−`;
- под сравнением — `hint` проверки (одна строка, из сервера);
- для закрытых примеров функционального задания: «Закрытый пример 3: вход не показывается. Подсказка: проверь границу диапазона» — текст `hint` из категории примера (2.2), без раскрытия входа.

Текущая консоль (stdout/stderr) остаётся выше: ошибки компилятора — это тоже «получили».

### 1.4 Выноски

`blockquote`, первый `strong` которого равен одной из меток `Важно.`, `Подсказка.`, `Типичная ошибка.`, `Зачем.` → классы `callout callout-important | callout-hint | callout-mistake | callout-why`: цветная левая полоса (cyan / muted / red / green), иконка-метка, фон `var(--soft)`. Подсказка — `<details>` (свёрнута). Без метки — обычная цитата. Реализация: компонент `blockquote` в `components` `ReactMarkdown`; метку определять по тексту первого `strong`, не по HTML.

### 1.5 Навигация по заданиям

- Над Markdown (сразу под «После урока ты сможешь») — полоса чипов «Задания: 01 Поздоровайся… · 02 Почини… · 03 Две строки», текущее подсвечено, выполненные — с галочкой (`progress.completed`). Клик = выбрать задание и прокрутить левую панель к его карточке (`id` заголовка уже есть: `headingID`).
- Список «Практика» внизу остаётся (для тех, кто дочитал).
- Кнопка «К заданию» в правой панели прокручивает левую к карточке.

### 1.6 Отказ до запуска (422)

Ответы 422 от `/exercises/{id}/run|submit` показывать не баннером, а в «Результате» со статусом «Не принято — код не допущен к проверке» и текстом сервера; баннер — только для сетевых и 5xx ошибок.

## 2. API

### 2.1 Проверка (`runner.Check`) — новые необязательные поля

```text
Check {
  name      string   // как сейчас
  passed    bool     // как сейчас
  expected  string   // ждали (текст; для JSON-примеров — одна строка)
  actual    string   // получили
  hint      string   // одна фраза, что посмотреть
  criterion int      // индекс в exercises[].criteria или -1
}
```

Старые клиенты игнорируют новые поля; `checks_hash`/evidence не трогаем: хэш считается по `name`+`passed` как сейчас (проверить в `internal/assessment` перед изменением; если хэш покрывает всю структуру — поля добавлять только в ответ API, не в сохранённую попытку).

### 2.2 Заполнение полей

- Программные задания (`api.go`, ветка `submit`): `expected = ex.PublicOutput`, `actual = result.Stdout` (+ `result.Stderr` отдельной пометкой); `hint` по ситуации: exit≠0 → «Сначала почини ошибку компилятора выше»; совпадает после trim, но не точно → «Разошлись пробелы или переводы строк: включи показ невидимых»; структура → конкретно, что не найдено («нужен ровно один вызов fmt.Println с answer()»). `criterion`: по порядку критериев карточки.
- Функциональные задания (`grading.go` `Check`): для публичных примеров `expected = string(e)`, `actual = lines[i]`; для закрытых — `expected`/`actual` пустые, `hint` из необязательного поля спецификации `private_hints[]` (по одному на закрытый пример; схема grading JSON строгая — поле добавить в `specJSON`, пустое по умолчанию). Пока `private_hints` нет — `hint` = «закрытый пример: проверь границы и пустой ввод».
- 422 от `Spec.Request` — тело как сейчас, frontend показывает в «Результате» (1.6).

### 2.3 Публичные входы функциональных примеров

`GET /api/lessons/{id}` уже отдаёт `public_output`. Добавить `public_examples: [{input, output}]` для `kind: function` (из `spec.publicInput`/`publicExpected`; закрытые не отдавать) — чтобы карточка показывала «вход → результат».

HTML-набросок (статический, без зависимостей): `docs/mockups/lesson-task-card.html` — открыть в браузере.

## 4. Приёмка

- Playwright (desktop + mobile, light + dark): карточка видна при открытии zero-01; «Ожидаемый вывод» содержит `Go готов!`; подсказка свёрнута, раскрывается кликом и клавиатурой; при вводе `fmt.Println("Привет, Go!")` и «Проверить» — статус «Не принято», блок «Ждали/Получили» с обеими строками и подсветкой первой расхождения; при правильном коде — «Принято», чипы заданий показывают галочку; axe без нарушений; нет горизонтальной прокрутки.
- Go: unit-тест на заполнение `expected/actual/hint` для программных и функциональных проверок; закрытые примеры никогда не содержат `expected`/`actual`; `checks_hash` прежних попыток не меняется.
- Существующие тесты не меняют смысл: `tests/learning.spec.ts` (golden path, «Go готов!», «Показать решение»), `tests/curriculum.spec.ts` (`.function-exercise-note`, статусы), `internal/content` (title, 3 упражнения, 5 вопросов, примеры запускаются).
- После изменений frontend — `web` typecheck/build, затем полный `make test` и e2e в окне без замеров GPU.
