# M11 backend ecosystem snapshot: P3 TaskFlow / P4 ScaleLab

Проверено 2026-10-16 по официальным upstream release notes, upstream client repositories, Go module proxy и Docker Hub registry metadata. Это исследовательский snapshot, не утверждение о тестировании зависимостей вместе с приложением. Уже зафиксированные Go 1.27.2, pgx 5.11.0 и PostgreSQL 18.6 повторно не оценивались.

## Выбор для учебного пути

Для P3 достаточно PostgreSQL + одного асинхронного механизма. Начать с Go worker pool и PostgreSQL-backed outbox/jobs: это раскрывает retries, idempotency и транзакции без отдельной инфраструктуры. Когда проекту действительно нужен брокер, добавить **RabbitMQ 4.3.x + официальный Go AMQP 0-9-1 клиент**, закреплённые конкретными версиями. Redis оставить опциональным расширением P3/P4 для измеренного cache или rate-limit; он не заменяет durable queue. P4 сравнивает baseline до/после и нагрузку, а не включает Redis и RabbitMQ «на всякий случай». Это соответствует P3/P4 в E4 и неделе 10 E2 спецификации.

Выбор RabbitMQ обусловлен соответствием явной очереди задач P3 и upstream-клиентом, поддерживаемым командой RabbitMQ. Redis проще для cache/rate-limit, однако Redis 8 имеет лицензирование RSALv2/SSPLv1/AGPLv3 на выбор, что требует осознанного решения для open-source проекта. Это сведения из лицензии, не юридическое заключение. Если нужна наименьшая локальная сложность, начать вообще без отдельного брокера, с SQL outbox; RabbitMQ — следующий наглядный шаг курса.

### Уточнение генерации gRPC

Официальный gRPC quick-start на момент доступа клонирует `grpc-go` tag `v1.83.2`, хотя Go module proxy latest уже возвращает `v1.84.0`. Документ команд `@latest` только для знакомства; для курса следует pin-ить версии обоих plugins в tool manifest и проверять generated code в CI. `protoc-gen-go-grpc` имеет отдельный version stream от gRPC runtime; requirements из `.mod` показывают минимумы модулей, от которых собирался plugin, но не официальную гарантию полного cross-version matrix. Поэтому выбранная пара требует compile test до утверждения.

`protoc-gen-go` не имеет отдельного module path/version stream: бинарник устанавливается из корневого `google.golang.org/protobuf` module, здесь v1.36.12 (`go install google.golang.org/protobuf/cmd/protoc-gen-go@v1.36.12`). Запрос `proxy.golang.org/google.golang.org/protobuf/cmd/protoc-gen-go/@latest` возвращает 404, что подтверждает, что его нужно версионировать через root module. `protoc-gen-go-grpc` — отдельный nested module и имеет собственную v1.6.2.

### `protoc` compiler binary

Официальный Protocol Buffers release feed показывает latest stable **v36.2**, released 2026-09-17; supported protoc release series — 36.x (active) и 33.x (maintenance). Для Go x86_64/Linux asset `protoc-36.2-linux-x86_64.zip` официальный release metadata публикует SHA-256 `121f6c7afe1d4d0e3ea6aab9432038599250134cbf4474cb1167d2c7decd4278`. Это отдельный native compiler executable, не Go module/plugin version. Официальная gRPC Quick Start всё ещё задаёт минимум `protoc` major v3; это compatibility floor, не утверждение, что следует использовать старый compiler. [official v36.2 release/assets](https://github.com/protocolbuffers/protobuf/releases), [official install instructions](https://protobuf.dev/installation/), [protoc support policy](https://protobuf.dev/support/version-support/). Binary не скачивался и checksum локально не проверялся.

Не выдавать amd64 digest за гарантию arm64/всех платформ. Image registry metadata прочитана; сами образы в этом исследовании не загружались и не запускались.

## Локальная воспроизводимость и пределы проверки

- Для разработчика: Compose только для явно выбранного компонента, healthcheck + readiness wait, фиксированные image reference, локальные ephemeral volumes, опубликованный порт только на `127.0.0.1`; не публиковать broker/Redis в интернет. Тесты должны ожидать готовность сервиса, а не полагаться на `depends_on` как на проверку готовности.
- Для CI: закрепить OCI digest вместе с платформой; запускать настоящий integration suite для выбранного backend через Docker-compatible локальный runtime. Использовать уникальные vhost/database/key prefix на job, случайные credentials, cleanup и timeout. Локальный success не подтверждает remote CI — фактически remote CI не проверялся.
- Для Go воспроизводимости: pin runtime modules и генераторы отдельно, commit `go.mod`/`go.sum`, использовать `go mod verify`; для gRPC также фиксировать `protoc` compiler. Точные module `go` directives для выбранных версий проверены в таблице; фактический MVS graph, licenses и advisories сверить в момент внедрения.
- Нынешний production runner намеренно network-none и изолирован. Эти middleware services предназначены только для trusted local platform service/integration test harness, никогда для student Go container; не подключать broker credentials/socket к sandbox. Существующий rootless Podman runtime и текущий M10 evidence не переоценивались.
- Ограничение доступа к Docker socket и Compose ownership важны: не исполнять предоставленные пользователем Compose manifests на shared host. Для курса выдавать только контролируемый репозиторием набор сервисов.

## Пробелы, которые остаются до внедрения

Это desktop/upstream research, не исполняемый compatibility proof. Не скачивались Docker images, не поднимались сервисы, не запускались Go integration tests, не вычислялся полный MVS graph, не проверялись платформа arm64, transitive advisories, Erlang patch image digest, RabbitMQ plugins или gRPC generator/runtime cross-version matrix. `protoc` checksum получен из официальной release metadata, но файл не скачивался для локальной сверки. Redis image digest проверен только для linux/amd64. Версии быстро меняются: refresh release/support state, security patch, module proxy JSON и architecture digests непосредственно перед M11 implementation; зафиксировать реальный выбранный minimum stack в version matrix только после локального end-to-end теста.
