# M9 credentials: практическое исследование

Проверено **2026-10-15** по официальным спецификациям и репозиториям. Это архитектурное исследование, не реализация и не проверка совместимости выпускаемого credential. Для общего контекста границ доверия см. [`CREDENTIALS.md`](CREDENTIALS.md). Код и зависимости не менялись.

## Решение для первого локального этапа

Сначала реализовать собственный минимальный JSON-формат `open-go-academy.local-credential.v1`, явно помеченный как **локальная самовыдача**. Это позволяет отработать выпуск после существующего серверного `RankAward`, подпись Ed25519, скачивание JSON, проверку подписи и отзыв без внешнего сервиса. Не называть этот формат W3C VC или Open Badges 3.0 и не использовать их типы/контексты как знак соответствия. Локальный формат — не формат общеобязательного свидетельства: подпись удостоверяет владение ключом и целостность данных относительно доверенного открытого ключа, но сама по себе не доказывает репутацию издателя, личность владельца или обучение.

Рекомендуемый поток:

1. Сервер проверяет сохранённый `RankAward` и зафиксированную версию критериев в одной транзакции выдачи; клиент не передаёт ранг, балл, дату или evidence как источник истины. Уникальность по пользователю и achievement предотвращает повторные сертификаты. Отдельный случай отзыва сохраняется аудируемо.
2. Создаётся случайный credential ID. Запись содержит issuer profile (`local-self-issued`), achievement/rank, версию criteria, ссылку на идентификатор серверного award, время выпуска и необязательный срок действия. Не включать email, исходники, ответы экзамена, полный журнал обучения или внутренние проверки.
3. По умолчанию credential приватный и публичное отображение имени выключено. До включения страницы проверки явно показать владельцу поля, которые станут публичными, и получить opt-in. Предлагать псевдоним. Сам JSON можно скачать без публикации verify-страницы.
4. Зафиксировать узкий формат подписания: байты полезной нагрузки — [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785) для объекта `credential`; подпись — Go stdlib [`crypto/ed25519`](https://pkg.go.dev/crypto/ed25519) / Ed25519 по [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032), с отдельным постоянным префиксом домена `open-go-academy:local-credential:v1\n`. JSON-envelope содержит `format`, `credential`, `signature` (`Ed25519`, `key_id`, base64url подпись) и открытый ключ либо ссылку на его локальную копию. Верификатор отклоняет неизвестный формат/алгоритм, неправильные размеры ключа/подписи, неверный ID key, изменённые поля и некорректные даты. Не подписывать неканонический результат `json.Marshal` как универсальное правило и не полагаться на порядок ключей в JSON.
5. Приватный ключ генерировать через `crypto/rand`, хранить отдельно от репозитория, web assets, БД, пользовательского runner и логов, ограничить правами ОС `0600`; не отдавать его API или браузеру. Для локального приложения файл в каталоге данных допустим как начальный компромисс, но это не аппаратное хранилище и не защита от владельца ОС. При потере ключа локальный verify fingerprint меняется; не переподписывать старые credentials молча.
6. Проверка возвращает раздельные состояния: `signature valid/invalid`, `issuer trusted/unknown`, `credential active/revoked`, `status unavailable`. Для локального режима ключ считается trusted только при сравнении с ключом/fingerprint, который проверяющий доверенно добавил локально; ключ, вложенный в файл, позволяет проверить целостность лишь условно и не является цепочкой доверия. Сетевой сбой никогда не означает «действителен».
7. Отзыв вести по случайному ID в локальной БД и проверять по собственному verify endpoint только если пользователь включил публичную страницу. Отзыв атомарно фиксирует время и причину с ограниченным набором значений, пишет аудит, не удаляет исходный подписанный файл и не меняет его подпись. Для автономной проверки статус будет неизвестен/устаревший, если нет доступного доверенного источника статуса. Такой endpoint раскрывает факт просмотра ID; документация UI должна это сообщать.
8. UI, PDF, JSON и публичная страница повторяют текст: «Локальный credential Open Go Academy. Самостоятельная локальная установка; подпись не подтверждает личность, аккредитацию, трудовой стаж или независимую проверку издателя». QR содержит только URL локальной страницы проверки и случайный ID, никогда имя/evidence/сам JSON.

Криптографический нюанс: RFC 8785 + Ed25519 над собственным envelope — чёткий протокол приложения, но **не** VC Data Integrity proof автоматически. Если позже будет выбран W3C/1EdTech профиль, реализовать выбранный Data Integrity cryptosuite целиком (трансформация, canonicalization, proof configuration/serialization и формат ключа), закрепить контексты и схемы по хешам, проверить официальные vectors независимым verifier. В документации W3C EdDSA v1.0 есть отдельные профили `eddsa-rdfc-2022` и `eddsa-jcs-2022`; наличие Ed25519 не делает произвольную JSON-подпись одним из них.

## Текущие стандартные источники и миграционный gate

- [W3C VC Data Model 2.0 Recommendation, 2025-05-15](https://www.w3.org/TR/2025/REC-vc-data-model-2.0-20250515/) задаёт модель issuer/holder/verifier, VC claims, context и `proof`; корректная подпись доказывает автора сообщения, а не признание издателя всеми verifier.
- [W3C Verifiable Credential Data Integrity 1.0](https://www.w3.org/TR/vc-data-integrity/) рекомендует фиксировать порядок и криптографические хеши context для verifier без JSON-LD и прямо описывает JSON Canonicalization Scheme (RFC 8785) и RDF Dataset Canonicalization как разные механизмы. Нельзя смешивать их или выдумывать профиль подписи.
- [W3C Data Integrity EdDSA Cryptosuites v1.0](https://www.w3.org/TR/vc-di-eddsa/) задаёт точную обработку Ed25519, а не просто алгоритм. Нормативное приложение содержит `eddsa-jcs-2022` и `eddsa-rdfc-2022` и test vectors.
- [W3C Bitstring Status List v1.0 Recommendation](https://www.w3.org/TR/vc-bitstring-status-list/) — стандартный privacy-preserving список при переходе к совместимому VC-профилю. В нём подписывается сама status-list credential; нужно отдельно проверить её подпись, свежесть и статус. Не выдавать нестандартный локальный endpoint за Bitstring Status List.
- [1EdTech Open Badges 3.0](https://standards.1edtech.org/open-badges/specifications/standards/v3p0) сейчас привязан к VC Data Model 2.0; страница перечисляет JSON Schema для AchievementCredential и правила проверки proof/status. История Final-изменений включает правки схем/контекста в октябре 2025, ноябре 2025 и апреле–июне 2026. Поэтому для будущей интеграции закрепить точную версию schema/context, получить их из ссылок на официальной странице, сохранить локальные копии и SHA-256, прогнать схему и официальные примеры; не использовать изменяемую `main`/`develop` ветку или сетевой context во время проверки.
- [1EdTech Open Badges certification guide](https://standards.1edtech.org/open-badges/specifications/standards/v3p0/cert) описывает отдельную программу проверки/сертификации. Собственные schema/crypto tests или соответствие JSON Schema не дают права называть продукт «1EdTech certified».

**M9 schema gate:** пока validator не принимает созданный документ по выбранной версии OB schema и подпись не проверяется independent known-good verifier по официальному profile/vector, показывать только собственный локальный формат. Даже успешная проверка JSON Schema подтверждает лишь форму документа, не криптографическую, issuer-trust или certification compliance.

## QR, PDF и кириллица

Наименее сложная рекомендация — **одна библиотека** [`github.com/gpdf-dev/gpdf`](https://pkg.go.dev/github.com/gpdf-dev/gpdf), версия **v1.0.13**, опубликована 2026-09-05, MIT, требует Go 1.22+. Первичный README описывает pure-Go генерацию PDF, встроенный QR writer и регистрацию/встраивание TrueType-font; changelog v1.0.13 от 2026-09-04 отдельно чинит рендер Cyrillic/других non-Latin glyphs в overlay. Таким образом не нужны отдельный QR-модуль, браузер, внешний API или системный PDF renderer. Это молодой проект (importers на pkg.go.dev на дату проверки — 0), поэтому до production добавить smoke/golden-тест PDF, QR decode тест и проверку extractable Cyrillic текста в PDF; не считать заявление README самостоятельным QA.

Для русского PDF подходит обычный TrueType [Noto Sans](https://github.com/google/fonts/tree/main/ofl/notosans): Google Fonts metadata указывает OFL, наборы `cyrillic`/`cyrillic-ext`; Noto upstream называет это семейство Noto Sans 2.015. Локально обнаружен `/usr/share/fonts/google-noto/NotoSans-Regular.ttf`: 621,572 bytes, `fc-scan` сообщает Noto Sans Regular/version 132055 (2.015), `fc-query` подтверждает кириллический диапазон; SHA-256 `478c558ea716033cd60c03438f628dfa75694dcf6b5f6d505a2f05fd2b4f3823`. Файл принадлежит Fedora RPM `google-noto-sans-fonts-20251201-2.fc44.noarch`, чьи RPM metadata объявляют `OFL-1.1`. Но путь, указанный для соседней лицензии `/usr/share/licenses/google-noto-fonts-common/LICENSE`, содержит текст **Apache-2.0**, а не OFL. Значит, эту соседнюю лицензию нельзя копировать как лицензию шрифта. Для vendoring скопировать один TTF и **OFL.txt из upstream Noto Sans 2.015**, добавить происхождение/version/SHA-256 и сам OFL в `internal/credentialrender/assets`; локальный Fedora binary — проверенный кандидат, но перед фиксацией сравнить его байты с закреплённым upstream release asset и приложить совпадающий upstream OFL. Не брать файл из системы по runtime-пути и не предполагать, что системный font можно распространять без этой проверки.

Официальный Go module proxy и pkg.go.dev на 2026-10-15 показывают [`golang.org/x/image/font/opentype`](https://pkg.go.dev/golang.org/x/image@v0.47.0/font/opentype) **v0.47.0**, опубликован 2026-10-09, BSD-3-Clause. Pin в proxy metadata ведёт на `go.googlesource.com/image`, tag `v0.47.0`, commit `c437a9130dcb43e6df402a034160826e29fd29b8`. Module требует Go 1.26.0; текущий проектный Go 1.27.2 его покрывает. Временная проверка вне repository скачала именно v0.47.0 и успешно распарсила найденный Noto Sans TTF (`bytes=621572 parsed=true err=<nil>`). Временный go.mod также показывает транзитивные `golang.org/x/sys v0.49.0` и `golang.org/x/text v0.43.0`. `opentype` — parser/rasterizer, не PDF writer; docs отдельно предупреждают, что он не защищён от вредоносных/повреждённых font inputs. Для asset, который приложение само поставляет и не принимает от пользователя, он годится как проверка/измеритель глифов или fallback; `gpdf` уже принимает встроенные TTF bytes, поэтому добавлять `x/image` в продуктовый build только ради генерации PDF/QR не требуется. Никогда не передавать ему пользовательский TTF.

Если приложение отдельно отдаёт PNG QR (не только QR внутри PDF), проверить [`github.com/yeqown/go-qrcode/v2`](https://github.com/yeqown/go-qrcode), **v2.2.5**, MIT, последний GitHub release 2025-02-14; модуль умеет QR версии 1–40 и writer в изображение. Однако это второй dependency и для узкого M9 не нужен при встроенном QR `gpdf`. Не рекомендую начинать новый код на [`skip2/go-qrcode`](https://pkg.go.dev/github.com/skip2/go-qrcode): API хорошо документирован и MIT, но опубликованный module псевдо-version датирован 2020-06-17, GitHub не показывает tagged releases, а в репозитории остаются открытые PR/issue. Возможная простота не компенсирует отсутствие свежего релизного pin.

Версии и Unicode-заявления проверены по pkg.go.dev/официальным upstream страницам на дату выше; локальная font metadata/лицензионный пакет и parser smoke проверены. Сам PDF, фактическую встройку шрифта в него, визуальную верстку и чтение QR камерой **в этом research-only проходе не тестировал**.

## Реализованное решение (2026-10-15)

Вместо рекомендованного JCS выбран собственный **fixed-struct** wire format `oga-local-v1`: `encoding/json.Marshal` структуры Payload с зафиксированным порядком полей, UTF-8 и Go JSON escaping; подпись Ed25519 над `open-go-academy:credential:v1` + NUL + эти байты. Это не RFC8785/JCS, не W3C/OB proof suite. Node crypto verifier в browser test независимо проверяет detached Ed25519 с тем же явно заданным доменом/encoding; embedded key не считается источником доверия. Format нужен при любом изменении canonical representation. Key ID — SHA256(raw32byte public key); private64byte key0600, no symlinks, missing/mismatched key с существующими records блокирует startup. Автоматическая ротация не реализована.

Рендер: `gpdf v1.0.13` + `x/image v0.47.0`. Выбран установленный **DejaVu Sans** с собственным соответствующим лицензированием, вместо Noto с обнаруженным несовпадением соседнего LICENSE. Vendored `internal/credentialrender/assets/DejaVuSans.ttf`, SHA256 `f0d9a390aa7cf43999a2fd1502a47c381bc7809ab5fac6937f0f6dd6524096cd`, исходник `/usr/share/fonts/dejavu-sans-fonts/DejaVuSans.ttf`, условия в LICENSE-DejaVu.txt из того же пакета (Bitstream/DejaVu/Arev). Изменение шрифта не выполнялось. Font attribution сохранён. В 2026-10-18 владелец выбрал MIT для platform code и CC BY 4.0 для оригинальных учебных материалов; root `LICENSE`, `COURSE_LICENSE.md` and `NOTICE` define this split. Это не заменяет third-party/legal review.

PDF отрендерен Poppler, кириллица извлекается pdftotext, PNG1400x1000 и PDFpreview визуально просмотрены. Исправлена реальная ошибка повторного bold DrawString с не сброшенным Dot. Независимые dev-only [`jsQR`](https://github.com/cozmo/jsQR)1.4.0 и [`pngjs`](https://github.com/pngjs/pngjs)7.0.0 (версии npmregistry verified2026-10-15) декодировали одинаковый verifyURL из QRPNG, certificatePNG и PDF-raster. Это actual decode, в отличие от базового PNG decode unit-test. PNG/PDF не являются криптографически подписанными PDF: авторитетный signed payload хранится в JSON, статус — в локальной БД; QR только ссылка.
