## Остаточные finding-и

### P2 — уровни всё ещё почти дублируют друг друга в Middle-16…18

- **Middle-16:** `middle-16-medium` и `middle-16-hard` имеют одну сигнатуру из трёх bool и одну и ту же последовательность условий. Различается только последний результат для опубликованного, но не завершённого состояния: `pending` против `retry_or_pending` (`internal/content/solutions/middle-16-medium/main.go:3`, `internal/content/solutions/middle-16-hard/main.go:3`). Это не добавляет новую наблюдаемую предпосылку или алгоритмическую работу.
- **Middle-17:** Medium и Hard также используют одну тройку bool и одинаковые переходы; Hard меняет только исход для подтверждённой публикации без отметки строки на `retry_may_duplicate` (`internal/content/solutions/middle-17-medium/main.go:3`, `internal/content/solutions/middle-17-hard/main.go:3`). Это полезное название crash window, но уровень Hard не проверяет дополнительное решение или новую ветвь.
- **Middle-18:** Easy и Medium повторяют ту же классификацию по успеху/commit, временной ошибке и фиксированному порогу трёх попыток; Hard лишь делает порог входом (`internal/content/solutions/middle-18-easy/main.go:3`, `internal/content/solutions/middle-18-medium/main.go:3`, `internal/content/solutions/middle-18-hard/main.go:3`).

Минимальное исправление: для Hard в каждом из этих уроков добавить новую переменную состояния и проверяемый инвариант, а не только новый текстовый label; либо честно переименовать уровни как варианты классификации и не учитывать их как три возрастающих доказательства навыка. До этого исходный P2 о недостаточном различии уровней устранён не полностью.

### P2 — незадействованные поля оставляют ошибки вне grading-векторов

- `middle-20-hard` принимает `mandatory`, но не читает его (`internal/content/solutions/middle-20-hard/main.go:3`). Если `returned=true`, функция всегда отвечает `unrouted`; текущий spec содержит только `mandatory=true, returned=true` и не определяет противоречивое сочетание `mandatory=false, returned=true` (`internal/grading/specs/middle-20-hard.json:10`). По уроку return трактуется в контексте mandatory публикации (`internal/content/data/middle-20.md:13`). Контракту нужно либо определить/отклонить невозможное сочетание, либо убрать лишний параметр; затем добавить private vector, который отличает реализацию с использованием mandatory от текущей.
- `middle-22-hard` принимает `elapsedSeconds`, но не использует его (`internal/content/solutions/middle-22-hard/main.go:3`). Все Hard-векторы задают нулевое время (`internal/grading/specs/middle-22-hard.json:10`), поэтому этот дефект не обнаруживается: например, при `available=2`, `refillPerSecond=2`, `elapsedSeconds=2`, `cost=5` ответ должен учитывать уже прошедшее пополнение. Также `cost > capacity` сейчас даёт конечное время ожидания, хотя bucket не может накопить такую сумму, а выражение `(deficit + refillPerSecond - 1)` может переполнить `int64`. Минимальное исправление: определить, является ли elapsed частью уже прошедшего времени, обработать недостижимый cost и безопасное округление вверх; добавить ненулевое время, cost выше capacity и near-MaxInt64 вектора.
