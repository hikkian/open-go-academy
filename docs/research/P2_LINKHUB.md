## Минимальная граница продукта

Сохранить учебный сценарий LinkHub: зарегистрированный пользователь создаёт/читает/изменяет/удаляет свои short links; redirect по slug публичен только для включённой ссылки; теги принадлежат пользователю, link-tag связи не позволяют ссылаться на чужие теги. Отдельные admin/role flows можно отложить: на первом вертикальном пути достаточно ролей `user` и `admin` с server-side проверкой. Владелец каждого ресурса определяется из аутентифицированной сессии, никогда из присланного `user_id`.

Минимальные маршруты:

| Метод и путь | Доступ |
|---|---|
| `POST /api/v1/auth/register`, `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/me` | публичная регистрация / текущая сессия |
| `GET /api/v1/links`, `POST /api/v1/links`, `GET /api/v1/links/{id}`, `PATCH /api/v1/links/{id}`, `DELETE /api/v1/links/{id}` | владелец; list имеет bounded pagination |
| `GET /api/v1/tags`, `POST /api/v1/tags`, `PATCH /api/v1/tags/{id}`, `DELETE /api/v1/tags/{id}` | владелец |
| `GET /{slug}` | redirect lookup; только `enabled`, валидированный slug, фиксированный `Location` из сохранённой URL |
| `/healthz` | только состояние процесса; без секретов/DSN |

Рекомендуемые учебные сущности: `users(id, email_normalized UNIQUE, password_hash, role, created_at)`; `sessions(token_hash PRIMARY KEY, user_id FK, expires_at, created_at)`; `links(id, owner_id FK, slug UNIQUE, target_url, enabled, created_at, updated_at)`; `tags(id, owner_id FK, name_normalized, UNIQUE(owner_id,name_normalized))`; `link_tags(link_id, tag_id, PRIMARY KEY(link_id,tag_id))`. Индексы минимум по `links(owner_id, created_at DESC)`, unique slug, session expiry и обеим сторонам join по потребности. Для ownership CRUD запрос должен атомарно включать owner (`WHERE id=$n AND owner_id=$m`) или проверять owner в транзакции; не делать отдельный insecure lookup, за которым следует mutate только по ID. Foreign keys/cascade выбирать явно и проверять миграциями.

Использовать SQL migrations в каталоге проекта, например `0001_init.up.sql` / `0001_init.down.sql`, применяемые детерминированно при старте тестовой fixture или отдельной командой. На первом вертикальном проекте допустим свой короткий versioned migration runner с таблицей schema version, транзакцией и advisory/startup lock; не вводить ORM и второй migration dependency без учебной необходимости. Raw SQL только параметризованный через pgx (`$1`, `$2`); идентификаторы таблиц/сортировки брать только из константного allowlist, никогда из JSON/query пользователя. Для create/update транзакционно записывать link и tag associations.

Не принимать абсолютные redirect URL как значение header напрямую из запроса; разбирать через `net/url`, ограничить схемы `http`/`https`, hostname/length, запретить CR/LF/control characters и формировать redirect только из сохранённой нормализованной записи. Для redirect endpoint не запрашивать target с сервера: это исключает SSRF-путь. Случайные slugs генерировать `crypto/rand`, проверять уникальность с ограниченным числом повторов, не полагаться на проверку наличия перед insert. Slugs не должны давать access control.

## Сессии, пароль и HTTP защита

- Сессия — opaque случайный token от `crypto/rand` с достаточной энтропией; хранить в БД только хеш токена (например SHA-256), cookie отдавать HttpOnly, SameSite=Lax/Strict, Path=/, без Domain, Secure при HTTPS. На login/regenerate менять token, ограничить срок жизни и logout отзывает серверную запись. OWASP рекомендует cookie-флаги и не хранить session/refresh credentials в Web Storage ([Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). При stateful browser cookie применять CSRF token и проверять Origin для изменяющих state запросов; SameSite — дополнительный слой, не единственная защита ([CSRF Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). `Secure` обязателен в HTTPS deployment; для HTTP loopback учебного режима поведение документировать отдельно.
- Нормализовать email один раз и enforce uniqueness в БД. В ответе регистрации не раскрывать, существует ли адрес, если поведение позволяет enumeration; login ошибки единообразны. Пароль не хранить/логировать в открытом виде. `crypto/pbkdf2.Key` требует выбрать/записать versioned параметры (hash, iterations, output length, random per-user salt); лимитировать длину до дорогого KDF, сравнивать derived bytes константным временем. Выполнить calibration benchmark до фиксации work factor. Альтернатива Argon2id требует pinned `golang.org/x/crypto` и калибровки memory/time budget. Не описывать ни один вариант как проверенный против конкретного offline cracking budget.
- Ограничивать тело JSON через `http.MaxBytesReader`, отвергать неизвестные поля/лишние JSON values, выставлять Content-Type, ясные status/error codes. Ограничить URL/slug/tag/email длины, нормализовать Unicode-политику и whitelists. Настроить `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, graceful shutdown; не логировать credentials, cookie, password, DSN и полные чувствительные target URLs. Structured logs `slog` с request ID, operation, status, latency.
- Вводить bounded pagination и фильтры, request/login/registration limits и ограниченный pool соединений. Для учебного local Compose лимит в памяти допустим; не выдавать его за защиту от распределённого злоупотребления или public deployment. Admin role проверять на сервере на каждом соответствующем endpoint. Ошибка доступа между пользователями возвращает одинаковую семантику not-found/forbidden, выбранную единообразно.

## Изоляция, запуск и экспорт

Этот API обслуживает LinkHub records; он никогда не компилирует и не исполняет отправленный пользовательский Go-код. Запуск/тест пользовательского Go-кода платформы остаётся в уже отделённом rootless worker с `network=none`, ограниченными ресурсами и fail-closed поведением из [SANDBOX_SECURITY.md](SANDBOX_SECURITY.md) и [D4](../MASTER_SPEC.md). Для P2 даются starter/reference, SQL и команды локальной разработки; проект можно экспортировать в Git-ready каталог/ZIP. Пользователь запускает API + PostgreSQL через local Docker/Podman Compose на своей машине. Нельзя передавать source/API-запросы в hosted service, монтировать runner/socket в API или выполнять `os/exec` с кодом ученика.

Compose должен содержать только приложение/DB при необходимости, локальный DB volume и healthcheck; postgres port по умолчанию не публиковать на все интерфейсы (для клиента host bind только loopback). Приложение не должно запускаться root внутри собственного сервиса, если будет добавлен image; PostgreSQL credentials и session secret подавать из локального ignored env file/secret mechanism, не коммитить sample реальные секреты. Не добавлять оплачиваемые зависимости. Точный OCI digest и platform записать в проектном lock/config после выбора архитектуры; официальная страница образа и Registry API выше проверены, сам образ не скачивался и локальная Compose-конфигурация пока не запускалась.

## Тест-план при реализации

### Режим A: stdlib-only unit/HTTP без БД

Отделить handlers от `LinkStore`/`UserStore` interfaces и покрыть маршруты `httptest` с fake store: method/path matching и 405; JSON success/error/oversize/unknown fields; validation таблицами; slug collision retries; redirect disabled/missing/enabled; handler не принимает owner ID из body/query; authentication/session invalid/expired/logout; CSRF/origin rejection. Проверить middleware chaining, panic recovery, request IDs и отсутствие password/token в captured logs. Этот режим запускается офлайн стандартной командой Go после установки зафиксированного toolchain и ничего не загружает. Fake store даёт изолированную проверку HTTP поведения, но не проверяет SQL, миграции или транзакции.

### Режим B: настоящая БД

Использовать временную PostgreSQL 18.6 из OCI через локальную rootless Podman/Docker Compose; данные только в временном project volume, случайный локальный порт/credentials, lifecycle гарантированно удаляет только созданную fixture. Создать DB, применить все migrations с пустой схемы, применить повторно/проверить версию, затем запустить интеграционные тесты на pgx и удалить fixture. Не использовать пользовательскую `.data/academy.db` платформы и не очищать существующие DB/volume. Компилятор/test worker остаётся отдельно и без сети. Тестовое приложение получает DB URL, но тестируемый Go user code его не получает.

Для reproducible offline CI заранее закешировать или vendoring разрешённые точные Go module зависимости и образ PostgreSQL; запускать Go build/test с `GOPROXY=off`, `GOSUMDB=off`, `GOTOOLCHAIN=local`, отключённой сетью для runner/test code и использовать лишь локально доступные content-addressed modules/image. Отдельный dependency-update шаг в среде с разрешённым доступом обновляет `go.mod`/`go.sum`/OCI digest по review. Если локальные cache/image отсутствуют, корректный результат — режим A проходит, режим B unavailable/skipped с явной причиной; не подменять БД fake-реализацией и не заявлять интеграционную проверку.

### Обязательные security/acceptance cases

1. User A не может list/get/update/delete link User B по ID; не может attach B's tag; подмена `owner_id` в create/update игнорируется/отвергается. Параллельные CRUD/rename не создают ownership race.
2. SQL injection payloads в email, slug, query filters, tags и target URL остаются данными; проверять попытки изменения WHERE/order/filter, quoting и DB error leakage. Для ORDER BY — только enum→константа.
3. Slug duplicate concurrent inserts: unique index корректно разрешает одну запись и повтор с лимитом возвращает контролируемую ошибку. Ограничения и FK подтверждены реальным PostgreSQL, не только fake store.
4. Auth: неправильный пароль одинаково неуспешен для отсутствующей/существующей учётки; токены случайны, hashed at rest, logout/revoke/expiry; session fixation regression, password/body/log redaction, bounded request/KDF abuse, rate-limit backoff. Derived password hash constant-time comparison.
5. CSRF: отсутствующий/неверный CSRF token и чужой Origin блокируют cookie-auth mutations; безопасные GET/HEAD не меняют состояние. Cookie attributes проверяются HTTP тестом для HTTPS configuration.
6. Redirect: несуществующий/disabled slug не redirect; валидный возвращает ожидаемый 302/307; CRLF, control chars, `javascript:`, `data:`, malformed URLs и длинные поля отвергаются; endpoint не делает outbound network request.
7. Migrations на чистой БД и upgrade path с предыдущей fixture; rollback/foreign-key/indexes/unique constraints и transaction rollback при ошибке tag association. Проверить limit/timeout/shutdown без утечки goroutine/connections.
8. Negative scope test: API не создаёт subprocess и не имеет runner/Podman/Docker socket dependency; submit/save user source остаётся текстом. Единственная execution boundary проекта — отдельный worker по существующим D2 правилам.

Проверяемые источники использованы для выбора кандидатов; приложение, Compose, миграции, KDF parameters, архитектурная совместимость на нескольких ОС и тесты P2 в этой исследовательской задаче не реализовывались и не запускались.
