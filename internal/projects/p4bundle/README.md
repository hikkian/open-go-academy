# P4 — ScaleLab: измеряемая оптимизация

**Уровень:** Middle+ · **Go:** 1.27.2 · **Зависимости:** только стандартная библиотека.

## Задача

Сервис получает поток событий с `service`, `region` и `bytes`. Для отчёта нужно посчитать количество событий и суммарный объём по каждой паре `(service, region)`. В проекте есть заведомо дорогая, но корректная реализация и независимая reference-реализация. Ваша задача — доказать стоимость исходного решения, найти её профилем и оптимизировать без изменения результата. Рост скорости сам по себе не является целью: решение должно соблюдать заданный бюджет памяти, корректность и явно сформулированный SLO.

Это учебный лабораторный стенд, а не продакшен-сервис и не подтверждение производственной готовности.

## Предварительные знания и словарь

Перед началом уверенно пользуйтесь функциями, структурами, срезами, map, указателями, ошибками, пакетами и тестами Go; понимайте big-O, хеш-таблицу, аллокацию/сборку мусора, `context` и конкурентный доступ. Также нужны базовые знания HTTP-сервиса и метрик latency/throughput. Если эти темы незнакомы, сначала пройдите Middle и P3 TaskFlow.

- **Benchmark (микротест производительности):** повторяемое измерение операции через `testing.B`; результат зависит от среды.
- **ns/op:** наносекунды на одну операцию; **B/op:** байты, выделенные на операцию; **allocs/op:** число аллокаций.
- **Профиль (profile):** выборка CPU, памяти или блокировок для объяснения затрат. Профиль указывает кандидатов, но не доказывает причину сам по себе.
- **pprof:** инструменты Go для чтения и визуализации профилей CPU/heap.
- **Heap/inuse_space:** удерживаемая память в момент снимка; **alloc_space:** накопленные выделения. Это разные вопросы.
- **Throughput:** обработанные запросы/события в единицу времени. **Latency:** время ответа; p95 — порог, ниже которого укладываются 95% наблюдений.
- **SLO:** целевой уровень сервиса, например p95 ≤ 40 мс при 2 000 запросах/с и ошибках < 0,1%. Это цель сценария, не обещание данной программы.
- **Capacity (ёмкость):** нагрузка, которую система выдерживает при заданных SLO и ресурсном бюджете.
- **Headroom (запас):** резерв мощности на пик/отказы. **Backpressure (обратное давление):** ограничение входящего потока, когда потребитель не успевает.
- **Amdahl's law (закон Амдала):** ускорение ограничено долей времени, на которую реально влияет оптимизация.
- **Fault injection (внесение отказа):** контролируемое моделирование таймаута, перегрузки или потери зависимости.

## Артефакты и ограничения

- `starter/`: компилируемый учебный каркас с сохранённым корректным baseline; измерительный протокол и оптимизация остаются ученику.
- `reference/`: самостоятельное решение, эталонные тесты и benchmark baseline/optimized.
- Работайте на Go 1.27.2, без сторонних пакетов. Не переносите benchmark-цифры между машинами как обещание.
- Нельзя менять семантику, отбрасывать данные, ограничивать вход без явно описанной политики, либо сравнивать разные наборы данных.

## Этапы и checkpoints

1. **Зафиксировать гипотезу.** Укажите ожидаемый узкий участок и почему. Не оптимизируйте «на глаз».
2. **Проверить контракт.** Реализуйте/сохраните тесты на пустой вход, повторные ключи, пустые строки ключей, нулевые байты, большие значения и переполнение `uint64` (должно возвращаться понятное `error`, без частичного результата).
3. **Снять baseline.** Запустите benchmark не менее 5 раз (`-count=5`), сохраните полную команду, Go/OS/архитектуру/CPU, параметры генератора и сырые строки. Используйте одинаковые данные для обоих вариантов.
4. **Найти причину.** Снимите CPU и heap профили, исследуйте верхние функции и аллокации через `go tool pprof`. Сопоставьте их с кодом и тестируйте одну гипотезу за раз.
5. **Оптимизировать.** Измените представление/алгоритм, оставьте сравнение baseline. Объясните почему изменение сокращает конкретную работу и какие у него ограничения.
6. **Проверить after.** Запустите те же тесты и benchmark на тех же данных. Сравните ns/op, B/op, allocs/op; примените `benchstat`, если он у вас установлен, но не добавляйте зависимость в проект.
7. **Перевести в capacity/SLO.** Для заданного профиля нагрузки посчитайте необходимую обработку, запас и бюджет ресурсов. Отдельно укажите, почему микробенчмарк не равен end-to-end SLO.
8. **Fault/edge review.** Обсудите burst, пустой/очень большой batch, перекошенные ключи, переполнение, отмену запроса, давление памяти, GC, холодный запуск и деградацию при отключённом downstream. Не внедряйте конкуренцию, если она не нужна или не измерена.
9. **Собрать evidence package.** Сдайте diff, тесты, сырые результаты, профили/текстовый разбор, расчёты, ограничения и короткий postmortem «что ожидали / что увидели / что изменили».

## Воспроизводимые команды

Из `reference/`:

```sh
go version
go test -count=1 ./...
go vet ./...
go test -run '^$' -bench 'BenchmarkAggregate' -benchmem -count=5 ./...
go test -run '^$' -bench 'BenchmarkAggregateBaseline' -cpuprofile cpu.out -memprofile mem.out
go tool pprof -top cpu.out
go tool pprof -top -alloc_space mem.out
go tool pprof -top -inuse_space mem.out
```

Профили создавайте отдельными запусками для baseline и optimized, называйте их однозначно и не коммитьте бинарные профили без необходимости. Для сравнения внешнего HTTP SLO проектируйте нагрузочный эксперимент отдельно: прогрев, фиксированная длительность, контролируемая concurrency, latency histogram и ошибки. Не выводите p95 из `ns/op`.

## Расчёт capacity — шаблон

Пусть `R` — целевой запросов/с, `E` — событий в запросе, `T` — измеренная стоимость обработки события (с), `C` — число доступных CPU-ядер, `U` — допустимая доля CPU (например 0,65), `H` — коэффициент запаса (например 1,3). Оценка CPU-ядер: `cores ≈ R × E × T × H / U`. Это только грубая нижняя оценка: учтите сериализацию, сеть, БД, ожидание, GC, contention и хвостовую latency. Сверьте с нагрузочным тестом и проверьте деградацию при отказе зависимости.

**Сценарий для своего отчёта:** R=2 000 req/s, E=100 событий/request, p95 цель=40ms, error-rate <0,1%, CPU budget=65%, headroom=30%, память ≤512 MiB. Подставьте полученное `ns/op`, объясните допущения, затем признайте ограничения пересчёта. Это учебное целевое условие, не измеренный результат.

## Evidence package (заполнить)

1. Контракт/версия кода и точный commit или архив.
2. `go version`, `go env GOOS GOARCH`, модель CPU, ОС, thermal/power context.
3. Полные команды, seed и параметры данных, минимум пять сырых baseline/after строк.
4. Таблица ns/op, B/op, allocs/op и относительное изменение; тесты до/после.
5. Профили CPU и alloc_space/inuse_space с интерпретацией и проверяемой ссылкой на код.
6. Capacity-расчёт, SLO, headroom, результаты fault/edge сценариев.
7. Компромиссы, что не измерено, риски переноса в production, incident/postmortem заметка.

### Контрольный benchmark этого reference

Зафиксированный локальный прогон: Go 1.27.2 linux/amd64, AMD Ryzen 5 5600 (6 ядер/12 потоков), Linux `7.2.10-200.fc44.x86_64`. Команда: `go test -run '^$' -bench 'BenchmarkAggregate' -benchmem -count=5 ./...` (из `reference/`). Набор детерминированный: 4 096 событий, 64 сервиса × 16 регионов, seed `0x51ca1ab`. Перед запуском таймера benchmark сравнивает результаты baseline и optimized на том же наборе. В повторном пятисерийном прогоне медиана baseline — 728 589 ns/op, 389 937 B/op, 12 310 allocs/op; optimized — 440 141 ns/op, 337 646 B/op, 3 013 allocs/op. Это наблюдение только для данной машины/версии кода. Сырые строки измерения сохранены в `reference/benchmark-results.txt`; они не гарантируют ускорения в другой среде и не доказывают end-to-end SLO. Профильные команды выше нужно выполнить самостоятельно; профиль не прикладывается как будто он был получен.

## Запуск и сдача

```sh
cd starter
go test ./...
go vet ./...
```

Для защиты объясните выбор метрики, как убедились в одинаковости результата, какое наблюдение подтвердило узкое место, что произошло с памятью и как оптимизация влияет на tail latency/capacity. Автоматические проверки не сертифицируют production readiness, реальные SLO или инженерную должность.

Проверка отправки выполняет доверенные Go-тесты рядом с вашим пакетом. Поэтому для действий «Запустить тесты» и «Проверить проект» пакет не должен объявлять `init`/`TestMain`, а пользовательские тесты не должны вызывать `os.Exit` или `runtime.Goexit`: такие process hooks могут завершить тестовый процесс до запуска проверок. Обычная CLI-точка входа `main` может использовать `os.Exit` для кода возврата.
