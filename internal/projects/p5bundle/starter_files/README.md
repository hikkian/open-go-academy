# P5 starter — сначала решение, затем прототип

Это неполный учебный пакет. Go-код должен собираться с Go 1.27.2, но методы `Queue` намеренно возвращают `ErrNotImplemented`. Это не готовый продукт и не обход задания: ваша работа — выбрать один риск из архитектуры, сформулировать его инвариант, реализовать минимальный эксперимент и показать, что он ломается без вашего контроля.

## Шаг 1: снять неопределённость

Заполните `design/requirements.md`. Не превращайте неизвестные значения заказчика в «факты». Для каждого допущения укажите владельца решения, опасность ошибки и способ/дату проверки. Выведите из требований несколько проверяемых инвариантов.

## Шаг 2: описать систему и выбор

Подготовьте диаграмму и заполните шаблоны ADR в `design/`. Включите синхронный путь приёма, durable commit, worker, внешнее действие, повтор/отказ и tenant trust boundary. Для каждого решения сравните жизнеспособные альтернативы и условия пересмотра. Добавьте модель отказов/угроз, расчёт нагрузки с единицами, SLI/SLO как гипотезы, alert/runbook, backup/restore, rollout/rollback, incident plan и учебный postmortem.

## Шаг 3: проверяемый риск

Стартовая гипотеза прототипа: доставка может быть повторной, lease worker может истечь во время паузы, а старый worker может попытаться подтвердить событие после нового владельца. Реализуйте атомарное идемпотентное добавление, конкурентную выдачу, повторную выдачу после истечения lease, возрастающий fence token и отказ stale `Complete`. Зафиксируйте время в аргументах — тесты не должны зависеть от `time.Sleep`.

Можно выбрать другой архитектурный риск, если он глубже соответствует вашим ADR; тогда перепишите контракт и тесты. Не называйте in-memory mutex эквивалентом транзакции БД, не обещайте exactly-once для произвольного внешнего эффекта и не выводите из prototype production SLO.

## Шаг 4: завершение

Добавьте unit-тесты на нормальный путь, дубли, конкурентность, сбой и повторное восстановление; запускайте `go test -race ./...`, `go vet ./...`, `go build ./...`. Документируйте команды, Go version и вывод. Подготовьте краткий postmortem сценария из вашей модели. Затем проведите защиту: почему выбраны эти альтернативы, что изменится при новом ограничении, как восстанавливается система.

Для Senior rank требуется отдельная независимая аутентифицированная human review точной версии артефактов и устная/синхронная защита. Самооценка и оценка ИИ не принимаются как решение reviewer. Рубрика и ограничения — в [`../rubric.md`](../rubric.md) и [`../threat-model.md`](../threat-model.md).
