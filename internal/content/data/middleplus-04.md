# CPU profile и поиск горячего пути

## Что ты сделаешь

Ты научишься читать CPU-профиль Go как то, чем он является, — выборку стеков под конкретной нагрузкой, а не полный учёт затрат приложения. Разберёшь разницу между `flat` и `cum`, поймёшь, почему широкий блок на flame graph не равен медленному запросу, и как профиль связан с benchmark из прошлых уроков. Три функции урока — `ProfileShare`, `ValidProfileCounts`, `HotPathCandidate` — закрепляют арифметику выборки: доля сэмплов, непротиворечивость счётчиков и порог, после которого функцию стоит исследовать.

## Профиль — это выборка стеков

CPU-профиль собирают `runtime/pprof` или `go test -cpuprofile`, а читают через `go tool pprof`. Сборщик периодически, примерно сто раз в секунду, записывает текущий стек вызовов каждого работающего потока. Каждая запись — сэмпл (sample). Профиль не фиксирует каждое машинное действие: очень короткие события могут не попасть ни в один сэмпл, а горячий участок оценивается статистически — по доле сэмплов, в которых он встретился.

Отсюда два следствия. Отсутствие функции в профиле не означает нулевую стоимость. И профиль относится только к тому времени и той нагрузке, под которой его собрали: профиль простаивающего сервера не объясняет насыщение под трафиком.

```go group=share mode=run
package main

import "fmt"

func share(sample, total int) int {
    if total <= 0 || sample < 0 || sample > total {
        return -1
    }
    return sample * 100 / total
}

func main() {
    total := 4000
    fmt.Println("parse:", share(1000, total), "%")
    fmt.Println("gc:", share(120, total), "%")
    fmt.Println("ошибка:", share(5000, total))
}
```

Вывод:

```text
parse: 25 %
gc: 3 %
ошибка: -1
```

Доля сэмплов — условная оценка доли процессорного времени, а не точная доля wall-clock: ожидание ввода-вывода в CPU-профиль не попадает вовсе.

> **Важно.** Сначала убедись, что это именно CPU-профиль, что он снят с того бинарника и под той нагрузкой, о которой ты задаёшь вопрос. Иначе дальнейший разбор — анализ чужого эксперимента.

## flat и cum — две разные цифры

У каждого узла в `pprof -top` две стоимости. `flat` — сэмплы, в которых функция была на вершине стека, то есть выполняла собственный код. `cum` (cumulative) — сэмплы, где она была где угодно в стеке: собственная работа плюс всё, что она вызвала. У обработчика запроса `cum` почти всегда велик — он вызывает всё остальное; это не повод его переписывать.

```go group=topline mode=run
package main

import (
    "fmt"
    "strings"
)

func main() {
    rows := []string{
        "1000 25.00% 25.00% 1000 25.00% parse",
        "40 1.00% 26.00% 3600 90.00% handleRequest",
        "600 15.00% 41.00% 600 15.00% strconv.ParseInt",
    }
    for _, row := range rows {
        f := strings.Fields(row)
        fmt.Printf("%-18s flat=%-5s cum=%s\n", f[5], f[0], f[3])
    }
}
```

Вывод:

```text
parse              flat=1000  cum=1000
handleRequest      flat=40    cum=3600
strconv.ParseInt   flat=600   cum=600
```

`handleRequest` держит 90 % сэмплов по `cum`, но собственной работы у него один процент: дорогое — внизу стека. Ищи нижний общий участок нескольких путей и сопоставляй его с кодом и гипотезой. Широкий блок на flame graph отражает накопленные сэмплы, а не задержку одного запроса: он может быть суммой миллиона дешёвых вызовов.

> **Типичная ошибка.** Переписать функцию с большим `cum`, не посмотрев на `flat` её потомков. Стоимость просто переедет в новое место.

## Как читать вывод pprof -top

Команда `go tool pprof -top cpu.out` печатает таблицу из пяти чисел на строку: `flat`, `flat%`, `sum%`, `cum`, `cum%`. Первые два — собственная стоимость и её доля; `sum%` — накопленная доля строк сверху до текущей, по ней видно, сколько функций объясняют, скажем, 80 % сэмплов; последние два — накопленная стоимость и её доля. Строки отсортированы по `flat`, поэтому обработчики и `main` обычно внизу, хотя их `cum%` близок к ста.

Полезные ключи: `-cum` сортирует по накопленной стоимости и показывает структуру вызовов сверху вниз; `-focus=имя` оставляет только пути через функцию; `-list имя` раскладывает сэмплы по строкам исходника. Начинай с `-top` без ключей, чтобы увидеть собственные стоимости, затем переходи к `-list` для лидера: часто дорогой оказывается одна строка — преобразование, выделение, копирование.

## Нагрузка, под которой снимают профиль

Профиль отвечает на вопрос «где уходит CPU под этой нагрузкой». Поэтому нагрузка должна быть той самой, из вопроса: тот же сценарий, что в benchmark, или воспроизводимая нагрузка на сервис с записанными параметрами. Записывай команду, период сбора, частоту сэмплирования и параметры процесса. Повышение частоты сэмплирования увеличивает стоимость наблюдения и может сделать профиль менее репрезентативным.

Сбор профиля сам меняет расходы. Поэтому профильный прогон не используют как финальную цифру скорости: профиль находит кандидата, а подтверждает эффект обычное сопоставимое сравнение benchmark с повторами. После изменения повтори и benchmark, и профиль, проверь корректность и посмотри, не стало ли хуже на другой нагрузке.

## Когда CPU-профиль молчит

Если `top` показывает `runtime.mallocgc` или сборщик мусора, это подсказка проверить аллокации и heap-профиль (следующий урок), а не отключать GC вслепую. Если программа ждёт — базу, сеть, блокировку, — CPU-профиль покажет мало активности, потому что ожидание не тратит процессор; тогда нужен другой сигнал: block profile, mutex profile, trace или распределение времени запроса. CPU, mutex и block профили отвечают на разные вопросы и по-разному нагружают систему; не смешивай их выводы.

```go group=hotspot mode=run
package main

import "fmt"

func candidate(flat, cumulative, total, minPercent int) bool {
    if total <= 0 || flat < 0 || cumulative < flat || cumulative > total || minPercent < 0 || minPercent > 100 {
        return false
    }
    threshold := (total/100)*minPercent + ((total%100)*minPercent+99)/100
    return flat >= threshold
}

func main() {
    fmt.Println(candidate(60, 70, 100, 50), candidate(20, 60, 100, 50), candidate(5, 20, 100, 50))
    fmt.Println(candidate(1, 1, 3, 34))
}
```

Вывод:

```text
true false false
false
```

Вторая строка показывает округление порога вверх: 34 % от трёх сэмплов — это 1,02, значит нужно два сэмпла, и одного недостаточно. Порог считается без дробной арифметики: целая часть от `total/100`, умноженная на процент, плюс остаток, округлённый вверх. Кандидат — это функция, которую стоит исследовать на той же нагрузке, а не приказ оптимизировать.

> **Зачем.** Запиши заранее, какой профиль мог бы опровергнуть гипотезу. Если никакой — это не гипотеза, а предпочтение.

## Следующий различающий эксперимент

Профиль показывает, где уходит время, но не почему. Между наблюдением и правкой стоит ещё один шаг — эксперимент, который отличает одно объяснение от другого, и его стоит записать так же тщательно, как команду сбора профиля.

Дорогая функция в профиле — это алгоритм, число вызовов, размер входа или конкуренция? Чтобы различить, считай вызовы или подбери контрольный вход, меняющий только одну предполагаемую причину: удвой размер входа при том же числе вызовов, или число вызовов при том же размере. Удаление горячего узла может лишь перенести работу: после изменения сравни не только `flat` узла, но и суммарный `cum` пути. Сохраняй профили «до» и «после» с одинаковым типом и сценарием; сравнение разных типов профилей или разных нагрузок — не сравнение. Если после правки доля лидера упала, а общее время benchmark не изменилось, работа переехала, а не исчезла, — и это тоже результат, который стоит записать.

## Типичные ошибки

- Профиль простаивающего процесса как объяснение проблем под нагрузкой.
- `cum` обработчика как повод переписать обработчик, а не найти дорогого потомка.
- Ширина блока flame graph как задержка запроса: это накопленные сэмплы, возможно от миллиона дешёвых вызовов.
- Профильный прогон как итоговое число скорости: сбор профиля меняет расходы.
- CPU-профиль для программы, которая ждёт: нужен block, mutex профиль или trace.
- Смешение CPU-, heap- и block-профилей в один вывод: у них разные вопросы и разная стоимость.

## Самостоятельная лаборатория

Сними CPU-профиль с benchmark из второго урока: `go test -run '^$' -bench=Parse -cpuprofile=cpu.out`, затем `go tool pprof -top cpu.out`. Выпиши три верхние строки по `flat` и три по `cum`, укажи для каждой, собственная это работа или вызванная. Посчитай долю сэмплов лидера по `flat` функцией `share` из примера и реши по порогу 20 %, кандидат ли это. Затем удвой размер входа, повтори профиль и запиши, какие узлы изменили долю, — это и есть различающий эксперимент. Отдельно отметь, сколько сэмплов собрано всего: при коротком прогоне их может быть меньше тысячи, и доли в один-два процента тогда ничего не значат. Удали `cpu.out` после работы.

## Если что-то пошло не так

- `-1` вместо `0` для `sample = 0` → ноль сэмплов — допустимое значение, проверка должна быть `sample < 0`, а не `<= 0`.
- `25` для `sample > total` → проверка `sample > total` отсутствует.
- `true` при `flat > cumulative` в задании 2 → `cumulative >= flat` пропущено: собственная работа не может превышать накопленную.
- Порог считается с дробями → `float` не нужен: целая часть плюс остаток с округлением вверх, как в примере.
- `import … is not allowed` → импорты запрещены: только целочисленная арифметика.

## Практика

Три функции без `main` и печати; среда показывает результаты числами и `bool`.

### Задание 1 · Easy: вычисли долю CPU samples

**Цель.** Вернуть целочисленный процент `sample · 100 / total` при `0 < total ≤ MaxInt/100` и `0 ≤ sample ≤ total`; иначе `−1`.

**Ожидаемый вывод** — для `(sample=25, total=100)`:

```text
25
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func ProfileShare(sample, total int) int`. Импорты запрещены.
2. Верни `-1`, если `total <= 0`, `total > int(^uint(0)>>1)/100`, `sample < 0` или `sample > total`.
3. Иначе верни `sample * 100 / total` — целочисленное деление округляет вниз.
4. «Запустить», «Проверить» — закрытые примеры: `(0, 10)` → `0`, `(11, 10)` → `-1`.

**Как проверить себя.** Ноль сэмплов — ноль процентов, не ошибка; сэмплов больше общего числа быть не может; верхняя граница `total` защищает умножение от переполнения.

**Если не принято.**
- Красный закрытый пример `(0, 10)` → проверка `sample <= 0` вместо `< 0`.
- Красный `(11, 10)` → нет проверки `sample > total`.

> **Подсказка.** `int(^uint(0) >> 1)` — наибольшее значение `int` без импорта `math`.

### Задание 2 · Medium: проверь profile counts

**Цель.** Вернуть `true`, если `total > 0` и `0 ≤ flat ≤ cumulative ≤ total`.

**Ожидаемый вывод** — для `(flat=10, cumulative=40, total=100)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ValidProfileCounts(flat, cumulative, total int) bool`. Импорты запрещены.
2. Верни `total > 0 && flat >= 0 && cumulative >= flat && cumulative <= total`.
3. «Запустить», «Проверить» — закрытые примеры: `flat > cumulative` → `false`, `total = 0` → `false`.

**Как проверить себя.** Собственная стоимость не превышает накопленную, накопленная — общее число сэмплов; это модель с одним знаменателем, у реального pprof бывают разные типы сэмплов.

**Если не принято.**
- `true` для `(50, 40, 100)` → пропущено `cumulative >= flat`.
- `true` для `(1, 1, 0)` → `total > 0` не проверен.

> **Подсказка.** Четыре сравнения через `&&`, порядок произвольный.

### Задание 3 · Hard: выбери hotspot по flat threshold

**Цель.** Вернуть `true`, если счётчики согласованы и доля `flat` не меньше `minPercent` процентов от `total`, с порогом, округлённым вверх и без дробной арифметики.

**Ожидаемый вывод** — для `(flat=60, cumulative=70, total=100, minPercent=50)`:

```text
true
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func HotPathCandidate(flat, cumulative, total, minPercent int) bool`. Импорты запрещены.
2. Верни `false`, если счётчики несогласованы (как в задании 2) или `minPercent` вне `0…100`.
3. Порог: `(total/100)*minPercent + ((total%100)*minPercent + 99)/100`.
4. Верни `flat >= threshold`. «Запустить», «Проверить» — закрытые примеры: `(5, 20, 100, 50)` → `false`, `(20, 60, 100, 50)` → `false`.

**Как проверить себя.** Решает `flat`, не `cumulative`: функция с большим `cum` и маленьким `flat` — не кандидат; при `total = 3` и `minPercent = 34` порог равен двум сэмплам.

**Если не принято.**
- `true` для `(20, 60, 100, 50)` → сравнивается `cumulative` вместо `flat`.
- Разные ответы на границе → порог посчитан с округлением вниз или через `float`.
- `true` при `minPercent = 150` → диапазон процента не проверен.

> **Подсказка.** Кандидат — приглашение исследовать на той же нагрузке, не вердикт об оптимизации.

## Итог

- CPU-профиль — выборка стеков под конкретной нагрузкой; доля сэмплов — оценка, короткие события могут не попасть.
- `flat` — собственная работа, `cum` — вместе с потомками; дорогое обычно внизу стека, а не в обработчике.
- Профиль находит кандидата; подтверждают эффект benchmark с повторами и различающий эксперимент на той же нагрузке.
