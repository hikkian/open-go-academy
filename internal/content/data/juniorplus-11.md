## Зачем нужны транзакции

Транзакция (transaction, транзакция) объединяет несколько SQL команд в одну логическую операцию. Если короткая ссылка создаётся вместе с записью аудита, успех только половины может оставить несогласованное состояние. `BEGIN` начинает работу, `COMMIT` фиксирует результат, `ROLLBACK` отменяет изменения, которые ещё не зафиксированы. Это даёт атомарность для выбранной группы команд, но не исправляет ошибочную бизнес-логику.

Граница должна соответствовать одному действию пользователя. Не открывайте транзакцию до чтения HTTP тела или сетевого вызова: соединение и блокировки будут удерживаться дольше. Не помещайте внутри транзакции обращение к внешнему сервису, у которого нет общего протокола commit. Подготовьте вход, откройте транзакцию, выполните связанные изменения, завершите или отмените её как можно короче.

В Go транзакция — ресурс с обязательным решением. После `Begin` следует гарантировать `Rollback` на раннем выходе, а явный `Commit` выполняется только после успеха всех операций. `defer tx.Rollback(ctx)` часто служит страховкой: после commit дополнительный rollback вернёт ошибку «уже завершено», которую в этом пути можно игнорировать. Важно использовать корректный context и не терять первичную ошибку.

## Ошибки, гонки и ограничения

Constraint должен защищать инвариант независимо от предварительных запросов. Например, уникальность slug не следует реализовывать только как «сначала SELECT, затем INSERT»: две транзакции могут одновременно пройти SELECT. Пусть UNIQUE ограничение решит, кто победит. Приложение преобразует SQLSTATE конфликта в стабильную ошибку API.

Уровень изоляции (isolation) определяет, какие параллельные изменения видит транзакция и от каких аномалий защищает база. Начинающему не нужно угадывать уровень по названию. Нужно распознать, что два независимых запроса могут пересечься, определить инвариант и позволить базе его защитить. При serialization failure сервер сообщает, что одну транзакцию нужно повторить целиком. Retry возможен только с ограничением попыток и повторным выполнением транзакционной операции; нельзя повторять отдельную случайную команду после неизвестного частичного внешнего эффекта.

Deadlock — цикл ожидания блокировок. PostgreSQL прерывает одну сторону, чтобы система могла продолжить. Упорядочивание действий и короткие транзакции уменьшают риск, но не устраняют его во всех системах. При повторе deadlock должна повторяться вся безопасная транзакция, а не операция с отправленным письмом или списанием у стороннего провайдера.

## Миграции как история схемы

Миграция (migration) — версионированное изменение схемы, которое воспроизводится на другой машине. Не редактируйте уже применённый файл так, будто его никто не запускал: разные базы тогда будут иметь одинаковую версию с разным содержимым. Добавьте новый номер/идентификатор, порядок применения, ожидаемое изменение и обратный шаг, если он безопасен.

Проверка на пустой базе отвечает на вопрос, может ли новый разработчик получить нужную схему с нуля. Проверка старой схемы отвечает на вопрос, применима ли новая версия к уже существующим данным. Это две разные проверки. Для опасного изменения сначала планируют совместимую последовательность (добавить поле, писать оба формата, перенести данные, затем убрать старое), а не удаляют рабочую колонку одним шагом.

Таблица `schema_migrations` хранит применённые версии. Два процесса, стартовавших одновременно, не должны применить одну схему хаотично. В P2 reference миграция берёт advisory lock, применяет SQL и запись о версии в одной транзакции. Это конкретный учебный пример, а не универсальный migration framework. Откат `down` способен уничтожить данные; запускать его разрешено только на disposable проектной базе.

### Разбор кода и упражнений

В Go пример с небольшой in-memory моделью показывает границу между подготовкой операций и успешной фиксацией. Он компилируется на стандартной библиотеке и не притворяется транзакцией PostgreSQL. Задача Easy определяет, когда ещё можно просить rollback. Medium проверяет allowlist версии. Hard разрешает лишь два retryable SQLSTATE. Сами функции не создают транзакции, не доказывают atomicity и не подтверждают реальное применение файлов миграций.

SQL demonstration создаёт временные таблицы и две связанные записи внутри транзакции. После `ROLLBACK` проверяется, что временная структура исчезла. Этот fenced-блок выполняется в одноразовой PostgreSQL при проверке материала. В учебном приложении откройте «Проекты» → P2 LinkHub, поместите эквивалент в проектный migration/query и используйте P2 tests/verification: отдельный project worker запускает Go и интеграционные проверки с временной базой; он не принимает SQL-блок как standalone input.

### Практическая процедура

1. Сформулируйте инвариант одной фразой: например, «ссылка и запись аудита появляются вместе».
2. Укажите, какие запросы входят в транзакцию, а какие подготовлены заранее.
3. Определите, что делает код при ошибке каждого шага.
4. Убедитесь, что uniqueness/FK/CHECK закреплены в базе.
5. Примените миграции к пустой disposable схеме и повторите команду второй раз.
6. Проверьте версионирование и фиксируйте отказ, а не проглатывайте его.

`COMMIT` — момент решения, а не обещание, что пользователь получил HTTP ответ. Соединение может оборваться после фиксации, и клиент не узнает, завершилась ли операция. Это причина проектировать API с безопасной повторяемостью там, где это требуется, и не пытаться компенсировать неопределённость простым «повтори всё».

Перед следующим уроком нарисуйте путь: миграция создаёт ограничения, транзакция объединяет изменения, repository вызывает запросы, context ограничивает их срок. Любое из этих звеньев может завершиться ошибкой, но публичная система должна сообщать безопасную категорию и сохранять диагностическую причину внутри.


## Три запускаемых Go-примера

### Transaction Model

```go group=transaction-model mode=run
package main

import "fmt"

type Tx struct { committed bool; failed bool }
func (tx Tx) NeedsRollback() bool { return tx.failed && !tx.committed }
func main() { fmt.Println((Tx{failed:true}).NeedsRollback(), (Tx{committed:true,failed:true}).NeedsRollback()) }
```

Этот пример закончен: `package main`, imports и `main` входят в блок. Запустите его обычным runner главы, затем измените один вход. В нём нет подключения к PostgreSQL; смысл примера — локальный контракт на границе с будущим запросом. Сравните вывод с объяснением выше и сформулируйте, чего этот эксперимент не доказывает.

## SQL-практика для P2 worker

Атомарность пары изменений. Следующий блок самодостаточен: все таблицы временные, входные строки заданы прямо, а изменения отменяются. Его следует отправлять SQL worker в проектном рабочем месте P2; обычный Go function runner не подключает базу и не выполняет этот блок. Здесь нет команд управления сервером, файловой системы или роли.

```sql
BEGIN;
CREATE TEMP TABLE demo_links(id integer PRIMARY KEY, slug text UNIQUE);
CREATE TEMP TABLE demo_audit(link_id integer REFERENCES demo_links(id), action text NOT NULL);
INSERT INTO demo_links VALUES (1, 'docs');
INSERT INTO demo_audit VALUES (1, 'created');
SELECT l.slug, a.action FROM demo_links l JOIN demo_audit a ON a.link_id = l.id;
ROLLBACK;
SELECT to_regclass('pg_temp.demo_links') IS NULL AS rolled_back;
```

Предскажите вывод каждой команды, затем измените одно условие `WHERE` или JOIN и проверьте результат в disposable PostgreSQL, используя аналогичный запрос в P2 repository/migration. Если project worker недоступен, разберите блок как текст; не переносите его в общую базу.

## Практика E / M / H

- **Easy: Реши, нужна ли отмена.** Верни true, когда операция провалилась до commit; после committed rollback уже не отменяет зафиксированные изменения. Функция моделирует решение, но не выполняет транзакцию.
- **Medium: Проверь версию миграции.** Разреши только точный идентификатор 0001_init или 0002_link_index. Пустая строка и неизвестные версии запрещены. Реальная система отдельно хранит применённые миграции и сериализует конкурентный запуск.
- **Hard: Не повторяй рискованную операцию без причины.** true только для SQLSTATE 40001 (serialization_failure) и 40P01 (deadlock_detected). Retry должен повторять целиком идемпотентную/транзакционную работу ограниченное число раз с новой транзакцией и тем же deadline; прочие ошибки не повторяй автоматически.

Три упражнения проверяются детерминированными примерами функции Go. Ни одно не запускает PostgreSQL, не проверяет план запроса и не доказывает навык написания исполняемого SQL. Самостоятельная практика с запросами — в P2 workspace: перенесите SQL в проектный файл и проверяйте через Go integration tests и project verification с disposable DB. В каждом упражнении сначала запишите ожидаемый результат для стандартного и граничного входа, затем добавьте минимальную проверку. Не маскируйте ошибку пустым значением, если контракт требует отдельную категорию.

## Типичные ошибки и самостоятельная диагностика

- Транзакция оставлена открытой на сетевое ожидание. Перенесите внешние операции за границу DB транзакции.
- После ошибки одной команды приложение всё равно фиксирует другую. Все связанные изменения должны иметь один commit point.
- Ретраится только последняя SQL команда. Для serialization/deadlock перезапускайте безопасный цельный блок в новой транзакции.
- Файл уже применённой миграции переписан. Добавьте новую версию и проверьте upgrade path на старой схеме.

При отладке записывайте вход, ожидаемую категорию, фактический результат и состояние disposable базы. Не сохраняйте DSN, токен, cookie или содержимое реального пользовательского payload в журнал примера. Повторяемость важнее большого лога: один владелец, один объект и короткий запрос дают лучший минимальный случай.

## Повторение и глоссарий

Вернитесь к трём опорам главы: модель данных должна иметь ограничения; SQL связывает текст запроса и параметры безопасно; результат требует правильного порядка и обработки ошибок/ресурсов. Свяжите их с предыдущими знаниями: ошибки и интерфейсы из Junior помогают отделить доменную категорию от драйвера, context и integration tests делают внешнюю зависимость наблюдаемой. Дальше P2 применит тему к коротким ссылкам и пользовательским данным.

- **transaction (транзакция)** — Группа операций с общим решением о фиксации или отмене.
- **commit (фиксация)** — Подтверждение транзакции, после которого её изменения становятся частью состояния.
- **rollback (откат)** — Отмена незакоммиченных изменений транзакции.
- **isolation (изоляция)** — Правила видимости параллельных изменений между транзакциями.
- **migration (миграция)** — Версионированное изменение схемы с воспроизводимым направлением.
- **atomicity (атомарность)** — Свойство «всё либо ничего» для оговорённой группы операций.

Оцените доказательства отдельно: компилируемый Go пример подтверждает локальный контракт; SQL блок показывает исполняемый запрос при наличии реального worker; интеграционные проверки P2 подтверждают поведение с PostgreSQL; security review необходим для утверждений о доступе. Один слой не следует описывать как доказательство другого.
