## Драйвер и пул соединений

Go процесс не говорит PostgreSQL напрямую через SQL строку. Драйвер PostgreSQL реализует wire protocol (сетевой протокол) и преобразование значений. В P2 за это отвечает `github.com/jackc/pgx/v5` версии из `reference/go.mod`, а `pgxpool` управляет повторным использованием соединений. Приложение открывает пул один раз на жизненный цикл, внедряет repository в handlers и закрывает пул при завершении. Создание нового пула на каждый HTTP запрос съедает соединения и усложняет отмену.

Пул ограничен: максимум соединений, таймаут подключения и серверные лимиты должны быть согласованы. «Пул открыт» не всегда значит, что сервер уже доступен и запрос сработает; проверка readiness зависит от того, может ли приложение выполнить нужную операцию. Не держите взятое соединение без причины. Каждое взятое соединение нужно вернуть, а каждый результат `Rows` — закрыть.

## Context идёт через всю цепочку

Context (контекст) несёт отмену и deadline. HTTP запрос получает свой `r.Context()`. Repository передаёт именно его в `Query`, `QueryRow`, `Exec` и `Begin`. Если клиент закрыл соединение или истёк срок, операции могут остановиться. Если передать `context.Background()` в запрос вместо request context, работа продолжится после ухода клиента и удержит ресурсы. Для фоновой задачи нужен отдельный осознанный жизненный цикл, а не случайное отсоединение.

Timeout выбирается с учётом всей операции. Если HTTP deadline равен 3 секундам, не следует начинать database query на 30 секунд. Можно задавать внутренний более короткий deadline, производный от родителя. Отмена — не SQLSTATE и не обычная бизнес-ошибка: распознавайте `context.Canceled` и `context.DeadlineExceeded` через `errors.Is`, а структуру ошибки базы проверяйте через `errors.As` к `*pgconn.PgError`.

## QueryRow, Query и Scan

`QueryRow` удобен, когда ожидается максимум одна строка. Вызов возвращает объект, а фактическая ошибка появляется в `Scan`. PostgreSQL может вернуть `pgx.ErrNoRows`; это штатная ветка поиска, а не stack trace для HTTP клиента. Этот sentinel не следует выдавать за серверную `*pgconn.PgError` с кодом 02000: проверяйте `errors.Is(err, pgx.ErrNoRows)` отдельно от `errors.As` к структурированной ошибке сервера. Число аргументов и типы назначения `Scan` должны совпадать с выбранными столбцами. Nullable столбец требует nullable типа/указателя либо явного SQL `COALESCE`, если отсутствие по смыслу заменяется значением.

`Query` возвращает итератор `Rows`. Стандартный порядок: `defer rows.Close()`, цикл `Next`, `Scan`, затем проверить `rows.Err()`. Ошибка может возникнуть уже после нескольких строк. Не возвращайте частичный успешный список без явного контракта, если дочитывание завершилось отказом. Учитывайте порядок сортировки: SQL не обязан возвращать строки в удобной для UI последовательности без `ORDER BY`.

`Exec` подходит для команд, где строковый результат не нужен. Если надо убедиться, что изменена одна запись, изучите `CommandTag`/число затронутых строк и обработайте случай «не найдено». Для создания с возвращаемым ID лучше `QueryRow(... RETURNING id).Scan(&id)`.

## Repository — место для данных, не для HTTP

Repository обычно принимает доменные значения и context, формирует параметризированный запрос, сканирует результат и переводит известные отказы. Он не должен читать `r.Form` и выбирать HTTP status. Handler преобразует HTTP контракт, service применяет предметную операцию, repository говорит с базой. Для маленького проекта не требуется абстрагировать каждую строку интерфейсом; интерфейс полезен там, где потребителю нужна подмена в тесте или разделение ответственности.

Секреты конфигурации приходят из окружения или локального `.env`, который не коммитят. DSN может содержать пароль, поэтому его нельзя писать в logs или ошибки. Reference ограничивает pool и серверные statement/lock timeout как обучающие настройки. Их значения подходят конкретному проекту и не являются универсальной рекомендацией для большой нагрузки.

## Constraint ошибки и границы retry

pgx-ошибка включает SQLSTATE и constraint metadata. Используйте структурные поля, не ищите подстроку в английском сообщении. Unique violation можно преобразовать в conflict. При этом ошибка соединения или превышение statement timeout не равны «alias занят». Невалидная конфигурация не должна уносить секрет в публичный error response.

Retry допустим только для семантически повторяемой транзакции при конкретных transient SQLSTATE, например serialization failure и deadlock. Создайте новую транзакцию и повторите весь её блок, ограничьте число попыток, сохраните request deadline. Не повторяйте context cancellation и uniqueness violation. Функция Hard проверяет только классификацию кода, а вызывающая интеграция обязана реализовать остальные свойства.

### P2 reference и настоящая практика

Текущий reference проекта находится в `content/projects/p2/reference`. Его `go.mod` закрепляет pgx v5.11.0; проект описан для Go 1.27.2 и PostgreSQL 18.6. Сверяйтесь с конкретными файлами: `postgres.go` показывает запросы и перевод ошибок, `migrations/0001_init.up.sql` — ограничения и индексы, integration tests — операции с disposable DB. Практическое рабочее место P2 подключает реальный одноразовый PostgreSQL worker. Базовый runner уроков не может подключаться к базе и выполняет лишь три pure Go функции ниже.

Не запускайте код главы как `go run` без проекта, когда он импортирует pgx: учебный runner не устанавливает внешние зависимости. Разбирайте pgx в контексте project reference, где version и `go.sum` уже зафиксированы. Go примеры далее — законченные компилируемые стандартные программы, иллюстрирующие request context, безопасную нормализацию ошибки и закрытие `io.Closer`; они не выдают этот стандартный helper за pgx запрос.

### Диагностика

- `ErrNoRows` не обработан и превращается в 500 для нормального отсутствия.
- `rows.Err()` не проверен после цикла.
- `Rows` или pool не закрываются.
- Вызов использует Background вместо context HTTP запроса.
- Значения подставлены в SQL текст вместо отдельных `$1` аргументов.
- Retry производится бесконечно, после отмены либо с тем же завершённым tx.
- Сканирование nullable значения в обычную строку не соответствует схеме.

Проследите один путь в проекте: handler передал request context, repository вызвал `QueryRow`, `Scan` заполнил модель, constraint ошибка превратилась в доменную категорию, HTTP слой вернул стабильный безопасный ответ. Затем отмените context или найдите отсутствующий slug и сравните путь отказа. Этот trace полезнее, чем запомнить названия пакетов.

## SQL-практика для P2 worker

Query с ограничением владельца. Следующий блок самодостаточен: все таблицы временные, входные строки заданы прямо, а изменения отменяются. Его следует отправлять SQL worker в проектном рабочем месте P2; обычный Go function runner не подключает базу и не выполняет этот блок. Здесь нет команд управления сервером, файловой системы или роли.

```sql
BEGIN;
CREATE TEMP TABLE demo_owners(id integer PRIMARY KEY, label text NOT NULL);
CREATE TEMP TABLE demo_links(id integer PRIMARY KEY, owner_id integer NOT NULL REFERENCES demo_owners(id), slug text NOT NULL);
INSERT INTO demo_owners VALUES (1, 'Алия'), (2, 'Бек');
INSERT INTO demo_links VALUES (10, 1, 'docs'), (20, 2, 'home');
PREPARE demo_find(integer, text) AS
  SELECT id, owner_id, slug FROM demo_links WHERE owner_id = $1 AND slug = $2;
EXECUTE demo_find(1, 'docs');
EXECUTE demo_find(2, 'docs');
ROLLBACK;
```

Предскажите вывод каждой команды, затем измените одно условие `WHERE` или JOIN и проверьте результат в disposable PostgreSQL, используя аналогичный запрос в P2 repository/migration. Если project worker недоступен, разберите блок как текст; не переносите его в общую базу.

## Практика E / M / H

- **Easy: Различи NULL и пустое значение.** Если present=false, верни "", false независимо от value. Если present=true, верни value, true, включая пустую строку. Это моделирует наличие nullable значения; преобразование конкретного SQL-типа делает Scan/pgtype.
- **Medium: Преобразуй результат поиска в стабильную категорию.** Пустой SQLSTATE означает success; переданный код 23505 → conflict, 02000 → not_found, 57014 → canceled, всё остальное → storage_error. Это функция категоризации строки, не адаптер pgx.ErrNoRows. В реальном pgx-коде сначала проверь errors.Is(err, pgx.ErrNoRows), затем структуру server error через *pgconn.PgError и cancellation через context; функция не обращается к PostgreSQL.
- **Hard: Повторяй только транзакционные конфликты.** Разреши retry только для 40001 и 40P01; timeout, cancellation, connection error и uniqueness conflict верни false. Проверяющая функция не доказывает, что вызывающий код создаёт новую транзакцию, ограничивает попытки и передаёт deadline.

Три упражнения проверяются детерминированными примерами функции Go. Ни одно не запускает PostgreSQL, не проверяет план запроса и не доказывает навык написания исполняемого SQL. Самостоятельная практика с запросами — в P2 workspace: перенесите SQL в проектный файл и проверяйте через Go integration tests и project verification с disposable DB. В каждом упражнении сначала запишите ожидаемый результат для стандартного и граничного входа, затем добавьте минимальную проверку. Не маскируйте ошибку пустым значением, если контракт требует отдельную категорию.

## Типичные ошибки и самостоятельная диагностика

- rows.Close или rows.Err забыты. Проверьте happy path и отказ чтения после нескольких строк.
- Нет строки воспринимается как системная авария. Сопоставьте pgx.ErrNoRows с ожидаемой доменной категорией.
- Контекст теряется между handler и repository. Проследите один параметр до вызова pgx.
- Retry затрагивает cancellation или conflict. Сначала классифицируйте отказ и соблюдайте deadline/лимит попыток.

При отладке записывайте вход, ожидаемую категорию, фактический результат и состояние disposable базы. Не сохраняйте DSN, токен, cookie или содержимое реального пользовательского payload в журнал примера. Повторяемость важнее большого лога: один владелец, один объект и короткий запрос дают лучший минимальный случай.

## Повторение и глоссарий

Вернитесь к трём опорам главы: модель данных должна иметь ограничения; SQL связывает текст запроса и параметры безопасно; результат требует правильного порядка и обработки ошибок/ресурсов. Свяжите их с предыдущими знаниями: ошибки и интерфейсы из Junior помогают отделить доменную категорию от драйвера, context и integration tests делают внешнюю зависимость наблюдаемой. Дальше P2 применит тему к коротким ссылкам и пользовательским данным.

- **driver (драйвер)** — Библиотека, переводящая операции Go в протокол конкретной базы.
- **connection_pool (пул соединений)** — Ограниченный набор повторно используемых соединений с жизненным циклом.
- **context (контекст)** — Объект отмены и срока операции, передаваемый по цепочке вызовов.
- **repository (репозиторий)** — Компонент доступа к данным и преобразования результатов хранения.
- **pgx (pgx)** — PostgreSQL toolkit для Go с пакетами pgx и pgxpool.
- **rows (строки результата)** — Итератор результата Query, который необходимо дочитать и закрыть.

Оцените доказательства отдельно: компилируемый Go пример подтверждает локальный контракт; SQL блок показывает исполняемый запрос при наличии реального worker; интеграционные проверки P2 подтверждают поведение с PostgreSQL; security review необходим для утверждений о доступе. Один слой не следует описывать как доказательство другого.
