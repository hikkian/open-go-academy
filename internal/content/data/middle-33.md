# SLI/SLO и error budget

## Что ты сделаешь

Ты напишешь три проверки для показателей надёжности: классификацию окна наблюдения по числу событий и ошибок, проверку цели по допустимому числу сбоев и решение о бюджете ошибок с действием при превышении. Функции работают с целыми числами и не считают показатели по реальным логам.

## SLI: что именно измеряем

Индикатор уровня сервиса (SLI) — это число, которое описывает качество работы, например долю успешных запросов. Чтобы он был проверяемым, нужно назвать четыре вещи: что считается успешным событием, какой знаменатель, за какое окно наблюдения и из какого источника данных. Без них два человека получат разные числа из одних и тех же логов, и спорить станет не о чем.

Пример показывает, как одна и та же выборка даёт разные ответы в зависимости от того, что считать знаменателем. Здесь знаменатель — все запросы, а не только запросы к конкретному маршруту:

```go
package main

import "fmt"

func main() {
    total, failed := 200, 4
    fmt.Printf("%.1f%% errors\n", 100*float64(failed)/float64(total))
}
```

Вывод: `2.0% errors`. Число верно только для выбранного знаменателя и окна. Если знаменатель сменить на один маршрут, результат изменится, хотя логи те же.

## Пустое окно

Если за окно не было ни одного события, доля ошибок не определена. Ноль ошибок при нуле запросов — это отсутствие данных, а не хорошая работа. Поэтому классификация сначала отделяет пустое окно, а потом смотрит на ошибки.

Пустое окно требует отдельного решения. Его стоит показывать на дашборде отдельной меткой, чтобы дежурный видел разницу между спокойным сервисом и сервисом без данных. Его можно считать неизвестным состоянием и не запускать решения по бюджету. Молча считать его успешным опасно: сервис, который перестал получать трафик из-за сбоя балансировщика, будет выглядеть идеально.

> **Важно.** Пустой результат — это «неизвестно», а не «ноль». Так показатель не маскирует простой сервиса под надёжность.

## SLO и SLA

Цель уровня сервиса (SLO) — внутреннее число, по которому принимают решения: например, девяносто девять процентов успешных запросов за месяц. Соглашение об уровне сервиса (SLA) — договорное обязательство перед клиентом, с компенсациями и последствиями. SLO обычно строже SLA: запас между ними даёт время заметить проблему раньше, чем клиент получит право на компенсацию.

Учебная проверка SLO работает только с числами. Она не решает, какой процент обязателен для клиента. Такое решение принимают продукт и юристы, а не функция.

## Допустимое число сбоев

Если цель равна проценту, то допустимое число сбоев в окне — это доля от числа запросов. Например, при двух процентах и тысяче запросов допустимо двадцать сбоев. Дробная часть отбрасывается вниз: если допустимо два с половиной сбоя, то разрешённых сбоев два, потому что «не больше доли» означает именно это.

Умножение `total * percent` может переполнить целое число на больших окнах. Поэтому считают через частное и остаток. Пример показывает, что результат совпадает с прямым расчётом на маленьком числе:

```go
package main

import "fmt"

func limit(total, percent int) int {
    q, r := total/100, total%100
    return q*percent + (r*percent)/100
}

func main() {
    fmt.Println(limit(1000, 2), limit(100, 2), limit(3, 33))
}
```

Вывод: `20 2 0`. Для тысячи запросов при двух процентах допустимо двадцать сбоев, для ста — два, а для трёх запросов при тридцати трёх процентах допустимых сбоев нет: дробная часть отброшена.

## Проверка цели

Проверка цели сравнивает число сбоев с допустимым пределом. Ровно предел проходит: двадцать сбоев из тысячи при цели два процента — это в рамках. Двадцать один сбой уже нарушает цель. Неверные данные — отрицательный объём, сбоев больше запросов, процент вне диапазона — не должны давать ни «прошло», ни «не прошло».

Пример показывает такую проверку на граничных значениях:

```go
package main

import "fmt"

func meets(total, failed, limit int) bool {
    return failed <= limit
}

func main() {
    fmt.Println(meets(1000, 20, 20), meets(1000, 21, 20))
}
```

Вывод: `true false`. Граница включена: предел проходит ровно, а лишний сбой — нет.

## Бюджет ошибок и действие

Бюджет ошибок — это разность между допустимым числом сбоев и фактическим. Пока бюджет есть, команда может рисковать: выкатывать изменения, экспериментировать. Когда бюджет исчерпан, рискованные изменения замораживают и вкладываются в надёжность. Важно, что действие выбирается заранее и записывается, а не решается в момент пожара.

Бюджет полезно показывать не только как число, но и как скорость его расходования: сколько ошибок в час съедает допуск и сколько часов осталось до исчерпания при текущей скорости. Такая оценка дает время на реакцию раньше, чем бюджет закончится.

Учебная функция возвращает три метки: данные неверны, бюджет превышен и изменения нужно заморозить, либо бюджет в норме. Какие именно изменения считаются рискованными, решает команда.

## Что меняется при изменении порога

Порог — самое чувствительное число в модели. Если цель поднять с двух процентов до трёх, допустимое число сбоев вырастет на треть, и команда получит больше свободы для рискованных изменений. Поэтому изменение порога — решение, которое записывают вместе с обоснованием: почему прежний порог больше не отражает потребности пользователей.

Порог и окно связаны. Цель в процентах за месяц и цель за сутки дают разный допуск: суточное окно короче и шумнее, и один плохой час в нём может исчерпать бюджет. Поэтому окно выбирают вместе с порогом и не меняют их по отдельности.

## Модель и механизм

Для показателя надёжности полезны три вопроса. Что считается успешным событием и каким окном мы его измеряем? Какой порог допустим и кто его утвердил? Какое действие следует за превышением? Ответы записываются до первого дашборда.

Синхронизация здесь не нужна, потому что расчёт выполняется по готовым счётчикам. Цена подхода — показатели требуют стабильных источников данных: если логи меняют формат, число меняется без реального изменения сервиса.

## Типичные ошибки и исправление

Первая ошибка — считать пустое окно хорошим результатом. Она самая частая: после сбоя балансировщика или сбора логов окно становится пустым, и дашборд показывает зелёные цифры ровно тогда, когда сервис недоступен. Исправление — отдельное состояние «нет данных».

Вторая — менять знаменатель без записи. Исправление — фиксировать знаменатель в определении SLI.

Третья — округлять допустимое число сбоев вверх. Исправление — отбрасывание дробной части.

Четвёртая — решать действие при превышении в момент инцидента. Исправление — правило заранее, с конкретными изменениями под заморозкой.

> **Типичная ошибка.** Вычислять процент из ошибок и запросов, которые собраны из разных окон. Числитель и знаменатель должны относиться к одному окну и одному источнику.

## Если что-то пошло не так

- Дашборд показывает идеальную надёжность при простое → пустое окно считается нулём ошибок; покажи отсутствие данных отдельно.
- Два отчёта дают разные проценты из одних логов → знаменатель или окно различаются; запиши определение SLI.
- Бюджет исчерпан, а изменения продолжают выкатывать → действие не записано; заведи правило и проверяй его.
- Расчёт допустимых сбоев переполняется на больших окнах → умножение без частного и остатка; используй формулу из этой главы.

## Воспроизводимая лабораторная: предел бюджета ошибок

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Логи и дашборды не нужны: окно задаётся числами в самой программе.

Программа ниже считает допустимое число сбоев для тысячи запросов при цели два процента. Затем она проверяет два окна: с двадцатью и с двадцатью одним сбоем. Запусти её во временном каталоге и сравни вывод с ожидаемым.

```go
package main

import "fmt"

func limit(total, percent int) int {
    q, r := total/100, total%100
    return q*percent + (r*percent)/100
}

func main() {
    total, percent := 1000, 2
    max := limit(total, percent)
    fmt.Println("limit:", max)
    for _, failed := range []int{20, 21} {
        action := "within_budget"
        if failed > max {
            action = "freeze_risky_changes"
        }
        fmt.Println(failed, action)
    }
}
```

**Ожидайте:** строка `limit: 20`, затем `20 within_budget` и `21 freeze_risky_changes`. Граница включена: двадцать сбоев проходят, двадцать один — нет.

**Очистка:** программа ничего не создаёт на диске. Если запускал её во временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- SLI проверяем только вместе с успешным событием, знаменателем, окном и источником данных; без них два расчёта расходятся.
- Пустое окно означает неизвестный результат, а не нулевые ошибки; допустимое число сбоев округляется вниз.
- Действие при превышении бюджета выбирается заранее и записывается; функция лишь отличает «в бюджете» от «заморозить изменения».
