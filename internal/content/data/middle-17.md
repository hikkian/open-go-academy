# PostgreSQL outbox и публикация события

## Что ты сделаешь

Ты напишешь три функции-модели для outbox: решение relay до и после фиксации, выбор следующего шага по подтверждению брокера и порядок вызовов публикации и отметки с учётом сбоя. Функции работают с переданными фактами и журналом вызовов, поэтому проверяют логику без реального брокера и базы.

## Две системы — два окна отказа

База данных и брокер — независимые системы. Если обработчик сначала делает `UPDATE orders`, а затем отправляет событие `OrderChanged`, процесс может упасть между этими шагами. Порядок «сначала publish» тоже ошибочен: брокер уже увидел событие, а транзакция заказа откатилась.

Transactional outbox записывает бизнес-изменение и строку события в одну транзакцию PostgreSQL. После commit отдельный relay читает готовые строки и публикует их. Так источник истины о намерении находится рядом с изменением, которое его породило.

Пример показывает правильный порядок шагов в журнале. Событие появляется после фиксации, а не до неё:

```go
package main

import "fmt"

func main() {
    steps := []string{}
    steps = append(steps, "insert order", "insert outbox", "commit")
    steps = append(steps, "publish")
    fmt.Println(steps)
}
```

Вывод: `[insert order insert outbox commit publish]`. Журнал показывает порядок, но не доказывает атомарность: её даёт только транзакция базы.

## Что пишется в одной транзакции

Команда, например создание заказа, открывает транзакцию, вставляет заказ, формирует событие `OrderCreated` с отдельным идентификатором и записывает его в outbox. Затем транзакция фиксируется. Если любая вставка падает до commit, заказ и событие откатываются вместе.

При review проверь, что доменная запись и событие создаются через один и тот же транзакционный контекст. Если репозиторий открыл собственную транзакцию, внешне похожий код не обеспечивает общий commit.

> **Важно.** Событие нельзя показывать relay до commit. В откатившейся транзакции строки outbox не существует, и публиковать нечего.

## Захват строк и lease

После commit несколько экземпляров relay могут читать outbox одновременно. Чтобы не брать одну строку дважды, используют захват (claim) с ограниченным временем удержания, например `FOR UPDATE SKIP LOCKED` или другую проверенную стратегию. Результат зависит от транзакции и схемы, поэтому стратегию нужно проверять на реальной базе.

Захват обычно временный: владельцу выдаётся аренда (lease) с владельцем и сроком действия. Если worker погиб, после истечения срока другой процесс может восстановить запись. Если worker проснулся уже после передачи аренды, оба могут отправить сообщение. Поэтому дедупликация на стороне потребителя остаётся обязательной.

Публикацию делают пакетами ограниченного размера. Слишком маленький пакет увеличивает накладные расходы, слишком большой удерживает ресурсы и замедляет восстановление после сбоя. Размер подбирают по измерению: сколько строк обрабатывается за секунду и как растёт задержка при увеличении пакета.

Порядок внутри одного агрегата тоже важен. Если события одного заказа должны идти по номеру последовательности, строка outbox хранит идентификатор агрегата и номер, а relay не должен переставлять события одного агрегата. Одна строка на событие не гарантирует порядок между конкурирующими relay-экземплярами. Количество пакетов для строк считают округлением вверх:

```go
package main

import "fmt"

func main() {
    rows, batch := 25, 10
    fmt.Println((rows + batch - 1) / batch)
}
```

Вывод: `3`. Двадцать пять строк по десять в пакете дают три пакета, последний неполный. Эта арифметика нужна для планирования, а не для гарантии доставки.

## Окно после публикации

После публикации возникает неопределённость. Брокер мог принять событие, но ответ не дошёл, либо процесс упал до отметки `published_at`. При перезапуске relay увидит строку как необработанную и отправит её снова. Пример показывает, когда дубликат возможен:

```go
package main

import "fmt"

func main() {
    published := true
    marked := false
    fmt.Println("duplicate possible:", published && !marked)
}
```

Вывод: `duplicate possible: true`. Событие опубликовано, но отметка не сохранилась, поэтому повтор возможен. Устранять такой дубликат должен потребитель: событие несёт стабильный идентификатор, и повтор с тем же ID не должен породить второй эффект.

> **Типичная ошибка.** Считать, что отметка `published` гарантирует отсутствие дубля. Между подтверждением брокера и отметкой есть окно отказа, и оно существует всегда.

Проверяй падение после каждой операции: до commit, после commit до захвата, после захвата, после публикации до подтверждения, после подтверждения до отметки, после отметки до удаления или архивации. У каждой точки должен быть восстановительный переход. Если какая-то точка не имеет ответа «что будет при рестарте», значит, протокол неполон.

Удерживать блокировку строки во время неограниченного сетевого вызова нельзя: это блокирует таблицу и другие экземпляры relay. Короткий захват с арендой и подтверждение брокера уменьшают риск, но их реализацию нужно проверять на реальном брокере.

## Порядок «зафиксировать — опубликовать — отметить»

Правильный порядок: зафиксировать бизнес-изменение и событие, опубликовать событие, подтвердить брокеру и отметить строку. Отметка делается только после подтверждения. Если отметить строку раньше публикации, падение до публикации потеряет событие навсегда.

Подтверждение брокера определяется протоколом. Простой возврат метода клиента может не означать сохранённого подтверждения, поэтому в модели `brokerAccepted` означает именно наблюдаемое подтверждение.

## Модель и механизм

Сначала различай состояние программы и расписание. Состояние — факт commit, факт подтверждения брокера и отметка строки. Расписание — момент падения relay относительно этих шагов. Корректная политика должна давать допустимое решение при любом падении.

Для outbox полезны три вопроса. Что известно до публикации? Что известно после подтверждения? Что произойдёт при рестарте в каждой точке? Ответы записываются до написания relay.

Синхронизация имеет цену. Lease добавляет поля и сроки, пакеты увеличивают задержку публикации, а очистка строк требует аудита. Очистка не должна удалять строки, нужные для восстановления или аудита. Обычно строки переносят в архив по сроку, который больше окна восстановления и срока хранения аудита. Удалять их раньше — значит лишить себя возможности восстановить событие после длительного простоя брокера.

## Типичные ошибки и исправление

Первая ошибка — публиковать событие до commit. Исправление — relay читает только зафиксированные строки.

Вторая — отмечать строку до подтверждения брокера. Исправление — отметка после подтверждения и с тем же идентификатором.

Третья — удалять строку сразу после одного вызова публикации. Без подтверждения событие может потеряться. Исправление — удалять строку только после подтверждения и срока аудита.

## Если что-то пошло не так

- Потребитель видит заказ, которого нет → событие опубликовано до commit; перенеси публикацию после фиксации.
- Одно и то же событие приходит дважды → окно после публикации; проверь дедупликацию по идентификатору события.
- Строки копятся и не публикуются → relay не захватывает строки или lease не истекает; проверь срок аренды.
- Одна строка публикуется параллельно двумя экземплярами → claim не исключает конкуренцию; проверь стратегию блокировок.

## Схема события и наблюдаемость

Схема события версионируется независимо от таблицы заказа. Потребитель старой версии может получить новое поле или новый тип, поэтому изменения делают совместимыми: новое поле добавляют с значением по умолчанию, а несовместимое изменение сопровождают явным событием о смене версии. Внутренние модели SQL в публичный payload не помещают: outbox — контракт между производителем и потребителем, а не просто колонка JSON.

Relay должен сообщать о старейшем необработанном событии и о времени последней успешной публикации. Количество строк само по себе не показывает срочность: десять событий, задержанных на сутки, могут быть опаснее тысячи событий, задержанных на секунду. Поэтому алерт строят по возрасту и backlog, а ручная повторная отправка обязана сохранять исходный идентификатор события, иначе дедупликация перестанет работать.

## Итог

- Бизнес-изменение и событие записываются в одной транзакции; relay публикует только зафиксированные строки.
- Между публикацией и отметкой есть окно отказа, поэтому дубликаты возможны и устраняются на стороне потребителя по идентификатору события.
- Порядок «зафиксировать — опубликовать — отметить» защищает от потери события; удаление строк допустимо только после подтверждения и срока аудита.
