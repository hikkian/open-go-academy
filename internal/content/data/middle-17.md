# PostgreSQL outbox и публикация события

## Почему эта тема важна

База данных и брокер — две независимые системы. Если handler сначала делает `UPDATE orders`, а затем отправляет `OrderChanged`, процесс может упасть между этими шагами. Порядок «сначала publish» тоже ошибочен: брокер уже увидел событие, а транзакция заказа откатилась. Transactional outbox записывает бизнес-изменение и строку-событие в одну транзакцию PostgreSQL. После commit отдельный relay читает готовые строки и публикует их. Так источник истины о намерении находится рядом с изменением, которое его породило.

Событие нельзя показывать relay до commit. В откатившейся транзакции outbox row не существует и публиковать нечего. После commit строка остаётся доступной для повтора, пока relay не обработает её. Захват строк несколькими relay-воркерами обычно требует безопасного claim/lease (например, транзакционного выбора доступных записей и отметки владельца) и ограничения времени удержания. Если worker погиб, lease должен позволить восстановить запись; если два worker одновременно считают себя владельцами, дубликат вероятен.

После publish возникает тонкая неопределённость. Брокер мог принять событие, но ответ не дошёл, либо процесс упал до обновления `published_at`. При перезапуске relay увидит запись как необработанную и отправит её снова. Поэтому outbox обычно гарантирует повторяемую доставку при корректных предпосылках, а не ровно одну сетевую публикацию. Event ID и idempotent consumer позволяют безопасно устранить дубликат на стороне эффекта. Ack broker-у и отметка строки должны быть определены по протоколу: простой возврат метода клиента может не означать сохранённое подтверждение.

Планируйте рост таблицы: индексы для доступных записей, пакетный размер, очистка завершённых строк, задержка публикации, число ошибок и возраст backlog. Очистка не должна удалить строки, нужные для аудита или повторного восстановления. Политика ошибок разделяет временный отказ брокера (bounded retry с backoff) и постоянную ошибку схемы/события (изоляция и сигнал оператору). Бесконечный быстрый retry может создать шторм.

Easy принимает решение discard до commit или publish после него. Medium отделяет подтверждение брокера от отметки строки. Hard показывает crash-window как retry_may_duplicate. Эти три уровня помогают рассуждать о переходах, но не реализуют SQL, блокировку строки, publisher confirm или запуск relay. Для этого нужна отдельная проверка на закреплённой версии PostgreSQL и реальном брокере с остановкой процесса в каждой границе.

При review outbox-схемы проследите, чтобы доменная запись и событие создавались одним transaction handle. Если repository открыл другую транзакцию, внешне похожий код не обеспечивает общий commit. Событие должно иметь версию схемы, уникальный ID и минимальный payload. Секреты и личные данные не следует копировать без нужды: очередь может иметь более длинный срок хранения и более широкие права чтения. Изменение формата события требует совместимости producer и consumer.

## Практика трёх уровней

**Easy — middle-17-easy.** Реализуйте самый узкий контракт. Перед кодом выпишите таблицу вход → результат, отдельно нормальный случай, границу и некорректное состояние. Не добавляйте состояние, которого нет в сигнатуре. Проверьте, что каждый выход имеет конкретное значение для вызывающего слоя.

**Medium — middle-17-medium.** Добавьте независимый сигнал или состояние из условия. Решайте ветви в заданном порядке: сначала невалидное состояние, затем уже совершённый эффект/отмена, затем доступность ресурса, затем временной лимит и только после этого повтор или отказ. Этот порядок важен там, где две причины истинны одновременно. Проверьте конфликтующие входы из public/private vectors.

**Hard — middle-17-hard.** Разберите окно сбоя, неизвестный результат либо ограниченный отказ. Запишите, что система знает до сбоя и что может подтвердить после перезапуска. Не выводите «ровно один раз» из локальной категории: при неопределённом подтверждении реальная система должна повторить безопасно либо запросить сверку. Решение из функции — лишь политика для заданных фактов.

## Три исполняемых примера

```go group=middle-17-easy mode=run
package main
import "fmt"


func OutboxActionEasy(committed bool, published bool) string {
	if !committed { return "discard" }
	if !published { return "publish" }
	return "complete"
}

func main() { fmt.Println(OutboxActionEasy(false, false)) }
```

```go group=middle-17-medium mode=run
package main
import "fmt"


func OutboxActionMedium(committed bool, brokerAccepted bool, rowMarked bool) string {
	if !committed { return "discard" }
	if !brokerAccepted { return "publish" }
	if !rowMarked { return "mark_published" }
	return "complete"
}

func main() { fmt.Println(OutboxActionMedium(false, false, false)) }
```

```go group=middle-17-hard mode=run
package main
import "fmt"


func OutboxCrashHard(committed bool, brokerAccepted bool, rowMarked bool) string {
	if !committed { return "discard" }
	if !brokerAccepted { return "publish" }
	if !rowMarked { return "retry_may_duplicate" }
	return "complete"
}

func main() { fmt.Println(OutboxCrashHard(false, false, false)) }
```

## Как читать примеры и проверять выводы

Примеры ниже компилируются как небольшие программы и показывают публичный reference для упражнения. Каждый запускает только чистую функцию: в нём нет сетевого клиента, локальной БД, goroutine, таймера, брокера или настоящей конфигурации сервера. Вывод показывает результат контракта на названном input. Он не означает, что внешняя зависимость выдала такой исход, сохранила данные или соблюла порядок. Если пример и формулировка расходятся, исправлять нужно контракт или reference вместе, а не подгонять hidden tests под один частный ответ.

Табличный тест должен называть смысл каждой строки. Укажите входы, ожидаемую категорию и инвариант, который проверяется. Одного «happy path» недостаточно: добавьте точную границу, значение за границей и пересечение двух сигналов, когда приоритет важен. Private vectors должны ловить реализацию, которая всегда возвращает один удобный ответ, игнорирует отдельный аргумент, путает `>=` и `>` или не замечает некорректный счётчик. Случаи должны быть компактны и детерминированы, чтобы ученик мог воспроизвести их локально.

## Что потребуется для реальной проверки

Переход от helper к работающему backend потребует другого набора доказательств. Зафиксируйте версии runtime и зависимости, конфигурацию, лимиты, время ожидания, политику подтверждений и порядок фиксации. Для отказного теста отметьте точку, где процесс останавливается, перезапустите компонент и посчитайте итоговый эффект. Проверяйте, что отмена освобождает ресурсы, повтор не умножает изменение, а постоянная ошибка не крутится бесконечно. Снимайте метрики задержки, backlog и повторов. Unit test не может заменить такие проверки.

Если в системе участвует PostgreSQL, проверьте миграцию, уникальные ограничения, транзакционные границы и конкурентный сценарий на реальном закреплённом движке. Если участвует брокер, тест должен включать его фактический ack/confirm режим и рестарт consumer или relay. Если результат зависит от сети, используйте контролируемый локальный контейнер или fault proxy, а не случайную задержку. Очистка должна быть изолирована от пользовательских данных. Повторяемая команда и зафиксированный fixture позволяют другому разработчику независимо подтвердить результат.

## Диагностика и проектное решение

Начинайте расследование с наблюдаемого состояния: счётчики до операции, момент commit/ack, возвращённая категория, число повторов и конечный эффект. Сверьте часы, единицы измерения и идентификатор операции. Не делайте вывод по одному лог-сообщению, если его могло создать несколько попыток. Корреляционный ID должен быть безопасен и одинаков для повтора; payload, токены, DSN и личные сведения не следует без необходимости писать в лог.

При выборе политики опишите цену обеих сторон. Увеличить ожидание — значит дать системе больше времени, но занять запрос и ресурсы дольше. Быстро отказать — значит сохранить capacity, но передать восстановление вызывающему коду. Повтор — шанс пережить transient сбой и вероятность дублирования. Dead-letter — остановка автоматического шума ценой необходимости диагностики и replay. Хороший middle-level ответ называет условие переключения политики и метрику, которая это условие обнаружит.

Устойчивое решение имеет владельца каждого инварианта. Handler отвечает за решение и контекст; repository — за транзакционное состояние; адаптер брокера — за mapping ack/nack; операторская политика — за лимиты, очередь повторов и восстановление. Не размывайте ответственность между слоями. Наблюдаемая функция из grader помогает изолировать одно правило, а интеграционная система проверяет взаимодействие владельцев. Это разные масштабы доказательства, и оба могут понадобиться.

### Самопроверка

1. Какой вход пересекает границу контракта и меняет решение?
2. Какой отказ может произойти после внешнего эффекта, но до локального подтверждения?
3. Какая часть поведения проверена чистой функцией, а какая требует конкретной инфраструктуры?
4. Какой тест способен обнаружить дубликат, потерю эффекта или утечку ожидающего ресурса?

Перед завершением назовите один непокрытый отказ и один конкретный тест, который мог бы опровергнуть ваше решение. Сохраните команду, fixture, версии и фактическое число эффектов. Не расширяйте утверждение за пределы наблюдений: правильный результат helper — необходимая проверка правила, но не сертификат поведения всей системы.

## Жизненный цикл одной outbox-записи

Команда `CreateOrder` открывает транзакцию, вставляет заказ, формирует событие `OrderCreated` с отдельным event ID и записывает его в outbox, затем фиксирует transaction. Если любая вставка падает до commit, заказ и событие откатываются вместе. Relay видит только подтверждённые строки. Он атомарно claim-ит небольшой пакет, публикует события и помечает результат; параллельные relay должны координировать claim, чтобы не бесконечно брать одну и ту же строку одновременно. Claim обычно временный: после истечения lease другой процесс должен иметь возможность восстановить работу.

Easy намеренно показывает только «commit не состоялся — discard; состоялся — publish». Нельзя публиковать событие до commit, иначе consumer может увидеть несуществующий заказ. Но после commit relay ещё может быть остановлен до первой публикации. Поэтому сообщение не должно строиться заново из произвольного текущего состояния заказа без правил совместимости; сохранённое событие фиксирует факт, который должен быть доставлен. Outbox не должен превращаться в вечный backup без очистки, но и преждевременно удалять записи нельзя.

В Medium brokerAccepted — отдельный вход. Допустим, publisher confirm получен. Relay теперь должен сохранить `published_at` или статус delivered. Если он падает до SQL update, то после рестарта запись снова готова к публикации. Hard называет этот исход retry_may_duplicate. Не существует локального шага, который атомарно соединяет confirm брокера и commit строки PostgreSQL, если не используется согласованный distributed protocol. В типичном outbox решении принимают возможные дубликаты и обеспечивают idempotent consumer.

### Захват и конкурентная работа

Несколько экземпляров relay могут использовать `FOR UPDATE SKIP LOCKED` или другую проверенную стратегию claim, но результат зависит от транзакции и схемы. Долгая транзакция, удерживающая locks во время сетевой отправки, способна заблокировать очистку и другие worker-ы. Lease-стратегия уменьшает время блокировок, но требует token/owner, срока действия и безопасного завершения. Если worker продержал lease, а затем проснулся после его передачи другому worker, оба могут отправить сообщение. Дедупликация на consumer всё ещё нужна.

Публикацию делайте пакетами с ограниченным размером и параллелизмом. Слишком маленький batch увеличивает overhead; слишком большой batch удерживает ресурсы и замедляет восстановление. Учитывайте порядок, если события одного aggregate должны идти по sequence. В outbox row можно сохранить aggregate ID и sequence, но dispatcher должен не нарушать требуемый порядок или продукт должен допустить перестановку. Одна строка на событие не гарантирует порядок доставки между конкурирующими relay-ами.

### Векторы и контрольные мутанты

Мутант Hard, который выдаёт complete при brokerAccepted до rowMarked, пропускает риск повторной публикации. Мутант, который возвращает discard после commit, теряет событие. Проверяйте границы всех комбинаций и документируйте, какие наборы вообще могут встретиться в production. Невозможные по схеме состояния всё равно полезны как диагностика: если они появляются из реального хранилища, модель процесса или миграция нарушила инвариант.

### Интеграционный план

Запустите закреплённые версии PostgreSQL и брокера. В одной транзакции создайте доменную строку и outbox row; откатите другой сценарий и убедитесь, что relay ничего не публикует. Для crash-window добавьте контролируемый hook между confirm и mark, убейте relay, перезапустите и подтвердите возможный дубль, затем проверьте, что consumer применил эффект один раз. Дополнительно проверьте broker недоступен, lease истёк, два relay конкурируют, а DLQ/monitor сигнализирует постоянную ошибку. Не удаляйте тестовые строки до проверки восстановления.

### Проверка инварианта outbox

Формулировка должна быть точной: «для каждого commit-нутого изменения, требующего события, существует durable outbox row с event ID; строка может быть опубликована один или несколько раз; потребитель предотвращает повтор эффекта». Она не утверждает доставку с нулевой задержкой: relay может быть остановлен. Не утверждает exactly-once: публикация может повториться. Она предполагает, что база сохраняет commit согласно своей durability конфигурации, relay продолжит работу, broker подтвердит публикацию, а мониторинг обнаружит застрявшие строки.

Проверьте crash после каждой операции: до commit; после commit до claim; после claim; после broker publish до confirm; после confirm до mark; после mark до удаления/архивации. У каждого места есть восстановительный переход. Удаление строки после одного локального вызова `Publish` без подтверждения может потерять событие. Удерживать lock на время неограниченного network call может блокировать таблицу. Короткий claim lease и confirm протокол уменьшают риски, но их конкретная реализация нуждается в проверке.

Схема события версионируется независимо от таблицы заказа. Consumer старой версии может получить новое поле или тип. Используйте совместимое расширение, default и явное событие о несовместимости. Не помещайте внутренние SQL модели в публичный payload. Outbox — контракт между producer и consumer, а не просто колонка JSON.

### Дополнительный контроль

Relay должен сигнализировать о старейшем необработанном событии и длительности последней успешной публикации. Количество строк само по себе не показывает срочность: десять событий, задержанных сутки, могут быть опаснее тысячи событий, задержанных секунду. Создайте алерт по age/backlog и документируйте безопасный ручной re-drive. Повторная отправка должна сохранять исходный event ID, чтобы consumer dedup продолжал действовать. Ручная правка статуса строки без знания результата broker confirm может скрыть потерю.

### Термины

- **outbox (исходящая очередь в БД)** — Таблица событий, записываемая рядом с бизнес-изменением.

- **commit (фиксация транзакции)** — Успешное завершение атомарной группы SQL изменений.

- **relay (передатчик)** — Процесс, который публикует сохранённые события.
