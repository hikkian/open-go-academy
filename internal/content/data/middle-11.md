# MVCC и уровни изоляции PostgreSQL

## Что ты сделаешь

Ты напишешь три функции-модели: чтение значения, видимого снимку, чтение второго значения в паре и остаток повторов после ошибки сериализации. Примеры главы покажут, как версии строк связаны со снимком, и почему чтение снимка не равно блокировке записи.

## MVCC — версии вместо перезаписи

PostgreSQL использует MVCC (многоверсионное управление конкурентностью). Изменение строки не стирает старую версию сразу: создаётся новая версия, а старая остаётся видимой тем транзакциям, которые начались раньше. Каждая транзакция читает версии по своему снимку и уровню изоляции.

Это объясняет, почему читатель не ждёт писателя в обычном случае. Читатель выбирает версию, которая была зафиксирована до его снимка. Писатель создаёт новую версию. Конфликт возникает, когда два участника пытаются изменить одну и ту же строку, а не когда один только читает.

## Модель видимости

Упрощённо версия видима снимку, если она зафиксирована не позже момента снимка. Пример показывает это правило на двух версиях одной строки: значение `10`, зафиксированное в момент `5`, и значение `11`, зафиксированное в момент `9`.

```go
package main

import "fmt"

type version struct {
    value    int
    commitTS int
}

func visible(versions []version, snapshotTS int) int {
    value := 0
    for _, v := range versions {
        if v.commitTS <= snapshotTS {
            value = v.value
        }
    }
    return value
}

func main() {
    versions := []version{{value: 10, commitTS: 5}, {value: 11, commitTS: 9}}
    fmt.Println(visible(versions, 6), visible(versions, 9))
}
```

Вывод: `10 11`. Снимок в момент `6` ещё не видит версию, зафиксированную в `9`, а снимок в момент `9` видит. Модель не воспроизводит настоящий PostgreSQL, но показывает, почему одно и то же чтение может дать разные значения в разных снимках.

> **Важно.** Модель описывает правило видимости, а не реализацию. Реальная видимость зависит от идентификаторов транзакций, статуса commit и уровня изоляции, и проверяется только на реальном сервере.

## READ COMMITTED и REPEATABLE READ

При READ COMMITTED каждый statement получает собственный снимок. Два `SELECT` в одной транзакции могут увидеть разные зафиксированные изменения, если между ними другой участник успел сделать commit. Это ожидаемое поведение уровня, а не ошибка.

При REPEATABLE READ чтения транзакции опираются на один согласованный снимок. Изменения других участников, зафиксированные после начала транзакции, для неё не видны. Но изменить строку, которую уже изменил другой участник, всё равно нельзя: транзакция получит ошибку конфликта.

Выбор уровня — это выбор того, какие аномалии допустимы. Не выбирай уровень по привычке. Запиши, какой инвариант должен сохраняться, и проверь его на выбранном уровне.

## SERIALIZABLE и повтор транзакции

SERIALIZABLE может завершить транзакцию ошибкой сериализации, если её результат нельзя объяснить последовательным порядком. Ошибка отменяет транзакцию целиком. Повторить только последний запрос нельзя: предыдущие чтения уже устарели и могут быть основой для решения.

Поэтому приложение повторяет всю транзакцию. Перед повтором определи, какие побочные эффекты находятся внутри неё. Если повтор отправит второй платёж или второе сообщение, его нужно вынести за пределы транзакции или сделать идемпотентным, например через уникальный ключ операции.

## Снимок чтения и блокировка записи

Снимок чтения не равен блокировке. Транзакция может прочитать остаток, другой участник изменить его и зафиксировать, а первая транзакция попытается записать вычисление, основанное на старом остатке. Снимок не предотвращает такую запись сам по себе.

Условный `UPDATE` выражает проверку и изменение одним statement. Например, списание проходит только при достаточном остатке, и проверка делается над актуальной версией строки. Модель ниже повторяет это правило: изменение применяется, только если баланс не меньше списания.

```go
package main

import "fmt"

func update(balance, debit int64) (int64, bool) {
    if debit < 0 || balance < debit {
        return balance, false
    }
    return balance - debit, true
}

func main() {
    next, ok := update(40, 12)
    fmt.Println(next, ok)
    same, ok := update(5, 8)
    fmt.Println(same, ok)
}
```

Вывод: `28 true` и затем `5 false`. Функция отказывает, когда списание больше остатка, и не меняет баланс. В SQL то же правило записывается условием `WHERE` в самом `UPDATE`.

Если используется `SELECT ... FOR UPDATE`, блокировка удерживается до конца транзакции. Держи её коротко и задавай таймаут. Сетевой вызов внутри транзакции удерживает соединение и строку дольше, чем нужно.

## Compare-and-set по версии

Иногда приложение хранит собственный номер версии в строке и обновляет её, только если номер не изменился. Это похоже на условный `UPDATE` с проверкой версии. Модель ниже показывает правило: запись проходит, только если версия совпала с ожидаемой.

```go
package main

import "fmt"

type versioned struct {
    value   int64
    version int64
}

func compareAndSet(x versioned, expected, next int64) (versioned, bool) {
    if x.version != expected {
        return x, false
    }
    x.value = next
    x.version++
    return x, true
}

func main() {
    x, ok := compareAndSet(versioned{value: 7, version: 3}, 3, 9)
    fmt.Println(x.value, x.version, ok)
}
```

Вывод: `9 4 true`. Версия совпала, значение заменено, номер версии вырос. Если бы версия в строке уже стала четырьмя, результат был бы `7 4 false`, и вызывающий код должен был бы перечитать строку.

## Типичные ошибки и исправление

Первая ошибка — считать, что снимок блокирует запись. Снимок выбирает версию для чтения. Блокировка создаётся явными средствами или конфликтующей записью. Исправление — проверять, какие операции действительно блокируют друг друга.

Вторая — проверять условие отдельным `SELECT`, а потом писать. Между двумя запросами другой участник может изменить строку. Исправление — условный `UPDATE` или блокировка на время проверки и записи.

Третья — повторять только последний запрос после ошибки сериализации. Исправление — повторять транзакцию целиком и не допускать внешних эффектов внутри неё.

> **Типичная ошибка.** Тестировать изоляцию в одной сессии. Одно соединение не создаёт конкуренции, поэтому аномалия просто не появится. Нужны две сессии с явным порядком действий.

## Если что-то пошло не так

- Два чтения в одной транзакции дают разные значения → уровень READ COMMITTED: каждый statement видит свой снимок; для одного снимка выбери REPEATABLE READ.
- Обновление теряется под нагрузкой → проверка и запись разделены; перенеси условие в `UPDATE`.
- Ошибка сериализации не повторяется → повтор затрагивает только последний запрос; повтори всю транзакцию.
- Соединения висят → блокировка удерживается долго; убери сетевой вызов из транзакции и задай таймаут.

## Лаборатория перед практикой

Подготовь одну строку со счётчиком в disposable базе. Открой две сессии: в первой начни транзакцию на уровне READ COMMITTED и прочитай счётчик. Во второй увеличь счётчик и выполни commit. Перед чтением в первой сессии запиши предсказание: какое значение она увидит при следующем `SELECT`, и почему. Затем выполни чтение и сравни.

Повтори тот же порядок действий с REPEATABLE READ и сравни результат. Журнал эксперимента содержит версию сервера, уровни изоляции, полный список statements в каждой сессии, предсказания и фактические значения. В конце откати первую транзакцию, чтобы не оставить открытых сессий и не загрязнить данные.

Функции этой практики не открывают транзакцию и не проверяют снимок PostgreSQL. Они показывают правило видимости и правило повтора на переданных числах. Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда поднимает только disposable PostgreSQL из P3 Compose на loopback-порту 55433; пароль существует только в окружении shell. Она ждёт healthcheck, запускает точный тест и удаляет контейнер и volume при завершении блока:


Уровни проверяют разные алгоритмы по теме главы. Векторы охватывают только чистую функцию: они не запускают горутины и не заменяют интеграционные проверки.

## Итог

- MVCC хранит версии строк, и каждая транзакция читает версию по своему снимку и уровню изоляции.
- Снимок выбирает версию для чтения; блокировку создают явные средства и конфликтующие записи.
- Ошибку сериализации повторяют всей транзакцией, а побочные эффекты внутри неё делают безопасными для повтора.
