# P2 LinkHub: интеграция и безопасность

## Что ты сделаешь

Ты напишешь три решения, которые связывают части P2: `RedirectAllowed` разрешит переход только для включённой и проверенной ссылки, `OwnerAccess` сравнит владельца сессии и владельца ресурса, `TagAssociationOutcome` выберет исход привязки тега к ссылке. Каждая функция — правило; она не делает HTTP-запрос, не открывает базу и не читает сессию.

## Свести протокол, состояние и доверие

В P2 одна операция проходит через три слоя. HTTP boundary принимает запрос и решает, кто его отправил. Состояние лежит в PostgreSQL: ссылки, теги и их связи. Доверие — это то, что сервер знает сам: владелец из серверной сессии, а не значение из тела или query.

Ошибка обычно возникает на стыке слоёв. HTTP-обработчик проверил вход, но запрос к базе выбрал строку только по идентификатору. Или транзакция записала связь, которая не должна была появиться, потому что владельцы тега и ссылки не совпадали. Поэтому каждое решение в этой главе принимается на основании данных, которые сервер получил сам.

## Полный сценарий short link

Контракт P2 лежит в `content/projects/p2/openapi.yaml`. Там описаны `POST /api/v1/links`, `GET` и `PATCH` для `/api/v1/links/{id}`, `/api/v1/tags` и переход по короткому адресу `/{slug}`. Сценарий создания ссылки проходит так: сессия определяет владельца, handler проверяет тело, repository пишет ссылку, затем связывает тег, если он указан.

Переход по короткому адресу — отдельный путь. Он не требует сессии, но разрешает редирект только если ссылка включена и её целевой адрес прошёл проверку при сохранении. Сам обработчик не должен делать HTTP-запрос к цели: это открывает дорогу к SSRF и утечкам внутренней сети. Проверка `RedirectAllowed` описывает только это правило.

> **Важно.** Ответ 302 с `Location` — это контракт, а не доказательство безопасности. Тест должен проверять и статус, и заголовок, и поведение для отключённой ссылки.

## Аутентификация и CSRF на HTTP boundary

Изменяющие запросы в API используют cookie-сессию и требуют CSRF-проверку. Владелец берётся из сессии, которую сервер нашёл по случайному токену. Пример того, как редирект проверяется тестом без сети:

```go
package main

import (
    "fmt"
    "net/http"
    "net/http/httptest"
)

func main() {
    h := func(w http.ResponseWriter, r *http.Request) {
        http.Redirect(w, r, "https://example.test/", http.StatusFound)
    }
    rec := httptest.NewRecorder()
    h(rec, httptest.NewRequest(http.MethodGet, "/x", nil))
    fmt.Println(rec.Code, rec.Header().Get("Location"))
}
```

Вывод: `302 https://example.test/`. Тест видит статус и заголовок, а сеть не участвует.

## Интеграция SQL и откат

Ownership должен попасть в условие SQL, а не только в код после выборки. Для связи ссылки и тега это значит: обе строки принадлежат одному владельцу, и обе проверки выполняются в одной транзакции. Если любая из них не прошла, транзакция откатывается, и связь не появляется.

Пустое значение владельца не совпадает ни с чем, даже с другим пустым значением. Пример правила:

```go
package main

import "fmt"

func sameOwner(a, b string) bool {
    return a != "" && a == b
}

func main() {
    fmt.Println(sameOwner("u1", "u1"), sameOwner("", ""))
}
```

Вывод: `true false`. Два пустых идентификатора не доказывают владение.

> **Типичная ошибка.** Считать, что тег создан и ссылка создана, значит связь атомарна. Каждая запись может пройти отдельно, а связь окажется наполовину. Атомарность проверяет integration test с PostgreSQL, а не pure function.

## Readiness, Compose и проверка снаружи

Перед проверкой сценария убедись, что сервис готов: база доступна, миграции применены и API отвечает. Эти сигналы разобраны в главе про Compose. Pure helper в этой главе получает уже измеренное состояние, но не выполняет ping и не запускает миграции.

Полный путь проверяется на нескольких уровнях: unit tests правил, HTTP tests обработчика, PostgreSQL integration tests на одноразовой базе и ручной review того, что реально выставлено наружу. Автоматические тесты не заменяют последний шаг.

## Нарисовать threat model, а затем проверить

Threat model в P2 лежит в `content/projects/p2/threat-model.md`. Он перечисляет активы, участников и меры защиты, а также явные ограничения. Перед проверкой сценария сформулируй, что злоумышленник может сделать: подменить владельца в теле, угадать идентификатор ссылки, открыть чужой тег, использовать редирект для перехода во внутреннюю сеть.

Каждый пункт связывается с местом в коде и тестом. Если связи нет, пункт остаётся открытым, а не закрытым надеждой на сетевой периметр.

## Разбирать отказ систематически

Когда сценарий не работает, идём по слоям: запрос дошёл до handler; сессия найдена; владелец совпал; SQL условие выбрало строку; транзакция закоммичена; ответ соответствует контракту. Такой порядок быстрее ищет причину, чем гадание по сообщению об ошибке.

## Если что-то пошло не так

- Чужая ссылка изменилась → владелец взят из тела или условие SQL не содержит владельца.
- Редирект ведёт на отключённую ссылку → проверка enabled отсутствует или стоит после перехода.
- Тег привязан к чужой ссылке → владельцы не сравнивались или транзакция не откатилась.
- Тест проходит, но связь наполовину записана → нет integration test с транзакцией.

## Практика

Три задания. Функции проверяются на входах из блока «Ожидаемый вывод»; закрытые примеры видны только в «Проверить». Сеть, база и сессия не используются.

### Задание 1 · Перенаправляй только валидную активную ссылку

**Цель.** Вернуть `true`, только если ссылка включена и её целевой адрес ранее прошёл проверку. Иначе `false`.

**Ожидаемый вывод** — входы: включена и проверена, затем отключена и проверена:

```text
true
false
```

**Шаги.**
1. Выбери задание «Перенаправляй только валидную активную ссылку»: в файле есть `RedirectAllowed` с `panic("TODO")`. Импорты не нужны.
2. Если `enabled` равно `false`, верни `false`.
3. Если `targetValidated` равно `false`, верни `false`.
4. Иначе верни `true`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** `true` и `false`; все три критерия зелёные.

**Если не принято.**
- Непроверенная цель при включённой ссылке даёт `true` → без `targetValidated` переход не разрешён.
- Отключённая ссылка даёт `true` → проверка `enabled` обязательна.

> **Подсказка.** Два условия отказа, потом разрешение.

### Задание 2 · Проверь object ownership

**Цель.** Без сессии вернуть `"unauthorized"`. Пустой или несовпадающий владелец ресурса даёт `"not_found"`. Только совпадение непустых идентификаторов даёт `"allow"`.

**Ожидаемый вывод** — входы: без сессии, затем сессия `u1` и владелец ресурса `u2`:

```text
"unauthorized"
"not_found"
```

**Шаги.**
1. Выбери задание «Проверь object ownership»: в файле есть `OwnerAccess` с `panic("TODO")`. Импорты не нужны.
2. Если `authenticated` равно `false`, верни `"unauthorized"`.
3. Если `sessionOwner` или `resourceOwner` пустой, верни `"not_found"`.
4. Если владельцы не совпадают, верни `"not_found"`.
5. Иначе верни `"allow"`.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках; все три критерия зелёные.

**Если не принято.**
- Пустые `sessionOwner` и `resourceOwner` дают `"allow"` → пустой владелец не совпадает ни с чем.
- Ресурс другого владельца даёт `"allow"` → сравнение владельцев обязательно.

> **Подсказка.** Порядок: сессия, потом пустые значения, потом сравнение.

### Задание 3 · Свяжи ссылку и tag атомарно

**Цель.** Пустые или разные владельцы дают `"rejected"`. Совпадающие владельцы без зафиксированной транзакции дают `"rolled_back"`. Только совпадающие непустые владельцы при `committed` дают `"linked"`.

**Ожидаемый вывод** — входы: владельцы совпадают и транзакция зафиксирована, затем владельцы разные:

```text
"linked"
"rejected"
```

**Шаги.**
1. Выбери задание «Свяжи ссылку и tag атомарно»: в файле есть `TagAssociationOutcome` с `panic("TODO")`. Импорты не нужны.
2. Если `linkOwner` или `tagOwner` пустой либо владельцы не совпадают, верни `"rejected"`.
3. Если `transactionCommitted` равно `false`, верни `"rolled_back"`.
4. Иначе верни `"linked"`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках; все три критерия зелёные.

**Если не принято.**
- Незафиксированная транзакция при совпадающих владельцах даёт `"linked"` → связь без коммита не считается сделанной.
- Пустые владельцы при `transactionCommitted=true` дают `"linked"` → пустые значения отклоняются.

> **Подсказка.** Сначала владельцы, потом транзакция.

## Итог

- Владелец берётся из серверной сессии и проверяется в условии SQL, а не только в коде.
- Переход по короткой ссылке разрешён только для включённой и проверенной цели.
- Связь ссылки и тега атомарна только при транзакции и integration test с PostgreSQL.
- Оценка главы — это только самостоятельное evidence по критериям курса; автоматические тесты, human review и внешнее подтверждение — отдельные процессы.
