# TLS и безопасный транспорт

## Задача защищённого канала

TLS (Transport Layer Security, защита транспортного уровня) защищает обмен между двумя сетевыми концами. HTTPS — это HTTP, передаваемый поверх TLS. TLS решает важные задачи: шифрует содержимое канала от наблюдателей на маршруте; помогает обнаружить изменение защищённых данных; аутентифицирует сервер через проверку сертификата и имени узла. Всё это верно только при корректной проверке сертификата и надёжном доверенном наборе корней.

Слово «безопасный» здесь имеет ограниченный смысл. HTTPS не проверяет пользователя приложения, не решает, может ли пользователь удалить чужую ссылку, не гарантирует, что данные безопасно хранятся у сервера, и не защищает от вредоносного кода на самом клиенте. Авторизация — отдельное решение приложения. Если владелец токена отправил запрос по HTTPS, корректный TLS не превращает токен в безопасное доказательство права на любой объект.

В TLS-соединении клиент и сервер согласуют криптографические параметры и производные ключи, затем защищают трафик. При обычном HTTPS клиент проверяет цепочку сертификатов до доверенного корня и соответствие имени URL сертификату. Просроченный, неизвестно подписанный или предъявленный для другого имени сертификат должен привести к ошибке. Корректный сертификат подтверждает связь публичного ключа с проверяемой DNS-идентичностью в рамках модели доверия; он не обещает порядочность сервера и не подписывает бизнес-ответ.

```text
URL scheme=https → TCP connection → TLS handshake and certificate check → HTTP messages
```

Схема `https` — намерение клиента использовать TLS. Строковая проверка схемы не выполняет handshake, не загружает сертификат и не проверяет его срок или имя. Не называйте `url.Scheme == "https"` «проверкой безопасного сервера»: это только решение о протоколе, который нужно использовать.

## Сертификат и модель доверия

Сертификат (certificate, удостоверение публичного ключа и идентичности) содержит публичный ключ, имя или имена узлов, срок действия и подпись удостоверяющего центра (CA). Клиент проверяет цепочку подписей и правила имени. В браузере список доверенных корней устанавливается системой или браузером; в тесте мы можем явно доверить сертификат, созданный тестовым сервером. Сертификат — публичный материал. Закрытый ключ должен оставаться закрытым.

Обмен ключами TLS согласует ключи защищённого сеанса. При современных настройках это обычно не означает, что стороны посылают друг другу общий пароль. Точный набор алгоритмов зависит от реализации и версии TLS; приложение обычно не должно писать TLS вручную. `net/http` использует стек стандартной библиотеки и проверяет сертификаты по умолчанию.

Модель угроз важна. Пассивный наблюдатель в сети не должен прочитать тело и заголовки защищённого HTTPS-запроса. Активный посредник, который меняет трафик или притворяется сервером, должен быть обнаружен через проверку сертификата. Но HTTPS не скрывает все метаданные: адрес назначения, время и объём передачи могут быть видны. Прокси или конечная система, завершающая TLS, видит открытый HTTP. Компрометированный клиент видит ввод пользователя до шифрования, а приложение-сервер — запрос после расшифровки.

### Граница HTTPS и авторизации

Представим два маршрута: `GET /links/abc` и `DELETE /links/abc`. Оба могут идти в одном корректном TLS-канале. Если сервер не проверяет владельца ресурса, транспортная защита не предотвратит удаление чужого объекта. Аналогично, шифрование не исправляет слабый пароль, утечку access log, SQL injection или чрезмерный размер запроса.

TLS защищает соединение, а не объект доменной модели. Поэтому проверяйте каждую границу отдельно: сертификат и имя — на транспортной стороне; формат сообщения — у HTTP parser; право пользователя — у авторизации; владение и целостность записи — в правилах и хранилище.

## Пример 1. Проверить только выбранную схему URL

Путь `main.go`. Функция ниже намеренно проверяет структуру URL и `https`-схему. Она не подтверждает существование узла и сертификат.

```go group=https-scheme mode=run
package main

import (
	"fmt"
	"net/url"
)

func IsHTTPSOrigin(raw string) bool {
	u, err := url.Parse(raw)
	return err == nil && u.Scheme == "https" && u.Host != ""
}

func main() { fmt.Println(IsHTTPSOrigin("https://api.example.test/path")) }
```

Результат `true` означает лишь «похожая абсолютная HTTPS ссылка». Сертификат ещё не предъявлен и не проверен. Валидация URL для сохранения пользовательской цели также должна ограничить схемы, имя, порт, credentials и длину; наличие HTTPS не отменяет правила редиректа.

## Пример 2. Доверять сертификату только тестового TLS-сервера

`httptest.NewTLSServer` создаёт локальный сервер с тестовым сертификатом. Вызов `server.Client()` возвращает клиент, которому доверен именно сертификат этого тестового сервера. Все запросы остаются внутри процесса и не идут в интернет.

```go group=trusted-test-tls mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	server := httptest.NewTLSServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprint(w, "local test")
	}))
	defer server.Close()

	response, err := server.Client().Get(server.URL)
	if err != nil { panic(err) }
	defer response.Body.Close()
	fmt.Println(response.StatusCode)
}
```

Не заменяйте `server.Client()` на клиент с отключённой проверкой. Доверие ограничено тестовым сертификатом, а URL выдан самим сервером. Этот паттерн полезен для тестов TLS-кода, но не для обычного production доверия произвольным сертификатам.

## Пример 3. Проверка сертификата — отдельное наблюдение

```go group=reject-untrusted-test-cert mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	server := httptest.NewTLSServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { w.WriteHeader(http.StatusNoContent) }))
	defer server.Close()
	client := &http.Client{Transport: &http.Transport{Proxy: nil}}
	_, err := client.Get(server.URL)
	fmt.Println(err != nil)
}
```

Обычный клиент не доверяет случайному сертификату тестового TLS-сервера, поэтому ожидается `true`. Здесь мы печатаем только наличие ошибки: точный текст зависит от TLS и окружения. Корректный тест не должен сравнивать нестабильное диагностическое сообщение целиком. Если использовать доверенный `server.Client()`, тест проверяет успешный локальный handshake.

## Типичные ошибки и их диагностика

- **Отключать TLS verification при ошибке.** Это стирает защиту от подмены. Сначала проверьте имя URL, системное время, срок и SAN сертификата, цепочку CA и конфигурацию тестового trust store.
- **Считать префикс `https://` доказательством безопасности.** Разбор строки не выполняет криптографическую проверку. Называйте такую функцию проверкой схемы или синтаксиса.
- **Забывать закрыть response body.** После успешного HTTP-вызова вызывайте `Close`; иначе соединения хуже переиспользуются, а тестовые ресурсы остаются заняты.
- **Сравнивать полный текст TLS ошибки.** Формат текста может меняться. Проверяйте наличие ошибки либо устойчивые типы, если задача требует конкретной классификации.
- **Путать TLS authentication с логином.** Сертификат сервера помогает удостоверить сервер для клиента. Обычный HTTPS сам по себе не устанавливает пользовательскую личность и не принимает решение о ролях.
- **Доверять любому тестовому сертификату постоянно.** В тесте trust ограничен конкретным локальным сервером. Не копируйте тестовый CA в общий системный trust store.

Для локального теста доверяйте только временной цепочке, предоставленной `httptest`; не меняйте общий системный trust store. В примере с намеренно недоверенным сертификатом proxy отключён, чтобы даже пользовательские `HTTP_PROXY` настройки не перенаправили локальный запрос на внешний адрес.

TLS-ошибка до HTTP означает, что статус приложения недоступен: сервер не смог успешно завершить защищённый обмен. Не диагностируйте такую ошибку как `404`. И наоборот, полученный HTTP `404` обычно означает, что TLS и HTTP путь уже сработали достаточно, чтобы приложение отправило ответ.

### Что именно проверяет клиент

Успешная TLS проверка составная. Клиент выбрал имя из URL; получил сертификат и промежуточную цепочку; проверил подписи до своего доверенного корня; проверил срок; проверил, что имя URL подходит одной из допустимых идентичностей сертификата; согласовал криптографический handshake. Ошибка в любом из этих шагов может оборвать обмен до появления HTTP-статуса.

Имя субъекта сертификата в старой форме и `Subject Alternative Name` (SAN, альтернативное имя субъекта) имеют свои правила. Нельзя сравнить `CommonName` вручную строковым равенством и считать сертификат проверенным. Стандартные клиенты учитывают wildcard и DNS name rules. Пользовательский callback проверки сертификата может случайно ослабить поведение или принять имя по неверной политике. Настраивайте доверенные корни только осознанно.

Пиннинг сертификата или публичного ключа иногда нужен в ограниченных приложениях, но имеет отдельные требования ротации, fallback и восстановления. Жёсткое копирование текущего сертификата может остановить приложение при штатном продлении. Для обычного backend API используйте системное доверие и корректное имя; не реализуйте собственную криптографию.

### TLS завершён на прокси

В production HTTPS может завершаться на reverse proxy или load balancer, а между ним и Go приложением идти другой транспорт. Клиент доверяет сертификату внешнего узла; внутренний hop требует собственной модели доверия. Заголовок `X-Forwarded-Proto: https`, присланный любым клиентом, нельзя автоматически считать доказательством: только доверенный proxy должен удалять входное значение и ставить своё, а приложение должно знать его адресную границу.

TLS не скрывает адрес назначения от сети так же, как он скрывает тело. Метаданные соединения нужны для доставки пакетов, а размер и время обмена могут быть видны. Аналитика угроз должна честно назвать эту границу. Утверждение «HTTPS делает весь трафик невидимым» слишком сильное.

### Тестовая изоляция сертификата

Детерминированный тест должен явно владеть сертификатом. `httptest.NewTLSServer` создаёт временный ключ и сертификат; `server.Client()` доверяет цепочке этого сервера. После теста `Close` прекращает соединение и освобождает listener. Не сохраняйте тестовый private key в исходники и не добавляйте временный корень в системные сертификаты. Такой тест доказывает поведение конкретного client stack в тестовой среде, но не проверяет, что production CA настроен правильно.

## Практика

- **Easy:** решите, выбрал ли клиент схему HTTPS по абсолютной URL строке. Проверяйте пустой ввод, относительный путь, `http`, `https`, пустой host и нестандартный регистр схемы по контракту.
- **Medium:** классифицируйте выбранную scheme как HTTPS transport, обычный HTTP без TLS или неподдерживаемую scheme. Сертификат, имя, срок и доверенная цепочка обсуждаются по теории как отдельные наблюдения, но функция задания их не проверяет.
- **Hard:** примите решение URL policy: подходит ли absolute HTTP(S) URL и должен ли cleartext HTTP быть заменён на HTTPS. Возвращайте категорию выбранного транспорта; не утверждайте, что функция проверила certificate validation.

Условия тестов должны разделять URL scheme, host и HTTP статус. Сертификат, его имя, срок и доверенная цепочка разбираются по описанным выше наблюдениям, но строковая функция этой главы не объявляет их проверенными. Если локальный тест не выполнял TLS handshake, он не доказывает результат проверки сертификата.

## Мини-глоссарий

- **TLS** — протокол криптографической защиты соединения.
- **HTTPS** — HTTP поверх TLS.
- **certificate (сертификат)** — подписанное удостоверение публичного ключа и идентичности.
- **CA (удостоверяющий центр)** — издатель, которому клиент может доверять.
- **certificate verification (проверка сертификата)** — проверка цепочки, имени и срока сертификата.
- **encryption (шифрование)** — преобразование данных, скрывающее содержание от постороннего без ключа.
- **authentication (аутентификация)** — проверка заявленной идентичности; контекст определяет, чьей именно.
- **authorization (авторизация)** — решение, разрешено ли действие конкретному субъекту.
