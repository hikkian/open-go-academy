# Оценка ёмкости и устойчивый запас

## Что ты сделаешь

Ты научишься отвечать на вопрос «сколько система успевает» числом с единицей, окном и названным ограничивающим ресурсом, а не количеством горутин. Разберёшь, зачем нужен запас сверх обычной нагрузки и как посчитать бюджет без переполнения. Три функции урока — `CapacityClass`, `CapacityBudget`, `CapacityDecision` — это арифметика сравнения скорости поступления с допустимым бюджетом; измерений они не делают.

## Зачем нужна эта граница

Ёмкость (capacity) — завершённая полезная работа за единицу времени при заданном составе запросов и конфигурации. Чтобы сравнение имело смысл, скорость поступления (arrival rate) и способность обработки (service capacity) должны быть в одной единице — например, задач в секунду — и измерены в одном окне. Число соединений, потоков или горутин ёмкость не измеряет: тысяча горутин, ждущих базу, обрабатывают ноль задач в секунду.

Второй вопрос — запас. Если обычный поток занимает весь ресурс, после короткого пика накопленная очередь не уменьшится: некому её разгребать. Запас — это доля ресурса, которую не планируют занимать в норме, чтобы было куда расти при всплеске и чем восстанавливаться после сбоя. И запас по числу исполнителей бесполезен, если ограничивает память или база: у каждого вывода о ёмкости есть единица, окно и ограничивающий ресурс.

```go group=class mode=run
package main

import "fmt"

func capacityClass(workers, arrival int) string {
    if workers <= 0 || arrival < 0 {
        return "invalid"
    }
    if arrival > workers {
        return "over"
    }
    return "within"
}

func main() {
    fmt.Println(capacityClass(2, 1), capacityClass(2, 2), capacityClass(2, 3), capacityClass(0, 0), capacityClass(2, -1))
}
```

Вывод:

```text
within within over invalid invalid
```

Равенство — ещё `within`: модель учебная и считает, что исполнитель, занятый ровно на сто процентов, справляется. В реальности сто процентов — это уже очередь, и именно поэтому в следующих функциях появляется резерв.

> **Важно.** `workers` и `arrival` обязаны быть в одной единице за одно окно. «Десять исполнителей» и «восемь запросов в секунду» сравнимы, только если каждый исполнитель завершает ровно одну задачу в секунду — это допущение модели, и его надо записать.

## Бюджет с резервом без переполнения

Бюджет — число исполнителей, которое разрешено занять в норме: `workers · (100 − reserve) / 100` с округлением вниз. Наивное умножение переполнится на больших числах, поэтому считают через частное и остаток от деления на сто: `workers/100 · p + (workers%100) · p / 100`, где `p = 100 − reserve`.

```go group=budget mode=run
package main

import "fmt"

func budget(workers, reservePercent int) int {
    if workers <= 0 || reservePercent < 0 || reservePercent > 100 {
        return -1
    }
    p := 100 - reservePercent
    return workers/100*p + (workers%100)*p/100
}

func main() {
    fmt.Println(budget(100, 0), budget(100, 20), budget(101, 1), budget(100, 100), budget(10, 101))
    maxInt := int(^uint(0) >> 1)
    fmt.Println(budget(maxInt, 1) > 0, budget(maxInt, 0) == maxInt)
}
```

Вывод:

```text
100 80 99 0 -1
true true
```

Частное на долю не превосходит `workers`, остаток меньше ста — произведение остатка на долю не переполнится. Резерв в сто процентов даёт нулевой бюджет: это допустимый вход (полная остановка приёма), а не ошибка; резерв вне 0…100 — ошибка.

> **Типичная ошибка.** `workers * p / 100` «для простоты». На тестовых числах работает, на `MaxInt` даёт отрицательный бюджет, и система «откроет» приём без ограничений.

## Решение: вход против бюджета

Сравнивать поступление надо с бюджетом, а не с полной ёмкостью: `over` означает «выше того, что мы разрешили себе занимать», даже если физически исполнители ещё есть. Так всплеск виден до того, как очередь стала проблемой.

```go group=decision mode=run
package main

import "fmt"

func decision(workers, arrival, reservePercent int) string {
    if workers <= 0 || arrival < 0 || reservePercent < 0 || reservePercent > 100 {
        return "invalid"
    }
    p := 100 - reservePercent
    b := workers/100*p + (workers%100)*p/100
    if arrival > b {
        return "over"
    }
    return "within"
}

func main() {
    fmt.Println(decision(100, 80, 20), decision(100, 81, 20), decision(100, 1, 99), decision(100, 1, 100), decision(100, 0, 100))
}
```

Вывод:

```text
within over within over within
```

При резерве 99 % бюджет — один исполнитель, и одна задача в секунду ещё «внутри»; при резерве 100 % бюджет нулевой, и даже одна задача — превышение, а ноль задач — нет. Это и есть граница ёмкости: пара чисел и правило, записанные до инцидента.

> **Зачем.** Если граница не записана заранее, во время инцидента её выберут по текущему графику, и она окажется там, где удобно, а не там, где безопасно.

## Всплески, окно усреднения и хвост

Поступление в среднем за минуту может укладываться в бюджет, а в каждую десятую секунду — превышать его вдвое. Чем длиннее окно усреднения, тем ровнее график и тем больше спрятано всплесков; чем короче — тем больше шума. Поэтому окно для сравнения с бюджетом выбирают по времени, за которое очередь становится проблемой: если задержка на пять секунд уже нарушает контракт, окно в минуту бесполезно. Запиши рядом два числа — среднее и максимум по коротким окнам — и сравнивай с бюджетом оба; резерв как раз и покрывает разницу между ними.

Отдельно учитывай состав работы: сто лёгких запросов и сто тяжёлых — одно «поступление» и разная нагрузка. Если состав меняется в течение дня, ёмкость нужно измерять на худшем реалистичном составе, а не на среднем. Модель урока однородна по задачам, и это её главное допущение.

## Что считать и как записывать

Для каждой оценки ёмкости запиши: единицу (задач в секунду, запросов в минуту), окно (секунда, минута, час), состав работы (какие запросы и в какой пропорции), ограничивающий ресурс (CPU, память, соединения с базой, нижестоящий сервис), резерв в процентах и источник числа — измерение под нагрузкой или расчёт по модели. Расчёт по модели честно помечается: он не доказывает, что задачи однородны, что нижестоящая зависимость справится и что реальная система выдержит поток.

Отдельно проверь, что ограничивающий ресурс — тот, который ты считаешь. Десять исполнителей при пуле из пяти соединений с базой дают ёмкость пяти; память на задачу при ста исполнителях может превысить лимит контейнера раньше, чем CPU. Ёмкость — минимум по всем ресурсам, а не число в одной строке конфигурации.

## Ёмкость и восстановление после сбоя

Запас нужен не только для всплесков. После сбоя нижестоящей зависимости накопилась очередь из тысячи задач; чтобы разгрести её за минуту при обычном потоке, ёмкость должна превышать поступление на тысячу задач в минуту сверх нормы. Если резерв меньше, очередь будет сокращаться часами, и каждый новый сбой начнётся с ещё не разобранного хвоста. Поэтому резерв рассчитывают из двух требований — пик поступления и время восстановления — и берут большее. Это число тоже записывается с обоснованием, а не выбирается «процентов двадцать, как обычно».

## Практическая процедура

Нарисуй путь одной задачи: поступила, принята, выполняется, завершилась или отклонена. На каждом переходе назови ресурс, который он занимает, и его предел. Затем для типичного состава запросов оцени стоимость одной задачи по каждому ресурсу и посчитай ёмкость как минимум по ресурсам. Выбери резерв и запиши, из чего он следует: из истории всплесков, из времени восстановления после сбоя или из требования к задержке. Только после этого сравни поступление с бюджетом и реши, что делать при превышении — это тема следующего урока об обратном давлении.

Итоговая запись о ёмкости помещается в пять строк: «обработчик X: 120 задач/с при 8 исполнителях на составе Y, ограничивает пул соединений (10), резерв 25 % из времени восстановления 2 минуты, бюджет 90 задач/с, измерено на стенде Z 2026-10-20». Если какой-то из пяти строк нет, цифра ёмкости не готова к использованию в решениях.

## Типичные ошибки

- Ёмкость в горутинах или соединениях, а не в завершённой работе за время.
- Поступление и способность в разных единицах или окнах.
- Бюджет равен ёмкости: нет запаса на всплеск и восстановление.
- Умножение без защиты от переполнения.
- Ограничивающий ресурс не назван: считали CPU, а упёрлись в пул соединений.
- Расчёт по модели выдан за измерение под нагрузкой.

## Самостоятельная лаборатория

Возьми один обработчик своего сервиса и измерь на одноразовом стенде, сколько задач в секунду он завершает при фиксированном числе исполнителей и типичном составе входов; повтори при удвоенном числе исполнителей и посмотри, удвоилась ли ёмкость или упёрлась в другой ресурс. Запиши таблицу: исполнители, задач в секунду, какой ресурс был насыщен. Выбери резерв и посчитай бюджет функцией из примера, затем подай поток на десять процентов выше бюджета и зафиксируй, как растёт очередь. Удали стенд.

## Если что-то пошло не так

- `over` при `arrival == workers` → в задании 1 равенство — ещё `within`; сравнение строгое `>`.
- Отрицательный бюджет на больших числах → умножение без частного и остатка.
- `-1` при резерве 100 → сто процентов допустимы и дают ноль; ошибка — только вне 0…100.
- `within` при `arrival = 1` и резерве 100 → бюджет равен нулю, одна задача — превышение.
- `import … is not allowed` → импорты запрещены: целочисленная арифметика.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и числами. Закрытые примеры включают `MaxInt` — формула обязана не переполняться.

### Задание 1 · Easy: классификация capacity

**Цель.** `workers ≤ 0` или `arrival < 0` → `invalid`; `arrival > workers` → `over`; иначе `within`.

**Ожидаемый вывод** — для `(workers=2, arrival=1)`:

```text
"within"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func CapacityClass(workers int, arrival int) string`. Импорты запрещены.
2. Сначала проверка входов, затем сравнение `arrival > workers`, иначе `"within"`.
3. «Запустить», «Проверить» — закрытые примеры: равенство → `within`; `(2, 3)` → `over`; `(0, 0)` и `(2, -1)` → `invalid`.

**Как проверить себя.** Единицы `workers` и `arrival` одинаковы по допущению модели; ноль задач при положительном числе исполнителей — `within`.

**Если не принято.**
- `over` при равенстве → нестрогое сравнение.
- `within` для `(0, 0)` → проверка `workers <= 0` отсутствует.

> **Подсказка.** Это счётчик учебной модели в единицах за секунду, не benchmark.

### Задание 2 · Medium: безопасный reserve budget

**Цель.** `workers ≤ 0` или резерв вне 0…100 → `−1`; иначе `floor(workers · (100 − reserve) / 100)` без переполнения.

**Ожидаемый вывод** — для `(workers=100, reservePercent=0)`:

```text
100
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func CapacityBudget(workers int, reservePercent int) int`. Импорты запрещены.
2. Проверь входы; `p := 100 - reservePercent`.
3. Верни `workers/100*p + (workers%100)*p/100`.
4. «Запустить», «Проверить» — закрытые примеры: резерв 1, 99, 100; `MaxInt` с резервом 0, 1 и 99; резерв 101 и −1 → `−1`.

**Как проверить себя.** `(101, 1)` → 99, `(100, 99)` → 1, `(100, 100)` → 0, `MaxInt` с резервом 0 — сам `MaxInt`.

**Если не принято.**
- Отрицательный результат на `MaxInt` → умножение до деления.
- `−1` при резерве 100 → граница включительная.

> **Подсказка.** Разложи `workers` на частное и остаток по сто: произведение частного на долю не больше `workers`, остаток меньше ста.

### Задание 3 · Hard: решение по capacity boundary

**Цель.** Некорректные входы → `invalid`; посчитать бюджет как в задании 2; `arrival` выше бюджета → `over`, иначе `within`.

**Ожидаемый вывод** — для `(workers=100, arrival=80, reservePercent=20)`:

```text
"within"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func CapacityDecision(workers int, arrival int, reservePercent int) string`. Импорты запрещены.
2. `workers <= 0`, `arrival < 0` или резерв вне 0…100 → `"invalid"`.
3. Бюджет через частное и остаток; `arrival > budget` → `"over"`, иначе `"within"`.
4. «Запустить», «Проверить» — закрытые примеры: `(100, 81, 20)` → `over`; `(100, 1, 100)` → `over`; `(100, 0, 100)` → `within`; `MaxInt` против `MaxInt` при резерве 0 → `within`, при резерве 1 → `over`.

**Как проверить себя.** Точное равенство на `MaxInt` — `within`; расчётный предел не равен измеренной пропускной способности системы.

**Если не принято.**
- `within` для `(100, 81, 20)` → сравнение с `workers`, а не с бюджетом.
- Неверный ответ на `MaxInt` → переполнение в бюджете.

> **Подсказка.** Это задание 2 плюс одно сравнение; переиспользуй формулу буквально.

## Итог

- Ёмкость — завершённая работа за время при названном составе и ресурсе; поступление сравнивают с ней в одних единицах и окне.
- Резерв — доля, которую не занимают в норме; бюджет считают через частное и остаток, чтобы не переполниться.
- Граница ёмкости записывается до инцидента: единица, окно, ресурс, резерв, источник числа.
