# 13. Оценка ёмкости и устойчивый запас

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-12`
**Цель:** Пропускная способность — завершённые полезные операции за единицу времени при заданном составе запросов. Число соединений или количество запущенных горутин само по себе не измеряет ёмкость. Для учебной модели мы сравниваем arrival rate (скорость поступления) и service capacity (способность обработки), причём оба значения должны описывать одинаковые единицы и окно наблюдения.

## Термины и перевод

- **Capacity envelope** — допустимый диапазон нагрузки, при котором заданный ресурс справляется с работой в описанных условиях.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Ёмкость отвечает на вопрос: сколько одинаковой полезной работы система успевает завершить за выбранное время? Чтобы сравнение имело смысл, скорость поступления и скорость завершения должны иметь одинаковую единицу (например, задач в секунду) и одинаковое окно. Число горутин или соединений само по себе такой ответ не даёт.

Сначала задайте исходный ресурсный предел, затем резерв и только после этого сравнивайте вход с допустимым бюджетом. В helper этого урока резерв уменьшает число доступных исполнителей по целочисленной формуле; результат `within` означает лишь, что два заданных числа согласуются с этой формулой. Он не доказывает, что реальные задачи однородны, что downstream (нижестоящая зависимость) справится или что измеренная система выдержит поток.

Разделяйте пропускную способность и запас для восстановления. Если обычный поток уже занимает весь ресурс, после короткого пика накопленная очередь может не уменьшаться. И наоборот, запас по числу worker не поможет, если ограничивает память или база. Поэтому у каждого вывода должна быть единица, окно и названный ограничивающий ресурс.

## Три запускаемых примера

### Пример 1: обычный путь

```go
package main

import "fmt"

func CapacityClass(workers int, arrival int) string {
	if workers <= 0 || arrival < 0 { return "invalid" }; if arrival > workers { return "over" }; return "within"
}

func main() { fmt.Println(CapacityClass(2, 2)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 2: решение с несколькими сигналами

```go
package main

import "fmt"

func CapacityBudget(workers int, reservePercent int) int {
	if workers <= 0 || reservePercent < 0 || reservePercent > 100 { return -1 }; p := 100-reservePercent; return workers/100*p + (workers%100)*p/100
}

func main() { fmt.Println(CapacityBudget(100, 20)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 3: проверка ограниченного инварианта

```go
package main

import "fmt"

func CapacityDecision(workers int, arrival int, reservePercent int) string {
	if workers <= 0 || arrival < 0 || reservePercent < 0 || reservePercent > 100 { return "invalid" }; p := 100-reservePercent; budget := workers/100*p + (workers%100)*p/100; if arrival > budget { return "over" }; return "within"
}

func main() { fmt.Println(CapacityDecision(100, 81, 20)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.


## Безопасная целочисленная граница

Пусть `p=100-reservePercent`, поэтому при валидном проценте `0<=p<=100`. Разложим `workers=100*q+r`, где `q=workers/100`, `r=workers%100`. Тогда `floor(workers*p/100)=q*p+floor(r*p/100)`. Первая часть не больше workers, вторая перемножает только значения меньше 100. Сумма остаётся в диапазоне `[0, workers]`, поэтому 64-битный MaxInt не оборачивается в отрицательное значение. При резерве `reservePercent=100` значение `p=0`, следовательно, бюджет равен нулю — это валидная граница. Сначала обязательно проверьте workers>0, reservePercent∈[0,100] и arrival>=0. Формула убирает переполнение именно в этой helper; она не измеряет очередь, входящий поток или реальную пропускную способность сервиса.

## Практическая процедура

Составьте карточку измерения: версия и команда запуска, одинаковый набор работы, длительность окна, число исполнителей, критерий завершения полезной операции и сырые результаты каждого повтора. Сначала снимите baseline (исходный уровень), не меняя код; затем измените один параметр, например число worker, и повторите тот же набор. Проверьте, что сравниваете завершённые операции, а не только принятые.

Запишите устойчивую скорость обработки и поведение накопленной очереди после пика. Если входная скорость больше скорости завершения, очередь растёт; если после снижения входа она не сокращается, ресурсный запас не обеспечивает восстановления. Отдельно укажите, что именно не измерялось: например, пропускная способность базы или хвостовая задержка.

Локальный бенчмарк характеризует выбранный код на указанной машине. Три детерминированных примера урока проверяют классификацию и целочисленную границу; они не создают нагрузку и не являются доказательством production capacity (ёмкости в рабочей системе).

## Разбор сценария: Оценка ёмкости и устойчивый запас

Возьмите небольшой синтетический поток одинаковых задач и заранее выберите окно, единицу и условие завершения. Запишите baseline, затем рассчитайте допустимый бюджет с резервом. Сравните входную скорость с бюджетом и обозначьте, что в реальном исполнении потребовало бы отдельного измерения.

Теперь рассмотрите короткий пик: зафиксируйте, сколько работы осталось после его окончания и за какое время она могла бы быть завершена при выбранном запасе. Не выдавайте расчёт по числу worker за наблюдение очереди. Если задача длится по-разному, либо используйте фиксированный набор, либо разделите категории и сравните их отдельно.

В отчёте сохраните входные значения, единицы, формулу, команду и фактические повторы. Вывод должен быть опровержимым: «при этих входах helper возвращает `over`», а не «сервис выдерживает нагрузку». Следующее полезное измерение — проверить реальное время завершения фиксированного набора при одном изменённом лимите.

## Лаборатория: найти ограничивающий ресурс

### Численный сценарий

Представьте учебный обработчик с четырьмя исполнителями. Каждый исполнитель заканчивает в среднем десять задач в секунду на фиксированном синтетическом наборе. Начальная оценка мощности равна сорока задачам в секунду, но резерв в двадцать процентов оставляет бюджет в тридцать две задачи в секунду. При поступлении двадцати восьми задач в секунду модель говорит только, что вход ниже выбранного бюджета. При поступлении тридцати пяти — выше него. Ни один расчёт не говорит, что реальные задачи одинаковы или что зависимость выдерживает этот поток.

Добавьте неодинаковую длительность. Если одна задача занимает в десять раз дольше, суммарное число worker не равно числу завершённых задач: занятый медленной задачей исполнитель недоступен остальным. Если же все исполнители ждут базу, увеличение их числа может только увеличить одновременный спрос к базе. Поэтому единица «задача в секунду» пригодна лишь при оговорённом составе и стоимости работы. Сравнивайте одинаковый набор либо разбивайте результаты по классам задач.

### Последовательность эксперимента

1. Зафиксируйте версию кода, версию Go, машину, размер набора, способ прогрева и длительность окна. Определите полезное завершение: например, операция закончилась и результат проверен, а не просто попала в очередь.
2. Запишите исходный запуск несколько раз. Сохраняйте каждый результат, включая неудачные. Отметьте разброс, а не только среднее. Если один прогон резко отличается, не удаляйте его без объяснения: сначала выясните, менялись ли нагрузка, фоновые процессы или состояние зависимости.
3. Поменяйте ровно один фактор, например число worker с четырёх до пяти. Повторите тот же набор и окно. Если одновременно меняются очередь и размер входа, эксперимент уже не различает влияние факторов.
4. Сравните завершённую полезную работу, накопление очереди и время восстановления после короткого пика. Отметьте, какой ресурс насыщается первым. При отсутствии инструментирования честно оставьте причину неизвестной.

### Как читать результат

Если вход ниже расчётного предела, но очередь растёт, значит модель не включает важный фактор либо измерения несопоставимы. Проверьте одинаковы ли единицы, окна и критерии завершения; затем исследуйте память, соединения или нижестоящую базу. Если кандидат с большим числом worker показывает больше выполнений, но заметно ухудшает хвост ожидания, нельзя назвать его лучшим только по throughput (пропускной способности). Запас оценивают вместе с последствиями для задержки и восстановления.

Для отчёта ответьте: что считалось завершением, какой ресурс был ограничителем, какая часть результата повторилась и какое наблюдение опровергло исходную гипотезу? Примеры helper проверяют арифметическую классификацию и безопасную целочисленную формулу. Они не создают нагрузку, не измеряют скорость и не подтверждают ёмкость сервиса. Следующий проверяемый шаг — бенчмарк фиксированной операции, а затем отдельное измерение реальной зависимости в изолированной среде.

### Пиковая нагрузка и восстановление

Нагрузочный профиль не всегда постоянен. Сервис может получать обычный поток, короткий всплеск, а затем период восстановления. Для простой оценки задайте средний приток `λ` и среднюю скорость завершения `μ` в одинаковых задачах за секунду. Когда `λ < μ`, свободная мощность в принципе может уменьшать накопленную работу; когда `λ > μ`, очередь растёт. При равенстве нет запаса для случайных колебаний и возврата после сбоя. Это упрощённое рассуждение предполагает постоянные скорости и одинаковые задачи, поэтому не заменяет измерение распределения.

Например, вход в 30 задач/с и выход в 36 задач/с дают запас 6 задач/с только при устойчивой доступности всех ресурсов. Если накоплено 600 задач, идеальный срок разгрузки равен 100 секундам без нового пика. Если обычный поток продолжается, остаётся лишь разница между выходом и входом; при входе 30 и выходе 36 это 100 секунд всё ещё совпадает, потому что разница уже 6. Если же выход упал до 33, разгрузка занимает 200 секунд. В реальном случае учитывайте ошибки, повторную доставку и изменение длительности операций.

Не смешивайте максимальную наблюдаемую скорость с устойчивой. Краткий benchmark может использовать кэш, прогретую память и заранее открытые соединения. Длительный тест выявляет утечки, накопление задержек и исчерпание пула. Запишите длительность, прогрев и форму нагрузки. Проверьте функциональную корректность до и после нагрузочного прогона, чтобы высокая скорость не получилась из-за пропущенной работы.

### Проверьте ограничение распределения

Средняя скорость может скрыть неоднородность. Допустим, 90% задач занимают 10 мс, а 10% — 500 мс. Среднее время составит около 59 мс, но пользователи редких долгих задач увидят намного худшую задержку. Если все worker заняты долгими задачами, новая короткая работа ждёт, несмотря на привлекательное среднее. Зафиксируйте распределение или как минимум несколько процентилей и размер выборки. Процентили на малом наборе также нестабильны, поэтому показывайте число наблюдений.

Сопоставьте throughput и задержку при росте параллелизма. Один дополнительный worker может увеличить число законченных задач, но усилить очередь к базе и ухудшить p95. Выберите критерий успеха до измерения: например, увеличить полезные завершения при сохранении выбранного порога ожидания. Такая формулировка исключает выбор одной удобной метрики после прогона.

### Выберите критерий нагрузки

Не начинайте с вопроса «какая скорость максимально возможна?». Начните с критерия полезности: какая доля операций должна завершиться в пределах срока, какая ошибка считается неуспехом и какое время восстановления приемлемо. Максимальная пропускная способность, достигнутая при огромной задержке, может быть хуже меньшей скорости со стабильным временем ответа. Сохраните входной профиль, потому что число коротких запросов нельзя сравнивать с таким же числом дорогих.

Для учебного отчёта сформулируйте решение условно: «при четырёх worker и входе 28 задач/с helper относит значения к допустимому диапазону при заданном резерве». Следом перечислите, каких наблюдений не хватает для вывода о системе: длительности по классам, измеренной очереди, доли ошибок и состояния зависимости. Это делает заключение точным, но не преувеличивает его.

## Практика Easy / Medium / Hard

**Easy — классификация потока.** Реализуйте `CapacityClass` для arrival/workers. Проверьте свободный, точный и превышенный лимит, а также невалидные входы. Единицы в учебной модели должны совпадать.

**Medium — расчет резервного бюджета.** Реализуйте `CapacityBudget`: разделите workers на частное и остаток по 100, затем примените долю после резерва. Проверьте 0%, 1%, 99%, 100%, MaxInt и некорректные диапазоны.

**Hard — решение допуска.** Реализуйте `CapacityDecision`, соединив валидацию, расчет и сравнение arrival с бюджетом. Проверьте равенство на точной границе и соседнее превышение, в том числе при MaxInt. Это проверяет арифметику модели, не реальный capacity.
