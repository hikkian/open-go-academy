# 13. Оценка ёмкости и устойчивый запас

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-12`
**Цель:** Пропускная способность — завершённые полезные операции за единицу времени при заданном составе запросов. Число соединений или количество запущенных горутин само по себе не измеряет ёмкость. Для учебной модели мы сравниваем arrival rate (скорость поступления) и service capacity (способность обработки), причём оба значения должны описывать одинаковые единицы и окно наблюдения.

## Термины и перевод

- **Capacity envelope** — допустимый диапазон нагрузки, при котором заданный ресурс справляется с работой в описанных условиях.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

В этой главе ёмкость рассматривается как сопоставление двух скоростей в одинаковых единицах и окне наблюдения. Резерв уменьшает допустимый поток по явно заданной формуле; он не означает, что сервис действительно обработает столько запросов. Перед сравнением проверьте входные диапазоны, а вывод классификатора формулируйте только как результат учебной модели.

Начните с определения ответственности. Producer (производитель) предлагает работу; admission control (контроль допуска) решает принять её; worker (обработчик) исполняет; downstream (нижестоящая зависимость) может ограничить скорость; наблюдаемость сообщает, что произошло. Разделите ожидающую работу и выполняемую: queue depth (глубина очереди) обычно не включает уже захваченные worker элементы. Уточните момент, когда задача считается принятой, завершённой и повторяемой. Эти определения влияют на потери при остановке и на то, какой знаменатель использовать для SLI.

У модели всегда есть budget (бюджет ресурсов): конечные worker, память очереди, соединения, время запроса и допустимое число попыток. Две независимые очереди могут делить один бюджет памяти; несколько worker могут одновременно захватить все соединения пула. При capacity (ёмкости) рассматривайте полезную работу, а не только высокий throughput. Если потребитель быстрее источника, запас мощности бывает нужен для пиков и восстановления backlog. Запас не отменяет ограничений; его необходимо выразить через конкретный ресурс и объяснить, какое поведение система выбирает после исчерпания.

Backpressure (обратное давление) передаёт производителю сигнал о насыщении через ограниченный канал, ожидание с deadline или отказ. Бесконечная очередь маскирует перегрузку: запрос ещё не завершён, но ресурсы и время уже заняты. Не всякий caller умеет безопасно повторить отказ; для каждого ответа укажите семантику повторного вызова, retry-after и ключ идемпотентности. При остановке приложения сначала прекратите выдавать новые задания, затем дождитесь grace period (льготного периода), а после истечения предела отмените оставшееся с наблюдаемым итогом.

Повторы должны быть привязаны к классу ошибки и остаточному deadline. Повторять постоянную ошибку, некорректный ввод, отказ авторизации или конфликт транзакции без специального правила вредно. Для временного сбоя задайте ограниченное число попыток, backoff и общий retry budget, чтобы один запрос не породил лавину. Idempotency (идемпотентность) позволяет безопасно повторить эффект при стабильном ключе и сохранённом результате; она не появляется автоматически из-за HTTP, очереди или транзакции. Exactly-once (ровно один раз) — сильное утверждение, которое часто скрывает повторную доставку и отдельную атомарность каждого побочного эффекта.

При публикации события между базой и брокером существует граница. Outbox (исходящий журнал) связывает изменение и запись о намерении отправки транзакцией базы; publisher может читать запись повторно. Однако commit и публикация не становятся одной общей транзакцией. Consumer (потребитель) может применить эффект и упасть до ack (подтверждения), после чего получить дубликат. Разберите state machine явно: записано, опубликовано, подтверждено, отложено или отправлено в dead letter (маршрут безнадёжных сообщений). Для каждого перехода укажите условия и способ восстановления.

Наблюдаемость должна позволить различить «работы много», «работа старая», «работа падает», «worker завис» и «метрика перестала поступать». Полезны queue depth, возраст старейшего события, принятые и завершённые операции, retry count, timeout, насыщение пула и число отклонённых запросов. Счётчики должны иметь ограниченную кардинальность labels (меток); не помещайте туда request ID, пользовательский текст или секреты. График среднего времени может скрывать хвост задержек, а средняя глубина очереди — короткий опасный пик. Для каждой метрики напишите единицу, окно, источник и известное ограничение.

## Три запускаемых примера

### Пример 1: обычный путь

```go
package main

import "fmt"

func CapacityClass(workers int, arrival int) string {
	if workers <= 0 || arrival < 0 { return "invalid" }; if arrival > workers { return "over" }; return "within"
}

func main() { fmt.Println(CapacityClass(2, 2)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 2: решение с несколькими сигналами

```go
package main

import "fmt"

func CapacityBudget(workers int, reservePercent int) int {
	if workers <= 0 || reservePercent < 0 || reservePercent > 100 { return -1 }; p := 100-reservePercent; return workers/100*p + (workers%100)*p/100
}

func main() { fmt.Println(CapacityBudget(100, 20)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 3: проверка ограниченного инварианта

```go
package main

import "fmt"

func CapacityDecision(workers int, arrival int, reservePercent int) string {
	if workers <= 0 || arrival < 0 || reservePercent < 0 || reservePercent > 100 { return "invalid" }; p := 100-reservePercent; budget := workers/100*p + (workers%100)*p/100; if arrival > budget { return "over" }; return "within"
}

func main() { fmt.Println(CapacityDecision(100, 81, 20)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.


## Безопасная целочисленная граница

Пусть `p=100-reservePercent`, поэтому при валидном проценте `1<=p<=100`. Разложим `workers=100*q+r`, где `q=workers/100`, `r=workers%100`. Тогда `floor(workers*p/100)=q*p+floor(r*p/100)`. Первая часть не больше workers, вторая перемножает только значения меньше 100. Сумма остаётся в диапазоне `[0, workers]`, поэтому 64-битный MaxInt не оборачивается в отрицательное значение. Сначала обязательно проверьте workers>0, reservePercent∈[0,100) и arrival>=0. Формула убирает переполнение именно в этой helper; она не измеряет очередь, входящий поток или реальную пропускную способность сервиса.

## Практическая процедура

Числа следует читать вместе с формой распределения и способом получения. Для SLI (индикатора уровня сервиса) задайте добрые и плохие события; для SLO (цели уровня сервиса) — окно и допустимую долю плохих. Error budget (бюджет ошибок) нельзя рассчитывать без знаменателя и политики для отсутствующих данных. Если измерение происходит на локальной машине, в отчёте фиксируются версия Go, версия ОС, команда, вход, прогрев, повторы и состояние зависимостей. Бенчмарк Go измеряет указанный код в указанном окружении, а не обещает latency живого HTTP сервиса.

Fault injection (инъекция отказа) помогает проверить выбранную границу только при ограниченном воздействии и заранее известном stop condition (условии остановки). Сначала сформулируйте ожидаемый инвариант и исходное состояние, затем вызовите один сценарий сбоя, соберите события и проверьте восстановление. Не запускайте эксперимент на пользовательских данных или внешней инфраструктуре. Укажите, какой отказ моделируется, какой не моделируется и какие гарантии остаются неизвестны. Результат локального симулятора подтверждает только написанное правило для выбранной последовательности, а не устойчивость неизвестной системы.

Для rollout (постепенного выпуска) задайте малую долю трафика или фиксированную тестовую выборку, критерии расширения и автоматическую/ручную остановку. Canary (канареечный запуск) сравнивает новую версию с baseline при сопоставимом input; отличие трафика может сделать сравнение бессмысленным. Rollback (откат) должен учитывать миграцию схемы, формат событий и уже записанные данные. Нельзя расширять rollout из-за отсутствия сигналов, если мониторинг не готов. Минимальная выборка, окно и последовательность остановки — часть правила, а не детали после выпуска.

P4 ScaleLab — учебный стенд, где гипотеза превращается в воспроизводимую карточку измерения. Запишите commit или точный исходный файл, Go version, ОС/архитектуру, CPU, команду, все flags, dataset hash, число запусков и итог каждого запуска. Сначала сохраните baseline, затем меняйте один фактор и повторите на том же input. Отмечайте метрики, которые ухудшились, и проверяйте функциональную корректность. Не выбирайте только самый удачный запуск. Можно применить benchstat для статистического сравнения `go test -bench`, но само наличие инструмента не превращает плохой эксперимент в валидный.

Разбор postmortem (послеинцидентный разбор) начинает с временной шкалы и наблюдаемых фактов: какие сигналы были доступны, что видели участники, какие действия предпринимались и почему защитная мера не сработала. Blameless (без обвинения) не отменяет ответственности за конкретные действия; он помогает исправить интерфейсы, лимиты, алерты, процедуры и проверки, которые формировали решение. Action item (пункт действия) должен описывать проверяемое изменение, владельца и критерий закрытия. «Будьте внимательнее» не является технической мерой и обычно не предотвращает повторение.

Не смешивайте локальную классификацию с гарантиями распределённой системы. Несколько реплик могут независимо принять работу, часы могут расходиться, метрика приходить с задержкой, а lease истечь во время выполнения. Чистая функция не знает о конкурентных транзакциях и сетевом partition (разделении сети). Для реальной гарантии требуются протокол, ownership, хранилище состояния, fencing или другой механизм, а затем тесты и threat model. В этой главе мы сознательно удерживаем задачу внутри небольшой модели и перечисляем, чего модель не покрывает.

Как автор отчёта, сформулируйте утверждение так, чтобы его можно было опровергнуть: например, «при входе ниже установленного лимита функция выбирает admit», а не «сервис выдерживает нагрузку». Приложите данные до и после, укажите неопределённость и альтернативное объяснение. Не удаляйте неудачные повторы. Если измерение изменилось одновременно с нагрузкой, версией runtime и размером очереди, причинный вывод не следует из этих цифр. Предложите следующий эксперимент, который различит гипотезы.

Когда вы завершите главу, вы сможете рассуждать о capacity, показать ограниченную политику и объяснить её границы. Это учебный навык, а не production-опыт и не подтверждение готовности к дежурствам. В проекте P4 результаты должны быть воспроизводимыми и проверяемыми другим читателем. В следующем уроке предполагайте, что ваши фактические измерения могут опровергнуть исходное ожидание; именно это делает инженерную практику полезной.

## Разбор сценария: Оценка ёмкости и устойчивый запас

Рассмотрим фиктивный сервис при ограничениях из лабораторной карточки. Он получает конечный поток однотипных учебных задач; приём и завершение фиксируются раздельно. Зафиксируйте входной объём, единицы, длительность и одновременность. Если задача занимает разное время, повторите сценарий на одинаковом наборе или разделите типы. Не подменяйте синтетический набор живым трафиком. До старта договоритесь о верхнем пределе памяти, числе исполнителей и поведении при остановке. Эти пределы — часть эксперимента, даже если программа выполняется только локально.

Затем запишите ожидаемое поведение по шагам: новый элемент предлагается; политика допуска отвечает; элемент ожидает или исполняется; завершение либо ошибка учитывается; повтор ограничивается; закрытие прекращает приём и сохраняет допустимый результат. Для каждой точки назовите, какую информацию видит вызывающая сторона. Если вызывающая сторона получает timeout, неизвестно, завершился ли эффект; повтор требует idempotency key или запроса состояния. Если элемент durable (сохраняемый), необходимо определить срок хранения и очистку. Если он ephemeral (временный), честно описать риск потери при перезапуске.

Сначала прогоните обычный случай, потом один граничный, затем один отказ. Сохраняйте входы и ответы, а не только итоговую метку. При обнаружении ошибки зафиксируйте текущий результат, исправьте ровно одно правило и повторите тот же набор. Это покажет разницу между изменением кода и изменением данных. Когда результат не изменился, проверьте, что тест действительно доходит до интересующей ветки и что ожидание различает состояния. Тест с единственным ожидаемым happy path (успешным путём) не защищает от перегрузки.

Сформулируйте эксплуатационную реакцию заранее: кто получает сигнал, какое действие безопасно, как долго допускается деградация и как подтвердить восстановление. В настоящей системе эти решения должны учитывать владельцев данных, изоляцию tenant, секреты, резервное восстановление и договорённости между командами. В упражнении они остаются открытыми проектными вопросами, а не симулируются недостающей кнопкой. Не указывайте выдуманное значение SLA. Если продукта нет, SLO является только целевой гипотезой лаборатории.

После прогона подготовьте короткий evidence package (набор доказательств): код политики, векторы, ожидаемые и фактические ответы, точная команда и версия Go. Для benchmark добавьте результаты каждой репетиции, переделанную версию и baseline. Для fault case сохраните описание воздействия и условие остановки. Дайте другому читателю возможность повторить процедуру без догадки. Если вход зависит от seed, сохраните seed; если зависит от внешнего образа контейнера, закрепите digest либо обозначьте, что он не закреплён. Ничего из этого само по себе не является proof безопасности.


## Практика Easy / Medium / Hard

**Easy — классификация потока.** Реализуйте `CapacityClass` для arrival/workers. Проверьте свободный, точный и превышенный лимит, а также невалидные входы. Единицы в учебной модели должны совпадать.

**Medium — расчет резервного бюджета.** Реализуйте `CapacityBudget`: разделите workers на частное и остаток по 100, затем примените долю после резерва. Проверьте 0%, 1%, 99%, 100%, MaxInt и некорректные диапазоны.

**Hard — решение допуска.** Реализуйте `CapacityDecision`, соединив валидацию, расчет и сравнение arrival с бюджетом. Проверьте равенство на точной границе и соседнее превышение, в том числе при MaxInt. Это проверяет арифметику модели, не реальный capacity.
