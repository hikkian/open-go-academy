# Первый HTTP-сервер на net/http

## Handler — программа, отвечающая на один запрос

Пакет `net/http` стандартной библиотеки Go предоставляет HTTP клиент, сервер, маршрутизацию и тестовые инструменты. Handler (обработчик) — значение с методом `ServeHTTP(http.ResponseWriter, *http.Request)`. Сервер вызывает его для входящего запроса; тест может вызвать тот же метод напрямую. Поэтому сначала удобно научиться проверять обработчики в памяти, без открытого порта и риска случайно опубликовать сервер.

`http.ResponseWriter` предоставляет место для заголовков и ответа. `*http.Request` содержит разобранные метод, URL, заголовки, контекст и тело. Один handler решает поведение запроса; он не обязан читать URL из сети или открывать listener. `http.HandlerFunc` адаптирует функцию с той же парой параметров к интерфейсу Handler.

В HTTP ответе заголовки должны быть заданы до первой записи тела. `WriteHeader(status)` задаёт статус один раз; первый `Write` автоматически отправляет `200 OK`, если статус ещё не указан. Поэтому привычная ошибка — писать JSON, а затем вызывать `WriteHeader(201)`: фактически клиент уже получил `200`. Создайте небольшую функцию `writeJSON`, которая задаёт Content-Type, статус и кодирует тело в одном стабильном порядке.

`http.ServeMux` сопоставляет пути и вызывает нужный handler. Начиная с современного Go можно добавлять шаблоны с методом, например `GET /health`. При использовании версии Go из учебного окружения поведение стандартной библиотеки определено его release; для учебной главы ниже используется методный шаблон. Если проект должен работать на старой версии, используйте совместимый mux и проверьте метод вручную.

```text
http.Server → ServeMux → route match → http.Handler → ResponseWriter
                    Request ──────────────────────→
```

Сервер управляет чтением HTTP протокола, deadline, соединениями и завершением. Mux выбирает handler. Handler проверяет вход и пишет результат. Это полезное разделение, но для первых задач не нужен сложный архитектурный слой.

## Запуск production-сервера и проверка handler — разные действия

`ListenAndServe` открывает реальный listener и остаётся активным до ошибки или остановки. Для локального backend позже потребуется корректно закрывать его через `Shutdown`, задавать тайм-ауты и согласовывать адрес/конфигурацию. Не запускайте сервер на `0.0.0.0` по привычке: адрес bind определяет, кто может соединиться.

`httptest.NewRecorder` и `httptest.NewRequest` позволяют проверить handler прямо в процессе. Такой тест не занимает порт, не зависит от DNS, браузера или внешней службы. Это надёжный первый уровень тестирования HTTP-контракта; настоящие границы сокета и TLS проверяются отдельно.

## Пример 1. Самый короткий handler

Путь `main.go`. Handler отвечает на один локальный запрос.

```go group=first-handler mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	h := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/plain; charset=utf-8")
		w.WriteHeader(http.StatusOK)
		fmt.Fprint(w, "healthy")
	})
	r := httptest.NewRecorder()
	h.ServeHTTP(r, httptest.NewRequest(http.MethodGet, "/health", nil))
	fmt.Println(r.Code, r.Body.String())
}
```

Вывод `200 healthy` подтверждает только вызов handler и запись ответа. `httptest.NewRecorder` хранит ответ в памяти; клиент и сервер не обмениваются TCP-пакетами.

## Пример 2. Методный маршрут через ServeMux

```go group=mux-health mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusNoContent)
	})
	recorder := httptest.NewRecorder()
	mux.ServeHTTP(recorder, httptest.NewRequest(http.MethodGet, "/health", nil))
	fmt.Println(recorder.Code)
}
```

Метод включён в маршрут. При запросе того же пути неправильным методом современный ServeMux различает method mismatch. Не оборачивайте этот ответ ручным `404`, не проверив контракт mux. Явные тесты должны фиксировать маршрут, метод и статус.

## Пример 3. JSON ответ с одним владельцем кодирования

```go group=json-handler mode=run
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	h := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json; charset=utf-8")
		w.WriteHeader(http.StatusOK)
		_ = json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
	})
	recorder := httptest.NewRecorder()
	h.ServeHTTP(recorder, httptest.NewRequest(http.MethodGet, "/health", nil))
	var body map[string]string
	err := json.Unmarshal(recorder.Body.Bytes(), &body)
	fmt.Println(recorder.Code, err == nil, body["status"])
}
```

Encoder добавляет завершающий перевод строки; это корректно для JSON ответа. Тест декодирует body вместо сравнения случайного форматирования JSON.

## Тестирование и ответственность компонентов

Функциональный handler удобно собрать через конструктор `NewHealthHandler() http.Handler`. Конструктор упрощает замену зависимостей в будущих уроках, но сейчас может возвращать один `http.HandlerFunc`. Тест подаёт request fixture и проверяет состояние recorder. Если проверяется JSON, декодируйте его в структуру или `map`.

Минимальный набор для маршрута: ожидаемый метод и путь; обычный успешный ответ; неверный метод; неизвестный путь; требуемый Content-Type; отсутствие неожиданного body для `204`. Добавляйте только проверки, вытекающие из контракта. Группируйте тесты таблицей `name/request/wantStatus/wantBody`, чтобы новая граница не требовала дублировать тестовый boilerplate.

Тесты должны отделять статус от тела: неверный статус может соседствовать с правильным JSON. Для порядка маршрутов важно проверить конкретный запрос, который совпадает с несколькими шаблонами. В серверном коде не используйте глобальное default поведение без понимания, какие handlers зарегистрированы.

### Разбор запроса без предположений

`Request.Method` — строка; маршрут выбирает допустимую операцию. `Request.URL.Path` — декодированная форма пути согласно parser, а `Request.URL.RawPath` может сохранить необычное экранирование. Не используйте поле `RequestURI` вместо структурированной URL для построения бизнес-ID. У `Request.Header` регистронезависимые HTTP ключи; пользуйтесь `Header.Get`, а не индексом произвольного регистра.

Тело — поток `io.ReadCloser`, а не готовая безопасная строка. Его можно прочитать только один раз, если не заменить reader после сохранения байтов. Не делайте `io.ReadAll` без лимита. Для JSON используйте `json.Decoder` после применения ограничителя, проверьте ошибку декодирования, обязательные поля и лишнее значение. Закрытие тела обычно выполняет HTTP server/client infrastructure; handler может закрыть заменённый wrapper, если сам владеет им.

Request context переносит deadline и отмену. Сетевой клиент может отключиться, из-за чего context будет отменён. Долгая работа должна передавать context в зависимости, иначе handler продолжит тяжёлую работу после ухода клиента. Сейчас storage нет, но не добавляйте к каждому запросу `context.Background()` вместо `r.Context()`.

### Обслуживание процесса

Есть важное отличие между конструктором handler и вызовом `http.ListenAndServe`. Конструктор формирует приложение; его можно тестировать многократно. Запуск процесса привязывает порт и принимает неограниченные будущие запросы, поэтому требует конфигурации, timeout, graceful shutdown и логирования. Учебные задания намеренно останавливаются на первом компоненте. Запускаемый backend будет отдельным интеграционным этапом.

Не используйте `http.DefaultServeMux` и `http.HandleFunc` глобально в пакете для учебных маршрутов. Глобальная регистрация делает тесты зависимыми от порядка, может случайно смешать маршруты и превращает состояние процесса в скрытую зависимость. Фабрика `NewRouter()` возвращает независимый mux для каждого теста.

Когда позже всё-таки запускается процесс, создайте явный `http.Server` с `Addr`, `Handler`, `ReadHeaderTimeout` и разумными общими timeout. `ListenAndServe` возвращает ошибку, когда сервер остановлен; ожидаемая ошибка `http.ErrServerClosed` не равна случайному crash. `Shutdown(ctx)` просит текущие handlers закончить работу в пределах deadline. Эти lifecycle решения относятся к main и конфигурации запуска, а не должны скрываться внутри health handler.

Удобное упражнение для новичка — проследить ownership: main создал mux и server; mux держит зарегистрированные handlers; handler владеет бизнес-ответом одного запроса; writer направляет байты клиенту. Если каждый слой знает про все остальные, возникает жёсткая сцепка. На этом этапе не вводите интерфейс ради интерфейса, но отделите точку запуска от функции, которую тест можно вызвать синхронно.

### Ответ должен иметь одного владельца

После отправки status нельзя изменить уже записанные headers. Это похоже на необратимую границу: сначала соберите и проверьте данные, затем начинайте ответ. Если JSON encoder может отказать из-за writer, handler не может отправить второй JSON error поверх частичного первого. Серверный лог может отметить сбой записи, но клиент мог уже увидеть часть тела.

Если API поддерживает `HEAD`, должен быть такой же статус и представление headers, что у GET, но без фактического тела. Стандартный ServeMux поддерживает method matching в современном Go; тестируйте реальный наблюдаемый ответ, а не только то, что handler зарегистрирован. Для `405` укажите `Allow`; если framework выставляет его автоматически, проверьте итог.

## Типичные ошибки

- **Вызывать `WriteHeader` после body.** Проверьте порядок: headers → status → body. Если забыли explicit status, первый write автоматически отправляет 200.
- **Игнорировать ошибку JSON Encoder.** Запись ответа может завершиться ошибкой соединения. Handler может записать её в безопасный server-side log, но уже отправленный клиенту статус исправить нельзя.
- **Вручную конкатенировать JSON.** Кавычки и управляющие символы требуют экранирования. Используйте `encoding/json`.
- **Считать recorder полноценным сервером.** Он не тестирует bind, TLS, сетевые тайм-ауты и client behavior.
- **Обрабатывать все запросы как GET.** Явно проверяйте method или используйте method route. Необработанные методы должны иметь понятный ответ.
- **Возвращать ошибки только в тексте.** Статус и стабильный код в теле нужны клиенту для детерминированной реакции.

Если recorder показывает `200`, а вы задали `201`, найдите первую операцию записи в writer. Если тело пустое, проверьте early return, метод и выбранную mux ветку. Если тест получает `404`, проверьте точное совпадение пути и наличие маршрута; разделяйте маршрутное отсутствие и доменное отсутствие ресурса.

При отладке проверьте также, что ваш тест реально вызвал нужный handler. Частая ошибка: тест проверяет правильный recorder, но зарегистрировал другой mux или создал URL с лишним slash. Покажите в failure сообщение `got status/body/header`, это сократит время поиска. Используйте независимый recorder для каждого запроса: повторное использование ответа скрывает накопленные body bytes и headers от предыдущего случая.

## Практика

- **Easy:** создайте handler для `GET /health`, который возвращает JSON `{"status":"ok"}` со статусом `200` и корректным Content-Type. На другой метод верните контрактный отказ.
- **Medium:** через `httptest` проверьте POST JSON echo handler: декодируйте переданный объект и верните поля в JSON; malformed body должен дать клиентский error, а не `500`.
- **Hard:** постройте in-memory handler коллекции ссылок: `GET /links` возвращает фиксированный список, неверный путь — `404`, другой метод — `405`/`Allow`. Не создавайте настоящую сеть или хранилище.

Проверяемые критерии: точные метод и маршрут; корректный статус; заголовки до тела; семантически одинаковый JSON; ответы на неверный метод, неизвестный путь и malformed input. Размер тела пока ограничится в следующей главе. Решение держите в отдельном каталоге и сначала проверьте публичные cases, затем добавьте собственную таблицу.

## Мини-глоссарий

- **`net/http`** — пакет стандартной библиотеки для HTTP клиента и сервера.
- **handler (обработчик)** — компонент, реализующий `ServeHTTP`.
- **`ResponseWriter`** — интерфейс формирования ответа.
- **`ServeMux`** — стандартный выбор маршрута и handler.
- **`httptest`** — инструменты тестирования HTTP в памяти.
- **listener (слушатель)** — сетевой endpoint, принимающий соединения.
- **method route** — маршрут, выбирающий handler также по HTTP методу.
- **JSON encoder** — компонент стандартной библиотеки для JSON сериализации.
