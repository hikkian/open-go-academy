# SLI, SLO и error budget

## Что ты сделаешь

Ты научишься задавать индикатор уровня сервиса так, чтобы его можно было посчитать и оспорить: что считается хорошим событием, что плохим, что в знаменателе, что делать с отсутствующими данными. Разберёшь, как из цели и окна получается бюджет ошибок, и посчитаешь его без переполнения на любых `int`. Три функции урока — `SLOBand`, `SLOMeets`, `BudgetRemaining` — это арифметика счётчиков и порога; они не собирают запросы и не задают продуктовую цель.

## Зачем нужна эта граница

Индикатор уровня сервиса (SLI) — измеримая доля или распределение событий, связанных с опытом пользователя: доля успешных запросов, доля запросов быстрее порога, доля свежих результатов. Цель уровня сервиса (SLO) задаёт порог для индикатора и окно: «99,5 % запросов успешны за 30 дней». Бюджет ошибок (error budget) — допустимое число плохих событий, вытекающее из цели и того же знаменателя: при миллионе запросов за окно и цели 99,5 % бюджет — пять тысяч ошибок.

До вычисления определи: что такое хорошее событие и плохое; единицу учёта (запрос, пользовательская операция, минута); фильтр (исключаем ли проверки здоровья и ботов); обработку отсутствующих данных. Запрос без ответа не должен исчезать из знаменателя только потому, что телеметрия не записалась — иначе падение сборщика метрик «улучшает» SLI. Ноль событий — не идеальный результат, а отсутствие данных, и для него нужно отдельное правило.

```go group=band mode=run
package main

import "fmt"

func sloBand(total, failed int) string {
    if total <= 0 || failed < 0 || failed > total {
        return "invalid"
    }
    if failed == 0 {
        return "within"
    }
    return "errors"
}

func main() {
    fmt.Println(sloBand(100, 0), sloBand(100, 1), sloBand(0, 0), sloBand(-1, 1), sloBand(10, -1), sloBand(10, 11))
}
```

Вывод:

```text
within errors invalid invalid invalid invalid
```

Нулевой знаменатель — `invalid`, а не `within`: без событий нечего оценивать. Больше ошибок, чем событий, — ошибка учёта, и её лучше увидеть как `invalid`, чем как «100 % ошибок».

> **Важно.** Учебная арифметика — не SLA. SLA — договор с последствиями за нарушение; SLO — внутренняя цель; SLI — измерение. Число без политики «что делаем при исчерпании бюджета» ничего не описывает.

## Порог без переполнения

Цель «не больше `p` процентов ошибок» означает допустимое число плохих событий `floor(total · p / 100)`. Умножать `total` на `p` нельзя: при `total` около `MaxInt` произведение переполнится и порог станет отрицательным. Умножать `failed` на 100 — тоже. Считают через частное и остаток: `(total/100)·p + (total%100)·p/100`. Первое слагаемое не превышает `total`, второе — меньше `p`, переполнения нет.

```go group=meets mode=run
package main

import "fmt"

func sloMeets(total, failed, maxErrorPercent int) bool {
    if total <= 0 || failed < 0 || failed > total || maxErrorPercent < 0 || maxErrorPercent > 100 {
        return false
    }
    allowed := (total/100)*maxErrorPercent + (total%100)*maxErrorPercent/100
    return failed <= allowed
}

func main() {
    maxInt := int(^uint(0) >> 1)
    fmt.Println(sloMeets(100, 1, 1), sloMeets(100, 2, 1), sloMeets(1, 0, 0))
    fmt.Println(sloMeets(maxInt, maxInt, 0), sloMeets(maxInt, maxInt, 100), sloMeets(-1, 1, 2))
}
```

Вывод:

```text
true false true
false true false
```

При цели «0 % ошибок» допустимо ноль плохих событий: один запрос без ошибок проходит, `MaxInt` ошибок из `MaxInt` — нет. При цели «100 %» проходит всё. Проценты вне диапазона — `false`, как и некорректные счётчики; `false` здесь — «цель не выполнена или вход негоден», и в отчёте это различают отдельно.

> **Типичная ошибка.** Сравнивать `failed*100/total <= p`. На обычных числах работает, на больших даёт переполнение, а ещё теряет точность: 1 ошибка из 150 при цели 0,5 % — это 0 % по целочисленному делению и «выполнено».

## Остаток бюджета

Остаток бюджета — допустимое число ошибок минус фактическое. Положительный остаток — запас на окно, ноль — бюджет исчерпан ровно, отрицательный — превышен. Для некорректного входа нужен сигнал, который нельзя спутать с остатком: минимальное значение `int` — оно не может быть настоящим остатком, потому что допустимое число ошибок неотрицательно, а `failed` не больше `total`.

```go group=budget mode=run
package main

import "fmt"

func budgetRemaining(total, failed, maxErrorPercent int) int {
    minInt := -int(^uint(0)>>1) - 1
    if total <= 0 || failed < 0 || failed > total || maxErrorPercent < 0 || maxErrorPercent > 100 {
        return minInt
    }
    allowed := (total/100)*maxErrorPercent + (total%100)*maxErrorPercent/100
    return allowed - failed
}

func main() {
    fmt.Println(budgetRemaining(100, 1, 1), budgetRemaining(100, 2, 1), budgetRemaining(100, 0, 100), budgetRemaining(1, 0, 0))
    fmt.Println(budgetRemaining(100, 0, 101) == -int(^uint(0)>>1)-1)
}
```

Вывод:

```text
0 -1 100 0
true
```

Именно остаток error budget — число оставшихся допустимых ошибок — становится операционным сигналом. Остаток в событиях, а не в процентах: «осталось 37 ошибок до конца окна» — это число, по которому можно принять решение о выкладке, а «0,004 %» — нет. Остаток error budget и есть то, что ограничивает риск: выкладки замораживают, когда он близок к нулю, и ускоряют, когда его много.

> **Зачем.** Бюджет связывает надёжность с темпом изменений: если его тратят инциденты, выпусков становится меньше; если бюджет не расходуется, можно рисковать больше.

## Что счётчики умеют и чего нет

Индикаторы на основе счётчиков «хорошие из всех» описывают доли: доступность, долю быстрых ответов, если быстрый ответ определён порогом и считается как хорошее событие. Для цели «99 % запросов быстрее 300 мс» пороговые счётчики good/total позволяют проверить именно это условие: считаем запросы быстрее порога и все запросы. Но они не позволяют восстановить точное числовое значение p95: из двух счётчиков не узнать, была ли медленная часть на 310 мс или на 3 секунды. Для распределения задержки нужны гистограммы с бакетами, а для точных квантилей — сырые наблюдения или sketch.

Поэтому формулировка цели определяет инструмент: «доля быстрее порога» — счётчики; «p95 не выше» — гистограмма с заранее выбранными границами; «медиана не выше» — тоже гистограмма. Сравнивать SLO по доле с SLO по квантилю нельзя — они измеряют разное.

## Алерт по скорости сжигания бюджета

Алерт «SLI ниже цели» приходит, когда бюджет уже потрачен. Полезнее следить за скоростью сжигания (burn rate): какая доля бюджета окна уходит за час. Если за час сгорает столько, сколько рассчитано на день, — это инцидент, даже если SLI за месяц ещё в норме. Два окна — короткое для быстрых сбоев и длинное для медленной деградации — ловят разные классы проблем; у каждого свой порог скорости и своя срочность. Скорость считается по тем же счётчикам good/total, что и сам индикатор, и наследует их ограничения: если телеметрия теряет события, скорость сжигания занижена.

## Владелец и политика

У индикатора есть владелец, который отвечает за определение и его изменения; у цели — политика: что происходит при исчерпании бюджета (заморозка выпусков, приоритет надёжности над функциями, разбор инцидентов), кто её применяет и как снимается. Цель без политики — число на графике. Окно тоже выбирают осознанно: скользящие 30 дней сглаживают, календарный месяц даёт «обнуление» первого числа, короткое окно для алертов — часы. Разные окна для одной цели — нормально, если записано, какое для чего.

## Практическая процедура

Для одной операции сервиса запиши: хорошее событие, плохое, единицу, фильтр, правило для отсутствующих данных, окно, цель в процентах, владельца, политику при исчерпании. Посчитай бюджет на ожидаемое число событий функцией из урока и проверь руками границу: ровно допустимое число ошибок — цель выполнена, на одну больше — нет. Затем для цели по задержке реши, нужны ли счётчики или гистограмма, и запиши порог или границы бакетов.

## Типичные ошибки

- Исчезновение запросов без ответа из знаменателя: сбой телеметрии «улучшает» SLI.
- Ноль событий как 100 % доступности.
- Умножение счётчиков при расчёте порога: переполнение на больших числах, потеря точности на малых.
- Остаток бюджета в процентах вместо событий: по нему не принять решение.
- Цель по p95 на счётчиках good/total: невозможно.
- Цель без владельца и политики: число без последствий.

## Самостоятельная лаборатория

Возьми журнал запросов учебного сервиса за час и определи для него SLI доступности и SLI скорости с порогом. Посчитай оба по счётчикам и бюджет ошибок на цель 99 % функциями урока. Затем удали из журнала десять процентов строк «как будто телеметрия упала» и пересчитай — запиши, как изменились доли и почему это проблема. Построй гистограмму задержки с пятью бакетами и покажи, что p95 из неё — интервал, а не число.

## Если что-то пошло не так

- `within` при `total = 0` → нулевой знаменатель — `invalid`.
- Отрицательный порог на `MaxInt` → умножение до деления.
- `true` при `failed` на единицу больше допуска → сравнение `<` вместо `<=` или порог округлён вверх.
- Остаток не `MinInt` для процента 101 → проверка диапазона процента отсутствует.
- `-1` вместо `MinInt` для некорректного входа → сигнал некорректности должен быть неотличим от остатка.
- `import … is not allowed` → импорты запрещены; `MinInt` — `-int(^uint(0)>>1) - 1`.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках, `bool` и числами. Закрытые примеры включают `MaxInt`; расчёт обязан не переполняться.

### Задание 1 · Easy: sli, slo и error budget — классификация

**Цель.** `total ≤ 0` или `failed` вне `[0, total]` → `invalid`; `failed = 0` → `within`; иначе `errors`.

**Ожидаемый вывод** — для `(100, 0)` и `(100, 1)`:

```text
"within"
"errors"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func SLOBand(total int, failed int) string`. Импорты запрещены.
2. Валидность, затем `failed == 0`.
3. «Запустить», «Проверить» — закрытые примеры: `total = 0`, `total = -1`, `failed = -1`, `failed > total` → `invalid`.

**Как проверить себя.** Единственная ошибка — уже `errors`; нулевой знаменатель — ошибка входа.

**Если не принято.**
- `within` для `(0, 0)` → проверка `total <= 0` отсутствует.
- `errors` для `(10, 11)` → `failed > total` — `invalid`.

> **Подсказка.** Три `return`; это предусловие для двух следующих функций.

### Задание 2 · Medium: sli, slo и error budget — политика

**Цель.** `false` при некорректных счётчиках или проценте вне `[0, 100]`; иначе `true`, если `failed` не больше `floor(total · maxErrorPercent / 100)`, посчитанного без переполнения.

**Ожидаемый вывод** — для `(100, 1, 1)` и `(100, 2, 1)`:

```text
true
false
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func SLOMeets(total int, failed int, maxErrorPercent int) bool`. Импорты запрещены.
2. Проверь диапазоны; `allowed := (total/100)*maxErrorPercent + (total%100)*maxErrorPercent/100`.
3. Верни `failed <= allowed`. «Запустить», «Проверить» — закрытые примеры: `MaxInt` при 0 % → `false`, при 100 % → `true`; `(1, 0, 0)` → `true`; отрицательный `total` → `false`.

**Как проверить себя.** Ровно допустимое число ошибок — `true`, на одну больше — `false`; на `MaxInt` ответ верный и без переполнения.

**Если не принято.**
- `false` на `MaxInt` при 100 % → переполнение в произведении.
- `true` при `failed = allowed + 1` → сравнение нестрогое в другую сторону.

> **Подсказка.** Частное на процент не больше `total`, остаток на процент — меньше 10 000: складывать безопасно.

### Задание 3 · Hard: sli, slo и error budget — остаток бюджета

**Цель.** Некорректный вход → минимальный `int`; иначе допустимое число ошибок (как в задании 2) минус `failed`: положительно — запас, ноль — исчерпан, отрицательно — превышен.

**Ожидаемый вывод** — для `(100, 1, 1)` и `(100, 2, 1)`:

```text
0
-1
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func BudgetRemaining(total int, failed int, maxErrorPercent int) int`. Импорты запрещены.
2. `minInt := -int(^uint(0)>>1) - 1`; при некорректном входе верни его.
3. Посчитай `allowed` без переполнения и верни `allowed - failed`.
4. «Запустить», «Проверить» — закрытые примеры: процент 101 → `MinInt`; `MaxInt` ошибок при 0 % → `-MaxInt`; `MaxInt` при 100 % → `0`; `(100, 0, 100)` → `100`.

**Как проверить себя.** `MinInt` не может быть настоящим остатком, поэтому он однозначно означает некорректный вход; остаток считается в событиях.

**Если не принято.**
- `-1` для некорректного входа → перепутан с остатком «превышен на одно событие».
- Неверный остаток на `MaxInt` → переполнение в `allowed`.

> **Подсказка.** Это задание 2 с вычитанием вместо сравнения и другим сигналом ошибки.

## Итог

- SLI — измерение с названными хорошим и плохим событием, знаменателем, фильтром и правилом для пропусков; SLO — порог и окно; бюджет — события, а не проценты.
- Порог и остаток считают через частное и остаток от деления на сто; некорректный вход сигналят значением, которое не может быть остатком.
- Счётчики измеряют доли, гистограммы — распределения; у цели есть владелец, окно и политика при исчерпании бюджета.
