# 21. SLI, SLO и error budget

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-20`
**Цель:** SLI (индикатор уровня сервиса) измеряет конкретный аспект опыта, SLO (цель уровня сервиса) задаёт порог для окна, а error budget (бюджет ошибок) — допустимую долю плохих событий в этом окне. Эти определения требуют знаменателя, фильтрации и правила обработки отсутствующих данных. Учебная арифметика не является SLA и не описывает доступность внешнего сервиса.

## Термины и перевод

- **SLI и SLO** — SLI (индикатор уровня сервиса) измеряет конкретный аспект опыта, SLO (цель уровня сервиса) задаёт порог для окна, а error budget (бюджет ошибок) — допустимую долю плохих событий в этом окне. Эти определения требуют знаменателя, фильтрации и правила обработки отсутствующих данных. Учебная арифметика не является SLA и не описывает доступность внешнего сервиса.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Индикатор уровня сервиса (SLI) — измеряемая доля или распределение событий, связанных с опытом пользователя. Цель уровня сервиса (SLO) задаёт порог и временное окно для выбранного индикатора. Бюджет ошибок — допустимое число или доля плохих событий, вытекающая из цели и того же знаменателя.

До вычисления определите good event (хорошее событие), bad event (плохое событие), единицу учёта, фильтр и обработку отсутствующих данных. Например, запрос без ответа не должен исчезать из знаменателя только потому, что телеметрия не записалась. Если событий ноль, долю нельзя трактовать как идеальный результат без отдельного правила.

Helper арифметически проверяет заданные счётчики и порог. Он не собирает запросы, не задаёт продуктовый SLO и не подтверждает SLA — договорённый уровень сервиса. Отдельно определите владельца метрики и действия при исчерпании бюджета; одно число без политики не описывает операционное решение.

## Три запускаемых примера

### Пример 1: обычный путь

```go
package main

import "fmt"

func SLOBand(total int, failed int) string {
	if total <= 0 || failed < 0 || failed > total { return "invalid" }; if failed == 0 { return "within" }; return "errors"
}

func main() {
	fmt.Println(SLOBand(100, 0))
	fmt.Println(SLOBand(100, 1))
}
```

Скомпилируйте сохранённый блок как `go run main.go`. Вывод: `within`, затем `errors`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 2: решение с несколькими сигналами

Чтобы поддержать любой положительный `int`, включая `MaxInt`, нельзя непосредственно умножать `failed*100` или `total*maxErrorPercent`: оба произведения могут переполниться. Вместо этого вычислите целочисленный порог `floor(total*percent/100)` через частное и остаток: `(total/100)*percent + (total%100)*percent/100`. При `percent` в `[0,100]` каждая промежуточная величина не превышает `total`, а произведение остатка на процент не больше 9900.

```go
package main

import "fmt"

func SLOMeets(total int, failed int, maxErrorPercent int) bool {
	if total <= 0 || failed < 0 || failed > total || maxErrorPercent < 0 || maxErrorPercent > 100 {
		return false
	}
	allowed := (total/100)*maxErrorPercent + (total%100)*maxErrorPercent/100
	return failed <= allowed
}

func main() { fmt.Println(SLOMeets(100, 1, 2)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 3: проверка ограниченного инварианта

```go
package main

import "fmt"

func BudgetRemaining(total int, failed int, maxErrorPercent int) bool {
	if total <= 0 || failed < 0 || failed > total || maxErrorPercent < 0 || maxErrorPercent > 100 {
		return false
	}
	allowed := (total/100)*maxErrorPercent + (total%100)*maxErrorPercent/100
	return failed <= allowed
}

func main() { fmt.Println(BudgetRemaining(100, 1, 2)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.


## Практическая процедура

Опишите метрику одной фразой: «числитель — ..., знаменатель — ..., окно — ..., исключения — ...». Затем вручную рассчитайте несколько маленьких наборов: все события хорошие, одно плохое, ровно на границе и отсутствующие/нулевые данные. Сопоставьте долю с порогом и проверьте, не округляет ли функция до сравнения.

Определите, как окно движется и что происходит с запоздавшим сигналом. Если метрика вычисляется по запросам, укажите, учитываются ли отмены и ошибки зависимости. Для error budget (бюджета ошибок) покажите формулу, исходное число событий и политику, когда данные неполны.

Сохраните версии входных значений и результат. Векторы проверяют учебную арифметику и её границы; они не дают измерений живого сервиса и не выбирают приемлемую цель. Без реальных данных SLO остаётся лабораторной гипотезой, а не обещанием доступности.

## Разбор сценария: SLI, SLO и error budget

Возьмите конечную таблицу событий за условное окно и пометьте каждое как хорошее, плохое или неучтённое по заранее заданному правилу. Рассчитайте знаменатель и долю плохих, затем сравните с целью. Покажите граничный случай, где значение ровно равно порогу, и объясните, включительна ли граница.

Теперь удалите один сигнал и снова выполните расчёт. Если политика считает пропуск неизвестным, результат должен быть «недостаточно данных», а не молчаливое улучшение доли. Если упражнение принимает только числа, явно отметьте, что helper не умеет отличать потерю телеметрии от отсутствия событий.

Сформулируйте решение, которое следует из модели, и отделите его от управленческого действия. Вычисленный остаток бюджета не говорит автоматически, что выпуск нужно остановить. Не назначайте внешнему сервису выдуманный SLA; для проверки реального SLI понадобятся источник телеметрии, верифицированное окно и правила неполных данных.

## Лаборатория: определить знаменатель до вычисления SLO

### Численный сценарий

Пусть за окно поступило 1000 запросов. По контракту 985 завершились успешно в пределах целевой задержки, 10 завершились ошибкой, ещё 5 не получили наблюдаемого результата из-за разрыва телеметрии. Если считать только записанные успешные и ошибочные события, доля плохих равна 10 из 995. Если неизвестные пять запросов включить как плохие до восстановления данных, это 15 из 1000. Выбор политики меняет результат; его нельзя спрятать в коде округления.

При цели не хуже 2% первый вариант даёт около 1,01%, второй — 1,5%; оба внутри цели, но расход бюджета разный. При более строгой цели 1,2% выводы разойдутся. Поэтому численный helper должен получить уже согласованные счётчики и не может сам решить, что означает потерянный сигнал. Дополнительно проверьте нулевой знаменатель: доля для окна без учтённых событий не равна автоматически нулю ошибок.

### Постройте спецификацию индикатора

Запишите определение одной метрики до запроса чисел: событие в знаменателе, условие хорошего события, порог, окно и фильтры. Для задержки укажите, измеряете ли вы долю запросов ниже порога или percentile (процентиль) распределения. Эти определения отвечают на разные вопросы. Например, «95-й процентиль до 300 мс» нельзя вычислить по одним счётчикам хороших и плохих запросов без сохранённого распределения или корректного агрегата.

Укажите источники данных и запоздание. Если событие пришло после закрытия окна, вы пересчитываете окно или фиксируете позднюю корректировку? Если часть сервиса не экспортировала метрики, помечается ли окно неполным? Определите владельца правила и доступный артефакт для повторной проверки. Не подбирайте SLO после просмотра результата так, чтобы он выглядел успешным.

### Проведите ручной расчёт

1. Возьмите небольшие числа, чтобы вычислить долю вручную.
2. Проверьте ровное равенство порогу и соседние значения по обе стороны.
3. Измените только политику неизвестных данных и сравните результат.
4. Рассчитайте допустимое количество плохих событий из общего объёма и цели; не путайте процент и число событий.
5. Пересчитайте при другом окне, чтобы увидеть, как одинаковое количество ошибок влияет на разные знаменатели.

### Обсудите решение и пределы

Error budget (бюджет ошибок) показывает, сколько плохих событий остаётся относительно выбранной цели и окна. Он не является счётом на будущие ошибки и не задаёт автоматическую остановку выпуска. Решение может учитывать длительность нарушения, безопасность изменений, качество сигнала и цену отката. Зафиксируйте правило заранее, а не задним числом.

Helper урока проверяет только предоставленные числа, диапазоны и границу. Он не собирает телеметрию, не обнаруживает двойной учёт и не выбирает цель. Учебный расчёт не создаёт SLA (договорённый уровень сервиса). Для реального SLI нужен независимый источник событий и проверка того, что пропуски, отмены, повторы и запоздавшие данные обработаны последовательно.

### Скользящие окна и смысл бюджета

Фиксированное окно, например календарный час, сбрасывает счётчик на границе. Скользящее окно рассматривает каждый момент относительно предыдущего периода. Один и тот же сбой около границы может выглядеть как короткий всплеск в двух фиксированных окнах или как единое событие в скользящем. При сравнении результатов фиксируйте конкретное правило окна, часовой пояс, задержку доставки и способ учёта запоздавших событий.

Допустим, цель требует 99,9% хороших из 10 000 запросов за окно. Это позволяет не более десяти плохих событий, если граница включительна и знаменатель полный. Для окна только из ста запросов тот же процент не даёт практической точности: один плохой запрос — уже 1%. Небольшая выборка делает долю чувствительной к единичному событию. Поэтому пригодность окна зависит от объёма, пользовательского пути и стоимости ошибки.

Решение о расходовании бюджета может остановить рискованный выпуск или перенаправить усилия на надёжность. Но нельзя переводить бюджет в разрешение «ошибиться ещё N раз» без понимания причин, зависимости и воздействия. Уточните, кто принимает решение и как бюджет пересчитывается после корректировки данных.

### Не скрывайте плохие события фильтром

Фильтр исключений должен быть определён до подсчёта. Например, внутренние health-check запросы могут быть не частью пользовательского опыта, но отменённые пользовательские запросы нельзя автоматически исключить только потому, что они неудобны для показателя. Сохраните число исключённых событий и причину фильтра. Иначе изменение фильтра может улучшить SLI без изменения сервиса.

Проверьте двойной учёт повторов: один пользовательский запрос может породить несколько сетевых попыток. Метрика по попыткам и метрика по логическим операциям отвечают на разные вопросы. Выберите единицу и дедупликацию до агрегации. Helper, принимающий готовые числа, не способен заметить, что знаменатель уже включает retries дважды.

### Точная граница и округление

Доля в процентах часто округляется для экрана, но решение лучше вычислять по целым числам, если это предотвращает ошибки границы. Для 19 плохих событий из 1000 это 1,9%; для 20 — ровно 2%. При цели «не более 2%» второй результат проходит, если сравнение включительное. При цели «менее 2%» он уже нарушает правило. Формулировка должна однозначно задавать `<=` или `<`.

Сохраните исходные числитель и знаменатель, а не только строку «1,9%». При округлении до одного знака 1,95% может отображаться как 2,0%, что затрудняет объяснение решения. Разделите значение для показа и внутреннее точное сравнение. Тестируйте равенство и значения по обе стороны от границы.

Также проверьте переполнение целочисленного произведения при крупном объёме событий. Учебный helper имеет заданные пределы типов; для реального счётчика нужно определить максимальный объём окна и безопасную формулу.

## Практика Easy / Medium / Hard

**Easy — классификация.** Реализуйте первую функцию из контракта и проверьте корректный обычный случай, пустую/нулевую границу и явно невозможное значение. Результат должен точно совпасть с контрактом.

**Medium — политика с приоритетом.** Реализуйте вторую функцию. Сначала перечислите правила сверху вниз; при нескольких одновременно истинных условиях применяется первое. Добавьте тесты обычного состояния, насыщения, неизвестного значения и некорректной комбинации. Для числа/boolean не преобразуйте выход в произвольную строку.

**Hard — инвариант.** Реализуйте третью функцию, которая подтверждает только безопасную комбинацию предусловий. Граничный и противоречивый векторы обязаны отклоняться. Объясните, почему успешный результат helper не является реальным benchmark, fault test, безопасным rollout или гарантией доступности. Public и private cases находятся в JSON specs соответствующих exercise ID.
