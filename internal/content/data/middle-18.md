# Подтверждение сообщения и повторная доставка

## Почему эта тема важна

Ack (подтверждение) сообщает брокеру, что consumer завершил обработку в рамках выбранного протокола. Nack/reject (отрицательное подтверждение) сообщает, что обработка не завершена; брокер может вернуть сообщение, удалить его или отправить в dead-letter в зависимости от флагов и конфигурации. Название метода не определяет семантику без ack mode, requeue policy, очереди и клиента. Поэтому приложение сначала классифицирует исход, а адаптер к брокеру переводит его в корректные вызовы.

Ключевое правило: подтверждение следует за устойчивым эффектом. Если consumer сделал ack, а процесс упал до commit базы, сообщение может исчезнуть, хотя результат не сохранён. Если commit уже состоялся, а ack потерялся, повторная доставка вероятна; handler должен распознать уже применённый event ID или повторный idempotency key. Такая защита должна быть атомарна с доменным изменением: записать «обработано» в отдельной независимой транзакции недостаточно, если между двумя фиксациями возможен сбой.

Повтор нужен для временных ошибок: короткая недоступность базы, ограниченный network timeout или throttling. Ошибка валидации, неизвестный тип события или несовместимая версия payload чаще постоянны; бесконечный retry только забивает очередь. Задайте максимальное число попыток, backoff и jitter (разброс задержки), чтобы множество worker-ов не повторяли запрос одновременно. После лимита используйте dead-letter маршрут с безопасным диагностическим контекстом, причиной и event ID. Не включайте секреты и полные пользовательские payload в логи.

Неизвестный результат сложнее обычной ошибки. Например, запрос к базе вернул timeout: commit мог состояться до разрыва соединения. Немедленный retry способен повторить эффект. Используйте идемпотентность, проверку состояния операции или отдельный reconciliation workflow. Разделяйте `handlerCommitted` и сетевое знание consumer: локальный факт commit и знание о нём — разные вещи.

Easy классифицирует простой исход handler-а и предел в три попытки. Medium добавляет уже сохранённый эффект: после commit надо ack, а не повторно выполнять работу; если ack не состоялся, повтор при доставке безопасен только с идемпотентной обработкой. Hard вводит состояния `committed`, `uncommitted` и `unknown`: сначала проверяется допустимость состояния, затем committed подтверждается, unknown требует сверки, и только uncommitted оценивает retry budget. Функция не задаёт конкретные nack flags, задержку, DLQ, ack mode или число delivery, которое учитывает брокер.

В интеграционном тесте запустите конкретный брокер и закрепите настройки очереди. Проверьте успешный ack; временную ошибку и повтор; permanent error и dead-letter; падение consumer после commit до ack; падение до commit; отмену при остановке. Убедитесь, что каждый тест имеет таймаут и очистку ресурсов. Подсчитайте, сколько раз произошёл эффект, а не только сколько раз вызван handler: один доставленный event может вызвать повторное выполнение функции, но итоговый эффект должен остаться один при включённой дедупликации.

Операционная диагностика включает redelivery count, возраст сообщения, глубину retry/DLQ, длительность handler и причину nack. Если увеличивать число попыток без ограничения, постоянная ошибка превращается в нагрузочный инцидент. Если сразу отправлять все ошибки в DLQ, transient outage теряет автоматическое восстановление. Политика должна различать категории и оставлять путь безопасного повторного запуска после исправления причины.

## Практика трёх уровней

**Easy — middle-18-easy.** Реализуйте самый узкий контракт. Перед кодом выпишите таблицу вход → результат, отдельно нормальный случай, границу и некорректное состояние. Не добавляйте состояние, которого нет в сигнатуре. Проверьте, что каждый выход имеет конкретное значение для вызывающего слоя.

**Medium — middle-18-medium.** Добавьте независимый сигнал или состояние из условия. Решайте ветви в заданном порядке: сначала невалидное состояние, затем уже совершённый эффект/отмена, затем доступность ресурса, затем временной лимит и только после этого повтор или отказ. Этот порядок важен там, где две причины истинны одновременно. Проверьте конфликтующие входы из public/private vectors.

**Hard — middle-18-hard.** Добавьте три состояния commit. При unknown сначала нужна сверка по event ID: blind retry может повторить уже сохранённый эффект. Для uncommitted примените retry budget и после его исчерпания отправьте задачу в dead-letter. committed подтверждается независимо от исчерпанного счётчика: повтор эффекта опаснее. Тесты разделяют неопределённость результата и обычную временную ошибку.

## Три исполняемых примера

```go group=middle-18-easy mode=run
package main
import "fmt"


func MessageDispositionEasy(transient bool, attempts int64, succeeded bool) string {
	if attempts < 0 { return "invalid" }
	if succeeded { return "ack" }
	if !transient { return "reject" }
	if attempts >= 3 { return "dead_letter" }
	return "retry"
}

func main() { fmt.Println(MessageDispositionEasy(false, 0, true)) }
```

```go group=middle-18-medium mode=run
package main
import "fmt"


func MessageAckMedium(transient bool, attempts int64, handlerCommitted bool) string {
	if attempts < 0 { return "invalid" }
	if handlerCommitted { return "ack" }
	if !transient { return "reject" }
	if attempts >= 3 { return "dead_letter" }
	return "retry"
}

func main() { fmt.Println(MessageAckMedium(false, 0, true)) }
```

```go group=middle-18-hard mode=run
package main
import "fmt"

func MessageAckHard(commitState string, transient bool, attempts, maxAttempts int64) string {
	if commitState != "committed" && commitState != "uncommitted" && commitState != "unknown" { return "invalid" }
	if commitState == "committed" { return "ack" }
	if commitState == "unknown" { return "reconcile" }
	if attempts < 0 || maxAttempts <= 0 { return "invalid" }
	if !transient { return "reject" }
	if attempts >= maxAttempts { return "dead_letter" }
	return "retry"
}

func main() { fmt.Println(MessageAckHard("unknown", true, 1, 3)) }
```

## Как читать примеры и проверять выводы

Примеры ниже компилируются как небольшие программы и показывают публичный reference для упражнения. Каждый запускает только чистую функцию: в нём нет сетевого клиента, локальной БД, goroutine, таймера, брокера или настоящей конфигурации сервера. Вывод показывает результат контракта на названном input. Он не означает, что внешняя зависимость выдала такой исход, сохранила данные или соблюла порядок. Если пример и формулировка расходятся, исправлять нужно контракт или reference вместе, а не подгонять hidden tests под один частный ответ.

Табличный тест должен называть смысл каждой строки. Укажите входы, ожидаемую категорию и инвариант, который проверяется. Одного «happy path» недостаточно: добавьте точную границу, значение за границей и пересечение двух сигналов, когда приоритет важен. Private vectors должны ловить реализацию, которая всегда возвращает один удобный ответ, игнорирует отдельный аргумент, путает `>=` и `>` или не замечает некорректный счётчик. Случаи должны быть компактны и детерминированы, чтобы ученик мог воспроизвести их локально.

## Что потребуется для реальной проверки

Переход от helper к работающему backend потребует другого набора доказательств. Зафиксируйте версии runtime и зависимости, конфигурацию, лимиты, время ожидания, политику подтверждений и порядок фиксации. Для отказного теста отметьте точку, где процесс останавливается, перезапустите компонент и посчитайте итоговый эффект. Проверяйте, что отмена освобождает ресурсы, повтор не умножает изменение, а постоянная ошибка не крутится бесконечно. Снимайте метрики задержки, backlog и повторов. Unit test не может заменить такие проверки.

Если в системе участвует PostgreSQL, проверьте миграцию, уникальные ограничения, транзакционные границы и конкурентный сценарий на реальном закреплённом движке. Если участвует брокер, тест должен включать его фактический ack/confirm режим и рестарт consumer или relay. Если результат зависит от сети, используйте контролируемый локальный контейнер или fault proxy, а не случайную задержку. Очистка должна быть изолирована от пользовательских данных. Повторяемая команда и зафиксированный fixture позволяют другому разработчику независимо подтвердить результат.

## Диагностика и проектное решение

Начинайте расследование с наблюдаемого состояния: счётчики до операции, момент commit/ack, возвращённая категория, число повторов и конечный эффект. Сверьте часы, единицы измерения и идентификатор операции. Не делайте вывод по одному лог-сообщению, если его могло создать несколько попыток. Корреляционный ID должен быть безопасен и одинаков для повтора; payload, токены, DSN и личные сведения не следует без необходимости писать в лог.

При выборе политики опишите цену обеих сторон. Увеличить ожидание — значит дать системе больше времени, но занять запрос и ресурсы дольше. Быстро отказать — значит сохранить capacity, но передать восстановление вызывающему коду. Повтор — шанс пережить transient сбой и вероятность дублирования. Dead-letter — остановка автоматического шума ценой необходимости диагностики и replay. Хороший middle-level ответ называет условие переключения политики и метрику, которая это условие обнаружит.

Устойчивое решение имеет владельца каждого инварианта. Handler отвечает за решение и контекст; repository — за транзакционное состояние; адаптер брокера — за mapping ack/nack; операторская политика — за лимиты, очередь повторов и восстановление. Не размывайте ответственность между слоями. Наблюдаемая функция из grader помогает изолировать одно правило, а интеграционная система проверяет взаимодействие владельцев. Это разные масштабы доказательства, и оба могут понадобиться.

### Самопроверка

1. Какой вход пересекает границу контракта и меняет решение?
2. Какой отказ может произойти после внешнего эффекта, но до локального подтверждения?
3. Какая часть поведения проверена чистой функцией, а какая требует конкретной инфраструктуры?
4. Какой тест способен обнаружить дубликат, потерю эффекта или утечку ожидающего ресурса?

Перед завершением назовите один непокрытый отказ и один конкретный тест, который мог бы опровергнуть ваше решение. Сохраните команду, fixture, версии и фактическое число эффектов. Не расширяйте утверждение за пределы наблюдений: правильный результат helper — необходимая проверка правила, но не сертификат поведения всей системы.

## Таблица решений для сообщения

Начните с классификации результата handler, а не со значения `requeue` в API. Успех означает: доменный эффект и необходимые записи уже commit-нуты. Постоянная ошибка означает, что тот же вход при повторе не изменится: например, неизвестная версия или нарушенный бизнес-инвариант. Временная ошибка допускает шанс на успех позже: краткая недоступность базы, ограничение скорости или сетевой timeout. Не все сетевые ошибки точно временные: timeout может произойти после commit, поэтому сначала нужна идемпотентная операция либо сверка состояния.

Для Easy вектор `transient=true, attempts=2` при лимите 3 разрешает ещё один retry, а `attempts=3` отправляет в dead-letter. Подсчёт должен иметь однозначную точку: это текущий номер доставки или число уже выполненных попыток? В нашей формулировке attempts — уже начатые попытки, и при `attempts >= limit` новая не начинается. Medium добавляет `handlerCommitted`: после сохранённого эффекта нужно ack, даже если приём ответа вызвал локальную ошибку. Иначе повторится уже выполненная операция. Hard делает maxAttempts явным, чтобы политика не была зашита в magic number.

### Ack, nack и DLQ

Ack только после commit минимизирует риск потери эффекта, но оставляет окно повторной доставки между commit и ack. Nack с requeue может немедленно вернуть сообщение и создать горячую петлю; используйте delayed retry или backoff, если брокер и архитектура это поддерживают. Reject без requeue обычно означает окончательное прекращение повторов, но конкретная судьба сообщения определяется dead-letter binding и конфигурацией. Не полагайтесь на название параметра: проверьте документацию и интеграционное поведение выбранного клиента и версии.

DLQ — не мусорная корзина. Сохраняйте исходный event ID, безопасную причину, число попыток, время последней доставки и версию схемы. Ограничьте доступ и хранение, поскольку payload может содержать данные клиента. Оператор должен иметь процесс классифицировать причину, исправить её, затем безопасно переотправить событие с тем же ID или новым replay ID по принятому контракту. Бесконтрольный replay всей DLQ способен снова перегрузить зависимость.

### Четыре отказные точки

1. Падение до выполнения эффекта: сообщение должно остаться доступным для повторной обработки.
2. Временная ошибка до commit: ограниченный retry может исправить краткий отказ.
3. Падение после commit и до ack: возможен дубликат; dedup защищает доменное изменение.
4. Постоянная ошибка: быстрый бесконечный retry бесполезен; после лимита сообщение изолируется и становится видимым для разбора.

Для каждой точки укажите, кто владеет retry: приложение, middleware, broker или scheduler. Если одновременно включены все слои, число попыток перемножается и может превысить ожидаемый лимит. Например, 5 попыток приложения поверх 10 broker delivery — до 50 обработок. Установите общий бюджет и передавайте оставшееся время/число попыток между слоями, когда это возможно.

### Проверка границы лимита

Протестируйте attempts -1, 0, limit-1, limit и значение выше limit. Для `handlerCommitted=true` решение должно оставаться ack даже на предельном attempts, поскольку повтор не исправляет уже завершённый эффект и может создать дубль. Для постоянной ошибки выбор reject имеет приоритет над transient retry. В Hard проверьте отрицательный attempts при uncommitted и maxAttempts=0 как invalid. При committed даже некорректный retry budget не меняет ack; при unknown он не должен мешать reconcile. Это приоритет состояний, а не одобрение такой конфигурации: отдельный загрузчик обязан валидировать budget при старте.

### Реальный тест адаптера

Откройте фиксированную тестовую очередь, включите ожидаемый ack mode, отправьте событие с ID и выполните контролируемые ошибки. Проверьте, что ack действительно удаляет сообщение, nack/requeue вызывает повтор с ожидаемой задержкой, а reject ведёт в нужный DLQ. Затем остановите consumer в точке после commit до ack. После рестарта broker должен доставить повтор, handler должен распознать ID, и количество бизнес-эффектов останется равным одному. Запишите redelivery count и очистите очередь после assertion. Такой тест подтверждает именно выбранные настройки и версию брокера; он не является универсальной гарантией для другого deployment.

### Расчёт общего бюджета повторов

Попытки должны иметь одну точку отсчёта. Если `attempts` включает текущую доставку, проверка `attempts >= maxAttempts` означает, что текущая обработка уже достигла лимита и следующую не планируем. Если считать только предыдущие повторы, формула будет иной. Уточните это в документации конфигурации и метрике. Локальная функция принимает уже согласованное целое число; она не знает, увеличил ли брокер delivery count до или после вызова handler.

Учитывайте повторы клиента, worker и брокера вместе. Если HTTP producer повторит публикацию трижды, а consumer получит каждую запись пять раз, handler может увидеть пятнадцать запусков. Стабильный event ID должен пережить producer retry; иначе каждый повтор будет выглядеть новой задачей и дедупликация не поможет. Лимит системы следует считать на всём пути, а не отдельно в каждой библиотеке.

Временная ошибка должна быть ограничена общим временем жизни задачи. Если одна попытка занимает 20 секунд и допускается десять, SLA в одну минуту уже невозможен без параллельного исполнения. Backoff уменьшает давление, но продлевает возраст сообщения. Сопоставьте timeout, retry delay, visibility/lease timeout и общий deadline. Если handler ещё работает после истечения lease, broker может выдать ту же задачу другому worker; это снова требует idempotency и управления конкурентностью.

### Термины

- **ack (подтверждение)** — Сообщение обработано и может быть удалено из очереди.

- **nack (отрицательное подтверждение)** — Сообщение не обработано; брокер применяет выбранную политику.

- **redelivery (повторная доставка)** — Повторная выдача сообщения после незавершённой обработки.
