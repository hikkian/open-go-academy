# Подтверждение сообщения и повторная доставка

## Что ты сделаешь

Ты напишешь три функции-решения для потребителя: ack, reject, retry или dead-letter по результату обработки; подтверждение только после фиксации эффекта; и политику для неизвестного результата commit. Функции работают с переданными фактами, поэтому проверяют логику без реального брокера.

## Ack подтверждает устойчивый эффект

Ack (подтверждение) сообщает брокеру, что потребитель завершил обработку по выбранному протоколу. Nack или reject (отрицательное подтверждение) сообщает, что обработка не завершена. Что именно сделает брокер дальше — вернёт сообщение, удалит его или отправит в dead-letter — зависит от флагов, режима подтверждения и конфигурации очереди. Название метода само по себе семантику не определяет.

Главное правило: подтверждение следует за устойчивым эффектом. Если потребитель сделал ack, а процесс упал до commit базы, сообщение исчезнет, а результат не сохранится. Поэтому порядок такой: обработка, фиксация, подтверждение. Пример показывает правильный порядок в журнале:

```go
package main

import "fmt"

func main() {
    steps := []string{"process", "commit"}
    steps = append(steps, "ack")
    fmt.Println(steps)
}
```

Вывод: `[process commit ack]`. Подтверждение стоит последним, и падение до него приводит только к повтору, а не к потере.

> **Важно.** Если commit состоялся, а ack потерялся, повторная доставка вероятна. Обработчик должен распознать уже применённый event ID и не повторить эффект.

## Временная и постоянная ошибка

Повтор нужен для временных ошибок: короткая недоступность базы, ограниченный таймаут сети или ограничение скорости. Ошибка валидации, неизвестный тип события или несовместимая версия payload обычно постоянны. Бесконечный повтор такой ошибки только забивает очередь.

Поэтому сначала классифицируют ошибку: временная она или постоянная. Классификация принадлежит обработчику, потому что только он знает смысл ошибки. Неизвестный тип события — постоянная ошибка, а таймаут сети — временная, но только если эффект точно не зафиксирован.

Поэтому задают предел попыток и растущую паузу между ними. Пауза удваивается на каждом шаге. Пример показывает такой график:

```go
package main

import "fmt"

func main() {
    delay := 100
    for attempt := 1; attempt <= 3; attempt++ {
        fmt.Println(attempt, delay)
        delay *= 2
    }
}
```

Вывод: три строки `1 100`, `2 200`, `3 400`. Удвоение снижает давление на зависимость. В реальной системе к паузе добавляют случайный разброс (jitter), чтобы множество потребителей не повторяли запросы одновременно.

## Лимит попыток

Счётчик попыток должен иметь одну точку отсчёта. Пример показывает, что попытки начинаются при нуле и новая попытка не начинается, когда достигнут лимит:

```go
package main

import "fmt"

func main() {
    limit := 3
    attempts := 0
    for attempts < limit {
        attempts++
    }
    fmt.Println(attempts, attempts >= limit)
}
```

Вывод: `3 true`. Исчерпанный бюджет означает, что сообщение уходит в dead-letter, а не в очередной повтор. Dead-letter очередь — не мусорная корзина: в ней сохраняют исходный event ID, безопасную причину, число попыток и время последней доставки.

## Неизвестный результат

Неизвестный результат опаснее обычной ошибки. Пример: запрос к базе вернул таймаут, а commit мог состояться до разрыва соединения. Немедленный повтор способен повторить эффект.

Поэтому сначала сверяют состояние операции по стабильному идентификатору события. Только если известно, что эффекта нет, можно повторять. Локальный факт commit и знание о нём — разные вещи: процесс может не знать, что commit уже произошёл.

> **Типичная ошибка.** Считать каждую сетевую ошибку временной. Таймаут может произойти после commit, и тогда повтор без сверки создаст дубль.

## Модель и механизм

Подтверждение сообщения — это обещание о результате, которое должно опираться на устойчивый эффект. Модель разделяет три случая: эффект зафиксирован, эффект не зафиксирован и результат неизвестен. Для каждого случая задан свой ответ брокеру.

Для потребителя полезны три вопроса. Зафиксирован ли эффект? Какая ошибка произошла, временная или постоянная? Сколько попыток уже начато? Ответы записываются до написания обработчика.

Синхронизация имеет цену. Подтверждение после commit добавляет окно повторной доставки, а повторы занимают ресурсы. Выбор лимита — продуктовое решение, которое нужно измерять по возрасту сообщения и глубине очереди.

## Типичные ошибки и исправление

Первая ошибка — подтверждать сообщение до фиксации эффекта. Исправление — ack после commit.

Вторая — повторять постоянную ошибку без лимита. Исправление — классификация ошибки и предел попыток.

Третья — повторять неизвестный результат вслепую. Исправление — сверка по стабильному идентификатору.

## Если что-то пошло не так

- Сообщение исчезло, эффекта нет → подтверждение отправлено до commit; перенеси ack после фиксации.
- Эффект выполнен дважды → повтор после потерянного подтверждения не распознан; проверь идентификатор события.
- Очередь забита одной и той же ошибкой → постоянная ошибка повторяется; добавь классификацию и dead-letter.
- Сообщение обрабатывается больше ожидаемого → попытки перемножаются между слоями; задай общий бюджет.

## Четыре точки отказа

Потребитель может упасть в четырёх местах, и для каждого места поведение своё.

Первая точка — падение до выполнения эффекта. Сообщение должно остаться доступным, чтобы его обработали повторно. Вторая — временная ошибка до commit. Ограниченный повтор способен исправить краткий отказ. Третья — падение после commit и до ack. Здесь возможен дубликат, и дедупликация защищает доменное изменение. Четвёртая — постоянная ошибка. Бесконечный повтор бесполезен: после лимита сообщение изолируется и становится видимым для разбора.

Для каждой точки нужно знать, кто владеет повтором: приложение, промежуточный слой, брокер или планировщик. Если все слои повторяют одновременно, попытки перемножаются. Пять попыток приложения поверх десяти доставок брокера дают до пятидесяти обработок. Поэтому устанавливают общий бюджет и передают оставшееся число попыток и время между слоями, когда это возможно.

## Ack, nack и dead-letter

Подтверждение только после commit минимизирует риск потери эффекта, но оставляет окно повторной доставки между commit и ack. Отрицательное подтверждение с возвратом в очередь (requeue) может сразу вернуть сообщение и создать горячий цикл. Лучше использовать отложенный повтор с ростом паузы, если брокер и архитектура это поддерживают.

Отклонение без возврата обычно означает окончательное прекращение повторов, но судьба сообщения определяется привязкой dead-letter и конфигурацией. Не полагайся на название параметра: проверь документацию и поведение выбранного клиента и версии.

Dead-letter очередь — не мусорная корзина. Сохраняй исходный event ID, безопасную причину, число попыток, время последней доставки и версию схемы. Ограничь доступ и срок хранения, потому что полезная нагрузка может содержать данные клиента. Оператор должен классифицировать причину, исправить её и переотправить событие с тем же ID. Бесконтрольный повтор всей очереди способен снова перегрузить зависимость.

## Проверка адаптера с настоящим брокером

Функции этой главы описывают решение, а не отправку подтверждения. Чтобы проверить адаптер, откройте тестовую очередь с известными настройками подтверждения, отправьте событие с ID и вызовите контролируемые ошибки. Проверьте, что подтверждение действительно удаляет сообщение, отрицательное подтверждение с возвратом вызывает повтор с ожидаемой задержкой, а отклонение уводит сообщение в нужную dead-letter очередь.

Затем остановите потребителя после commit и до ack. После перезапуска брокер должен доставить повтор, обработчик должен распознать ID, а число бизнес-эффектов должно остаться равным одному. Запиши число повторных доставок и очисти очередь после проверки. Такой тест подтверждает именно выбранные настройки и версию брокера, но не является универсальной гарантией для другого окружения.

## Лаборатория перед практикой

Возьми пример с лимитом попыток и поменяй условие на `attempts > limit`. Перед запуском запиши, какое значение напечатает программа и совпадёт ли оно с исходным. Затем запусти программу и сравни. Потом добавь проверку на границе, когда попытки равны лимиту, и предскажи, сколько обработок выполнит такой код.

Журнал эксперимента содержит версию Go, исходное и изменённое условие, предсказание, наблюдение и значение лимита. Граница «равно лимиту» — самое частое место ошибки: одна лишняя попытка означает одну лишнюю обработку, а при нескольких слоях — умножение.

## Практика

### Задание 1 · Решение по результату обработчика

**Цель.** Вход — `transient`, `attempts`, `succeeded`. Если `attempts` меньше нуля, верни `"invalid"`. Если обработка успешна, верни `"ack"`. Если ошибка постоянная, верни `"reject"`. Если временная и попыток меньше трёх, верни `"retry"`. Иначе верни `"dead_letter"`.

**Ожидаемый вывод** — входы: `transient = false, attempts = 0, succeeded = true`; затем `transient = false, attempts = 0, succeeded = false`; затем `transient = true, attempts = 1, succeeded = false`; затем `transient = true, attempts = 3, succeeded = false`:

```text
"reject"
"retry"
"dead_letter"
```

- `"ack"` при неуспешной обработке → флаг успеха перепутан.

> **Подсказка.** Порядок веток: корректность, успех, постоянная ошибка, лимит.

### Задание 3 · Неопределённый commit и восстановление

**Цель.** Вход — `commitState` (`"committed"`, `"uncommitted"` или `"unknown"`), `transient`, `attempts`, `maxAttempts`. Любое другое состояние даёт `"invalid"`. Для `"committed"` верни `"ack"` независимо от попыток. Для `"unknown"` верни `"reconcile"`: сначала сверка по событию, а не слепой повтор. Для `"uncommitted"` при `attempts < 0` или `maxAttempts <= 0` верни `"invalid"`; постоянная ошибка даёт `"reject"`; исчерпанный бюджет — `"dead_letter"`; иначе `"retry"`.

```text
"reconcile"
"retry"
```

5. Если `attempts` меньше нуля или `maxAttempts` не положителен, верни `"invalid"`.
6. Если ошибка постоянная, верни `"reject"`.

**Если не принято.**

## Итог

- Подтверждение идёт после фиксации эффекта; падение до него приводит к повтору, а не к потере.
- Временные ошибки повторяют с ограничением и растущей паузой, постоянные отклоняют, исчерпанные уходят в dead-letter.
- Неизвестный результат commit требует сверки по стабильному идентификатору, а не слепого повтора.
