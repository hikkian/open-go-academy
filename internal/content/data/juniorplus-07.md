# Валидация и ошибки HTTP

## Проверяйте форму до действия

Валидация (validation, проверка входных данных) отвечает, можно ли использовать конкретное значение по контракту. Это не одно действие, а несколько проверок на границе между недоверенным сообщением и внутренней логикой.

Синтаксическая валидация проверяет форму: JSON разбирается, строка содержит допустимые символы, URL абсолютен. Доменная проверка (domain rule) проверяет смысл: alias имеет разумную длину, target соответствует разрешённым схемам, пользователь может создать такое число записей. Инфраструктурная проверка проверяет возможность операции: база данных отвечает, уникальный индекс доступен. Смешивать их в одну «ошибку запроса» неудобно и небезопасно.

Клиент полностью контролирует request body, query, заголовки и путь. Даже вход из вашего собственного интерфейса считается недоверенным на сервере: пользователь может использовать другой клиент или изменить запрос. Читайте данные с ограничением размера до полного разбора, затем декодируйте, проверьте обязательные поля, лишние данные, доменный формат и только после этого выполняйте действие. Проверка на frontend улучшает удобство, но сервер остаётся источником истины.

Размер — часть синтаксической границы. Если endpoint принимает JSON до 8 KiB, примените `http.MaxBytesReader`; при превышении верните `413 Request Entity Too Large` или современный эквивалентный `413 Content Too Large` по контракту. Не читайте неизвестно большой поток целиком в память. Ограничивайте число элементов массива, вложенность или длительность парсинга, если это нужно модели угроз.

## Ошибка — наблюдаемый контракт

HTTP статус подсказывает клиенту категорию результата:

| Статус | Типичная причина | Действие клиента |
|---|---|---|
| `400` | malformed или недопустимая форма | исправить сообщение |
| `401` | аутентификация отсутствует/неверна | запросить или обновить identity по контракту |
| `403` | субъект известен, действие запрещено | не повторять без изменившегося права |
| `404` | путь или ресурс не найден | исправить URI или состояние |
| `409` | конфликт текущего состояния, например занятый alias | выбрать другой alias или обновить данные |
| `413` | тело превышает лимит | уменьшить сообщение |
| `415` | неподдерживаемый Content-Type | выбрать формат из контракта |
| `500` | внутренняя ошибка приложения | сообщить об ошибке; не раскрывать реализацию |

Точные правила зависят от приложения. Некорректное JSON тело — `400`; валидный JSON с уже занятым alias — разумный `409`; отсутствующая запись — `404`. Не превращайте неожиданный отказ базы в `400`, потому что клиент не сможет отличить ошибку пользователя от сбоя системы.

Верните стабильное JSON тело с безопасным machine code: `{"code":"invalid_alias","message":"Проверьте alias"}`. Текст может локализоваться, но code остаётся машинно понятным. Не возвращайте `err.Error()` напрямую: там могут быть внутренние пути, таблицы, запросы, имена узлов и данные пользователя. Сервер может записать внутреннюю причину в защищённый лог с корреляционным ID, но также без секретов.

## Пример 1. Alias ограниченной формы

```go group=validate-alias mode=run
package main

import (
	"fmt"
	"strings"
	"unicode/utf8"
)

func ValidateAlias(alias string) string {
	if alias == "" || strings.TrimSpace(alias) != alias { return "invalid_alias" }
	if utf8.RuneCountInString(alias) > 24 { return "alias_too_long" }
	for _, r := range alias {
		if !(r >= 'a' && r <= 'z' || r >= '0' && r <= '9' || r == '-') { return "invalid_alias" }
	}
	return ""
}

func main() { fmt.Println(ValidateAlias("go-2026"), ValidateAlias("bad alias")) }
```

Пустая строка означает успех только потому, что таков договор примера. В API ответ превращают в код и статус на границе handler. Rune count считает кодовые точки, а UTF-8 размер в байтах — другое. Политика задаёт, какой лимит нужен, а не интуиция.

## Пример 2. Разобрать URL и ограничить схему

```go group=validate-target mode=run
package main

import (
	"fmt"
	"net/url"
)

func ValidateTarget(raw string) string {
	u, err := url.Parse(raw)
	if err != nil || u.Host == "" || u.User != nil || u.Fragment != "" { return "invalid_target" }
	if u.Scheme != "https" && u.Scheme != "http" { return "unsupported_scheme" }
	return ""
}

func main() { fmt.Println(ValidateTarget("https://go.dev/"), ValidateTarget("javascript:alert(1)")) }
```

Разрешать ли HTTP, userinfo или fragment — продуктовая политика. Даже успешно прошедший URL не гарантирует безопасный редирект, DNS результат или удалённый TLS сертификат. Если сервер будет сам загружать цель, возникает SSRF риск, и нужна отдельная строгая политика адресов/редиректов; этот урок не создаёт сетевой fetcher.

## Пример 3. Ограничить JSON body в handler

```go group=bounded-json mode=run
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
)

func main() {
	h := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		r.Body = http.MaxBytesReader(w, r.Body, 16)
		var value map[string]string
		if err := json.NewDecoder(r.Body).Decode(&value); err != nil {
			http.Error(w, "invalid request", http.StatusBadRequest)
			return
		}
		w.WriteHeader(http.StatusNoContent)
	})
	recorder := httptest.NewRecorder()
	h.ServeHTTP(recorder, httptest.NewRequest(http.MethodPost, "/", strings.NewReader(`{"name":"oversized value"}`)))
	fmt.Println(recorder.Code)
}
```

Для реального API выберите лимит осмысленно и отдельно обработайте превышение как `413`, а повреждённый JSON как `400`; в коротком демонстрационном handler они объединены ради минимальности. Не копируйте эту ошибочную детализацию в production. После одного Decode для строгого контракта проверьте EOF, чтобы отвергнуть второе значение.

## Граница ошибки и внутренние причины

Обработайте известные ошибки на уровне, где они понимают их смысл. Валидация alias может вернуть `400`. Уникальное ограничение базы может означать `409`. Timeout внешнего сервиса может означать временный `502`/`503`; внутренняя ошибка — `500`. Не анализируйте человеческий текст ошибки через `strings.Contains("duplicate")`: используйте типизированную ошибку или код базы, определённый в конкретном интеграционном слое.

Наблюдаемый контракт не должен меняться с именем локального файла или текстом SQL. Клиенту достаточно категории и безопасного действия. Оператору нужен диагностический контекст, но этот лог тоже должен быть ограниченным, доступным только уполномоченным ролям и без credential/body по умолчанию.

Ошибка до выполнения операции отличается от частичного эффекта. Если бизнес-транзакция уже создала запись, а сериализация ответа сломалась, ответ может быть `500`, но состояние не обязательно откатилось. На следующих главах проверим транзакции и тесты. Здесь явно отделяйте «запрос отклонён до изменения» от «исход операции неизвестен».

### Порядок проверки важен

Удобная последовательность начинается с дешёвых и ограниченных условий: размер байтов; допустимый Content-Type; один JSON объект; обязательные поля; синтаксическая форма; доменные правила; авторизация; изменение состояния. Порядок не абсолютен для каждого приложения, но валидация до database query уменьшает лишнюю работу и помогает не раскрывать существование приватной записи до проверки доступа.

Отсутствующее поле не равно строке `""`; `null` не всегда равно отсутствию; число `0` может быть допустимым или означать не задано. При `json.Unmarshal` в структуру пустой строковый field и пропущенное поле часто выглядят одинаково. Если контракт должен различать их, используйте указатель, `json.RawMessage` или отдельный тип; затем проверьте все формы. Не усложняйте модель, если API явно считает их одинаковыми.

Хороший ответ на validation failure помогает человеку найти поле, но не должен возвращать все присланные данные. Для многопольной формы можно вернуть список ошибок по имени поля, ограниченный небольшим количеством. При этом не включайте secret input, например пароль, токен или приватный target query. Не полагайтесь на вставку пользовательской строки в log без структурированного экранирования.

### Максимумы должны иметь понятное основание

Лимит тела выбирают с учётом нормального запроса и затрат обработки. Слишком малый лимит делает API непригодным; слишком большой оставляет memory exhaustion риск. Запишите единицу измерения (байты, не символы), измерьте ожидаемую полезную нагрузку и проверьте значение на границе: ровно лимит допускается, лимит + 1 отклоняется. Отдельно ограничьте число JSON элементов, если короткий body способен вызвать чрезмерную работу.

Бумажная проверка до реализации экономит время: перечислите каждую ошибочную форму, ожидаемый status, стабильный code и выполняется ли побочный эффект. Для неверного JSON эффект не должен начинаться; конфликт можно обнаружить только после проверки формы; внутренний отказ не следует объявлять виной пользователя.

## Типичные ошибки и исправления

- **Декодировать неограниченное тело.** Установите лимит до чтения, до `json.Decoder`.
- **Считать тип `string` достаточной валидацией.** Проверьте пустоту, длину, символы и доменные ограничения.
- **Принимать поле клиента как источник полномочий.** Владелец определяется проверенной серверной сессией, не JSON.
- **Печатать внутреннюю ошибку клиенту.** Верните стабильный code, а детали рассмотрите в безопасном логировании.
- **Возвращать `200` с полем `error`.** Клиент, proxy и мониторинг воспринимают успешный status как успех. Выберите корректный status.
- **Смешивать invalid, conflict и not found.** Это разные действия клиента и разные состояния модели.
- **Принимать неизвестные JSON-поля молча без решения.** Явно разрешите расширение или включите strict decoder; документируйте поведение.

При неожиданном `400` возьмите точное публичное тело и проверьте, не объединены ли malformed JSON, пустое поле и oversized body. При `500` уберите детали из ответа, но сохраните безопасную диагностику на сервере. Составьте минимальный body, который воспроизводит ошибку, и не кладите токены в issue или console.

## Практика

- **Easy:** верните ошибку при пустом или отсутствующем alias; валидный alias продолжает обработку. Учтите только явно перечисленные границы.
- **Medium:** проверяйте alias длиной не больше заданного лимита, состоящий из строчных латинских букв, цифр и дефиса; проверяйте абсолютный URL с разрешённой `http`/`https` схемой. Неверная схема должна иметь отдельный code.
- **Hard:** декодируйте JSON тела строго и ограниченно, различите malformed, oversized, missing, domain invalid, not found, conflict и internal; клиентская ошибка содержит стабильный code без текста базы, stack trace, token или пути файла.

Для теста oversized тела используйте small selector в входе trusted driver, а большой поток стройте внутри driver. Это сохраняет JSON-вектор маленьким. Критерий успеха — правильный status и безопасная категория; форматирование JSON может различаться, если его структура соответствует контракту.

## Проверка понимания

1. В чём разница синтаксической и доменной проверки?
2. Зачем ограничивать body до JSON decode?
3. Почему уникальный конфликт часто отличается от неправильного синтаксиса?
4. Какие детали нельзя отдавать в error body?
5. Чем серверная проверка отличается от клиентской подсказки формы?
6. Что должен вернуть handler для второго JSON объекта, если контракт строгий?

Повторите REST статус таблицу и серверные границы. В следующей главе middleware даст общую точку для request ID и ограничений, но доменная валидация всё равно остаётся у конкретного handler/service.

## Мини-глоссарий

- **validation (валидация)** — проверка формы и допустимого смысла входа.
- **domain rule (доменное правило)** — ограничение, вытекающее из модели продукта.
- **payload (полезная нагрузка)** — данные тела запроса или ответа.
- **bounded input (ограниченный ввод)** — поток с явным пределом размера/ресурсов.
- **error response (ответ-ошибка)** — стабильное HTTP представление отказа.
- **conflict (конфликт)** — сообщение валидно, но конфликтует с текущим состоянием.
- **redaction (редактирование)** — удаление или маскирование чувствительных данных.
- **SSRF** — риск, когда сервер по контролируемому клиентом URL делает сетевой запрос.
