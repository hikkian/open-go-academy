# EXPLAIN, индексы и стоимость плана

## Что ты сделаешь

Ты напишешь три функции-правила: классификация доли совпадений, проверка порога для индекса без переполнения и решение с учётом чтений и записей. Функции работают с переданными оценками, поэтому они проверяют арифметику отдельно от реального плана PostgreSQL.

## Что показывает EXPLAIN

`EXPLAIN` (план выполнения) просит PostgreSQL описать выбранный способ получить строки. В плане появляются узлы чтения таблицы, например `Seq Scan` (последовательное чтение) или `Index Scan` (чтение через индекс), фильтры, соединения и оценки `rows` и `cost`.

`rows` — ожидаемое число строк на выходе узла. `cost` — внутренняя относительная оценка работы в условных единицах. Это не миллисекунды и не счёт за ресурсы. Фактическое время даёт только `EXPLAIN ANALYZE`, но он выполняет запрос, поэтому применять его к запросу с побочным эффектом нельзя.

Читай план снизу вверх. Листья получают строки из таблиц, родительские узлы фильтруют, соединяют и сортируют их. Сравни оценку `rows` на каждом узле: там, где фильтр резко уменьшает поток, и находится главный выбор планировщика.

Безопасный учебный пример использует временную таблицу сессии. Он не меняет постоянные таблицы и не удаляет данные. Строки вставляются ровно в количестве 10 000, затем строится индекс, обновляется статистика и выполняется только `EXPLAIN`:

```sql
CREATE TEMP TABLE academy_lesson13_events (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    state text NOT NULL CHECK (state IN ('rare', 'common'))
);
INSERT INTO academy_lesson13_events(state)
SELECT CASE WHEN n <= 100 THEN 'rare' ELSE 'common' END
FROM generate_series(1, 10000) AS n;
CREATE INDEX academy_lesson13_events_state_idx
    ON academy_lesson13_events(state);
ANALYZE academy_lesson13_events;
EXPLAIN SELECT event_id FROM academy_lesson13_events WHERE state = 'rare';
```

Пример вывода для такого маленького набора может выглядеть так:

```text
Index Scan using academy_lesson13_events_state_idx on academy_lesson13_events
  (cost=0.29..10.04 rows=100 width=8)
  Index Cond: (state = 'rare'::text)
```

Это образец для чтения, а не гарантия. Версия PostgreSQL, статистика и физическое расположение строк могут изменить узел и оценки. Измени условие на `state = 'common'`, повтори `EXPLAIN` и сравни решение планировщика.

## Селективность — доля, а не число

Selectivity (селективность) — доля строк, которую ожидается оставить условие. Если в таблице 10 000 строк, а условию соответствуют 10, селективность 0,1%. Если совпадают 8 000, она около 80%.

Доля выражается в процентах, и удобно считать её вещественным числом. Пример показывает, как получить процент из двух целых:

```go
package main

import "fmt"

func main() {
    matches, total := 10, 10000
    fmt.Printf("%.1f%%\n", 100*float64(matches)/float64(total))
}
```

Вывод: `0.1%`. Число выведено для чтения человеком. Для проверки границ лучше работать с целыми значениями, потому что вещественные числа округляют и усложняют сравнение на границе.

Низкая доля часто делает индекс полезным, но универсального процента нет. Случайное чтение многих страниц по индексу может стоить дороже одного последовательного прохода. Статистика PostgreSQL выборочная и устаревает; после заметного изменения данных её обновляет `ANALYZE`.

## Индекс несёт цену записи

Индекс ускоряет поиск, но замедляет `INSERT`, `UPDATE` затронутого столбца и `DELETE`. Он также занимает место и требует обслуживания. Поэтому решение зависит от четырёх вещей: селективности, ширины строк, частоты чтения и частоты записи. Не добавляй индекс только потому, что столбец встречается в `WHERE`.

Индекс может быть невыгоден даже при редких совпадениях, если запись в таблицу идёт очень часто. Редкое чтение может не окупить удорожание каждой вставки.

## Граница без переполнения

Пусть индекс рассматривается, если совпадений меньше четверти строк. Строгое условие записывается как `4 * matches < total`. Но умножение двух больших `int64` может переполниться, и знак результата станет неверным.

Для целых `total > 0` строгое условие эквивалентно `matches <= (total-1)/4`. Здесь нет умножения, поэтому граница надёжна даже на `MaxInt64`. Пример показывает, что произведение может переполниться:

```go
package main

import "fmt"

func main() {
    var m int64 = 1 << 62
    fmt.Println(4*m < 100, 4*m)
}
```

Вывод: `true 0`. Произведение `4 * 2^62` не помещается в `int64`, поэтому результат обёртывается в ноль, и сравнение дало бы неверный ответ. Проверка без умножения этого не допускает.

> **Важно.** Перед любой арифметикой проверь знаки и границы входа. Сначала `matches <= total`, потом порог.

Граница зависит и от размера таблицы. При `total = 1` порог равен нулю: индекс оправдан только если совпадений нет вовсе. При `total = 100` совпадения до 24 включительно проходят порог, а 25 — уже нет. Это правило одно и то же для малых и больших таблиц; разница лишь в том, сколько строк нужно прочитать последовательно.

## Чтения, записи и выбор

Индекс выгоден, когда чтений много, а записей мало. Если записей больше чтений, индекс может съедать больше ресурсов, чем экономит. Эти соотношения сравниваются напрямую, без умножения, как и порог селективности.

Пример показывает такое сравнение для одного набора чисел:

```go
package main

import "fmt"

func main() {
    reads, writes := int64(8), int64(2)
    fmt.Println(writes > reads, reads >= writes)
}
```

Вывод: `false true`. Здесь записей меньше, чем чтений, поэтому учебное правило не отвергает индекс по записи. Решение всё равно требует измерения на реальной нагрузке.

## Точность оценки и пределы модели

Оценки `rows` и `matches` не являются фактами. Это числа для рассуждения. Планировщик опирается на статистику, которая может быть перекошенной или устаревшей. Поэтому функции этой главы не выбирают индекс в продакшене, а только проверяют заданные правила.

Для реального решения откройте `EXPLAIN`, найди узел чтения, проверь оценку строк и посмотри, где отбрасываются строки. Сравни план до и после индекса на одинаковых данных и статистике. Если estimate заметно расходится с фактом, изучи распределение данных и выполни `ANALYZE` до добавления новых индексов.

## Типичные ошибки и исправление

Первая ошибка — принимать `cost` за время в миллисекундах. Это условная оценка, сравнимая только внутри одного плана. Исправление — измерять время отдельно на одинаковом наборе данных.

Вторая — считать оценку `rows` фактическим числом строк. Исправление — сравнивать оценку с фактом через `EXPLAIN ANALYZE` на безопасном read-only запросе.

Третья — умножать `int64` до проверки границ. Исправление — сравнивать через деление с остатком.

Четвёртая — делать вывод об индексе по одной доле селективности. Исправление — учитывать частоту записи и стоимость обслуживания.

> **Типичная ошибка.** Запускать `EXPLAIN ANALYZE` на запросе с побочным эффектом и думать, что это только план. Команда действительно выполняет запрос.

## Если что-то пошло не так

- План всегда выбирает последовательное чтение → таблица маленькая или статистика устарела; выполни `ANALYZE` и проверь объём данных.
- Оценка и факт сильно расходятся → распределение значений перекошено; изучи частоты значений в столбце.
- Запись замедлилась после индекса → индекс дорог для частых изменений; сравни с бюджетом записи.
- Правило даёт неожиданный ответ на больших числах → где-то есть умножение; проверь границы и переведи сравнение в деление.

## Практика

### Практический мост: посмотреть реальный план SQL

Функции этой практики не обращаются к планировщику PostgreSQL и не измеряют план. Они проверяют правила на переданных числах. В проекте P3 есть миграции и запросы, но отдельного теста на `EXPLAIN` нет. Команду `EXPLAIN` для реальных таблиц запускай только на disposable базе, а имена таблиц и столбцов сверяй с миграциями проекта. Без данных план может выбрать последовательное чтение, и это не доказывает пользу индекса на рабочей нагрузке. Для содержательного сравнения загрузи контролируемый набор и сравни планы на одной выборке.

Функции ниже применяют заданные пороги к целым оценкам. Порог 1% и порог 25% являются условиями упражнения, а не выбором PostgreSQL.

### Задание 1 · Классифицируй долю совпадений

**Цель.** Для `matches` и `total` верни строку: `invalid`, если значение отрицательно или `matches > total`; `no_rows`, если `total = 0`; `none`, если `matches = 0`; `sparse`, если `matches` не больше `total / 100` с целым делением; иначе `common`.

**Ожидаемый вывод** — входы: `matches = 10, total = 10000`, затем `matches = 20, total = 1000`:

```text
"sparse"
"common"
```

**Шаги.**
1. Выбери задание «Классифицируй долю совпадений»: в файле есть `MatchSelectivity` с `panic("TODO")`. Импорты не нужны.
2. Проверь знаки и `matches > total`; при нарушении верни `invalid`.
3. Если `total` равен нулю, верни `no_rows`.
4. Если `matches` равен нулю, верни `none`.
5. Вычисли `total / 100` с целым делением и сравни с `matches`.
6. Если `matches` не больше, верни `sparse`; иначе `common`.
7. Нажми «Запустить» и сравни с блоком выше.
8. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `common` для `matches = 5, total = 1000` → порог вычислен неверно; `total / 100` здесь равен 10.
- `none` при ненулевом `matches` → проверка на ноль стоит раньше нужной ветки.
- Результат для `total = 0` отличается от `no_rows` → ветка пустой таблицы идёт после других проверок.

> **Подсказка.** Порядок веток важен: сначала корректность входа, потом пустые случаи, потом порог.

### Задание 2 · Найди границу индексного кандидата без переполнения

**Цель.** Верни `invalid` при отрицательном значении или `matches > total`, `no_rows` при `total = 0`. Иначе `index_candidate`, когда строго выполнено `4 * matches < total`, и `sequential` в остальных случаях. Не вычисляй `4 * matches`: используй эквивалентное целочисленное сравнение без переполнения.

**Ожидаемый вывод** — входы: `matches = 24, total = 100`, затем `matches = 25, total = 100`, затем `matches = 0, total = 1`:

```text

"sequential"
"index_candidate"
```

**Шаги.**
1. Выбери задание «Найди границу индексного кандидата без переполнения»: в файле есть `IndexScanCandidate` с `panic("TODO")`. Импорты не нужны.
2. Проверь знаки и `matches > total`; при нарушении верни `invalid`.
3. Если `total` равен нулю, верни `no_rows`.
4. Для `total > 0` сравни `matches` с `(total - 1) / 4`.
5. Если не больше, верни `index_candidate`; иначе `sequential`.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `index_candidate` при `matches = 25, total = 100` → граница сдвинута на единицу; проверь деление.
- Неверный ответ на `MaxInt64` → где-то есть умножение или вычисление переполнилось.
- `no_rows` для ненулевого `total` → проверка пустой таблицы сработала не по `total`.

> **Подсказка.** Для `total > 0` строгое `4 * matches < total` совпадает с `matches <= (total - 1) / 4`.
