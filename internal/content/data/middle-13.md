# EXPLAIN, индексы и стоимость плана

## Зачем эта тема нужна

Запрос может быть корректным и всё же тратить слишком много времени, читая миллионы строк ради нескольких совпадений. EXPLAIN показывает планировщику SQL и его оценку стоимости до запуска запроса. Индекс добавляет путь поиска, но занимает место и делает каждую запись дороже. Middle-инженер должен уметь прочитать план, сопоставить его с распределением данных и измерить эффект, прежде чем оставлять индекс в схеме.

Учебные функции ниже дают детерминированную классификацию оценок, а SQL-пример показывает, как попросить PostgreSQL построить план на временной таблице. Эти демонстрации отвечают на разные вопросы: функция проверяет арифметическую границу, EXPLAIN показывает решение конкретного планировщика для текущих статистик. Ни одно из них не обещает одинаковый план для всех версий и наборов данных.

## Сначала определим границу

EXPLAIN (план выполнения) просит PostgreSQL описать выбранный способ получить строки. План может содержать Seq Scan (последовательное чтение), Index Scan (чтение через индекс), фильтры, соединения и оценки `rows`/`cost`. `rows` — ожидаемое число выходных строк, а `cost` — внутренняя относительная оценка работы, не миллисекунды и не счёт за ресурсы. В `EXPLAIN ANALYZE` запрос действительно выполняется и выводит наблюдаемые значения; здесь сначала используем безопасный `EXPLAIN` без выполнения запроса.

Индекс особенно полезен, когда условие отбирает небольшую долю строк и подходящий индекс существует. Если подходят многие строки, PostgreSQL может предпочесть последовательное чтение, потому что переходы от индекса к множеству страниц таблицы стоят дороже. Индекс также замедляет `INSERT`, `UPDATE` затронутого столбца и `DELETE`, требует места и обслуживания. Поэтому решение зависит от селективности, ширины строк, корреляции ключа с физическим порядком, частоты чтения и записи. Не добавляйте индекс лишь потому, что столбец встречается в WHERE.

## Как читать EXPLAIN и думать о селективности

План — дерево операций, которое PostgreSQL строит с учётом запроса, статистики и доступных индексов. В листьях обычно появляются способы чтения таблиц; родительские узлы фильтруют, соединяют, сортируют или агрегируют результат. Читайте план снизу вверх: сначала узел получает строки, затем родитель обрабатывает их. Сравните оценку `rows` на узлах и посмотрите, где фильтр уменьшает поток. Сильная ошибка оценки может привести к неудачному порядку соединений или выбору неэффективного метода.

Selectivity (селективность) — доля строк, которую ожидается оставить после условия. Если таблица содержит 100 000 строк и условию соответствует около 100, селективность примерно 0,1%. Если совпадают 80 000 строк, она около 80%. Низкая доля часто делает индекс полезным, но универсального процента нет: случайное чтение многих страниц может оказаться дороже одного последовательного прохода. Статистика PostgreSQL является выборочной и может устареть; после значимого изменения данных её обновляет `ANALYZE`.

Безопасный учебный пример использует временную таблицу текущей сессии: он не меняет постоянные таблицы проекта и не удаляет пользовательские данные. Вставка ограничена ровно 10 000 строками, затем строится индекс, обновляется статистика и выполняется только `EXPLAIN`, а не сам SELECT:

```sql
CREATE TEMP TABLE academy_lesson13_events (
    event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    state text NOT NULL CHECK (state IN ('rare', 'common'))
);
INSERT INTO academy_lesson13_events(state)
SELECT CASE WHEN n <= 100 THEN 'rare' ELSE 'common' END
FROM generate_series(1, 10000) AS n;
CREATE INDEX academy_lesson13_events_state_idx
    ON academy_lesson13_events(state);
ANALYZE academy_lesson13_events;
EXPLAIN SELECT event_id FROM academy_lesson13_events WHERE state = 'rare';
```

Примерный формат результата для такого маленького fixture может выглядеть так:

```text
Index Scan using academy_lesson13_events_state_idx on academy_lesson13_events
  (cost=0.29..10.04 rows=100 width=8)
  Index Cond: (state = 'rare'::text)
```

Это образец для чтения, а не зафиксированная гарантия: версия PostgreSQL, статистика, настройки и физическое расположение строк могут изменить узел, стоимость и оценки. `cost` не означает миллисекунды, `rows` — оценка, а не фактический счётчик. Измените условие на `state = 'common'`, повторите EXPLAIN и сравните решение. Чтобы узнать фактическое время и реальные строки, нужен `EXPLAIN ANALYZE`; он запускает запрос, поэтому применять его следует только к безопасному read-only запросу и контролируемому окружению.

Индекс несёт цену записи. В проекте измерьте репрезентативные чтения до и после индекса, затем отдельно сравните скорость и объём записей на одном и том же fixture. Не делайте вывод по одному запуску на пустой или крошечной таблице: кэш страниц, шум среды и прогрев влияют на время. Сначала объясните гипотезу, зафиксируйте структуру данных, обновите статистику и проверьте план; затем измеряйте повторно одинаковым сценарием.

## Практика Go: от selectivity к стоимости записи

Три следующих функции моделируют разную сложность решения. Это не PostgreSQL planner: они применяют явно заданные учебные пороги к целым оценкам и помогают проверить арифметику отдельно от реального плана.

```go group=middle-13-decision mode=run
package main
import "fmt"
func MatchSelectivity(matches, total int64) string {
 if matches < 0 || total < 0 || matches > total { return "invalid" }
 if total == 0 { return "no_rows" }; if matches == 0 { return "none" }
 if matches <= total/100 { return "sparse" }; return "common"
}
func main() { fmt.Println(MatchSelectivity(10, 10000)); fmt.Println(MatchSelectivity(20, 1000)) }
```

Вывод первого примера: `sparse`, затем `common`. При одинаковых предположениях первый fixture соответствует 0,1% строк, второй — 2%. Это классы упражнения, а не универсальная граница полезности индекса.

## Маленький тест без внешней системы

Точная граница здесь строгая: 4 × matches < total. Чтобы не умножать потенциально большие int64, перепишем условие для целого `matches` как `matches <= (total-1)/4` при `total > 0`. Для total=100 значения 24 и 25 оказываются по разные стороны границы.

```go group=middle-13-table mode=run
package main
import "fmt"
func IndexScanCandidate(matches, total int64) string {
 if matches < 0 || total < 0 || matches > total { return "invalid" }
 if total == 0 { return "no_rows" }
 if matches <= (total-1)/4 { return "index_candidate" }; return "sequential"
}
func main() { fmt.Println(IndexScanCandidate(24, 100)); fmt.Println(IndexScanCandidate(25, 100)) }
```

Вывод второго примера: `index_candidate`, затем `sequential`. Проверка `matches <= (total-1)/4` точно эквивалентна строгому условию `4*matches < total` для целых `total > 0`, но не умножает значения и потому не переполняется при MaxInt64. Равенство 25% относится к `sequential` согласно строгому контракту.

## Точность оценки и пределы модели

Оценки `rows` и `matches` — не гарантированные факты, а числа для рассуждения. В упражнении они заданы явно, поэтому функция может применять стабильное правило. Реальный PostgreSQL оценивает распределение по статистике и может ошибаться, особенно если колонка имеет перекошенные значения или статистика давно не обновлялась. Поэтому helper не должен выдаваться за функцию выбора индекса в production.

Умножение двух произвольных `int64` может переполниться и изменить знак либо сравнение. Для условия `4*matches < total` при `total > 0` используйте эквивалент `matches <= (total-1)/4`; вычитание безопасно после проверки положительного `total`. Для процентного класса `matches <= total/100` также нет умножения. Сначала проверьте неотрицательность и `matches <= total`, затем рассчитывайте границы.

Для реального решения откройте план `EXPLAIN`, найдите узел чтения и условия, проверьте оценку числа строк и посмотрите, где отбрасываются строки. Сравните план до и после индекса на одинаковых данных и статистике. Если индекс улучшает чтение, но ухудшает частую запись сверх допустимого бюджета, решение может быть неверным для workload продукта. Зафиксируйте обе стороны trade-off.

```go group=middle-13-errors mode=run
package main
import "fmt"
func IndexReadWriteDecision(matches, total, reads, writes int64) string {
 if matches < 0 || total < 0 || reads < 0 || writes < 0 || matches > total { return "invalid" }
 if total == 0 { return "no_rows" }
 if matches > (total-1)/4 { return "sequential" }
 if writes > reads { return "write_heavy" }; return "index_candidate"
}
func main() {
 fmt.Println(IndexReadWriteDecision(20, 100, 8, 2))
 fmt.Println(IndexReadWriteDecision(20, 100, 2, 8))
 fmt.Println(IndexReadWriteDecision(2305843009213693951, 9223372036854775807, 9223372036854775807, 0))
}
```

Третий пример учитывает read/write mix: если порог selectivity пройден, но записей больше, чем чтений, учебное правило возвращает `write_heavy`. Оно не измеряет стоимость SQL операций; это демонстрация явного компромисса в фиксированной модели.

## Типичные ошибки и диагностика

- Принимать `cost` за время в миллисекундах.
- Считать оценку `rows` фактическим числом совпавших строк.
- Умножать пользовательские или статистические `int64`-оценки до проверки границ.
- Делать универсальный вывод о полезности индекса по одной доле selectivity.
- Игнорировать цену обновления и хранения индекса.
- Запускать `EXPLAIN ANALYZE` на запросе с побочным эффектом, не понимая, что он действительно исполняет запрос.

При диагностике сначала убедитесь, что таблица содержит representative данные и свежую статистику. Сравните предполагаемые и фактические строки из безопасного `EXPLAIN ANALYZE` только для read-only запроса. Изменяйте одно условие за раз, записывайте версию PostgreSQL и не сравнивайте стоимость на разных fixture как будто это один эксперимент. Если estimate заметно расходится с actual rows, изучите распределение данных и `ANALYZE`, прежде чем добавлять очередной индекс.

## Практика и самопроверка

**Easy.** В `middle-13-easy` классифицируйте долю `matches/total`. Покажите пустую таблицу, ноль совпадений и ровно 1% на MaxInt64.

**Medium.** В `middle-13-medium` проверьте строгую границу `4*matches < total`, включая точное равенство и соседние значения у MaxInt64. Перепишите сравнение как `(total-1)/4`, не вычисляя произведение.

**Hard.** В `middle-13-hard` добавьте read/write mix, проверьте равенство reads=writes и значения MaxInt64. Объясните, почему этот фиксированный helper не заменяет планировщик.

Для реальной проверки повторите SQL fixture в закреплённой версии PostgreSQL, запустите `ANALYZE`, сохраните `EXPLAIN` и запишите размер таблицы и индексированных данных. При отдельном сравнении времени используйте одинаковое число запусков и одинаковый набор строк, но помните, что локальный тест не предсказывает другую машину и production workload.

## Итог и повторение

Теперь вы умеете читать базовые поля плана, объяснять selectivity, сопоставлять read/write trade-off и избегать overflow в фиксированных целочисленных правилах. Повторите `juniorplus-10` про SQL-запросы и индексы. Следующий шаг — измерить реальный запрос на выбранном fixture, сверить estimate с actual rows и проверить, что индекс оправдывает цену обновления.

## Практический мост: посмотреть реальный план SQL

Helper по стоимости/категории не обращается к планировщику PostgreSQL и не измеряет план. В P3 есть миграции и запросы, но отдельного acceptance-теста `EXPLAIN` нет. При запущенном disposable Compose окружении из корня проекта выполните `docker compose exec -T db psql -U taskflow -d taskflow -c "EXPLAIN (COSTS, VERBOSE) SELECT id, state, updated_at FROM tasks WHERE project_id = '00000000-0000-0000-0000-000000000001' ORDER BY updated_at DESC, id LIMIT 100;"`. Подтвердите имя сервиса БД по `content/projects/p3/compose.yaml`; используйте только disposable БД. Без данных план может выбрать последовательное чтение, что не доказывает пользу индекса на рабочей нагрузке. Для содержательного сравнения загрузите контролируемый fixture и сравните планы на одной выборке. Helper SQL не исполняет.

### Термины

- **EXPLAIN (план выполнения)** — PostgreSQL выбирает способ получить строки.

- **selectivity (селективность)** — Доля строк, подходящая условию.

- **sequential scan (последовательное чтение)** — Проверка строк таблицы без поиска по индексу.


## Лабораторный сценарий: от гипотезы до восстановления

Сформулируйте гипотезу: «при одинаковой таблице редкое значение может дать индексный путь, а частое — последовательный; дополнительная запись увеличивает цену индекса». Сначала сохраните EXPLAIN без изменения данных, затем меняйте только значение фильтра и сравнивайте узел, estimate и cost. Для арифметических упражнений отдельно подберите пары строго ниже, ровно на, и сразу выше порога. Запишите ожидаемый результат до запуска.

Соберите матрицу случаев: пустая таблица, 0 совпадений, около 1%, около 25%, большая доля, invalid estimate и MaxInt64. Для hard добавьте много чтений/мало записей и мало чтений/много записей. Зафиксируйте результат функции и отдельно ожидаемый плановый узел. Эти результаты не обязаны совпасть: planner опирается на статистику и стоимость страниц, а helper применяет только заданную арифметику.

Проведите три прохода: сначала `EXPLAIN` для `rare`, затем для `common`, наконец повторите после обновления статистики через `ANALYZE`. Не запускайте `EXPLAIN ANALYZE` для изменения данных: он исполняет запрос. Если хотите оценить записи, выполняйте измерение только на отдельном временном/тестовом окружении. Сравнивайте один и тот же объём данных и фиксируйте конфигурацию; выводы по cost остаются оценками, а выводы по времени чувствительны к машине и cache state.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для hard гипотеза имеет три исхода: доля выше порога означает sequential; доля ниже порога при writes>reads — write_heavy; доля ниже порога и reads>=writes — index_candidate. Проверьте все переходы, включая равные счётчики. Решение использует только сравнения и не умножает оценки, поэтому MaxInt64 допустим при выполнении входных границ. Оно не измеряет страницы, cache hit ratio или реальные задержки.

Назовите два факта, которые способны изменить решение: частота чтений и записей, а также распределение значений по столбцу. Если продукт стал в основном записывающим, индекс может не окупаться. Если значение почти всегда одно и то же, индекс по одиночному столбцу может читать большую часть таблицы. Рассмотрите составной индекс, если запрос фильтрует по нескольким полям, но проектируйте его по реальным запросам и проверяйте дополнительные затраты на каждую запись.

В коротком отчёте сохраните PostgreSQL version, точный SQL, DDL, число строк и распределение, индекс, команду `ANALYZE`, полный план и оговорку о том, что `cost` не время. Для сравнения до/после индекса дополните отчёт измерениями SELECT и INSERT на фиксированном fixture. Функциональный grader проверяет только named contract; план и performance требуют отдельных реальных database tests.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает реальный план PostgreSQL, а примерный cost не предсказывает фактические миллисекунды.
