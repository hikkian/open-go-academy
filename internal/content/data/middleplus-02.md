# Go benchmarks и стоимость операции

## Что ты сделаешь

Ты научишься читать строку вывода `go test -bench` без иллюзий: что такое `ns/op`, `B/op` и `allocs/op`, почему это три разных измерения и как устроен benchmark, у которого компилятор не выбрасывает работу, а подготовка данных не попадает в таймер. Три функции урока — `MetricLabel`, `ValidBenchmarkResult`, `BenchmarkComparison` — закрепляют правила чтения: подпись метрики, проверка формы результата и честное сравнение двух прогонов без подмены одной метрики другой.

## Как устроен Go benchmark

Benchmark в Go — функция вида `func BenchmarkX(b *testing.B)`. Обвязка (benchmark harness) повторяет тело с меняющимся `b.N`: число итераций выбирает она сама, чтобы получить пригодную длительность. Поэтому в теле нельзя предполагать фиксированное `N`, печатать на каждой итерации или накапливать состояние, которое меняет стоимость следующей итерации.

Подготовка данных — чтение fixture, построение больших структур — либо осознанно входит в измеряемый участок, либо выносится из него: `b.ResetTimer()` обнуляет накопленное время после setup, `b.StopTimer()` и `b.StartTimer()` ставят таймер на паузу. Неверное место этих вызовов меняет сам эксперимент, а не точность.

```text
func BenchmarkParse(b *testing.B) {
    input := loadFixture()      // setup: не должен попасть в таймер
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        sink = parse(input)     // измеряемая операция; результат остаётся наблюдаемым
    }
}
```

> **Важно.** Результат операции должен быть наблюдаем. Если компилятор может доказать, что вычисление ни на что не влияет, он вправе его убрать, и benchmark измерит пустой цикл. Запись в переменную уровня пакета (sink) сохраняет наблюдаемость; это технический приём, а не повод заводить общее изменяемое состояние между параллельными прогонами.

## Три числа в одной строке

Строка вывода `go test -bench` выглядит так: имя с суффиксом числа процессоров, число итераций, затем метрики. `ns/op` — наносекунды на операцию, нормированное время внутри обвязки; `B/op` — байты, выделенные на операцию; `allocs/op` — число выделений на операцию. Последние две появляются при `b.ReportAllocs()` или флаге `-benchmem`.

```go group=benchline mode=run
package main

import (
    "fmt"
    "strings"
)

func main() {
    line := "BenchmarkParse-8   2000000   612 ns/op   96 B/op   3 allocs/op"
    fields := strings.Fields(line)
    fmt.Println("имя:", fields[0], "итераций:", fields[1])
    for i := 2; i+1 < len(fields); i += 2 {
        fmt.Println(fields[i+1], "=", fields[i])
    }
}
```

Вывод:

```text
имя: BenchmarkParse-8 итераций: 2000000
ns/op = 612
B/op = 96
allocs/op = 3
```

Это три разных измерения одной операции. Сокращение аллокаций не гарантирует меньшую задержку: выделения могли быть дешёвыми, а время уходило в вычисления. Меньшее `ns/op` ничего не говорит об удерживаемой памяти. Метаданные benchmark обязаны назвать ровно одну операцию, иначе число нельзя интерпретировать; варианты группируют в sub-benchmark с одними и теми же fixture и настройками.

> **Типичная ошибка.** Сравнить `ns/op` одного прогона с `ns/op` другого, где число итераций, размер входа или режим `-benchtime` отличались. Единица одна, операция — уже нет.

## Что измеряем: вызов, пакет или pipeline

Явно запиши, что считается операцией: одиночный вызов функции, пакет из тысячи записей или весь путь с сериализацией, копированием, логированием и доступом к хранилищу. От этого зависит, какую единицу ты получишь и с чем её можно сравнивать. Для pipeline уточни, входит ли в таймер ожидание ввода-вывода: benchmark CPU-пути с внезапным сетевым вызовом внутри измеряет сеть, а не код.

Проверь, как стоимость масштабируется: измени размер входа в два раза и посмотри, выросло ли время в два или в четыре. Если ожидался линейный алгоритм, а время растёт квадратично, ищи вложенные циклы и дорогие операции внутри. Не экстраполируй измерения маленького fixture на большие размеры без модели и отдельного замера.

```go group=metric mode=run
package main

import "fmt"

func label(metric string) string {
    switch metric {
    case "time":
        return "ns_per_op"
    case "bytes":
        return "bytes_per_op"
    case "allocs":
        return "allocs_per_op"
    }
    return "unknown"
}

func main() {
    fmt.Println(label("time"), label("bytes"), label("allocs"), label("cpu"), label(""))
}
```

Вывод:

```text
ns_per_op bytes_per_op allocs_per_op unknown unknown
```

Подпись метрики — вопрос дисциплины отчёта: в таблице результатов каждая колонка называется по единице, а не по догадке читателя. Классификатор ничего не измеряет; он лишь не даёт перепутать байты с числом выделений.

## Варианты под одним именем: sub-benchmark

Когда нужно сравнить две реализации или несколько размеров входа, не заводи отдельные файлы и не меняй код между прогонами. `b.Run("size=1k", func(b *testing.B) { … })` создаёт sub-benchmark: у каждого варианта своё имя в выводе, но общий fixture, те же флаги и тот же процесс. Тогда строки отчёта сравнимы по построению, а не по памяти о том, «что я тогда запускал».

```text
BenchmarkParse/size=1k-8     500000    2410 ns/op    96 B/op    3 allocs/op
BenchmarkParse/size=10k-8     50000   24880 ns/op    96 B/op    3 allocs/op
```

Здесь видно, что время выросло примерно в десять раз при десятикратном входе, а память на операцию не изменилась — ровно тот вопрос о масштабировании, который стоит задать до оптимизации. Если имя варианта не называет, чем он отличается, читатель отчёта не сможет повторить сравнение.

## Короткий прогон — это дымовая проверка

Воспроизводимая команда фиксирует режимы: `-count` для повторов, `-benchtime` для длительности, `-run '^$'` чтобы не запускать обычные тесты, `-benchmem` для памяти. Короткий локальный запуск — только проверка, что benchmark вообще работает. Финальный эксперимент выбирает длительность и число повторов исходя из ожидаемого эффекта и шума (об этом следующий урок). Исходный вывод хранится без ручного редактирования.

Benchmark не интеграционный тест: он не подтверждает корректность HTTP-обработчика, базы или очереди. Сначала семантику проверяют обычными тестами, затем измеряют стоимость представительного пути. Для `b.RunParallel` отдельно проверь безопасное разделение данных и не сравнивай его с последовательной версией, если вопрос не включает стоимость конкурентного доступа.

```go group=decision mode=run
package main

import "fmt"

func compare(baseNs, candNs, baseAllocs, candAllocs int64) string {
    if baseNs <= 0 || candNs <= 0 || baseAllocs < 0 || candAllocs < 0 {
        return "invalid"
    }
    if candNs < baseNs && candAllocs <= baseAllocs {
        return "faster_no_allocation_regression"
    }
    if candNs >= baseNs && candAllocs >= baseAllocs {
        return "no_metric_improved"
    }
    return "tradeoff"
}

func main() {
    fmt.Println(compare(100, 90, 4, 4))
    fmt.Println(compare(100, 90, 4, 5))
    fmt.Println(compare(100, 110, 4, 3))
    fmt.Println(compare(100, 120, 4, 4))
}
```

Вывод:

```text
faster_no_allocation_regression
tradeoff
no_metric_improved
no_metric_improved
```

Слово `tradeoff` означает ровно одно: по одной метрике лучше, по другой хуже, и решать должен человек, зная, что дороже в этом сервисе — время или память. Таблица решений работает по паре агрегатов и ничего не знает о разбросе повторов.

> **Зачем.** Если выписать правило сравнения до прогона, после прогона не останется соблазна выбрать ту метрику, по которой «победил» кандидат.

## Типичные ошибки

- Подготовка данных внутри таймера: `ResetTimer` стоит после setup, иначе измеряется чтение fixture.
- Результат никуда не записан: компилятор убрал работу, benchmark показывает нереально малые наносекунды.
- Фиксированное число итераций или накопление состояния в теле: с ростом `b.N` операция меняется.
- Сравнение разных операций под одним именем: без sub-benchmark и одинаковых fixture числа несопоставимы.
- «Меньше аллокаций — значит быстрее»: три метрики независимы, выигрыш по одной не переносится на другие.
- Один короткий прогон как финальная цифра: это дымовая проверка, а не измерение.

## Самостоятельная лаборатория

Возьми небольшую чистую функцию из своего проекта и напиши к ней benchmark: setup до `ResetTimer`, результат в sink. Запусти с `-benchmem -count=3` и сохрани вывод как есть. Затем удвой размер входа и повтори. Запиши в карточку: что считалось операцией, какие три числа получились на каждом размере, как выросло время, что из этого ты не можешь заключить (например, о задержке в сервисе). Если какая-то метрика «улучшилась» между прогонами без изменения кода — это оценка шума, а не эффект.

## Если что-то пошло не так

- `missing return at end of function` → у `MetricLabel` нет `return "unknown"` после `switch`.
- Красный закрытый пример с пустой строкой → `""` — тоже неизвестная метрика, ветка `default` должна её покрывать.
- `false` при корректных числах в задании 2 → условие для времени строгое (`> 0`), для байтов и аллокаций — нестрогое (`>= 0`); перепутаны.
- `tradeoff` вместо `invalid` → проверка диапазонов стоит после сравнения; она должна быть первой.
- `import … is not allowed` → импорты в заданиях запрещены: это сравнения чисел и строк.

## Практика

Три функции без `main` и печати; среда вызывает их и показывает результаты строками JSON: строки в кавычках, `bool` и числа как есть.

### Задание 1 · Easy: сопоставь имя метрики Go benchmark

**Цель.** Превратить `time`, `bytes`, `allocs` в `ns_per_op`, `bytes_per_op`, `allocs_per_op`, а любую другую строку — в `unknown`.

**Ожидаемый вывод** — для `time`, `bytes`, `allocs`:

```text
"ns_per_op"
"bytes_per_op"
"allocs_per_op"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func MetricLabel(metric string) string`. Импорты запрещены.
2. `switch metric` с тремя `case` и `default`, возвращающим `"unknown"`.
3. «Запустить», «Проверить» — закрытые примеры: `other` и пустая строка → `unknown`.

**Как проверить себя.** Три подписи совпадают буква в букву (подчёркивания, не дефисы); неизвестное и пустое имя дают `unknown`.

**Если не принято.**
- Красный закрытый пример для `""` → нет ветки по умолчанию или она возвращает не `unknown`.
- `bytes_per_op` для `allocs` → перепутаны байты и число выделений — та самая ошибка, против которой задание.

> **Подсказка.** Это подпись, не измерение: функция не должна ничего считать, только сопоставлять строки.

### Задание 2 · Medium: проверь диапазоны показателей benchmark

**Цель.** Вернуть `true`, только если `ns/op > 0`, `B/op >= 0` и `allocs/op >= 0`.

**Ожидаемый вывод** — для `(12, 64, 2)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ValidBenchmarkResult(nsPerOp, bytesPerOp, allocsPerOp int64) bool`. Импорты запрещены.
2. Верни `nsPerOp > 0 && bytesPerOp >= 0 && allocsPerOp >= 0`.
3. «Запустить», «Проверить» — закрытые примеры: нулевое время → `false`, отрицательные байты → `false`.

**Как проверить себя.** Нулевое время невозможно для реальной операции, а ноль байтов и ноль аллокаций — нормальны; функция проверяет только непротиворечивость чисел, не корректность обвязки.

**Если не принято.**
- `true` при `nsPerOp = 0` → для времени нужно строгое `> 0`.
- `false` при `bytesPerOp = 0` → для байтов и аллокаций нужно `>= 0`.

> **Подсказка.** Одна строка из трёх сравнений через `&&`.

### Задание 3 · Hard: сравни время и аллокации без подмены метрик

**Цель.** По `ns/op` и `allocs/op` базы и кандидата вернуть `invalid`, `faster_no_allocation_regression`, `no_metric_improved` или `tradeoff`.

**Ожидаемый вывод** — для `(baseNs=100, candidateNs=90, baseAllocs=4, candidateAllocs=4)`:

```text
"faster_no_allocation_regression"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func BenchmarkComparison(baseNs, candidateNs, baseAllocs, candidateAllocs int64) string`. Импорты запрещены.
2. Первой проверкой: время `<= 0` или аллокации `< 0` у любой стороны → `"invalid"`.
3. Кандидат быстрее (`candidateNs < baseNs`) и аллокаций не больше (`<=`) → `"faster_no_allocation_regression"`.
4. Кандидат не быстрее (`>=`) и аллокаций не меньше (`>=`) → `"no_metric_improved"`.
5. Всё остальное → `"tradeoff"`. «Запустить», «Проверить» — закрытые примеры: быстрее, но больше аллокаций → `tradeoff`; медленнее, но меньше аллокаций → `tradeoff`; отрицательное время → `invalid`.

**Как проверить себя.** Равное время и равные аллокации — `no_metric_improved` (ничего не улучшилось); улучшение по одной метрике при ухудшении другой — всегда `tradeoff`, в обе стороны.

**Если не принято.**
- `faster_no_allocation_regression` при росте аллокаций → во втором правиле нужно `candidateAllocs <= baseAllocs`.
- `tradeoff` при равных метриках → третье правило должно использовать нестрогие сравнения `>=`.
- `invalid` не срабатывает для `baseNs = -1` → проверка диапазонов стоит не первой.

> **Подсказка.** Порядок правил и есть политика: сначала валидность, потом «лучше по обеим», потом «не лучше ни по одной», остальное — компромисс.

## Итог

- Benchmark измеряет одну названную операцию: setup вне таймера, результат в sink, число итераций выбирает обвязка.
- `ns/op`, `B/op`, `allocs/op` — три независимых измерения; выигрыш по одному не переносится на другие.
- Сравнение двух прогонов — политика, записанная до запуска; разброс повторов она не учитывает — это следующий урок.
