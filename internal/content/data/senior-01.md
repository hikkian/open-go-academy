# Неопределённые требования: превратить просьбу в проверяемое решение

## Что ты сделаешь

Ты разберёшь просьбу вроде «сделать быстрый сервис задач для крупных клиентов» на слои — факты, предположения, вопросы, ограничения — и научишься записывать решение так, чтобы в нём был виден следующий безопасный эксперимент. Три функции урока — `RequirementKind`, `CriterionState`, `NextStep` — это крошечные политики сортировки, которыми ты будешь пользоваться в голове на каждом обсуждении. Они не читают тикеты и не проектируют архитектуру за тебя; они проверяют, что ты различаешь «подтверждено», «предполагаем» и «надо спросить».

## Просьба — ещё не требование

«Быстрый» — это какая операция, какая доля запросов и какое время? «Крупный» — сколько пользователей, записей и одновременных клиентов? Кто клиент: человек, организация, другая система? Что происходит при частичной недоступности? Если инженер незаметно подставит свои ответы, архитектура будет точной только для вымышленной задачи.

Senior не обязан знать ответы заранее. Его работа — показать, какие неизвестные меняют решение, собрать доступные свидетельства и выбрать следующий шаг с учётом риска. Хороший итог обсуждения иногда звучит так: «Пока не выбираем микросервисы; сначала измерим объём и подтвердим границу владения данными». Отложенное решение — не бездействие, если у него есть срок, ответственный и критерий пересмотра.

Четыре термина урока: требование (requirement) — нужное наблюдаемое поведение или ограничение; предположение (assumption) — рабочее утверждение без достаточного подтверждения; свидетельство (evidence) — наблюдение с источником и контекстом; запись решения (decision record) — выбор, альтернативы, последствия и условие пересмотра.

> **Важно.** Эти понятия не заменяют переговоры. Они нужны, чтобы факты не смешивались с выводами, а чужое мнение — с измерением.

## Разбор просьбы по слоям

Начни с пользователя и его задачи: кто начинает действие, какую цель преследует, какие данные получает или меняет, что считает успешным завершением. Уточни границу процесса: входной запрос, фоновая работа, экспорт, отчёт, ручная операция. Глагол «создать» может означать черновик, подтверждённую запись, отправленное уведомление или необратимую финансовую операцию; без уточнения команда поспорит об этом после того, как построит несовместимые части.

Затем раздели функциональные требования и атрибуты качества (quality attributes). Функциональное — что система делает: владелец может отменить ещё не начатую задачу. Атрибут качества — как она себя ведёт: задержка, доступность, целостность, конфиденциальность, восстановление, удобство изменения. «Данные нельзя потерять» требует события подтверждения, модели отказа и допустимого окна восстановления — это влияет на архитектуру сильнее любого endpoint.

Третий слой — ограничения: срок, совместимость с существующей системой, регион хранения, запрет менять клиент, операционная команда, бюджет. У каждого ограничения есть источник: политика, контракт, измерение или чьё-то пока не подтверждённое мнение. Различай «мы не можем» и «мы пока не знаем, как» — первое сужает решения, второе требует расследования.

Наконец, составь список неизвестных и ранжируй их по влиянию. Цвет кнопки не меняет модель данных; семантика удаления, число арендаторов (tenant) или допустимая задержка могут поменять владение данными, индексы и границу процесса. Проверочный вопрос для каждого пробела: какое решение выберем при ответе A и какое — при ответе B? Если ветви сходятся, вопрос подождёт; если расходятся — исследуй его рано.

```go group=requirement mode=run
package main

import "fmt"

func status(answer string) string {
    if answer == "" {
        return "clarify"
    }
    if answer == "confirmed" {
        return "evidence"
    }
    return "assumption"
}

func main() {
    fmt.Println(status(""), status("confirmed"), status("maybe"), status("Confirmed"))
}
```

Вывод:

```text
clarify evidence assumption assumption
```

Пустой ответ требует вопроса; явно подтверждённый помечается свидетельством; всё остальное остаётся предположением — в том числе «Confirmed» с большой буквы, потому что в реестре метка либо точная, либо никакая. В настоящем реестре рядом хранятся источник и уровень уверенности; эта программа их не проверяет.

## Измеримость без ложной точности

«Должно быть надёжно» не становится критерием от добавления процента. Нужны окно наблюдения, знаменатель, измеряемая операция, метод сбора и исключения. Доля успешных чтений за месяц ничего не говорит о задержке записи и не объясняет, считаются ли плановые работы. Число без границ выглядит убедительнее, чем заслуживает.

Для каждого критерия укажи исходный вопрос, цель или качественный тест, сценарий, период, источник данных и владельца подтверждения. Если приемлемая цель неизвестна — не выдумывай её: обозначь диапазон для исследования. Число с тестовой машины не становится прогнозом production-нагрузки.

Различай критерий приёмки (acceptance criterion) и гипотезу. Критерий — наблюдаемое условие, по которому работу принимают: «запрос возвращает только записи текущей организации» проверяется негативным тестом на соседнего арендатора. Гипотеза объясняет, почему ожидается результат, и называет наблюдение, которое её опровергнет: «индекс улучшит p95» требует той же базы, запроса, версии и повторяемого измерения.

```go group=criterion mode=run
package main

import "fmt"

func criterion(target, source string) string {
    if target == "" || source == "" {
        return "incomplete"
    }
    return "review"
}

func main() {
    fmt.Println(criterion("p95", "synthetic-test"), criterion("", "log"), criterion("availability", ""))
}
```

Вывод:

```text
review incomplete incomplete
```

Программа различает только заполненность двух строк. `review` — приглашение проверить критерий человеком, а не принятие требования: пригодность метрики и правдивость источника код не оценивает.

> **Типичная ошибка.** Путать отсутствие сведений с нулём. «Неизвестно» хранится отдельно от «измерили ноль», иначе пробел превращается в факт.

## Конфликты и способы уменьшить неопределённость

Заказчики приносят несовместимые приоритеты: минимальная стоимость и почти нулевой простой; немедленная глобальная запись и локальное продолжение при потере сети; удаление данных и полная история действий. Не объявляй один голос главным без полномочий. Запиши конфликт, последствия каждой стороны, кто принимает продуктовый риск и к какому сроку нужен ответ.

Способ уменьшить неопределённость выбирают по природе вопроса. Интервью выясняет термин и процесс; анализ событий показывает фактический профиль; ограниченный прототип проверяет трудный механизм; нагрузочный тест исследует конкретный workload; правовая или security-проверка отвечает на вопросы своей области. Прототип очереди не скажет, имеет ли команда право хранить поле; опрос не докажет throughput; профиль не покажет, какую потерю данных бизнес считает допустимой.

Ранжируй неизвестные по двум осям: насколько вероятно, что предположение неверно, и насколько дорого обнаружить это поздно. Это средство разговора, а не точная вероятность; не превращай таблицу в сумму баллов с неоткалиброванной шкалой. Высокое влияние и слабое свидетельство — проверять рано; для менее значимого пробела подойдёт обратимое решение с записанным предположением и датой проверки.

> **Зачем.** У каждого эксперимента есть предел: бюджет времени, безопасный объём данных, владелец и условие остановки. Внешние пользователи, production-данные и платная инфраструктура не должны становиться случайным полигоном — только синтетические fixtures, отдельный тестовый арендатор и одноразовая среда.

## Как записывать решение

Компактная запись содержит контекст, подтверждённые требования, открытые вопросы, принятые предположения, альтернативы, выбранное действие и его последствия, плюс дату пересмотра или сигнал, который заставит вернуться к выбору. Это не стенограмма: читатель должен быстро понять, что известно, что нет и почему команда действует сейчас.

Отделяй решение от статуса. «Мы выбрали монолит» — выбор; «система выдерживает пять тысяч запросов» — проверяемое утверждение, которому нужны измерение и среда. Ссылки ведут на конкретный источник, версию документа, эксперимент или тест; если подтверждения нет — так и напиши. Документирование неопределённости не ослабляет работу, оно мешает временной догадке стать неоспоримым фактом.

Решения различаются ценой изменения. Формат внутреннего интерфейса можно отложить, пока он локален; публичный API, схема хранения и идентификаторы клиентов дороги из-за уже выпущенных потребителей и записанных данных. Поэтому сначала фиксируют устойчивые инварианты и обратимые границы, затем уточняют детали, требующие свидетельств. Не проектируй абстракцию «на будущее» без сценария, но и не зашивай предположение в необратимую миграцию.

```go group=decision mode=run
package main

import "fmt"

func nextStep(reversible, highImpact bool) string {
    if !reversible && highImpact {
        return "evidence-first"
    }
    if reversible {
        return "timeboxed-trial"
    }
    return "owner-review"
}

func main() {
    fmt.Println(nextStep(false, true), nextStep(true, true), nextStep(false, false), nextStep(true, false))
}
```

Вывод:

```text
evidence-first timeboxed-trial owner-review timeboxed-trial
```

Это локальная политика: необратимое и важное решение сначала требует свидетельств; обратимое можно попробовать в ограниченное время; необратимое, но малозначимое — отдать владельцу на проверку. В живом процессе ещё нужно договориться, что значит «высокая цена», кто владеет риском и как измерить эксперимент.

## Типичные ошибки

- Пересказывать пожелание как точное требование: спроси о действии, пользователе, результате, исключении и способе проверки.
- Подставлять собственный порог: пометь гипотезой, найди владельца критерия и данные, способные изменить решение.
- Считать один источник универсальным: укажи контекст выборки и независимый способ подтверждения.
- Смешивать требование и решение: сначала нужное поведение, потом варианты и их стоимость.
- Оставлять предположение без срока: назначь дату или событие пересмотра либо выбери обратимое действие.
- Утверждать гарантию на основании unit-теста: назови точный контракт теста и недостающие системные доказательства.

Если обсуждение зашло в тупик, нарисуй две ветви ответа на спорный вопрос и для каждой перечисли последствия для данных, интерфейса, операций, безопасности и восстановления. Если команда не может назвать факты, различающие ветви, варианты пока искусственные; если может — найди самый дешёвый безопасный эксперимент.

## Самостоятельная работа без ИИ

Возьми знакомую небольшую функцию приложения и напиши три версии запроса: исходную формулировку, список уточнений и один проверяемый критерий. Рядом отметь, какое решение изменится от каждого возможного ответа. Выбери неизвестное с наибольшей стоимостью позднего обнаружения и опиши безопасный эксперимент, срок и условие остановки. На следующий день перечитай карточку, оставив только заголовки, и попробуй восстановить цепочку решения; если не получается — карточка неполна.

## Если что-то пошло не так

- Красный закрытый пример `"Confirmed"` → сравнение без учёта регистра; контракт требует ровно `confirmed`.
- `review` для пустого источника → проверяются не оба аргумента: нужно `||`, а не `&&`.
- `timeboxed-trial` для необратимого важного решения → ветка «обратимо» стоит раньше ветки «необратимо и важно»; приоритет у первой из описания.
- `missing return` → нет последнего `return` для случая «остальные».
- `import … is not allowed` → импорты в заданиях урока запрещены: это сравнения строк и логика.

## Практика

Три функции без `main` и печати; среда вызывает их и показывает результаты строками JSON в кавычках. Успешное прохождение подтверждает только таблицу соответствия для ограниченного контракта — не качество интервью, свидетельств или архитектуры.

### Задание 1 · Классификация ответа

**Цель.** Пустая строка → `clarify`; ровно `confirmed` → `evidence`; любое другое непустое значение → `assumption`.

**Ожидаемый вывод** — для `""` и `"confirmed"`:

```text
"clarify"
"evidence"
```

**Шаги.**
1. Выбери задание «Классификация ответа»: сигнатура `func RequirementKind(answer string) string`. Импорты запрещены.
2. Первая проверка — `answer == ""`, вторая — `answer == "confirmed"`, последний `return "assumption"`.
3. «Запустить», «Проверить» — закрытые примеры: `"uncertain"` и `"Confirmed"` → оба `assumption`.

**Как проверить себя.** Сравнение чувствительно к регистру; функция классифицирует только метку и не проверяет происхождение ответа.

**Если не принято.**
- Красный закрытый пример `"Confirmed"` → приведение к нижнему регистру или сравнение без учёта регистра.
- `assumption` для пустой строки → проверка пустоты стоит не первой.

> **Подсказка.** Три `return`, два `if`; порядок проверок — часть контракта.

### Задание 2 · Полнота критерия

**Цель.** Если `target` или `source` пуст → `incomplete`; иначе → `review`.

**Ожидаемый вывод** — для `("p95", "synthetic-test")` и `("", "log")`:

```text
"review"
"incomplete"
```

**Шаги.**
1. Выбери задание «Полнота критерия»: сигнатура `func CriterionState(target, source string) string`. Импорты запрещены.
2. Верни `"incomplete"`, если `target == "" || source == ""`; иначе `"review"`.
3. «Запустить», «Проверить» — закрытые примеры: `("availability", "")` → `incomplete`, `("x", "y")` → `review`.

**Как проверить себя.** `review` никогда не превращается в `accepted`: пригодность метрики и источника проверяет человек.

**Если не принято.**
- `review` для `("availability", "")` → проверен только `target`.
- Красный «пример 1» → перепутаны значения: заполненные оба поля дают `review`.

> **Подсказка.** Одно условие с `||` и два `return`.

### Задание 3 · Следующий безопасный шаг

**Цель.** Необратимо и влияние высокое → `evidence-first`; иначе обратимо → `timeboxed-trial`; остальное → `owner-review`.

**Ожидаемый вывод** — для `(reversible=false, highImpact=true)` и `(true, true)`:

```text
"evidence-first"
"timeboxed-trial"
```

**Шаги.**
1. Выбери задание «Следующий безопасный шаг»: сигнатура `func NextStep(reversible, highImpact bool) string`. Импорты запрещены.
2. Первая ветка — `!reversible && highImpact`; вторая — `reversible`; последний `return "owner-review"`.
3. «Запустить», «Проверить» — закрытые примеры: `(false, false)` → `owner-review`, `(true, false)` → `timeboxed-trial`.

**Как проверить себя.** Обратимое решение всегда даёт `timeboxed-trial` независимо от влияния; `owner-review` остаётся только для необратимого и малозначимого.

**Если не принято.**
- `timeboxed-trial` для `(false, true)` → ветка «обратимо» стоит первой.
- `owner-review` для `(true, false)` → условие второй ветки проверяет ещё и `highImpact`, хотя не должно.

> **Подсказка.** Функция не оценивает обратимость и влияние — она только применяет приоритет к переданным флагам.

## Проверь себя

- Как отличить требование от предположения?
- Какой вопрос стоит уточнить первым?
- Что доказывают векторы заданий, а что нет?
- Какой ответ на открытый вопрос изменил бы границу данных?
- Какова стоимость ошибки и как отменить временное решение?

## Итог

- Просьбу разбирают по слоям: пользователь и задача, функциональные требования и атрибуты качества, ограничения с источником, неизвестные по влиянию.
- Критерий приёмки — наблюдаемое условие с источником и владельцем; гипотеза называет опровергающее наблюдение; «неизвестно» хранится отдельно от нуля.
- Запись решения фиксирует выбор, альтернативы, последствия и условие пересмотра; необратимое и важное требует свидетельств до действия.
