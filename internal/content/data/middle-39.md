# 39. TaskFlow: race, shutdown и нагрузка

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `middle-38`; предыдущая глава `middle-38`.  
**Планируемый порядок каталога:** 79.  
**Результат:** Останавливать приём задач и дренировать активные операции в bounded grace period.; Фиксировать параметры и границы load/failure tests и интерпретировать результаты race detector.; Не трактовать conjunction из флагов как фактический запуск тестов или гарантию отсутствия гонок.

## Глоссарий

- **data race (гонка данных)** — Несинхронизированный конкурентный доступ к общей памяти, где есть запись.
- **graceful shutdown (мягкое завершение)** — Прекращение приёма новой работы и ограниченное ожидание уже начатой.
- **bounded workload (ограниченная нагрузка)** — Тест с зафиксированными пределами запросов, времени и ресурсов.
- **race detector (детектор гонок)** — Инструмент Go, обнаруживающий исполняемые несинхронизированные обращения.
- **cancellation (отмена)** — Кооперативный сигнал прекратить работу через context.

## Теория и границы применения

Проверка race, shutdown и нагрузки должна быть ограниченной и воспроизводимой. Сначала сформулируйте workload: число worker, количество операций, длительность, размер данных и верхний предел ресурсов. Для короткого unit/failure прогона используйте небольшой фиксированный объём; нагрузочный тест не должен превращаться в бесконечный генератор запросов. Сравнивайте одинаковые версии и параметры, иначе различия среды будут выданы за изменение кода.

Go race detector (`go test -race`) находит гонки данных, проявившиеся на исполняемых тестом путях. Он не доказывает отсутствие гонок при всех последовательностях и не обнаруживает каждую логическую гонку, например потерю обновления, если доступы формально синхронизированы. Создайте конкурентный тест, который действительно запускает операции одновременно, дождитесь их завершения и проверяйте бизнес-инварианты. Подтверждайте базовый тест без нагрузки до сравнения результатов.

Мягкое завершение — управляемый протокол. Сначала readiness прекращает привлекать новые запросы, затем admission gate перестаёт запускать новые фоновые задачи. Уже выполняющаяся работа получает конечный grace period. Успевшие задачи завершаются; после срока context отменяет остаток, listener и клиенты закрываются в порядке владения ресурсами. Контекст не прерывает код, который его игнорирует, поэтому верхний уровень обязан иметь жёсткий предел завершения и отчёт об оставшейся работе.

Проверьте пустой процесс, одну активную задачу, несколько параллельных задач, отмену во время I/O и задачу, которая игнорирует context. Во время drain новые запросы должны отвергаться предсказуемо, уже подтверждённые результаты не должны теряться, а ресурсы должны закрываться ровно одним владельцем. Не закрывайте канал, пока отправители могут писать. `WaitGroup` полезен только если вы контролируете регистрацию и гарантированно не добавляете работу после начала ожидания.

Измеряйте фактические ошибки, задержку и завершённые операции с верхней границей времени и памяти. Если нагрузка не достигла заданной интенсивности или telemetry пропала, результат неопределённый, а не PASS. Фиксируйте версии Go, команду, параметры, число повторов и пропущенные проверки. Benchmark отвечает на сравнение реализации в конкретной среде; он не устанавливает production SLO без репрезентативных данных и согласованного окна.

`LoadFits`, `CloseStatus` и `ReleaseEvidence` — функции классификации. Последняя проверяет только переданные флаги и не запускает `go test`, race detector, failure suite или нагрузку. Для release evidence приложите реальные exit codes и параметры к версии кода. Один успешный `go test -race` подтверждает только этот прогон и его охват.

Для bounded load запишите offered rate, длительность, предел конкурентных задач и ожидаемый диапазон завершений. Ограничивайте нагрузчик собственным context и гарантируйте закрытие его ресурсов. Снимайте baseline на пустом окружении и повторяйте одинаковый прогон; не сравнивайте запуск с прогретым кэшем против холодного, не отметив это. При замедлении фиксируйте распределение latency, ошибки, активные goroutines и очередь, не только среднее. Укажите, если runner контейнера или CI ограничил CPU: число запросов само по себе не описывает интенсивность. Failure scenario должен иметь stop condition по latency/error rate, времени и числу незавершённых операций. Проверка graceful shutdown включает сигнал остановки и конечный deadline процесса, а не только вызов функции Close. После завершения убедитесь, что фоновый worker не остался, временные файлы удалены и новый запуск проходит health check. Результат `ReleaseEvidence` нельзя получить честно, пока эти команды не выполнены и не сохранены вместе с версией кода.

## Три самостоятельных запускаемых примера

### Пример 1: `LoadFits`

Контракт: true для nonnegative offered и positive capacity, если offered<=capacity.

```go
package main

import "fmt"

func LoadFits(offered, capacity int) bool {
	return offered >= 0 && capacity > 0 && offered <= capacity
}

func main() {
	fmt.Println(LoadFits(8, 10))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `CloseStatus`

Контракт: Отрицательная active→invalid; ноль→closed; активность и expired→cancel_remaining; иначе draining.

```go
package main

import "fmt"

func CloseStatus(active int, graceExpired bool) string {
	if active < 0 { return "invalid" }; if active == 0 { return "closed" }; if graceExpired { return "cancel_remaining" }; return "draining"
}

func main() {
	fmt.Println(CloseStatus(0, false))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `ReleaseEvidence`

Контракт: true только когда все четыре независимых evidence checks отмечены; helper сам тесты не запускает.

```go
package main

import "fmt"

func ReleaseEvidence(unit, race, failure, boundedLoad bool) bool {
	return unit && race && failure && boundedLoad
}

func main() {
	fmt.Println(ReleaseEvidence(true, true, true, true))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

## Лабораторная карточка TaskFlow: TaskFlow: race, shutdown и нагрузка

Определите конкретный сценарий с одной пользовательской операцией. Укажите principal, объект, tenant, действие и ожидаемое состояние. Перечислите trust boundary (границу доверия), где вход считается недоверенным, где аутентификация проверена, и какой сервис принимает окончательное решение. Затем перечислите наблюдения: ответ HTTP, доменное событие, запись данных, лог и trace. Если одно из наблюдений отсутствует или запаздывает, результат должен оставаться неопределённым, а не автоматически считаться успешным.

До запуска теста зафиксируйте начальное состояние и независимые данные для двух владельцев. Включите положительный случай и минимум две отрицательные комбинации: неверный tenant, неверная роль, отменённый context, истёкший deadline, закрытие сервера или повторное событие — выберите те, которые относятся к теме главы. Подтвердите, что отрицательный сценарий не меняет данные и не пишет секрет в лог. Если чистый helper не может показать этот эффект, обозначьте интеграционную проверку как отдельное обязательное доказательство.

Наблюдение следует отделить от интерпретации. «Ответ вернул 404» — факт теста; «IDOR невозможен» — слишком сильный вывод. Чтобы обосновать более узкое утверждение, проверьте конкретный endpoint с authenticated principal, запустите запрос с чужим ID и подтвердите отсутствие утечки тела и побочного изменения. Аналогично, один `go test -race` на небольшой набор не гарантирует отсутствия data race при другой последовательности. Укажите точные пути, которые тест фактически исполнил.

Для operational readiness перечислите владельцев процедур: кто меняет readiness, кто наблюдает drain, кто смотрит saturation, кто останавливает нагрузочный тест и кто принимает rollback решение. Пороговые значения должны быть определены владельцами проекта и измерены на сопоставимой среде. Эта программа не задаёт production SLA. Если у учебной системы пока нет измеренных данных, запишите только ожидаемые проверки и назовите статус как непроверенный.

Для failure case определите инъекцию только в тестовой среде и ограничьте воздействие числом запросов, временем либо тестовой очередью. До старта проверьте cleanup и состояние ресурса. После эксперимента подтвердите, что соединения закрыты, временные записи очищены и service вернулся к ready только после проверки обязательной зависимости. При неожиданном результате немедленно прекратите эксперимент и сохраните логи с очищенными секретами. Не расширяйте нагрузку, пока не объяснили расхождение и не повторили исходный контрольный прогон.
