# TaskFlow: race, shutdown и нагрузка

## Что ты сделаешь

Ты напишешь три проверки, которые относятся к финальному этапу TaskFlow: решение о закрытии при остановке, проверку, помещается ли заданная нагрузка в ёмкость, и сборку решения о готовности из независимых признаков. Функции получают числа и флаги и возвращают ответ. Они не запускают нагрузочный тест, не вызывают детектор гонок и не закрывают пул. Эти действия выполняются в стенде, а здесь проверяется только логика их интерпретации.

## Остановка без потери работы

Остановка сервиса проходит в три шага. Сначала сервис перестаёт принимать новые задачи, то есть отвечает на новые запросы отказом, а readiness сообщает, что приём закрыт. Затем он ждёт завершения уже начатых операций в пределах ограниченного срока. Наконец, если срок истёк, оставшиеся операции отменяются через контекст, и сервис закрывает пул.

Срок ожидания задаётся заранее и записывается в настройки. Без него остановка может висеть бесконечно, потому что одна зависшая операция держит процесс. С другой стороны, срок слишком короткий обрывает работу, которая почти завершилась. Значение выбирают по измеренной длительности самой долгой операции плюс запас. Запас обычно берут не меньше половины длительности самой долгой операции, иначе обычный разброс времени будет принят за зависание и срок сработает ложно. Это число тоже записывают в настройки, а не оставляют в коде без пояснения.

Решение о состоянии закрытия удобно выразить функцией. Пример 1 показывает, как число активных операций и флаг истёкшего срока дают одно из состояний.

```go
package main

import "fmt"

func closeState(active int, graceExpired bool) string {
	if active < 0 {
		return "invalid"
	}
	if active == 0 {
		return "closed"
	}
	if graceExpired {
		return "cancel_remaining"
	}
	return "draining"
}

func main() {
	fmt.Println(closeState(0, false))
	fmt.Println(closeState(2, false))
	fmt.Println(closeState(2, true))
}
```

Вывод: `closed`, `draining`, `cancel_remaining`. Состояние `draining` означает, что приём уже закрыт, а работа ещё идёт. Отрицательное число активных операций — ошибка счётчика, и решение о закрытии не принимается.

## Гонки данных и детектор

Гонка данных возникает, когда две горутины обращаются к одной переменной, и хотя бы одна из них пишет, без синхронизации. Результат становится зависящим от планировщика: иногда всё работает, иногда счётчик показывает неверное значение. Такие ошибки плохо воспроизводятся, поэтому их нельзя найти прогоном вручную.

Детектор гонок встроен в Go и включается флагом `-race` у `go test` и `go run`. Он отслеживает реальные обращения во время прогона и сообщает о гонке, если она произошла на этом пути выполнения. Отсутствие отчёта не доказывает отсутствие гонки: непокрытый путь остаётся непроверенным. Поэтому детектор запускают вместе с тестами, которые одновременно нагружают общий код.

Пример 2 показывает защищённый счётчик. Мьютекс не даёт двум горутинам писать одновременно, и итог детерминирован.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	var wg sync.WaitGroup
	count := 0
	for i := 0; i < 10; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 100; j++ {
				mu.Lock()
				count++
				mu.Unlock()
			}
		}()
	}
	wg.Wait()
	fmt.Println(count)
}
```

Вывод: `1000`. Без мьютекса тот же код может печатать меньшее число, и `-race` укажет на конфликтующие строки. Сам вывод `1000` не доказывает отсутствие гонки, он показывает только, что в этом прогоне общий счётчик не потерял обновлений.

## Закрытие с ожиданием

Пример 3 показывает ожидание завершения операций. Каждая горутина работает и сообщает о завершении через `WaitGroup`. Главный поток ждёт, пока все операции не закончатся, и только после этого печатает итог.

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	results := make(chan string, 3)
	for i := 1; i <= 3; i++ {
		wg.Add(1)
		go func(id int) {
			defer wg.Done()
			results <- fmt.Sprintf("job %d done", id)
		}(i)
	}
	wg.Wait()
	close(results)
	n := 0
	for range results {
		n++
	}
	fmt.Println("all done", n)
}
```

Вывод: `all done 3`. Буфер канала равен числу операций, поэтому никто не блокируется на отправке, а `close` после `Wait` безопасен: в канал больше никто не пишет. Закрыть канал до ожидания нельзя: горутина, которая ещё пишет, получит панику.

## Ограниченная нагрузка

Нагрузочный тест нужен, чтобы узнать, выдержит ли система заданный поток задач. Главное правило — нагрузка должна быть ограничена. Запись «создать задач столько, сколько успеем за минуту» не воспроизводима: результат зависит от машины, и сравнить два прогона нельзя. Правильно задать число предлагаемых задач, число одновременных клиентов и длительность, и измерять то, что система сделала за это время.

Задание 1 этой главы проверяет самую простую форму этой идеи: нагрузка помещается в ёмкость, если предлагаемое число не больше ёмкости. Это простая проверка, но она делает границу явной. Если предлагаемое число больше ёмкости, тест ожидает отказ или очередь, а не молчаливое ускорение.

Результаты нагрузочного прогона хранят вместе с параметрами: версия кода, число клиентов, размер пакета, длительность, характеристики машины и состояние соседних процессов. Без параметров сравнение двух чисел ничего не говорит. Сохранённый отчёт должен позволять повторить прогон и получить сопоставимый результат.

## Тест отказа под нагрузкой

Тест отказа проверяет, что система делает, когда часть зависимостей падает во время нагрузки. Он интереснее, чем тест без сбоев, потому что именно при сбое проявляются ошибки закрытия: зависшие горутины, потерянные задачи и неотмеченные строки. Порядок такой же, как в предыдущих главах: сначала фиксируется ожидаемое поведение, затем запускается сбой в стенде и сравнивается результат.

Для TaskFlow ожидаемое поведение при остановке под нагрузкой записывают так. Новые задачи получают отказ. Уже принятые задачи либо завершаются в срок, либо возвращаются в очередь с отметкой. Ни одна задача не теряется и не публикуется дважды. Если хотя бы один пункт не выполнен, тест фиксирует отказ, даже когда все остальные показатели в норме.

## Сборка решения о готовности

Решение о выпуске состоит из нескольких независимых признаков: модульные тесты прошли, детектор гонок не сообщил о гонке на нагрузочном пути, тест отказа дал ожидаемое поведение, нагрузка ограничена. Каждый признак получен своим способом и может отсутствовать. Поэтому решение записывается как конъюнкция: все признаки обязательны, и отсутствие любого делает результат ложным.

Функция из задания Hard показывает эту сборку. Она возвращает истину только тогда, когда все четыре признака отмечены. Сама функция ничего не запускает: она принимает готовые флаги. Поэтому её результат — лишь отражение того, что записали люди или инструменты, а не доказательство качества.

## Что видно в отчёте прогона

Отчёт прогона отвечает на три вопроса: что сделали, как быстро и что пошло не так. Первый ответ дают параметры: число клиентов, число задач, размер пакета, длительность и версия кода. Второй — распределение времени ответа, а не одно среднее значение. Среднее скрывает хвост, и именно в хвосте живут таймауты, которые пользователь замечает. Третий ответ дают ошибки по классам: отказ при остановке, таймаут, конфликт записи.

Отчёт хранят рядом с кодом, из которого он получен, и не перезаписывают. Новый прогон добавляется отдельной строкой. Так видно, стало ли хуже после изменения, а не только каким получилось число сегодня. Если стенд менялся между прогонами, это тоже записывается, иначе разница в цифрах будет принята за эффект кода.

## Типичные ошибки и исправление

> **Типичная ошибка.** Считать, что отсутствие сообщения детектора гонок означает отсутствие гонки. Детектор видит только те пути, которые реально выполнились в прогоне.

Другие ошибки в этой главе повторяются. Остановка ждёт без срока и висит на зависшей операции. Закрытие канала делается до того, как все писатели завершились. Нагрузка задана без границ и не воспроизводится. Результаты сохраняются без параметров, и сравнение ничего не значит.

## Если что-то пошло не так

- Остановка не завершается минутами → нет срока ожидания или зависшая операция не отменяется; добавь контекст с таймаутом.
- Паника «send on closed channel» при остановке → канал закрыт до `Wait`; закрывай после ожидания всех писателей.
- Нагрузочный прогон на разных машинах даёт разные числа → параметры не записаны; сохраняй версию и ресурсы машины.
- Детектор молчит, но счётчик врёт → путь без нагрузки не покрыт; добавь тест с параллельными вызовами.

> **Подсказка.** Сначала вход, затем ноль, потом срок. Ноль означает закрытие, даже если срок истёк.

## Итог

- Остановка сначала закрывает приём, потом ждёт операции в пределах заранее заданного срока, и только затем отменяет оставшееся.
- Детектор гонок сообщает о гонках на реально выполненных путях; нагрузка ограничивается числами, а результаты хранятся вместе с параметрами прогона.
- Решение о выпуске собирается из независимых признаков, и логическая сборка лишь отражает записанные факты, а не заменяет тесты.
