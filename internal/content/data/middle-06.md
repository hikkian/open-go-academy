# Mutex и критическая секция

## Что ты сделаешь

Ты напишешь три функции-модели для составного состояния: изменение баланса с ограничением, применение последовательности изменений и перевод между двумя счетами. Примеры главы покажут, почему mutex защищает инвариант, а не отдельное присваивание, и что происходит, когда проверка и запись разделены.

## Mutex даёт исключительное владение

`sync.Mutex` позволяет одному участнику держать критическую секцию. Пока один участник держит `Lock`, другой участник того же mutex ждёт у `Lock` и не входит в секцию. Это взаимное исключение, а не порядок выполнения: кто именно войдёт первым, программа не обещает.

Пример с общим счётчиком: сто горутин увеличивают баланс под одним mutex. Без блокировки результат мог бы потерять часть обновлений. С блокировкой он всегда равен ста.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var mu sync.Mutex
    var wg sync.WaitGroup
    balance := 0
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()
            balance++
            mu.Unlock()
        }()
    }
    wg.Wait()
    fmt.Println(balance)
}
```

Вывод: `100`. Каждое увеличение выполняется целиком внутри критической секции, поэтому два участника не читают одно и то же старое значение.

## Критическая секция покрывает инвариант

Защищать нужно не отдельную строку, а весь переход от согласованного состояния к следующему согласованному состоянию. Если баланс и версия меняются вместе, их обновление должно быть видно другим участникам целиком. Иначе кто-то прочитает новый баланс и старую версию.

```go
package main

import (
    "fmt"
    "sync"
)

type account struct {
    mu      sync.Mutex
    balance int
    version int
}

func (a *account) deposit(n int) {
    a.mu.Lock()
    defer a.mu.Unlock()
    a.balance += n
    a.version++
}

func main() {
    acc := &account{}
    var wg sync.WaitGroup
    for i := 0; i < 3; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            acc.deposit(10)
        }()
    }
    wg.Wait()
    fmt.Println(acc.balance, acc.version)
}
```

Вывод: `30 3`. Баланс и версия меняются внутри одной секции, поэтому каждое изменение видно целиком. Если бы `version++` стоял вне `Lock`, версия могла бы отставать от баланса.

## Чтение тоже доступ

Чтение конфликтует с записью. Одновременное чтение и запись того же поля без синхронизации — гонка данных, даже если кажется, что читается одно число. Поэтому читатель тоже берёт тот же mutex, если значение может меняться.

Если читателей много, а записи редки, существует `sync.RWMutex`: читатели берут `RLock` и могут работать одновременно, а писатель `Lock` ждёт, пока все читатели уйдут. Этот выбор стоит делать после измерения. Для короткой секции обычный `Mutex` часто быстрее, потому что `RWMutex` сам по себе тратит ресурсы на учёт читателей.

Инструкция `defer mu.Unlock()` сразу после `Lock` защищает от раннего выхода. Все ветки возврата освобождают блокировку, и забыть `Unlock` при добавлении нового `return` становится трудно.

```go
package main

import (
    "fmt"
    "sync"
)

var mu sync.Mutex
var limit = 5

func trySet(v int) bool {
    mu.Lock()
    defer mu.Unlock()
    if v > limit {
        return false
    }
    limit = v
    return true
}

func main() {
    a := trySet(3)
    b := trySet(9)
    fmt.Println(a, b, limit)
}
```

Вывод: `true false 3`. Проверка лимита и его запись находятся в одной секции, поэтому второй вызов видит результат первого.

## Что нельзя делать под блокировкой

Критическая секция должна быть достаточно широкой, чтобы сохранить инвариант, и достаточно короткой, чтобы не мешать остальным. Не вызывай под lock неизвестный callback, сетевой запрос, медленный ввод или запись в медленный журнал. Такой код держит блокировку дольше, чем нужно, и других участников становится много в очереди ожидания.

Callback опасен вдвойне: он может снова взять тот же mutex. `sync.Mutex` не реентрантен: повторный `Lock` той же горутиной ждёт освобождения, которого не будет, и программа зависнет. Если такой вызов неизбежен, вынеси его за пределы секции: скопируй нужные данные под lock, отпусти блокировку и только потом вызывай внешний код.

Если нужны два mutex, захватывай их в одном глобальном порядке. Иначе первый участник будет ждать второй mutex, держа первый, а второй участник — наоборот. Оба будут ждать друг друга вечно.

> **Важно.** Mutex защищает только тех, кто его захватывает. Если часть кода читает поле напрямую, мимо протокола, инвариант уже не защищён, даже если у структуры есть блокировка.

## Модель и механизм

Инвариант для mutex-а — это связь нескольких полей, которая должна быть истинна между операциями. Сначала запиши эту связь словами, потом найди все места, где поля читаются или меняются, и только после этого реши, какой lock их покрывает.

Для составного состояния полезны три вопроса. Какой инвариант должен сохраняться всегда? Какие поля в него входят? Какие операции читают или меняют их? Ответы записываются до кода: блокировка без явного инварианта лишь закрывает видимую часть проблемы.

Синхронизация имеет цену. Mutex создаёт ожидание, и чем шире секция, тем дольше ждут остальные. Поэтому сначала сохраняют инвариант, а потом сужают секцию, и только после этого измеряют нагрузку.

## Типичные ошибки и исправление

Первая ошибка — защищать только запись, а проверку и чтение оставить снаружи. Тогда между проверкой и записью другой участник успевает изменить состояние. Исправление — держать lock на весь переход, включая проверку.

Вторая — держать lock только вокруг одной половины инварианта. Баланс обновлён, а версия ещё нет, и читатель видит противоречивую пару значений. Исправление — менять связанные поля в одной секции.

Третья — забыть `Unlock` на ветке раннего возврата. Программа зависнет при первой же ошибке. Исправление — `defer Unlock` сразу после `Lock`.

> **Типичная ошибка.** Считать, что зелёный тест на итоговый счётчик доказывает корректность. Тест может пропустить нарушение согласованности соседних полей, которое проявляется между операциями. Проверяй инвариант напрямую.

## Если что-то пошло не так

- Программа зависла на `Lock` → участник не отпустил блокировку или взял её повторно; проверь `defer Unlock` и вызовы под lock.
- Итог меняется от запуска к запуску → часть обращений к полю идёт мимо mutex; найди все чтения и записи.
- Два mutex дают взаимную блокировку → порядок захвата различается; зафиксируй единый порядок.
- Тест на счётчик проходит, а данные противоречивы → проверяется только итог; добавь проверку инварианта.

## Лаборатория перед практикой

Возьми пример с `deposit` и вынеси `a.version++` за `Unlock`, оставив баланс под блокировкой. Перед запуском запиши, может ли читатель увидеть новый баланс со старой версией, и почему. Затем добавь читателя, который в цикле читает оба поля под тем же `Lock`, и проверь, выполняется ли твой прогноз хотя бы в одном запуске.

Важно помнить, что один запуск не доказывает отсутствие ошибки. Журнал эксперимента содержит версию Go, команду с флагом `-race`, число участников, предсказание и наблюдение. Если наблюдение совпало с предсказанием, запиши, что именно подтверждено, а что осталось непроверенным: например, другие расписания.

### Практический мост: критическая секция в сервисе

Helper не использует mutex и не проверяет, защищены ли все обращения к общей памяти. Реальное согласование конкурентных операций в проекте P3 делает PostgreSQL: транзакции и уникальные ограничения. Тест `TestPostgresTaskOutboxAndTenantIsolation` в `content/projects/p3/reference/postgres_integration_test.go` проверяет именно это. Для реального DB-сценария используй disposable PostgreSQL.

Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда поднимает только disposable PostgreSQL из P3 Compose на loopback-порту 55433; пароль существует только в окружении shell. Она ждёт healthcheck, запускает точный тест и удаляет контейнер и volume при завершении блока:

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle06 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидай повтор ключа без дубликата и один receipt. Это SQL-инвариант, а не проверка Go `sync.Mutex`. Векторы этой главы охватывают только чистые функции: они не запускают goroutine и не заменяют интеграционные проверки.

## Итог

- Mutex даёт взаимное исключение: пока один участник держит блокировку, другой участник ждёт и не входит в секцию.
- Блокировка покрывает весь переход между согласованными состояниями, включая проверку и связанные поля.
- Защита действует только для тех, кто использует тот же mutex; внешний код вызывается вне секции.
