**Результат:** Выбирать повторы только для transient errors и в пределах deadline и общего retry budget.; Вычислять bounded exponential backoff без переполнения и лишней работы.; Различать scalar helper checks и интеграционные доказательства retry, bulkhead и breaker.

## Глоссарий

- **deadline (срок выполнения)** — Верхняя граница времени операции; после истечения downstream работа должна кооперативно завершиться.
- **retry budget (бюджет повторов)** — Общий предел дополнительных попыток, который не даёт сбоям усиливаться между слоями.
- **exponential backoff (экспоненциальная пауза)** — Увеличение задержки между временными повторами с верхним пределом.
- **bulkhead (изоляция ресурса)** — Ограничение числа одновременных операций на отдельной зависимости.
- **circuit breaker (автоматический выключатель)** — Состояния closed/open/half-open, управляющие допуском запросов после ошибок.

## Теория и границы применения

Повтор (retry) — новая попытка той же операции после ошибки. Он уместен только тогда, когда ошибка временная, операция может быть безопасно повторена, а в deadline ещё осталось время. Ошибка валидации, отказ в доступе и большинство ошибок конфигурации не станут временными от ещё одного запроса. Для записи сначала определите идемпотентный ключ или другой механизм защиты от повторного эффекта. Иначе ответ сервера может потеряться после успешного commit, и клиент создаст дубликат.

Политика повтора должна ограничивать число попыток, общий бюджет и время. Если клиент делает три попытки, а каждый из двух внутренних слоёв тоже делает три, одно исходное действие способно превратиться в 27 downstream вызовов. Выберите один слой-владелец повтора либо распределённый бюджет. Задержка exponential backoff растёт примерно как base × 2^attempt; верхняя граница ограничивает ожидание. В реальном распределённом сервисе добавляют jitter (случайное отклонение), чтобы множество клиентов не повторили запрос одновременно. Упражнение `BackoffMillis` намеренно считает детерминированные целые миллисекунды, без случайности и планировщика.

Deadline (крайний срок) ограничивает всю цепочку, а не только один вызов. Перед повтором надо оставить время на задержку и следующую попытку. В Go deadline передают через `context.Context`; дочерняя операция обязана проверять `ctx.Done()` и передавать контекст дальше. `context` — кооперативный сигнал: он не прерывает произвольный код или сетевую библиотеку, которая его игнорирует. Таймаут одного запроса downstream не заменяет общий срок родительской операции.

Bulkhead ограничивает конкуренцию вокруг конкретного ресурса: например, не более восьми одновременных запросов к медленному сервису. При насыщении политика должна быстро и предсказуемо отказать либо ждать только в пределах оставшегося deadline. Circuit breaker — отдельная state machine: closed пропускает работу и считает ошибки, open быстро отказывает, half-open допускает ограниченное число проб после периода охлаждения. Изменение строки `state` в чистом helper не реализует счётчики, окна, атомарный допуск или переходы между состояниями.

Проверяйте политику на фиксированных часах и управляемом fake downstream: успешный ответ, transient и permanent error, исчерпание бюджета, истечение deadline во время ожидания, насыщение bulkhead и переход breaker. Для concurrency нужны тесты реального кода допуска и отмены, включая освобождение слота после ошибки. Не называйте малую таблицу векторов доказательством доступности или SLA: она подтверждает лишь перечисленные входы и правила приоритета.

В TaskFlow зафиксируйте владельца политики: где классифицируют ошибку, кто расходует общий бюджет, кто устанавливает deadline и какая операция идемпотентна. Если любой из этих ответов неизвестен, retry должен быть отключён для этой операции до уточнения. Приёмочные выводы подтверждаются отдельным ограниченным integration test и наблюдаемыми числами попыток, а не только результатом helper.

Практически сравните две политики при одной и той же последовательности: transient timeout, затем успех. Без retry пользователь получает timeout, хотя зависимость восстановилась; с одной ограниченной попыткой система может завершить работу. Теперь добавьте задержку, которая длиннее остатка deadline: повтор только ухудшит latency. Ещё один сценарий — запись commit прошла, но ответ потерялся. Повтор безопасен лишь когда доменная операция защищена идемпотентным ключом, а не потому, что ошибка выглядит временной. Зафиксируйте для каждой попытки номер, причину, оставшееся время и итог без записи чувствительных payload. В тесте часы должны управляться вручную, иначе проверка backoff будет медленной и flaky. Убедитесь, что отмена во время ожидания возвращает управление и не удерживает bulkhead слот. Эти наблюдения переводят абстрактные helper rules в проверяемое поведение политики, не превращая локальный прогон в обещание production доступности.

## Три самостоятельных запускаемых примера

### Пример 1: `RetryDecision`

Контракт: Некорректные диапазоны→invalid; постоянная ошибка→stop; exhausted limit→exhausted; иначе retry.

```go
package main

import "fmt"

func RetryDecision(attempt, maxAttempts int, transient bool) string {
	if attempt < 0 || maxAttempts <= 0 { return "invalid" }; if !transient { return "stop" }; if attempt >= maxAttempts { return "exhausted" }; return "retry"
}

func main() {
	fmt.Println(RetryDecision(1, 3, true))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `BackoffMillis`

Контракт: Невалидные отрицательные значения→0; иначе base*2^attempt с насыщением в maxMillis без overflow.

```go
package main

import "fmt"

func BackoffMillis(attempt, baseMillis, maxMillis int) int {
	if attempt < 0 || baseMillis < 0 || maxMillis < 0 { return 0 }; delay:=baseMillis; for i:=0; i<attempt && delay<maxMillis; i++ { if delay > maxMillis/2 { return maxMillis }; delay*=2 }; if delay>maxMillis { return maxMillis }; return delay
}

func main() {
	fmt.Println(BackoffMillis(2, 100, 1000))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `CircuitAction`

Контракт: Deadline истёк→timeout; плохой bulkhead→invalid; насыщен→bulkhead_full; затем open/half_open/closed→reject_open/probe/call; иное→invalid_state.

```go
package main

import "fmt"

func CircuitAction(state string, deadlineLeftMillis, active, limit int) string {
	if deadlineLeftMillis <= 0 { return "timeout" }; if active < 0 || limit <= 0 { return "invalid" }; if active >= limit { return "bulkhead_full" }; switch state { case "open": return "reject_open"; case "half_open": return "probe"; case "closed": return "call"; default: return "invalid_state" }
}

func main() {
	fmt.Println(CircuitAction("closed", 500, 1, 4))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.
