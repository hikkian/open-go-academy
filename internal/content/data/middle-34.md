# Retries, timeout, bulkhead и circuit breaker

## Что ты сделаешь

Ты напишешь три проверки защиты от перегрузки: решение о повторе по классу ошибки и бюджету попыток, ограниченную экспоненциальную задержку без переполнения и выбор действия для вызова с учётом срока, изоляции и состояния зависимости. Функции решают по переданным числам и не выполняют запросы.

## Повтор только временной ошибки

Повтор полезен, когда ошибка может исчезнуть: кратковременная недоступность, таймаут, ограничение скорости. Повтор постоянной ошибки ничего не меняет и только добавляет нагрузку. Поэтому первое решение — классификация ошибки, а не таймер.

Перед повтором проверяются четыре условия. Ошибка временная. Операция безопасна к повтору: либо идемпотентна, либо имеет ключ, по которому её узнают. Остался срок запроса. Остался бюджет попыток. Если хотя бы одно условие нарушено, повтор не выполняется.

> **Важно.** Повтор операции, которая уже выполнила эффект, создаёт дубль. Поэтому безопасность повтора проверяется отдельно от временности ошибки.

## Порядок решения о повторе

Решение о повторе читают сверху вниз. Сначала отвергаются некорректные значения: отрицательная попытка и лимит, который не положителен. Затем постоянная ошибка даёт остановку, даже если попытки остались. И только временная ошибка при исчерпанном лимите даёт отказ по бюджету. Остаётся повтор.

Пример показывает такой порядок. Постоянная ошибка останавливает обработку раньше, чем исчерпанный бюджет:

```go
package main

import "fmt"

func decide(attempt, max int, transient bool) string {
    switch {
    case attempt < 0 || max <= 0:
        return "invalid"
    case !transient:
        return "stop"
    case attempt >= max:
        return "exhausted"
    }
    return "retry"
}

func main() {
    fmt.Println(decide(3, 3, false), decide(3, 3, true), decide(2, 3, true))
}
```

Вывод: `stop exhausted retry`. Постоянная ошибка на последней попытке даёт `stop`, а не `exhausted`: повторять её нельзя ни при каком бюджете.

## Экспоненциальная задержка с пределом

Задержка между повторами растёт экспоненциально: база умножается на два на каждой попытке. Без предела она быстро становится бессмысленной, поэтому её ограничивают сверху. Без защиты от переполнения умножение на большую попытку даёт отрицательное число или ноль, и клиент начинает повторять мгновенно.

Вычисление ведут с насыщением: как только значение достигло предела, дальше не умножают. Пример показывает такую последовательность для базы сто миллисекунд и предела пятьсот:

```go
package main

import "fmt"

func backoff(attempt, base, max int) int {
    if attempt < 0 || base < 0 || max < 0 {
        return 0
    }
    v := base
    for i := 0; i < attempt && v < max; i++ {
        if v > max/2 {
            return max
        }
        v *= 2
    }
    if v > max {
        return max
    }
    return v
}

func main() {
    for a := 0; a <= 4; a++ {
        fmt.Println(a, backoff(a, 100, 500))
    }
}
```

Вывод: `0 100`, `1 200`, `2 400`, `3 500`, `4 500`. На третьей попытке значение упирается в предел, и дальше задержка не растёт.

## Случайный разброс

Одинаковая задержка у всех клиентов означает, что они повторят запрос в один момент. Это создаёт волну нагрузки на уже перегруженную зависимость. Поэтому к задержке добавляют случайный разброс. Разброс проверяют на контролируемом источнике случайности, а не в тестах с реальным временем.

## Таймаут и общий срок

Таймаут отдельной попытки не может быть длиннее оставшегося срока запроса. Если клиент готов ждать две секунды, а одна попытка занимает полторы, второй попытки уже не будет, и повтор бессмыслен. Поэтому повтор проверяет остаток срока до задержки, а не после неё.

Срок нужно учитывать во всех слоях. Если верхний слой повторяет три раза, а нижний ещё три, получается девять обращений к зависимости на один запрос. Такое умножение называют усилением повторов (retry amplification). Его предотвращают общим бюджетом попыток на весь путь вызова, а не бюджетом в каждом слое.

## Изоляция ресурса

Изоляция переборкой (bulkhead) ограничивает число одновременных вызовов к одной зависимости. Если один медленный клиент занял все слоты, остальные запросы получают отказ сразу, а не ждут вместе с ним. Изоляция защищает остальные части системы, но не делает медленную зависимость быстрее. Поэтому переборку настраивают отдельно для каждой зависимости: медленный платёжный сервис не должен занимать слоты, нужные каталогу.

Проверка изоляции — это проверка числа занятых слотов. Слот занят, пока вызов не завершился. Отрицательное число занятых слотов означает ошибку учёта, а предел должен быть положительным.

## Circuit breaker

Размыкатель цепи (circuit breaker) перестаёт вызывать зависимость, которая стабильно падает. В открытом состоянии вызовы отклоняются сразу. В полуоткрытом состоянии пропускают один пробный вызов. Если он успешен, цепь замыкается, если нет — снова открывается.

Пример показывает выбор действия для трёх состояний. Открытая цепь отклоняет вызов, полуоткрытая пропускает пробный, закрытая пропускает обычный:

```go
package main

import "fmt"

func action(state string) string {
    switch state {
    case "open":
        return "reject_open"
    case "half_open":
        return "probe"
    case "closed":
        return "call"
    }
    return "invalid_state"
}

func main() {
    fmt.Println(action("open"), action("half_open"), action("closed"))
}
```

Вывод: `reject_open probe call`. Пробный вызов в полуоткрытом состоянии один: остальные запросы в это время получают отказ, иначе пробы превратятся в новую волну нагрузки. Одна и та же зависимость получает разное поведение в зависимости от состояния цепи.

## Модель и механизм

Для защиты от перегрузки полезны три вопроса. Какие ошибки повторяемы и операции ли безопасны к повтору? Какой общий бюджет на весь путь вызова? Что происходит с нагрузкой, когда зависимость падает? Ответы записываются как политика до написания клиента.

Синхронизация здесь важна: счётчики занятых слотов и состояние цепи меняются из многих горутин. Их защищают атомарно или под мьютексом, иначе бюджет и изоляция перестают соответствовать действительности.

Заметьте, что порядок проверок в функции решения тоже часть политики. Сначала отсекаются неверные входы, потом исчерпанный бюджет, и только после этого разрешается следующая попытка. Если поменять порядок, некорректный запрос может получить повтор, а исчерпанный бюджет не будет виден в логах.

## Типичные ошибки и исправление

Первая ошибка — повторять все ошибки подряд. Исправление — классификация ошибок и отдельное решение о повторе.

Вторая — повторять неидемпотентную операцию без ключа. Исправление — ключ операции или запрет повтора.

Третья — складывать бюджеты слоёв. Исправление — общий бюджет на весь путь.

Четвёртая — держать размыкатель открытым навсегда. Исправление — пробный вызов через заданный интервал.

> **Типичная ошибка.** Считать, что circuit breaker защищает запросы, которые уже выполняются. Он решает только, пускать ли новые вызовы; уже начатые вызовы нужно завершать или отменять по сроку.

## Если что-то пошло не так

- Нагрузка на зависимость растёт в несколько раз при сбое → повторы на нескольких слоях складываются; введи общий бюджет.
- Все клиенты повторяют одновременно → задержка без разброса; добавь случайную составляющую.
- Медленный клиент блокирует остальных → нет изоляции; ограничь число одновременных вызовов.
- Размыкатель не закрывается после восстановления зависимости → нет пробного вызова; добавь полуоткрытое состояние.

## Воспроизводимая лабораторная: задержка и предел повторов

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Сеть и зависимость не нужны: задержки считаются, а не ждутся.

Программа ниже печатает последовательность задержек для базы сто миллисекунд и предела пятьсот, а затем решение о повторе для трёх попыток. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import "fmt"

func backoff(attempt, base, max int) int {
    v := base
    for i := 0; i < attempt && v < max; i++ {
        if v > max/2 {
            return max
        }
        v *= 2
    }
    if v > max {
        return max
    }
    return v
}

func main() {
    total := 0
    for a := 0; a < 4; a++ {
        d := backoff(a, 100, 500)
        total += d
        fmt.Println("attempt", a, "delay", d)
    }
    fmt.Println("total", total)
}
```

**Ожидайте:** четыре строки `attempt 0 delay 100`, `attempt 1 delay 200`, `attempt 2 delay 400`, `attempt 3 delay 500`, затем `total 1200`. Суммарная задержка показывает, сколько клиент ждёт, если повторяет все попытки подряд.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- Повтор разрешён только для временной ошибки, безопасной операции, при остатке срока и бюджета попыток.
- Задержка растёт экспоненциально, ограничена сверху и считается с насыщением; общий бюджет попыток задаётся на весь путь вызова.
- Изоляция ограничивает число одновременных вызовов, а размыкатель прекращает вызовы стабильно падающей зависимости; оба решения проверяются интеграционными тестами.
