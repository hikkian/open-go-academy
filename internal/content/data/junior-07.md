## Интерфейсы и композиция

Интерфейс (interface) — набор требований к поведению: имя метода, параметры и результаты. Тип реализует такой контракт не объявлением «implements», а наличием подходящих методов. Это не наследование состояния. Интерфейс обычно принадлежит коду, который его использует: потребитель формулирует минимальную потребность, а поставщик типа удовлетворяет ей случайно и без зависимости от пакета потребителя.

В Go композиция (composition) соединяет небольшие значения и делегирует поведение через поля и методы. Встраивание (embedding) помещает поле внутрь структуры и продвигает доступ к его методам, но само по себе не создаёт подтип и не решает вопрос владения. Несколько маленьких контрактов часто яснее одного интерфейса «на все случаи». Указывайте интерфейс в параметре функции, когда действительно нужна подмена поведения; для данных используйте конкретный тип.

Пустой интерфейс interface{} или any принимает любое значение, но почти ничего не обещает вызывающему коду. Сужение типа (type assertion) и переключатель типов (type switch) нужны только когда контракт действительно допускает варианты. Не превращайте их в скрытую систему динамических типов. Указатель на интерфейс обычно не нужен: интерфейс уже содержит динамический тип и значение.

Особая ловушка — типизированный nil (typed nil). Если переменная с типом *File равна nil, присваивание её в переменную интерфейса Reader создаёт интерфейс с динамическим типом *File и nil-значением. Сам интерфейс при этом не равен nil. Поэтому проверка reader == nil не обнаружит такой случай, а вызов метода может упасть. Лучше возвращать настоящий nil-интерфейс, проверять указатель до преобразования или проектировать метод, который безопасно обрабатывает nil receiver, если это понятно и оправдано.

Компилятор проверяет соответствие методов только там, где значение используется как интерфейс. Явное утверждение var _ io.Reader = (*File)(nil) — compile-time assertion (проверка при компиляции); оно полезно для важной границы пакета, но не требуется повсюду. При добавлении метода меняется контракт типов, при смене receiver легко потерять реализацию: значение и указатель имеют разные наборы методов.

Контракт должен объяснять семантику, а не только сигнатуру. Что означает EOF? Можно ли вызвать метод параллельно? Кто закрывает ресурс? Может ли метод вернуть частичный результат вместе с ошибкой? Интерфейс io.Reader обещает чтение в буфер и использует io.EOF для обычного окончания потока; конкретные источники могут иметь дополнительные ошибки. Потребитель обязан проверять результат и ошибку согласно контракту.

Функция с io.Reader принимает данные из файла, памяти, сети или тестового источника одинаково. Для этого урока используем strings.NewReader: никакого внешнего файла или сети не нужно. Так тест контролирует вход и воспроизводит пограничный случай. В боевом коде внедряйте именно небольшую потребность, например чтение, а не весь большой клиент, если функция вызывает только Read.

Тестовая подмена (fake) — простая настоящая реализация контракта для теста. Она хранит входные байты и фиксирует вызовы, если это важно. Подмена не должна повторять алгоритм production-кода: иначе один и тот же дефект окажется в обоих местах. Предпочитайте strings.Reader, bytes.Buffer и другие стандартные значения, если они уже подходят. Mock-фреймворк новичку не нужен.

Ошибки являются частью результата. Если интерфейсный метод возвращает error, вызывающий код проверяет её сразу и при необходимости добавляет контекст через %w, сохраняя errors.Is и errors.As. Не сравнивайте текст ошибки для управления потоком. При преобразовании конкретного типа в интерфейс следите, чтобы ошибка не была typed nil: возвращайте nil явно, когда успех означает отсутствие ошибки.

Не вводите интерфейс заранее «на будущее». Признак полезной границы: две реальные реализации, изоляция нестабильного ресурса или более простой тест контракта. Признак лишней абстракции: единственная реализация, интерфейс с десятком методов, универсальный фабричный слой и тест, который проверяет только вызов мока. Сначала напишите конкретный код, затем извлеките минимальное требование, если оно появилось.

В этом уроке цель — не запомнить синтаксис, а предсказать значения интерфейса. Нарисуйте пару «динамический тип / динамическое значение» для nil-указателя и обычного указателя. Затем проследите передачу io.Reader: вызывающий код знает только Read, реализация знает, откуда берутся байты. Такой рисунок помогает отделить контракт от реализации.

Проверяйте поведение на пустом имени, пробелах, кириллице и управляющих пробелах. Правило validateName ниже намеренно ограничено: после strings.TrimSpace строка должна содержать хотя бы одну букву или цифру; внутренние пробелы разрешены. В production решение о Unicode-нормализации и допустимых символах должно следовать продуктовым требованиям; простая проверка не является универсальной политикой имени.

Три упражнения отличаются предметом навыка: реализовать маленький контракт поведения, определить валидность строки по правилам, затем прочитать весь вход через интерфейс и обработать ошибки. Не оценивается архитектурная красота автоматической системой; критерии функциональны. Отдельно объясните, почему интерфейс выбран на границе чтения и почему не нужен интерфейс для обычной строки.

Для отладки сначала проверьте compile error: набор методов, pointer/value receiver, импорт, написание имени. Если компилируется, но проверка nil ведёт себя неожиданно, выведите или исследуйте отдельно динамический тип и nil-значение в локальном тесте, не маскируя проблему форматированием. Для строки напечатайте длину до и после TrimSpace. Для потока проверьте число байтов и ошибку на EOF.

Не используйте reflect, unsafe, runtime или внешние пакеты ради этой главы. Все примеры работают со стандартной библиотекой. В реальной системе поведение конкретного reader может зависеть от источника, но публичный контракт функции не должен требовать, чтобы студент создавал файл на компьютере или делал сетевой запрос.

### Полная программа: поведение интерфейса

Сохраните пример как `main.go`. `io.Reader` и `strings.NewReader` показывают границу зависимости без файла на диске.

```go
package main

import ("fmt"; "io"; "strings")

func firstLine(r io.Reader) (string, error) {
    var b [64]byte
    n, err := r.Read(b[:])
    if err != nil && err != io.EOF { return "", err }
    return strings.TrimSpace(string(b[:n])), nil
}
func main() {
    line, err := firstLine(strings.NewReader("  Go\n"))
    if err != nil { fmt.Println("error:", err); return }
    fmt.Println(line)
}
```

Вывод: `Go`. Размер буфера ограничен намеренно для короткого примера; производственная построчная обработка требует явно заданного лимита и политики больших строк.

### Проверки и критерии

Функциональный автогрейдер проверяет только опубликованную сигнатуру и входы/выходы. Он не доказывает хорошую декомпозицию, корректную семантику всех сторонних reader или качество комментариев. Проверьте вручную: когда interface равен nil; может ли метод указателя быть вызван через значение; кому принадлежит закрытие ресурса; сохраняет ли %w цепочку ошибки. Для реальной практики написания Go-тестов откройте P1 workspace-проект и запустите `go test ./...`; эта задача не утверждает, что студентские тесты доказаны проверкой данной функции.

### Частые ошибки и помощь без ИИ

`cannot use x as io.Reader` означает, что набор методов не соответствует контракту: сверьте имя, параметры, receiver и возвращаемые значения. Если nil-проверка неожиданна, проверьте typed nil. Если компилятор пишет `declared and not used`, удалите лишнюю переменную или примените её. Если тест падает только на пробелах, сопоставьте контракт TrimSpace с тем, что вы удаляете вручную. Запишите минимальный вход, на котором поведение отличается, и сначала добавьте его как тест.

AI Tutor необязателен. До подсказки сформулируйте ожидаемое поведение и один минимальный контрпример. Не вставляйте секреты или личные данные. При использовании объяснения сверяйте каждый совет с контрактом, компилятором и тестами; готовый ответ без собственной проверки не является доказательством понимания.

### Итог и словарь

После главы вы должны читать маленький интерфейс, сопоставлять его с методами типа, объяснять typed nil, выбирать композицию и проверять контракт с in-memory источником. Если можете лишь повторить термин, вернитесь к примеру и измените тип reader, сохранив поведение функции.

**Мини-глоссарий:** interface — интерфейс, контракт методов; implementation — реализация, тип с требуемыми методами; composition — композиция, сборка поведения из частей; dependency — зависимость, значение или поведение, необходимое коду; typed nil — типизированный nil, интерфейс с типом и nil-значением; io.Reader — контракт чтения байтов; fake — тестовая реализация поведения.

## Уточнение контракта: что именно обещает интерфейс

Методная сигнатура показывает лишь механическую форму вызова. Документация должна дополнять её смыслом. Для Reader нулевой байт не является окончанием: окончание сообщается ошибкой io.EOF. Получатель может получить одновременно число байтов больше нуля и ошибку. Поэтому корректный код сначала обрабатывает n байтов, а затем решает, является ли err допустимым завершением. Если вместо чтения вызывается только проверка `r != nil`, она отвечает лишь на вопрос о наличии значения, а не о возможности успешного чтения. Такое ограничение намеренно демонстрирует, что контракт можно проверить поверхностно; при проектировании собственного API сформулируйте полезную семантику.

У интерфейсов есть практическая цена: вызывающая сторона зависит от абстракции, зато реализация должна удовлетворять контракту, а диагностика может стать менее прямой. Когда внутри функции один конкретный тип и никаких тестовых или ресурсных границ нет, интерфейс затрудняет чтение без пользы. Когда функция читает, пишет, считает время или отправляет запрос, граница может сделать поведение заменяемым. Не создавайте отдельную структуру-адаптер, если стандартный тип уже реализует нужный интерфейс.

Указатель и значение отличаются не только тем, что один можно сделать nil. Receiver по значению получает копию структуры, а pointer receiver может менять исходное значение. Методный набор значения включает методы с receiver T; методный набор *T включает методы с receiver T и *T. Поэтому `var _ io.Reader = file` может не компилироваться, а `var _ io.Reader = &file` — компилироваться. Выбор receiver обсуждался раньше; здесь важно проверить, какое именно значение передаётся через интерфейс.

Для typed nil не существует одного универсального исправления. Можно изменить функцию так, чтобы она проверяла указатель до возврата интерфейса. Можно определить метод, который безопасен на nil receiver, если это естественная семантика типа. Можно выбрать конкретный результат или отдельный флаг вместо интерфейса. Проверка reflect здесь запрещена и не нужна: правильная форма API устраняет неоднозначность раньше.

### Дополнительная самостоятельная практика

Создайте интерфейс из одного метода только после того, как напишете потребителя. Попросите его принять два разных стандартных значения, например strings.Reader и bytes.Buffer, если выбранный контракт им подходит. Затем удалите один метод из интерфейса и посмотрите, какие вызовы всё ещё нужны. Это упражнение показывает принцип «минимального контракта» на реальном коде. Добавлять фиктивную вторую реализацию ради галочки не нужно.

Сформулируйте три свойства интерфейса словами: какие вызовы разрешены, какое значение означает успех и кто управляет временем жизни связанного ресурса. Если на вопрос о закрытии ответа нет, интерфейс или комментарий неполон. Если контракт обещает повторный вызов, проверьте, сохраняет ли состояние реализация. Если такого обещания нет, не выводите его только из названия метода.

Проверьте задачу вручную с nil-интерфейсом и интерфейсом, содержащим nil-указатель. Затем отдельно проверьте объект, который имеет методы с value receiver, и объект, который имеет только pointer receiver. Запишите результаты рядом с типом и значением. Эти четыре случая помогают обнаружить ошибку ещё до отладки сложной архитектуры.

### Пример: распознать типизированный nil

Этот пример специально печатает две проверки и показывает ловушку. Никакой метод не вызывается, поэтому паники нет.

```go
package main

import "fmt"

type Speaker interface { Speak() string }
type Person struct{}
func (*Person) Speak() string { return "hello" }
func main() {
    var p *Person
    var s Speaker = p
    fmt.Println(p == nil)
    fmt.Println(s == nil)
}
```

Вывод: `true`, затем `false`. Здесь интерфейс содержит тип `*Person`, хотя значение указателя nil.

### Пример: композиция из маленьких частей

```go
package main

import "fmt"

type Label struct { Text string }
type Notice struct { Label Label }
func (l Label) String() string { return l.Text }
func (n Notice) Render() string { return "[" + n.Label.String() + "]" }
func main() { fmt.Println((Notice{Label: Label{Text: "готово"}}).Render()) }
```

Вывод: `[готово]`. Notice содержит Label и делегирует форматирование; это композиция, не наследование.
