# Health, readiness и структурные логи

## Что ты сделаешь

Ты напишешь три части наблюдаемости: статус пробы процесса, правило разрешённых полей журнала и классификатор публичной ошибки, который не выдаёт внутренние детали. Все функции работают с переданными значениями, а сами пробы и журналы они не запускают.

## Liveness и readiness

Проба живости (liveness) отвечает на вопрос, жив ли процесс. Если она не отвечает, оркестратор перезапускает контейнер. Проба готовности (readiness) отвечает на другой вопрос: может ли процесс принять запрос прямо сейчас. Если она не проходит, балансировщик временно перестаёт слать трафик, но процесс не перезапускают.

Путать эти пробы опасно, и ошибка здесь дорогая: она превращает локальный сбой в перезапуск всего сервиса. Если сделать readiness слишком строгой и проверять базу, временный сбой базы перезапустит все экземпляры сразу. Если сделать liveness зависимой от внешних сервисов, сервис будет перезапускаться из-за чужой проблемы.

> **Важно.** Liveness должна проверять только состояние самого процесса. Готовность учитывает зависимости, но её отказ не означает, что процесс надо перезапустить.

## Статус пробы

Процесс сначала запускается, затем подключает зависимости. Поэтому статус пробы имеет три состояния: процесс ещё стартует, процесс запущен, но зависимости не готовы, и процесс готов. Порядок проверок важен: пока процесс не запущен, говорить о зависимостях бессмысленно.

Пример показывает такой порядок. Если процесс не стартовал, ответ `starting` важнее любого состояния зависимостей:

```go
package main

import "fmt"

func probe(started, depsReady bool) string {
    if !started {
        return "starting"
    }
    if !depsReady {
        return "not_ready"
    }
    return "ready"
}

func main() {
    fmt.Println(probe(false, false), probe(true, false), probe(true, true))
}
```

Вывод: `starting not_ready ready`. Одинаковое состояние зависимостей даёт разный ответ в зависимости от того, стартовал ли процесс.

## Структурный журнал

Структурный журнал пишет события как набор полей: ключ и значение. Это удобно для поиска, но опасно для приватности: строка JSON с паролем всё равно раскрывает пароль. Поэтому журнал должен писать только разрешённые поля. Запрещённое поле не попадает в запись, даже если его добавили в код случайно.

Список разрешённых полей задаёт явно: идентификатор запроса, маршрут, статус и длительность. Всё остальное по умолчанию запрещено. Такой подход надёжнее чёрного списка: новый секрет не попадёт в журнал, пока его никто не разрешит.

Пример показывает журнал с фильтром по ключам. Заголовок авторизации и тело запроса отбрасываются, а разрешённые поля сохраняются:

```go
package main

import (
    "encoding/json"
    "fmt"
)

func main() {
    allowed := map[string]bool{"request_id": true, "route": true, "status": true, "duration_ms": true}
    event := map[string]any{"route": "/tasks", "status": 200, "authorization": "Bearer x", "duration_ms": 12}
    out := map[string]any{}
    for k, v := range event {
        if allowed[k] {
            out[k] = v
        }
    }
    b, _ := json.Marshal(out)
    fmt.Println(string(b))
}
```

Вывод: `{"duration_ms":12,"route":"/tasks","status":200}`. Поле `authorization` не попало в журнал, потому что его нет в списке разрешённых. Ключи сериализуются в алфавитном порядке, поэтому вывод детерминирован.

## Точность ключей

Сравнение ключей точное и чувствительное к регистру. Ключ `Route` не равен `route`, а пустой ключ запрещён. Это кажется строгим, но иначе в журнале появятся два поля с одним смыслом, и поиск по одному из них пропустит записи.

Нельзя считать разрешённым поле, которое похоже на разрешённое. `duration` — не то же самое, что `duration_ms`. Опечатка в ключе должна давать отказ, а не тихо проходить.

## Публичная ошибка

Клиент получает ответ об ошибке, и этот ответ не должен содержать внутренних деталей: текста исключения, имени таблицы, стека. Внутренняя причина остаётся в журнале сервера. Клиенту отдаётся обобщённая категория. Ошибки клиента, то есть статусы 4xx, можно описать безопасно, потому что они не раскрывают устройство сервиса. Ошибки сервера, наоборот, почти всегда содержат внутренние детали, и их нужно обобщать.

Классификатор решает три вещи: статус ошибки вообще допустим, есть ли внутренние детали, и какую категорию получит клиент. Статус вне диапазона ошибок — ошибка классификатора, а не ответ клиенту.

## Частота проб и пороги

Оркестратор опрашивает пробы регулярно. Частота и число подряд идущих отказов решают, когда начинается перезапуск или исключение из балансировки. Слишком частая проба нагружает сервис, а слишком редкая замедляет реакцию на реальный отказ. Пороги подбирают вместе: один неудачный ответ не должен перезапускать процесс, но и десять минут молчания тоже недопустимы.

Для readiness это особенно важно, потому что ответ пробы влияет на весь трафик сервиса: короткий всплеск задержек базы не должен выводить все экземпляры из балансировки одновременно. Поэтому readiness обычно допускает несколько подряд неудачных проб, прежде чем убрать экземпляр, а liveness настраивают так, чтобы перезапуск означал действительно зависший процесс.

## Что проверяет проба

Проба не проверяет бизнес-логику и не выполняет полный запрос. Она отвечает на узкий вопрос: может ли процесс сейчас ответить. Поэтому тяжёлые проверки внутри пробы опасны: проба сама начинает нагружать систему, которую должна измерять. Для более глубокой диагностики есть отдельные метрики и синтетические сценарии.

Тест пробы тоже узкий. Он запускает обработчик пробы с заранее заданным состоянием процесса и зависимостей и сравнивает ответ с ожидаемым. Такой тест быстрый, и его можно запускать при каждом изменении кода, в отличие от полного сценария с базой. Он проверяет, что статус соответствует состоянию процесса и зависимостей, и что отказ зависимости не меняет liveness. Полный путь запроса проверяется интеграционным тестом.

## Модель и механизм

Для наблюдаемости полезны три вопроса. Что означает каждая проба для оркестратора? Какие поля разрешены в журнале и кто их разрешает? Что видит клиент, а что остаётся внутри? Ответы записываются как контракт до добавления новых полей.

Синхронизация здесь не нужна: все функции главы чистые. Поэтому их тесты быстрые и детерминированные, и их удобно запускать при каждом изменении кода журнала. Цена подхода — список разрешённых полей требует сопровождения. Его стоит хранить в одном месте, а не разбрасывать по коду логирования.

## Типичные ошибки и исправление

Первая ошибка — проверять базу в liveness. Исправление — liveness только про процесс, зависимости относятся к readiness.

Вторая — писать тело запроса в журнал «для отладки». Исправление — тело не пишется, а для отладки пишется его размер и категория ошибки.

Третья — чёрный список полей. Исправление — белый список: новое поле запрещено, пока его не разрешили.

Четвёртая — возвращать клиенту текст исключения. Исправление — обобщённая категория, а детали остаются во внутреннем журнале.

> **Типичная ошибка.** Добавить в журнал заголовок авторизации, чтобы «проверить токен». Тогда токен попадает в систему логирования и живёт там дольше самого токена.

## Если что-то пошло не так

- Контейнеры перезапускаются, когда недоступна база → зависимость проверяется в liveness; оставь в ней только состояние процесса.
- В журнале появился пароль → поле не в белом списке; проверь, как оно туда попало.
- Клиент видит текст исключения → классификатор не отделяет внутреннюю причину от публичной категории.
- Поиск по журналу пропускает записи → ключи написаны с разным регистром; используй один вариант.

## Практика

Эти задания проверяют правила пробы, журнала и ошибок по переданным значениям. Функции не выполняют HTTP-запросы и не пишут журналы. Закрытые примеры видны только в «Проверить».

### Задание 1 · Easy: health, readiness и структурные логи — базовое правило

**Цель.** Реализуй `ProbeStatus(started, dependenciesReady bool) string`. Если процесс не стартовал, верни `"starting"`. Если стартовал, но зависимости не готовы, верни `"not_ready"`. Иначе верни `"ready"`.

**Ожидаемый вывод** — входы: процесс стартовал, зависимости готовы:

```text

```

**Шаги.**
1. Выбери задание «Easy: health, readiness и структурные логи — базовое правило»: в файле есть `ProbeStatus` с `panic("TODO")`. Импорты не нужны.
2. Если `started` ложно, верни `"starting"`.

4. Иначе верни `"ready"`.

## Воспроизводимая лабораторная: журнал без секретов

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Сеть и внешний агрегатор журналов не нужны: запись формируется в памяти и выводится в стандартный поток.

Программа ниже формирует событие с полями запроса и секретом, оставляет только разрешённые поля и печатает результат. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import (
    "encoding/json"
    "fmt"
    "strings"
)

func main() {
    allowed := map[string]bool{"request_id": true, "route": true, "status": true, "duration_ms": true}
    event := map[string]any{
        "request_id":    "r-17",
        "route":         "/tasks/{id}",
        "status":        404,
        "duration_ms":   9,
        "authorization": "Bearer secret-token",
        "request_body":  strings.Repeat("x", 5),
    }
    out := map[string]any{}
    for k, v := range event {
        if allowed[k] {
            out[k] = v
        }
    }
    b, _ := json.Marshal(out)
    fmt.Println(string(b))
    fmt.Println("secret leaked:", strings.Contains(string(b), "secret-token"))
}
```

**Ожидайте:** первая строка `{"duration_ms":9,"request_id":"r-17","route":"/tasks/{id}","status":404}`, вторая `secret leaked: false`. Секрет и тело запроса в журнал не попали, а ключи идут в алфавитном порядке.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

- Чем liveness отличается от readiness?
- Почему отсутствие ошибки в readiness-пробе не равно живости?

- Почему список разрешённых полей надёжнее списка запрещённых?
- Почему клиенту нельзя возвращать внутреннюю причину ошибки?

## Итог

- Liveness проверяет процесс и ведёт к перезапуску; readiness учитывает зависимости и ведёт к исключению из балансировки.
- Журнал пишет только поля из белого списка; секреты и тело запроса в него не попадают. Записи журнала должны быть одинаковыми по форме: тогда поиск и агрегация работают без особых случаев для каждого маршрута.
- Клиент получает обобщённую категорию ошибки, а внутренняя причина остаётся в журнале сервера. Так клиент получает понятный ответ, а эксплуатация видит полную причину.
