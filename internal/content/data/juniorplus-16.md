# Authorization, роли и ownership

## После входа сервер всё ещё должен принимать решение

Authorization (авторизация) отвечает, разрешено ли конкретному principal выполнить action над resource. Principal — субъект запроса, извлечённый из проверенной сервером session. Resource — запись или коллекция, к которой обратились. Action — операция `read`, `update`, `delete`, `create` или другая явно описанная. Authorization decision — ответ сервера по собственной политике.

Проверенная cookie доказывает, что сервер нашёл действующую сессию для principal. Она сама не означает доступ ко всем данным. Если User A запрашивает `GET /links/record-of-B`, сервер обязан проверить ownership или роль, даже когда token корректный. Клиентские `user_id`, `owner_id`, `role`, `is_admin` и `permissions` в JSON или query не являются источником полномочий.

Role (роль) группирует набор действий: например `user` работает со своими ссылками, `admin` — с ограниченным административным набором. Role должна храниться/назначаться в доверенном серверном состоянии. Дайте доступ deny by default (запрет по умолчанию): если principal, роль, ресурс, действие или правило не распознано, результат deny. Не начинайте с «разрешить, кроме нескольких плохих случаев».

## Object-level check и ownership в SQL

Проверка `owner_id` относится к конкретному объекту. Проверка только роли (`role == "user"`) не отвечает, принадлежит ли запись текущему пользователю. Ownership (владение) — серверная связь principal→resource, полученная из доверенного storage.

В PostgreSQL запрос на чтение/изменение должен включать владельца:

```sql
SELECT id, slug, target_url FROM links WHERE id = $1 AND owner_id = $2;
UPDATE links SET target_url = $1 WHERE id = $2 AND owner_id = $3;
DELETE FROM links WHERE id = $1 AND owner_id = $2;
```

Значения `$1...$n` — bind parameters, а не текстовая конкатенация. Если UPDATE/Delete затронул ноль строк, сервер не обнаружил доступный объект. В зависимости от политики можно одинаково отвечать `404` и на неизвестный ID, и на чужой объект, чтобы не раскрывать существование приватной записи. Выберите поведение один раз и тестируйте его на всех методах.

Отдельный insecure lookup (`SELECT owner_id WHERE id = ?`), затем update только по id создаёт race и окно между проверкой и изменением. Более узкий запрос объединяет условие ownership с действием в одной операции. Для сложной политики используйте транзакцию и соответствующее блокирование/изоляцию, но не полагайтесь на client pre-check.

Least privilege (минимальные полномочия) означает давать субъекту лишь необходимые действия, объекты и область. Админ не должен быть обходом всех правил без аудитируемой причины. Новая роль или action пока не описаны — откажите. Не смешивайте role и owner: роль говорит о классе субъекта, owner связывает его с конкретным ресурсом.

## IDOR и проверка на повторяемых запросах

IDOR (Insecure Direct Object Reference, небезопасный прямой идентификатор объекта) возникает, когда клиент получает/подбирает ID другого объекта, а сервер проверяет только факт существования записи. Случайный UUID может затруднить угадывание, но не является authorization. Публичный slug также не должен выдавать секретную приватную страницу.

Проверяйте матрицу из разных участников, объектов и методов. Создайте записи User A и User B, затем от имени A проверьте чтение, изменение и удаление ID владельца B. Сверьте response и состояние после запроса. Проверка только `403` недостаточна: endpoint мог уже изменить запись, а затем отказать. Проверяйте side effect.

AuthZ проверки проводятся после получения principal из authentication слоя, но перед чтением/изменением ресурса согласно policy. Для приватной коллекции фильтруйте `owner_id` в list запросе; object permission на каждый элемент после общего списка уже слишком поздно, если данные попали в память и лог.

## Пример 1. Простое решение владельца

Файл `main.go`; policy имеет три независимых входа, и unknown action по умолчанию запрещён.

```go group=owner-policy mode=run
package main

import "fmt"

func OwnsResource(principalID, ownerID int64) bool {
	return principalID > 0 && ownerID > 0 && principalID == ownerID
}

func main() {
	fmt.Println(OwnsResource(7,7), OwnsResource(7,9), OwnsResource(0,0))
}
```

Вывод `true false false` не подтверждает identity. Он предполагает, что principalID уже пришёл из проверенной сессии; request body не должен напрямую вызывать эту функцию с обоими клиентскими IDs.

## Пример 2. Handler использует серверный principal

Значение principal помещено в request context доверенной auth middleware. Handler не читает `owner_id` из query или JSON.

```go group=principal-handler mode=run
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
)

type principalKey struct{}
func withPrincipal(r *http.Request,id int64)*http.Request{return r.WithContext(context.WithValue(r.Context(),principalKey{},id))}
func principalID(r *http.Request)(int64,bool){v,ok:=r.Context().Value(principalKey{}).(int64);return v,ok&&v>0}

func linkHandler(w http.ResponseWriter,r *http.Request){
	user,ok:=principalID(r);if !ok{http.Error(w,"unauthenticated",401);return}
	owner:=int64(7) // result of an owner-scoped repository fixture
	if !OwnsResource(user,owner){http.NotFound(w,r);return}
	fmt.Fprint(w,"link visible")
}
func OwnsResource(user,owner int64)bool{return user>0&&user==owner}

func main(){
	request:=withPrincipal(httptest.NewRequest("GET","/links/123?owner_id=99",nil),7)
	w:=httptest.NewRecorder();linkHandler(w,request)
	fmt.Println(w.Code,w.Body.String())
}
```

Query `owner_id=99` не повлиял на principal или owner fixture. В production owner берётся из repository с server-side user ID. Если middleware не установило principal, запрос отклоняется.

## Пример 3. Проверка ownership прямо в запросе

SQL выбирает объект и владельца одним атомарным условием; параметр principal обязан поступить из проверенной сессии.

```go group=owned-query mode=run
package main

import (
	"fmt"
	"strings"
)

const readOwnedLink = "SELECT id, slug, target_url FROM links WHERE id = $1 AND owner_id = $2"

func main(){
	fmt.Println(strings.Contains(readOwnedLink,"owner_id = $2"),strings.Contains(readOwnedLink,"$1"))
}
```

Вывод подтверждает лишь, что строка fixture содержит две ожидаемые части. Он не проверяет синтаксис PostgreSQL, применение параметров драйвером, index, транзакцию или результат реального ownership test. Эти свойства требуют PostgreSQL integration suite. Ключевой принцип — никакой SQL fragment не конкатенируется с ID или role клиента.

## Роль против права на объект

Представьте простую матрицу. Пользователь может читать, обновлять и удалять собственную ссылку. Admin может читать/изменять предусмотренную административную область, а неизвестные административные действия всё равно закрыты. Публичный redirect к включённому slug — отдельный анонимный `read` use case, не доступ к CRUD детали. Прописывайте исключения отдельно.

### Область роли и непрямые объекты

Role не должна выбираться параметром API. Если клиент прислал `role=admin`, это лишь непроверенное значение. Приложение берёт роль из доверенной серверной записи, связанной с principal; изменение роли требует отдельного узко защищённого use case и аудита. Старая cookie не должна бесконечно хранить устаревшее полномочие после revoke или смены роли.

Непрямая связь тоже несёт ownership. Пользователь может попытаться прикрепить принадлежащий другому владельцу tag к своей ссылке, добавить collaborator к чужому project или сообщить ID другого tenant. Проверка нужна для каждого объекта, затронутого одной командой, а не только основной ссылки. Если команда меняет несколько таблиц, выполняйте ownership checks и запись в одной транзакции, чтобы отказ не оставил частичный side effect.

List/search часто становится незаметным путём утечки: endpoint корректно проверяет единичный объект, но возвращает всю коллекцию. Добавьте owner predicate в запрос до pagination и count; иначе количество чужих объектов может раскрыться даже при скрытых строках. Тестируйте страницу с записями двух пользователей, проверьте, что участник видит только свои строки и их количество.

Права во времени тоже меняются. Если роль отозвана, cookie principal всё ещё может быть аутентифицирован, но authorization слой должен читать актуальную роль или ограниченно кэшировать grants. Для учебного P2 role/ownership можно проверять на каждом запросе по текущему серверному состоянию; начинайте с правильной простой модели до оптимизации.

Не полагайтесь на скрытие кнопки UI или route в JavaScript. Любое решение интерфейса лишь улучшает опыт. Backend должен применить одинаковую проверку для browser, curl и любого другого клиента. Не возвращайте объект, а затем не проверяйте на frontend, стоит ли показать его.

Логи authorization должны показывать корреляционный ID, безопасную категорию решения и route label; не печатайте сессию, пароль или полный приватный body. Если ответ унифицирован как `404`, внутренняя audit запись может хранить reason code с правильной защитой и retention. Не называйте и не журналируйте попытку как доказанное злонамеренное поведение: перепутанный ID тоже возможен.

## Типичные ошибки и диагностика

- **Доверять owner ID, присланному клиентом.** Получайте principal из server-side session и фильтруйте repository запрос.
- **Проверить владельца только на GET.** Повторите тест для PATCH, DELETE, association и list.
- **Считать случайный UUID authorization.** ID obscurity не заменяет policy.
- **Сделать role check вместо object check.** Роль `user` не отвечает, кому принадлежит выбранный id.
- **Выполнить mutation до отказа.** Проверяйте состояние после запрещённого запроса.
- **Забыть список.** `SELECT * FROM links` для всех, затем фильтр в handler уже мог отправить данные в лог и память.
- **Разрешить неизвестную роль или действие.** Новые строковые enum значения должны приводить к deny.
- **Сделать ownership lookup отдельно от update.** Между шагами может произойти изменение состояния; включайте owner в write predicate.
- **Отдать разные подробные ответы.** Ясный `403` иногда полезен, но при идентификаторах приватных объектов выберите единообразную not-found policy.

Для отладки заведите два principals и два ресурса, затем меняйте только выбранный object ID. Убедитесь, что A видит A, не видит B и не меняет B; после каждого запроса прочитайте обе записи через test store. Повторите ровно тот же случай с admin policy и сравните ожидаемое право.

Когда внешняя ошибка унифицирована в `404`, проверьте её вместе с отдельной защищённой диагностикой. Корреляционный ID связывает отказ с запросом, но не должен содержать principal ID, session hash или секрет. В тесте сравнивайте публичное поведение и безопасное audit событие; внутренний reason code не выдавайте в response body.

## Практика

- **Easy:** запретите mutation без аутентифицированного principal. Безопасный публичный read остаётся отдельной явно разрешённой операцией.
- **Medium:** для CRUD разрешайте user действовать только со своей записью; подставьте два разных owner ID и проверьте read/update/delete результат.
- **Hard:** постройте deny-by-default decision по `authenticated principal, role, action, owner`; разрешите только перечисленные user/admin actions. Добавьте cross-user IDOR tests для list, read, update и delete, включая доказательство отсутствия side effect.

## Мини-глоссарий

- **authorization (авторизация)** — проверка разрешённости действия.
- **principal (субъект)** — проверенная личность или service account запроса.
- **resource (ресурс)** — объект, доступ к которому проверяется.
- **role (роль)** — группа разрешений для категории субъекта.
- **ownership (владение)** — связь субъекта с конкретным объектом.
- **least privilege** — предоставление только необходимых прав и области.
- **IDOR** — доступ к чужому объекту через прямой, недостаточно проверенный ID.
- **deny by default** — неизвестное или неразрешённое условие ведёт к отказу.
