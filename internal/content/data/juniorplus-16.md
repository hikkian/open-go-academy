# Authorization, роли и ownership

## Что ты сделаешь

Ты напишешь три решения доступа: `CanMutate` разрешит изменение только аутентифицированному пользователю, `OwnsResource` проверит, что ресурс принадлежит тому, кто его запрашивает, `Authorize` выберет результат по роли, действию и владельцу с отказом по умолчанию. Функции получают уже проверенные данные и не читают их из тела запроса.

## Аутентификация отвечает «кто», авторизация — «что можно»

После входа сервер знает, кто пользователь (principal). Но это не значит, что ему разрешено всё. Авторизация решает, можно ли выполнить конкретное действие с конкретным ресурсом. Поэтому проверка делается для каждого действия, а не один раз при входе.

Принцип отказа по умолчанию: всё, что явно не разрешено, запрещено. Неизвестная роль, неизвестное действие или неизвестный идентификатор дают отказ.

## Владелец и object-level проверка

Ресурс принадлежит владельцу (`owner`). Проверка «есть ли у пользователя доступ к ресурсу» требует сравнить идентификатор пользователя с владельцем ресурса, причём владелец берётся из хранилища, а не из запроса. Иначе клиент подставит чужой идентификатор в тело и получит чужие данные.

Сравнение идентификаторов числами или строками показывает, почему нужна точность:

```go
package main

import "fmt"

func main() {
    principal := int64(7)
    owner := int64(7)
    fmt.Println(principal == owner, principal > 0)
}
```

Вывод: `true true`. Равенство и положительность — два отдельных условия.

> **Важно.** Идентификатор `0` и отрицательные значения не принадлежат никому. Проверка владельца без проверки положительности пропустит пустой или испорченный идентификатор.

## Ownership в запросе, а не только в коде

Проверка на стороне приложения нужна, но её недостаточно: запрос к базе тоже должен ограничивать строки владельцем. Иначе между проверкой и выполнением может появиться гонка, и поиск по идентификатору вернёт чужую запись. Условие владельца записывают в `WHERE` вместе с идентификатором ресурса:

```go
package main

import "fmt"

func main() {
    const query = "SELECT id FROM links WHERE id = $1 AND owner_id = $2"
    fmt.Println(query)
}
```

Вывод: запрос с двумя условиями. Две переменные передаются параметрами, поэтому чужой идентификатор не найдёт строку.

> **Типичная ошибка.** Проверить владельца в коде после выборки по одному `id`. Строка уже прочитана, и лишние данные могли попасть в журнал или ответ.

## IDOR: повторяемый идентификатор

Insecure Direct Object Reference (IDOR) — уязвимость, когда сервер отдаёт ресурс по идентификатору без проверки владельца. Злоумышленник просто меняет число в адресе. Защита одна: на каждом обращении проверяется владелец, а не только то, что пользователь вошёл.

## Если что-то пошло не так

- Чужой ресурс отдан → проверка владельца отсутствует для действия или проверяется идентификатор из тела.
- Роль пришла в теле запроса → роль берётся из серверной сессии.
- Неизвестное действие разрешено → отказ по умолчанию должен стоять последним.
- `undefined: int64` → тип проверяется в описании функции; используй `int64` явно.

### Задание 1 · Запрети mutation без principal

**Цель.** Вернуть `true` только для аутентифицированного пользователя. Публичное чтение сюда не относится.

**Ожидаемый вывод** — входы: аутентифицированный пользователь, затем анонимный:

```text
true
false
```

**Шаги.**
1. Выбери задание «Запрети mutation без principal»: в файле есть `CanMutate` с `panic("TODO")`.
2. Верни значение флага `authenticated`.
3. Нажми «Запустить» и сравни с блоком выше.
4. Нажми «Проверить».

**Как проверить себя.** `true` и `false`; все три критерия зелёные.

**Если не принято.**
- Анонимный пользователь получает `true` → функция должна возвращать `authenticated`, а не константу.
- Аутентифицированный получает `false` → проверка инвертирована.

> **Подсказка.** Одна строка: возврат того же флага, который передан.

**Цель.** Вернуть `true`, только если идентификаторы положительные и равны. Иначе `false`.

3. Проверь, что `principalID` равен `ownerID`.
4. Верни `true`, если оба условия выполнены, иначе `false`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** `true` и `false`; все три критерия зелёные.

**Если не принято.**

> **Подсказка.** Два условия через `&&`: положительность и равенство.

### Задание 3 · Прими deny-by-default решение

**Цель.** Неаутентифицированный — `unauthenticated`. Идентификаторы должны быть положительными, иначе `forbidden`. Пользователь может `read`, `update` и `delete` только своё. Администратор — те же действия с любым владельцем. Неизвестная роль, действие или отсутствие права — `forbidden`.

**Ожидаемый вывод** — входы: пользователь читает свою запись, затем администратор удаляет запись чужого владельца:

```text
"allow"
"allow"
```

**Шаги.**
1. Выбери задание «Прими deny-by-default решение»: в файле есть `Authorize` с `panic("TODO")`. Импорты не нужны.
2. Если `authenticated` ложно, верни `unauthenticated`.
3. Если `principalID` или `ownerID` не положительные, верни `forbidden`.
4. Если действие не одно из `read`, `update`, `delete`, верни `forbidden`.
5. Для роли `user` разреши только при равных идентификаторах; иначе `forbidden`.
6. Для роли `admin` разреши любого владельца; для остальных ролей — `forbidden`.
7. Нажми «Запустить» и сравни с блоком выше.
8. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках: `"allow"` и `"allow"`; все три критерия зелёные.

**Если не принято.**
- Пользователь получает `allow` для чужого ресурса → для роли `user` сравнивай владельца.
- Роль `guest` даёт `allow` → неизвестная роль отказывает.
- Администратор с нулевым `principalID` получает `allow` → положительность проверяется для всех ролей.

> **Подсказка.** Отказ по умолчанию: сначала все случаи, которые запрещены, а разрешения — последними.
