## Файлы, JSON и интерфейсы ввода-вывода

Поток ввода-вывода (I/O stream) позволяет читать или записывать последовательность байтов. Интерфейс io.Reader описывает Read([]byte), а io.Writer — Write([]byte). Функция, принимающая Reader, не обязана знать, пришли ли байты из файла, памяти или сети. Это облегчает тестирование и разделяет обработку данных от выбора источника.

Чтение файла — работа с внешним ресурсом: файл может отсутствовать, быть недоступным, пустым или измениться во время чтения. Проверяйте ошибку открытия и чтения. Если вы открыли файл, закройте его через defer Close сразу после успешной проверки ошибки. В функции, получившей готовый Reader, обычно закрывает ресурс тот, кто его создал; контракт должен это сказать.

JSON — текстовый формат обмена структурированными данными. `json.Decoder` читает поток, `json.Encoder` пишет одно JSON-значение на строку. Теги вроде `json:"name"` задают имена полей. Синтаксически правильный JSON может нарушать предметные правила: обязательное имя пустое, число отрицательное, идентификатор дублируется. Поэтому после Decode нужен этап проверки доменного контракта.

В Go поля структуры должны быть экспортируемы, чтобы encoding/json мог записать их без пользовательских MarshalJSON методов. Для курса действует строгая граница: не добавляйте custom serialization hooks. Проверяющая система сравнивает нормализованное присутствие ошибок и их поведение, а не сериализует тексты ошибок как обычные данные.

Decoder по умолчанию может игнорировать неизвестные поля. Строгий API может вызвать DisallowUnknownFields, но это осознанная политика совместимости: новые поля тогда ломают старых клиентов. После одного документа можно убедиться, что больше нет данных, попробовав второй Decode и ожидая io.EOF. Синтаксическая корректность не означает полное потребление входа.

Пример ReadItems читает ограниченный поток полностью, декодирует список и проверяет каждую запись. Для маленького упражнения стандартный io.ReadAll приемлем, если вход ограничен драйвером; в серверном приложении обязательно ограничить размер до чтения. Нельзя бездумно читать бесконечный сетевой поток или огромный файл в память.

Валидация должна быть предсказуемой: trim пробелов, проверить непустой идентификатор и положительное количество, обнаружить повтор. Ошибка сообщает категорию и контекст, но не содержит секретов и внутренний stack trace. Частичный результат при ошибке обычно не возвращается, если контракт явно не обещает его; здесь возвращается nil и ошибка.

Тестируйте через strings.NewReader: валидный JSON, пустой массив, пустой ввод, сломанные скобки, неверный тип поля, пустое имя, отрицательное число и trailing data. Тест не должен зависеть от локальных файлов. Если задача требует файла, создайте fixture внутри t.TempDir и удаление будет автоматическим после теста.

Encode добавляет перевод строки после значения, что удобно для потокового формата. Пишите только сериализуемую проекцию, содержащую публичные поля. Ошибки — управляющие значения программы, а не произвольный текстовый формат API. Для передачи ошибок используйте стабильный код/категорию, если это требуется внешним контрактом; в этом упражнении grader проверяет функцию по возвращённым типам.

Не игнорируйте ошибку Decode или Write. Если Writer завершился досрочно, вызывающий код должен узнать о проблеме. Не закрывайте Reader, полученный параметром, если функция не владеет им. Для файла, созданного функцией, владелец закрывает его. Такие правила владения предотвращают утечки дескрипторов и неожиданные побочные эффекты.

Границы `io.Reader` допускают частичные чтения: один Read может вернуть меньше байтов, чем буфер позволяет, и это не обязательно конец. io.ReadAll продолжает чтение до EOF. При ручном цикле обрабатывайте n и err одновременно: допустимо получить n>0 вместе с ненулевой ошибкой, и данные всё равно нужно использовать. Не предполагайте, что один вызов возвращает весь документ.

Для JSON-разбора два этапа остаются разными: decode проверяет синтаксис и типовую форму; validate проверяет смысл. Например, `{"name":"", "quantity":-1}` может быть корректным JSON, но недопустимой записью. Разделение помогает выдавать точные ошибки, тестировать правила независимо и не переносить продуктовую логику в сериализатор.

### Полная программа: чтение и проверка JSON

Сохраните как `main.go`. Пример использует память, а не обязательный файл на диске.

```go
package main

import ("encoding/json"; "fmt"; "io"; "strings")

type Item struct { Name string `json:"name"`; Quantity int `json:"quantity"` }
func ReadItems(r io.Reader) ([]Item, error) {
    raw, err := io.ReadAll(r); if err != nil { return nil, err }
    var items []Item
    if err := json.Unmarshal(raw, &items); err != nil { return nil, err }
    for i := range items {
        items[i].Name = strings.TrimSpace(items[i].Name)
        if items[i].Name == "" || items[i].Quantity <= 0 { return nil, fmt.Errorf("item %d is invalid", i) }
    }
    return items, nil
}
func main() {
    items, err := ReadItems(strings.NewReader(`[{"name":" pens ","quantity":2}]`))
    if err != nil { fmt.Println("error:", err); return }
    fmt.Println(items[0].Name, items[0].Quantity)
}
```

Вывод: `pens 2`. Для production входа добавляют верхнюю границу размера и политику неизвестных полей.

### Задания, проверки и честные критерии

Easy декодирует запись и проверяет обязательное поле. Medium реализует ReadItems: пустой корректный список даёт пустой результат, повреждённый документ и невалидная запись дают ошибку. Hard проверяет round-trip валидированных записей, сохраняя доменный инвариант и контекст ошибки. Для полного проекта критерии дополнительно проверяют размер входа, закрытие ресурсов и CLI поведение, но функциональная функция сама по себе не подтверждает качество файла или README.

Ответы: отделяет источник; владелец по контракту; форма против предметных правил; да; защита памяти/ресурсов; завершает значение newline; ошибка управляет потоком и сериализация требует нормализованного публичного контракта; t.TempDir и fixture.

Если Decode падает, проверьте точную позицию и кавычки. Если декодирование прошло, но тест отказал, исследуйте предметное правило. Если данные обрезаны, проверьте частичные чтения и ошибку. Если тест зависит от текущей папки или личного файла, перенесите его на strings.Reader либо временный каталог. **Мини-глоссарий:** serialization — сериализация; JSON — текстовое представление данных; reader — интерфейс чтения; writer — интерфейс записи; validation — проверка предметных правил; resource — ресурс; fixture — тестовая заготовка; EOF — конец потока.

## Надёжная граница файлов

Путь к файлу может быть абсолютным или относительным. Относительный путь разрешается относительно текущего рабочего каталога процесса, а не обязательно каталога исходника. Поэтому программа, запускаемая из другого места, может внезапно не найти файл. CLI должен документировать базу путей или принимать путь явно. Тест создаёт fixture в `t.TempDir`, передаёт конкретный путь и не зависит от личной папки пользователя.

Операции с файловой системой могут прерваться после частичного результата. Чтение может вернуть байты и ошибку; запись — записать только часть. Функции `io.ReadAll` и `io.Copy` обрабатывают повторные чтения/записи по контракту, но всё равно возвращают ошибку. Не игнорируйте её и не объявляйте весь документ успешным только потому, что начало разобралось.

При записи важен жизненный цикл. Проверьте ошибку создания файла до defer Close. Вызов Close сам может сообщить ошибку сброса буфера, поэтому для критичного вывода её иногда нужно проверить явно. В учебной функции, принимающей io.Writer, закрытие обычно не входит в её ответственность: writer принадлежит вызывающему коду. Ясная граница владения позволяет тесту использовать bytes.Buffer без искусственного закрытия.

Ограничение размера должно применяться до неограниченного выделения памяти. Для HTTP используют ограниченный reader, для файла можно проверить размер и всё равно учитывать изменение файла между проверкой и чтением. Для маленького локального P1 зафиксируйте разумный максимум и верните понятную ошибку. Текущая функция для простоты доверяет ограниченному входу trusted driver; это не пример публичного сервера.

## JSON и совместимость схемы

Тег JSON фиксирует внешнее имя поля независимо от Go-стиля. Поля без тегов обычно сериализуются с именами Go, что часто не соответствует API-схеме. Тег `omitempty` опускает нулевые значения и может стереть важную разницу между «поле отсутствует» и «значение равно нулю». Добавляйте его только когда контракт различает эти состояния корректно.

Структурное декодирование может оставить неизвестные поля незамеченными. Приём лишних полей помогает совместимости расширяемых документов, но может скрывать опечатку. Строгий decoder отклоняет их, что упрощает CLI контракт, но усложняет эволюцию формата. Выберите и опишите политику. Тест должен проверять её явно.

Ошибка парсинга обычно содержит позицию, но её текст может меняться между версиями. Стабильный API сообщает собственный код ошибки или категорию и сохраняет исходную причину внутри программы. Не сравнивайте текст стандартной ошибки как единственный контракт. В наших упражнениях достаточно вернуть ненулевую ошибку и не выдавать частичный результат.

Числа JSON имеют ограничения представления. Декодирование произвольного числа во float64 может потерять точность больших целых. Для предметных денежных величин используйте целые minor units и подходящую типизированную структуру; если нужен произвольный JSON-тип, явно выберите UseNumber и разберите формат. Не подменяйте безопасную числовую политику случайным преобразованием.

## Политика ресурсов и повторяемые тесты

Открытый файл должен быть закрыт ровно владельцем после последнего использования. Дважды закрывать обычно безопасно не для всех ресурсов, а забытое закрытие удерживает дескриптор. На уровне функции, принимающей уже созданный Reader, не закрывайте его без договорённости. На уровне `main`, который сам открыл файл, закрытие принадлежит main/обёртке. Документируйте эту границу в API.

Для тестов чтения используйте память, когда предмет теста — JSON и правила валидации. Для проверки открытия, прав доступа и маршрута файла создавайте временный каталог и файл. Не читайте случайный домашний файл пользователя; он делает тесты неповторяемыми и может содержать приватные данные. Временный каталог очищается тестовым раннером после завершения.

Если тест работает локально, но падает в CI, ищите предположение о пути, регистре имён файлов, окончаниях строк или локали. Файловая система может быть чувствительной к регистру. Запускайте тест из корня модуля, используйте filepath.Join вместо ручной склейки разделителей и не предполагайте, что каталог проекта является текущей папкой любого вызывающего процесса.

### Пример: encode через Writer

```go
package main

import ("encoding/json"; "fmt"; "strings")

type Note struct { Text string `json:"text"` }
func main() { var out strings.Builder; err:=json.NewEncoder(&out).Encode(Note{Text:"учёба"}); if err!=nil { fmt.Println("error:",err); return }; fmt.Print(out.String()) }
```

Программа записывает JSON в память и печатает его с завершающим переводом строки. Внешний файл не требуется.

### Пример: JSON decode и отдельная валидация

```go
package main

import ("encoding/json"; "fmt"; "strings")

type Entry struct { Name string `json:"name"` }
func main() { var e Entry; err:=json.NewDecoder(strings.NewReader(`{"name":"Go"}`)).Decode(&e); if err!=nil { fmt.Println("invalid JSON"); return }; if e.Name=="" { fmt.Println("name is required"); return }; fmt.Println(e.Name) }
```

Вывод: `Go`. Decode подтвердил форму и тип, а отдельная проверка проверила обязательное поле.
