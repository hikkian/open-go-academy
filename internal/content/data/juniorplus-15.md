# Пароли, сессии и authentication

## Кто обращается к API

Authentication (аутентификация, установление личности запроса) отвечает на вопрос «какому субъекту принадлежит этот запрос?». Authorization (авторизация, разрешение действия) отвечает на вопрос «может ли этот субъект выполнить действие над этим объектом?». Правильный password проверяет первую границу. Он не выдаёт автоматически право удалить любую ссылку.

Браузерный API часто хранит server-side session. После успешного входа сервер создаёт случайный opaque token — непрозрачное случайное значение, в котором нет user ID, роли или имени. Клиент хранит token в cookie; сервер хранит только хеш токена и связанные user/expiry/revocation данные. При каждом запросе сервер хеширует полученный token, ищет запись и получает principal (проверенный субъект) из серверной сессии. Запрос не может назначить себе другой principal через JSON `user_id`.

Сессия имеет жизненный цикл: создание после успешного login; rotation после смены личности или повышения полномочий; истечение срока; logout и отзыв на сервере. Срок в cookie полезен браузеру, но сервер должен проверять `expires_at` по собственной записи. Если очистить cookie, но оставить активную строку, украденный токен продолжит работать до истечения срока.

## Хранение и защита пароля

Пароль — секрет низкой энтропии, который пользователь может повторить на других сайтах. Нельзя хранить пароль открытым текстом, шифровать так, чтобы его можно было расшифровать, добавлять его в log или возвращать из API. Вместо этого хранится результат password KDF (key derivation function, функция получения ключа из пароля) с индивидуальной случайной солью и параметрами алгоритма.

Для этого учебного P2 задан стандартный PBKDF2-HMAC-SHA-256 с **600 000 итерациями**, солью не короче 16 случайных байтов и 32-байтовым derived value. Go 1.27.2 предоставляет пакет `crypto/pbkdf2`; код не требует стороннего криптографического пакета. Сохраняйте вместе с derived bytes версию алгоритма, count итераций, длину ключа и соль, чтобы формат можно было менять и проверять. Параметр должен быть одинаковым при создании и проверке записи.

PBKDF2 затратна по CPU, но не является memory-hard: специализированный GPU может выполнять много параллельных догадок. Argon2id использует память и время и часто выбирается для новых password stores, но в этом минимальном проекте потребовал бы внешнюю зависимость и калибровку памяти. Не выдавайте 600 000 итераций за вечную гарантию безопасности, фиксированную рекомендацию для любой машины или измеренную защиту от заданного атакующего. Цена KDF влияет на latency login и DoS риск; ограничивайте длину входа до дорогой операции и ограничивайте частоту попыток.

Сравнивайте derived bytes через constant-time comparison, например `crypto/subtle.ConstantTimeCompare`. Обычное сравнение строк может закончиться при первом отличающемся байте, создавая утечку времени. Соль должна быть уникальной и случайной для каждого пользователя; соль не секретна, можно сохранить рядом с hash. Секретным остаётся пароль, и именно его нельзя писать в журнал.

## Token в cookie и CSRF

Session cookie должна включать `HttpOnly` (JavaScript не читает значение), `Secure` (браузер не отправляет cookie поверх обычного HTTP), подходящий `SameSite`, `Path=/` и отсутствие ненужного `Domain`. В эталонном P2 для HTTPS используются `Secure`, `HttpOnly` и `SameSite=Strict`. В примере ниже отдельно показан допустимый вариант `SameSite=Lax`; выбор `Strict` сильнее ограничивает cross-site отправку, но способен изменить пользовательские переходы. `SameSite` — дополнительный слой, не полная защита.

Cookie прикладывается браузером автоматически. Сайт атакующего может попытаться инициировать изменяющий запрос от имени открытой сессии. CSRF (Cross-Site Request Forgery, подделка межсайтового запроса) защищается отдельным проверяемым токеном запроса и проверкой Origin для state-changing методов. Проверка SameSite дополняет, но не заменяет токен и Origin. Не требуйте CSRF токен от безопасного read-only GET, а бизнес-операция не должна меняться при GET.

Проверяйте точный ожидаемый Origin или небольшой allowlist, назначенный конфигурацией. Нельзя считать произвольный присланный `Origin` доверенным. Для login/register/logout также продумайте CSRF и одинаковые ошибки; не раскрывайте без необходимости, существует ли email.

## Пример 1. Случайный opaque token и хеш для хранения

Ниже token живёт только в памяти процесса и не выводится. Два буфера генерируются криптографическим источником `crypto/rand`; хеширование токена не является password KDF.

```go group=opaque-session-token mode=run
package main

import (
	"crypto/rand"
	"crypto/sha256"
	"fmt"
)

func main() {
	token := make([]byte, 32)
	if _, err := rand.Read(token); err != nil { panic(err) }
	storedHash := sha256.Sum256(token)
	fmt.Println(len(token), len(storedHash))
}
```

Случайность токена не заменяет expiry, revoke, secure cookie или CSRF. Хеш допустимо хранить для lookup; в cookie находится исходное случайное значение. Не записывайте token в log ради отладки.

## Пример 2. Cookie flags и наблюдение через recorder

```go group=session-cookie mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func main() {
	h := http.HandlerFunc(func(w http.ResponseWriter,r *http.Request) {
		http.SetCookie(w,&http.Cookie{Name:"session",Value:"opaque-fixture",Path:"/",Secure:true,HttpOnly:true,SameSite:http.SameSiteLaxMode,Expires:time.Unix(1800000000,0).UTC()})
		w.WriteHeader(http.StatusNoContent)
	})
	r:=httptest.NewRecorder()
	h.ServeHTTP(r,httptest.NewRequest(http.MethodPost,"/login",nil))
	cookie:=r.Result().Cookies()[0]
	fmt.Println(cookie.Name,cookie.Secure,cookie.HttpOnly,cookie.SameSite==http.SameSiteLaxMode)
}
```

`opaque-fixture` — фиктивное значение для наблюдаемого test response, не пароль и не токен реальной сессии. Production token должен быть генерирован случайно. Установка cookie флагов не доказывает, что сервер сверил запись или отозвал её при logout.

## Пример 3. PBKDF2 с фиксированным форматом проверки

Пример работает на Go 1.27.2. Он генерирует краткоживущие случайные байты вместо литерала пароля, использует 16-байтовую salt, PBKDF2-HMAC-SHA-256, ровно 600 000 итераций и результат 32 байта. Derived value и случайная тестовая последовательность не печатаются.

```go group=pbkdf2-storage mode=run
package main

import (
	"crypto/rand"
	"crypto/pbkdf2"
	"crypto/sha256"
	"crypto/subtle"
	"fmt"
)

func main() {
	passwordBytes:=make([]byte,24)
	salt:=make([]byte,16)
	if _,err:=rand.Read(passwordBytes);err!=nil{panic(err)}
	if _,err:=rand.Read(salt);err!=nil{panic(err)}
	const iterations=600000
	const keyLength=32
	stored,err:=pbkdf2.Key(sha256.New,string(passwordBytes),salt,iterations,keyLength)
	if err!=nil{panic(err)}
	checked,err:=pbkdf2.Key(sha256.New,string(passwordBytes),salt,iterations,keyLength)
	if err!=nil{panic(err)}
	fmt.Println(len(salt),len(stored),subtle.ConstantTimeCompare(stored,checked)==1)
}
```

Вывод `16 32 true` подтверждает формат и повторную проверку внутри этого локального примера, но не безопасность настроек против любого атакующего. В API пароль приходит из request body; до PBKDF2 проверяйте body limit, длину и rate limit, не сохраняйте вход или derived hash в лог. Для login возьмите алгоритм и параметры из сохранённой версии, пересчитайте и сравните constant-time.

## Угроза фиксации и последовательность событий

Session fixation — использование атакующим заранее известного session ID, который жертва затем сохраняет после входа. После успешного login создайте новый token, запишите хеш нового, отзовите старую анонимную сессию и установите новую cookie. При изменении чувствительной роли или повторной аутентификации rotation тоже может быть нужна.

Успешный вход сам по себе должен быть атомарно отражён в серверном состоянии. Если токен выдан клиенту, а запись не сохранена, запросы не пройдут. Если запись создана, но ответ потерян, клиент не знает исход. Обработка повторного login должна создавать контролируемую новую сессию и иметь короткую границу времени, а не оставлять credential в log.

### Версия KDF и migration параметров

PBKDF2 параметры — версия формата, а не просто три числа в конфиге. При чтении учётной записи используйте алгоритм и count именно из её версии; иначе смена настройки сломает вход существующих пользователей. Новую запись можно создавать новым параметром, а после успешного login постепенно пересчитать старый derived value. Уменьшать число итераций незаметно нельзя.

600 000 HMAC-SHA-256 итераций — выбранный P2 baseline. Производительность нужно измерить на целевой машине перед открытием функции широкому трафику. Ограничьте длину password input, concurrency дорогих KDF операций и частоту login. Без этих границ attacker может заставить сервер выполнять дорогой PBKDF2 многократно. Нельзя обещать устойчивость к конкретному offline cracking budget только по числу итераций; для такого claim нужна отдельная актуальная оценка оборудования и угроз.

В базе сохраняется salt и derived output. Не сохраняйте исходный пароль даже «временно», не отправляйте его в analytics, diagnostic span, exception text или email. Reset password создаёт новый секрет и отзывает или меняет действующие сессии; старое значение не восстанавливается.

Logout должен удалять или отзывать server-side запись и одновременно очищать cookie с теми же `Path` и `Domain`, что использовались при установке. Только очистить cookie недостаточно для уже украденного копирования token. Истечение сессии должно сравниваться серверными часами; тесты вводят fake clock, чтобы не ждать реальный срок.

## Типичные ошибки и диагностика

- **Хранить пароль reversible encryption или открытым текстом.** Оставляйте только versioned KDF result, salt и параметры.
- **Использовать одну salt у всех.** Уникальная криптографически случайная соль мешает общим precomputed таблицам.
- **Сравнивать обычным `==`.** Используйте constant-time compare для derived bytes.
- **Положить session token в URL или localStorage.** URL утекает в историю/log; browser Web Storage доступен JavaScript. Для этого сценария используйте HttpOnly cookie.
- **Доверять user ID из body.** Principal извлекает server-side session middleware, а не клиентский JSON.
- **Считать SameSite полной CSRF защитой.** Проверяйте отдельный CSRF token и Origin на mutation endpoints.
- **Оставить старый session при login.** Поверните token, иначе возможна fixation.
- **Удалить cookie и считать session отозванной.** Отзовите запись на сервере.
- **Запустить дорогую KDF на безлимитном body.** Проверяйте размер до KDF и ограничивайте частоту входов.

Если cookie не сохраняется в браузере, посмотрите все attributes в recorder и применённую HTTPS конфигурацию. Если логин проходит, но `/me` не распознаёт сессию, проверьте путь cookie, hash токена в БД, expiry, logout и одинаковое имя cookie. Для CSRF создайте запрос с другим Origin, убедитесь, что состояние не меняется, и отдельно докажите, что нормальный same-origin mutation с верным token проходит.

Фиксируйте и отрицательный исход входа: отсутствие учётной записи и неправильный пароль обычно должны иметь совместимый публичный error contract, чтобы endpoint не отвечал, существует ли email. Лимитируйте body, нормализуйте email по выбранной политике и применяйте rate limiting. Одинаковая строка ошибки без ограничения попыток не мешает перебору; разные эти меры закрывают разные части риска.

## Практика

- **Easy:** проверьте, что password hash policy принимает от 600 000 до 1 200 000 PBKDF2 итераций включительно, salt не короче 16 bytes и derived output ровно 32 bytes. Верхний предел задаёт бюджет CPU учебной конфигурации: большее число само по себе не делает KDF криптографически хуже. Это валидатор параметров, не криптографическое доказательство безопасности.
- **Medium:** внедрите `now` и сравните expiry: сессия истекла при `expiresAt <= now`; проверить срок в будущем, ровно сейчас и в прошлом.
- **Hard:** разрешайте browser mutation только для POST/PUT/PATCH/DELETE и только при успешно проверенном CSRF token плюс доверенном Origin; GET/HEAD/OPTIONS не являются изменяющими маршрутами. Назовите, что сама функция предполагает проверенным ранее.

## Мини-глоссарий

- **authentication (аутентификация)** — установление субъекта запроса.
- **session (сессия)** — серверное состояние входа с ограниченным сроком и отзывом.
- **opaque token (непрозрачный токен)** — случайный идентификатор без встроенного user data.
- **PBKDF2** — password KDF на базе повторного HMAC вычисления.
- **salt (соль)** — уникальное случайное значение, сохраняемое рядом с derived hash.
- **CSRF** — подделка запроса браузером с автоматически отправленной cookie.
- **session rotation** — замена session token после изменения доверенной личности.
- **constant-time comparison** — сравнение, не прекращающее работу на первом отличающемся байте.
