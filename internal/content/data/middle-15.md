# Идемпотентные изменения и повторы запроса

## Почему эта тема важна

Клиент отправил команду, сервер сохранил изменение, но ответ потерялся в сети. Клиент видит timeout и не знает, завершилась ли операция. Повтор без защиты может списать деньги или создать второй заказ. Idempotency key (ключ идемпотентности) связывает несколько доставок одного логического намерения. Для одного ключа система должна различить новую операцию, тот же запрос, конфликтующий запрос и работу, исход которой ещё не известен.

Ключ должен быть стабилен при повторе и ограничен областью владельца: например, tenant + endpoint + key. Храните отпечаток канонического payload (полезной нагрузки), а не сравнивайте произвольную сериализацию, где порядок полей или форматирование могут различаться. Один ключ с тем же отпечатком может вернуть сохранённый результат; тот же ключ с другим содержимым — conflict. Для отсутствующей записи сравнение payload не имеет смысла: результат `new` должен быть одинаков при любом флаге сравнения.

Есть важная гонка: два запроса одновременно проверили, что ключа нет. Оба пытаются вставить его. Проверка `SELECT` перед `INSERT` не делает операцию атомарной. В PostgreSQL нужен уникальный constraint по выбранной области ключа; проигравший insert затем читает существующую строку и сравнивает payload. Изоляция, обработка `ON CONFLICT`, блокировки и транзакция зависят от конкретной схемы. Учебный helper этого не выполняет.

Запись ключа, бизнес-изменение и ответ должны проектироваться совместно. Если сохранить только «ключ занят», а процесс упадёт до бизнес-эффекта, повтор зависнет в in_progress. Если эффект записан, но ответ потерян, повтор должен восстановить прежний результат, а не выполнить эффект снова. Поэтому сохраняют состояние операции и нужный ответ либо устойчивую ссылку на результат в согласованной транзакции. Для долгих операций нужна явная модель lease/recovery и правила очистки старых ключей.

Easy моделирует новую запись, replay и conflict. Medium добавляет in_progress, чтобы не выдать незавершённую работу за успех. Hard описывает проигравшую вставку уникального ключа и случай completed без сохранённого ответа как unknown_result. Это специально не «retry»: побочный эффект мог произойти. Такой исход требует сверки или доменного восстановления. Функции работают только с переданными булевыми фактами и ничего не сериализуют, не блокируют и не гарантируют транзакционность.

Проверьте также срок хранения ключа. Слишком короткий TTL позволяет позднему повтору снова выполнить команду; бесконечное хранение увеличивает базу и может хранить чувствительные данные. Период хранения должен быть не короче допустимого окна повторов продукта, а очистка — не удалять записи, пока связанные операции ещё могут повториться. Логи должны содержать безопасный идентификатор и итоговую категорию, но не секретный payload или credentials.

## Практика трёх уровней

**Easy — middle-15-easy.** Реализуйте самый узкий контракт. Перед кодом выпишите таблицу вход → результат, отдельно нормальный случай, границу и некорректное состояние. Не добавляйте состояние, которого нет в сигнатуре. Проверьте, что каждый выход имеет конкретное значение для вызывающего слоя.

**Medium — middle-15-medium.** Добавьте независимый сигнал или состояние из условия. Решайте ветви в заданном порядке: сначала невалидное состояние, затем уже совершённый эффект/отмена, затем доступность ресурса, затем временной лимит и только после этого повтор или отказ. Этот порядок важен там, где две причины истинны одновременно. Проверьте конфликтующие входы из public/private vectors.

**Hard — middle-15-hard.** Разберите окно сбоя, неизвестный результат либо ограниченный отказ. Запишите, что система знает до сбоя и что может подтвердить после перезапуска. Не выводите «ровно один раз» из локальной категории: при неопределённом подтверждении реальная система должна повторить безопасно либо запросить сверку. Решение из функции — лишь политика для заданных фактов.

## Три исполняемых примера

```go group=middle-15-easy mode=run
package main
import "fmt"


func IdempotencyOutcomeEasy(seen bool, samePayload bool) string {
	if !seen { return "new" }
	if samePayload { return "replay" }
	return "conflict"
}

func main() { fmt.Println(IdempotencyOutcomeEasy(false, false)) }
```

```go group=middle-15-medium mode=run
package main
import "fmt"


func IdempotencyStateMedium(found bool, payloadMatches bool, completed bool) string {
	if !found { return "new" }
	if !payloadMatches { return "conflict" }
	if !completed { return "in_progress" }
	return "replay"
}

func main() { fmt.Println(IdempotencyStateMedium(false, false, false)) }
```

```go group=middle-15-hard mode=run
package main
import "fmt"


func IdempotencyRaceHard(inserted bool, payloadMatches bool, completed bool, hasStoredResponse bool) string {
	if inserted { return "created" }
	if !payloadMatches { return "conflict" }
	if !completed { return "in_progress" }
	if hasStoredResponse { return "replay" }
	return "unknown_result"
}

func main() { fmt.Println(IdempotencyRaceHard(true, false, false, false)) }
```

## Как читать примеры и проверять выводы

Примеры ниже компилируются как небольшие программы и показывают публичный reference для упражнения. Каждый запускает только чистую функцию: в нём нет сетевого клиента, локальной БД, goroutine, таймера, брокера или настоящей конфигурации сервера. Вывод показывает результат контракта на названном input. Он не означает, что внешняя зависимость выдала такой исход, сохранила данные или соблюла порядок. Если пример и формулировка расходятся, исправлять нужно контракт или reference вместе, а не подгонять hidden tests под один частный ответ.

Табличный тест должен называть смысл каждой строки. Укажите входы, ожидаемую категорию и инвариант, который проверяется. Одного «happy path» недостаточно: добавьте точную границу, значение за границей и пересечение двух сигналов, когда приоритет важен. Private vectors должны ловить реализацию, которая всегда возвращает один удобный ответ, игнорирует отдельный аргумент, путает `>=` и `>` или не замечает некорректный счётчик. Случаи должны быть компактны и детерминированы, чтобы ученик мог воспроизвести их локально.

## Что потребуется для реальной проверки

Переход от helper к работающему backend потребует другого набора доказательств. Зафиксируйте версии runtime и зависимости, конфигурацию, лимиты, время ожидания, политику подтверждений и порядок фиксации. Для отказного теста отметьте точку, где процесс останавливается, перезапустите компонент и посчитайте итоговый эффект. Проверяйте, что отмена освобождает ресурсы, повтор не умножает изменение, а постоянная ошибка не крутится бесконечно. Снимайте метрики задержки, backlog и повторов. Unit test не может заменить такие проверки.

Если в системе участвует PostgreSQL, проверьте миграцию, уникальные ограничения, транзакционные границы и конкурентный сценарий на реальном закреплённом движке. Если участвует брокер, тест должен включать его фактический ack/confirm режим и рестарт consumer или relay. Если результат зависит от сети, используйте контролируемый локальный контейнер или fault proxy, а не случайную задержку. Очистка должна быть изолирована от пользовательских данных. Повторяемая команда и зафиксированный fixture позволяют другому разработчику независимо подтвердить результат.

## Диагностика и проектное решение

Начинайте расследование с наблюдаемого состояния: счётчики до операции, момент commit/ack, возвращённая категория, число повторов и конечный эффект. Сверьте часы, единицы измерения и идентификатор операции. Не делайте вывод по одному лог-сообщению, если его могло создать несколько попыток. Корреляционный ID должен быть безопасен и одинаков для повтора; payload, токены, DSN и личные сведения не следует без необходимости писать в лог.

При выборе политики опишите цену обеих сторон. Увеличить ожидание — значит дать системе больше времени, но занять запрос и ресурсы дольше. Быстро отказать — значит сохранить capacity, но передать восстановление вызывающему коду. Повтор — шанс пережить transient сбой и вероятность дублирования. Dead-letter — остановка автоматического шума ценой необходимости диагностики и replay. Хороший middle-level ответ называет условие переключения политики и метрику, которая это условие обнаружит.

Устойчивое решение имеет владельца каждого инварианта. Handler отвечает за решение и контекст; repository — за транзакционное состояние; адаптер брокера — за mapping ack/nack; операторская политика — за лимиты, очередь повторов и восстановление. Не размывайте ответственность между слоями. Наблюдаемая функция из grader помогает изолировать одно правило, а интеграционная система проверяет взаимодействие владельцев. Это разные масштабы доказательства, и оба могут понадобиться.

### Самопроверка

1. Какой вход пересекает границу контракта и меняет решение?
2. Какой отказ может произойти после внешнего эффекта, но до локального подтверждения?
3. Какая часть поведения проверена чистой функцией, а какая требует конкретной инфраструктуры?
4. Какой тест способен обнаружить дубликат, потерю эффекта или утечку ожидающего ресурса?

Перед завершением назовите один непокрытый отказ и один конкретный тест, который мог бы опровергнуть ваше решение. Сохраните команду, fixture, версии и фактическое число эффектов. Не расширяйте утверждение за пределы наблюдений: правильный результат helper — необходимая проверка правила, но не сертификат поведения всей системы.

## Сценарий: клиент повторил POST

Пусть клиент создал заказ с ключом `checkout-77`. Сервер проверил отсутствие записи, начал transaction, сохранил заказ и idempotency record, но соединение оборвалось до ответа. Клиент повторил запрос с тем же ключом и тем же payload. Ожидаемое решение — вернуть сохранённый результат, а не создавать второй заказ. Теперь клиент по ошибке повторяет тот же ключ с другой суммой: это conflict, поскольку ключ уже обозначает другую команду. Смена поля при одинаковом ключе не является новым запросом.

Перед хешированием определите канонизацию. JSON `{"amount":5,"currency":"USD"}` и `{"currency":"USD","amount":5}` могут быть семантически одинаковы, хотя байты различаются. С другой стороны, отбросить поле валюты опасно. Зафиксируйте включённые поля, их нормализацию и версию схемы. Сохраняемый fingerprint следует сравнивать постоянным безопасным способом и не включать секреты, если их можно избежать. Ключ сам по себе не аутентифицирует пользователя: tenant/user scope должен быть частью уникальности, чтобы чужой клиент не прочитал чужой сохранённый ответ.

### Переходы состояния

Новая операция создаёт запись в состоянии in_progress, затем фиксирует доменное изменение и конечный ответ согласно выбранной транзакционной модели. Для короткой SQL-команды удобно записать idempotency row, изменение и ответ в одной транзакции. Для долгой фоновой операции отдельная запись может оставаться in_progress; тогда нужны lease owner, lease expiry и протокол восстановления после падения worker. Состояние нельзя навечно оставлять in_progress только потому, что процесс остановился. Повтор должен либо увидеть действующего владельца, либо безопасно восстановить истёкшую работу.

В Hard сценарии `inserted=false` значит, что именно эта попытка не получила уникальный ключ. Сначала нужно прочитать строку-победителя: другой payload даст conflict, незавершённая работа — in_progress, готовый результат — replay. Если работа помечена завершённой, но ответа нет, helper возвращает unknown_result. Это не косметическая ветка: неполное сохранение результата может привести к повтору побочного эффекта. Операционный процесс может запросить фактическое состояние заказа по доменному ID и восстановить ответ либо поднять ручную сверку.

### Негативные тесты

Мутант «всегда new» ломается на совпадающем и конфликтном повторе. Мутант «всегда replay» ломается на отсутствующей записи. Реализация, которая возвращает conflict для неизвестного ключа, проваливает `seen=false, samePayload=false`. Мутант, игнорирующий completed, выдаст replay для ещё выполняющейся операции. Hard private vectors отдельно проверяют race-loss и отсутствие сохранённого ответа. Сравните полный набор состояний; тестировать только первый запрос означает вообще не проверять идемпотентность.

### Что проверяет БД тест

Запустите две транзакции с одинаковым tenant/key барьером, чтобы обе дошли до вставки одновременно. Уникальное ограничение должно допустить одного победителя; проигравший должен корректно прочитать результат после конфликта. Проверьте одинаковый payload, конфликтный payload и падение до/после commit. Подсчитайте количество созданных заказов и повторных списаний. Простая пара последовательных HTTP запросов не воспроизводит гонку. Наконец, проверьте очистку: удалить запись ранее максимального окна повторов — значит разрешить дубли позднего retry. Срок хранения и объём ответа должны иметь продуктовый предел.

### Разбор конкурентного случая

Запустите две goroutine, которые одновременно отправляют `tenant=A, key=order-9`. Обе могут прочитать отсутствие записи, если код делает предварительный SELECT. Затем обе пытаются выполнить INSERT. Уникальный индекс должен сериализовать победу: одна транзакция создаёт запись, другая получает конфликт. Вторая сторона после конфликта должна перечитать строку и классифицировать её. Без уникального ограничения обе транзакции могут пройти проверку и записать два эффекта. В памяти процесса mutex не защитит от второй реплики сервиса и рестарта.

Важно, где находится transaction boundary. Вариант «сначала committed idempotency row, затем создать заказ» оставляет ключ занят при ошибке создания. Вариант «создать заказ, потом записать ключ» оставляет окно повторного создания. Если обе операции в одной PostgreSQL транзакции, rollback отменяет обе, commit фиксирует обе. Если побочный эффект — внешний API, такой транзакции нет; тогда нужен отдельный state machine, outbox или idempotent downstream API. Не называйте всё это одной функцией.

Сохранённый ответ может содержать личные данные. Ограничьте срок хранения и выдавайте результат только в том же auth scope, где был создан ключ. Идемпотентность предотвращает повторы команды, но не заменяет authorization: чужой пользователь не должен получить ответ, угадав ключ. Rate limit также необходим, чтобы злоумышленник не создал неограниченное число записей.

### Дополнительный контроль

Приватность является частью контракта. Успешный replay должен проверять аутентифицированный tenant и владельца операции до возврата сохранённого тела ответа. Не отдавайте полный request fingerprint наружу: он может раскрыть сведения о payload или позволить корреляцию. В журнале достаточно безопасного operation ID, категории `new/replay/conflict` и latency. Хранение idempotency ответов может увеличить стоимость базы; храните только поля, нужные для повторного ответа, и определите удаление в соответствии с окном retry.

### Термины

- **idempotency key (ключ идемпотентности)** — Идентификатор одной логической операции при повторах.

- **replay (повтор)** — Повторная доставка того же запроса или сообщения.

- **unique constraint (ограничение уникальности)** — Защита базы от двух строк с одним ключом.
