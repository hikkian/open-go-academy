# Идемпотентные изменения и повторы запроса

## Что ты сделаешь

Ты напишешь три функции-решения для повторов: новая операция или повтор, учёт незавершённой работы и исход гонки вставки ключа. Функции получают уже известные факты о записи и возвращают категорию, а сами не выполняют SQL и не отправляют запросы.

## Зачем нужен ключ операции

Клиент отправил команду, сервер сохранил изменение, но ответ потерялся в сети. Клиент видит таймаут и не знает, завершилась ли операция. Повтор без защиты может списать деньги дважды или создать второй заказ.

Ключ идемпотентности (idempotency key) связывает несколько доставок одного и того же логического намерения. Для одного ключа система должна различать четыре ситуации: новая операция, тот же запрос, конфликтующий запрос и работа, исход которой ещё не известен. Ключ должен быть стабилен при повторе и ограничен областью владельца, например связкой «tenant, endpoint, ключ».

> **Важно.** Ключ сам по себе не аутентифицирует пользователя. Если область не включает владельца, чужой клиент, угадав ключ, получит чужой сохранённый ответ.

## Отпечаток канонического payload

Для сравнения содержимого хранят отпечаток канонического payload, а не произвольную текстовую форму. Одинаковый по смыслу JSON может иметь разные байты: порядок полей, пробелы и форматирование меняются. Поэтому каноническая форма задаётся правилами: какие поля входят, как их нормализовать и какая версия схемы используется.

Пример показывает, что `encoding/json` сортирует ключи словаря. Два одинаковых по смыслу словаря дают одинаковую строку:

```go
package main

import (
    "encoding/json"
    "fmt"
)

func main() {
    a, _ := json.Marshal(map[string]any{"currency": "USD", "amount": 5})
    b, _ := json.Marshal(map[string]any{"amount": 5, "currency": "USD"})
    fmt.Println(string(a) == string(b), string(a))
}
```

Вывод: `true {"amount":5,"currency":"USD"}`. Совпадение строк здесь получено благодаря сортировке ключей. Для настоящего API правила канонизации нужно записать явно, потому что не каждое поле можно отбросить при сравнении: отбрасывание валюты из примера сделало бы разные суммы «одинаковыми».

Один ключ с тем же отпечатком может вернуть сохранённый результат. Тот же ключ с другим содержимым — конфликт. Для отсутствующей записи сравнение содержимого не имеет смысла: результат `new` одинаков при любом значении флага совпадения.

## Гонка вставки ключа

Есть важная гонка: два запроса одновременно проверили, что ключа нет, и оба пытаются его вставить. Проверка `SELECT` перед `INSERT` не делает операцию атомарной. Между проверкой и вставкой другой участник успевает записать тот же ключ.

Защиту даёт уникальное ограничение в базе по выбранной области ключа. Побеждает одна вставка, а проигравшая попытка читает существующую строку и классифицирует её. Пример моделирует уникальность набором: повторный ключ обнаруживается и пропускается.

```go
package main

import "fmt"

func main() {
    keys := map[string]bool{}
    for _, k := range []string{"order-9", "order-9", "order-10"} {
        if keys[k] {
            fmt.Println("duplicate", k)
            continue
        }
        keys[k] = true
    }
    fmt.Println(len(keys))
}
```

Вывод: `duplicate order-9` и затем `2`. Набор здесь играет роль уникального ограничения только в учебной модели. В базе за уникальность отвечает индекс, а не память процесса: mutex не защищает от второй реплики сервиса и от рестарта.

## Состояние операции

Запись ключа, бизнес-изменение и ответ должны проектироваться вместе. Если сохранить только факт «ключ занят», а процесс упадёт до бизнес-эффекта, повтор будет ждать вечно в состоянии `in_progress`. Если эффект записан, но ответ потерян, повтор должен вернуть прежний результат, а не выполнить эффект снова.

Незавершённая операция не считается успешной и не должна запускаться параллельно второй раз. Поэтому состояние `in_progress` нужно различать с состоянием `done`. Пример показывает такой выбор по состоянию записи:

```go
package main

import "fmt"

func main() {
    for _, state := range []string{"in_progress", "done"} {
        switch state {
        case "in_progress":
            fmt.Println("wait")
        case "done":
            fmt.Println("replay")
        }
    }
}
```

Вывод: `wait` и затем `replay`. Ветки отражают разное поведение: ждать чужую работу и возвращать готовый ответ — не одно и то же.

## Неизвестный результат

Самый опасный случай — операция помечена завершённой, но сохранённого ответа нет. Это значит, что эффект мог произойти, а ответ не записался. Слепой повтор запустит побочный эффект второй раз, поэтому такой исход называют `unknown_result`. Его нельзя выдавать за ошибку без последствий или за успех.

Операционный процесс должен запросить фактическое состояние по доменному идентификатору, восстановить ответ или поднять ручную сверку. Это не косметическая ветка: неполное сохранение результата может привести к дублю платежа.

> **Типичная ошибка.** Считать, что при любой ошибке повтор безопасен. Повтор безопасен только для операции, которая не оставила эффекта или является идемпотентной по ключу.

## Срок хранения и приватность

Ключи хранят не вечно. Слишком короткий срок позволяет позднему повтору снова выполнить команду, бесконечное хранение раздувает базу и может держать чувствительные данные. Срок должен быть не короче окна повторов продукта, а очистка не должна удалять записи, пока связанные операции могут повториться.

Сохранённый ответ может содержать личные данные. Выдавай его только в том же области аутентификации, где был создан ключ. В журнал пиши безопасный идентификатор операции и итоговую категорию, но не payload и не учётные данные.

Идемпотентность защищает от повторов команды, но не заменяет авторизацию и ограничение частоты. Злоумышленник, создающий новые ключи, может заполнить таблицу ключей без ограничения. Поэтому число ключей на клиента ограничивают так же, как обычные запросы.

## Модель и механизм

Сначала различай состояние программы и расписание. Состояние — запись ключа, отпечаток, статус операции и сохранённый ответ. Расписание — порядок, в котором два запроса проверяют и вставляют ключ. Корректная политика должна давать допустимое решение при любом порядке.

Для повтора полезны три вопроса. Существует ли запись? Совпадает ли содержимое? Завершена ли операция и сохранён ли ответ? Ответы записываются до написания кода, а не после первого падения.

Синхронизация имеет цену. Уникальный индекс и транзакция добавляют ожидание, а ключи занимают место. Срок хранения выбирают по окну повторов, а не по удобству очистки.

Решение о классе ответа тоже имеет цену. Если вернуть `conflict` слишком часто, честный клиент с нестабильным сериализатором получит ложные отказы. Если вернуть `replay` без проверки содержимого, злоумышленник сможет получить чужой результат. Правило должно учитывать обе стороны и быть описано в контракте API.

Для долгих операций, которые выполняет фоновый обработчик, одного статуса мало. Записывают владельца аренды (lease owner) и момент её истечения. Если обработчик упал, по истечении срока другой участник может забрать операцию и восстановить её. Без такого протокола запись навсегда остаётся в `in_progress`, а повтор клиента ждёт результата, который никогда не придёт.

## Лаборатория перед практикой

Возьми пример с `keys` и представь, что два обработчика одновременно выполняют проверку `keys[k]` для одного ключа `order-9` до записи. Перед запуском запиши, какие строки напечатает программа в каждом из двух вариантов: последовательном и конкурентном. Затем добавь горутины и `sync.Mutex` вокруг проверки и записи, запусти программу несколько раз и сравни результат.

Журнал эксперимента содержит версию Go, число запусков, предсказание, наблюдение и вывод `-race`, если он появился. Отсутствие ошибки в нескольких запусках не доказывает корректность: мьютекс в одном процессе не защитит от второй реплики сервиса. Поэтому итоговое правило остаётся тем же — уникальное ограничение в базе.

## Типичные ошибки и исправление

Первая ошибка — проверить ключ через `SELECT`, а потом вставить. Между проверкой и вставкой возможна гонка. Исправление — уникальное ограничение и обработка конфликта на вставке.

Вторая — сохранять ключ до бизнес-эффекта. Если процесс упадёт, ключ останется занятым навсегда. Исправление — согласованная транзакция или явное состояние восстановления.

Третья — сравнивать сырой JSON. Разный порядок полей даст ложный конфликт. Исправление — отпечаток канонической формы.

## Если что-то пошло не так

- Повтор создаёт второй заказ → ключ не защищён уникальным ограничением или область ключа слишком узкая.
- Клиент получает `conflict` при повторе той же операции → канонизация включает поля, которые меняются между повторами, например временную метку.
- Операция висит в `in_progress` навсегда → процесс упал до завершения; нужна аренда и восстановление по истечении срока.
- Чужой клиент получает сохранённый ответ → область ключа не включает владельца.

## Практика

Эти задания моделируют решения по переданным фактам. Функции не выполняют SQL, не блокируют и не гарантируют транзакционность. Закрытые примеры видны только в «Проверить».

### Задание 1 · Повтор одного ключа

**Цель.** Вход — `seen` (запись есть) и `samePayload` (содержимое совпало). Если записи нет, верни `"new"` независимо от `samePayload`. Если запись есть и содержимое совпало, верни `"replay"`. Иначе верни `"conflict"`.

**Ожидаемый вывод** — входы: `seen = false, samePayload = false`; `seen = false, samePayload = true`; `seen = true, samePayload = true`; `seen = true, samePayload = false`:

```text
"new"
"new"
"replay"
"conflict"
```

1. Выбери задание «Повтор одного ключа»: в файле есть `IdempotencyOutcomeEasy` с `panic("TODO")`. Импорты не нужны.
2. Если записи нет, верни `"new"`.
3. Если содержимое совпало, верни `"replay"`.
4. Иначе верни `"conflict"`.
5. Нажми «Запустить» и сравни с блоком выше.

**Как проверить себя.** Четыре строки в кавычках; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `"conflict"` для нового ключа → сравнение содержимого выполняется до проверки записи.
- `"replay"` при другом содержимом → флаг совпадения не проверен.

> **Подсказка.** Сначала проверка существования записи, потом совпадение содержимого.

2. Если записи нет, верни `"new"`.

## Итог

- Ключ операции различает новую операцию, повтор, конфликт и незавершённую работу; отпечаток канонического содержимого сравнивают по правилам.
- Защиту от гонки даёт уникальное ограничение в базе, а не проверка перед вставкой.
- Завершённая операция без сохранённого ответа требует сверки, потому что слепой повтор может дублировать эффект.
