# Селективность и выбор SQL-плана

## Что ты сделаешь

Ты научишься рассуждать о запросе так, как рассуждает планировщик PostgreSQL: какая доля строк подходит под предикат, что об этом знает статистика и во сколько обойдётся альтернативный способ доступа. Три функции урока — `SelectivityClass`, `ValidSelectivity`, `IndexCandidate` — это арифметика доли и первичный фильтр «стоит ли смотреть план», а не замена `EXPLAIN`.

## Селективность — доля, а не абсолютное число

Селективность (selectivity) — доля строк, удовлетворяющих предикату, от множества строк, которое оптимизатор рассматривает. Предикат по почти уникальному `email` оставляет одну строку из миллиона — низкая селективность в смысле доли, «высокая избирательность» в бытовом смысле; чтобы не путаться, в уроке говорим о доле. Флаг `active = true` в таблице, где активны почти все, оставляет 95 % строк. Знаменатель важен так же, как числитель: 500 совпадений из 1 000 и из 10 000 000 — разные задачи.

```go group=selectivity mode=run
package main

import "fmt"

func class(matches, total int) string {
    if total <= 0 || matches < 0 || matches > total {
        return "invalid"
    }
    lowCeil := (total + 9) / 10
    half := (total + 1) / 2
    switch {
    case matches < lowCeil:
        return "low"
    case matches < half:
        return "medium"
    }
    return "high"
}

func main() {
    fmt.Println(class(5, 100), class(10, 100), class(49, 100), class(50, 100))
    fmt.Println(class(1, 15), class(2, 15), class(0, 0))
}
```

Вывод:

```text
low medium medium high
low medium invalid
```

Пороги 10 % и 50 % — условность учебной модели, а не эвристика планировщика. Их считают целочисленно с округлением вверх: для 15 строк порог «меньше 10 %» — это меньше двух строк. Реальный план зависит от статистики, стоимости, индексов, параметров и распределения данных.

> **Важно.** Низкая доля сама по себе не означает «нужен индекс». Индексный доступ — это случайные чтения страниц; при большом числе подходящих строк или плохой локальности последовательное чтение всей таблицы дешевле.

## Стоимость доступа: последовательное чтение против случайного

Последовательное сканирование читает все страницы таблицы подряд — дорого, но предсказуемо. Индексный доступ читает листья индекса и затем страницы таблицы для каждой подходящей строки; если строки разбросаны, каждая — отдельное случайное чтение. Планировщик сравнивает оценку стоимости обоих путей через модель с весами последовательной и случайной страницы.

```go group=pages mode=run
package main

import "fmt"

func main() {
    const rowsPerPage = 100
    totalRows := 1_000_000
    tablePages := totalRows / rowsPerPage
    for _, matches := range []int{100, 10_000, 100_000} {
        // худший случай: каждая подходящая строка на своей странице
        randomPages := matches
        if randomPages > tablePages {
            randomPages = tablePages
        }
        fmt.Printf("совпадений %7d: seq=%d страниц, index≈%d случайных страниц\n", matches, tablePages, randomPages)
    }
}
```

Вывод:

```text
совпадений     100: seq=10000 страниц, index≈100 случайных страниц
совпадений   10000: seq=10000 страниц, index≈10000 случайных страниц
совпадений  100000: seq=10000 страниц, index≈10000 случайных страниц
```

При ста совпадениях индекс читает в сто раз меньше страниц; при десяти тысячах — столько же, но случайно, то есть дороже; при ста тысячах выигрыша нет вовсе. Модель грубая — она не учитывает корреляцию расположения строк с ключом и кеш, — но показывает, почему планировщик переключается на последовательное чтение задолго до 50 %.

## Статистика: откуда планировщик берёт долю

Оценка строится на статистике столбцов: гистограммы, самые частые значения, доля NULL, число различных значений. `ANALYZE` обновляет её; устаревшая статистика после массовых вставок, перекос (skew) распределения, корреляция между столбцами и параметризованные значения делают оценку неточной. Расширенная статистика помогает некоторым коррелированным условиям, но добавлять её механически не стоит.

`EXPLAIN` показывает план и оценку `rows`; `EXPLAIN ANALYZE` действительно исполняет запрос и показывает фактические строки и время. Для изменяющих команд это опасно: оборачивай в транзакцию с откатом или работай на одноразовом стенде. План — не сертификат скорости: фактический результат зависит от кеша, конкуренции и диска, а выполнение прогревает кеши и влияет на следующий прогон.

```go group=estimate mode=run
package main

import (
    "fmt"
    "strings"
)

func main() {
    lines := []string{
        "Index Scan on orders (cost=0.43..8.45 rows=8 width=64) (actual rows=5 loops=1)",
        "Seq Scan on events (cost=0.00..18334.00 rows=1200 width=40) (actual rows=240000 loops=1)",
    }
    for _, l := range lines {
        var est, act int
        for _, f := range strings.Fields(l) {
            f = strings.Trim(f, "()")
            if strings.HasPrefix(f, "rows=") {
                if est == 0 {
                    fmt.Sscanf(f, "rows=%d", &est)
                } else {
                    fmt.Sscanf(f, "rows=%d", &act)
                }
            }
        }
        fmt.Printf("%-10s оценка=%d факт=%d  расхождение x%d\n", strings.Fields(l)[0], est, act, act/max(est, 1))
    }
}
```

Вывод:

```text
Index      оценка=8 факт=5  расхождение x0
Seq        оценка=1200 факт=240000  расхождение x200
```

Первая строка — оценка близка к факту, план можно обсуждать. Вторая — планировщик ждал тысячу строк, а получил четверть миллиона: это сигнал о статистике, перекосе или параметре, а не о «плохом индексе». Разбирать план с расхождением в двести раз бессмысленно, пока не выяснена причина расхождения.

> **Типичная ошибка.** Скопировать план с другой таблицы или другого стенда. Другой размер, другой перекос, другая статистика — другой план.

## Параметры и подготовленные запросы

Параметризованный запрос (`WHERE status = $1`) безопасен от инъекций, но для планировщика значение параметра — неизвестное. Пока значение не подставлено, он оценивает долю по средней статистике столбца: для `pending` (2 %) и `done` (98 %) оценка одна и та же, и план один — хотя для первого выгоден индекс, а для второго последовательное чтение. PostgreSQL после нескольких выполнений подготовленного запроса сравнивает стоимость обобщённого плана с планами под конкретные значения и может закрепить обобщённый; тогда редкое значение получает план, рассчитанный на частое.

Поэтому при расхождении оценки и факта проверяй не только статистику, но и форму параметра: `EXPLAIN` с литералом и с параметром дают разные ответы на один вопрос. Это не повод отказываться от параметризации — повод знать, как выглядит план для редкого значения, и при необходимости разделить запросы для сильно перекошенных столбцов.

## Вопрос к плану формулируется узко

«Нужен ли индекс вообще?» — вопрос без ответа. «Уменьшит ли индекс по `status` число прочитанных страниц для фильтра `status = 'pending'` при текущем распределении, где pending — 2 % строк?» — вопрос, на который отвечают `EXPLAIN ANALYZE` и профиль нагрузки. Для каждого запроса запиши частоту, число возвращаемых строк, фильтры, сортировку, распределение задержек и допустимую свежесть. Индекс, выгодный одному маршруту, может вредить общему профилю с большим числом записей: каждая вставка обновляет и его.

Планы меняются после роста таблицы, `VACUUM` и `ANALYZE`; снимок сегодняшнего плана не предсказывает сезонный профиль. Сохраняй пару «fixture + команда», чтобы повторить анализ на тех же данных.

> **Зачем.** Учебные функции урока — первичная группировка для исследования: они говорят, стоит ли открывать план, но не заменяют его.

Запиши для каждого запроса, с каким значением параметра снят план и при какой статистике: без этих двух строк план в отчёте нельзя ни повторить, ни оспорить, и сравнение «до индекса» и «после» становится сравнением разных экспериментов.

## Типичные ошибки

- Путать долю с числом: 500 совпадений — низкая доля в десяти миллионах и половина в тысяче.
- Считать низкую долю доказательством пользы индекса без оценки случайных чтений.
- Читать план с расхождением оценки и факта в сотни раз, не обновив статистику и не проверив перекос.
- `EXPLAIN ANALYZE` на изменяющей команде вне транзакции с откатом.
- Переносить план между таблицами разного размера и распределения.
- Добавлять индекс ради одного запроса, не посчитав цену для записи.

## Самостоятельная лаборатория

На одноразовом PostgreSQL создай таблицу из миллиона синтетических строк с колонкой `status`, где `pending` — 2 %, `done` — 98 %. Выполни `ANALYZE`, затем `EXPLAIN ANALYZE` для фильтра по каждому значению до и после создания индекса по `status`. Выпиши для каждого из четырёх планов: тип доступа, оценку `rows`, факт, время. Посчитай долю функцией из первого примера и проверь, согласуется ли выбор планировщика с интуицией о случайных чтениях. Затем вставь ещё миллион строк со `status = 'pending'` без `ANALYZE` и повтори `EXPLAIN` — расхождение оценки и факта покажет, что такое устаревшая статистика. Удали стенд.

## Если что, пошло не так

- `medium` вместо `low` для `(1, 15)` → порог посчитан как `total / 10` без округления вверх; для 15 строк порог — две строки.
- `invalid` не срабатывает для `matches > total` → проверка диапазона неполная.
- `true` в задании 3 для оценки 80 из 100 → граница «меньше половины» не проверена или половина посчитана с округлением вниз.
- `false` для `total = 0` в задании 2 — верно; `true` — проверка `total > 0` отсутствует.
- `import … is not allowed` → импорты запрещены: целочисленная арифметика.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Пороги и правила — учебная модель, не эвристика PostgreSQL.

### Задание 1 · Easy: оцени selectivity по доле строк

**Цель.** Классифицировать долю `matches / total`: `low` при доле меньше 10 %, `medium` — меньше 50 %, иначе `high`; некорректные входы → `invalid`.

**Ожидаемый вывод** — для `(matches=5, total=100)`:

```text
"low"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func SelectivityClass(matches, total int) string`. Импорты запрещены.
2. Первой проверкой: `total <= 0`, `matches < 0` или `matches > total` → `"invalid"`.
3. Пороги с округлением вверх: `lowCeil := (total + 9) / 10`, `half := (total + 1) / 2`.
4. `matches < lowCeil` → `"low"`; `matches < half` → `"medium"`; иначе `"high"`. «Запустить», «Проверить» — закрытые примеры: `(90, 100)` → `high`, `(-1, 100)` → `invalid`.

**Как проверить себя.** Для 100 строк: 9 → `low`, 10 → `medium`, 49 → `medium`, 50 → `high`; для 15 строк: 1 → `low`, 2 → `medium`.

**Если не принято.**
- Красный закрытый пример `(-1, 100)` → проверка знака отсутствует.
- Граничные значения дают сдвиг на единицу → пороги считаются с округлением вниз.

> **Подсказка.** `(total + 9) / 10` — это `ceil(total / 10)` в целых числах; тот же приём с `+ 1` для половины.

### Задание 2 · Medium: проверь знаменатель и cardinality

**Цель.** Вернуть `true`, если `total > 0` и `0 ≤ matches ≤ total`.

**Ожидаемый вывод** — для `(matches=1, total=10)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ValidSelectivity(matches, total int) bool`. Импорты запрещены.
2. Верни `total > 0 && matches >= 0 && matches <= total`.
3. «Запустить», «Проверить» — закрытые примеры: `(11, 10)` → `false`, `(0, 0)` → `false`.

**Как проверить себя.** Ноль совпадений при положительном итоге — допустимо; нулевой знаменатель — нет; совпадений больше строк быть не может.

**Если не принято.**
- `true` для `(0, 0)` → условие `total >= 0` вместо `> 0`.
- `true` для `(11, 10)` → нет проверки `matches <= total`.

> **Подсказка.** Это предусловие для двух других функций; вынеси его мысленно в отдельную проверку и переиспользуй.

### Задание 3 · Hard: сравни estimate и actual для кандидата индекса

**Цель.** Вернуть `true`, если входы корректны и оценка планировщика `estimatedRows` меньше половины общего числа строк (половина — с округлением вверх).

**Ожидаемый вывод** — для `(matches=5, total=100, estimatedRows=8)`:

```text
true
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func IndexCandidate(matches, total, estimatedRows int) bool`. Импорты запрещены.
2. Верни `false`, если `total <= 0`, `matches < 0`, `matches > total` или `estimatedRows < 0`.
3. `half := (total + 1) / 2`; верни `estimatedRows < half`.
4. «Запустить», «Проверить» — закрытые примеры: оценка 80 из 100 → `false`; `total = 0` → `false`.

**Как проверить себя.** Решает оценка планировщика, а не факт: функция отвечает «стоит ли открывать `EXPLAIN`», а расхождение оценки с фактом — отдельный вопрос о статистике.

**Если не принято.**
- `true` для `(5, 0, 1)` → предусловия из задания 2 не проверены.
- `true` при оценке ровно в половину → сравнение `<=` вместо `<`.
- `false` при корректных входах → `estimatedRows < 0` принят за ошибку там, где он равен нулю: ноль — допустимая оценка.

> **Подсказка.** Эта функция не доказывает, что индекс будет быстрее: цена случайных чтений и цена записи остаются за планом и измерением.

## Проверь себя

- Что такое селективность и почему важен знаменатель?
- Почему низкая доля не гарантирует индексный доступ?
- Откуда планировщик берёт оценку `rows` и когда она устаревает?
- Чем `EXPLAIN` отличается от `EXPLAIN ANALYZE` и когда второй опасен?
- Что означает расхождение оценки и факта в сто раз?

## Итог

- Селективность — доля от рассматриваемого множества; пороги урока — учебная модель, план решает планировщик по статистике и стоимости.
- Индексный доступ — случайные чтения; при большой доле совпадений последовательное чтение дешевле.
- Расхождение оценки и факта — вопрос о статистике и перекосе, который решают до обсуждения индекса; вопрос к плану формулируется узко.
