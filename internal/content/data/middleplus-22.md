# 22. Canary rollout, остановка и rollback

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-21`
**Цель:** Canary rollout (постепенный выпуск) направляет ограниченную часть трафика на новую версию и сравнивает сигналы по заранее заданному правилу. Плохая телеметрия или слишком маленькая выборка не подтверждают безопасность; отсутствие ошибки в малом числе запросов не равняется отсутствию риска. Rollback (откат) должен быть подготовлен заранее, совместим с данными и доступен оператору.

## Термины и перевод

- **Постепенный rollout** — Canary rollout (постепенный выпуск) направляет ограниченную часть трафика на новую версию и сравнивает сигналы по заранее заданному правилу. Плохая телеметрия или слишком маленькая выборка не подтверждают безопасность; отсутствие ошибки в малом числе запросов не равняется отсутствию риска. Rollback (откат) должен быть подготовлен заранее, совместим с данными и доступен оператору.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Канареечный выпуск (canary rollout) направляет ограниченную долю запросов или тестовую выборку на новую версию, пока её сигналы сравниваются с исходной версией. Решение «расширить», «держать», «остановить» или «откатить» имеет смысл только при заранее заданном пороге и достаточных данных.

Сначала проверьте готовность телеметрии и минимальный объём выборки; отсутствие метрик не является успешным результатом. Затем сравните одинаковые SLI и сопоставимые окна. Если новая версия меняет схему или уже записанные данные, rollback (откат) должен быть совместим с таким состоянием и иметь ясный триггер.

Примеры урока классифицируют состояние выпуска по переданным числам, boolean и статусам. Они не переключают трафик, не проверяют наблюдаемость и не запускают rollback. Значит, вывод касается только заданной политики: он не доказывает, что выпуск безопасен для реального сервиса.

## Три запускаемых примера


### Пример 1: Canary: sample adequacy, evidence readiness and exact SLO boundary

```go
package main

import "fmt"

func RolloutAction(errorPercent int, threshold int, sampleCount int, minimumSample int, evidenceReady bool) string { if errorPercent<0||errorPercent>100||threshold<0||threshold>100||sampleCount<0||minimumSample<=0{return "invalid"}; if !evidenceReady||sampleCount<minimumSample{return "hold"}; if errorPercent>threshold{return "rollback"}; return "expand" }

func main() { fmt.Println(RolloutAction(1, 5, 120, 100, true)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 2: Canary policy with explicit hold, stop, expand and rollback states

```go
package main

import "fmt"

func CanaryDecision(errorPercent int, threshold int, sampleCount int, minimumSample int, evidenceReady bool, rollbackReady bool) string { if errorPercent<0||errorPercent>100||threshold<0||threshold>100||sampleCount<0||minimumSample<=0{return "invalid"}; if !evidenceReady||sampleCount<minimumSample{return "insufficient"}; if errorPercent>threshold {if rollbackReady{return "rollback"}; return "stop"}; return "expand" }

func main() { fmt.Println(CanaryDecision(1, 5, 120, 100, true, true)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 3: Invariant: advance only with adequate evidence and within threshold

```go
package main

import "fmt"

func ContinueRollout(errorPercent int, threshold int, sampleCount int, minimumSample int, evidenceReady bool, rollbackReady bool) bool { if errorPercent<0||errorPercent>100||threshold<0||threshold>100||sampleCount<0||minimumSample<=0||!evidenceReady{return false}; if sampleCount<minimumSample||errorPercent>threshold{return false}; return true }

func main() { fmt.Println(ContinueRollout(1, 5, 120, 100, true, true)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.

## Практическая процедура

Определите минимальную выборку, окно, допустимое отклонение SLO и правило для отсутствующих/запаздывающих данных. До сравнения проверьте готовность сигналов. Если данных недостаточно, оставьте выпуск на текущей ступени; не считайте пустой график хорошим показателем.

Запишите таблицу переходов: мало данных — hold (удержать); превышен порог — stop или rollback; достаточные данные в пределах порога — expand (расширить). Выберите примеры для точной границы, недостоверной телеметрии и несовместимого отката. Для каждого укажите наблюдение и ожидаемое решение.

Примените helper к векторам и сверьте порядок приоритетов. Его результат не подтверждает трафик, миграцию или восстановимость данных. Реальный rollout требует подготовленного оператора, сравнимого источника измерений и проверенной процедуры отката; этого учебная модель не исполняет.

## Разбор сценария: Canary rollout, остановка и rollback

Опишите вымышленный, ограниченный выпуск без обращения к живому трафику: сначала проверка мониторинга, затем минимальная выборка, ожидание полного окна и оценка заданного SLI. На каждом шаге запишите, достаточно ли данных и какое правило перехода применяется. Не смешивайте число запросов с длительностью наблюдения.

Пройдите три исхода: данных пока мало; данные достаточны и порог соблюдён; порог превышен или телеметрия ненадёжна. Зафиксируйте, где политика удерживает выпуск, где расширяет ступень и где требует остановки. Перед сценарием отката перечислите предположения о совместимости схемы и уже сохранённых данных; если они неизвестны, решение должно остаться неопределённым.

В отчёте приведите входы helper и ожидаемое состояние, а также назовите всё, что он не проверяет: маршрутизацию трафика, полноту метрик, длительность окна и реальный возврат версии. Следующий шаг для работающей системы — репетиция с тестовым трафиком и проверенной процедурой восстановления.

## Лаборатория: пройти ступени canary выпуска

### Численный сценарий

Предположим, новая версия получает первые 20 запросов, а минимальная выборка задана как 100. Даже если ошибок нет, данных недостаточно для расширения. Ноль ошибок из двадцати — наблюдение, а не доказательство отсутствия риска. После набора 100 запросов пусть наблюдались 3 плохих события, а порог допуска равен 2%. Доля равна 3%, значит, согласно этому правилу выпуск следует остановить или откатить. Точное действие должно быть выбрано заранее, а helper должен отражать его приоритет.

Другой риск — сравнивать разные нагрузки. Если baseline (исходная версия) получила короткие запросы, а canary — тяжёлые, разница задержек не доказывает регрессию версии. Выберите одинаковый набор или сопоставимые сегменты. Проверяйте также readiness (готовность) телеметрии: пустой график не означает нулевую ошибку.

### Подготовьте таблицу решений

Запишите состояние мониторинга, число наблюдений, окно, долю плохих событий, совместимость миграции и допустимое действие. Сначала проверяется готовность доказательств; затем достаточность выборки; потом порог; только после этих проверок возможен переход на следующую ступень. Если порог превышен, `stop` и `rollback` — разные решения. Остановка прекращает дальнейшее расширение, а откат возвращает предыдущую версию, если это безопасно для данных.

Добавьте вариант, где метрика отсутствует, и вариант, где выборка достаточна, но окно ещё не завершено. Опишите, удерживается ли версия и кто получает решение. Не создавайте произвольное значение SLO для примера с реальным сервисом: здесь числа только условные учебные входы. Пометьте их как предположения.

### Упражнение с переходами

1. Запустите правило с недостаточной выборкой и исправной телеметрией. Ожидайте hold (удержать), а не expand.
2. Сохраните размер выборки и измените только качество телеметрии на неизвестное. Проверьте, что отсутствие сигнала не даёт разрешение.
3. Увеличьте выборку до минимума, сохраняя SLI внутри порога. Проверьте допустимое расширение.
4. Превысьте точную границу на единицу и запишите ожидаемое состояние остановки.
5. Перед откатом проверьте состояние схемы и данных; если совместимость не задана, результат должен быть «нужна проверка», а не безусловное действие.

### Сравнение и восстановление

Сравнивайте baseline и candidate (кандидат) на одинаковом окне, сопоставимом входе и одинаковом определении хорошего события. Сохраните фактические знаменатели и время сбора. Если происходит изменение трафика, деградация зависимости или пропуск телеметрии, обозначьте это как фактор, который мешает причинному выводу.

Репетиция rollback должна проверять не только возврат бинарной версии, но и совместимость уже созданных данных и сообщений. Публичные примеры урока классифицируют переданное состояние, но не направляют трафик и не выполняют восстановление. Они не подтверждают достаточность реальной выборки, точность метрик, автоматический stop или возможность отката. Следующий интеграционный этап — испытание на тестовом трафике с оператором, контрольным сигналом и заранее проверенной процедурой возврата.

### Совместимость перед откатом

Откат бинарного файла безопасен только если старый код понимает состояние, которое успела создать новая версия. Перед выпуском проверьте схему базы, формат сообщений и внешние эффекты. Часто применяют расширяющую миграцию: сначала добавляют поле, которое умеют игнорировать старые версии, затем выпускают код, а удаление старого формата откладывают. Такая последовательность снижает риск, но требует отдельной проверки на конкретной схеме.

Если новая версия уже записала несовместимые данные, возврат приложения может не восстановить прежнее поведение. План rollback должен включать обратимую миграцию или безопасное чтение старого и нового формата. Не выполняйте разрушительное преобразование до окончания периода, когда старый код ещё может вернуться. Укажите владельца данных и способ восстановления копии, если обратное преобразование невозможно.

Репетируйте остановку на стадии, когда новые запросы уже получают ответ, но расширение ещё не началось. Проверьте, кто может нажать stop, как убедиться в переключении маршрута, и какой сигнал подтверждает завершение. Helper из урока не имеет оператора, маршрутизатора или доступа к базе, поэтому он не доказывает исполнимость rollback.

### Уточните владельца и срок решения

Ступень выпуска должна иметь владельца, который может остановить расширение, и окно, в котором он получает сигнал. Автоматический переход допустим только если правило проверяет качество телеметрии и точный минимум наблюдений. Укажите, что происходит, если оператор недоступен или система мониторинга молчит; по умолчанию такой случай не является разрешением расшириться.

После перехода сохраните решение, его входные числа и версию политики. Это позволит понять, почему система расширилась или остановилась. Если порог изменили позднее, пометьте новую редакцию, а не пересчитывайте старое решение так, будто оно было принято по новым условиям. Эти управленческие и телеметрические вопросы не входят в helper, но являются частью реального rollout-контракта.

### Учитывайте длительность и сегменты

Минимум 100 событий не гарантирует, что наблюдение длилось достаточно долго. Сто запросов за секунду могут показать мгновенную проблему, но не выявить утечку памяти или периодический сбой. С другой стороны, окно в сутки для низкого трафика может задержать решение слишком надолго. Укажите оба критерия: объём и временной интервал, а также что делать, когда один из них выполнен, а второй нет.

Общая доля может скрыть сегмент, который полностью деградировал. Если продукт имеет критичные маршруты или регионы, сравните их отдельными группами с достаточной выборкой и ограниченными метками. Не создавайте неограниченную кардинальность по каждому пользователю. Изменение состава трафика тоже влияет на сравнение, поэтому фиксируйте распределение или стратифицируйте результат.

Такие решения усложняют политику, но не должны превращаться в бесконечное число правил. Назовите сегменты, которые действительно важны для пользовательского результата, и задайте условия stop до начала выпуска.

### Различайте остановку и откат

Остановка выпуска не всегда требует немедленного переключения назад: если версия не получает новых запросов, можно сначала собрать дополнительное доказательство. Но при подтверждённом нарушении порога дальнейшее ожидание способно увеличить ущерб. Укажите, какое правило выбирает между hold и rollback, и кто может изменить его при активном инциденте. В упражнении это решение остаётся политикой; helper не управляет стадиями выпуска.

## Практика Easy / Medium / Hard

**Easy — классификация.** Реализуйте первую функцию из контракта и проверьте корректный обычный случай, пустую/нулевую границу и явно невозможное значение. Результат должен точно совпасть с контрактом.

**Medium — политика с приоритетом.** Реализуйте вторую функцию. Сначала перечислите правила сверху вниз; при нескольких одновременно истинных условиях применяется первое. Добавьте тесты обычного состояния, насыщения, неизвестного значения и некорректной комбинации. Для числа/boolean не преобразуйте выход в произвольную строку.

**Hard — инвариант.** Реализуйте третью функцию, которая подтверждает только безопасную комбинацию предусловий. Граничный и противоречивый векторы обязаны отклоняться. Объясните, почему успешный результат helper не является реальным benchmark, fault test, безопасным rollout или гарантией доступности. Public и private cases находятся в JSON specs соответствующих exercise ID.
