# Воспроизводимый baseline для Go

## Что ты сделаешь

Ты напишешь три маленькие функции-политики, которые стоят в конце любого измерения: `BenchmarkDelta` считает изменение со знаком, `ComparableBaseline` отвечает, можно ли вообще сравнивать два замера, `BaselineDecision` применяет порог и называет результат. Главное же в уроке — не код, а дисциплина: как записать исходный замер (baseline) так, чтобы другой человек повторил его и мог оспорить вывод. Это подготовка к проекту P4 ScaleLab; сами функции ничего не измеряют и не доказывают ускорение сервиса.

## Какое наблюдение заставит нас передумать

Оптимизация начинается с неудобного вопроса: какое наблюдение заставит изменить решение? Без ответа команда переписывает читаемый код, крутит конфигурацию и объявляет победу по одному удачному запуску. Дисциплина измерений (measurement discipline) отделяет наблюдение от интерпретации: мы записываем входы, среду, процедуру и неопределённость, чтобы эксперимент можно было повторить.

Baseline — зафиксированное наблюдение до изменения, снятое по той же процедуре, по которой потом снимут «после». Сначала запиши ожидание обычными словами, затем сигнал, который его опровергнет. «Стало быстрее» — не проверяемо; «на фиксированном наборе входов и закреплённом toolchain распределение повторов снизилось, а результат остался корректным» — уже да.

> **Важно.** Различай изменение кода и изменение стенда. Если между «до» и «после» поменялись Go, данные или машина, сравнения нет — есть два разных эксперимента.

## У числа есть единица, источник и контекст

Длительность без единицы, счётчик без периода и процент без знаменателя читаются неверно. До эксперимента выпиши: что измеряется, каким способом, где начинается и заканчивается измеряемый участок, какие данные подаются, какие значения исключаются и по какому правилу. Число из учебного fixture называй fixture, а не наблюдением реального процесса.

Для Go-эксперимента сохраняй commit, версию Go, ОС и архитектуру, модель CPU и ограничения контейнера, команду, параметры, входные данные и число повторов. Для базы данных добавь версию сервера, схему, индексы, статистику, размер и распределение fixture, настройки пула и точный SQL. Эти сведения не делают результат универсальным — они делают его обсуждаемым.

```go group=manifest mode=run
package main

import "fmt"

type Baseline struct {
    Commit  string
    Go      string
    Command string
    Repeats int
    Unit    string
}

func (b Baseline) Complete() bool {
    return b.Commit != "" && b.Go != "" && b.Command != "" && b.Repeats > 0 && b.Unit != ""
}

func main() {
    full := Baseline{"a1b2c3d", "go1.27.2 linux/amd64", "go test -bench=Parse -count=10", 10, "ns/op"}
    partial := Baseline{Command: "go test -bench=.", Repeats: 1}
    fmt.Println(full.Complete(), partial.Complete())
}
```

Вывод:

```text
true false
```

Манифест — проверяемый список, а не заметка на память. Неполный манифест означает, что сравнение пока носит исследовательский характер; это нормально, если так и записано.

> **Типичная ошибка.** Корреляция вместо причины. Изменение совпало с лучшим числом — но возможны прогрев, планировщик ОС, соседняя нагрузка, сборка мусора, состояние кеша или просто вариация. Сильный вывод ограничен областью эксперимента: «в этих условиях наблюдалось такое различие», а не «этот вариант всегда быстрее».

## От гипотезы к измерению

Работай от гипотезы, а не от инструмента. Гипотеза связывает причину и ожидаемое наблюдение: «если основная стоимость — повторное выделение буфера, его повторное использование уменьшит число выделений, но может увеличить удерживаемую память». Здесь две проверяемые стороны, и обе нужно измерить на репрезентативном пути. Профиль не выбирает за инженера бизнес-компромисс.

Порядок один: зафиксируй baseline до правки; сделай несколько прогонов одной командой; не удаляй неудобные результаты; не меняй параллельно данные, параметры и окружение. Если прогон испорчен внешним событием, запиши причину и правило исключения заранее. Храни сырые значения рядом со сводкой: когда разброс велик относительно ожидаемого эффекта, честный вывод — «данных недостаточно», а не победа по среднему.

```go group=delta mode=run
package main

import "fmt"

func delta(before, after int64) int64 { return before - after }

func main() {
    runs := [][2]int64{{100, 90}, {100, 110}, {100, 100}}
    for _, r := range runs {
        d := delta(r[0], r[1])
        switch {
        case d > 0:
            fmt.Println(d, "сокращение")
        case d < 0:
            fmt.Println(d, "регресс")
        default:
            fmt.Println(d, "равенство")
        }
    }
}
```

Вывод:

```text
10 сокращение
-10 регресс
0 равенство
```

Положительная разность значит лишь, что второе число меньше первого. Что это означает, задают название метрики и единица: для `ns/op` меньше — лучше, для `ops/s` — наоборот.

## Центр, разброс и хвосты

Среднее чувствительно к редким большим значениям; медиана описывает центральное наблюдение, но прячет хвост; квантили показывают границы доли наблюдений, но требуют достаточной выборки и честного описания метода расчёта. Ни одна сводная статистика не заменяет исходный набор значений. Малое число прогонов не даёт судить о редких событиях, поэтому не обещай точность, которой процедура не обеспечивает.

Профиль — тоже выборка. Sampling-профиль оценивает, как часто сэмпл попадал в стек; отсутствие функции в профиле не означает нулевую стоимость. CPU-профиль отвечает на вопрос о времени под выбранной нагрузкой; heap-профиль — разный в зависимости от того, смотришь ли накопленные выделения или живые объекты на момент снимка. Сравнивай профили одного типа и одного сценария; ширина блока в картинке — средство навигации, а не доказательство.

С планом SQL так же: оценки оптимизатора — прогноз по статистике, а фактические строки и время нужны, чтобы увидеть расхождение. Не запускай разрушительные команды на чужой базе и не переноси план из случайной среды. Индекс, секционирование и чтение с реплики меняют эксплуатационные свойства, а не одно время ответа.

> **Зачем.** После наблюдения задай альтернативные объяснения и следующий различающий эксперимент. Дорогая функция в профиле — это алгоритм, число вызовов, размер входа или конкуренция? Одно изменение за раз уменьшает неоднозначность.

## Baseline как экспериментальный объект

Отдели систему, которую измеряешь, от генератора нагрузки и от машины-наблюдателя. Если один компьютер обслуживает приложение, синтезирует запросы и строит профили, конкуренция за CPU и память исказит наблюдение; в локальной лаборатории это допустимый компромисс, но его записывают. Укажи параллелизм, число worker, форму запросов, долю ошибок, период прогрева и критерий корректности: совпадение ответа, сохранённое состояние или инвариант.

Репрезентативность — не «как в production», а «входы отвечают на поставленный вопрос». Для парсера важны распределение длин и доля невалидных строк, для SQL — кардинальность и перекос ключей, для очереди — размер сообщения и поведение потребителя. Начинай с малого зафиксированного fixture и не увеличивай объём данных незаметно между сравниваемыми коммитами.

Перед сравнением задай условие остановки: максимальное время, число повторов, допустимый размер вывода. Это защита ресурса и гарантия, что сценарии не исполняются несопоставимо долго. Урок не предлагает универсальный порог успеха: критерий зависит от продукта, бюджета ошибок и стоимости изменения; в P4 решение ссылается на артефакты, а не на придуманные цифры задержки.

```go group=decision mode=run
package main

import "fmt"

func decide(before, after, minImprovement int64) string {
    if before < 0 || after < 0 || minImprovement < 0 {
        return "invalid"
    }
    d := before - after
    if d < 0 {
        return "regression"
    }
    if d >= minImprovement {
        return "candidate"
    }
    return "below_threshold"
}

func main() {
    fmt.Println(decide(100, 90, 5), decide(100, 98, 5), decide(100, 110, 5), decide(-1, 0, 5))
}
```

Вывод:

```text
candidate below_threshold regression invalid
```

`candidate` — результат таблицы решений, не вердикт. Он не утверждает, что изменение безопасно, статистически убедительно или готово к выпуску.

## Типичные ошибки

- Измерять слишком короткий путь, который не соответствует операции пользователя: уточни границу и проверь, не вынесена ли подготовка за таймер по ошибке.
- Сравнивать разные входы, планы, профили или версии среды: вернись к артефактам и повтори на одинаковой процедуре.
- Подменять наблюдения единственным средним: храни повторения и сообщай их число.
- Считать профиль причинным доказательством: он локализует кандидата, после чего гипотезу меняют и измеряют тот же сценарий.
- Делать глобальный вывод из локального fixture: перечисли ограничения и сценарии, нужные для более широкого утверждения.
- Внедрять оптимизацию без проверки семантики: функциональные и граничные проверки до и после, отдельно память, сложность и путь отката.

## Самостоятельная лаборатория

Заведи таблицу наблюдений с колонками `run`, `value`, `unit`, `input_id`, `environment`, `note` и заполни её только реально полученными данными либо явно помеченными учебными числами — не смешивай. Посчитай сводку независимо, проверь руками крайние и пустые случаи. Запиши гипотезу, что она поддерживает, чего не доказывает и какое наблюдение изменит решение. Для проектов с внешней базой используй только одноразовую локальную среду; если её нет — синтетический fixture с честной пометкой, что интеграционная проверка не выполнялась.

Перед тем как принять результат, дай коллеге карточку: вопрос, закреплённое состояние, процедура, единица, условие остановки. Попроси пересказать, что измерялось, не показывая твою интерпретацию. Если он делает более сильный вывод, чем ты, — уточни текст; если вывод расходится при точном повторе — сравни артефакты и окружение до новой правки.

## Если что-то пошло не так

- `missing return at end of function` → у функции решения нет последнего `return` для случая «ниже порога».
- Красный закрытый пример с `minImprovement = -1` → проверка на отрицательные значения должна покрывать все три аргумента и стоять первой.
- Красный пример `(100, 98, 5)` → порог сравнивается строго (`>`), а нужно «не меньше» (`>=`).
- `false` вместо `true` в задании 2 → пропущено одно из трёх условий или использовано `||` вместо `&&`.
- `import … is not allowed` → импорты в заданиях урока запрещены: это арифметика и логика над аргументами.

## Практика

Три функции без `main` и печати; среда вызывает их и показывает результаты строками JSON. Числа и `bool` показываются как есть, строки — в кавычках.

### Задание 1 · Easy: вычисли signed delta baseline

**Цель.** Вернуть `before - after` в тех же единицах: положительное число — длительность сократилась, отрицательное — регресс, ноль — равенство.

**Ожидаемый вывод** — для `(100, 90)` и `(100, 110)`:

```text
10
-10
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func BenchmarkDelta(before, after int64) int64`. Импорты запрещены.
2. Замени `panic("TODO")` на `return before - after`.
3. «Запустить», сравни знак. «Проверить» — закрытые примеры: `(0, 0)` → `0`, `(1, 0)` → `1`.

**Как проверить себя.** Знак соответствует направлению: `after` меньше `before` — число положительное; единица та же, что у входов; это не модуль разности и не процент.

**Если не принято.**
- `-10` и `10` поменялись местами → вычитание в другом порядке: нужно именно `before - after`.
- Ответ всегда положительный → ты взял модуль; знак — часть контракта.

> **Подсказка.** Оба входа неотрицательны и не превосходят `MaxInt64`, поэтому вычитание не переполняется — лишних проверок не нужно.

### Задание 2 · Medium: проверь сопоставимость baseline

**Цель.** Вернуть `true` только когда workload зафиксирован, единицы совпадают и среда сопоставима — все три отметки одновременно.

**Ожидаемый вывод** — для `(true, true, true)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ComparableBaseline(validWorkload, sameUnit, sameEnvironment bool) bool`. Импорты запрещены.
2. Верни `validWorkload && sameUnit && sameEnvironment`.
3. «Запустить», «Проверить» — закрытые примеры: `(true, false, true)` → `false`, `(false, true, true)` → `false`.

**Как проверить себя.** Любая ложная отметка даёт `false`; функция оценивает только переданные флаги и не проверяет саму среду.

**Если не принято.**
- Закрытый пример даёт `true` при одной ложной отметке → использовано `||` или одно условие пропущено.
- `panic("TODO")` в «Результате» → стартовый код не заменён.

> **Подсказка.** Это чеклист из трёх пунктов; «сопоставимо» значит «все три», а не «большинство».

### Задание 3 · Hard: примени порог решения к измеренной дельте

**Цель.** По `before`, `after` и минимальному выигрышу вернуть `invalid`, `regression`, `candidate_improved` или `below_threshold`.

**Ожидаемый вывод** — для `(100, 90, 5)`:

```text
"candidate_improved"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func BaselineDecision(before, after, minImprovement int64) string`. Импорты запрещены.
2. Первой проверкой: если любой из трёх аргументов отрицателен — `"invalid"`.
3. Посчитай `delta := before - after`: при `delta < 0` — `"regression"`; при `delta >= minImprovement` — `"candidate_improved"`; иначе — `"below_threshold"`.
4. «Запустить», «Проверить» — закрытые примеры: `(100, 98, 5)` → `below_threshold`, `(100, 110, 5)` → `regression`, `(100, 90, -1)` → `invalid`.

**Как проверить себя.** Порядок веток: сначала валидность, потом знак, потом порог; выигрыш ровно в `minImprovement` — уже `candidate_improved`.

**Если не принято.**
- Красный закрытый пример `(100, 90, -1)` → отрицательный порог не проверен или проверка стоит после вычисления дельты.
- `below_threshold` вместо `regression` → сравнение с порогом раньше проверки знака.
- `regression` для дельты, равной порогу → строгое `>` вместо `>=`.

> **Подсказка.** Четыре ветки — три `if` и последний `return`; порядок веток и есть политика.

## Итог

- Baseline — манифест: commit, toolchain, среда, команда, входы, повторы, единица; без него сравнения нет.
- Храни сырые значения, смотри центр, разброс и хвосты; профиль и план SQL локализуют кандидата, но не доказывают причину.
- Функции урока — политика над числами: знак дельты, чеклист сопоставимости, порог решения; ускорение сервиса они не доказывают.
