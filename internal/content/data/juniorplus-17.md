# Конфигурация, логи и OpenAPI

## Что ты сделаешь

Ты напишешь три проверки, которые относятся к запуску и наблюдаемости сервиса: `ConfigValid` отклонит неполную конфигурацию, `LogFieldAllowed` разрешит только безопасные поля журнала, `ReadinessState` различит готовность и доступность процесса. Функции получают уже измеренные значения: они не открывают соединение, не пишут журнал и не отвечают по HTTP.

## Конфигурация — входные данные, а не исходный код

Конфигурация описывает, как запустить программу локально, в тесте или в другой среде: адрес listener, разрешённый Origin браузера, URL PostgreSQL, лимиты и таймауты. Секретное значение приходит из окружения или хранилища секретов, а не из коммита, примера в документации или обычного журнала. Файл `.env.example` содержит имена и безопасный placeholder; локальный `.env` исключён из Git.

Проверяй обязательные значения при старте и завершай запуск безопасной категорией ошибки. Пустой DSN не должен выглядеть как готовность. Но формат значения и работа сервиса — разные вопросы: корректно разобранный URL не доказывает, что PostgreSQL работает, пароль подходит и миграции прошли. Reference P2 `LoadConfig` требует `LINKHUB_DATABASE_URL` и нормализует Origin; открытие соединения и миграции выполняются отдельно.

Пример проверки обязательного значения. Ошибка называет переменную, но не её значение:

```go
package main

import "fmt"

func required(name, value string) error {
    if value == "" {
        return fmt.Errorf("%s is required", name)
    }
    return nil
}

func main() {
    fmt.Println(required("LINKHUB_DATABASE_URL", ""))
}
```

Вывод: `LINKHUB_DATABASE_URL is required`. Имя переменной попало в текст, а значение в тексте не появилось.

> **Важно.** При ошибке подключения не печатай DSN: в его user-info часто лежат имя пользователя и пароль.

## Логи по allowlist

Структурированный журнал отделяет имя поля от значения. Это упрощает фильтрацию, но не защищает приватность: строка JSON с паролем всё равно раскрывает пароль. Начни с небольшого allowlist: `request_id`, `method`, `status` и `duration_ms`. LinkHub reference пишет именно такие поля и не записывает query, headers или body.

Deny-list известных имён проигрывает новому полю, которого автор не предвидел. Allowlist требует явного решения для каждого имени. Не записывай `Authorization`, `Cookie`, session token, CSRF token, полный query string, DSN и payload.

Пример разрешённых полей:

```go
package main

import "fmt"

var allowed = map[string]bool{
    "request_id":  true,
    "method":      true,
    "status":      true,
    "duration_ms": true,
}

func main() {
    fmt.Println(allowed["status"], allowed["cookie"])
}
```

Вывод: `true false`. Поле, которого нет в списке, не получает разрешения по умолчанию.

> **Типичная ошибка.** Писать путь запроса с реальным идентификатором. Даже `/links/42` может быть персональным; вместо фактического пути логируй известную форму маршрута, например `/links/{id}`.

## OpenAPI — машинно-читаемое обещание HTTP

OpenAPI описывает путь, method, безопасность, параметры, форму body и возможные responses. Контракт P2 лежит в `content/projects/p2/openapi.yaml`; README, примеры и фактические handlers должны совпадать с ним. Если создать ссылку можно только с ответом 201, а конфликт даёт 409, это должно быть записано в договоре.

Описание не доказывает поведение. Строка `security` показывает обещанную cookie-схему, но не тестирует middleware или проверку владельца. Машинная проверка drift полезна, только если её реально запускают: не называй YAML актуальным по одному файлу или grep.

## Health и readiness — разные сигналы

Health check сообщает, жив ли процесс. Readiness отвечает, готово ли приложение принять рабочий запрос с нужными зависимостями. HTTP 200 у health URL не доказывает доступность каждой таблицы, а ping базы не доказывает корректность всего API.

В текущем P2 OpenAPI описывает `GET /healthz` как process health с телом `status: ok`. Отдельного readiness endpoint там нет, и в этой главе его не нужно выдумывать. Пример того, как состояние превращается в ответ:

```go
package main

import "fmt"

func state(connected bool) string {
    if !connected {
        return "not_ready"
    }
    return "ready"
}

func main() {
    fmt.Println(state(false), state(true))
}
```

Вывод: `not_ready ready`. Функция получает уже измеренное состояние и сама ничего не проверяет.

> **Важно.** Readiness показывает состояние только в момент проверки. База может стать недоступной через миллисекунду, поэтому обработчики всё равно должны корректно переживать timeout и отказ зависимости.

## Проследить настоящий P2

Прочитай `content/projects/p2/reference/config.go`, `main.go`, `http.go` и OpenAPI. Сначала переменные окружения проверяются без вывода секрета; запуск ограничивает контекст и открывает PostgreSQL; pool применяет миграции; handler получает logger; ответ уходит обратно по HTTP. В журнал попадают разрешённые поля, а ошибка подключения превращается в короткую категорию.

Сравни это с `.env.example` и `.gitignore`, не копируя значение пароля. Easy-задание проверяет только синтаксис DSN и Origin и не входит в базу. Medium разрешает имена полей, но не запускает handler. Hard сводит уже известные сигналы и не измеряет readiness. Для реального поведения нужны config tests, HTTP tests и проверка drift между OpenAPI и сервером.

## Если что-то пошло не так

- Пароль попал в текст ошибки старта → DSN печатается целиком; оставь внутреннюю категорию без user-info.
- Новое поле появилось в журнале без объяснения → убери его из allowlist и добавь тест с безопасным fixture.
- Health описан как гарантия готовности базы → проверь точный контракт `/healthz` и порядок запуска.
- `undefined: url` → импорт `"net/url"` не добавлен.

## Практика

Три задания. Функции проверяются на входах из блока «Ожидаемый вывод»; закрытые примеры видны только в «Проверить». Соединения с базой, HTTP и журналы не используются.

### Задание 1 · Отклони неполную конфигурацию

**Цель.** Вернуть `true`, если `databaseURL` разбирается как URL со схемой `postgres` или `postgresql` и непустым host, а `origin` — абсолютный `http` или `https` origin без userinfo, пути (кроме `/`), query и fragment. Иначе `false`.

**Ожидаемый вывод** — входы: корректные DSN и Origin, затем пустой DSN:

```text
true
false
```

**Шаги.**
1. Выбери задание «Отклони неполную конфигурацию»: в файле есть `ConfigValid` с `panic("TODO")`. Добавь импорты, которые используешь: `"net/url"` и, при необходимости, `"strings"`.
2. Разбери `databaseURL` через `url.Parse`; при ошибке верни `false`.
3. Проверь схему и непустой host у DSN.
4. Проверь у `origin` схему `http` или `https`, отсутствие userinfo, query и fragment, и пустой путь или `/`.
5. Верни `true`, только если все условия выполнены.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** `true` и `false`; все три критерия зелёные.

**Если не принято.**
- Пустой DSN даёт `true` → непустой host обязателен.
- Origin с путём `/links` принят → путь допустим только пустой или `/`.
- Origin с `user:pass@` принят → userinfo запрещён.

> **Подсказка.** Сначала ошибка разбора, потом DSN, потом Origin.

### Задание 2 · Оставь в журнале только разрешённые поля

**Цель.** Вернуть `true` для `request_id`, `method`, `status` и `duration_ms` и `false` для любого другого имени, включая `path`, `cookie` и `Authorization`.

**Ожидаемый вывод** — входы: `request_id`, `Authorization`, затем `status`:

```text
true
false
true
```

**Шаги.**
1. Выбери задание «Оставь в журнале только разрешённые поля»: в файле есть `LogFieldAllowed` с `panic("TODO")`. Импорты не нужны.
2. Сравни `name` с каждым из четырёх разрешённых имён точно, с учётом регистра.
3. Если совпало с одним из них, верни `true`.
4. Иначе верни `false`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Три значения; все три критерия зелёные.

**Если не принято.**
- `Authorization` принят → заголовок не входит в список.
- `Status` с заглавной буквой принят → имена журнала регистрозависимы.
- `path` принят → путь запроса не входит в разрешённые поля.

> **Подсказка.** Удобен `switch` с четырьмя значениями и веткой `default`.

### Задание 3 · Отдели готовность от доступности процесса

**Цель.** Вернуть `"not_ready"`, если база недоступна. Иначе `"migrations_pending"`, если миграции не актуальны. Иначе `"ready"`.

**Ожидаемый вывод** — входы: база недоступна, затем подключена с неактуальными миграциями, затем подключена и актуальна:

```text
"not_ready"
"migrations_pending"
"ready"
```

**Шаги.**
1. Выбери задание «Отдели готовность от доступности процесса»: в файле есть `ReadinessState` с `panic("TODO")`. Импорты не нужны.
2. Если `databaseConnected` равно `false`, верни `"not_ready"`.
3. Если `migrationsCurrent` равно `false`, верни `"migrations_pending"`.
4. Иначе верни `"ready"`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Три строки в кавычках; все три критерия зелёные.

**Если не принято.**
- База недоступна, миграции актуальны, а ответ `"ready"` → сначала проверяется соединение.
- Подключённая база с неактуальными миграциями даёт `"ready"` → миграции тоже блокируют готовность.

> **Подсказка.** Порядок важен: сначала база, потом миграции, и только потом `"ready"`.

## Итог

- Конфигурация проверяется при старте; ошибка называет переменную, но не раскрывает значение.
- Журнал пишет только поля из allowlist; `Authorization`, cookie и DSN в него не попадают.
- Health говорит о процессе, readiness — о готовности с зависимостями; OpenAPI описывает обещание HTTP, но не доказывает его выполнение.
- Оценка главы — это только самостоятельное evidence по критериям курса; автоматические тесты, human review и внешнее подтверждение — отдельные процессы.
