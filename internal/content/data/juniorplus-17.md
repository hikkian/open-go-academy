## Конфигурация — входные данные, а не исходный код

Конфигурация описывает, как запустить одну программу локально, в тесте или в другой среде. Типичные значения — адрес listener, разрешённый Origin браузера, URL PostgreSQL, лимиты и таймауты. Секретное значение должно прийти из локального окружения или подходящего хранилища секретов, а не из коммита, API ответа, учебного примера или обычного журнала. Файл .env.example содержит имена и безопасный placeholder; локальный .env исключён Git. Вставлять credential в репозиторий, screenshot или chat transcript нельзя.

Проверяйте обязательные значения на старте и завершайте запуск с безопасной категорией ошибки. Пустой DSN не должен выглядеть как успешная готовность до первого запроса. Но формат значения и работа сервиса — разные вопросы. Разобранный URL не подтверждает, что PostgreSQL работает, credential подходит, миграции завершились и текущая операция проходит. Reference P2 LoadConfig требует LINKHUB_DATABASE_URL и нормализует Origin; OpenPG отдельно открывает соединение и применяет миграции. При ошибке connection не печатайте DSN: в его user-info часто лежат имя и пароль.

Не принимайте значения окружения как типобезопасные только потому, что они строковые. Проверяйте допустимые схему и host, границы чисел, режим cookie и обязательный секрет без его эха. Если список разрешённых Origin должен содержать один URL, произвольный путь/query/fragment меняет смысл политики. Объясняйте разницу между отсутствующим значением, некорректным форматом и доступной, но ещё не мигрированной базой. Чем раньше ошибочная конфигурация выявляется, тем проще воспроизвести её без пользовательского запроса.

## Логи по allowlist

Структурированный журнал отделяет имя поля от значения. Это упрощает фильтрацию и корреляцию, но само по себе не защищает приватность. JSON строка с password всё равно раскрывает пароль. Начните с небольшого allowlist: request_id, method, status, route template и длительность, когда каждое поле оправдано. LinkHub reference пишет request_id, method, status и duration; он не записывает query, headers или body.

Не записывайте Authorization, Cookie, session token, CSRF token, полный query string, DSN и payload. Deny-list известных имён проигрывает новому секретному полю, которого автор не предвидел. Allowlist требует явного решения для каждой новой записи. Если поле необходимо для диагностики, проверьте источник, максимальную длину, возможность подстановки человеком и место downstream хранения. Случайный control character может испортить текстовую запись; структурированный encoder помогает сохранить форму, но не делает содержимое допустимым.

Вместо полного URL используйте известную форму маршрута, например /links/{id}, если она существует. ID может быть персональным или чувствительным, поэтому даже path не автоматически безопасен. Не логируйте тело ради отладки ошибки JSON. Тест с fixture secret проверяет, что точная строка не попала в output, но ещё нужен обзор схемы, exporter, уровня доступа и срока хранения журналов. Публичный API error отвечает стабильной короткой категорией, подробность остается внутри безопасной диагностической границы.

## OpenAPI — машинно-читаемое обещание HTTP

OpenAPI описывает путь, method, security, параметры, форму body и возможные responses. P2 contract лежит в content/projects/p2/openapi.yaml; README, примеры и фактические handlers должны совпадать с ним. Если создать ссылку можно только с ответом 201 или конфликт даёт 409, это должно быть отражено в договоре. Если PATCH требует полное представление, описание required полей должно быть точным. Неполное описание приводит к клиентам, которые не умеют предсказуемо обработать легальный ответ.

Проверяйте additionalProperties, required fields, ограничения длины, формат UUID, body bounds, cookie auth и CSRF header. Пример должен содержать только фиктивные values, не реальный session или пароль. Description может объяснить редирект, но не доказывает что handler проверяет enabled флаг. Security scheme показывает обещанную схему cookie, но не тестирует middleware или ownership predicate. Машинная проверка drift полезна только если она действительно запускается; не называйте YAML актуальным на основе одного grep.

Решите, кто обновляет договор, когда меняется API. Хороший review сравнивает один route в OpenAPI, handler, тестах и прикладной инструкции. Полезно написать короткий acceptance test на method/status/header/body semantics, затем сверить ограничения schema. Не пытайтесь описать всю внутреннюю реализацию: контракт публикует observable behavior. SQL column names, скрытый checker state и значения секретов не должны попадать туда без причины.

## Health и readiness — разные сигналы

Health check сообщает, жив ли процесс или базовая часть приложения. Readiness отвечает, готово ли оно взять реальный запрос с необходимой схемой и зависимостями. HTTP 200 у health URL не доказывает доступность каждой таблицы, а database ping не доказывает корректность полного API. Формулируйте точное содержание probe вместо расплывчатого «всё здорово».

Текущий P2 OpenAPI описывает GET /healthz как process health и простое тело с status=ok. В reference миграции применяются через OpenPG до того, как начинает слушать HTTP server, но отдельного readiness endpoint в OpenAPI нет. В этой главе не добавляйте вымышленный URL. Можно нарисовать будущую readiness схему, назвать сигналы и предложить contract, однако отличайте предложение от существующей реализации.

Readiness показывает состояние только сейчас. База может стать недоступной через миллисекунду, поэтому обработчики всё равно должны корректно переживать timeout и отказ зависимости. В distributed deployment система может исключить неготовый экземпляр из трафика, не перезапуская живой процесс; проектный local setup устроен проще. Не раскрывайте диагностические подробности DB всем внешним клиентам через health response.

## Проследить настоящий P2

Прочитайте content/projects/p2/reference/config.go, main.go, http.go и OpenAPI. Сначала env валидируется без вывода секрета; startup ограничивает контекст и открывает PostgreSQL; pool мигрирует схему; handler создаётся с logger; response идёт назад по HTTP. В лог попадают разрешённые поля, а connection failure превращается в краткую категорию. Сверьте это с `.env.example`, `.gitignore` и contract, не копируя значение пароля.

Easy задание проверяет синтаксическую форму DSN и Origin, но не пытается войти в DB. Medium разрешает имена полей, но не запускает handler. Hard сводит уже известные сигналы и не измеряет readiness. Для реального поведения нужны config tests, HTTP tests, проверка drift между OpenAPI и сервером, а также review полей журнала. Такая граница нужна намеренно: детерминированное упражнение не может честно обещать зависимость, которой оно не подключает.

При диагностике ошибки запуска разложите путь: локальный env файл создан? placeholder изменён? Origin проходит validation? endpoint БД доступен? миграция применена? HTTP слушает ожидаемый адрес? Не раскрывайте значение, чтобы ответить на эти вопросы. Режимы readiness должны быть различимы внутри тестовой системы и по возможности безопасны внешнему клиенту. Если log показал query token, исправьте allowlist, добавьте регрессионный fixture и проверьте exporter.

После практики запишите для проекта список required env имен, политику выдачи ошибки, поля журнала, точный смысл health URL и отличия от readiness. Для каждого утверждения укажите файл и тест. Такой короткий evidence map связывает API documentation, операционный запуск и безопасность в целое.

## Три законченных запускаемых Go-примера

### Origin

```go group=origin mode=run
package main

import ("fmt";"net/url")

func valid(raw string) bool { u,e:=url.Parse(raw);return e==nil && (u.Scheme=="http" || u.Scheme=="https") && u.Hostname()!="" && u.User==nil && (u.Path=="" || u.Path=="/") && u.RawQuery=="" && u.Fragment=="" }
func main(){fmt.Println(valid("http://127.0.0.1:8097"),valid("https://example.test/path"))}
```

Это полная программа со стандартным импортом, package main и main. Она использует только фиксированные локальные значения: не читает секреты окружения, не соединяется с сетью и не утверждает, что проверила сервис. Запустите пример и измените ровно одну входную величину.

### Allowlist

```go group=allowlist mode=run
package main

import "fmt"

func allow(key string) bool { switch key {case "request_id","method","status","duration_ms":return true;default:return false} }
func main(){fmt.Println(allow("status"),allow("cookie"))}
```

Это полная программа со стандартным импортом, package main и main. Она использует только фиксированные локальные значения: не читает секреты окружения, не соединяется с сетью и не утверждает, что проверила сервис. Запустите пример и измените ровно одну входную величину.

### Readiness

```go group=readiness mode=run
package main

import "fmt"

func ready(db,migrated bool) bool{return db&&migrated}
func main(){fmt.Println(ready(false,true),ready(true,false),ready(true,true))}
```

Это полная программа со стандартным импортом, package main и main. Она использует только фиксированные локальные значения: не читает секреты окружения, не соединяется с сетью и не утверждает, что проверила сервис. Запустите пример и измените ровно одну входную величину.

## E / M / H: практика функции

- **Easy: Отклони неполную конфигурацию.** Верни true, если databaseURL разбирается как URL со схемой postgres/postgresql и непустым host; origin — абсолютный http/https origin без userinfo, path (кроме /), query и fragment. Не возвращай и не логируй исходные строки. Это синтаксическая проверка, не проверка доступности БД.
- **Medium: Оставь в журнале только разрешённые поля.** Разреши ровно request_id, method, status и duration_ms. Не включай path, query, headers, cookies, body, DSN, пароль или токен. Это проверяет helper allowlist; реальную запись и отсутствие secret fixtures нужно проверять отдельным log test.
- **Hard: Отдели готовность от доступности процесса.** Если база недоступна — not_ready; иначе если миграции не актуальны — migrations_pending; иначе ready. Helper обрабатывает уже измеренные состояния и сам не выполняет ping, healthcheck или миграцию. HTTP listener может отвечать, когда зависимость ещё не готова.

Function grader компилирует доверенный код и сравнивает JSON для public/hidden cases. Он запускает только helper и не исполняет PostgreSQL, Compose, HTTP API или review rubric. Названия ready, allow и reviewed_evidence принадлежат малой таблице решений этой функции; не выдавайте их за полный security pass.

## Типичные ошибки и диагностика

- Дампится DSN при ошибке старта. Оставьте внутреннюю категорию без user-info.
- OpenAPI объявлен «тестом», хотя запускался только YAML parse. Выполните реальный schema-contract test.
- Health endpoint описан как гарантия DB readiness. Найдите его точный контракт и startup flow.
- Появился новый log field без объяснения. Уберите его до теста с безопасными fixtures.

## Повторение и глоссарий

Проследите полный путь проекта от публичного HTTP ответа назад к handler, context, repository, transaction и configuration. Для каждого участка назовите файл, команду или test, который даёт evidence. Отдельно назовите неизвестное, требующее человека, и boundary, которая не проверялась. Не расширяйте claim за пределы наблюдаемого результата.

- **configuration (конфигурация)** — Проверенные значения окружения, определяющие запуск приложения.
- **secret (секрет)** — Значение, раскрытие которого даёт доступ или раскрывает защищённые данные.
- **structured_log (структурированный журнал)** — Запись полей и значений по явной схеме.
- **OpenAPI (OpenAPI)** — Машиночитаемый контракт путей, параметров, запросов и ответов HTTP API.
- **health_check (проверка здоровья)** — Сигнал с явно описанным смыслом о состоянии процесса или приложения.
- **readiness (готовность)** — Состояние приложения, когда оно может принимать рабочий запрос с нужными зависимостями.

Оценка главы означает только самостоятельное evidence по критериям курса. Automatic tests, human review и внешнее профессиональное подтверждение являются отдельными процессами.
