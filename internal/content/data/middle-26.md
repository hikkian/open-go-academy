## Зачем эта тема нужна

Backend-операция часто проверяет ввод, меняет несколько связанных записей и возвращает стабильную доменную причину отказа. Важно не только выбрать итоговую строку, но и проверить порядок вызовов: не начинать работу для неверного запроса, не фиксировать неуспешное изменение и освобождать незавершённый ресурс.

В этой главе мы отделяем контракт приложения от гарантий хранилища. Упражнения используют интерфейсы и контролируемые fake-объекты: они дают заданные ответы и записывают вызовы. Это позволяет детерминированно проверить протокол кода. Fake не запускает SQL, не моделирует поведение драйвера, конкурентные транзакции, isolation или ACID. Подтверждение этих свойств требует отдельного интеграционного теста с выбранной реальной базой.

## Сначала определим границу

Validation (валидация) проверяет форму и допустимые значения до побочного эффекта. Domain error (доменная ошибка) называет продуктовую причину стабильным кодом вроде `conflict` или `not_found`. Handler переводит эту категорию в безопасный HTTP-ответ и не раскрывает текст драйвера, SQL, DSN или stack trace.

Транзакционный протокол в примерах имеет этапы Begin → Apply → Commit. При конфликте, ошибке изменения или неизвестном результате Apply вызывается Rollback, а Commit пропускается. Если Commit сообщает об ошибке, результат может быть неопределённым; попытка Rollback не доказывает, что commit не произошёл. Проверка уникальности только в приложении также не защищает от гонки: constraint базы и преобразование типизированной ошибки остаются отдельными обязанностями адаптера хранения.

Easy проверяет validation до Begin. Medium добавляет изменение, доменные категории, commit и cleanup. Hard дополнительно наблюдает точный trace fake-операций. Никакой из уровней не утверждает атомарность реальной БД или атомарность внешнего API вместе с SQL; для внешней публикации нужен отдельный протокол, например outbox.

## Easy: validation до Begin

Интерфейс намеренно мал: `Begin` сообщает, удалось ли получить управляемую транзакцию. Неверный ввод должен завершиться до вызова метода. На этом уровне запись и commit ещё не моделируются.

```go group=middle-26-easy mode=run
package main
import "fmt"

type BeginnerEasy interface { Begin() bool }
func ValidationBoundaryEasy(valid bool, tx BeginnerEasy) string {
	if !valid { return "invalid" }
	if tx == nil { return "dependency_missing" }
	if !tx.Begin() { return "begin_failed" }
	return "ready_to_write"
}
type fakeBeginner struct { calls int; ok bool }
func (f *fakeBeginner) Begin() bool { f.calls++; return f.ok }
func main() {
	fake := &fakeBeginner{ok:true}
	fmt.Printf("%s:%d\n", ValidationBoundaryEasy(false, fake), fake.calls)
}
```

Ожидаемый результат — `invalid:0`: fake подтверждает, что `Begin` не вызывался. Это наблюдение относится только к данному вызову модели.

## Medium: изменение и доменный исход

Добавьте методы `Apply`, `Commit` и `Rollback`. Только `ok` разрешает Commit. Конфликт, ошибка записи и неизвестный код приводят к Rollback и безопасному outcome. При ошибке Commit возвращайте `commit_outcome_unknown`: локальный интерфейс не может определить состояние настоящего сервера базы после потери ответа.

```go group=middle-26-medium mode=run
package main
import "fmt"

type TransactionMedium interface {
	Begin() bool
	Apply() string
	Commit() bool
	Rollback()
}
func RunTransactionMedium(valid bool, tx TransactionMedium) string {
	if !valid { return "invalid" }
	if tx == nil { return "dependency_missing" }
	if !tx.Begin() { return "begin_failed" }
	switch tx.Apply() {
	case "ok":
	case "conflict": tx.Rollback(); return "conflict"
	case "write_failed": tx.Rollback(); return "write_error"
	default: tx.Rollback(); return "internal_error"
	}
	if !tx.Commit() { tx.Rollback(); return "commit_outcome_unknown" }
	return "committed"
}
type fakeTransaction struct { apply string; commit bool }
func (f fakeTransaction) Begin() bool { return true }
func (f fakeTransaction) Apply() string { return f.apply }
func (f fakeTransaction) Commit() bool { return f.commit }
func (f fakeTransaction) Rollback() {}
func main() { fmt.Println(RunTransactionMedium(true, fakeTransaction{apply:"conflict",commit:true})) }
```

Ожидаемый результат — `conflict`. В grading fake задаёт исход операции; Hard отдельно проверяет фактический порядок вызовов.

## Hard: наблюдаемый failure trace

Hard использует тот же протокол. Функция возвращает только категорию (`committed`, `conflict`, `write_error`, `internal_error`, `begin_failed`, `commit_outcome_unknown`, `dependency_missing` или `invalid`). Grader driver независимо записывает каждый вызов fake и добавляет наблюдаемый trace к категории в формате `outcome:op1,op2`. Успешный путь — `committed:begin,apply,commit`; конфликт — `conflict:begin,apply,rollback`; неверный ввод — `invalid:`. При ошибке записи ожидается Rollback без Commit. Commit failure оставляет неизвестный результат и может сопровождаться только best-effort попыткой Rollback.

```go group=middle-26-hard mode=run
package main
import "fmt"

type TransactionHard interface {
	Begin() bool
	Apply() string
	Commit() bool
	Rollback()
}
func RunTransactionHard(valid bool, tx TransactionHard) string {
	if !valid { return "invalid" }
	if tx == nil { return "dependency_missing" }
	if !tx.Begin() { return "begin_failed" }
	switch tx.Apply() {
	case "ok":
	case "conflict": tx.Rollback(); return "conflict"
	case "write_failed": tx.Rollback(); return "write_error"
	default: tx.Rollback(); return "internal_error"
	}
	if !tx.Commit() { tx.Rollback(); return "commit_outcome_unknown" }
	return "committed"
}
type fakeTransaction struct { events []string }
func (f *fakeTransaction) Begin() bool { f.events=append(f.events,"begin"); return true }
func (f *fakeTransaction) Apply() string { f.events=append(f.events,"apply"); return "conflict" }
func (f *fakeTransaction) Commit() bool { f.events=append(f.events,"commit"); return true }
func (f *fakeTransaction) Rollback() { f.events=append(f.events,"rollback") }
func main() { f:=&fakeTransaction{}; outcome:=RunTransactionHard(true,f); fmt.Printf("%s:%v\n",outcome,f.events) }
```

Функция возвращает только `conflict`; driver отдельно наблюдает ожидаемый trace `[begin apply rollback]` и соединяет его с категорией для проверки. Grader также проверяет, что invalid не вызывает методов, ошибка `Begin` останавливает путь, а failure после Begin не приводит к Commit. Этот fake проверяет лишь вызовы интерфейса. Он не подтверждает, что конкретный SQL-драйвер выполнил откат или что несколько строк атомарны.

## Что проверять в интеграции отдельно

На выбранной реальной БД отдельные integration tests должны проверить constraint при конкурирующих запросах, ошибку после первого изменения, наблюдаемое состояние с нового соединения после rollback, успешный commit нескольких изменений и неопределённый ответ при сбое commit. Зафиксируйте версию БД, драйвер, конфигурацию и процедуру очистки. Вызов внешнего API не становится частью SQL-транзакции автоматически.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy проверяет отсутствие Begin для invalid; Medium — мутацию, доменный отказ и commit/rollback; Hard — точную последовательность вызовов fake. Эти grader-векторы не являются интеграционным тестом базы. Отдельно проверьте constraint, rollback после частичного изменения и состояние после ошибки commit на выбранном драйвере.

## Итог и повторение

Теперь вы умеете описать ограниченную модель темы «Валидация, доменная ошибка и транзакция», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `middle-25`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **domain error (доменная ошибка)** — Стабильная категория ошибки правила продукта.

- **transaction (транзакция)** — Атомарная группа операций базы данных.

- **rollback (откат)** — Отмена незавершённых изменений транзакции.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «Валидация, доменная ошибка и транзакция» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «invalid не вызывает Begin; успешный путь вызывает Begin → Apply → Commit; отказ после Begin вызывает Rollback и не вызывает Commit». Fake позволяет повторить этот протокол, но не показывает, восстановится ли состояние реальной базы. Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Матрица ошибок и транзакционный cleanup

Прежде чем писать HTTP mapping, определите стабильные категории: invalid input, conflict, not found и internal failure. Маппинг должен быть исчерпывающим и безопасным: неизвестный код — общий 500, а не текст ошибки драйвера. Клиент получает request ID для поддержки; внутренний лог связывает его с очищенными деталями. Не возвращайте SQL constraint name, credentials, адрес базы или пользовательский payload.

У транзакции есть явные стадии: начать, выполнить проверки и изменения, commit; при любой ошибке до commit вызвать rollback. Ошибка commit тоже означает, что результат может быть неизвестен клиенту: не предполагайте без доказательств, что изменения точно отсутствуют. Повтор команды требует idempotency key либо способа прочитать результат. Уникальное ограничение должно существовать в базе, потому что предварительное чтение не предотвращает две конкурентные записи.

Сценарии интеграции проверяют invalid input до открытия транзакции, конфликт constraint, ошибку записи после первого изменения, ошибку commit и успешное изменение нескольких строк. После каждого отказа прочитайте состояние с нового соединения и убедитесь, что инвариант сохранён. Для внешней публикации проверьте outbox отдельно: запись события и доменная запись фиксируются вместе, relay публикует повторяемо, consumer дедуплицирует. Упражнения Middle-26 измеряют только вызовы интерфейса на fake. Они не измеряют факт успешного SQL commit, isolation или атомарность.


При тайм-ауте (`timeout`) транзакция могла зафиксироваться (`commit`), даже если ответ потерялся; повторяйте критичную команду только с ключом идемпотентности (`idempotency key`). Ошибку ограничения (`constraint`) переводите в доменную категорию по коду драйвера, а не по свободному тексту.


Ошибка ограничения (`constraint error`) превращается адаптером хранения в доменную ошибку без зависимости от SQL в логике предметной области. Сохраняйте первопричину для диагностики, а внешние ответы и логи очищайте. Тестируйте обе стороны этого контракта.

## Воспроизводимая лабораторная: транзакция и отказ записи

```sh
  sleep 1

```
