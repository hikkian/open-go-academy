# Валидация, доменная ошибка и транзакция

## Что ты сделаешь

Ты напишешь три функции-протокола: проверку ввода до открытия транзакции, выбор между фиксацией и откатом по результату записи и тот же протокол с журналом вызовов, по которому видно порядок операций. Транзакция здесь подменяется учебным fake, который записывает вызовы.

## Ввод проверяют до транзакции

Транзакция занимает соединение с базой и держит блокировки до фиксации или отката. Если ввод заведомо неверен, открывать транзакцию незачем: соединение будет занято впустую, а откат ничего не даст. Поэтому входная валидация стоит перед `Begin`.

Обратная ошибка тоже возможна: валидация может зависеть от состояния базы, например от уникальности имени. Такую проверку нельзя перенести до `Begin`, и её выполняют внутри транзакции. Граница «до Begin» касается только проверок, которые видны из входных данных.

> **Важно.** Валидация до `Begin` отбрасывает только то, что видно без базы. Она не заменяет проверку ограничений в самой базе.

## Доменная ошибка вместо текста драйвера

Драйвер базы возвращает ошибки с текстом, который зависит от версии и языка сервера. Вызывающий код не должен разбирать этот текст. Вместо него сценарий переводит внутренний результат в устойчивую доменную категорию, например `conflict` или `write_error`.

Категория безопасна для ответа: она не содержит имени таблицы, запроса или фрагмента данных. Внутренний журнал при этом сохраняет полную причину. Наружу уходит только категория.

Пример показывает такую замену. Строка драйвера сопоставляется с категорией, а неизвестная строка становится общей внутренней ошибкой:

```go
package main

import "fmt"

func category(driverErr string) string {
    switch driverErr {
    case "duplicate key":
        return "conflict"
    case "":
        return "ok"
    default:
        return "internal_error"
    }
}

func main() {
    fmt.Println(category("duplicate key"), category("timeout"))
}
```

Вывод: `conflict internal_error`. Неизвестная ошибка не утекает наружу под своим именем.

## Фиксация или откат

Протокол транзакции линейный: `Begin`, затем `Apply`, затем `Commit`. Если `Apply` вернул ошибку, фиксировать нельзя: изменение неполное. Вместо фиксации вызывают `Rollback`. Так же поступают при конфликте, потому что конфликтующая запись не должна попасть в базу.

Порядок вызовов фиксирует журнал. Пример показывает протокол при успехе и при ошибке записи:

```go
package main

import "fmt"

func run(applyOK bool) []string {
    log := []string{"begin", "apply"}
    if applyOK {
        log = append(log, "commit")
    } else {
        log = append(log, "rollback")
    }
    return log
}

func main() {
    fmt.Println(run(true))
    fmt.Println(run(false))
}
```

Вывод: `[begin apply commit]` и затем `[begin apply rollback]`. Тест сравнивает такие журналы, и любое отклонение от протокола становится видимым.

## Неизвестный исход фиксации

Самый трудный случай — ошибка при `Commit`. Фиксация могла пройти на стороне базы, а ответ потерялся. Тогда откат после неё может быть невозможен, а повтор без сверки способен записать данные дважды. Поэтому такой исход называют неизвестным и не выдают за неудачу.

Учебный fake в этой главе после неуспешного `Commit` вызывает `Rollback` и фиксирует это в журнале. Реальный драйвер ведёт себя иначе, и это проверяется на настоящей базе, а не на fake.

## Порядок проверок и категории

Категории в ответе идут в строгом порядке, и этот порядок задаёт поведение. Сначала проверяется ввод: неверный запрос не должен ни открыть транзакцию, ни обратиться к зависимости. Затем проверяется наличие зависимости: отсутствующий объект даёт категорию о конфигурации, а не о данных. Только после этого вызывается `Begin`, и результат каждого следующего шага определяет, фиксировать или откатывать.

Порядок важен потому, что разные категории означают разные действия для вызывающего кода. Неверный ввод просят исправить. Отказ `Begin` можно повторить. Неизвестный исход фиксации требует проверки состояния. Смешивать эти категории нельзя, иначе клиент повторит запрос, который уже выполнился.

## Ответ наружу

Ответ сервиса получает только категорию. Внутренний журнал может содержать полную причину: текст драйвера, номер ошибки, имя таблицы. Это помогает разработчику, но не должно попадать клиенту. Тот же принцип касается журнала вызовов в тестах: он нужен для проверки порядка, а не для показа пользователю.

Категории стоит описать в контракте API и не менять без согласования. Новая категория для существующей ошибки ломает клиентов, которые на неё опираются.

## Сверка неизвестного исхода

Неизвестный исход фиксации решают сверкой. Сценарий ищет запись по стабильному идентификатору операции и смотрит, есть ли она в базе. Если записи нет, повтор безопасен. Если есть, повтор создаст дубль, и клиенту нужно вернуть результат уже выполненной операции.

Сверка выполняется не сразу после ошибки, а с короткой паузой и ограниченным числом попыток: в этот момент база может ещё обрабатывать фиксацию. Если сверка сама не отвечает, исход остаётся неизвестным, и это тоже честный ответ.

Сверка — отдельная операция с собственными ошибками. Её тоже нужно описать как протокол с категориями, иначе неизвестный исход превратится в бесконечный цикл проверок.

## Модель и механизм

Для транзакционного протокола полезны три вопроса. Что известно до `Begin`? Что означает результат `Apply` для фиксации? Что известно после ошибки `Commit`? Ответы записываются как порядок вызовов до написания сценария.

Синхронизация не входит в эту модель: fake последователен. Ограничение fake в том, что он не воспроизводит блокировки и конкурентные транзакции. Поэтому его ответы доказывают порядок, но не изоляцию.

## Типичные ошибки и исправление

Первая ошибка — открывать транзакцию до проверки ввода. Исправление — проверка входных данных до `Begin`.

Вторая — возвращать текст ошибки драйвера. Исправление — доменная категория.

Третья — фиксировать транзакцию после ошибки записи. Исправление — откат при любом неуспешном `Apply`.

Четвёртая — считать ошибку `Commit` обычным отказом. Исправление — отдельная категория неизвестного исхода и сверка по идентификатору.

> **Типичная ошибка.** Сравнивать ошибку драйвера строкой в тесте и в коде сценария. Если драйвер изменит текст, сценарий начнёт возвращать другой ответ без предупреждения.

## Если что-то пошло не так

- Пустые транзакции занимают соединения → проверка ввода стоит после `Begin`; перенеси её выше.
- Ошибка записи, но данные сохранились → при `Apply` с ошибкой вызвали `Commit`; проверь ветвление.
- Повтор создал дубль после ошибки `Commit` → неизвестный исход принят за неудачу; нужна сверка.
- Ответ содержит текст из базы → категория не выставлена; верни доменный код.

## Практика

Эти задания проверяют порядок вызовов на подменной транзакции. Функции не обращаются к базе. Закрытые примеры видны только в «Проверить».

### Задание 1 · Validation до Begin — protocol boundary

**Цель.** Интерфейс `BeginnerEasy` с методом `Begin() bool` уже объявлен. Функция `ValidationBoundaryEasy(valid, tx)` сначала проверяет `valid`. Если ввод неверен, верни `"invalid:"`, не вызывая зависимость. Если `tx` равен `nil`, верни `"dependency_missing:"`. Иначе вызови `Begin` ровно один раз: при неуспехе верни `"begin_failed:begin"`, при успехе `"ready_to_write:begin"`.

**Ожидаемый вывод** — входы: `valid = true` с работающим `Begin`; затем `valid = false`:

```text
"ready_to_write:begin"
"invalid:"
```

**Шаги.**
1. Выбери задание «Validation до Begin — protocol boundary»: в файле есть `ValidationBoundaryEasy` с `panic("TODO")`.
2. Если `valid` ложно, верни `"invalid:"`, не трогая `tx`.
3. Если `tx` равен `nil`, верни `"dependency_missing:"`.
4. Вызови `Begin` один раз.
5. Если `Begin` вернул `false`, верни `"begin_failed:begin"`.
6. Иначе верни `"ready_to_write:begin"`.
7. Нажми «Запустить» и сравни с блоком выше.
8. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- `Begin` вызван при неверном вводе → проверка ввода стоит после вызова.
- `"ready_to_write:begin"` при неуспешном `Begin` → результат вызова не проверен.
- Паника при `nil` → проверка зависимости отсутствует.

> **Подсказка.** Сначала ввод, потом зависимость, потом вызов `Begin`.

### Задание 2 · Mutate, domain error и commit/rollback

**Цель.** Интерфейс `TransactionMedium` содержит методы `Begin() bool`, `Apply() string`, `Commit() bool` и `Rollback()`. Функция `RunTransactionMedium(valid, tx)` возвращает категорию без журнала. Неверный ввод — `"invalid"`. Неуспешный `Begin` — `"begin_failed"`. Результат `Apply` `"ok"` даёт `"committed"`, если `Commit` прошёл, иначе `"commit_outcome_unknown"`. Результат `"conflict"` даёт `"conflict"` после отката. Прочие ошибки записи и неожиданные состояния дают `"write_error"` или `"internal_error"` после отката.

**Ожидаемый вывод** — входы: успешная запись с успешной фиксацией; затем конфликт записи; затем неверный ввод:

```text
"committed"
"conflict"
"invalid"
```

**Шаги.**
1. Выбери задание «Mutate, domain error и commit/rollback»: в файле есть `RunTransactionMedium` с `panic("TODO")`.
2. Если `valid` ложно, верни `"invalid"`.
3. Вызови `Begin`; при неуспехе верни `"begin_failed"`.
4. Вызови `Apply` и сравни результат со строками контракта.
5. При `"ok"` вызови `Commit`: успех даёт `"committed"`, неуспех — `"commit_outcome_unknown"`.
6. При `"conflict"` вызови `Rollback` и верни `"conflict"`.
7. При других ошибках вызови `Rollback` и верни `"write_error"` или `"internal_error"`.
8. Нажми «Запустить» и сравни с блоком выше.
9. Нажми «Проверить».

**Как проверить себя.** Три строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- `"committed"` при конфликте → ветка конфликта не отделена от успеха.
- `"conflict"` без отката → откат пропущен после ошибки записи.
- `"invalid"` для верного ввода → проверка ввода выполнена неверно.

> **Подсказка.** Все ветки, кроме успешной фиксации, заканчиваются откатом.

### Задание 3 · Failure protocol с наблюдаемым trace

**Цель.** Тот же протокол, что в предыдущем задании, но ответ имеет вид `категория:вызовы`, где вызовы перечислены через запятую в порядке выполнения: `begin`, `apply`, `commit`, `rollback`. Неверный ввод даёт `"invalid:"`, отсутствующая зависимость — `"dependency_missing:"`. При неуспешном `Commit` откат всё равно вызывается, и журнал это показывает.

**Ожидаемый вывод** — входы: успешная запись; неверный ввод; конфликт записи:

```text
"committed:begin,apply,commit"
"invalid:"
"conflict:begin,apply,rollback"
```

**Шаги.**
1. Выбери задание «Failure protocol с наблюдаемым trace»: в файле есть `RunTransactionHard` с `panic("TODO")`.
2. Если `valid` ложно, верни `"invalid:"` без вызовов.
3. Если `tx` равен `nil`, верни `"dependency_missing:"`.
4. Добавляй имя каждого вызова в журнал сразу в момент вызова.
5. Вызови `Begin`; при неуспехе верни `"begin_failed:"` с журналом.
6. Вызови `Apply` и разбери результат, как в предыдущем задании.
7. Нажми «Запустить» и сравни с блоком выше.
8. Нажми «Проверить».

**Как проверить себя.** Три строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- В журнале нет `rollback` после конфликта → откат не вызван или не записан.
- `commit` в журнале после ошибки записи → фиксация вызвана при ошибке `Apply`.
- Журнал собран в конце функции → порядок вызовов потерян.

> **Подсказка.** Журнал пополняется в момент каждого вызова, поэтому порядок в нём совпадает с порядком выполнения.

## Воспроизводимая лабораторная: журнал транзакции

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Базы данных не нужны: транзакция моделируется подменной структурой, которая записывает вызовы.

Программа ниже выполняет два сценария: успешную запись и запись с ошибкой. Она печатает журнал вызовов каждого сценария. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import "fmt"

type fakeTx struct {
    applyResult string
    commitOK    bool
    log         []string
}

func (f *fakeTx) run() string {
    f.log = append(f.log, "begin")
    f.log = append(f.log, "apply")
    if f.applyResult != "ok" {
        f.log = append(f.log, "rollback")
        return "write_error"
    }
    if !f.commitOK {
        f.log = append(f.log, "commit", "rollback")
        return "commit_outcome_unknown"
    }
    f.log = append(f.log, "commit")
    return "committed"
}

func main() {
    ok := &fakeTx{applyResult: "ok", commitOK: true}
    fmt.Println(ok.run(), ok.log)
    bad := &fakeTx{applyResult: "write_failed", commitOK: true}
    fmt.Println(bad.run(), bad.log)
}
```

**Ожидайте:** первая строка `committed [begin apply commit]`, вторая `write_error [begin apply rollback]`. Журнал показывает порядок вызовов: при ошибке записи фиксации нет.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/<каталог>`.

## Проверь себя

- Когда следует выполнять входную валидацию относительно `Begin`?
- Зачем сопоставлять внутренние ошибки стабильным доменным outcome?
- Какой порядок вызовов ожидается при успехе и при ошибке `Apply` в учебном fake?
- Почему после неуспешного `Commit` в учебном fake вызывается `Rollback`?
- Что не доказывает fake-тест порядка вызовов?
- Почему результат `Commit` после ошибки считается неизвестным?

## Итог

- Ввод проверяют до `Begin`, если проверка видна из входных данных; так транзакция не занимает соединение впустую.
- Ошибки драйвера переводятся в доменные категории, безопасные для ответа; текст драйвера наружу не уходит.
- Ошибка `Apply` ведёт к откату, а ошибка `Commit` — к неизвестному исходу, который требует сверки, а не слепого повтора.
