# Валидация, доменная ошибка и транзакция

## Зачем эта тема нужна

В backend-сервисе тема «Валидация, доменная ошибка и транзакция» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

Validation (валидация) проверяет форму и допустимые значения до побочного эффекта. Domain error (доменная ошибка) называет продуктовую причину стабильным кодом вроде `conflict` или `not_found`. Handler переводит эту категорию в безопасный HTTP ответ. Он не должен отдавать наружу текст драйвера, SQL, DSN или stack trace. Неизвестная внутренняя ошибка должна оставаться общим 500 ответом, а детали следует очищать и записывать во внутренний журнал.

Transaction (транзакция) группирует изменения базы так, чтобы ошибка до commit не оставила частичное состояние. Правило «сначала проверить, потом записать» снижает ненужные транзакции, но проверка уникальности только в коде не защищает от гонки: constraint в базе и обработка его typed error остаются важны. Вызов внешнего API не становится атомарным с SQL commit; для него нужен отдельный протокол, например outbox.

Easy останавливается на `ready_to_write` и подчёркивает, что валидация ещё не равна commit. Medium отображает только известные domain codes; Hard вычисляет намеренный outcome и выбирает rollback при конфликте либо любой ошибке записи/commit. Строка `commit_requested` означает лишь решение локальной модели. Реальный код обязан вызвать `Rollback` при ошибке, проверить ошибку `Commit`, обеспечить уникальный constraint и протестировать частичный отказ на фактическом драйвере. Даже успешная функция не доказывает атомарность SQL.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «Валидация, доменная ошибка и транзакция». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-26-easy mode=run
package main
import "fmt"

func ValidationResultEasy(valid bool) string {
	if !valid { return "invalid" }; return "ready_to_write"
}

func main() { fmt.Println(ValidationResultEasy(true)) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «Валидация, доменная ошибка и транзакция» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-26-medium mode=run
package main
import "fmt"

func HTTPStatusForDomainErrorMedium(code string) int {
	switch code { case "invalid": return 400; case "conflict": return 409; case "not_found": return 404; default: return 500 }
}

func main() { fmt.Println(HTTPStatusForDomainErrorMedium("invalid")) }
```

Второй пример меняет вход так, чтобы пересечь границу контракта. Прочитайте его вместе с первым: какой именно параметр изменился и почему результат должен измениться? Эти два запуска проверяют заданное правило, но не обращаются к внешней зависимости и не доказывают её конфигурацию.

## Ошибка, повтор и восстановление

Валидируй до записи, отображай только устойчивые domain codes и не раскрывай текст драйвера. На write/commit error выполняй cleanup и проверяй состояние; SQL атомарность доказывает интеграционный test.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-26-hard mode=run
package main
import "fmt"

func TransactionOutcomeHard(valid, conflict, writeFailed, commitFailed bool) string {
	if !valid { return "invalid" }; if conflict || writeFailed || commitFailed { return "rollback" }; return "commit_requested"
}

func main() { fmt.Println(TransactionOutcomeHard(true, false, false, false)) }
```

Порядок ветвей hard-контракта для «Валидация, доменная ошибка и транзакция» задаёт приоритет при пересекающихся признаках. Зафиксируйте этот приоритет до реализации, а неожиданный ввод обрабатывайте отдельно от успешного результата. Тест-векторы проверяют только выбранные категории; внешний протокол требует отдельного сценария.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy разделяет invalid и готовность начать запись; Medium переводит ограниченный набор domain error в статус; Hard выбирает commit_requested или rollback с приоритетом validation. Проверь неизвестный error, write failure и commit failure. Интеграционный тест подтверждает constraint, rollback, commit error и отсутствие частично сохранённой строки.

## Итог и повторение

Теперь вы умеете описать ограниченную модель темы «Валидация, доменная ошибка и транзакция», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `middle-25`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **domain error (доменная ошибка)** — Стабильная категория ошибки правила продукта.

- **transaction (транзакция)** — Атомарная группа операций базы данных.

- **rollback (откат)** — Отмена незавершённых изменений транзакции.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «Валидация, доменная ошибка и транзакция» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «если вход меняется с обычного на граничный, решение должно перейти в заранее названную категорию; если зависимость временно недоступна, состояние остаётся восстанавливаемым». Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Матрица ошибок и транзакционный cleanup

Прежде чем писать HTTP mapping, определите стабильные категории: invalid input, conflict, not found и internal failure. Маппинг должен быть исчерпывающим и безопасным: неизвестный код — общий 500, а не текст ошибки драйвера. Клиент получает request ID для поддержки; внутренний лог связывает его с очищенными деталями. Не возвращайте SQL constraint name, credentials, адрес базы или пользовательский payload.

У транзакции есть явные стадии: начать, выполнить проверки и изменения, commit; при любой ошибке до commit вызвать rollback. Ошибка commit тоже означает, что результат может быть неизвестен клиенту: не предполагайте без доказательств, что изменения точно отсутствуют. Повтор команды требует idempotency key либо способа прочитать результат. Уникальное ограничение должно существовать в базе, потому что предварительное чтение не предотвращает две конкурентные записи.

Сценарии интеграции проверяют invalid input до открытия транзакции, конфликт constraint, ошибку записи после первого изменения, ошибку commit и успешное изменение нескольких строк. После каждого отказа прочитайте состояние с нового соединения и убедитесь, что инвариант сохранён. Для внешней публикации проверьте outbox отдельно: запись события и доменная запись фиксируются вместе, relay публикует повторяемо, consumer дедуплицирует. `commit_requested` в упражнении лишь обозначает выбранную ветвь, не факт успешного SQL commit.


Если клиент повторяет запрос после timeout, сервер может уже зафиксировать commit, но ответ потерялся. Поэтому для критичных команд предусмотрите idempotency key с уникальным ограничением и сохраняйте безопасный результат операции. Ошибка Commit иногда оставляет outcome неизвестным; сообщите клиенту retryable/unknown только по контракту и не создавайте дубль при повторе. Если ошибка constraint соответствует конфликту продукта, преобразуйте конкретный типизированный код драйвера в domain error, не анализируйте свободный текст и не раскрывайте его в HTTP.


Constraint error и бизнес-конфликт должны быть преобразованы через адаптер хранения, а не протекать как зависимость SQL в domain package. Сохраняйте исходную причину в цепочке внутренних ошибок для диагностики, но внешний ответ и логи редактируйте по принятой политике. В тесте проверьте одновременно безопасный ответ и сохранность полезной внутренней категории.
