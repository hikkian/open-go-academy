# Фоновая задача и гарантии доставки

## Почему эта тема важна

Фоновая задача обычно проходит путь producer (производитель) → broker/queue (брокер/очередь) → consumer (потребитель) → побочный эффект. Слова at-most-once и at-least-once описывают допустимые повторы и потери на всём пути, а не магическое свойство метода `Publish`. Чтобы назвать гарантию, укажите границы: что подтверждает producer, как брокер сохраняет сообщение, когда consumer подтверждает обработку и насколько эффект идемпотентен. Exactly-once нельзя вывести из одной API очереди: база приложения и брокер обычно не участвуют в общей атомарной транзакции.

При at-most-once отправитель или consumer не повторяет неопределённую операцию; это допускает потерю, зато исключает часть дубликатов. Такой вариант годится лишь когда потеря приемлема или данные можно восстановить из другого источника. При at-least-once система повторяет неподтверждённую доставку; это уменьшает шанс потери при корректной настройке, но один и тот же event может обработаться несколько раз. Обработчик должен быть безопасным к повтору: например, записывать event ID в таблицу с уникальным ограничением в той же транзакции, что и бизнес-изменение.

Рассмотрим порядок consumer: получить сообщение, применить эффект, зафиксировать транзакцию, отправить ack. Если процесс упал после commit, но до ack, брокер может отправить событие снова. Это ожидаемое окно дубликата при at-least-once, а не обязательно ошибка брокера. Если ack отправить до commit, падение между ack и commit приведёт к потере эффекта: брокер считает задачу завершённой. Если процесс упал до эффекта и до ack, повтор обычно нужен, но точное поведение зависит от lease/visibility timeout/ack policy.

Producer имеет собственное окно. Отправка может пройти на стороне брокера, но подтверждение потеряться. Producer не знает, принято ли событие, и может отправить его снова. Поэтому событию нужен устойчивый ID, а потребителю — дедупликация. Outbox часто связывает бизнес-commit с намерением публикации, однако relay также может повторить уже принятую публикацию до сохранения отметки. Outbox даёт надёжный источник для повтора при правильной схеме и эксплуатации; сам по себе он не превращает внешний вызов в exactly-once.

Easy различает две выбранные модели по явному вводу. Medium показывает окно consumer: ack до commit опасен, commit без ack допускает повтор. Hard добавляет порядок приоритетов и состояние pending. Это анализ заданных фактов, а не измерение RabbitMQ, Kafka или другого брокера. Реальный результат зависит от durable queue/topic, producer confirms, retention, consumer group/offset, ack mode, retry policy и восстановления после рестарта.

Для наблюдаемости измеряйте возраст старейшего сообщения, размер backlog, скорость поступления и обработки, число redelivery, повторов и dead-letter. Рост backlog может означать медленный handler, нехватку потребителей или недоступность downstream-системы. Добавление worker-ов иногда повышает конкуренцию за базу и ухудшает ситуацию. Ограничивайте параллелизм и скорость повторов, применяйте backoff с пределом и сохраняйте причину окончательного отказа для ручного разбора.

## Практика трёх уровней

**Easy — middle-16-easy.** Реализуйте самый узкий контракт. Перед кодом выпишите таблицу вход → результат, отдельно нормальный случай, границу и некорректное состояние. Не добавляйте состояние, которого нет в сигнатуре. Проверьте, что каждый выход имеет конкретное значение для вызывающего слоя.

**Medium — middle-16-medium.** Добавьте независимый сигнал или состояние из условия. Решайте ветви в заданном порядке: сначала невалидное состояние, затем уже совершённый эффект/отмена, затем доступность ресурса, затем временной лимит и только после этого повтор или отказ. Этот порядок важен там, где две причины истинны одновременно. Проверьте конфликтующие входы из public/private vectors.

**Hard — middle-16-hard.** Разберите окно сбоя, неизвестный результат либо ограниченный отказ. Запишите, что система знает до сбоя и что может подтвердить после перезапуска. Не выводите «ровно один раз» из локальной категории: при неопределённом подтверждении реальная система должна повторить безопасно либо запросить сверку. Решение из функции — лишь политика для заданных фактов.

## Три исполняемых примера

```go group=middle-16-easy mode=run
package main
import "fmt"


func DeliveryModeEasy(mode string) string {
	switch mode { case "loss_ok": return "at_most_once"; case "retry_possible": return "at_least_once"; default: return "invalid" }
}

func main() { fmt.Println(DeliveryModeEasy("loss_ok")) }
```

```go group=middle-16-medium mode=run
package main
import "fmt"


func DeliveryWindowMedium(published bool, handlerCommitted bool, acked bool) string {
	if acked && !handlerCommitted { return "unsafe_ack" }
	if !published { return "not_delivered" }
	if handlerCommitted && !acked { return "redelivery_possible" }
	if handlerCommitted && acked { return "complete" }
	return "pending"
}

func main() { fmt.Println(DeliveryWindowMedium(false, false, false)) }
```

```go group=middle-16-hard mode=run
package main
import "fmt"


func DeliveryWindowHard(published bool, handlerCommitted bool, acked bool) string {
	if acked && !handlerCommitted { return "unsafe_ack" }
	if !published { return "not_delivered" }
	if handlerCommitted && !acked { return "redelivery_possible" }
	if handlerCommitted && acked { return "complete" }
	return "retry_or_pending"
}

func main() { fmt.Println(DeliveryWindowHard(true, false, true)) }
```

## Как читать примеры и проверять выводы

Примеры ниже компилируются как небольшие программы и показывают публичный reference для упражнения. Каждый запускает только чистую функцию: в нём нет сетевого клиента, локальной БД, goroutine, таймера, брокера или настоящей конфигурации сервера. Вывод показывает результат контракта на названном input. Он не означает, что внешняя зависимость выдала такой исход, сохранила данные или соблюла порядок. Если пример и формулировка расходятся, исправлять нужно контракт или reference вместе, а не подгонять hidden tests под один частный ответ.

Табличный тест должен называть смысл каждой строки. Укажите входы, ожидаемую категорию и инвариант, который проверяется. Одного «happy path» недостаточно: добавьте точную границу, значение за границей и пересечение двух сигналов, когда приоритет важен. Private vectors должны ловить реализацию, которая всегда возвращает один удобный ответ, игнорирует отдельный аргумент, путает `>=` и `>` или не замечает некорректный счётчик. Случаи должны быть компактны и детерминированы, чтобы ученик мог воспроизвести их локально.

## Что потребуется для реальной проверки

Переход от helper к работающему backend потребует другого набора доказательств. Зафиксируйте версии runtime и зависимости, конфигурацию, лимиты, время ожидания, политику подтверждений и порядок фиксации. Для отказного теста отметьте точку, где процесс останавливается, перезапустите компонент и посчитайте итоговый эффект. Проверяйте, что отмена освобождает ресурсы, повтор не умножает изменение, а постоянная ошибка не крутится бесконечно. Снимайте метрики задержки, backlog и повторов. Unit test не может заменить такие проверки.

Если в системе участвует PostgreSQL, проверьте миграцию, уникальные ограничения, транзакционные границы и конкурентный сценарий на реальном закреплённом движке. Если участвует брокер, тест должен включать его фактический ack/confirm режим и рестарт consumer или relay. Если результат зависит от сети, используйте контролируемый локальный контейнер или fault proxy, а не случайную задержку. Очистка должна быть изолирована от пользовательских данных. Повторяемая команда и зафиксированный fixture позволяют другому разработчику независимо подтвердить результат.

## Диагностика и проектное решение

Начинайте расследование с наблюдаемого состояния: счётчики до операции, момент commit/ack, возвращённая категория, число повторов и конечный эффект. Сверьте часы, единицы измерения и идентификатор операции. Не делайте вывод по одному лог-сообщению, если его могло создать несколько попыток. Корреляционный ID должен быть безопасен и одинаков для повтора; payload, токены, DSN и личные сведения не следует без необходимости писать в лог.

При выборе политики опишите цену обеих сторон. Увеличить ожидание — значит дать системе больше времени, но занять запрос и ресурсы дольше. Быстро отказать — значит сохранить capacity, но передать восстановление вызывающему коду. Повтор — шанс пережить transient сбой и вероятность дублирования. Dead-letter — остановка автоматического шума ценой необходимости диагностики и replay. Хороший middle-level ответ называет условие переключения политики и метрику, которая это условие обнаружит.

Устойчивое решение имеет владельца каждого инварианта. Handler отвечает за решение и контекст; repository — за транзакционное состояние; адаптер брокера — за mapping ack/nack; операторская политика — за лимиты, очередь повторов и восстановление. Не размывайте ответственность между слоями. Наблюдаемая функция из grader помогает изолировать одно правило, а интеграционная система проверяет взаимодействие владельцев. Это разные масштабы доказательства, и оба могут понадобиться.

### Самопроверка

1. Какой вход пересекает границу контракта и меняет решение?
2. Какой отказ может произойти после внешнего эффекта, но до локального подтверждения?
3. Какая часть поведения проверена чистой функцией, а какая требует конкретной инфраструктуры?
4. Какой тест способен обнаружить дубликат, потерю эффекта или утечку ожидающего ресурса?

Перед завершением назовите один непокрытый отказ и один конкретный тест, который мог бы опровергнуть ваше решение. Сохраните команду, fixture, версии и фактическое число эффектов. Не расширяйте утверждение за пределы наблюдений: правильный результат helper — необходимая проверка правила, но не сертификат поведения всей системы.

## Матрица отказов для producer и consumer

Три факта в `DeliveryWindow` удобно записать как последовательность, но они принадлежат разным сторонам. Producer отправляет сообщение; брокер принимает/сохраняет его; consumer применяет эффект; consumer подтверждает доставку. Наши поля `published`, `handlerCommitted` и `acked` намеренно сводят несколько реальных шагов к небольшому набору наблюдений. Они помогают увидеть несовместимые состояния, но реальная система может не знать, был ли предыдущий шаг принят после сетевого timeout.

Состояние `published=false` означает, что по модели сообщения нет. Это может быть неудачная валидация, ошибка подключения либо неизвестный результат, если отправка могла достичь брокера до потери ответа. Поэтому Hard различает только явные входные факты и не называет решение exactly-once. Когда `published=true`, `handlerCommitted=false`, `acked=false`, остаётся работа: сообщение ещё не завершено и может ожидать или быть доставлено снова. Когда commit есть, но ack нет, broker redelivery может запустить handler снова. Именно поэтому consumer следует проектировать для at-least-once.

Представьте consumer, который сначала списывает баланс, затем ack. Если ack теряется, второе выполнение не должно сделать второе списание. Хранение event ID в таблице `processed_events` помогает, но запись ID должна участвовать в той же транзакции, что и изменение баланса. Иначе есть ещё одно окно отказа: эффект сохранён, а отметка отсутствует, либо отметка есть без эффекта. Альтернатива — бизнес-операция сама идемпотентна по стабильному operation key. Выбор зависит от доменной модели и ограничений хранения.

### Как отделить потерю от дубля

At-most-once система после неопределённого исхода может отказаться от повтора, оставив задачу потерянной. At-least-once повторяет неподтверждённую работу и допускает дубликат. Название гарантии должно сопровождаться предпосылками: durable storage включено? producer ждёт confirm? consumer ack manual? offset commit sync/async? какое окно retention? что произойдёт при рестарте? Без этих ответов слово «надёжная очередь» не описывает поведение.

Идемпотентность эффекта тоже ограничена временем хранения. Если dedup запись удаляется через сутки, но broker может повторить сообщение через неделю, повтор становится новым. Поэтому сравните срок dedup с максимальным replay/retention окном. Не храните весь payload без основания; ID, fingerprint и безопасный статус могут быть достаточны для проверки повтора.

### Мутанты и vectors

Проверьте ошибки порядка: вернуть complete при `acked=true, handlerCommitted=false`; трактовать `handlerCommitted=true, acked=false` как окончательное завершение; на `published=false` говорить redelivery. Private cases контролируют эти ветви. Для всех истинных флагов результат complete означает лишь, что абстрактная последовательность завершена по входам. Она не подтверждает устойчивость диска брокера. Преднамеренно подставьте противоречивую комбинацию и убедитесь, что небезопасный ack имеет более высокий приоритет, чем обычное ожидание.

### Отдельный эксперимент

В integration test остановите consumer в барьерной точке после commit, но до ack. Перезапуск должен показать redelivery, а количество доменных изменений должно остаться равным одному благодаря дедупликации. Второй тест останавливает consumer до commit: после восстановления сообщение должно быть обработано. Нужны управляемые барьеры и журнал фактических событий. Остановка процесса случайно через sleep может промахнуться мимо нужного окна. Сохраняйте broker config, время и число доставок вместе с результатом; тест на fake может подтвердить порядок вызовов, но не поведение при broker restart.

### Разбор конфигурации доставки

Для конкретного брокера соберите короткий deployment checklist: durable ли очередь или topic; когда producer получает подтверждение; может ли сообщение потеряться при рестарте; как consumer фиксирует ack/offset; что означает timeout; как выглядит redelivery; где задаётся retry delay; что происходит после лимита; как читается backlog. Отдельно проверьте транзакцию бизнес-хранилища. Ответ «мы используем Kafka/RabbitMQ» не отвечает на эти вопросы: версии, настройки и клиентская библиотека меняют наблюдаемое поведение.

Увеличение числа consumer-ов не обязательно повышает throughput. Если обработчики ждут одни и те же строки БД, дополнительная конкуренция увеличит lock contention. Если требуется порядок по ключу, параллельная обработка может нарушить его, даже когда брокер выдаёт сообщения упорядоченно в partition. Назовите ключ упорядочивания и границу параллелизма. Для независимых событий можно использовать большую конкуренцию, но это уже продуктовый инвариант.

Тестируйте не только «сообщение пришло», но и количество эффектов после намеренного сбоя. Сохраняйте идентификатор события и доменную запись. После каждого старта/рестарта проверяйте consumer lag, повторную доставку и конечное состояние. Фикстуры должны гарантировать начальное состояние, иначе остаток прошлого прогона может сделать повтор успешным случайно.

### Дополнительный контроль

Параметры доставки следует фиксировать вместе с тестовым результатом, потому что разные локальные профили могут вести себя иначе. Запишите имя очереди/topic, durable/persistent флаги, тип подтверждения producer, ack policy consumer, retry и DLQ binding. Не вставляйте credentials в отчёт. Изменение одного параметра может повлиять на сохранение или redelivery; повторите тест именно на новом конфиге. Если подтверждение асинхронное, дождитесь явного результата тестовым барьером, а не задержкой на несколько секунд.

### Термины

- **at-most-once (не более одного раза)** — Сообщение может потеряться, повтор исключён.

- **at-least-once (не менее одного раза)** — Доставка повторяется, поэтому возможны дубли.

- **delivery guarantee (гарантия доставки)** — Условия поведения сообщения при отказе.
