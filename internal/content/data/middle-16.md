# Фоновая задача и гарантии доставки

## Что ты сделаешь

Ты напишешь три функции-модели для фоновой задачи: выбор модели доставки, решение по окну обработки потребителя и порядок вызовов эффекта и подтверждения. Функции работают с переданными фактами и журналом вызовов, поэтому проверяют логику отдельно от реального брокера и базы.

## Путь сообщения и слова о гарантиях

Фоновая задача обычно проходит путь: производитель (producer) → брокер или очередь → потребитель (consumer) → побочный эффект. Слова «не более одного раза» и «не менее одного раза» описывают допустимые потери и повторы на всём пути. Они не являются свойством одного метода `Publish`.

Чтобы назвать гарантию, укажи границы: что подтверждает производитель, как брокер сохраняет сообщение, когда потребитель подтверждает обработку и насколько эффект идемпотентен. Гарантию «ровно один раз» нельзя вывести из одного API очереди: база приложения и брокер обычно не участвуют в общей атомарной транзакции.

## At-most-once и at-least-once

При at-most-once отправитель или потребитель не повторяет неопределённую операцию. Это допускает потерю, зато исключает часть дубликатов. Такой вариант годится, когда потеря приемлема или данные можно восстановить из другого источника.

При at-least-once система повторяет неподтверждённую доставку. Это уменьшает шанс потери при корректной настройке, но одно событие может обработаться несколько раз. Пример показывает, что без защиты два доставленных экземпляра дают два эффекта:

```go
package main

import "fmt"

func main() {
    deliveries := []string{"evt-7", "evt-7"}
    effects := 0
    for range deliveries {
        effects++
    }
    fmt.Println(len(deliveries), effects)
}
```

Вывод: `2 2`. Доставка дважды дала два эффекта. Поэтому при at-least-once обработчик обязан быть безопасным к повтору.

## Дедупликация по event ID

Самый распространённый способ — запомнить идентификатор события и пропускать уже обработанные. Пример показывает такую дедупликацию на наборе значений:

```go
package main

import "fmt"

func main() {
    seen := map[string]bool{}
    for _, id := range []string{"evt-1", "evt-1", "evt-2"} {
        if seen[id] {
            fmt.Println("skip", id)
            continue
        }
        seen[id] = true
        fmt.Println("apply", id)
    }
}
```

Вывод: `apply evt-1`, затем `skip evt-1`, затем `apply evt-2`. Повтор узнан по ID и не породил второй эффект.

В настоящей системе набор заменяет таблица с уникальным ограничением. Запись ID должна быть в той же транзакции, что и бизнес-изменение. Иначе появляется окно отказа: эффект сохранён, а отметка нет, либо отметка есть без эффекта.

Что хранить в записи дедупликации — отдельное решение. Обычно достаточно идентификатора события, статуса, времени обработки и короткого отпечатка содержимого, если он нужен для проверки повтора. Полный payload хранить без основания не стоит: он может содержать личные данные и раздувает таблицу.

> **Важно.** Таблица дедупликации должна хранить запись не короче окна повторов. Если запись удаляется раньше, поздний повтор станет новым событием.

## Порядок эффекта и подтверждения

Consumer обычно делает три шага: применяет эффект, фиксирует его и отправляет подтверждение (ack). Порядок важен. Если подтвердить сообщение до фиксации эффекта, падение между этими шагами приведёт к потере: брокер считает задачу выполненной, а эффекта нет.

Пример показывает правильный порядок через журнал вызовов:

```go
package main

import "fmt"

func main() {
    log := []string{}
    effect := func() { log = append(log, "effect") }
    ack := func() { log = append(log, "ack") }
    effect()
    ack()
    fmt.Println(log)
}
```

Вывод: `[effect ack]`. Журнал фиксирует порядок, который проверяет тест. Он не доказывает, что эффект был атомарно сохранён: для этого нужна реальная транзакция.

Если процесс упал после фиксации эффекта, но до ack, брокер отправит событие снова. Это ожидаемое окно дубликата при at-least-once, а не обязательно ошибка брокера.

## Окно производителя

Производитель тоже имеет окно. Отправка может пройти на стороне брокера, но подтверждение потеряться. Тогда производитель не знает, принято ли событие, и отправляет его снова. Поэтому событию нужен устойчивый ID, а потребителю — дедупликация по этому ID.

Outbox — это таблица, куда в той же транзакции, что и бизнес-изменение, записывают событие для публикации. Отдельный процесс затем читает таблицу и отправляет события в брокер. Так исчезает окно, в котором изменение есть, а события нет.

Outbox связывает бизнес-фиксацию с намерением опубликовать событие. Однако ретрансляция (relay) может повторить уже принятую публикацию до того, как отметит её в outbox. Outbox даёт надёжный источник для повтора при правильной схеме и эксплуатации, но сам не превращает внешний вызов в exactly-once.

## Повторы без бесконечного цикла

Повторы нужны для временных сбоев, но постоянная ошибка не должна крутиться бесконечно. Обычно задают предел попыток и растущую паузу между ними. Исчерпанные сообщения переводят в отдельную очередь неудачных сообщений (dead-letter), где их разбирает человек или отдельный процесс.

Очередь неудачных сообщений — не свалка. В ней сохраняют идентификатор события, причину последнего отказа и число попыток. Иначе диагностика начинается с нуля. Переотправка из такой очереди тоже должна проходить через дедупликацию: сообщение могло уже частично обработаться.

Метрики помогают заметить проблему раньше очереди: возраст старейшего сообщения, размер backlog, число повторов и число попаданий в неудачную очередь. Рост любой из них требует внимания до того, как потеряется первое событие.

## Лаборатория перед практикой

Возьми пример с журналом `log` и замени функцию `ack` так, чтобы она вызывалась до `effect`. Перед запуском запиши, какой журнал появится, и что произойдёт, если программа упадёт между двумя вызовами. Затем запусти программу и сравни. Потом верни правильный порядок и убедись, что журнал совпадает с ожидаемым.

Журнал эксперимента содержит версию Go, исходный порядок вызовов, изменённый порядок, предсказание, наблюдение и вывод о том, какое окно отказа появилось. Такой опыт показывает, почему подтверждение ставят после фиксации: журнал не доказывает атомарность, но показывает порядок, который защищает от потери.

## Модель и механизм

Сначала различай состояние программы и расписание. Состояние — факт публикации, фиксация эффекта, подтверждение и журнал дедупликации. Расписание — момент падения процесса относительно этих шагов. Корректная политика должна давать допустимый результат при любом падении.

Для доставки полезны несколько вопросов. Какой идентификатор есть у события? Где хранится факт обработки? Что видит повторная доставка? Что происходит, если процесс упал до эффекта? Что происходит, если упал после эффекта, но до подтверждения? Что знает потребитель при повторе? Ответы записываются до выбора гарантии.

Синхронизация имеет цену. Дедупликация занимает место и требует транзакции, а ретраи увеличивают нагрузку. Поэтому каждое повышение надёжности нужно сопоставлять с ценой: сколько места занимает дедупликация, сколько времени добавляет транзакция и сколько дополнительных повторов создаёт политика. Выбор гарантии — продуктовое решение: потеря телеметрии может быть приемлема, потеря платёжного изменения — нет.

## Типичные ошибки и исправление

Первая ошибка — подтверждать сообщение до фиксации эффекта. Исправление — ack только после commit.

Вторая — считать `at-least-once` безопасным без дедупликации. Исправление — отметка event ID в той же транзакции, что и эффект.

Третья — заявлять «ровно один раз» по одному API брокера. Исправление — называть реальные предпосылки: подтверждения, хранение, окно повторов.

> **Типичная ошибка.** Удалять записи дедупликации по времени без связи с окном повторов. Тогда поздний дубликат выполнит эффект второй раз.

## Если что-то пошло не так

- Сообщение исчезло после перезапуска → ack отправлен до фиксации эффекта; перенеси подтверждение после commit.
- Баланс списан дважды → дедупликация не защищает повтор или отметка не в транзакции.
- Backlog растёт, хотя потребители работают → обработчик ждёт общую блокировку; проверь конкуренцию за строки.
- Повтор не распознан через неделю → срок хранения дедупликации короче окна повторов.

## Итог

- Гарантия доставки описывает весь путь сообщения; потеря и повтор зависят от порядка подтверждения и фиксации.
- При at-least-once дубликаты неизбежны, поэтому эффект защищают дедупликацией по event ID в одной транзакции.
- Подтверждение идёт после фиксации эффекта; неизвестный исход подтверждения требует сверки, а не слепого повтора эффекта.
