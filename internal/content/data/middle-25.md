# Handler (обработчик), service (слой бизнес-правил), repository (слой хранения) и DI (внедрение зависимостей)

## Цель урока

Разделим один сценарий на небольшие роли и проверим, что зависимость действительно передана коду извне. В этой главе мы не поднимаем HTTP-сервер и БД: fake repository (поддельный репозиторий) возвращает заранее заданные ответы, чтобы поведение сервиса было наблюдаемым и повторяемым.

`handler` (обработчик) преобразует HTTP-вход и результат use case (сценария приложения). `service` (служба приложения) выполняет правило продукта. `repository` (репозиторий) скрывает чтение и запись. `interface` (интерфейс) в Go перечисляет методы, которые нужны потребителю; тип удовлетворяет интерфейсу неявно, если реализует эти методы. `dependency injection`, DI (внедрение зависимости), означает, что взаимодействующий компонент (`collaborator`) передают снаружи как явную зависимость. `composition root` (точка сборки) — место, где приложение создаёт конкретные реализации и соединяет их.

Направление вызовов в простом HTTP use case:

```text
HTTP → handler → service → repository interface → конкретное хранилище
                         ↑ зависимости передаёт composition root
```

Service не должен знать HTTP status code, а repository — формат HTTP-ответа. Сервисный интерфейс держат узким: только операции, которые нужны конкретному потребителю. Не следует создавать интерфейс для каждого типа «на всякий случай» и не нужно подключать DI-фреймворк для нескольких конструкторов.

## Как читать ошибки и границы примера

Упражнения используют короткие строковые категории, чтобы результат fake-зависимости было видно в grader. В рабочем коде вместо `bool` обычно возвращают `error`, сравнивают sentinel errors через `errors.Is` или оборачивают их через `%w`, а наружу отображают безопасную доменную категорию. Ошибка БД, сетевой отказ и неверный запрос — разные причины и не должны сливаться в одну.

Все три упражнения — локальные Go-функции с fake-зависимостями, а не интеграция с HTTP или SQL. Их тесты проверяют именно ветви описанного контракта. Они не доказывают корректность SQL, транзакций, миграций, сетевой доступности, потокобезопасности или запуска production wiring.

## Easy: прочитать через узкий интерфейс

Начнём с чтения профиля. Функция получает `ProfileReaderEasy` параметром, поэтому не создаёт глобальное хранилище и не выбирает сама конкретную БД. Fake в тестовом driver реализует тот же интерфейс.

```go group=middle-25-easy mode=run
package main

import "fmt"

type ProfileReaderEasy interface {
	FindProfile(id string) (name string, found bool)
}

func WelcomeEasy(repository ProfileReaderEasy, id string) string {
	if id == "" { return "invalid_request" }
	name, found := repository.FindProfile(id)
	if !found { return "not_found" }
	if name == "" { return "invalid_profile" }
	return "hello:" + name
}

type memoryProfile struct{}
func (memoryProfile) FindProfile(id string) (string, bool) { return "Алия", id == "7" }
func main() { fmt.Println(WelcomeEasy(memoryProfile{}, "7")) }
```

Разберите последовательность: сначала валидируется запрос, затем вызывается переданная зависимость, после чего результат переводится в категорию use case. Код не импортирует HTTP и не знает о SQL. Публичные и закрытые векторы включают успех, отсутствие профиля, пустой id и некорректную пустую запись.

## Medium: правило и запись через fake repository

Теперь сервис не только читает, но и принимает решение о переименовании. Пустые значения недопустимы; отсутствующая запись и уже существующее имя отличаются; ошибка записи видна вызывающему коду. Fake позволяет проверить все ветви без запуска базы данных.

```go group=middle-25-medium mode=run
package main

import "fmt"

type ProfileRepositoryMedium interface {
	FindProfile(id string) (name string, found bool)
	SaveProfile(id, name string) bool
}

func RenameProfileMedium(repository ProfileRepositoryMedium, id, newName string) string {
	if id == "" || newName == "" { return "invalid_request" }
	if repository == nil { return "dependency_missing" }
	oldName, found := repository.FindProfile(id)
	if !found { return "not_found" }
	if oldName == "" { return "invalid_profile" }
	if oldName == newName { return "unchanged" }
	if !repository.SaveProfile(id, newName) { return "storage_error" }
	return "updated"
}

type memoryProfile struct { oldName string; found bool; saveOK bool; writes int }
func (r *memoryProfile) FindProfile(id string) (string, bool) { return r.oldName, r.found }
func (r *memoryProfile) SaveProfile(id, name string) bool { r.writes++; return r.saveOK }
func main() {
	cases := []struct { id, name, old string; found, saveOK bool }{
		{"7", "Лена", "Алия", true, true}, {"7", "Алия", "Алия", true, true}, {"404", "Лена", "", false, true},
	}
	for _, tc := range cases {
		repository := &memoryProfile{oldName: tc.old, found: tc.found, saveOK: tc.saveOK}
		result := RenameProfileMedium(repository, tc.id, tc.name)
		fmt.Printf("%s:%d\n", result, repository.writes)
	}
}
```

Проверьте, почему проверка `oldName == newName` стоит до записи: при повторном запросе не нужна лишняя операция. Fake считает вызовы `SaveProfile`, поэтому ожидаемые строки `updated:1`, `unchanged:0`, `not_found:0` обнаруживают лишнюю или пропущенную запись. В реальном интерфейсе методы обычно возвращают конкретные ошибки, а service решает, какие из них являются конфликтом, а какие — временным отказом. Контракт здесь намеренно проще.

## Hard: скомпоновать две зависимости и увидеть частичный отказ

Создание профиля зависит от repository и audit sink (приёмник аудита). Сначала валидируется вход, затем сохраняется профиль, затем записывается событие. Если аудит падает после сохранения, функция возвращает `audit_error_after_create`: это частичный отказ, сохранение уже произошло. Нельзя притворяться, что операция откатилась. В реальном приложении для согласованной записи может потребоваться транзакция или transactional outbox (транзакционный outbox); этот маленький контракт их не реализует.

```go group=middle-25-hard mode=run
package main

import (
	"fmt"
	"strings"
)

type ProfileCreatorHard interface { CreateProfile(name string) bool }
type AuditSinkHard interface { Record(event string) bool }

func CreateProfileHard(repository ProfileCreatorHard, audit AuditSinkHard, name string) string {
	if name == "" { return "invalid_request" }
	if repository == nil || audit == nil { return "dependency_missing" }
	if !repository.CreateProfile(name) { return "create_error" }
	if !audit.Record("profile_created") { return "audit_error_after_create" }
	return "created"
}

type memoryProfile struct { createOK bool; events *[]string }
func (r *memoryProfile) CreateProfile(name string) bool { *r.events = append(*r.events, "create"); return r.createOK }
type memoryAudit struct { recordOK bool; events *[]string }
func (a *memoryAudit) Record(event string) bool { *a.events = append(*a.events, "audit:"+event); return a.recordOK }
func main() {
	cases := []struct { name string; createOK, auditOK bool }{{"Илья", true, true}, {"Илья", false, true}, {"Илья", true, false}}
	for _, tc := range cases {
		events := []string{}
		result := CreateProfileHard(&memoryProfile{createOK: tc.createOK, events: &events}, &memoryAudit{recordOK: tc.auditOK, events: &events}, tc.name)
		fmt.Printf("%s:%s\n", result, strings.Join(events, ","))
	}
}
```

Подумайте, что следует проверить отдельным integration test: сохранение и аудит при реальном отказе между шагами, а также выбранную стратегию восстановления. Fake записывает события, поэтому grading проверяет точный порядок: `create,audit:profile_created` при успехе и только `create` при отказе создания. Эти векторы проверяют только интерфейсный контракт, а не транзакцию или внешнее хранилище. В composition root `main` создаёт адаптеры и передаёт их конструктору сервиса; бизнес-правило тестируется без HTTP и БД.

## Частые ошибки

- Создавать repository внутри service: зависимость сложнее заменить тестовой и настроить в одном месте.
- Делать интерфейс «на всякий случай»: выбирайте методы от потребителя и вводите интерфейс там, где есть реальная граница.
- Возвращать SQL-текст клиенту: отделяйте внутреннюю ошибку от безопасного ответа handler.
- Считать последовательность двух записей атомарной: сбой между ними оставляет частично выполненный сценарий.
- Выдавать unit test на fake за доказательство SQL, транзакций или корректности запуска приложения.

## Где проходит граница в настоящем приложении

Представим use case «показать профиль по идентификатору». HTTP handler разбирает путь `/profiles/7`, проверяет, что идентификатор можно передать сервису, вызывает сервис и преобразует его результат в HTTP-код и JSON. Service не принимает `http.Request`: ему достаточно строки `id` и интерфейса чтения. Repository реализует интерфейс, обращаясь к конкретной схеме данных. Если завтра источник изменится с SQL на удалённый API, правило сервиса останется прежним, пока контракт чтения остаётся достаточным.

Граница не означает, что каждому слою обязательно нужен отдельный пакет или интерфейс. Для маленького приложения полезнее несколько ясных типов, чем каталог абстракций. Размещайте интерфейс рядом с потребителем: сервису нужен способ найти профиль, поэтому сервис определяет минимальный `ProfileReader`. Адаптер хранения уже реализует его неявно. Не добавляйте методы вроде `DeleteAll`, если сценарий их не использует. Узкий контракт проще подменить fake и труднее использовать случайно не по назначению.

Упражнение Easy показывает протокол вызова: валидация входа, чтение, интерпретация отсутствующей записи, формирование результата. Оно не моделирует HTTP-коды. В реальном handler `invalid_request` мог бы стать 400, `not_found` — 404, а успех — 200, но такое отображение относится к транспортной границе. Если код сервиса начнёт возвращать `http.StatusNotFound`, тест сервисного правила будет связан с HTTP и повторное использование в CLI станет сложнее.

Упражнение Medium добавляет запись и несколько состояний. Обратите внимание на порядок: сначала проверяется вход, после этого читается существующее состояние, затем оценивается доменное правило, и лишь при необходимости выполняется запись. Это не гарантия конкурентной уникальности. Два параллельных запроса могут одновременно прочитать старое имя; настоящая база должна защищать необходимые инварианты уникальным ограничением, условным update или транзакцией. Fake возвращает предсказуемый ответ одного вызова и не проверяет конкурентное поведение базы.

Упражнение Hard намеренно добавляет вторую зависимость. Сначала repository сохраняет профиль, затем audit sink принимает событие. Отказ второго шага показывает важное свойство: два обычных вызова не становятся одной атомарной операцией оттого, что их вызвали из одного метода. Возвращаемое состояние `audit_error_after_create` сообщает о неопределённой для вызывающего стороны ситуации. В реальном проекте нужно выбрать семантику: откатывать обе записи транзакцией в общей базе, записывать событие в outbox в одной транзакции или проектировать восстановление/повтор. Нельзя незаметно повторить создание, если оно уже прошло.

## Composition root без магии

В простом приложении точкой сборки служит функция запуска. Она читает конфигурацию, создаёт конкретный SQL repository, вызывает конструктор сервиса, передаёт service HTTP handler и запускает сервер. Это делает граф объектов видимым при чтении кода. DI-фреймворк не нужен, когда список зависимостей можно проследить обычными вызовами функций.

Конструктор полезен, когда проверяет обязательные зависимости. Например, `NewProfileService(repository ProfileReader) (*ProfileService, error)` может вернуть ошибку для отсутствующего repository. Тогда неправильная сборка обнаруживается до первого пользовательского запроса. Не скрывайте эту проверку в `init()` и не храните repository в изменяемой package variable: глобальное значение усложняет параллельные тесты, изоляцию экземпляров и повторную настройку.

Для интерфейса с методами можно проверить соответствие конкретного адаптера на этапе компиляции выражением `var _ ProfileReader = (*SQLProfileRepository)(nil)`. Это обнаружит несовпадающую сигнатуру метода. Такая проверка не доказывает, что SQL правильный, что запрос использует нужный индекс или что соединение открывается. Для этих утверждений потребуется тест на реальном драйвере и временной БД либо отдельной тестовой инфраструктуре.

Именование результата тоже часть границы. В учебном grader строка помогает видеть ветвь. В production-пакете лучше определить стабильные доменные ошибки или типизированный результат, а низкоуровневую ошибку сохранить с причиной для внутренней диагностики. Handler выбирает безопасное сообщение и код ответа; секреты, строки подключения и текст запроса не должны попадать в ответ клиенту. Не следует также бездумно скрывать все ошибки под одним `failed`: классификация должна позволять повторить временную ошибку и остановить неверный запрос.

## Как составить набор тестов

Unit test сервиса использует fake repository. В тесте задаётся найденный профиль, отсутствующая запись или ошибка сохранения, затем проверяется результат use case. Такой тест быстрый и помогает покрыть правило. Fake должен быть маленьким и явным: несколько полей для ответов и счётчик вызовов обычно понятнее универсального mock-объекта. Если контракт говорит «при unchanged не записывать», проверка числа вызовов `SaveProfile` напрямую подтверждает отсутствие побочного эффекта.

Unit test handler использует fake service или подходящий HTTP recorder и проверяет преобразование запроса и результата в транспорт. Это другой контракт, и его не нужно дублировать в тесте repository. Integration test соединяет настоящий адаптер и тестовую базу, выполняет миграции, записывает и читает строку, а затем очищает созданные данные. Если нужно проверить транзакцию, специально вызовите ошибку между записью данных и событием, после чего проверьте состояние обеих таблиц.

Набор тестов можно читать как лестницу доказательств: unit test локализует правило; compile-time interface check подтверждает совместимость типов; integration test проверяет выбранные реальные адаптеры; end-to-end тест убеждается, что HTTP-запрос проходит через собранное приложение. Каждый уровень отвечает на свой вопрос. Если unit test прошёл, нельзя заключать, что сервер стартует или база доступна. Если integration test прошёл для одной версии PostgreSQL и схемы, нельзя без дополнительных данных заключать, что то же верно для другой конфигурации.

## Самостоятельный разбор

Проследите один запрос через handler, service и repository. Измените fake так, чтобы профиль отсутствовал; проверьте `not_found` и отсутствие вызова записи. Затем повторите переименование без изменения имени и включите отказ audit sink: назовите уже выполненный побочный эффект.

Граница этих упражнений — fake: они не проверяют конкуренцию, отмену запроса, timeout базы, rollback, tenant isolation или приватность аудита. Зафиксируйте вход fake, результат и вызванные методы. Сформулируйте узкий вывод, например: «при отсутствии ID fake сервис возвращает `not_found` и не вызывает Save». SQL-маппинг, транзакция и запуск HTTP-приложения требуют отдельных проверок.

## Итог

На Easy вы читаете данные через узкий интерфейс; на Medium применяете правило и обрабатываете отказ записи; на Hard передаёте две зависимости и явно различаете полный успех и частичный отказ. Следующий практический шаг — собрать интерфейсы в конструкторе приложения и добавить отдельный integration test на выбранном хранилище. Локальный grader не выполняет этот интеграционный шаг.

## Воспроизводимая лабораторная: проследить DI до настоящего handler

**Prerequisites:** Go 1.27.2; достаточно исходников P3, БД не нужна. Из корня репозитория:

```sh
cd content/projects/p3/reference
go test -run '^TestErrorResponseDoesNotExposeInternalText$' -count=1 -v
rg -n 'NewServer|New.*Handler|type .*Repository interface|func New' --glob '*.go'
```

Откройте найденный конструктор сервера и проследите один вызов: handler → service/use case → переданный repository или pool. Запишите имя конкретной реализации, точку сборки, и тест, который подставляет fake; не называйте fake PostgreSQL. **Ожидайте:** тест проходит, а поиск показывает фактические конструкторы; если отдельный слой/interface отсутствует, зафиксируйте это как наблюдение, не выводите его из названия функции. Это дополняет fake-упражнение, но не подтверждает SQL. **Очистка:** только чтение исходников и тест; внешних ресурсов нет.
