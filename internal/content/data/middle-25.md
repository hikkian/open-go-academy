# Handler, service, repository и DI

## Зачем эта тема нужна

В backend-сервисе тема «Handler, service, repository и DI» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

Handler — транспортный адаптер: он декодирует запрос, проверяет формат и строит безопасный ответ. Service содержит правило продукта и координирует операции. Repository скрывает SQL и модель хранения за интерфейсом, который нужен service. Dependency injection (внедрение зависимости) означает, что объект получает collaborator (зависимость) извне, а не создаёт глобально внутри себя. Composition root (точка сборки) — место, где приложение создаёт конкретные реализации и связывает их.

Easy классифицирует несколько разрешённых операций. Medium проверяет, что service получил repository и clock (часы) явно; часы нужны для детерминированных правил срока и уменьшают зависимость теста от текущего времени. Hard проверяет цепочку handler → service → repository. Эти контракты делают границу видимой, но не подменяют настоящие интерфейсы Go и compile-time wiring. Для реального приложения объявите узкие интерфейсы около потребителя, передайте их в конструктор `NewService`, а в `main` свяжите Postgres repository, system clock и service.

Неправильные признаки: handler выполняет SQL напрямую; service импортирует HTTP типы; repository знает статус кодов; тест зависит от package global. В тесте подставьте fake repository и фиксированные часы, чтобы повторить конфликт и крайний срок. Отдельный integration test поднимает БД и проверяет SQL mapping. Доступность всех dependency bool в этой главе не доказывает здоровье соединения, транзакцию, корректность миграций или успешный сетевой вызов.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «Handler, service, repository и DI». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-25-easy mode=run
package main
import "fmt"

func LayerForOperationEasy(layer, operation string) string {
	if layer == "handler" && (operation == "decode" || operation == "encode") { return "allow" }; if layer == "service" && operation == "domain_rule" { return "allow" }; if layer == "repository" && operation == "sql_write" { return "allow" }; return "misplaced"
}

func main() { fmt.Println(LayerForOperationEasy("handler", "decode")) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «Handler, service, repository и DI» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-25-medium mode=run
package main
import "fmt"

func ServiceWiringMedium(repositoryBound, clockBound bool) string {
	if repositoryBound && clockBound { return "ready" }; if !repositoryBound && !clockBound { return "missing_repository_and_clock" }; if !repositoryBound { return "missing_repository" }; return "missing_clock"
}

func main() { fmt.Println(ServiceWiringMedium(true, true)) }
```

Второй пример меняет вход так, чтобы пересечь границу контракта. Прочитайте его вместе с первым: какой именно параметр изменился и почему результат должен измениться? Эти два запуска проверяют заданное правило, но не обращаются к внешней зависимости и не доказывают её конфигурацию.

## Ошибка, повтор и восстановление

Не открывай БД внутри handler и не создавай зависимости глобально. Собирай concrete implementations в composition root, передавай narrow interfaces конструктору и тестируй через fake repository/clock.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-25-hard mode=run
package main
import "fmt"

func RequestPathReadyHard(handlerBound, serviceBound, repositoryBound bool) bool {
	return handlerBound && serviceBound && repositoryBound
}

func main() { fmt.Println(RequestPathReadyHard(true, true, true)) }
```

Порядок ветвей hard-контракта для «Handler, service, repository и DI» задаёт приоритет при пересекающихся признаках. Зафиксируйте этот приоритет до реализации, а неожиданный ввод обрабатывайте отдельно от успешного результата. Тест-векторы проверяют только выбранные категории; внешний протокол требует отдельного сценария.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy распределяет роли; Medium диагностирует отсутствующую явную зависимость; Hard требует всю цепочку сборки. На практике передай fake repository и clock через конструктор, а production implementation собери в composition root. Compile-time тест и integration test БД нужны сверх таблицы ролей.

## Итог и повторение

Теперь вы умеете описать ограниченную модель темы «Handler, service, repository и DI», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `juniorplus-13`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **handler (обработчик)** — Преобразует HTTP вход и результат use case.

- **service (служба приложения)** — Координирует сценарий и доменные правила.

- **repository (репозиторий)** — Изолирует операции хранения.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «Handler, service, repository и DI» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «если вход меняется с обычного на граничный, решение должно перейти в заранее названную категорию; если зависимость временно недоступна, состояние остаётся восстанавливаемым». Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Проверка composition root

Сборка зависимостей должна быть видна в одном месте: `main` читает конфигурацию, создаёт пул базы, передаёт repository в `NewService`, передаёт service в HTTP handler и запускает сервер. Бизнес-пакет не должен сам открывать сетевой сокет или читать глобальные переменные окружения. Конструктор может отклонить nil dependency, чтобы ошибка конфигурации обнаруживалась при старте, а не в первом запросе.

Fake repository позволяет проверить доменное правило без SQL; фиксируемые часы позволяют воспроизвести срок действия или будущий момент. Не стоит создавать один «mock всего мира»: узкий интерфейс на стороне service обычно проще и остаётся стабильным. Для транзакционных операций repository интерфейс должен отражать границу единицы работы или принимать transaction-scoped executor; случайный набор независимых методов может сделать атомарность неявной.

Для compile-time проверки реализуйте интерфейс конкретным Postgres-адаптером и соберите application wiring. Для unit test подайте fake зависимости и удостоверьтесь, что неверное время или repository error распространяется в ожидаемую domain category. Интеграционный test проверяет migration и SQL. Локальная функция `RequestPathReadyHard` проверяет лишь три объявленных факта wiring: она не вызывает методы, не измеряет health и не подтверждает, что repository связан с правильной базой или tenant.


Не каждую функцию нужно помещать в интерфейс. Если объект не подменяется и не является границей зависимости, concrete type может быть понятнее. Интерфейс полезен, когда потребитель определяет минимальный набор операций, который он использует, а тест или другой адаптер реально предоставляет альтернативную реализацию. Конструкторы должны валидировать обязательные зависимости, возвращать ошибку при некорректной конфигурации и не скрывать соединение с базой в package init. Так приложение обнаруживает ошибку wiring при запуске.


Тест composition root проверяет, что сервис стартует с ожидаемыми конкретными адаптерами и завершается с ошибкой при отсутствующей обязательной конфигурации. Unit-тест сервиса не должен требовать локальную базу. В свою очередь integration test не следует подменять fake repository, если он должен проверить SQL, миграцию или обработку ошибки драйвера.
