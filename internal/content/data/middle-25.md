# Handler, service, repository и DI

## Что ты сделаешь

Ты напишешь три функции с узкими интерфейсами: чтение профиля с проверкой ввода, переименование с разными исходами и создание профиля с аудитом, где сбой второй записи нельзя скрыть. Все зависимости передаются аргументами, а тесты используют подставные реализации.

## Роли трёх слоёв

Обработчик (handler) принимает запрос, превращает его в вызов сценария и переводит результат в ответ. Сервис (service) содержит бизнес-правило: что допустимо, что нужно проверить и в каком порядке. Репозиторий (repository) отвечает за хранение и не решает, можно ли выполнить операцию.

Разделение нужно не ради количества файлов. Каждый слой отвечает на свой вопрос: обработчик — что пришло и что ответить, сервис — допустимо ли действие, репозиторий — что сохранено. Оно позволяет проверить правило без HTTP и без базы. Если правило смешано с кодом запроса, любая проверка требует поднять весь сервер.

## Зависимость передаётся аргументом

Функция, которая сама создаёт соединение с базой, становится непроверяемой. Вместо этого сервис получает интерфейс с нужными ему методами. Интерфейс должен быть узким: если сценарию нужно только чтение, в интерфейсе нет записи. Тогда подставная реализация пишется в пару строк.

Пример показывает такой интерфейс и подставную реализацию на словаре. Тест подменяет хранилище, не трогая функцию:

```go
package main

import "fmt"

type profileReader interface {
    FindProfile(id string) (name string, found bool)
}

type fakeProfiles map[string]string

func (f fakeProfiles) FindProfile(id string) (string, bool) {
    name, ok := f[id]
    return name, ok
}

func main() {
    repo := fakeProfiles{"7": "Алия"}
    var r profileReader = repo
    name, found := r.FindProfile("7")
    fmt.Println(name, found)
}
```

Вывод: `Алия true`. Функция сценария видит только интерфейс, и подмена хранилища не требует изменения её кода. Подставная реализация может возвращать заранее заданные ответы, например отсутствие записи или отказ записи, и тогда каждая ветка сценария проверяется по очереди.

Здесь стоит заметить, что интерфейс объявляет потребитель, а не производитель. Сценарий описывает, что ему нужно, а реализация хранилища подстраивается под это описание. Такой порядок держит зависимости направленными внутрь: сценарий не знает, как устроена база.

> **Важно.** Подставная реализация доказывает, что сценарий правильно использует интерфейс. Она не доказывает, что настоящее хранилище возвращает те же значения.

## Nil-зависимость

Если в интерфейсную переменную не положили реализацию, она равна `nil`, и вызов метода приводит к панике. Поэтому сценарий проверяет зависимости до первого вызова и возвращает понятную категорию. Пример показывает, что такая проверка делается явно:

```go
package main

import "fmt"

type auditSink interface {
    Record(event string) bool
}

func main() {
    var audit auditSink
    fmt.Println(audit == nil)
}
```

Вывод: `true`. Пустая интерфейсная переменная отличается от реализации с пустыми данными, и проверка `== nil` ловит именно первую.

## Порядок вызовов и частичный отказ

Сценарий с двумя записями обязан фиксировать порядок. Если сначала писать аудит, он опишет событие, которого ещё нет. Если создание прошло, а аудит упал, первая запись уже выполнена. Ответ должен это сказать, иначе вызывающий код решит, что ничего не произошло, и повторит создание.

Пример показывает журнал вызовов. Вызовы идут в порядке создание, затем аудит:

```go
package main

import "fmt"

func main() {
    calls := []string{}
    calls = append(calls, "create")
    calls = append(calls, "audit:profile_created")
    fmt.Println(calls)
}
```

Вывод: `[create audit:profile_created]`. Такой журнал тест сравнивает с ожидаемым порядком, и любая перестановка становится видимой.

## Что проверяет локальный тест

Локальный тест проверяет три вещи: ветви правила, порядок вызовов и реакцию на отказ каждой зависимости. Он не проверяет HTTP-код ответа, SQL-запрос, индексы и откат транзакции. Это отдельные проверки, и их результаты нельзя переносить друг на друга.

Локальный тест также не покажет, что ответ сервера соответствует результату сценария. Ошибка в сопоставлении категории с кодом HTTP находится в обработчике, и её нужно проверять тестом обработчика с реальным маршрутом.

Если сценарий пишет в базу и в очередь, локальный тест не покажет, что обе записи атомарны. Для этого нужна транзакция или схема outbox, а их проверяют на реальной базе.

## Модель и механизм

Для слоёв полезны три вопроса. Какой минимум нужен сценарию от каждой зависимости? Какой порядок вызовов обязателен? Что сообщает ответ, если одна из записей не выполнилась? Ответы записываются как интерфейсы и правила до написания функции.

Синхронизация тут не нужна: все функции главы последовательны. Если сценарий станет параллельным, порядок вызовов и журнал придётся защищать отдельно, и тогда подставная реализация должна быть потокобезопасной. Цена подхода — лишний интерфейс там, где зависимость одна и простая. Выделять интерфейс стоит, когда у него есть хотя бы одна подставная реализация в тестах.

## Типичные ошибки и исправление

Первая ошибка — брать широкий интерфейс «на всякий случай». Исправление — объявить только методы, которые использует сценарий.

Вторая — не проверять nil-зависимость. Исправление — явная проверка и отдельная категория ошибки.

Третья — скрывать частичный отказ общей категорией «ошибка». Исправление — ответ, в котором видно, какой эффект уже произошёл.

Четвёртая — считать, что подставная реализация доказывает работу базы. Исправление — отдельный интеграционный тест на настоящем хранилище.

> **Типичная ошибка.** Писать аудит до создания записи «для порядка в логе». Если создание упадёт, аудит опишет событие, которого никогда не было.

## Если что-то пошло не так

- Тест требует поднять сервер и базу → сценарий создаёт зависимости сам; передай их аргументами.
- Паника при запуске сценария без хранилища → не проверена nil-зависимость.
- Повтор создания после ошибки аудита создал дубль → ответ не сообщил о частичном отказе.
- Порядок вызовов в журнале не совпадает с ожидаемым → перепутаны шаги сценария.

### Задание 1 · Узкий интерфейс чтения и простое правило

**Цель.** Объяви интерфейс `ProfileReaderEasy` с методом `FindProfile(id string) (name string, found bool)` и реализуй `WelcomeEasy(repository, id)`. Пустой `id` даёт `"invalid_request"`. Если запись не найдена, верни `"not_found"`. Если запись найдена с пустым именем, верни `"invalid_profile"`. Иначе верни `"hello:"` и имя. Зависимость передаётся аргументом.

**Ожидаемый вывод** — входы: `id = "7"` в fake-репозитории, где у профиля 7 имя «Алия»; затем `id = "404"`, которого там нет; затем пустой `id`:

```text
"hello:Алия"
"not_found"
"invalid_request"
```

**Шаги.**
1. Выбери задание «Узкий интерфейс чтения и простое правило»: в файле есть `WelcomeEasy` с `panic("TODO")`. Интерфейс `ProfileReaderEasy` уже объявлен.
2. Если `id` пустой, верни `"invalid_request"`.
3. Вызови `FindProfile` с `id`.
4. Если запись не найдена, верни `"not_found"`.
5. Если имя пустое, верни `"invalid_profile"`.
6. Иначе верни `"hello:"` с именем.
7. Нажми «Запустить» и сравни с блоком выше.
8. Нажми «Проверить».

**Как проверить себя.** Три строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- `"not_found"` для существующего профиля → флаг `found` не использован.
- `"hello:"` с пустым именем → проверка имени стоит не на месте.
- Паника при пустом `id` → вызов репозитория стоит раньше проверки ввода.

> **Подсказка.** Сначала ввод, потом вызов, потом результат вызова.

### Задание 2 · Use case: переименование и отказ записи

**Цель.** Объяви `ProfileRepositoryMedium` с методами `FindProfile` и `SaveProfile(id, name string) bool`. Реализуй `RenameProfileMedium(repository, id, newName)`. Порядок проверок такой: нет репозитория — `"dependency_missing:0"`; пустой `id` или `newName` — `"invalid_request:0"`; запись не найдена — `"not_found:0"`; пустое старое имя — `"invalid_profile:0"`; имя совпадает с новым — `"unchanged:0"` без записи. Иначе вызови `SaveProfile`: неуспех даёт `"storage_error:1"`, успех — `"updated:1"`.

**Ожидаемый вывод** — входы: профиль 7 со старым именем «Алия», переименование в «Лена», запись проходит; затем профиль 7 с тем же именем «Алия»; затем `id = "404"`:

```text
"updated:1"
"unchanged:0"
"not_found:0"
```

**Шаги.**
1. Выбери задание «Use case: переименование и отказ записи»: в файле есть `RenameProfileMedium` с `panic("TODO")`.
2. Если репозиторий не передан, верни `"dependency_missing:0"`.
3. Если `id` или `newName` пустые, верни `"invalid_request:0"`.
4. Вызови `FindProfile`; если записи нет, верни `"not_found:0"`.
5. Если старое имя пустое, верни `"invalid_profile:0"`.
6. Если имя совпадает с новым, верни `"unchanged:0"`, не вызывая запись.
7. Вызови `SaveProfile`; при неуспехе верни `"storage_error:1"`, иначе `"updated:1"`.
8. Нажми «Запустить» и сравни с блоком выше.
9. Нажми «Проверить».

**Как проверить себя.** Три строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- `"updated:1"` при совпавшем имени → сравнение имён стоит после записи.
- `"unchanged:0"` с вызовом записи → проверка совпадения выполнена после `SaveProfile`.
- `"storage_error:0"` при неуспешной записи → счётчик попыток записи не учтён.

> **Подсказка.** Число после двоеточия считает попытки записи: без вызова записи оно равно нулю.

### Задание 3 · Две зависимости и частичный отказ

**Цель.** Объяви `ProfileCreatorHard` с методом `CreateProfile(name string) bool` и `AuditSinkHard` с методом `Record(event string) bool`. Реализуй `CreateProfileHard(repository, audit, name)`. Неуспешное создание — `"create_error:create"`. Успешное создание с неуспешным аудитом — `"audit_error_after_create:create,audit:profile_created"`. Оба успеха — `"created:create,audit:profile_created"`.

**Ожидаемый вывод** — входы: имя «Илья», обе зависимости успешны; затем создание отказало; затем создание прошло, аудит отказал:

```text
"created:create,audit:profile_created"
"create_error:create"
"audit_error_after_create:create,audit:profile_created"
```

**Шаги.**
1. Выбери задание «Две зависимости и частичный отказ»: в файле есть `CreateProfileHard` с `panic("TODO")`.
2. Если имя пустое, верни `"invalid_request:"`.
3. Если одна из зависимостей не передана, верни `"dependency_missing:"`.
4. Вызови `CreateProfile`; при неуспехе верни `"create_error:create"`.
5. Вызови `Record("profile_created")`; при неуспехе верни `"audit_error_after_create:"` с журналом вызовов.
6. Иначе верни `"created:"` с журналом вызовов.
7. Нажми «Запустить» и сравни с блоком выше.
8. Нажми «Проверить».

**Как проверить себя.** Три строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- `"create_error:create"` при отказе аудита → ошибка аудита перепутана с ошибкой создания.
- `"created:"` без журнала → журнал вызовов не собран.
- Аудит вызван до создания → порядок шагов нарушен.

> **Подсказка.** Журнал вызовов добавляй сразу в момент вызова, а не в конце функции.

## Воспроизводимая лабораторная: подставные зависимости сценария

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Внешние сервисы не нужны: лаборатория работает с подставными реализациями в памяти.

Программа ниже воспроизводит сценарий создания с отказом аудита. Она печатает журнал вызовов и ответ. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import "fmt"

type creator interface{ CreateProfile(name string) bool }
type auditor interface{ Record(event string) bool }

type fakeCreator struct{}

func (fakeCreator) CreateProfile(name string) bool { return true }

type failingAudit struct{}

func (failingAudit) Record(event string) bool { return false }

func create(repo creator, audit auditor, name string) (string, []string) {
    calls := []string{"create"}
    if !repo.CreateProfile(name) {
        return "create_error", calls
    }
    calls = append(calls, "audit:profile_created")
    if !audit.Record("profile_created") {
        return "audit_error_after_create", calls
    }
    return "created", calls
}

func main() {
    result, calls := create(fakeCreator{}, failingAudit{}, "Илья")
    fmt.Println(result, calls)
}
```

**Ожидайте:** одна строка `audit_error_after_create [create audit:profile_created]`. Создание прошло, поэтому журнал содержит оба вызова, а ответ сообщает о частичном отказе.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/<каталог>`.

## Итог

- Сценарий получает зависимости аргументами через узкие интерфейсы, поэтому его правило проверяется без сервера и базы.
- Частичный отказ двух записей сообщает, какой эффект уже произошёл, и не скрывается под общей ошибкой.
- Локальный тест доказывает ветки правила и порядок вызовов; HTTP, SQL и транзакции проверяются отдельно.
