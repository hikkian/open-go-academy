# P5: интерфейсы и контракты

## Что ты сделаешь

Ты задашь версионируемый программный интерфейс между ограниченными контекстами: владельца, входы и выходы, ошибки, срок выполнения и правила совместимости. Три функции урока решают, принимать ли версию запроса, является ли изменение совместимым и готов ли пакет API к ревью. Они не реализуют сервер и не заменяют тесты совместимости между producer и consumer.

## Разбор темы

Общий разбор P5 дан в senior-13; здесь речь о контрактах между компонентами, то есть о том, что обещает интерфейс и что он не обещает.

## Что входит в контракт

Контракт описывает не только форму запроса и ответа. Он называет владельца, допустимые входы и их границы, набор категорий ошибок, срок выполнения, правила повторной отправки и то, что происходит при неизвестных полях. Пока любой из этих пунктов не записан, потребитель будет угадывать поведение по примерам из чужого кода. Удобно начинать с трёх вопросов: кто отвечает за изменение формата, что клиент делает при ошибке категории «временная», и что происходит, если клиент отправил поле, которого сервер не знает.

Поля ответа различаются по устойчивости. Идентификатор и статус обычно стабильны; текст сообщения об ошибке стабилен только для человека и не должен попадать в логику клиента. Если клиент ветвит поведение по тексту, любая правка формулировки станет поломкой, и это надо считать нарушением контракта.

Срок выполнения — тоже часть контракта, и его стоит записывать числом. Фраза «отвечаем быстро» не дает клиенту ничего: он не знает, ждать ли две секунды или двадцать, прежде чем открыть ошибку. Укажите, сколько операция ждёт внутри себя и какой общий срок допускает клиент, включая повторы.

Категории ошибок стоит описать так, чтобы клиент мог выбрать действие по одному полю. Например, «неверный ввод» — не повторять и показать пользователю поле; «временная недоступность» — повторить с паузой; «конфликт версии» — перечитать ресурс и повторить изменение. Текст ошибки для человека может меняться, а категория — нет.

## Совместимость и версии

Изменение формата бывает совместимым и нет. Добавление необязательного поля обычно безопасно, если старые клиенты его игнорируют. Удаление поля или переименование ломает их сразу. Труднее всего заметить смену смысла: поле осталось с тем же именем и типом, но начало означать другие единицы или другой момент времени. Старый клиент продолжит работать и выдавать неверные числа, и никакой ошибки не будет.

Версия фиксирует договорённость. Одна стратегия — версия в пути или заголовке с окном поддержки старой версии, с датой окончания поддержки, которую объявляют заранее. Другая — расширение без новой версии, но с обязательными тестами совместимости. Выбор зависит от того, сколько клиентов и как быстро они обновляются.

Полезно заранее решить, что считается брешью в совместимости. Например: клиент не должен ломаться, если сервер добавил поле в ответ, сменил порядок полей в объекте или добавил новое значение перечисления. Многие клиенты падают именно на новом значении перечисления, если написаны со строгим разбором. Записанное правило даёт команде общий язык при ревью.

Окно поддержки старой версии начинается не с выпуска новой, а с объявления об уходе. Клиенты получают дату, после которой старая версия отвечает отказом, и время на переход. Без этого список потребителей становится неизвестным, и удалить старую версию никогда не удаётся безопасно.

Отдельно стоит описать, что делает сервер с неизвестной версией запроса. Два варианта: отвечать ошибкой с перечнем поддерживаемых версий или молча понизить до последней известной. Второй вариант удобен, но скрывает проблему клиента: он продолжает работать и не знает, что часть его полей игнорируется. Явный отказ лучше длительного тихого расхождения.

## Тесты контракта

Контракт проверяется не только в реализации производителя. Потребитель записывает свои ожидания — какие поля читает, какие ошибки обрабатывает — в виде набора примеров, а производитель запускает эти примеры в своей сборке. Так поломка видна до выпуска, а не у клиента. Такой подход называют consumer-driven тестированием. Он требует, чтобы потребители были известны и могли описать свои ожидания, поэтому для публичного API его дополняют схемой и набором эталонных примеров.

Тест, который проверяет только то, что сервер отвечает 200, ничего не доказывает. Нужны проверки отрицательных случаев: неверная версия, пустое обязательное поле, превышенный срок.

Ещё одна частая ошибка — тестировать только успешные ответы. Клиенту важнее поведение при сбое: повторять ли операцию, как долго ждать, что показать пользователю. Если эти случаи не записаны в контракте, каждая команда реализует их по-своему, и один и тот же отказ будет обрабатываться тремя разными способами.

Фикстуры контракта лучше хранить рядом с кодом потребителя и обновлять вместе с ним. Тогда изменение ожиданий клиента видно в том же ревью, что и изменение сервера. Если фикстуры лежат только у производителя, потребитель узнаёт о поломке через инцидент.

Для каждого из двух изменений укажите, совместимо ли оно, кто из клиентов сломается и каким тестом это проверить. Если у вас нет реального потребителя, назначьте его вымышленным и запишите его ожидания. Результат — текст контракта и список проверок, которые должны падать на сломанной версии.

## Версия контракта на входе

Пример 1 решает, принимать ли запрос по версии контракта. Версия не может быть нулевой или отрицательной; версия выше поддерживаемой не обрабатывается; всё остальное принимается.

```go
package main

import "fmt"

func contractVersion(version, supported int) string {
	if version <= 0 {
		return "invalid"
	}
	if version > supported {
		return "unsupported"
	}
	return "accepted"
}

func main() {
	fmt.Println(contractVersion(2, 3))
	fmt.Println(contractVersion(4, 3))
	fmt.Println(contractVersion(0, 3))
}
```

Вывод: `accepted`, `unsupported`, `invalid`. Явный отказ безопаснее частичного ответа: частичный ответ может незаметно потерять смысл поля, которого клиент не понимает.

## Совместимость изменения

Пример 2 классифицирует изменение контракта. Удаление поля или смена его смысла ломают существующих consumer-ов; чисто добавочное изменение можно рассматривать как кандидата; всё остальное не меняет контракт.

```go
package main

import "fmt"

func changeCompatibility(additive, removesField, changesMeaning bool) string {
	if removesField || changesMeaning {
		return "breaking"
	}
	if additive {
		return "candidate"
	}
	return "no_change"
}

func main() {
	fmt.Println(changeCompatibility(true, false, false))
	fmt.Println(changeCompatibility(true, true, false))
	fmt.Println(changeCompatibility(false, false, false))
}
```

Вывод: `candidate`, `breaking`, `no_change`. Даже добавочное изменение требует проверки старых consumer-ов: новое поле может конфликтовать с их собственной логикой.

## Пакет готовности контракта

Пример 3 собирает пакет API из трёх частей: владельца, каталога ошибок и политики версий. Отсутствие любой из них делает контракт неготовым к ревью.

```go
package main

import "fmt"

func contractReady(hasOwner, hasErrors, hasVersionPolicy bool) bool {
	return hasOwner && hasErrors && hasVersionPolicy
}

func main() {
	fmt.Println(contractReady(true, true, true))
	fmt.Println(contractReady(true, false, true))
}
```

Вывод: `true`, `false`. Флаги фиксируют наличие частей пакета; качество каждой части проверяет ревью и contract test.

## Если что-то пошло не так

- Меняешь единицу поля и оставляешь имя → оформи изменение как новую версию или новое поле с окном совместимости.
- Отвечаешь частично на неизвестную версию → верни явную категорию отказа с версией, которую поддерживаешь.
- Проверяешь контракт только в реализации → добавь consumer-driven тест, который фиксирует ожидания клиента.
- Пакет без владельца или каталога ошибок → не отдавай его на ревью до заполнения всех частей.

## Типичные ошибки контракта

Считать контракт готовым, когда есть только схема без описания ошибок. Ломать клиентов ради красивого имени поля и объяснять это «улучшением». Не назначать владельца контракта, поэтому никто не отвечает за обратную совместимость. Объявлять версию устаревшей без даты, после которой поддержка прекращается. Путать внутренний формат хранения с внешним контрактом и менять его вместе.

## Пример проверки совместимости

Проверка совместимости перед выпуском начинается со сравнения старой и новой схем. Список изменений разбивается на три группы: безопасные (добавление необязательного поля), требующие уведомления (новое значение перечисления), ломающие (удаление, переименование, смена смысла). Для каждой группы из второй и третьей указывается потребитель, которого это затронет, и дата, с которой изменение будет доступно. Такой список проверяется ревьюером отдельно от кода.

## Таймауты и повторы в контракте

Сетевой вызов может завершиться тремя способами: успехом, явной ошибкой и неопределённым исходом, когда ответа не было. Третий случай самый опасный, потому что клиент не знает, выполнилась ли операция. Контракт обязан сказать, безопасно ли повторить запрос и какой ключ идемпотентности его защищает. Для операций без такого ключа правило простое: повтор запрещён, и клиент показывает пользователю состояние «не подтверждено», а не «ошибка».

Повторы без лимита превращаются в собственную нагрузку на сервис. Контракт задаёт число попыток, интервал между ними и общий срок. Ошибки категории «временная» повторяются, «постоянная» — нет. Эта классификация принадлежит контракту, а не клиенту, иначе каждый потребитель решит по-своему.

Если сервер вернул частичный результат, контракт тоже должен это объяснить. Клиент, который получил половину списка без пометки, примет её за полный ответ. Поле «полный ли ответ» или отдельный признак усечения решает проблему раз и навсегда.

### Задание 1 · Easy: P5: интерфейсы и контракты — рабочая запись

**Цель.** Реализуй `ContractVersion(version int, supported int) string`: версия не больше нуля даёт `"invalid"`, версия выше поддерживаемой — `"unsupported"`, иначе `"accepted"`.

**Ожидаемый вывод** — для версии 2 при поддержке 3:

```text
"accepted"
```

**Шаги.**
1. Выбери задание «Easy: P5: интерфейсы и контракты — рабочая запись»: в файле есть `ContractVersion` с `panic("TODO")`. Импорты не нужны.
2. Если версия не положительна, верни `"invalid"`.
3. Если версия выше поддерживаемой, верни `"unsupported"`.
4. Иначе верни `"accepted"`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** В «Результате» одна строка в кавычках; версия 4 при поддержке 3 даёт `"unsupported"`.

**Если не принято.**
- `"accepted"` при версии 4 → сравнение с поддерживаемой версией не выполнено.
- `"unsupported"` при версии 3 → сравнение строгое вместо нестрогого.

> **Подсказка.** Сначала проверка на положительность, потом сравнение с поддержкой.

**Ожидаемый вывод** — для добавочного изменения без удалений и смены смысла:

```text
"candidate"
```

**Шаги.**
1. Выбери задание «Medium: P5: интерфейсы и контракты — decision artifact»: в файле есть `ChangeCompatibility` с `panic("TODO")`.
2. Если поле удаляется или меняется его смысл, верни `"breaking"`.
3. Иначе, если изменение добавочное, верни `"candidate"`.
4. Иначе верни `"no_change"`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Вывод — одна строка в кавычках; случай (false, false, true) даёт `"breaking"`.

**Если не принято.**
- `"candidate"` при удалении поля → проверка удаления стоит после добавочности.
- `"no_change"` при смене смысла → условие смены смысла не учтено.

> **Подсказка.** Сначала ломающие изменения, потом добавочные.

## Итог

- Контракт включает владельца, входы, выходы, ошибки, срок выполнения и правило совместимости; без них интерфейс не версионируем.
- Совместимость определяется смыслом поля, а не только формой JSON: удаление и смена смысла ломают consumer-ов даже при верной структуре.
- Проверка контракта выполняется тестами с обеих сторон, а явная версия и отказ на неизвестной версии защищают от тихих ошибок.
