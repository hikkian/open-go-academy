# Deadlock, утечка goroutine и отмена

## Что ты сделаешь

Ты напишешь три функции-модели: подсчёт заблокированных отправителей, выбор дочерних задач, которые продолжат работу после отмены родителя, и план разблокировки буфера. Главная часть урока — умение найти каждое ожидание и назвать того, кто его завершит.

## Deadlock и утечка — разные симптомы

Deadlock возникает, когда нужный прогресс невозможен. Пример: единственная горутина ждёт получения из канала, в который никто не отправит. Программа останавливается, и runtime сообщает, что все горутины спят.

Утечка горутины устроена иначе. Процесс продолжает работать, но забытая задача навсегда ждёт канал или ресурс. Снаружи оба случая могут выглядеть как зависший тест, поэтому различать их нужно по структуре ожидания, а не по симптому.

## Найди владельца каждого ожидания

Для каждой блокирующей операции назови того, кто её завершит. Receive завершает send или `close`. `WaitGroup.Wait` завершается, когда каждый добавленный участник вызвал `Done`. `Lock` завершается, когда другой владелец вызвал `Unlock`. Если ответа нет, ожидание не имеет владельца, и это место нужно пересматривать.

Удобно записывать ответ прямо в комментарий рядом с ожиданием, например `// ждём: отправитель в jobs; закрывает main после последней отправки`. Через месяц такой комментарий объяснит, почему код не зависнет. При ревью пустой комментарий у блокирующей операции — сигнал, что владелец не назван.

Такой список делается на бумаге до запуска. Для каждого пути выпиши успех, ошибку и отмену. Если на каком-то пути никто не разблокирует операцию, программа рано или поздно повиснет.

```go
package main

import "fmt"

func main() {
    jobs := make(chan int, 1)
    jobs <- 7
    close(jobs)
    for j := range jobs {
        fmt.Println(j)
    }
    fmt.Println("finished")
}
```

Вывод: `7` и затем `finished`. Цикл завершился, потому что владелец отправки закрыл канал. Если бы `close` отсутствовал, цикл ждал бы следующего значения вечно.

## Буфер не лечит отсутствующего получателя

Буферизованный канал допускает несколько отправок без получателя, но лишь до заполнения буфера. Дальше отправитель ждёт так же, как при небуферизованном канале. Поэтому буфер не делает ожидание безопасным: он только сдвигает момент, когда оно появится.

Закрытие канала сообщает получателям об окончании, но не освобождает заблокированного отправителя. Отправка в закрытый канал вызывает панику. Значит, закрывать нужно только тогда, когда отправителей больше нет, и один владелец координирует это решение.

## Отмена кооперативна

Контекст сообщает о намерении остановить работу через канал `Done`. Сам по себе он ничего не останавливает. Горутина, которая не читает `Done`, продолжит работать после отмены, даже если родительский контекст давно отменён.

Для дочерних задач поэтому нужен общий контекст. Работа читает `Done` в местах ожидания и перед побочными эффектами, освобождает ресурсы через `defer` и возвращается. Тихий выход без сообщения может оставить вызывающую сторону ждать результат, которого уже не будет.

Пример рабочего исполнителя, который завершается по закрытию очереди или по сигналу остановки:

```go
package main

import "fmt"

func worker(jobs <-chan int, results chan<- int, done <-chan struct{}) {
    for {
        select {
        case j, ok := <-jobs:
            if !ok {
                return
            }
            results <- j * 2
        case <-done:
            return
        }
    }
}

func main() {
    jobs := make(chan int, 2)
    results := make(chan int, 2)
    done := make(chan struct{})
    jobs <- 1
    jobs <- 2
    close(jobs)
    go worker(jobs, results, done)
    fmt.Println(<-results, <-results)
    close(done)
}
```

Вывод: `2 4`. Исполнитель обработал две задачи по порядку и вернулся, когда очередь закрыта. Канал `done` нужен для досрочной остановки; здесь он закрывается уже после того, как работа завершилась.

## Ограниченное ожидание shutdown

Graceful shutdown ждёт завершения работы, но не бесконечно. После срока система должна сообщить о незавершённой работе: записать журнал, вернуть ошибку или принудительно прекратить ожидание. Тихое продолжение ожидания превращает остановку сервиса в зависание.

У `WaitGroup` нет канала, поэтому в `select` его напрямую не выбрать. Обычный приём: отдельная горутина вызывает `wg.Wait()` и закрывает канал `finished`, а основной код ждёт `finished` или `ctx.Done()`. Тогда ожидание ограничено сроком, и горутина-обёртка завершается сразу после `Wait`. Если срок истёк раньше, обёртка всё равно дождётся `Wait`, поэтому работу, которая не реагирует на отмену, нужно исправлять внутри неё, а не в обёртке.

Срок задаётся через `context.WithTimeout`. Ожидание завершения делается через `select` с веткой готовности и веткой `ctx.Done()`. Если срок истёк раньше готовности, функция возвращает ошибку ожидания, и вызывающий код решает, что делать дальше.

## Модель и механизм

Сначала различай состояние программы и расписание. Состояние — значения, владение ресурсами и открытые каналы. Расписание — чередование шагов, выбранное системой во время исполнения. Корректная программа должна давать допустимый результат при любом расписании, которое разрешено языком.

Для поиска утечки полезны три вопроса. Кто запускает горутину? Кто ждёт её результат? Что произойдёт с ней при ошибке, отмене и срабатывании срока? Ответы записываются рядом с кодом до того, как добавляется канал или таймер.

Синхронизация имеет цену: ожидание, память и сложность. Добавление таймера или отмены не должно скрывать отсутствие владельца. Сначала найди владельца, потом выбирай механизм завершения.

## Как искать утечку в собственном коде

Сначала составь список всех мест, где запускается горутина. Для каждой выпиши, кто её ждёт, кто её отменяет и что будет, если вызывающий код уйдёт раньше результата. Места без ответа на любой из вопросов — первые кандидаты на утечку.

Затем проверь то, что видит runtime. В сервисе с `net/http/pprof` профиль горутин доступен по адресу `/debug/pprof/goroutine?debug=1`. В нём видно, где стоят заблокированные горутины и на какой операции. Если число горутин растёт со временем, а профиль показывает одно и то же место ожидания, это почти наверняка утечка. Профиль снимают до и после нагрузки и сравнивают.

Профиль показывает только то, что было в момент снимка. Поэтому утечку подтверждают повторным сценарием: запуск с отменой, с ошибкой и без них, после каждого шага сравнение числа горутин с исходным.

## Типичные ошибки и исправление

Первая ошибка — отпускать результат наружу, не дождавшись дочерней работы. Вызывающий код получает ответ, а горутина продолжает писать в уже закрытое или забытое место. Исправление — передавать контекст и ждать завершения через `WaitGroup` или канал.

Вторая — проверять утечку через `runtime.NumGoroutine()` сразу после `time.Sleep`. Число может быть случайным и зависеть от планировщика. Тест должен ждать явного сигнала завершения и иметь внешний срок.

Третья — выходить из цикла при отмене, не отправив результат, который ждёт другой участник. Исправление — на пути отмены отправлять ошибку или закрывать канал результата.

> **Типичная ошибка.** Считать, что `cancel()` остановил все горутины, созданные с этим контекстом. Отмена лишь сообщает о намерении, и горутина, которая не читает `Done`, продолжит работу.

## Если что-то пошло не так

- Процесс не завершается после сигнала остановки → какое-то ожидание не имеет владельца; найди блокирующую операцию без парного действия.
- Тест проходит, но горутины накапливаются → работа не читает `Done`; добавь проверку сигнала.
- Shutdown висит дольше срока → ожидание не ограничено контекстом; добавь `select` с `ctx.Done()`.
- Паника `send on closed channel` → закрытие выполнено раньше последней отправки; перенеси закрытие к владельцу.

## Лаборатория перед практикой

Возьми первый пример с `range jobs` и удали строку `close(jobs)`. Перед запуском запиши, что произойдёт после вывода `7`: программа завершится, зависнет или напечатает `finished`. Затем запусти её с таймаутом, например `timeout 5s go run main.go`, и сравни. Если программа зависла, назови ожидание без владельца и восстанови закрытие у владельца отправки.

Журнал эксперимента содержит версию Go, команду с таймаутом, изменённую строку, предсказание, сообщение runtime и исправление. Сообщение «all goroutines are asleep» означает, что ни одна горутина не может продолжить. Запиши это как факт, а не как догадку о причине.

## Практика

### Практический мост: утечки и остановка worker-а

Статусный helper не создаёт зависшую горутину и не доказывает освобождение ресурсов. P3 проверяет присоединение работы и срок shutdown в `content/projects/p3/reference/reference_test.go`: `TestRunWorkersJoinsInflightWork` и `TestWaitForWorkerHonorsShutdownDeadline`. Команда без БД: `cd content/projects/p3/reference && go test -run 'Test(RunWorkersJoinsInflightWork|WaitForWorkerHonorsShutdownDeadline)' -count=1`.

Ожидай завершение управляемой работы после сигнала и конечное ожидание. Для утечки в собственном обработчике добавь каналы входа и выхода и подтверди завершение отменённого пути. Тест P3 не распространяется за пределы своего worker runner-а.

Уровни проверяют разные алгоритмы по теме главы. Векторы охватывают только чистую функцию: они не запускают горутины, не устанавливают happens-before и не заменяют интеграционные проверки.

## Итог

- Для каждой блокирующей операции назван участник, который её завершит, на успехе, ошибке и отмене.
- Отмена контекста кооперативна: горутина должна сама читать `Done` и выходить; ожидание завершения ограничивается сроком.
- Буфер и закрытие канала не заменяют владельца: они меняют момент ожидания, а не его наличие.
