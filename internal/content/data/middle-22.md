# Rate limit и токен-бакет

## Что ты сделаешь

Ты напишешь три функции-модели для ограничения частоты: решение «пропустить или отказать» по остатку токенов, пополнение бакета за прошедшие секунды с пределом ёмкости и расчёт времени ожидания перед повтором. Функции работают с целыми числами и не обращаются ни к часам, ни к хранилищу.

## Что ограничивает токен-бакет

Токен-бакет (token bucket) хранит остаток токенов, но не больше ёмкости (capacity). Каждый запрос списывает свою стоимость (cost). Время добавляет токены с постоянной скоростью. Поэтому бакет ограничивает среднюю скорость и допускает короткий всплеск в пределах накопленного запаса.

Это не то же самое, что окно «не больше N запросов в минуту». Окно считает события внутри интервала, а бакет считает запас. Два правила дают разные ответы на один и тот же поток запросов: после долгой паузы бакет позволит всплеск, а строгое окно — нет.

## Почему токены целые

В учебной модели время измеряется целыми секундами, а токены — целыми единицами. Так правило можно проверить точно, без погрешности округления. Дробное время, миллисекунды и частичные токены требуют отдельного протокола: какие значения округляются, в какую сторону и где хранится дробный остаток.

Целые числа несут и опасность: произведение времени на скорость может выйти за пределы `int64`. Поэтому пополнение сначала проверяет, не достигнет ли запас ёмкости, а уже потом умножает. Пример показывает, как пополнение упирается в предел:

```go
package main

import "fmt"

func main() {
    capacity, available, refill := int64(10), int64(4), int64(2)
    for _, elapsed := range []int64{1, 3, 9} {
        t := available + elapsed*refill
        if t > capacity {
            t = capacity
        }
        fmt.Println(elapsed, t)
    }
}
```

Вывод: `1 6`, `3 10`, `9 10`. После трёх секунд бакет уже полон, и дальнейшее время ничего не добавляет.

## Пополнение с насыщением

Пополнение — это функция от прошедшего времени. За каждую секунду добавляется скорость, но остаток не превышает ёмкость. Если времени прошло много, правильнее сразу вернуть ёмкость, чем вычислять произведение, которое может переполниться.

Модель пополнения и списания стоит держать отдельно. Сначала считается остаток после пополнения. Затем проверяется, хватает ли его на стоимость. Только потом остаток уменьшается. Такой порядок не даёт списать токены, которых нет.

> **Важно.** Пополнение без предела ёмкости — самая частая ошибка. Бакет, который копит токены неделями, позволит гигантский всплеск после простоя.

## Общий лимит и локальный лимитер

Локальный лимитер хранит остаток в памяти одного процесса. Если сервис запущен в трёх экземплярах, каждый даст свой бюджет, и клиент получит втрое больше разрешённых запросов. Общий лимит требует общего состояния, например Redis, и тогда каждое списание становится сетевой операцией.

Ключ бакета тоже нужно выбрать явно. Пользователь, ключ API и адрес клиента дают разные границы: адрес может скрывать за собой целую сеть клиентов, а ключ API позволяет привязать лимит к договорённости. Ключи хранят не дольше окна, в котором лимит имеет смысл, а в журнал пишут не сам ключ, а его короткий отпечаток.

Общее состояние создаёт гонку. Две команды «прочитать остаток, потом записать» позволяют двум запросам увидеть один и тот же остаток и оба списать его. Поэтому чтение и списание выполняют атомарно: скриптом на стороне хранилища или транзакцией с проверкой результата.

## Отказ лимитера

Если хранилище лимитера недоступно, нужна заранее принятая политика. Fail-open пропускает запросы: сервис остаётся доступным, но защита от перегрузки пропадает. Fail-closed отказывает: защита сохраняется, но клиенты получают ошибку вместе с недоступным хранилищем. Выбор зависит от того, что опаснее: перегрузка или недоступность.

Политика должна быть явной в конфигурации и в тестах. Молчаливый выбор при ошибке хранилища часто оказывается fail-open, потому что исключение просто проглатывают.

## Время ожидания перед повтором

Когда запрос отклонён, клиенту полезно знать, через сколько секунд повторить. Ожидание считают по недостающим токенам и скорости пополнения. Недостаток делят на скорость с округлением вверх: если округлить вниз, клиент повторит запрос раньше, чем накопятся токены, и получит новый отказ.

Пример показывает округление вверх без вещественных чисел:

```go
package main

import "fmt"

func main() {
    deficit, refill := int64(3), int64(2)
    fmt.Println((deficit + refill - 1) / refill)
}
```

Вывод: `2`. Для трёх недостающих токенов при двух токенах в секунду нужно ждать две секунды, потому что одна секунда даст только два токена.

Если стоимость больше ёмкости, запрос недостижим при любом ожидании. Если скорость пополнения нулевая, токены не придут вовсе. В обоих случаях повтор бессмыслен, и ответ должен быть другим.

## Модель и механизм

Для ограничения частоты полезны три вопроса. Что считается запасом: токены, окна или очередь? Где лежит состояние и кто его обновляет? Что происходит, когда состояние недоступно? Ответы записываются до выбора библиотеки.

Учебные функции отвечают на вопросы арифметики: хватает ли запаса, сколько он будет через время, сколько ждать. Они не решают, атомарно ли списание, и не выбирают политику отказа.

## Типичные ошибки и исправление

Первая ошибка — пополнять бакет без предела ёмкости. Исправление — насыщение до ёмкости перед каждым списанием.

Вторая — считать локальный лимитер общим. Исправление — либо общее состояние с атомарным списанием, либо явная оговорка, что лимит на процесс.

Третья — округлять ожидание вниз. Исправление — округление вверх, потому что токены становятся доступны только по полной секунде.

Четвёртая — молча пропускать запросы при отказе хранилища. Исправление — явная политика и наблюдаемый счётчик пропущенных запросов.

> **Типичная ошибка.** Проверять остаток и списывать его двумя разными запросами к хранилищу. Между ними параллельный запрос успевает списать тот же остаток.

## Если что-то пошло не так

- Клиенты превышают лимит при нескольких экземплярах → бюджет локальный; перенеси остаток в общее хранилище.
- Всплеск после долгой паузы слишком велик → нет предела ёмкости; проверь насыщение при пополнении.
- Клиенты повторяют запрос и снова получают отказ → Retry-After округлён вниз или не учитывает стоимость.
- Запросы проходят при недоступном хранилище → политика отказа не задана явно.

## Практика

### Задание 1 · Token consume — локальное правило

**Цель.** Вход — `available`, `capacity`, `cost`. Если состояние некорректно (отрицательные значения, `available` больше `capacity`, `capacity` отрицательная) или `cost` не положителен, верни `"invalid"`. Если доступных токенов хватает на стоимость, верни `"allow"`. Иначе верни `"deny"`.

**Ожидаемый вывод** — входы: `5, 10, 3`; затем `2, 10, 3`; затем `10, 10, 10`:

```text
"allow"
"deny"
"allow"
```

1. Выбери задание «Token consume — локальное правило»: в файле есть `TokenDecisionEasy` с `panic("TODO")`. Импорты не нужны.
2. Проверь, что состояние корректно и стоимость положительна; иначе верни `"invalid"`.
3. Если `available` не меньше `cost`, верни `"allow"`.
4. Иначе верни `"deny"`.
5. Нажми «Запустить» и сравни с блоком выше.

**Если не принято.**
- `"allow"` при нехватке токенов → сравнение с `cost` выполнено неверно.
- `"allow"` при отрицательном остатке → проверка состояния пропущена.

> **Подсказка.** Сначала проверка корректности, потом сравнение с стоимостью.

### Задание 3 · Retry-after calculation — отказ и граница гарантии

**Цель.** Вход — `available`, `capacity`, `elapsedSeconds`, `refillPerSecond`, `cost`. > **Подсказка.** Недостаток делится на скорость с остатком: если остаток не нулевой, добавь одну секунду.

## Воспроизводимая лабораторная: бакет с управляемым временем

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Docker не нужен: лаборатория работает с локальной моделью без сети и без внешних сервисов.

Создай временный каталог в `/dev/shm`, положи в него программу ниже и запусти её. Программа проходит три шага: запрос при полном бакете, отказ при пустом и повтор после ожидания. Время задаётся числом секунд, а не часами системы.

```go
package main

import "fmt"

func main() {
    capacity, refill := int64(10), int64(2)
    available := int64(10)
    cost := int64(6)
    fmt.Println("step1", available >= cost)
    available -= cost
    fmt.Println("step2", available >= cost)
    elapsed := int64(2)
    available += elapsed * refill
    if available > capacity {
        available = capacity
    }
    fmt.Println("step3", available >= cost, available)
}
```

**Ожидайте:** первая строка `step1 true`, вторая `step2 false`, третья `step3 true 8`. После отказа бакет содержит четыре токена; за две секунды при двух токенах в секунду он дойдёт до восьми, и запрос на шесть токенов пройдёт.

**Очистка:** удали временный каталог с программой, например командой `rm -rf /dev/shm/<каталог>`. Ничего, кроме этого каталога, лаборатория не создаёт.

## Итог

- Токен-бакет ограничивает среднюю скорость с допуском на всплеск в пределах ёмкости; пополнение всегда ограничено ёмкостью.
- Локальный лимит не даёт общей гарантии: для нескольких экземпляров нужно общее состояние с атомарным списанием.
- Отказ хранилища лимитера требует явной политики fail-open или fail-closed, а время ожидания округляется вверх.
