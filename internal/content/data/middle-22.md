# Rate limit и токен-бакет

## Зачем эта тема нужна

В backend-сервисе тема «Rate limit и токен-бакет» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

Token bucket (токен-бакет) хранит доступный остаток токенов до capacity (ёмкости). Каждый запрос потребляет cost; время добавляет токены с заданной скоростью, но остаток не должен превышать ёмкость. Эта схема ограничивает среднюю скорость и допускает короткий burst (всплеск) в пределах накопленного запаса. Она не тождественна окну «N запросов в минуту» и не ограничивает общий объём пользователя без корректного ключа.

Easy отвечает только на вопрос, хватает ли уже доступных токенов. Medium моделирует refill за целое число секунд, ограничивает bucket capacity, затем списывает стоимость. Вход за пределами модели даёт -1, включая нехватку токенов. Hard рассчитывает Retry-After (время ожидания) для уже пополненного состояния: делит дефицит на скорость вверх, чтобы не разрешить запрос раньше времени. Настоящая реализация должна учитывать дробное время, часы, конкурентное списание, атомарность и верхние границы чисел.

Если состояние в Redis, две команды «прочитать, потом записать» допускают гонку: параллельные запросы увидят один остаток. Нужна атомарная операция, например Lua script, транзакционная конструкция с проверкой результата или другая зависимость с нужной гарантией. Также надо выбрать fail-open или fail-closed при отказе limiter и определить ключ (пользователь, API key, IP), privacy и срок хранения. Функция grader этих условий не проверяет.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «Rate limit и токен-бакет». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-22-easy mode=run
package main
import "fmt"

func TokenDecisionEasy(available, capacity, cost int64) string {
	if capacity < 0 || available < 0 || available > capacity || cost <= 0 { return "invalid" }; if available >= cost { return "allow" }; return "deny"
}

func main() { fmt.Println(TokenDecisionEasy(5, 10, 3)) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «Rate limit и токен-бакет» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-22-medium mode=run
package main
import "fmt"

func RefilledTokensMedium(available, capacity, elapsedSeconds, refillPerSecond, cost int64) int64 {
	if capacity < 0 || available < 0 || available > capacity || elapsedSeconds < 0 || refillPerSecond < 0 || cost <= 0 { return -1 }; refill := capacity - available; if refillPerSecond > 0 && elapsedSeconds > refill/refillPerSecond { available = capacity } else { available += elapsedSeconds * refillPerSecond }; if available > capacity { available = capacity }; if available < cost { return -1 }; return available - cost
}

func main() { fmt.Println(RefilledTokensMedium(4, 10, 2, 2, 7)) }
```

Второй пример меняет вход так, чтобы пересечь границу контракта. Прочитайте его вместе с первым: какой именно параметр изменился и почему результат должен измениться? Эти два запуска проверяют заданное правило, но не обращаются к внешней зависимости и не доказывают её конфигурацию.

## Ошибка, повтор и восстановление

Пополни bucket с cap до списания, но сделай чтение и запись атомарными. Избегай арифметического overflow; при недоступном limiter следуй заранее принятому fail-open/closed policy.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-22-hard mode=run
package main
import "fmt"

func RetryAfterSecondsHard(available, capacity, elapsedSeconds, refillPerSecond, cost int64) int64 {
	if capacity < 0 || available < 0 || available > capacity || elapsedSeconds < 0 || refillPerSecond < 0 || cost <= 0 { return -1 }; if available >= cost { return 0 }; if refillPerSecond == 0 { return -1 }; deficit := cost - available; return (deficit + refillPerSecond - 1) / refillPerSecond
}

func main() { fmt.Println(RetryAfterSecondsHard(2, 10, 0, 2, 5)) }
```

Порядок ветвей hard-контракта для «Rate limit и токен-бакет» задаёт приоритет при пересекающихся признаках. Зафиксируйте этот приоритет до реализации, а неожиданный ввод обрабатывайте отдельно от успешного результата. Тест-векторы проверяют только выбранные категории; внешний протокол требует отдельного сценария.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy принимает решение по текущему остатку; Medium пополняет, ограничивает capacity и списывает cost; Hard округляет ожидание вверх и отдельно обозначает невозможность пополнения. Проверь переполнение и гонку двух одновременных списаний отдельно от helper. Реальный тест должен подтверждать атомарность limiter на выбранной зависимости.

## Итог и повторение

Теперь вы умеете описать ограниченную модель темы «Rate limit и токен-бакет», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `middle-21`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **rate limit (ограничение частоты)** — Правило допуска запросов в заданном интервале.

- **token bucket (токен-бакет)** — Модель, где запрос тратит токен, а время пополняет запас.

- **shared store (общее хранилище)** — Хранилище лимита, совместно используемое процессами.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «Rate limit и токен-бакет» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «если вход меняется с обычного на граничный, решение должно перейти в заранее названную категорию; если зависимость временно недоступна, состояние остаётся восстанавливаемым». Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Конкурентное списание и отказ limiter

Если остаток равен трём и два параллельных запроса стоят по два токена, простое чтение остатка обоими запросами приведёт к двойному allow. Правило должно проверять и списывать атомарно. На одной машине это может быть mutex; в нескольких экземплярах сервиса нужен атомарный протокол в общем хранилище. Успех `TokenDecisionEasy` подтверждает только результат одного снимка состояния и не закрывает гонку.

Отдельно определите ключ бакета и последствия его компрометации. Ограничение по IP может объединить пользователей за NAT; ограничение по user ID требует аутентифицированного идентификатора; ключи не должны содержать секреты в метриках. При недоступности limiter продукт выбирает fail-open (пропустить запрос) или fail-closed (отказать); выбор зависит от того, защищает ли лимитер дорогую инфраструктуру либо влияет на доступность пользовательской операции.

Проверка реализации должна контролировать refill при нулевой скорости, заполнение выше capacity, cost больше capacity, отрицательное время и целочисленное переполнение. Для гонки запустите конкурентные операции над одним бакетом и сравните итоговый остаток с суммой разрешённых затрат. Отдельный integration test проверит атомарный скрипт/транзакцию на настоящем выбранном Redis. Пример главы работает с целыми секундами и не моделирует точность часов или сетевые таймауты.


При вычислении времени ожидания округление всегда направлено вверх: запрос не должен стать допустим раньше расчёта. Если cost превышает capacity, он никогда не пройдёт, даже после бесконечного ожидания; helper возвращает invalid/unavailable marker вместо огромного таймера. Для burst политика определяет, сохраняются ли токены во время простоя и когда начинается новый bucket. Эти правила важнее конкретной формулы, потому что напрямую влияют на пользовательские повторы и нагрузку на API.
