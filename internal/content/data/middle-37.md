# TaskFlow: CRUD, роли и тесты

## Что ты сделаешь

Ты напишешь три проверки, из которых складывается доступ к задачам TaskFlow: таблицу прав роли на действие, порядок решения для чтения и изменения задачи с маскировкой чужого проекта и помощника, который разрешает мутацию только при всех четырёх условиях. Функции получают значения и возвращают ответ. Они не выполняют запросы к базе, не читают сессию и не заменяют интеграционные тесты обработчиков.

## Роли и действия

В TaskFlow три роли. Владелец проекта может читать, менять и удалять задачи. Редактор читает и меняет, но не удаляет. Наблюдатель только читает. Всё, что не записано в таблице прав, запрещено. Это правило важнее любого отдельного исключения: новое действие, добавленное без строки в таблице, по умолчанию закрыто.

Пример 1 показывает таблицу прав в виде словаря. Отсутствующая роль даёт пустой срез, и проверка принадлежности не находит действия.

```go
package main

import "fmt"

var rights = map[string][]string{
	"owner":  {"read", "write", "delete"},
	"editor": {"read", "write"},
	"viewer": {"read"},
}

func main() {
	fmt.Println(len(rights["owner"]), len(rights["viewer"]))
	fmt.Println(rights["editor"][1])
	fmt.Println(len(rights["stranger"]))
}
```

Вывод: `3 1`, затем `write`, затем `0`. Роль `stranger` не описана, поэтому у неё ноль прав. Отсутствие записи означает отказ, а не доступ по умолчанию.

Пример 2 показывает тот же принцип для проверки действия. Важно не только разрешение, но и то, что функция сравнивает роль и действие точно, без приведения регистра и без подстановок.

```go
package main

import "fmt"

var rights = map[string][]string{
	"owner":  {"read", "write", "delete"},
	"editor": {"read", "write"},
	"viewer": {"read"},
}

func can(role, action string) bool {
	for _, a := range rights[role] {
		if a == action {
			return true
		}
	}
	return false
}

func main() {
	fmt.Println(can("editor", "delete"))
	fmt.Println(can("viewer", "read"))
	fmt.Println(can("Viewer", "read"))
}
```

Вывод: `false`, `true`, `false`. Регистр важен: `Viewer` не равен `viewer`, и такая роль не получает права. Если роли приходят из заголовков или токенов, их нормализуют один раз на границе запроса, а не в каждой функции.

## Порядок решения для одной задачи

Доступ к задаче проверяется в фиксированном порядке. Сначала выясняют, аутентифицирован ли пользователь. Если нет, ответ `unauthenticated`. Затем сравнивают проект задачи и проект пользователя. Чужой проект маскируется под `not_found`, чтобы злоумышленник не узнал, что задача существует. И только после этого проверяют право на действие: если его нет, отвечают `forbidden`.

Маскировка работает потому, что отсутствующая задача и задача чужого проекта получают одинаковый ответ. Пример 3 показывает, что функция поиска не различает эти случаи снаружи.

```go
package main

import "fmt"

type task struct {
	id     int
	tenant string
}

var tasks = []task{{1, "acme"}, {2, "globex"}}

func get(id int, tenant string) string {
	for _, t := range tasks {
		if t.id == id && t.tenant == tenant {
			return "found"
		}
	}
	return "not_found"
}

func main() {
	fmt.Println(get(1, "acme"))
	fmt.Println(get(2, "acme"))
	fmt.Println(get(9, "acme"))
}
```

Вывод: `found`, `not_found`, `not_found`. Задача 2 существует, но принадлежит другому проекту, и ответ совпадает с ответом для несуществующей задачи 9. Это и есть маскировка.

Чтение и изменение проверяются по той же схеме. Отличается только последнее действие. Для изменения сверх разрешения нужна валидная запись, и это отдельное условие, о котором речь ниже.

## Тесты и границы помощника

Тесты здесь разделены на два слоя. Помощник с одной функцией проверяется быстро и без сети: положительные и отрицательные случаи таблицы. Интеграционный тест поднимает обработчик и хранилище и проверяет, что путь через HTTP действительно вызывает проверку. Helper-тест не доказывает второй слой: обработчик мог забыть вызвать функцию, и юнит-тест этого не заметит.

Сценарии строят парами. Для каждого разрешения есть отказ рядом: наблюдатель читает, но не пишет; редактор пишет, но не удаляет; пользователь чужого проекта получает `not_found`, а не `forbidden`. Пример 4 показывает таблицу тестов в виде структуры с ожидаемым результатом.

```go
package main

import "fmt"

var rights = map[string][]string{
	"owner":  {"read", "write", "delete"},
	"editor": {"read", "write"},
	"viewer": {"read"},
}

func can(role, action string) bool {
	for _, a := range rights[role] {
		if a == action {
			return true
		}
	}
	return false
}

func main() {
	cases := []struct {
		role   string
		action string
		want   bool
	}{
		{"viewer", "read", true},
		{"viewer", "write", false},
	}
	for _, c := range cases {
		if can(c.role, c.action) == c.want {
			fmt.Println("PASS", c.role, c.action)
		} else {
			fmt.Println("FAIL", c.role, c.action)
		}
	}
}
```

Вывод: `PASS viewer read` и `PASS viewer write`. Таблица удобна тем, что новый случай добавляется одной строкой и сразу попадает в отчёт.

## IDOR и почему помощника мало

Insecure direct object reference, IDOR, возникает, когда обработчик доверяет идентификатору из запроса и не проверяет, принадлежит ли объект пользователю. Пользователь меняет число в адресе и получает чужую задачу. Помощник с правами роли этого не ловит, потому что роль у пользователя законная. Ошибка в том, что проверка принадлежности проекта не вызвана на пути чтения.

Поэтому для IDOR нужен интеграционный тест: создать две задачи в разных проектах, войти под пользователем первого проекта, запросить задачу второго и ожидать `not_found`. Такой тест падает, если кто-то убрал проверку проекта из обработчика, даже когда помощник по-прежнему проходит.

## Тестовый seed

Тестовые данные задают границы. Seed должен содержать хотя бы две организации, по одной задаче в каждой и по одному пользователю каждой роли. Без второго проекта тест маскировки ничего не проверяет. Без наблюдателя не видно, что права не расширяются по цепочке. Seed создаётся заново для каждого теста, иначе порядок запуска начнёт влиять на результат.

## Типичные ошибки и исправление

> **Типичная ошибка.** Проверять права только в помощнике и не проверять, что обработчик его вызывает. Тест помощника проходит, а реальный путь чтения открыт.

Другие ошибки похожи на предыдущие уроки. Таблица прав дополняется в обработчике, и правила нигде не видно целиком. Чужой проект отвечает `forbidden`, и по ответу видно, что задача существует. Seed общий для всех тестов, и один тест меняет данные для другого.

## Если что-то пошло не так

- Пользователь чужого проекта видит `forbidden` вместо `not_found` → маскировка не применена на пути чтения; перенеси проверку проекта раньше проверки права.
- Наблюдатель может изменить задачу → действие `write` отсутствует в таблице, но обработчик не сверяется с ней; проверь вызов.
- Тест проходит локально и падает в общем прогоне → seed общий; создавай данные в каждом тесте.
- Удалённая задача всё ещё читается → удаление не отражено в хранилище или читается кеш; проверь порядок операций.

## Практика

Эти задания проверяют только логику функций. Они не создают пользователей, не обращаются к базе и не проверяют сессию. Закрытые примеры видны только в «Проверить».

**Ожидаемый вывод** — вход: роль `editor`, действие `write`:

**Если не принято.**
- `true` для редактора при удалении → право удаления выдано шире, чем в контракте.
- `true` для неизвестной роли → отсутствие записи не закрыто по умолчанию.
- `false` для наблюдателя при чтении → строка `read` не записана для этой роли.

> **Подсказка.** Сначала запиши права владельца, затем вычитай их для редактора и наблюдателя.

**Шаги.**

**Если не принято.**
- `"forbidden"` для владельца без права чтения → владение должно разрешать доступ само по себе, как в контракте.
- `"forbidden"` вместо `"not_found"` для чужого проекта → порядок проверок перепутан.
- `"allow"` для неаутентифицированного пользователя → первая проверка пропущена.

> **Подсказка.** Порядок такой же, как в тексте: вход, проект, право. Меняя его, меняешь то, что видит злоумышленник.

## Воспроизводимая лабораторная: CRUD и tenant-проверка P3

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Настоящая база не нужна: лаборатория моделирует хранилище в памяти процесса и проверяет пути чтения и удаления.

Программа ниже создаёт два проекта, по одной задаче в каждом и двух пользователей. Она вызывает чтение и удаление от лица разных ролей и печатает ответы в фиксированном порядке. Запусти её во временном каталоге и сравни вывод с ожидаемым.

```go
package main

import "fmt"

type task struct {
	id     int
	tenant string
	title  string
}

type user struct {
	name   string
	tenant string
	role   string
}

var store = map[int]task{
	1: {1, "acme", "Ship"},
	2: {2, "globex", "Audit"},
}

var rights = map[string]map[string]bool{
	"owner":  {"read": true, "write": true, "delete": true},
	"editor": {"read": true, "write": true},
	"viewer": {"read": true},
}

func read(u user, id int) string {
	t, ok := store[id]
	if !ok || t.tenant != u.tenant {
		return "not_found"
	}
	if !rights[u.role]["read"] {
		return "forbidden"
	}
	return "ok " + t.title
}

func remove(u user, id int) string {
	t, ok := store[id]
	if !ok || t.tenant != u.tenant {
		return "not_found"
	}
	if !rights[u.role]["delete"] {
		return "forbidden"
	}
	delete(store, t.id)
	return "deleted"
}

func main() {
	acme := user{"ann", "acme", "viewer"}
	owner := user{"bob", "acme", "owner"}
	fmt.Println("viewer read 1:", read(acme, 1))
	fmt.Println("viewer read 2:", read(acme, 2))
	fmt.Println("viewer delete 1:", remove(acme, 1))
	fmt.Println("owner delete 1:", remove(owner, 1))
	fmt.Println("owner read 1:", read(owner, 1))
	fmt.Println("tasks left:", len(store))
}
```

**Ожидайте:** строки `viewer read 1: ok Ship`, `viewer read 2: not_found`, `viewer delete 1: forbidden`, `owner delete 1: deleted`, `owner read 1: not_found` и итог `tasks left: 1`. Вторая строка показывает маскировку: задача 2 существует в другом проекте и не отличается от отсутствующей.

**Очистка:** программа ничего не создаёт на диске и работает только в памяти процесса. Если запускал её во временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- Права роли записаны таблицей, всё отсутствующее закрыто по умолчанию, а порядок проверки задачи фиксирован: аутентификация, проект, право.
