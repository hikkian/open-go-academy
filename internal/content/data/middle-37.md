**Результат:** Применять роли к конкретному действию и scope, сохраняя порядок authn, tenant и permission checks.; Проверять CRUD handler и хранилище независимыми положительными и отрицательными сценариями.; Не считать helper-функцию заменой интеграционному тесту доступа.

## Глоссарий

- **authentication (аутентификация)** — Проверка учётных данных, после которой известен principal запроса.
- **authorization (авторизация)** — Проверка права principal на действие с конкретным объектом.
- **tenant scope (граница владельца)** — Область данных, к которой principal имеет доступ.
- **least privilege (минимальные полномочия)** — Выдача ровно тех прав, которые нужны данной операции.
- **table-driven test (табличный тест)** — Набор именованных входов и ожидаемых результатов для одного контракта.

## Теория и границы применения

Роли задают доступные действия, а не заменяют идентификацию пользователя. Authentication (аутентификация) устанавливает principal после проверки credential. Authorization (авторизация) решает, разрешено ли этому principal конкретное действие над данным объектом. Не принимайте `user_id`, роль или tenant из тела запроса как доказательство полномочия: доверенный principal должен приходить из проверенного серверного контекста.

Для TaskFlow зафиксируйте небольшую матрицу: owner читает, изменяет и удаляет; editor читает и изменяет; viewer только читает. Неизвестная роль и неизвестное действие запрещены по умолчанию. Затем примените scope: даже owner своей организации не должен менять задачу другого tenant. Ответ `not_found` для чужого объекта может уменьшить утечку его существования; это контракт API, который следует проверить одинаково для чтения и изменения.

Проверка права должна относиться к той же записи, которую меняет SQL. Наивная последовательность «SELECT, проверить tenant, позже UPDATE только по ID» допускает гонку, если состояние или принадлежность изменится между запросами. Предпочтите условную запись с `id`, `tenant_id` и ожидаемым состоянием в условии или подходящую транзакционную блокировку. Различайте отсутствие строки, конфликт состояния и отказ в доступе; детали ответа не должны включать чужие поля.

Валидация не равна авторизации. Корректно сформированный запрос всё ещё может быть запрещён, а разрешённая роль не делает некорректное поле допустимым. Обработчик связывает протокол и статус-код, service выражает доменное правило, repository ограничивает чтение/запись. Такое разделение облегчает тестирование, но интерфейсы сами по себе не создают границу безопасности.

Табличные unit tests полезны для всех сочетаний ролей и действий, включая неизвестные значения. Для handler/service нужны интеграционные проверки с двумя tenant: owner получает разрешённый результат, viewer не может писать, чужой tenant не читает и не меняет запись, unauthenticated не проходит. После отказа перепроверьте состояние базы и логи на отсутствие секретов. Один HTTP 404 ещё не доказывает отсутствие side effect.

`TaskAccess` и `MutationAllowed` моделируют только булевы решения. Они не проверяют создание principal, получение ID из надежного источника, транзакцию, SQL scope, CSRF/credential transport или конкурентное изменение данных. Для вывода о реальном приложении укажите фактически исполненные handler и запрос, окружение, начальные записи и наблюдаемое конечное состояние.

Составьте таблицу тестов не только по ролям, но и по источнику principal и объекту: owner своего проекта, editor своего проекта, viewer своего проекта, любой пользователь чужого tenant, anonymous request, неизвестная роль и удалённый проект. Проверяйте чтение и изменение отдельно: право read не должно случайно расширяться до write. Для каждой строки обозначьте ожидаемый HTTP status, изменится ли запись и что можно безопасно вернуть в ответе. В handler тесте используйте реальные middleware и хранилище проекта, а principal задавайте доверенным test helper-ом, который проходит тот же путь, что и приложение. Подмена заголовка `X-User-ID` не должна создавать authenticated identity, если production так не устроен. При негативном тесте сравните исходную и конечную запись, а не только status code. Имена аккаунтов и токены удаляйте из логов. После этого можно отдельно тестировать матрицу `RoleCan`: она остаётся быстрой проверкой политики, но не имитирует систему авторизации целиком.

## Три самостоятельных запускаемых примера

### Пример 1: `RoleCan`

Контракт: Owner: read/write/delete; editor: read/write; viewer: read; unknown action/role denied.

```go
package main

import "fmt"

func RoleCan(role, action string) bool {
	switch role { case "owner": return action=="read" || action=="write" || action=="delete"; case "editor": return action=="read" || action=="write"; case "viewer": return action=="read"; default: return false }
}

func main() {
	fmt.Println(RoleCan("editor", "write"))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `TaskAccess`

Контракт: Порядок: unauthenticated; чужой tenant маскируется not_found; затем отсутствие права forbidden; иначе allow.

```go
package main

import "fmt"

func TaskAccess(authenticated, sameTenant, isOwner, canRead bool) string {
	if !authenticated { return "unauthenticated" }; if !sameTenant { return "not_found" }; if !isOwner && !canRead { return "forbidden" }; return "allow"
}

func main() {
	fmt.Println(TaskAccess(true, true, true, false))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `MutationAllowed`

Контракт: true только при всех четырёх предусловиях; тестирование helper не заменяет интеграционный тест DB и handler.

```go
package main

import "fmt"

func MutationAllowed(authenticated, sameTenant, canWrite, validInput bool) bool {
	return authenticated && sameTenant && canWrite && validInput
}

func main() {
	fmt.Println(MutationAllowed(true, true, true, true))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

## Лабораторная карточка TaskFlow: TaskFlow: CRUD, роли и тесты

Определите конкретный сценарий с одной пользовательской операцией. Укажите principal, объект, tenant, действие и ожидаемое состояние. Перечислите trust boundary (границу доверия), где вход считается недоверенным, где аутентификация проверена, и какой сервис принимает окончательное решение. Затем перечислите наблюдения: ответ HTTP, доменное событие, запись данных, лог и trace. Если одно из наблюдений отсутствует или запаздывает, результат должен оставаться неопределённым, а не автоматически считаться успешным.

До запуска теста зафиксируйте начальное состояние и независимые данные для двух владельцев. Включите положительный случай и минимум две отрицательные комбинации: неверный tenant, неверная роль, отменённый context, истёкший deadline, закрытие сервера или повторное событие — выберите те, которые относятся к теме главы. Подтвердите, что отрицательный сценарий не меняет данные и не пишет секрет в лог. Если чистый helper не может показать этот эффект, обозначьте интеграционную проверку как отдельное обязательное доказательство.

Наблюдение следует отделить от интерпретации. «Ответ вернул 404» — факт теста; «IDOR невозможен» — слишком сильный вывод. Чтобы обосновать более узкое утверждение, проверьте конкретный endpoint с authenticated principal, запустите запрос с чужим ID и подтвердите отсутствие утечки тела и побочного изменения. Аналогично, один `go test -race` на небольшой набор не гарантирует отсутствия data race при другой последовательности. Укажите точные пути, которые тест фактически исполнил.

Для operational readiness перечислите владельцев процедур: кто меняет readiness, кто наблюдает drain, кто смотрит saturation, кто останавливает нагрузочный тест и кто принимает rollback решение. Пороговые значения должны быть определены владельцами проекта и измерены на сопоставимой среде. Эта программа не задаёт production SLA. Если у учебной системы пока нет измеренных данных, запишите только ожидаемые проверки и назовите статус как непроверенный.

Для failure case определите инъекцию только в тестовой среде и ограничьте воздействие числом запросов, временем либо тестовой очередью. До старта проверьте cleanup и состояние ресурса. После эксперимента подтвердите, что соединения закрыты, временные записи очищены и service вернулся к ready только после проверки обязательной зависимости. При неожиданном результате немедленно прекратите эксперимент и сохраните логи с очищенными секретами. Не расширяйте нагрузку, пока не объяснили расхождение и не повторили исходный контрольный прогон.
