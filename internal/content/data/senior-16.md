# P5: scale-out trade-offs

## Что ты сделаешь

Ты сравнишь варианты масштабирования: реплики без состояния, разбиение данных и вертикальный рост. Для выбранного варианта зададишь профиль нагрузки, измеряемый предел ресурса и первый ограниченный эксперимент. Три функции урока выбирают вариант по состоянию и координации, классифицируют запас мощности и собирают доказательства для сравнения. Они не измеряют систему и не заменяют эксперимент.

## Разбор темы

Общий разбор P5 дан в senior-13. Здесь речь о том, как масштабировать конкретную нагрузку и почему каждый способ масштабирования имеет свою цену.

## Состояние определяет способ масштабирования

Процесс без состояния можно размножить: любой экземпляр обработает любой запрос, и новые реплики подключаются за секунды. Всё, что хранится в памяти процесса, — сессия, кэш, незавершённая операция — становится препятствием. Прежде чем выбирать реплики, выпишите, что именно процесс держит между запросами и где это состояние могло бы жить. Если ответ «в базе» — масштабирование простое, но база становится общим узким местом. Если ответ «в памяти, и его нельзя потерять» — нужна координация или перенос состояния, и тогда реплики без дополнительной работы не помогут.

Различайте состояние, которое можно пересчитать, и состояние, которое пересчитать нельзя. Кэш ответа восстанавливается из источника. Незаписанный платёж — нет. Последствия потери у них разные, поэтому и решения будут разными.

## Партиционирование и горячие ключи

Разбиение данных на части уменьшает нагрузку на каждую часть, но вводит две новые задачи: запросы, которые пересекают части, и перенос данных между ними. Если все запросы касаются одного клиента, его данные хорошо лежат в одной части. Если один клиент создаёт половину нагрузки, эта часть станет горячей, и добавление частей ей не поможет.

Горячий ключ нужно искать измерением, а не предположением. Распределение запросов по ключам показывает, есть ли перекос. Иногда помогает разбиение самого горячего ключа на несколько подключей с последующим объединением результатов, но это усложняет чтение и должно быть записано как осознанное решение.

Выбор ключа разбиения — решение на годы, потому что его почти невозможно изменить без переноса всех данных. Ключ должен распределять нагрузку равномерно и при этом не разрывать данные, которые часто читаются вместе. Если разбить заказы по идентификатору заказа, каждый запрос «все заказы клиента» пойдёт во все части. Если разбить по клиенту, клиент с огромным объёмом станет горячим. Обе ошибки видны только на измеренном профиле, поэтому выбор проверяют до переноса данных.

## Измерять предел, а не оценивать

Расчёт мощности начинается с профиля нагрузки: сколько запросов в секунду, какой размер ответа, какая доля записи. Затем измеряется предел одного экземпляра на этом профиле — точка, где задержка начинает расти быстрее нагрузки. Эта цифра нужна для сравнения вариантов: если один экземпляр держит пятьсот запросов в секунду, а нагрузка 1200, для покрытия потребуется три экземпляра с запасом, и запас тоже надо измерить, а не назначать процентом.

Эксперимент сравнивает варианты при одинаковом профиле: до масштабирования и после, на одном и том же наборе данных. Изменение профиля между прогонами делает сравнение бессмысленным.

Измеряемый предел стоит перепроверять после каждого существенного изменения кода или данных. Предел, снятый на прошлом квартале, не описывает нынешний продукт: новые индексы, другой размер ответов или иной набор клиентов меняют кривую задержки. Поэтому измерение становится регулярной процедурой, а не разовым проектом.

## Кэш как способ масштабирования чтения

Кэш снимает часть чтений с основного хранилища, но переносит проблему свежести. Если данные меняются редко и читаются часто, кэш выгоден. Если они меняются чаще, чем читаются, кэш создаёт нагрузку на инвалидацию и выдаёт устаревшие ответы. Перед введением кэша запишите допустимую задержку свежести и способ инвалидации. Без этого кэш быстро становится источником тонких ошибок, которые трудно воспроизвести.

Полезно заранее выбрать, что клиент увидит, если кэш устарел. Иногда достаточно пометить ответ возрастом данных, иногда лучше повторить чтение из источника при подозрении на расхождение. Выбор зависит от того, что будет хуже для пользователя: старое значение или задержка.

Кэш тоже требует измерения. Доля попаданий показывает, сколько чтений реально снято с базы; если она низкая, кэш добавляет сложности и почти не помогает. Записывайте коэффициент попаданий вместе с нагрузкой на базу до и после введения кэша, иначе трудно понять, принёс ли он пользу.

## Выбор варианта масштабирования

Пример 1 сопоставляет состояние процесса и доступную координацию с вариантом масштабирования. Процесс без состояния можно размножить репликами; процесс с состоянием и координацией — разбить на части; процесс с состоянием без координации сначала требует вынести границу состояния.

```go
package main

import "fmt"

func scaleOption(stateful, coordinationAvailable bool) string {
	if !stateful {
		return "replicas_candidate"
	}
	if coordinationAvailable {
		return "partition_candidate"
	}
	return "state_boundary_first"
}

func main() {
	fmt.Println(scaleOption(false, false))
	fmt.Println(scaleOption(true, true))
	fmt.Println(scaleOption(true, false))
}
```

Вывод: `replicas_candidate`, `partition_candidate`, `state_boundary_first`. Кандидат — это гипотеза для эксперимента: он не говорит, что масштабирование уже безопасно или выгодно.

## Запас мощности

Пример 2 классифицирует измеренный спрос относительно измеренной мощности одной единицы и одного workload. Некорректные числа не обсуждаются; спрос выше мощности — перегрузка; спрос от 80% — запас мал; всё остальное считается достаточным запасом.

```go
package main

import "fmt"

func capacityHeadroom(capacity, demand int) string {
	if capacity <= 0 || demand < 0 {
		return "invalid"
	}
	if demand > capacity {
		return "over_limit"
	}
	if demand*100 >= capacity*80 {
		return "low_headroom"
	}
	return "headroom"
}

func main() {
	fmt.Println(capacityHeadroom(100, 50))
	fmt.Println(capacityHeadroom(100, 90))
	fmt.Println(capacityHeadroom(100, 101))
	fmt.Println(capacityHeadroom(0, 0))
}
```

Вывод: `headroom`, `low_headroom`, `over_limit`, `invalid`. Порог 80% — учебный; реальный порог выбирает владелец по модели отказа и сроку роста.

## Доказательства масштабирования

Пример 3 собирает три вида доказательств для сравнения до и после масштабирования: одинаковый workload, измеренное состояние и отказный тест. Пока хотя бы одного нет, вывод о выгоде не делается.

```go
package main

import "fmt"

func scaleEvidence(sameWorkload, stateMeasured, failureTested bool) bool {
	return sameWorkload && stateMeasured && failureTested
}

func main() {
	fmt.Println(scaleEvidence(true, true, true))
	fmt.Println(scaleEvidence(true, true, false))
}
```

Вывод: `true`, `false`. Флаги отмечают наличие доказательств, а не их качество; без измерения и отказного теста сравнение остаётся предположением.

## Если что-то пошло не так

- Делишь данные на части без анализа горячих ключей → сначала измерь распределение нагрузки и границы состояния.
- Сравниваешь результаты при разном workload → зафиксируй профиль нагрузки до и после изменения.
- Считаешь helper-проверку границ доказательством мощности → проведи нагрузочный эксперимент с критерием остановки.
- Запускаешь масштабирование без отказного теста → проверь поведение при потере реплики или зоны.

## Типичные ошибки масштабирования

Масштабировать веб-процессы, когда узкое место — база данных. Добавлять реплики к процессу с состоянием в памяти без переноса этого состояния. Считать предел по синтетическому тесту с равномерным распределением ключей, хотя в продукте есть горячие клиенты. Назначать запас процентом без измерения хвоста задержки. Сравнивать результаты до и после при разном профиле нагрузки и приписывать разницу масштабированию.

## Перенос состояния по шагам

Если процесс хранит состояние в памяти, перенос в общее хранилище делают по шагам, а не одной заменой. Сначала новый код учится записывать состояние и в память, и в хранилище, и сверяет результаты. Затем чтение переключается на хранилище, а запись в память прекращается. Только после того, как старые экземпляры полностью выведены из работы, удаляется код, который хранил состояние локально. Каждый шаг можно откатить, и каждый шаг имеет критерий перехода: например, расхождение между двумя источниками ноль на протяжении суток.

Такой порядок медленнее, зато не превращает перенос в одномоментный риск. Если на каком-то шаге видно расхождение, работа останавливается, а не продолжается в надежде, что оно рассосётся.

## Сценарий отказа при масштабировании

Масштабирование меняет сценарий отказа. Один экземпляр, который падал раз в месяц, при десяти экземплярах падает чаще, и вероятность одновременного падения двух возрастает. Если процесс с состоянием привязан к экземпляру, его потеря означает потерю части данных или сессий. Поэтому до масштабирования надо ответить, что случится, если один экземпляр исчезнет посреди запроса, и сколько пользователей это затронет.

Для разбиения по части данных важна отдельная проверка: что происходит с частью, когда её хранилище недоступно. Если все остальные части работают, ошибка должна касаться только клиентов этой части, а не всего сервиса. Эту проверку выполняют на стенде, отключая одну часть за раз.

## Что записывать в решение о масштабировании

Решение о масштабировании должно содержать профиль нагрузки с датой, измеренный предел одного экземпляра, выбранный вариант с причиной, отклонённые варианты, ожидаемый эффект с условием проверки и критерий отката. Без профиля и предела эффект нельзя ни проверить, ни оспорить. Такой документ короткий, но должен позволять человеку, который не участвовал в обсуждении, понять, почему выбран именно этот путь.

## Итог

- Вариант масштабирования выбирается по состоянию процесса и доступной координации, а не по моде на микросервисы или шардинг.
- Запас мощности измеряется по одному workload и одной единице; пороги задаёт владелец по модели отказа и сроку роста.
- Выгода масштабирования подтверждается сравнением при одинаковом workload, измеренном состоянии и отказном тесте.
