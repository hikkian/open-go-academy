# Параллельная работа и конкурентность

## Что ты сделаешь

Ты напишешь три чистые функции, которые моделируют распределение задач между исполнителями: `ConcurrencyCapacity` считает, сколько задач реально идут одновременно, `AssignWorkers` раздаёт задачи по кругу, `WorkerLoads` считает нагрузку каждого исполнителя. Параллельно ты прочитаешь и запустишь три настоящих конкурентных примера на `WaitGroup`, `Mutex` и `context`, научишься объяснять, что именно они гарантируют, и получишь мост к проекту P3, где те же идеи проверяются на реальной базе.

## Конкурентность и параллелизм — не одно и то же

Конкурентность (concurrency) — структура программы, в которой несколько независимых работ могут продвигаться в перекрывающиеся интервалы: пока одна ждёт ввод, другая использует процессор. Параллелизм (parallelism) — физическое исполнение в одно и то же время на разных ядрах. Одноядерная машина чередует горутины (goroutine — лёгкая задача Go), многоядерная может исполнять их параллельно. Поэтому «конкурентно» не означает «быстро»: координация сама стоит времени, а планировщик (scheduler) среды выполнения выбирает, какую готовую горутину запустить следующей, и момент переключения не входит в контракт языка.

Представь кассу и кухню. Заказ готовится независимо от того, кто сейчас платит — это перекрытие работ. Два повара режут разные овощи — параллельная работа. Два повара правят один рецептный лист — им нужен общий договор. Весь урок про этот договор.

> **Важно.** Корректная программа даёт допустимый результат при любом расписании, которое разрешают язык и примитивы. Если ответ верен только потому, что «эта горутина, наверное, выполнится первой», контракта нет.

## Состояние и расписание

Разделяй две вещи. Состояние — значения, владение ресурсами, открытые каналы. Расписание — чередование шагов, которое выбирает система во время исполнения. Перед тем как добавить канал, mutex или транзакцию, ответь на четыре вопроса и запиши ответы рядом с кодом: кто владеет изменяемым состоянием; какая операция передаёт владение или синхронизирует доступ; кто сообщает об окончании; что происходит при ошибке или отмене.

Цена ошибки конкретна: потерянное обновление, зависший запрос, повторный платёж, медленный shutdown, очередь, которая растёт быстрее обработки. Синхронизация тоже стоит денег: блокировка создаёт ожидание, копирование тратит память, более сильная изоляция в базе повышает вероятность конфликта, поэтому сначала сохраняют инвариант, а потом измеряют полный путь типичной нагрузки. Описывай отказ тремя фразами: какое состояние было до события, какие две операции пересеклись, какой неверный результат появился.

## Завершение делают явным

`go f()` — это только запуск. Чтобы знать, что работа закончена, нужен явный сигнал. В примере два производителя пишут квадраты чисел в канал, `sync.WaitGroup` дожидается обоих, и только после этого отдельная горутина закрывает канал.

```go group=middle-01-example1 mode=run
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    results := make(chan int, 2)
    for _, v := range []int{2, 3} {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            results <- n * n
        }(v)
    }
    go func() {
        wg.Wait()
        close(results)
    }()
    total := 0
    for n := range results {
        total += n
    }
    fmt.Println(total)
}
```

Вывод:

```text
13
```

Порядок прихода 4 и 9 не определён, но сумма — всегда 13: программа не зависит от расписания. Три точки держат контракт: `wg.Add(1)` до запуска горутины, `defer wg.Done()` в её начале, `close(results)` только после `wg.Wait()`. Закрыть канал, пока отправители живы, — паника; закрывать из нескольких мест — тоже. Право закрытия у одного владельца.

> **Типичная ошибка.** `time.Sleep` как синхронизация. Задержка делает тест стабильным на одной машине, но не задаёт отношение «произошло раньше» (happens-before). Жди событие, а не время.

## Общее состояние защищают там, где его трогают

Карта в Go не безопасна для одновременной записи. Mutex (блокировка взаимного доступа) защищает только те обращения, которые его берут: достаточно одного чтения без `Lock`, и гонка вернётся.

```go group=middle-01-example2 mode=run
package main

import (
    "fmt"
    "sync"
)

func main() {
    var mu sync.Mutex
    counts := map[string]int{}
    var wg sync.WaitGroup
    for _, key := range []string{"a", "b", "a"} {
        wg.Add(1)
        go func(k string) {
            defer wg.Done()
            mu.Lock()
            counts[k]++
            mu.Unlock()
        }(key)
    }
    wg.Wait()
    fmt.Println(counts["a"], counts["b"])
}
```

Вывод:

```text
2 1
```

Составь две колонки: «что гарантирует код» и «что остаётся за его пределами». Mutex гарантирует, что инкременты не теряются; он ничего не говорит о порядке, о производительности и о поведении, если кто-то обратится к `counts` без него. Буферизованный канал тоже не лечит блокировку — он лишь сдвигает порог: если потребитель не читает, буфер заполнится.

## Отмена кооперативна

Контекст (`context`) не останавливает горутину силой. Код должен сам читать `ctx.Done()` и завершаться, а каждая зависимость — принимать переданный контекст. В примере отмена происходит до начала работы, и работа честно сообщает об этом.

```go group=middle-01-example3 mode=run
package main

import (
    "context"
    "fmt"
)

func work(ctx context.Context, result chan<- string) {
    <-ctx.Done()
    result <- "cancelled"
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    cancel()
    ch := make(chan string, 1)
    work(ctx, ch)
    fmt.Println(<-ch)
}
```

Вывод:

```text
cancelled
```

Отменить ожидание родителя и забыть дочернюю работу — шестая по счёту, но первая по частоте ошибка в сервисах: запрос ушёл, а горутина продолжает писать в базу.

## Как читать сбой

Пять наблюдений и что проверять в каждом:

- **Прогресс остановился** → есть ожидание без возможного отправителя или разблокировки: выпиши все `send`, `receive`, `Lock`, `Wait` и владельца каждого.
- **Иногда неверный результат** → конкурирующий путь обходит общий протокол: повтори тест с `-race`, затем проверь каждое обращение к данным вручную.
- **Результат есть, но порядок другой** → контракт обещал набор, а ты ждал порядок: зафиксируй, нужен ли порядок и где он создаётся.
- **Ошибка после отмены** → отмена не дошла до зависимости или поздней записи: передай `context` в каждую точку побочного эффекта.
- **Транзакция видит неожиданное значение** → не определены уровень изоляции и граница снимка (snapshot): запиши порядок `commit` и SQL-команд (statement) и повтори на PostgreSQL.

> **Зачем.** Зелёный `-race` означает «гонка не найдена на исполненных путях», а не «гонок нет». Детектор проверяет увиденные расписания; остальное дают разные входы, ручной аудит доступов и ограниченная нагрузка.

## Если что-то пошло не так

- `fatal error: all goroutines are asleep - deadlock!` → кто-то ждёт канал, в который никто не пишет, или `Wait` без `Done`.
- `panic: send on closed channel` → канал закрыт раньше, чем закончились отправители.
- `concurrent map writes` → запись в карту без mutex.
- В задании `null` вместо `[]` → вернул nil-срез; создавай результат через `make([]int, 0)`.
- `import … is not allowed` → в заданиях урока импорты запрещены: это чистая арифметика над двумя числами.

## Практика

### Практический мост: от модели к реальному параллельному worker-у

Три функции ниже считают значения для чистых входов `[workers, tasks]`. Они не создают горутины, не синхронизируют доступ и не проверяют инвариант при реальном расписании — это модель раздачи задач, которую ты будешь держать в голове, читая настоящий код. Настоящая практика конкурентности в курсе — проект P3: обработчики таблицы исходящих событий (outbox workers) доставляют события параллельно, и тест `TestPostgresTaskOutboxAndTenantIsolation` в `content/projects/p3/reference/postgres_integration_test.go` проверяет, что подтверждение (receipt) ровно одно.

Запустить его можно на одноразовом PostgreSQL из Compose проекта P3 (нужны Go, Docker Compose v2 и OpenSSL; пароль живёт только в окружении оболочки, контейнер и том удаляются при выходе из блока):

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle01 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидай один конечный эффект при конкурентной доставке. Это проверка outbox на PostgreSQL, а не всех расписаний Go: зелёный тест не доказывает отсутствие гонок в другом коде.

Все три функции получают один срез `values` из двух чисел `[workers, tasks]` и возвращают срез. Среда показывает результат как JSON-список; пустой список — `[]`, а `null` считается ошибкой.

### Задание 1 · Параллельная работа и конкурентность — easy

**Цель.** Для `[workers, tasks]` вернуть `[min(workers, tasks)]`; при отрицательном значении — `[0]`.

**Ожидаемый вывод** — для `[3, 7]` и `[0, 4]`:

```text
[3]
[0]
```

**Шаги.**
1. Выбери задание «easy»: сигнатура `func ConcurrencyCapacity(values []int) []int`. Импорты запрещены.
2. Если `len(values) != 2` или любое из двух чисел отрицательно, верни `[]int{0}`.
3. Иначе верни `[]int{меньшее из двух}`.
4. «Запустить», сравни. «Проверить» — закрытые примеры: `[4, 2]` → `[2]`, `[-1, 5]` → `[0]`.

**Как проверить себя.** Семь задач при трёх исполнителях — одновременно идут три; ноль исполнителей — ноль задач; ответ всегда список из одного числа.

**Если не принято.**
- Красный закрытый пример `[-1, 5]` → проверка знака отсутствует или стоит после вычисления минимума.
- В «Получили» число без скобок → функция должна вернуть срез из одного элемента, не `int`.

> **Подсказка.** Минимум из двух чисел — одно `if`: начни с `n := values[0]` и замени его, если `values[1]` меньше.

### Задание 2 · Параллельная работа и конкурентность — medium

**Цель.** Для `[workers, tasks]` вернуть индекс исполнителя для каждой задачи по кругу; при `workers <= 0` или `tasks < 0` — пустой список.

**Ожидаемый вывод** — для `[3, 7]` и `[2, 4]`:

```text
[0,1,2,0,1,2,0]
[0,1,0,1]
```

**Шаги.**
1. Выбери задание «medium»: сигнатура `func AssignWorkers(values []int) []int`. Импорты запрещены.
2. Если `len(values) != 2`, `values[0] <= 0` или `values[1] < 0`, верни `[]int{}`.
3. Создай `out := make([]int, tasks)` и заполни `out[i] = i % workers`.
4. «Запустить», «Проверить» — закрытые примеры: `[1, 0]` → `[]`, `[0, 3]` → `[]`.

**Как проверить себя.** Длина ответа равна числу задач; индексы идут 0, 1, 2, 0, 1, 2…; для нуля задач — `[]`, не `null`.

**Если не принято.**
- `null` в «Получили» → вернул `nil`; для нуля задач `make([]int, 0)` даёт `[]`.
- Красный закрытый пример `[0, 3]` → ноль исполнителей — некорректный вход (`<= 0`), деление по модулю на ноль привело бы к панике.
- Индексы начинаются с 1 → исполнители нумеруются с нуля.

> **Подсказка.** `i % workers` — это и есть «по кругу»: седьмая задача (индекс 6) при трёх исполнителях уходит к `6 % 3 = 0`.

### Задание 3 · Параллельная работа и конкурентность — hard

**Цель.** Для `[workers, tasks]` вернуть, сколько задач достаётся каждому исполнителю при раздаче по кругу; некорректный вход — пустой список.

**Ожидаемый вывод** — для `[3, 7]` и `[4, 2]`:

```text
[3,2,2]
[1,1,0,0]
```

**Шаги.**
1. Выбери задание «hard»: сигнатура `func WorkerLoads(values []int) []int`. Импорты запрещены.
2. Та же проверка входа, что в задании 2: при нарушении верни `[]int{}`.
3. Создай `out := make([]int, workers)` и для `i` от 0 до `tasks-1` увеличь `out[i % workers]`.
4. «Запустить», «Проверить» — закрытые примеры: `[0, 4]` → `[]`, `[-1, 2]` → `[]`.

**Как проверить себя.** Длина ответа равна числу исполнителей, сумма элементов — числу задач; при `[4, 2]` два исполнителя простаивают с нулём.

**Если не принято.**
- Длина ответа равна числу задач → перепутаны роли: здесь срез по исполнителям, в задании 2 — по задачам.
- Сумма элементов меньше числа задач → цикл до `tasks` без последней итерации (`<`, не `<=`, но от нуля).
- `null` вместо `[]` → см. задание 2.

> **Подсказка.** Сравни с заданием 2: там ты записывал `i % workers` как значение, здесь используешь его как индекс.

## Итог

- Определи владение и инвариант до выбора механизма: кто владеет состоянием, кто синхронизирует, кто сообщает о завершении, что происходит при отмене.
- Завершение — явный сигнал (`WaitGroup`, закрытие канала одним владельцем), защита состояния — там, где его трогают, отмена — кооперативная через `context`.
- Локальная демонстрация и зелёный `-race` не доказывают системных свойств; для них есть интеграционный тест P3 на реальной базе.
