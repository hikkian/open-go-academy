## Пакеты, модули, документация и Git

Пакет (package) — единица организации и повторного использования Go-кода. Файлы в одной папке обычно объявляют одинаковое имя пакета и компилируются вместе. Импортируется пакет по пути модуля и папки, а не по имени файла. Пакет main создаёт исполняемую команду; обычный пакет предоставляет типы и функции другим пакетам.

Экспортируемое имя (exported identifier) начинается с заглавной буквы. Остальные пакеты видят только экспортируемые имена. Это правило действует для функций, типов, методов и полей структуры. Внутри пакета можно использовать закрытые имена с маленькой буквы. Не экспортируйте всё автоматически: публичный API сложнее менять.

Модуль (module) — версия и корень графа зависимостей, обозначенный go.mod. Директива module задаёт путь импорта, например example.local/academy; локальная папка calc доступна как example.local/academy/calc. `go mod init` начинает модуль, `go test ./...` проверяет пакеты рекурсивно. В этой платформе эти учебные команды показываются как команды, а не как Go fences.

Импорт связывает код с публичным именем пакета. Циклические зависимости запрещены: если A импортирует B, B не может импортировать A. Размещайте общие типы там, где они принадлежат по смыслу, а не создавайте пакет common для случайной смеси. Небольшие зависимости направлены внутрь к стабильной логике; командный пакет обычно собирает конфигурацию и вызывает функцию приложения.

Документация пакета начинается с комментария, который начинается с имени пакета. Комментарий экспортированной функции начинается с её имени и объясняет контракт: что принимается, что возвращается, какие ошибки возможны. Документация не должна пересказывать тело; она объясняет, как безопасно вызвать API и какие гарантии существуют.

Git — система контроля версий (version control). Рабочая копия содержит текущие изменения; staging area выбирает изменения для следующего коммита; commit сохраняет снимок и сообщение. `git status` показывает состояние, `git diff` показывает незастейдженные изменения, `git diff --staged` — staged, `git log` — историю. GitHub не обязателен для локальной истории.

Безопасный цикл: сначала `git status`, затем сделать небольшое законченное изменение, просмотреть `git diff`, запустить проверки, добавить только нужные файлы, просмотреть staged diff и создать коммит с конкретным сообщением. После коммита снова проверьте статус. Не используйте `git reset --hard` как способ «попробовать» — эта команда может удалить незакоммиченные изменения.

Коммит — не резервная копия и не подтверждение качества. Он фиксирует состояние, но не проверяет код. Разделяйте изменения так, чтобы сообщение объясняло намерение. Не коммитьте токены, базы данных, бинарные сборки и персональные данные. Перед передачей ветки проверьте diff и историю. В команде согласуйте общие правила ветвления отдельно.

ParseArgs в упражнении демонстрирует парсер среза аргументов без чтения os.Args, поэтому функцию можно тестировать. Контракт: пары `--name value` и `--limit integer`; неизвестные, повторные и неполные ключи — ошибка. Это не полная библиотека CLI и не запускает процесс. Для настоящей команды следует продумать help, stderr, exit codes и документацию.

Тестируйте parser на пустом наборе, корректных парах, отрицательном числе, неверном числе, повторном ключе и пропущенном значении. Ошибка должна быть полезна, но упражнение не проверяет точный текст. В будущем файлы и JSON добавят дополнительные ошибки и ресурсы; пока держим парсер чистой функцией.

Не добавляйте внешний модуль ради трёх аргументов. Зависимость имеет стоимость обновления, аудита и поставки. Стандартная библиотека подходит небольшому контракту. Для крупного CLI внешняя библиотека может быть разумна после обзора поддержки, лицензии и совместимости, но это отдельное архитектурное решение.

### Полная программа: отдельный пакет

Два файла относятся к одному модулю. Сохраните `calc/calc.go` и `main.go` в соответствующих путях. Импорт соответствует module path.

```go group=packages file=calc/calc.go mode=run
package calc

// Add складывает два числа.
func Add(a, b int) int { return a + b }
```

```go group=packages file=main.go mode=run
package main

import ("fmt"; "example.local/academy/calc")

func main() { fmt.Println(calc.Add(2, 3)) }
```

Модуль использует `module example.local/academy` и версию Go из учебной среды. Вывод `5`. В одном каталоге нельзя смешивать разные имена пакетов, кроме специальных test-файлов.

### Пример Git-проверки и упражнения

В терминале это команды: `git status`, `git diff`, затем после проверки `git add calc/calc.go main.go`, `git diff --staged`, `git commit -m "add calculator package"`, `git log -1`. Команды показывают состояние, но их наличие в уроке не выполняет действие за студента. Сначала убедитесь, что это именно учебная копия проекта. Никогда не запускайте разрушительную команду, не понимая её эффект.

Easy вынеси helper в экспортируемый пакет; Medium реализуй ParseArgs с явным контрактом; Hard составь сфокусированный commit и восстанови ошибочную правку, используя status/diff/log, без удаления чужих изменений. Автоматический функциональный грейдер проверяет только парсер. Качество Git-истории и понимание команд — ручной критерий. Практикуй тестирование через P1 workspace и `go test ./...`.

### Самопроверка и словарь

1. Чем package отличается от module? 2. Как имя становится экспортируемым? 3. Что задаёт import path? 4. Что проверяет `git diff --staged`? 5. Почему коммит не заменяет тест? 6. Зачем парсер принимает []string? 7. Что сообщает go test ./...? 8. Почему опасен reset --hard? Ответы: каталог кода против корня зависимостей/версии; заглавная первая буква; module path плюс папка; выбранные staged изменения; он сохраняет снимок, не доказывает поведение; детерминируемость и изоляция; запускает тесты всех пакетов; может отбросить незакоммиченную работу.

Если импорт не находится, сверь module в go.mod, путь каталога и регистр имени. Если имя недоступно, проверь заглавную букву. Если diff пуст, проверь текущую папку и сохранение файла. AI Tutor не нужен для команд: прочитай вывод status и diff; не копируй секреты в чат.

**Мини-глоссарий:** package — пакет; module — модуль; import path — путь импорта; exported — экспортируемый; dependency — зависимость; repository — репозиторий; staging — подготовка изменений; commit — коммит; diff — разница.

## Границы пакета как способ объяснить программу

Хорошая структура пакетов помогает читателю найти ответственность. Командный пакет обычно небольшой: разобрать окружение, построить зависимости и вызвать основной сценарий. Бизнес-правила полезно держать отдельно от терминала и файловой системы, если это даёт реальную повторную проверку. Но не разбивайте каждую функцию в отдельную папку: импорт и навигация тоже имеют цену.

Публичный API пакета — обещание совместимости. Экспортированные функции и поля используются внешним кодом, поэтому переименование может сломать потребителей. Начинайте с закрытых helper-функций и экспортируйте только то, что нужно другой границе. Комментарий к API помогает читать `go doc` и поисковые подсказки. Он должен называть ограничения, порядок и ошибки, если от них зависит корректное использование.

Имя пакета и путь импорта — разные понятия. Каталог `calc` может объявить `package mathutil`, и импортируемый идентификатор по умолчанию будет mathutil, хотя путь заканчивается на calc. Обычно имена делают согласованными. Путь включает module path и каталог; Go ищет код по модулю, а не по названию файла. Относительные импорты в модульном приложении не являются правильным способом связывать пакеты.

`go.mod` фиксирует путь модуля, минимальную версию языка/инструментария и зависимости. Суммы в `go.sum` помогают проверить содержимое внешних модулей. Не редактируйте суммы вручную. Для учебных примеров внешний модуль не нужен. Если проект всё-таки добавляет библиотеку, зафиксируйте обоснование, версию и проверку лицензии, а затем запустите тесты.

## Практический Git: наблюдать до изменения

Git работает с файлами проекта, поэтому сначала проверьте `pwd` и `git status`. Убедитесь, что вы в нужном репозитории и видите только ожидаемые изменения. Если другие файлы изменены, не включайте их автоматически. `git add -p` позволяет выбрать части файла, но его интерактивный интерфейс требует внимательности. После staging просмотрите `git diff --cached`.

Коммит должен отвечать, что изменено и зачем: «добавить проверку пустого имени» полезнее, чем «fix». Не помещайте в одно изменение рефакторинг, форматирование всего проекта и несвязанную функцию, если их можно разделить. Малые коммиты проще проверить и откатить. При этом не делите настолько мелко, что каждый снимок не собирается без причины.

`git log --oneline` показывает краткую историю, `git show` раскрывает один commit, а `git diff HEAD` сравнивает рабочее состояние с последним снимком. Эти команды помогают понять контекст до исправления. Если файл уже изменён кем-то ещё, прочитайте diff и сохраните чужую работу. Не используйте force push или очистку истории без согласованного процесса команды.

Восстановление зависит от того, где находятся изменения. Незастейдженный файл можно вернуть из конкретной версии, staged изменение можно снять со staging, коммит можно исправить новыми коммитами или согласованной операцией. Нет одной безопасной команды для всех случаев. Сначала сохраните копию или отдельную ветку и выясните состояние; затем выбирайте точное действие. Учебное задание просит осмыслить diff/status, а не запускать destructive-команду вслепую.

## Пакетная документация и локальная проверка

В README указывают назначение, требования к версии Go, быстрый запуск, тесты, формат конфигурации и ожидаемые ошибки. Установка должна быть воспроизводимой, а пример не должен требовать личного аккаунта, оплаченного сервиса или секретного файла. Комментарий в исходнике описывает API, README — путь пользователя. Они дополняют друг друга.

Перед передачей проверьте `go fmt`/`gofmt`, `go test ./...` и `go build ./...` согласно проектным инструкциям. Сборка всех пакетов обнаруживает недостающие импорты и доступность экспортируемых символов. Тесты не подтверждают лицензию и содержание README; эти вещи проверяются отдельно. Чистый статус после коммита помогает увидеть, не осталось ли забытого файла.

### Пример: экспортируемая функция пакета

```go
package main

import "fmt"

type Profile struct { Name string }
func DisplayName(p Profile) string { return p.Name }
func main() { fmt.Println(DisplayName(Profile{Name:"Алия"})) }
```

Вывод: `Алия`. DisplayName и поле Name экспортированы; локальный helper с маленькой буквы не виден импортирующему пакету.

### Пример: чистый разбор пары аргументов

```go
package main

import "fmt"

func hasFlag(args []string, flag string) bool { for _,arg:=range args { if arg==flag{return true} }; return false }
func main() { fmt.Println(hasFlag([]string{"--verbose","--name","Go"},"--verbose")); fmt.Println(hasFlag(nil,"--help")) }
```

Вывод: `true`, затем `false`. Функция не читает глобальное состояние процесса и легко тестируется.
