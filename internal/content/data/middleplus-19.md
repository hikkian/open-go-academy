# 19. Инъекция отказов и восстановление

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-18`  
**Цель:** Fault injection (инъекция отказа) намеренно моделирует ограниченный сбой, чтобы проверить реакцию системы. Она отличается от хаотического «ломания всего»: выбираются один компонент, точка отказа, наблюдаемый инвариант, предел воздействия и условие остановки. Учебный helper классифицирует заранее заданные сценарии и не подключается к реальному кластеру или процессу.

## Термины и перевод

- **Fault injection** — Fault injection (инъекция отказа) намеренно моделирует ограниченный сбой, чтобы проверить реакцию системы. Она отличается от хаотического «ломания всего»: выбираются один компонент, точка отказа, наблюдаемый инвариант, предел воздействия и условие остановки. Учебный helper классифицирует заранее заданные сценарии и не подключается к реальному кластеру или процессу.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Инъекция отказа (fault injection) — контролируемое внесение заранее выбранного сбоя, чтобы проверить конкретную реакцию. Для полезного опыта нужны четыре вещи: исходное состояние, точка воздействия, наблюдаемый инвариант и условие остановки. Без ограничений такой эксперимент может нарушить данные или создать побочный сбой, который затруднит вывод.

Урок моделирует стадии публикации и наблюдения: подготовка, commit, отправка события, подтверждение или восстановление. Сначала предскажите допустимый итог для каждой стадии, затем сопоставьте его с выбранным сценарием. Не путайте «ошибка была введена» с «система восстановилась»: нужно определить, какой факт показывает восстановление и не возник ли двойной эффект.

Локальный helper классифицирует конечные поля и последовательности. Он не останавливает процесс, не отключает сеть и не проверяет кластер. Поэтому вывод ограничивается детерминированным сценарием, а реальная устойчивость остаётся неизвестной без отдельного изолированного испытания.

## Три запускаемых примера


### Пример 1: Инъекция отказа: стадия, commit и наблюдение

```go
package main

import "fmt"

func FaultOutcome(stage string, committed bool, observed bool) string { switch stage { case "before_commit": if committed{return "inconsistent"}; return "no_change"; case "after_commit": if !committed{return "inconsistent"}; if observed{return "recover"}; return "reconcile"; case "publish": if !committed{return "no_change"}; if observed{return "retry"}; return "reconcile"; default:return "unknown" } }

func main() { fmt.Println(FaultOutcome("before_commit", false, false)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 2: Восстановление: согласование наблюдаемого эффекта

```go
package main

import "fmt"

func RecoveryStep(stage string, committed bool, observed bool, recovered bool, retryable bool) string { if recovered{return "done"}; switch stage { case "before_commit": if committed||observed{return "inspect"}; return "rollback"; case "after_commit": if !committed{return "inspect"}; if !observed{return "reconcile"}; return "inspect"; case "publish": if !committed{return "inspect"}; if !observed{return "reconcile"}; if retryable{return "retry"}; return "dead_letter"; default:return "inspect" } }

func main() { fmt.Println(RecoveryStep("before_commit", false, false, false, true)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 3: Повтор только после наблюдаемого publish и подтверждённого commit

```go
package main

import "fmt"

func SafeToRetry(stage string, committed bool, observed bool, retryable bool) bool { return stage=="publish"&&committed&&observed&&retryable }

func main() { fmt.Println(SafeToRetry("publish", true, true, true)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.

## Практическая процедура

Перед сценарием запишите исходное состояние и одно проверяемое утверждение, например: после commit намерение публикации сохраняется. Назовите точное место сбоя и безопасный stop condition (условие прекращения воздействия). Меняйте за прогон только одну точку отказа.

Собирайте последовательность событий, а не только финальный статус: что было записано, что наблюдалось, какой ack получен, какой шаг повторён. Затем проверьте инвариант и критерий восстановления. Если событие не наблюдалось, различайте «не произошло» и «телеметрия отсутствует».

Ограничьте процедуру локальным детерминированным примером или специально изолированной средой. Не направляйте её на пользовательские данные или внешнюю инфраструктуру. Примеры урока проверяют решения на векторах; они не исполняют отказ и не подтверждают поведение реальной системы или безопасность эксперимента.

## Разбор сценария: Инъекция отказов и восстановление

Выберите один безопасный сбой на фиксированной стадии: например, publisher завершился после сохранения outbox-записи, но до наблюдаемого подтверждения отправки. Запишите ожидаемые записи до отказа, состояние после перезапуска и допустимую повторную операцию. Не добавляйте одновременно задержку, потерю сети и перезапуск — иначе причина результата станет неясной.

После воздействия сравните факты с инвариантом. Если повтор произошёл, проверьте, не был ли эффект применён дважды; если запись исчезла, укажите, какая транзакционная граница могла её удалить. Заранее решите, что прекращает опыт: достижение лимита повторов, нарушение инварианта или потеря наблюдаемости.

В отчёте приведите сценариемоделируемые данные и ограничение вывода. Функция из урока проверяет последовательность полей, не внедряя сбой. Результат не является доказательством устойчивости к реальному отказу; для такого вывода понадобится изолированный интеграционный тест с сохранёнными журналами.

## Лаборатория: спланировать безопасное введение отказа

### Выбранная гипотеза

Сформулируйте узкое утверждение до эксперимента. Например: «если publisher завершится после записи намерения, но до подтверждённой публикации, после перезапуска событие останется доступно для повтора». Это проверяемо по сохранённому состоянию. Утверждение «система восстанавливается после сбоев» слишком широко: оно не задаёт тип отказа, допустимый ущерб, период восстановления или необходимые наблюдения.

Зафиксируйте исходное состояние и тестовые данные. Укажите один компонент и одну точку сбоя, например остановку локального процесса после commit. Не отключайте сразу базу, сеть и брокер. Для каждого прогона задайте предел воздействия и критерий прекращения: неожиданная потеря записи, рост повторов сверх лимита или отсутствие журналов. Если критерий сработал, остановите воздействие и сохраните артефакты.

### Пошаговая карточка эксперимента

1. Опишите ожидаемый инвариант и наблюдаемый факт, который его подтвердит. Например, строка outbox остаётся после перезапуска; сообщение становится доступно publisher.
2. Сохраните исходные данные и версию кода. Подготовьте локальную изолированную среду без пользовательских данных и внешних систем.
3. Выполните обычный сценарий без отказа. Это baseline (исходная линия), необходимая для проверки, что стенд работал до воздействия.
4. Внесите ровно один отказ в выбранной точке. Запишите время, состояние процесса и какие сигналы доступны.
5. Восстановите компонент по плану. Проверьте наличие события, число публикаций, идентификатор и эффект consumer.
6. Сравните факты с инвариантом. Не называйте отсутствие записи доказательством потери, если система могла записать её в другой источник.

### Различайте ввод ошибки и восстановление

Отказ — действие испытателя; сбой — наблюдаемое нарушение поведения; восстановление — достижение заданного нормального состояния. Если тест убил процесс, но не проверил сохранённую запись и дальнейшую публикацию, он проверил только способность остановить процесс. Если событие опубликовано дважды, но consumer обработал дубликат без повторного эффекта, вывод относится к двум проверенным компонентам, а не к всему кластеру.

Собирайте журналы до и после воздействия, а также счётчики повторов, ошибок и завершений. Укажите, какие наблюдения могли задержаться или потеряться. Отсутствие сигнала нельзя трактовать как отсутствие сбоя. Если экспериментальная телеметрия стала недоступна, результат — «неизвестно» и остановка, а не успешное восстановление.

### Ограничения и следующий тест

Не запускайте упражнение на пользовательских данных или внешней инфраструктуре. Условия изоляции, резервной копии и безопасного восстановления должны быть определены до настоящего испытания; helper этого курса не организует такие гарантии. Он классифицирует заранее заданную последовательность полей, не выполняет инъекцию отказа и не наблюдает живой процесс.

В итоговой карточке ответьте: что именно отказало, какое состояние сохранилось, какой сигнал доказывает восстановление, сколько раз повторилось событие, какие гарантии не проверены? Следующий шаг должен различать две гипотезы, например: событие потерялось или лишь задержалось. Для этого добавьте чтение состояния из источника истины и ограниченное время ожидания, сохраняя прежние условия опыта.

### Остановить опыт при потере наблюдаемости

Любое испытание опирается на сигнал, который подтверждает состояние после воздействия. Если журналы перестали поступать, нельзя продолжать и считать, что система восстановилась. Установите срок ожидания сигнала и правило прекращения: остановите инъекцию, верните компонент в исходное состояние и сохраните локальные журналы. Отдельно зафиксируйте, какой сигнал должен был появиться и почему он недоступен. Такой результат важен сам по себе: восстановление нельзя проверить при слепом наблюдателе.

Проверьте повторяемость на том же сценарии. Сначала один прогон выявляет грубую реакцию, затем повтор без изменения условий показывает, был ли результат случайным. Не меняйте несколько параметров, чтобы получить желаемое поведение. Если второй запуск отличается, сравните последовательность событий, фоновые процессы и начальное состояние. Не усредняйте разные сценарии в один результат.

Условия остановки должны быть конкретными и достижимыми. «Когда станет опасно» не помогает человеку принять решение. Например, прекратить после появления первой ошибки потери данных, после заданного числа повторов или через фиксированное время без сигнала. Числа в учебном примере условны; в организации предел согласуют с владельцами системы и тестовой среды.

### Сохраните воспроизводимый след

После опыта приложите фиксированный вход, ожидаемый переход состояния, команду запуска, версию программы и точку внесения сбоя. Запишите фактическую временную шкалу и все отклонения от плана. Если повторяемость зависит от seed, сохраните seed; если зависит от внешнего образа, укажите digest. Артефакты должны позволить другому инженеру повторить тот же ограниченный сценарий.

Не включайте секреты, реальные пользовательские данные или необезличенные журналы в учебный отчёт. В реальном проекте заранее определите доступ и срок хранения доказательств. При отсутствии доверенного источника времени отметьте точность часов. Набор доказательств поддерживает вывод, но сам не доказывает отсутствие других отказов.

### Критерий восстановления должен быть измерим

«Процесс снова работает» — недостаточный критерий, если сообщения всё ещё теряются или удваиваются. Задайте наблюдаемые условия: publisher может прочитать ожидающее событие; consumer применил эффект один раз по логическому ключу; повторные ошибки прекратились; очередь возвращается к обычному уровню. Выберите только те условия, которые нужны проверяемой гипотезе, и отделите их от общих целей доступности.

Определите максимальное время ожидания восстановления. Если сигнал не появился к сроку, завершите сценарий и оставьте исход неопределённым. Не продлевайте ожидание многократно только потому, что результат неудобен. Зафиксируйте, какая часть теста не была выполнена и какой новый инструмент наблюдения требуется.

Внешний сертификат или рейтинг не следует выводить из локального chaos-like (похожего на хаос-тест) упражнения. Оно подтверждает только заранее выбранный отказ, конфигурацию и наблюдения.

Укажите, кто разрешил испытание, где оно выполнялось и как восстановить исходное состояние, не затрагивая пользователей.

## Практика Easy / Medium / Hard

**Easy — классификация.** Реализуйте первую функцию из контракта и проверьте корректный обычный случай, пустую/нулевую границу и явно невозможное значение. Результат должен точно совпасть с контрактом.

**Medium — политика с приоритетом.** Реализуйте вторую функцию. Сначала перечислите правила сверху вниз; при нескольких одновременно истинных условиях применяется первое. Добавьте тесты обычного состояния, насыщения, неизвестного значения и некорректной комбинации. Для числа/boolean не преобразуйте выход в произвольную строку.

**Hard — инвариант.** Реализуйте третью функцию, которая подтверждает только безопасную комбинацию предусловий. Граничный и противоречивый векторы обязаны отклоняться. Объясните, почему успешный результат helper не является реальным benchmark, fault test, безопасным rollout или гарантией доступности. Public и private cases находятся в JSON specs соответствующих exercise ID.

### Рабочий вопрос 1: границы fault injection

Сопоставьте fault injection с владельцем источника истины и назовите событие, после которого повтор становится безопасным. Запишите сначала ожидаемое состояние, затем вход, действие и наблюдаемый исход. Не выводите причинность из одного совпадения; сохраните команду, версию среды, количество повторов и ошибочные варианты. Если данных недостаточно, итогом должна быть отметка «неизвестно» и план следующего измерения, а не уверенная оценка. Укажите, какая часть ответа проверяется функцией, а какая потребовала бы отдельного интеграционного теста или человеческого review.
