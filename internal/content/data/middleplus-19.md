# Инъекция отказов и восстановление

## Что ты сделаешь

Ты научишься ставить эксперимент с отказом так, чтобы из него следовал вывод: один компонент, одна точка воздействия, наблюдаемый инвариант, предел воздействия и условие остановки. Разберёшь стадии публикации — до commit, после commit, при отправке — и что в каждой считается восстановлением. Три функции урока — `FaultOutcome`, `RecoveryStep`, `SafeToRetry` — классифицируют заранее описанные сценарии; к процессу, сети и кластеру они не подключены.

## Зачем нужна эта граница

Инъекция отказа (fault injection) — контролируемое внесение заранее выбранного сбоя, чтобы проверить конкретную реакцию системы. Это не «сломать всё и посмотреть»: без ограничений эксперимент повредит данные или создаст побочный сбой, который помешает выводу. Полезный опыт требует четырёх вещей: исходное состояние, точка воздействия, наблюдаемый инвариант, условие остановки. Пятая — заранее записанный ожидаемый исход, иначе любой результат объявят «интересным».

Урок моделирует отказ на стадиях публикации из темы outbox: до commit, после commit, при отправке события. Для каждой стадии до эксперимента предсказывают допустимый итог и способ его наблюдать. «Ошибка введена» и «система восстановилась» — разные факты: второй требует проверки, что эффект применён ровно один раз и наблюдаем там, где его ждут.

```go group=outcome mode=run
package main

import "fmt"

func faultOutcome(stage string, committed, observed bool) string {
    switch stage {
    case "before_commit":
        if committed {
            return "inconsistent"
        }
        return "no_change"
    case "after_commit":
        if !committed {
            return "inconsistent"
        }
        if observed {
            return "recover"
        }
        return "reconcile"
    case "publish":
        if !committed {
            return "no_change"
        }
        if observed {
            return "retry"
        }
        return "reconcile"
    }
    return "unknown"
}

func main() {
    fmt.Println(faultOutcome("before_commit", false, false), faultOutcome("after_commit", true, true), faultOutcome("after_commit", true, false))
    fmt.Println(faultOutcome("publish", true, true), faultOutcome("publish", true, false), faultOutcome("publish", false, false), faultOutcome("after_commit", false, true), faultOutcome("mystery", false, false))
}
```

Вывод:

```text
no_change recover reconcile
retry reconcile no_change inconsistent unknown
```

Два флага описывают, что видно после сбоя: `committed` — транзакция зафиксирована, `observed` — эффект виден наблюдателю. Отказ до commit с зафиксированной транзакцией — противоречие модели (`inconsistent`): так не бывает, и если наблюдение это показывает, ошибка в наблюдении. После commit эффект должен быть виден — иначе нужна сверка (`reconcile`); при отправке события видимый эффект означает, что событие стоит повторить, невидимый — сверить.

> **Важно.** `inconsistent` — самый ценный исход эксперимента: он говорит, что модель стадий или способ наблюдения неверны, а не что «система странная».

## Что делать в каждой стадии

Классификация исхода — половина дела; вторая половина — шаг восстановления. Если восстановление уже подтверждено, делать нечего. До commit противоречивые наблюдения требуют разбора (`inspect`), иначе достаточно отката. После commit без зафиксированной транзакции — разбор; без видимого эффекта — сверка; с видимым эффектом — разбор, почему сбой вообще случился. При отправке: видимый эффект и повторяемое событие — повтор; неповторяемое — мёртвая очередь.

```go group=recovery mode=run
package main

import "fmt"

func recoveryStep(stage string, committed, observed, recovered, retryable bool) string {
    if recovered {
        return "done"
    }
    switch stage {
    case "before_commit":
        if committed || observed {
            return "inspect"
        }
        return "rollback"
    case "after_commit":
        if !committed {
            return "inspect"
        }
        if !observed {
            return "reconcile"
        }
        return "inspect"
    case "publish":
        if !committed {
            return "inspect"
        }
        if !observed {
            return "reconcile"
        }
        if retryable {
            return "retry"
        }
        return "dead_letter"
    }
    return "inspect"
}

func main() {
    fmt.Println(recoveryStep("before_commit", false, false, false, true), recoveryStep("publish", true, true, false, true), recoveryStep("publish", true, true, false, false))
    fmt.Println(recoveryStep("publish", true, false, false, true), recoveryStep("after_commit", true, true, false, true), recoveryStep("publish", true, true, true, false))
}
```

Вывод:

```text
rollback retry dead_letter
reconcile inspect done
```

Обрати внимание на `after_commit` с видимым эффектом: шаг — `inspect`, не `done`. Эффект на месте, но отказ был, и причина не известна; закрыть эксперимент без разбора — потерять его смысл. Неизвестная стадия тоже ведёт к разбору: модель не знает, что произошло.

> **Типичная ошибка.** Считать `done` любым исходом, где данные на месте. Восстановление — это подтверждённый факт, а не отсутствие видимых потерь.

## Когда повтор безопасен

Повтор публикации безопасен ровно в одном случае: стадия — отправка, транзакция зафиксирована, эффект виден, событие помечено повторяемым. Любое другое сочетание — отказ от повтора по умолчанию: до commit повторять нечего, без видимого эффекта сначала нужна сверка, неповторяемое событие ведёт в мёртвую очередь.

```go group=safe mode=run
package main

import "fmt"

func safeToRetry(stage string, committed, observed, retryable bool) bool {
    return stage == "publish" && committed && observed && retryable
}

func main() {
    fmt.Println(safeToRetry("publish", true, true, true), safeToRetry("publish", true, true, false))
    fmt.Println(safeToRetry("after_commit", true, true, true), safeToRetry("publish", true, false, true), safeToRetry("publish", false, true, true))
}
```

Вывод:

```text
true false
false false false
```

Консервативность здесь намеренная: ложное «безопасно» создаёт дубликат эффекта, ложное «небезопасно» — лишь задержку до ручного разбора. Инвариант эксперимента: ни одна проверка не разрешает повтор при неполных свидетельствах.

> **Зачем.** Перед настоящей инъекцией отказа запиши, какое наблюдение подтвердит каждое из четырёх условий, — без этого флаги в функции останутся предположениями.

## Какие отказы вносить

Отказы различаются по тому, что они нарушают. Задержка ответа зависимости проверяет сроки и очереди; обрыв соединения — обработку ошибок и повторы; падение процесса между двумя шагами — атомарность и восстановление, как в стадиях этого урока; потеря сообщения брокером — дедупликацию и мёртвую очередь; расхождение часов — логику сроков и возраста. Выбирают один вид на эксперимент и формулируют инвариант, который он должен не нарушить: «эффект применён ровно один раз», «ни один запрос не ждёт дольше срока», «после перезапуска издатель отправляет все pending».

Инвариант проверяется наблюдением, записанным заранее: запросом к базе, счётчиком у потребителя, метрикой возраста очереди. Если инвариант нельзя наблюдать, эксперимент не даст вывода — сначала добавляют наблюдаемость, потом вносят отказ.

## Как ставить эксперимент

Ограничь радиус: один экземпляр сервиса, один тип отказа (задержка, обрыв соединения, падение процесса между двумя шагами), одна операция. Задай предел: длительность, доля трафика, условие аварийной остановки — по метрике, которую проверяешь непрерывно. Запиши исходное состояние так, чтобы его можно было сравнить: число записей, последний идентификатор события, остаток outbox. Проведи, сними наблюдения по заранее названным сигналам, сравни с предсказанием, запиши отклонение. Эксперимент без предсказания — не эксперимент, а наблюдение за хаосом.

Локальные функции урока классифицируют поля и последовательности. Они не останавливают процесс, не рвут сеть и не проверяют кластер; их вывод ограничен детерминированным сценарием, а реальная устойчивость остаётся неизвестной без отдельного изолированного испытания.

## Практическая процедура

Для каждой стадии — до commit, после commit, отправка — заполни таблицу из пяти столбцов: что сломано; что видно наблюдателю (транзакция, эффект); ожидаемый исход; шаг восстановления; как подтвердить, что восстановление завершено. Затем добавь строку «неизвестная стадия» и убедись, что она ведёт к разбору, а не к повтору. Прогони таблицу через функции урока; расхождение — повод уточнить таблицу или модель.

Результат эксперимента — не «прошёл/не прошёл», а запись: что вносили, что предсказывали, что наблюдали, где разошлось, какой инвариант подтверждён и каким наблюдением, какой остался непроверенным. Такая запись становится входом для следующего эксперимента и для разбора реального инцидента: если отказ в production совпал с уже проверенным сценарием, сразу известно, что сработало по-другому. Эксперименты повторяют после значимых изменений кода и инфраструктуры — устойчивость, проверенная полгода назад, не переносится на сегодняшнюю систему автоматически.

## Типичные ошибки

- Эксперимент без предсказания исхода: любой результат «интересен».
- Нет условия остановки: отказ выходит за пределы радиуса.
- `done` по отсутствию видимых потерь без подтверждения.
- Повтор при неполных свидетельствах: дубликат эффекта.
- Неизвестная стадия трактуется как «ничего не случилось».
- Эксперимент на общей или production-среде.

## Самостоятельная лаборатория

Возьми outbox из прошлого урока на одноразовом стенде и внеси три отказа по очереди: убей процесс до commit, после commit до отправки, после отправки до подтверждения. Перед каждым запиши ожидаемое состояние таблиц и предполагаемый шаг восстановления, после — наблюдаемое. Классифицируй каждый случай функциями урока и сравни с ожиданием. Отдельно проверь, что повтор после третьего отказа с ключом идемпотентности не создаёт дубликата. Удали стенд.

## Если что-то пошло не так

- `no_change` для `before_commit` с `committed = true` → это противоречие, `inconsistent`.
- `recover` для `publish` → на стадии отправки видимый эффект означает `retry`, не `recover`.
- `rollback` при `recovered = true` → `done` проверяется первым.
- `done` для `after_commit` с видимым эффектом → в этой модели — `inspect`.
- `true` в задании 3 для `after_commit` → безопасен только `publish`.
- `import … is not allowed` → импорты запрещены: строки и флаги.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Стадии задаются строками `before_commit`, `after_commit`, `publish`; модель не доказывает свойств внешней системы.

### Задание 1 · Easy: инъекция отказов и восстановление — классификация

**Цель.** По стадии и флагам `committed`, `observed` вернуть `no_change`, `inconsistent`, `recover`, `reconcile`, `retry` или `unknown` по таблице урока.

**Ожидаемый вывод** — для `("before_commit", false, false)` и `("after_commit", true, true)`:

```text
"no_change"
"recover"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func FaultOutcome(stage string, committed bool, observed bool) string`. Импорты запрещены.
2. `before_commit`: `committed` → `inconsistent`, иначе `no_change`.
3. `after_commit`: `!committed` → `inconsistent`; `observed` → `recover`; иначе `reconcile`.
4. `publish`: `!committed` → `no_change`; `observed` → `retry`; иначе `reconcile`. Неизвестная стадия → `unknown`.
5. «Запустить», «Проверить» — закрытые примеры покрывают каждую ветку и неизвестную стадию.

**Как проверить себя.** `inconsistent` появляется только там, где флаг противоречит стадии; `publish` без commit — `no_change`, а не противоречие.

**Если не принято.**
- `inconsistent` для `("publish", false, …)` → на стадии отправки отсутствие commit допустимо.
- `recover` на `publish` → там видимый эффект даёт `retry`.

> **Подсказка.** `switch` по стадии, внутри — два `if`; последний `return "unknown"`.

### Задание 2 · Medium: инъекция отказов и восстановление — политика

**Цель.** `recovered` → `done`; затем по стадии: `before_commit` → `inspect` при любом из флагов, иначе `rollback`; `after_commit` → `inspect` без commit, `reconcile` без эффекта, иначе `inspect`; `publish` → те же проверки, при видимом эффекте `retry` или `dead_letter` по `retryable`; неизвестная стадия → `inspect`.

**Ожидаемый вывод** — для `("before_commit", false, false, false, true)` и `("publish", true, true, false, true)`:

```text
"rollback"
"retry"
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func RecoveryStep(stage string, committed bool, observed bool, recovered bool, retryable bool) string`. Импорты запрещены.
2. Первой строкой `recovered` → `"done"`.
3. Далее `switch` по стадии по правилам цели; `default` → `"inspect"`.
4. «Запустить», «Проверить» — закрытые примеры: неповторяемое на `publish` → `dead_letter`; без эффекта → `reconcile`; `after_commit` с эффектом → `inspect`; `recovered` → `done`.

**Как проверить себя.** `done` только по флагу восстановления; `after_commit` с видимым эффектом — `inspect`, потому что причина отказа не выяснена.

**Если не принято.**
- `done` для `after_commit` с эффектом → подтверждение восстановления — отдельный флаг.
- `retry` при `retryable = false` → нужна мёртвая очередь.

> **Подсказка.** Это таблица задания 1 с другой колонкой ответов плюс два флага.

### Задание 3 · Hard: инъекция отказов и восстановление — проверка инварианта

**Цель.** `true` только при `stage = "publish"`, `committed`, `observed` и `retryable`; все другие сочетания → `false`.

**Ожидаемый вывод** — для `("publish", true, true, true)` и `("publish", true, true, false)`:

```text
true
false
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func SafeToRetry(stage string, committed bool, observed bool, retryable bool) bool`. Импорты запрещены.
2. Верни `stage == "publish" && committed && observed && retryable`.
3. «Запустить», «Проверить» — закрытые примеры: другая стадия, нет commit, нет эффекта → `false`.

**Как проверить себя.** Одна комбинация даёт `true`; инвариант — повтор не разрешается при неполных свидетельствах.

**Если не принято.**
- `true` для `after_commit` → стадия не проверена.
- `true` без `observed` → повтор без видимого эффекта требует сверки, не повтора.

> **Подсказка.** Одно выражение из четырёх условий через `&&`.

- Почему `after_commit` с видимым эффектом ведёт к разбору, а не к `done`?
- В каком единственном случае повтор публикации безопасен?

## Итог

- Эксперимент с отказом — один компонент, одна точка, инвариант, предел, условие остановки и предсказание исхода до запуска.
- Исход читается по стадии и двум наблюдениям — commit и видимость эффекта; противоречие между ними — сигнал об ошибке модели или наблюдения.
- Повтор безопасен только при полных свидетельствах; восстановление подтверждают, а не предполагают по отсутствию потерь.
