# Каналы: отправитель и получатель

## Что ты сделаешь

Ты напишешь три функции-модели для передачи значений: префикс из канала, чтение до маркера и чередование производителей по раундам. Примеры урока покажут, как небуферизированный канал синхронизирует две стороны и почему у каждого канала должен быть один владелец закрытия.

## Небуферизированный канал — место встречи

Небуферизированный канал работает как rendezvous: отправка и получение встречаются, и обе стороны передают значение в один момент. Отправитель блокируется, пока получатель не готов принять значение. Получатель блокируется, пока не появится значение или закрытие.

Поэтому канал одновременно передаёт данные и синхронизирует выполнение. В примере главная горутина ждёт число, которое отправит другая горутина.

```go
package main

import "fmt"

func main() {
    ch := make(chan int)
    go func() {
        ch <- 42
    }()
    fmt.Println(<-ch)
}
```

Вывод: `42`. Строка `<-ch` не вернётся, пока горутина не отправит значение. Эта блокировка и есть синхронизация, а не случайность расписания.

## Закрытие сообщает конец

`close(ch)` сообщает получателям, что новых значений не будет. Закрывает канал только отправитель, который знает, что отправок больше нет. Закрытие не стирает буфер: уже отправленные значения можно прочитать. Пустой закрытый канал возвращает нулевое значение и флаг `ok == false`.

Флаг `ok` нужен, потому что ноль может быть настоящим данными. Без него `0` из канала и `0` от пустого закрытого канала выглядят одинаково.

```go
package main

import "fmt"

func main() {
    ch := make(chan int, 1)
    ch <- 0
    close(ch)
    v, ok := <-ch
    fmt.Println(v, ok)
    v, ok = <-ch
    fmt.Println(v, ok)
}
```

Вывод: `0 true` и затем `0 false`. Первое чтение получает отправленный ноль, второе видит пустой закрытый канал. Пример показывает последовательный сценарий и не моделирует одновременную отправку и закрытие.

## Цикл range и один владелец закрытия

`for v := range ch` читает значения до закрытия и опустошения канала. Цикл завершится только тогда, когда владелец закроет канал. Поэтому производитель закрывает канал в `defer`: закрытие выполнится после последней отправки даже при раннем выходе.

```go
package main

import "fmt"

func produce(out chan<- int, n int) {
    defer close(out)
    for i := 1; i <= n; i++ {
        out <- i
    }
}

func main() {
    ch := make(chan int)
    go produce(ch, 3)
    sum := 0
    for v := range ch {
        sum += v
    }
    fmt.Println(sum)
}
```

Вывод: `6`. Тип `chan<- int` запрещает функции `produce` читать из канала. Закрыть отправляющий канал она может, поэтому `defer close(out)` стоит рядом с отправкой и делает владение видимым в одном месте.

## Несколько производителей — один владелец закрытия

Когда производителей несколько, каждый из них не знает, отправляют ли остальные. Поэтому ни один производитель не закрывает общий канал. Вместо этого отдельная координирующая горутина ждёт всех производителей через `sync.WaitGroup` и только потом закрывает результат. Это тот же приём, что в примере из предыдущего урока, но теперь он относится к каналам.

Порядок событий здесь важен: каждый производитель вызывает `Done` после своей последней отправки, координатор вызывает `Wait` и `close` после последнего `Done`. Если поменять эти места, получатель может увидеть закрытие раньше, чем пришли все значения, либо отправитель попытается писать в уже закрытый канал.

## Модель и механизм

Сначала различай состояние программы и расписание. Состояние — значения, владение ресурсами и открытые каналы. Расписание — чередование шагов, выбранное системой во время исполнения. Корректная программа должна давать допустимый результат при любом расписании, которое разрешено языком и используемыми примитивами.

Для канала полезны три вопроса. Кто отправляет значения? Кто их читает? Кто закрывает канал и почему это безопасно в момент закрытия? Если на любой вопрос ответ «не знаю», протокол не определён, и код нельзя считать корректным.

Для модели памяти Go важен один факт: отправка значения в канал happens-before завершения соответствующего получения. Всё, что отправитель записал до отправки, видно получателю после того, как получение завершилось. Закрытие работает похоже: `close` happens-before чтения, которое вернуло признак закрытия. Поэтому канал передаёт и данные, и порядок событий.

Синхронизация имеет цену. Небуферизированный канал заставляет ждать обе стороны, буфер ускоряет производство, но откладывает блокировку, а лишние горутины занимают память. Сначала сохрани инвариант протокола, потом измеряй полный путь нагрузки и ищи узкое место.

## Буфер меняет момент ожидания

Буферизованный канал принимает отправки до заполнения буфера. Пока буфер не полон, отправитель не ждёт получателя. `len` показывает, сколько значений лежит в буфере, а `cap` — сколько он может вместить.

```go
package main

import "fmt"

func main() {
    ch := make(chan string, 2)
    ch <- "a"
    fmt.Println(len(ch), cap(ch))
}
```

Вывод: `1 2`. Отправка прошла без получателя, потому что буфер ещё не заполнен. Это удобно для очереди работ, но не отменяет владения: если получатель не появится, буфер заполнится, и отправитель заблокируется.

## Типичные ошибки и исправление

Первая ошибка — отправить значение в канал, который никто не читает. Небуферизированная отправка блокируется навсегда; если все горутины программы заблокированы, runtime сообщает о взаимной блокировке. Исправление — владелец получения, который гарантированно дойдёт до чтения, или отмена через context.

Вторая — закрывать канал несколькими участниками. Повторное закрытие вызывает панику, а отправка в закрытый канал тоже паника. Передай право закрытия одному владельцу, который дождался всех отправителей.

Третья — читать из `nil`-канала и ждать, что он вернёт значение. Чтение и отправка в `nil`-канал блокируются навсегда. Проверь, что канал создан через `make`, прежде чем передавать его в горутину.

Четвёртая — считать буфер решением проблемы. Буфер лишь меняет порог, при котором появится блокировка. Если потребитель никогда не прочитает, буфер рано или поздно заполнится.

Пятая — отправить и принять значение в одной горутине через небуферизированный канал. Отправка ждёт получения, получение ждёт отправки, и программа зависает. Исправление — отправку и получение разнести по разным горутинам или сделать канал буферизованным на нужное число значений.

```text
package main

import "fmt"

func main() {
    ch := make(chan int)
    ch <- 1
    fmt.Println(<-ch)
}
```

Этот фрагмент не запускается как пример: он зависнет. Первая строка `main` ждёт получателя, которого нет. Runtime сообщит о взаимной блокировке.

> **Важно.** Закрытие канала — это ошибка протокола, если не ясно, что отправителей больше нет. Panic при закрытии показывает нарушение владения, а не случайную гонку.

## Если что-то пошло не так

- Программа выводит `fatal error: all goroutines are asleep` → кто-то ждёт отправку или получение, которое никто не выполнит; найди обе стороны канала.
- Цикл `range` не завершается → канал никто не закрыл; закрывай в производителе через `defer`.
- Паника `close of closed channel` → канал закрыт дважды; оставь одно место закрытия.
- Результат пропускает значения → получатель вышел раньше; проверь условие выхода из цикла.
- Порядок значений меняется между запусками → порядок между разными производителями не гарантирован; если он важен, передавай вместе со значением его индекс.
- Паника `send on closed channel` появляется только в редком пути → где-то канал закрывается раньше последней отправки; проверь ветки ошибки и отмены, где закрытие могло случиться рано.

## Лаборатория перед практикой

Возьми пример с `produce` и замени `defer close(out)` на обычный `close(out)` сразу в начале функции, до цикла. Перед запуском запиши, что произойдёт: цикл отправит значение уже закрытому каналу. Затем запусти программу и сравни. Если результат совпал с предсказанием, верни `defer` на место и предскажи, что изменится, если убрать `close` полностью.

Журнал эксперимента содержит версию Go, команду запуска, входное значение, предсказание и наблюдение. Если предсказание не совпало, сначала объясни расхождение, и только потом меняй код. Так видно, какая модель была неверной: порядок закрытия или условие выхода из цикла.

### Задание 1 · Каналы: отправитель и получатель — easy

**Цель.** Вернуть первые `n` значений из списка вида `[n, значения...]`; при `n <= 0` вернуть пустой список.

**Ожидаемый вывод** — входы: `[3, 4, 5, 6, 7]`, затем `[8, 9]`:

```text
[4,5,6]
[9]
```

**Шаги.**
1. Выбери задание «Каналы: отправитель и получатель — easy»: в файле есть `TakeChannelPrefix` с `panic("TODO")`. Импорты не нужны.
2. Возьми первый элемент как `n`.
3. Если `n` меньше или равно нулю, верни пустой список `[]`.
4. Иначе возьми не больше `n` следующих значений; если их меньше, возьми сколько есть.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два списка в квадратных скобках; оба вывода совпадают буква в букву; все три критерия зелёные.

**Если не принято.**
- `null` вместо `[]` при `n <= 0` → результат остался nil-срезом; создай пустой срез.
- `[4,5,6,7]` для первого входа → ограничение `n` не применено.
- Паника с выходом за границу среза для `[8, 9]` → не учтено, что значений может быть меньше `n`.

> **Подсказка.** Сначала ветка `n <= 0`, потом цикл, который останавливается по `n` и по концу списка.

### Задание 3 · Каналы: отправитель и получатель — hard

**Цель.** Собрать значения по раундам. Вход: `[число производителей, число раундов, значения подряд]`: первые `число раундов` значений принадлежат первому производителю, следующие — второму, и так далее. Выведи значения по раундам, обходя производителей по порядку и пропуская отсутствующие.

**Ожидаемый вывод** — входы: `[2, 3, 10, 11, 12, 20, 21, 22]`, затем `[3, 1, 4, 5]`:

```text
[10,20,11,21,12,22]
[4,5]
```

**Шаги.**
1. Выбери задание «Каналы: отправитель и получатель — hard»: в файле есть `InterleaveProducers` с `panic("TODO")`. Импорты не нужны.
2. Прочитай первые два элемента: число производителей и число раундов.
3. Раздели остальные значения на блоки по числу раундов, по одному блоку на производителя.
4. Для каждого раунда пройди производителей по порядку и возьми их значение этого раунда.
5. Если значения у производителя закончились, пропусти его.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Два списка; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[10,11,12,20,21,22]` → порядок обхода сначала по производителям, а не по раундам; поменяй внешний и внутренний циклы.
- `[4,5,0]` для `[3, 1, 4, 5]` → пустой производитель не пропущен; проверь длину блока перед чтением.

> **Подсказка.** Блок производителя с номером `p` (с нуля) начинается с позиции `2 + p * число раундов`.

## Проверь себя

- Почему получатель небуферизированного канала ждёт отправку?
- Что означает флаг `ok` при чтении из закрытого канала?
- Кто должен закрывать канал, и почему именно он?

- Почему буфер не заменяет согласованный протокол закрытия?
- Почему `nil`-канал блокирует чтение навсегда?

## Итог

- Небуферизированный канал синхронизирует отправителя и получателя в момент передачи значения.
- Закрытие канала принадлежит одному владельцу, который знает, что отправителей больше нет.
- Буфер и `ok` меняют поведение чтения и блокировки, но не заменяют ясный протокол владения.
