# 20. Worker pool, concurrency limit и fairness

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-19`  
**Цель:** Concurrency limit (предел параллелизма) ограничивает одновременно выполняемую работу и тем самым защищает память, соединения и downstream. Увеличение числа worker (обработчиков) не всегда повышает полезную пропускную способность: зависимость может стать узким местом, а ожидание — удлиниться. Контракт должен определить поведение при нуле, переполнении, отмене и закрытии очереди.

## Термины и перевод

- **Ограничение параллелизма** — Concurrency limit (предел параллелизма) ограничивает одновременно выполняемую работу и тем самым защищает память, соединения и downstream. Увеличение числа worker (обработчиков) не всегда повышает полезную пропускную способность: зависимость может стать узким местом, а ожидание — удлиниться. Контракт должен определить поведение при нуле, переполнении, отмене и закрытии очереди.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Пул обработчиков (worker pool) ограничивает число задач, исполняемых одновременно. Это защищает общий ресурс, например память или соединения, но больше обработчиков не обязательно означает большую пропускную способность: все они могут ждать одну медленную зависимость.

После определения лимита остаётся выбрать порядок обслуживания. FIFO (первым пришёл — первым обслужен) даёт предсказуемый порядок, но длинная задача может задержать остальные. Приоритет помогает срочной работе, однако без правила старения низкий приоритет может ждать бесконечно. Этот урок задаёт детерминированное правило: сравнить приоритет/возраст по контракту, а при равенстве сохранить стабильный порядок.

Примеры вычисляют следующий выбор из готового списка. Они не создают goroutine (горутину), не распределяют работу по каналам и не измеряют параллелизм. Следовательно, доказательство ограничено тем, что классификатор выбирает ожидаемую задачу для заданного снимка очереди.

## Три запускаемых примера


### Пример 1: Deterministic worker turn: arrival order and starvation threshold

```go
package main

import "fmt"

func WorkerTurn(arrivalA int, arrivalB int, waitA int, waitB int, maxWait int) string { if arrivalA<0||arrivalB<0||waitA<0||waitB<0||maxWait<0{return "invalid"}; if waitA>=maxWait&&waitB>=maxWait { if waitA>=waitB{return "A"}; return "B" }; if waitA>=maxWait{return "A"}; if waitB>=maxWait{return "B"}; if arrivalA<=arrivalB{return "A"}; return "B" }

func main() { fmt.Println(WorkerTurn(1, 2, 0, 0, 5)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 2: Worker batch: starvation override then FIFO, stable ties

```go
package main

import "fmt"

func itoa(n int) string { if n==0{return "0"}; b:=[]byte{}; for n>0 {b=append([]byte{byte('0'+n%10)},b...); n/=10}; return string(b) }

func WorkerBatch(arrival []int, wait []int, workers int, maxWait int) string { if len(arrival)==0||len(arrival)!=len(wait)||workers<0||maxWait<0{return "invalid"}; for i:=range arrival { if arrival[i]<0||wait[i]<0{return "invalid"} }; if workers>len(arrival){workers=len(arrival)}; chosen:=make([]bool,len(arrival)); out:=""; for n:=0;n<workers;n++ { best:=-1; for i:=range arrival { if chosen[i]||wait[i]<maxWait{continue}; if best<0||wait[i]>wait[best]||(wait[i]==wait[best]&&arrival[i]<arrival[best]) {best=i} }; if best<0 { for i:=range arrival {if !chosen[i]&&(best<0||arrival[i]<arrival[best]){best=i}} }; chosen[best]=true; if n>0{out+=","}; out+=itoa(best) }; return out }

func main() { fmt.Println(WorkerBatch([]int{0, 1, 2}, []int{0, 7, 4}, 2, 5)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 3: Fairness invariant: every job past starvation bound gets a worker turn

```go
package main

import "fmt"

func WorkerFair(arrival []int, wait []int, selected []bool, maxWait int) bool { if len(arrival)==0||len(arrival)!=len(wait)||len(arrival)!=len(selected)||maxWait<0{return false}; for i:=range arrival {if arrival[i]<0||wait[i]<0{return false}; if !selected[i]&&wait[i]>=maxWait{return false}}; return true }

func main() { fmt.Println(WorkerFair([]int{0, 1, 2}, []int{1, 7, 2}, []bool{true, true, true}, 5)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.

## Практическая процедура

Сначала выпишите критерии выбора в порядке применения: срочная задача, достигнутый порог ожидания, обычный приоритет, стабильное разрешение равенства. Затем вручную прогоните короткую очередь и сравните с результатом helper. Включите равные времена и несколько задач, достигших порога, чтобы проверить детерминированность.

Определите, что означает «получил ход»: выбран следующим или фактически запущен? Укажите, как обновляется возраст после выбора, что происходит при отмене и как закрывается очередь. Это отделяет политику планирования от выполнения задач.

Публичные и закрытые примеры подтверждают выбор для векторов, но не гарантируют, что все ожидающие задачи получат ресурс при произвольном потоке. Для этого нужен тест планировщика с последовательным временем и проверкой верхней границы ожидания, а также отдельная проверка реального лимита активных worker.

## Разбор сценария: Worker pool, concurrency limit и fairness

Составьте очередь из нескольких задач с заданными arrival order (порядком поступления), приоритетом и возрастом. Для каждого рабочего хода примените правило выбора, удалите выбранную задачу и обновите состояние оставшихся. Отметьте, когда задача пересекает starvation threshold (порог голодания) и как приоритет этого факта меняет порядок.

Повторите последовательность с равными значениями, чтобы проверить стабильность ties (равенств): одинаковый вход должен давать одинаковый порядок. Затем добавьте отменённую задачу и решите, должна ли она занимать место или получить ход. Не подменяйте выбор задачи доказательством, что worker действительно свободен.

В отчёте покажите очередь до/после каждого выбора и сформулируйте предел: модель не включает время выполнения, блокировки, scheduler Go или downstream. Инвариант «задача старше порога получает ход» проверяется только на смоделированной последовательности; интеграционный тест должен ещё подтверждать его при конечной последовательности поступлений и реальном лимите параллелизма.

## Лаборатория: проверить справедливость расписания

### Численный сценарий

Представьте три задачи: A обычного приоритета поступила в момент 0, B высокого — в момент 2, C обычного — в момент 3. Пусть порог ожидания равен пяти единицам времени. Если в момент 6 приходит ещё одна задача высокого приоритета, A уже превысила порог и должна получить предусмотренную правилом возможность хода. Но что значит «получить ход»? Это может быть выбрана следующей задачей, зарезервирован слот worker или выполнение действительно началось. Контракт должен выбрать одно наблюдаемое событие.

Если обработчик занят и задача A просто выбрана на следующую позицию, она всё ещё ждёт завершения текущей работы. Если каждый worker может захватить задачу сам, независимые решения могут нарушить глобальный порядок. Helper примеров рассчитывает выбор по одному снимку очереди; он не синхронизирует goroutine и не доказывает, что запущенная работа завершится.

### Ручное разыгрывание очереди

1. Запишите arrival order (порядок поступления), приоритет и возраст каждой задачи. Используйте фиксированные значения времени, чтобы результат был повторяемым.
2. Примените правило выбора ровно один раз. Удалите выбранную задачу и отметьте, сколько времени прошло.
3. Повторите выбор для оставшихся задач. Не сбрасывайте возраст из-за выбора соседа; возраст сбрасывается только согласно реальному событию начала обслуживания.
4. Добавьте новую задачу высокого приоритета на каждом ходе и проследите, сохраняется ли возможность для старой обычной задачи.
5. Повторите с одинаковым временем и приоритетом. Проверьте стабильность равенств: должен ли побеждать более ранний вход или иной явно объявленный критерий?

### Что измерять

Наряду с числом обработанных задач зафиксируйте ожидание каждой задачи до начала, максимум ожидания по классу, время выполнения и число отмен. Среднее ожидание может выглядеть хорошим, даже если один элемент почти никогда не выбирается. Для fairness (справедливости) выберите конкретную границу, например максимальное время до старта при конечном потоке поступлений. Измерение должно описывать последовательность и предпосылку о том, что новые задачи когда-нибудь перестанут приходить.

Сравните чистый FIFO и правило с порогом ожидания на одной и той же последовательности. Не объявляйте приоритетное правило лучше, пока не проверили оба эффекта: срочные задачи по-прежнему обслуживаются, а старые обычные не голодают. Если долго исполняемая задача занимает единственный worker, планировщик может выбирать справедливо, но фактический запуск всё равно задержится. Отделяйте время в очереди от времени исполнения.

### Пределы доказательства

Публичные и закрытые векторы проверяют конкретные списки кандидатов и предсказанный выбор. Они не охватывают произвольные последовательности, гонки, отмены, закрытие каналов или panics. Для реального теста используйте детерминированные часы, управляемые завершения задач и проверку максимального числа активных исполнителей. При тестировании конкурентного кода фиксируйте порядок событий через каналы или барьеры, а не через `time.Sleep`.

В отчёте укажите точное определение «хода», правило равенства, предположение о поступлениях и эксперимент, который мог бы опровергнуть fairness. Модель не включает scheduler Go, блокировки и работу downstream. Успешный тест конечной последовательности подтверждает только этот набор и настроенные ограничения; он не является общей математической гарантией для любого потока.

### Время выполнения меняет fairness

Политика выбора следующей задачи — только одна часть справедливости. Пусть A ждёт 20 секунд, но после запуска занимает worker на 30 секунд; B ждёт 2 секунды и завершается за миллисекунду. Правило может корректно отдать A следующий ход, но среднее ожидание остальных увеличится. Разделяйте ожидание до старта, время выполнения и время до завершения. Для пользователя важен полный срок, а для проверки планировщика — какой именно участок вы измеряете.

Сравните non-preemptive (непрерываемое выполнение) и возможность отмены. Обычно Go worker не прерывает функцию автоматически: контекст сообщает отмену, а код должен её соблюдать. Задача, игнорирующая отмену, продолжит занимать слот. Не заявляйте, что отмена завершилась, пока worker действительно не вернулся или не освободил ресурс безопасным способом.

Проверяйте закрытие очереди отдельно: принимаются ли новые задачи после close, завершаются ли текущие, кто уведомляет ожидающих и как собираются ошибки? В учебном выборе нет каналов, panic recovery или shutdown protocol (протокола остановки). Эти вопросы надо оставить как явные границы, а не считать решёнными свойством справедливого выбора.

### Отмены и справедливый выход

Добавьте в последовательность задачу, чей контекст отменён до выбора. Политика должна сказать, остаётся ли она кандидатом и как освобождается её слот. Если отмена приходит после начала работы, worker должен проверять контекст и возвращаться; иначе очередь может быть справедливой к ожидающим, но зависать на отменённом исполнении. Зафиксируйте событие, подтверждающее завершение отмены.

При graceful shutdown (мягкой остановке) прекратите приём, решите судьбу ожидающих и дождитесь ограниченное время текущих задач. Не обещайте, что все задачи закончатся, если deadline остановки короче времени работы. Примеры планировщика не включают этот жизненный цикл, поэтому добавьте его в вопросы к интеграционной реализации.

## Практика Easy / Medium / Hard

**Easy — классификация.** Реализуйте первую функцию из контракта и проверьте корректный обычный случай, пустую/нулевую границу и явно невозможное значение. Результат должен точно совпасть с контрактом.

**Medium — политика с приоритетом.** Реализуйте вторую функцию. Сначала перечислите правила сверху вниз; при нескольких одновременно истинных условиях применяется первое. Добавьте тесты обычного состояния, насыщения, неизвестного значения и некорректной комбинации. Для числа/boolean не преобразуйте выход в произвольную строку.

**Hard — инвариант.** Реализуйте третью функцию, которая подтверждает только безопасную комбинацию предусловий. Граничный и противоречивый векторы обязаны отклоняться. Объясните, почему успешный результат helper не является реальным benchmark, fault test, безопасным rollout или гарантией доступности. Public и private cases находятся в JSON specs соответствующих exercise ID.
