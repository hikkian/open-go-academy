# Кеш-корректность и инвалидация

## Что ты сделаешь

Ты разберёшь, почему кеш — это ещё одна копия данных со своей моделью согласованности, где в схеме cache-aside прячутся гонки, что должно входить в ключ, что на самом деле обещает TTL и как вести себя, когда кеш недоступен. Три функции урока — `CacheAction`, `CacheEntryValid`, `CacheReadPolicy` — это консервативные правила над флагами записи, инвалидации и версии; атомарный протокол и Redis они не реализуют.

## Cache-aside и окно между шагами

Схема cache-aside: приложение ищет значение в кеше; при промахе читает источник истины и заполняет кеш; при изменении обновляет источник и инвалидирует ключ. Между шагами есть окна, в которых конкурентные запросы видят разное.

```go group=race mode=run
package main

import "fmt"

func main() {
    // учебная шкала времени: кто что сделал и в каком порядке
    steps := []string{
        "A: промах кеша, читает источник → v1",
        "B: commit v2 в источник",
        "B: удаляет ключ из кеша",
        "A: кладёт в кеш прочитанное v1",
    }
    cache := ""
    for i, s := range steps {
        fmt.Printf("%d. %s\n", i+1, s)
        switch i {
        case 2:
            cache = ""
        case 3:
            cache = "v1"
        }
    }
    fmt.Println("в кеше после шага 4:", cache, "— источник уже v2")
}
```

Вывод:

```text
1. A: промах кеша, читает источник → v1
2. B: commit v2 в источник
3. B: удаляет ключ из кеша
4. A: кладёт в кеш прочитанное v1
в кеше после шага 4: v1 — источник уже v2
```

Одно удаление ключа не защищает от такого устаревшего заполнения: запрос A успел прочитать старое значение до commit и записал его после инвалидации. Помогают версионные ключи, ограждающий токен (fencing token), сравнение-и-запись (compare-and-set) или сериализация обновлений одного ключа — у каждого механизма свои предпосылки, которые нужно проверить, а не предположить.

> **Важно.** Кеш — копия со своей моделью согласованности. Даже чтение с primary базы вернёт устаревшее значение, если перед базой стоит кеш, чья инвалидация отстала.

## Что входит в ключ

Ключ должен включать все измерения, от которых зависит ответ: арендатор, язык, область прав доступа, параметры фильтра и страницы, версия схемы ответа. Пропущенный арендатор — утечка данных между владельцами; пропущенная область прав — пользователь видит чужую проекцию. Кеш не является источником полномочий: решение о доступе не кешируют без тщательно заданной инвалидации, а чувствительный ответ отделяют от публичной проекции. Если в значении есть персональные данные, у записи есть срок хранения, очистка и правила доступа.

```go group=key mode=run
package main

import "fmt"

func cacheKey(tenant, locale, scope string, page int, schema int) string {
    return fmt.Sprintf("orders:t=%s:l=%s:s=%s:p=%d:v=%d", tenant, locale, scope, page, schema)
}

func main() {
    fmt.Println(cacheKey("acme", "ru", "admin", 1, 3))
    fmt.Println(cacheKey("acme", "ru", "viewer", 1, 3))
    fmt.Println(cacheKey("globex", "ru", "admin", 1, 3))
}
```

Вывод:

```text
orders:t=acme:l=ru:s=admin:p=1:v=3
orders:t=acme:l=ru:s=viewer:p=1:v=3
orders:t=globex:l=ru:s=admin:p=1:v=3
```

Три разных ключа для одной страницы заказов — потому что три разных ответа. Версия схемы в ключе (`v=3`) позволяет выпустить новый формат ответа, не вычищая старые записи: они просто перестанут читаться и истекут по TTL.

> **Типичная ошибка.** Ключ по идентификатору объекта без арендатора «потому что идентификаторы уникальны». Уникальность идентификатора не гарантирует, что ответ одинаков для всех, кто вправе его видеть.

## Что обещает TTL

TTL ограничивает время хранения записи с момента записи. Он не говорит, насколько свежо значение внутри этого окна: запись могла устареть через секунду после создания. TTL — предел ущерба от сбоя инвалидации, а не механизм согласованности. Случайный разброс TTL (jitter) распределяет истечения во времени, но делает точный момент истечения неизвестным.

```go group=entry mode=run
package main

import "fmt"

func entryValid(ageSeconds, ttlSeconds int64, versionMatches bool) bool {
    return ageSeconds >= 0 && ttlSeconds > 0 && ageSeconds < ttlSeconds && versionMatches
}

func main() {
    fmt.Println(entryValid(5, 10, true), entryValid(10, 10, true), entryValid(1, 10, false), entryValid(-1, 10, true))
}
```

Вывод:

```text
true false false false
```

Граница строгая: возраст, равный TTL, — уже просрочено. Совпадение версии — отдельное условие: запись в пределах TTL, но от предыдущей версии объекта, невалидна. Отрицательный возраст — расхождение часов между узлами, и такой записи доверять нельзя.

Отрицательное кеширование (запоминание «такого объекта нет») экономит запросы к источнику, но созданный объект останется невидимым до истечения отрицательной записи. Выдача устаревшего значения при обновлении в фоне (stale-while-revalidate) повышает доступность ценой заведомо не самого свежего ответа; для каких операций это допустимо — продуктовое решение, и для денег и безопасности ответ обычно «нет».

## Порядок commit, инвалидации и чтения

«Сначала commit в базе, потом удалить ключ» — простой и распространённый порядок, но между шагами возможен устаревший read. «Удалить до commit» хуже: запрос успеет заполнить кеш прежним значением, которое потом станет окончательно устаревшим. Транзакционный outbox надёжно доставит событие инвалидации, но задержка доставки оставляет окно устаревания, а потребитель должен быть идемпотентным. Версионированные ключи переключают «поколение» кеша атомарно для читателей, но требуют управления версиями и уборки старых значений.

```go group=readpolicy mode=run
package main

import "fmt"

func action(writeSucceeded, invalidationSucceeded bool) string {
    if !writeSucceeded {
        return "no_write"
    }
    if !invalidationSucceeded {
        return "bypass_or_retry"
    }
    return "cache_consistent"
}

func readPolicy(writeSucceeded, invalidationSucceeded, versionMatches bool) string {
    if writeSucceeded && invalidationSucceeded && versionMatches {
        return "cache"
    }
    return "source"
}

func main() {
    fmt.Println(action(true, true), action(true, false), action(false, true))
    fmt.Println(readPolicy(true, true, true), readPolicy(true, false, true), readPolicy(false, true, true))
}
```

Вывод:

```text
cache_consistent bypass_or_retry no_write
cache source source
```

`cache_consistent` означает только, что оба шага сообщили об успехе в этой модели; гонку из первого примера флаги не видят. Политика чтения консервативна: любой неуспешный сигнал отправляет к источнику истины, потому что лишнее обращение к базе дешевле устаревшего ответа пользователю.

> **Зачем.** Ищи механизм, который покрывает конкретный инвариант и восстановление после сбоя, а не «добавь TTL»: TTL ограничивает длительность ошибки, но не предотвращает её.

## Что измерять у кеша

Доля попаданий (hit ratio) — самая популярная и самая обманчивая метрика. Она растёт, когда ключ слишком общий (один ответ на всех арендаторов — попадание почти всегда и утечка почти наверняка), когда TTL слишком длинный (устаревшие выдачи считаются попаданиями) и когда отрицательные записи закрывают запросы к несуществующим объектам. Поэтому долю попаданий смотрят вместе с нагрузкой на источник, долей устаревших ответов по выборочной сверке с источником и распределением возраста записей при чтении.

Полезный приём — выборочная сверка: один запрос из тысячи, попавший в кеш, дополнительно читается из источника, и расхождение считается как метрика устаревания. Она дорогая на промилле, но единственная, которая измеряет корректность, а не экономию. Если метрика устаревания растёт после выпуска, виновата схема инвалидации, а не «плохой кеш».

## Когда кеш недоступен

Определи поведение заранее: пропустить кеш и нагрузить источник, вернуть контролируемую ошибку или включить ограниченный режим. Если все запросы одновременно уйдут в источник, случится лавина промахов (cache stampede). Объединение одинаковых запросов в один (singleflight) снижает дубликаты внутри процесса, но не между экземплярами; лимиты частоты и параллелизма защищают базу. Измеряй долю попаданий и нагрузку на источник вместе: высокая доля попаданий может скрывать ошибку ключа или устаревшие выдачи.

В отчёте о кеше, как и о реплике, у каждой цифры должен быть вид: доля попаданий за окно, доля устаревших по сверке, нагрузка на источник в запросах в секунду, распределение возраста записей. Цифра «95 % попаданий» без сверки и без нагрузки на источник не говорит, работает ли кеш правильно — только что он часто отвечает.

## Типичные ошибки

- Один `DELETE` ключа как защита от гонки чтения и записи.
- Ключ без арендатора, прав доступа или версии схемы.
- TTL как механизм согласованности, а не предел ущерба.
- Удаление ключа до commit в базе.
- Отрицательное кеширование без учёта создания объекта.
- Отсутствие плана на недоступность кеша: лавина промахов в источник.

## Самостоятельная лаборатория

Синхронизируй шаги каналами так, чтобы воспроизвести порядок из первого примера, и покажи устаревшее значение в кеше после завершения. Затем добавь версию в ключ или сравнение-и-запись и повтори: устаревшее заполнение должно исчезнуть. Запиши, какое предположение потребовалось для исправления (например, монотонная версия объекта), и что оно значит для реального Redis.

## Если что-то пошло не так

- `cache_consistent` при неуспешной инвалидации → порядок проверок: сначала запись, потом инвалидация.
- `true` при `age == ttl` → граница TTL строгая.
- `true` при несовпавшей версии → версия — отдельное обязательное условие.
- `cache` при любом неуспешном флаге → политика консервативна, нужны все три `true`.
- `import … is not allowed` → импорты запрещены: флаги и числа.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Входы — учебные флаги, не состояние реального кеша.

### Задание 1 · Easy: классифицируй результат invalidation

**Цель.** Запись не удалась → `no_write`; запись удалась, инвалидация нет → `bypass_or_retry`; обе удались → `cache_consistent`.

**Ожидаемый вывод** — для `(writeSucceeded=true, invalidationSucceeded=true)`:

```text
"cache_consistent"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func CacheAction(writeSucceeded, invalidationSucceeded bool) string`. Импорты запрещены.
2. `!writeSucceeded` → `"no_write"`; затем `!invalidationSucceeded` → `"bypass_or_retry"`; иначе `"cache_consistent"`.
3. «Запустить», «Проверить» — закрытые примеры: запись есть, инвалидации нет → `bypass_or_retry`; записи нет → `no_write`.

**Как проверить себя.** `cache_consistent` означает только, что оба флага истинны; о гонках с конкурентными чтениями он ничего не говорит.

**Если не принято.**
- `bypass_or_retry` при неудачной записи → проверка записи должна идти первой.
- `cache_consistent` при неудачной инвалидации → второе условие пропущено.

> **Подсказка.** Успешная запись в источник — не успешное обновление кеша; это два разных события.

### Задание 2 · Medium: проверь TTL и версию cache entry

**Цель.** Запись валидна, если `age ≥ 0`, `ttl > 0`, `age < ttl` и версия совпадает.

**Ожидаемый вывод** — для `(ageSeconds=5, ttlSeconds=10, versionMatches=true)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func CacheEntryValid(ageSeconds, ttlSeconds int64, versionMatches bool) bool`. Импорты запрещены.
2. Верни `ageSeconds >= 0 && ttlSeconds > 0 && ageSeconds < ttlSeconds && versionMatches`.
3. «Запустить», «Проверить» — закрытые примеры: `age == ttl` → `false`; версия не совпала → `false`.

**Как проверить себя.** Граница строгая; версия обязательна; расхождение часов, гонка инвалидации и порядок операций этой проверкой не покрыты.

**Если не принято.**
- `true` для `(10, 10, true)` → использовано `<=`.
- `true` при `versionMatches = false` → флаг не включён в условие.

> **Подсказка.** Четыре условия через `&&`; каждое отвечает на свой вопрос: возраст измерим, TTL задан, не просрочено, версия та.

### Задание 3 · Hard: выбери безопасный источник после write/invalidation

**Цель.** Читать из кеша, только если запись и инвалидация успешны и версия совпадает; иначе — из источника истины.

**Ожидаемый вывод** — для `(true, true, true)`:

```text
"cache"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func CacheReadPolicy(writeSucceeded, invalidationSucceeded, versionMatches bool) string`. Импорты запрещены.
2. Все три флага `true` → `"cache"`, иначе `"source"`.
3. «Запустить», «Проверить» — закрытые примеры: любой из трёх флагов `false` → `source`.

**Как проверить себя.** Политика консервативна: единственная комбинация даёт `cache`; это не доказательство согласованности, а правило «при сомнении — источник».

**Если не принято.**
- `cache` при одном ложном флаге → использовано `||` вместо `&&`.
- `source` при всех истинных → перепутано отрицание.

> **Подсказка.** Для гарантии нужен правильный порядок commit, инвалидации и чтения и тесты конкурентных чередований; функция лишь напоминает, когда кеш нельзя считать источником.

## Проверь себя

- Все ли влияющие на ответ поля включены в ключ кеша?
- В каком порядке идут commit, инвалидация и заполнение, и где окно устаревания?
- Что случится со старым конкурентным заполнением после удаления ключа?
- Что обещает TTL и чего не обещает?
- Какие ответы можно отдавать устаревшими при недоступности источника?

## Итог

- Кеш — копия со своей моделью согласованности; cache-aside с одним удалением ключа не защищает от устаревшего заполнения.
- Ключ включает все измерения ответа; TTL ограничивает ущерб, версия и порядок операций обеспечивают корректность.
- При сомнении — источник истины; план на недоступность кеша и защита от лавины промахов — часть дизайна.
