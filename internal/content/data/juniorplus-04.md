# JSON API и REST-ресурсы

## От функции к устойчивому контракту

API (Application Programming Interface, программный интерфейс приложения) задаёт, как две программы взаимодействуют. HTTP API выражает операции через метод, путь, заголовки, коды и тело. REST (Representational State Transfer, стиль проектирования взаимодействия ресурсами) предлагает мыслить устойчивыми ресурсами и представлениями этих ресурсов, а не придумывать отдельный глагольный URL для каждой кнопки.

Для LinkHub ресурсом может быть короткая ссылка. `GET /links/green` просит представление ссылки; `POST /links` просит создать новую; `PUT /links/green` задаёт представление с конкретным идентификатором; `DELETE /links/green` удаляет ресурс. Путь отвечает на вопрос «какой объект?», метод — «какое действие по контракту?». Не все API строго REST, но этот способ даёт понятную основу для методов, статусов и повторов.

Представление (representation, форма данных ресурса для обмена) может быть JSON объектом:

```json
{"alias":"green","target":"https://go.dev/"}
```

JSON — текстовый формат из объектов, массивов, строк, чисел, логических значений и `null`. `Content-Type: application/json` описывает тело; JSON сам не выполняет проверку доменных правил. Сервер должен независимо проверить неизвестные поля, обязательные значения, размеры и допустимые схемы URL. Клиентское поле `ownerId` нельзя считать достоверным только потому, что оно валидно сериализуется.

## Метод и статус рассказывают часть смысла

| Запрос | Типичная семантика | Возможный ответ |
|---|---|---|
| `GET /links/green` | прочитать ресурс | `200`, либо `404` |
| `POST /links` | создать ресурс в коллекции | `201` с `Location` |
| `PUT /links/green` | полностью установить известный ресурс | `200` или `204` |
| `PATCH /links/green` | изменить часть ресурса | `200` или `204` |
| `DELETE /links/green` | запросить удаление | `204` или контрактный `404` |

Это ориентиры, а не единственно допустимые коды любого API. Документируйте выбор. `201 Created` естественно сопровождается идентичностью созданного ресурса — через `Location`, тело или оба способа. `204 No Content` означает, что успешный ответ не несёт тела. Не помещайте JSON-текст после `204`.

Идемпотентность (idempotency, одинаковый итог при повторении операции) помогает понять автоматические повторы. `GET`, `PUT` и `DELETE` определены как идемпотентные по семантике HTTP. Это не обещает одинаковые коды у каждого повтора: первый DELETE может вернуть `204`, последующий `404`, хотя итоговое состояние ресурса «отсутствует» одинаково. `POST` обычно создаёт новый ресурс на каждом повторе и не становится безопасным от дубликатов автоматически. Если клиент может повторить `POST` после неизвестного исхода, нужен отдельный механизм идемпотентного ключа и его серверный контракт.

REST не означает «все пути имеют одинаковый стиль», не требует одной единственной JSON схемы и не обеспечивает правильную авторизацию. Важнее понятные идентичности ресурсов, статусы и проверяемое поведение. Redirect — ответ браузеру перейти к другой цели; это отличается от `GET` ресурса или `DELETE`.

## Пример 1. Таблица метода и статуса

В файле `main.go` функция моделирует учебный контракт. Производственный API может выбрать другой код для `PATCH`; условие задания должно сказать какой.

```go group=rest-method-status mode=run
package main

import "fmt"

func MethodStatus(method string) int {
	switch method {
	case "GET", "HEAD":
		return 200
	case "POST":
		return 201
	case "PUT", "PATCH":
		return 200
	case "DELETE":
		return 204
	default:
		return 405
	}
}

func main() { fmt.Println(MethodStatus("POST"), MethodStatus("DELETE"), MethodStatus("TRACE")) }
```

`405 Method Not Allowed` говорит, что метод не поддержан для выбранного ресурса. В HTTP сервер также должен указывать допустимые варианты в `Allow`. Простая таблица статусов не проверяет путь и не должна выдавать себя за router.

## Пример 2. Строгий JSON parser с пределом

Парсер тела должен иметь лимит и понятную политику неизвестных полей. Здесь используется небольшой фиксированный fixture, поэтому интернет и файловая система не задействованы.

```go group=strict-json-request mode=run
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"io"
)

type CreateLink struct {
	Alias string `json:"alias"`
	Target string `json:"target"`
}

func main() {
	body := []byte(`{"alias":"green","target":"https://go.dev/"}`)
	const maxBody = 1024
	limited := io.LimitReader(bytes.NewReader(body), maxBody+1)
	decoder := json.NewDecoder(limited)
	decoder.DisallowUnknownFields()
	var request CreateLink
	err := decoder.Decode(&request)
	fmt.Println(err == nil, request.Alias)
}
```

Этот пример показывает ограниченную порцию байтов и строгие имена полей. Для реального handler следует после первого объекта проверить EOF, иначе тело вроде `{} {}` может принять незамеченное второе JSON значение. `http.MaxBytesReader` связывает предел с запросом и возвращает специальную ошибку при превышении.

## Пример 3. Проверить HTTP-представление в памяти

```go group=rest-response-test mode=run
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		w.Header().Set("Location", "/links/green")
		w.WriteHeader(http.StatusCreated)
		_ = json.NewEncoder(w).Encode(map[string]string{"alias":"green"})
	})
	recorder := httptest.NewRecorder()
	handler.ServeHTTP(recorder, httptest.NewRequest(http.MethodPost, "/links", nil))
	fmt.Println(recorder.Code, recorder.Header().Get("Location"), recorder.Header().Get("Content-Type"))
}
```

Тест проверяет observable contract: статус, `Location`, формат. Он не проверяет базу данных. В JSON проверяйте содержимое после декодирования, а не сравнивайте строку с зависимостью от пробелов и порядка ключей.

## Как проектировать контрастный контракт

До кода ответьте на конкретные вопросы: какая коллекция и идентификатор; кто может читать или изменять; как выглядит нормальное тело; какие поля нельзя присылать; как формируется путь созданного ресурса; что произойдёт при повторе; как клиент отличит конфликт от отсутствия; какие заголовки обязательны. Небольшая таблица запросов и ответов дешевле, чем позднее изменение всех handlers.

Для LinkHub можно зафиксировать: `POST /links` принимает `alias` и абсолютный `target`; успешный ответ — `201`, JSON представление и `Location: /links/{alias}`; занятый alias — `409`; неправильная форма — `400`; чтение неизвестного alias — `404`; неподдерживаемый метод — `405` и `Allow`. Это пример учебного контракта, не универсальный стандарт.

Стабильная ошибка должна содержать машинный `code` и безопасное понятное сообщение, например `{"code":"invalid_target","message":"Укажите абсолютный HTTP(S) URL"}`. Не выводите SQL, пути файлов, access token, cookies или stack trace. Не выдавайте внутреннее исключение за форматированный пользовательский ответ.

### URI, query и путь ресурса

URI идентифицирует цель в API. Путь обычно организует ресурсы: `/links` — коллекция, `/links/green` — элемент. Query параметры уточняют чтение: `/links?limit=20&cursor=...`. Не превращайте изменяющее состояние действие в `GET /links?delete=green`: роботы, prefetch и кэши ожидают, что GET не меняет серверное состояние. Query и path имеют разные правила экранирования, поэтому не склеивайте URL из пользовательской строки.

Клиент и сервер договариваются, где лежит идентификатор. Если alias — часть path, путь каждого запроса должен быть валидным URI segment. `url.PathEscape` помогает кодировать сегмент, но кодирование не является валидацией доменной строки. Значение может быть корректно экранировано и всё равно запрещено правилами alias.

### Полная и частичная замена

`PUT` обычно задаёт целое представление ресурса по известному URI; `PATCH` представляет частичное изменение. Для учебного контракта решите, что означает отсутствующее поле, `null` и поле с нулевым значением. Простая Go структура может скрыть разницу между «поле отсутствовало» и «поле пришло с пустой строкой». Если это важно, используйте указатель или отдельный тип presence, а затем протестируйте все три случая. Не обновляйте пропущенные поля случайным нулевым значением.

Версионирование формата API можно решать разными способами: совместимое добавление поля, media type, URL prefix или явная версия документации. Версия схемы не должна быть способом скрыть сломанную обратную совместимость. До публикации составьте fixture старого клиента и проверьте, что новый сервер сохраняет обещанный ответ.

### Кэширование и безопасный GET

GET часто можно кэшировать, что хорошо для производительности чтения и плохо для тайных или персонализированных данных без корректной политики. Заголовки кэширования определяют свежесть и видимость. Не помещайте секрет в query «ради удобства», потому что URL может сохраняться кэшем и журналами. Не используйте GET для изменения записи: повторный GET допустим клиентом, прокси или crawler.

В этой главе мы пока не настраиваем кэш и авторизацию. Важно заметить, какие решения контракт должен уточнить позднее. REST-модель помогает выбрать метод, но не защищает ресурс от неавторизованного запроса.

## Типичные ошибки и диагностика

- **Смешивать ресурс и действие.** `POST /create-link` может работать, но коллекция `POST /links` даёт устойчивую модель для операций. Оценивайте не вкус пути, а предсказуемость всей API поверхности.
- **Отправлять тело с `204`.** Клиент может проигнорировать или неправильно обработать его. Используйте `200` с представлением либо `204` без body.
- **Считать JSON-структуру валидацией.** Декодер не решает, допустима ли схема URL и свободен ли alias.
- **Считать два одинаковых body одинаковыми контрактами.** Если статус различается, клиент видит разные условия. Проверьте и headers, и статус.
- **Сравнивать JSON строкой.** Декодируйте JSON и сравнивайте поля; отдельно проверяйте обязательные ключи и запрет лишних.
- **Автоматически повторять POST.** При тайм-ауте исход неизвестен. Повтор без дедупликации может создать второй объект.

Если клиент видит неожиданный `404`, сопоставьте точный метод и полный путь с таблицей. Если status успешный, но тело не декодируется, проверьте Content-Type, синтаксис и объём. Если redirect отправил браузер на другой host, проверьте кто выбирает target; URL цель из пользовательского ввода требует отдельной политики.

## Практика

- **Easy:** выберите ожидаемый статус по методу и результату ресурса. Включите неизвестный метод и проверку, что `204` не несёт body.
- **Medium:** разберите короткий API-контракт и верните machine-readable категорию метода: чтение, создание, замена, частичное изменение, удаление или неподдерживаемый. `OPTIONS` оговаривайте отдельно.
- **Hard:** соберите канонический путь ресурса из alias; корректно обрабатывайте пустое значение и зарезервированные символы URL сегмента. Не вставляйте непреобразованный alias в готовый путь.

Каждое решение должно следовать явной таблице, а не угадывать, что «обычно делает REST». Публичные примеры задают минимальные случаи; дополнительные проверки должны покрывать метод, отсутствующий ресурс, повтор и некорректный формат. Перед отправкой проверьте, что вывод содержит ровно одно JSON-значение на вход и завершающий перевод строки.

## Мини-глоссарий

- **API** — договор взаимодействия между программами.
- **REST** — стиль моделирования HTTP API через ресурсы и их представления.
- **resource (ресурс)** — объект или коллекция, адресуемые API.
- **representation (представление)** — передаваемая форма данных ресурса.
- **idempotency (идемпотентность)** — свойство повторения сохранить тот же смысловой итог.
- **JSON** — текстовая форма объектов и других значений для обмена.
- **Location** — HTTP-заголовок с URI созданного ресурса или redirect-цели.
- **405 Method Not Allowed** — статус о запрете метода для выбранного ресурса.
