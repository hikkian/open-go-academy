## Зачем приложению SQL

SQL (Structured Query Language, язык структурированных запросов) — способ описывать таблицы и просить реляционную базу читать или менять строки. Программа и PostgreSQL — разные процессы: локальная Go-функция не превращается в запрос сама по себе. Приложение передаёт текст операции и значения драйверу; драйвер связывает их с протоколом сервера. Здесь мы учимся читать контракт данных, а настоящие операции выполняем отдельно в проекте P2.

Начните с вопроса «какие факты должны пережить перезапуск?». Для LinkHub это пользователь и принадлежащая ему короткая ссылка. Таблица — не просто сетка для печати, а набор записей одного понятного типа. Столбцы описывают поля, строка — один объект. Имена и типы должны выражать смысл: `owner_id` указывает владельца, `enabled` — состояние ссылки, а `target_url` хранит назначение.

## Схема и целостность

Схема (schema) задаёт допустимую форму данных. `PRIMARY KEY` (первичный ключ) идентифицирует строку уникальным ненулевым ключом. `FOREIGN KEY` (внешний ключ) требует, чтобы ссылка указывала на существующего владельца. `NOT NULL` запрещает отсутствие значения; `UNIQUE` не допускает дубликат; `CHECK` проверяет правило, например длину адреса. Такое ограничение действует для всех путей записи: HTTP handler, CLI, миграция или будущий worker не смогут незаметно обойти его.

Ограничение — последний защитный слой целостности, но не замена удобной валидации. Если человек выбрал уже занятый alias, приложение может перевести конфликт в понятный ответ. Однако предварительный `SELECT`, а потом `INSERT` не гарантируют уникальность при параллельных запросах: обе проверки могут увидеть свободное имя. Уникальный индекс или constraint в самой базе решает гонку; код обрабатывает отказ после попытки записи.

## CRUD по шагам

CRUD — Create, Read, Update, Delete: создать, прочитать, изменить, удалить. В SQL этим отвечают `INSERT`, `SELECT`, `UPDATE`, `DELETE`. У каждой операции есть наблюдаемый контракт. Создание должно либо вернуть созданный идентификатор, либо ошибку. Чтение может вернуть ноль строк. Изменение с `WHERE` должно указывать, какую именно запись разрешено менять. Удаление с широким или отсутствующим условием опасно.

Не начинайте с ORM (object-relational mapper, объектно-реляционное отображение). Сначала прочитайте короткий явный запрос: какие таблицы он затрагивает, какие строки выбирает и какие значения меняет. P2 хранит SQL непосредственно в Go через pgx, поэтому можно проследить путь от функции repository до запроса и обратно.

## Параметризация и граница данных

Параметризированный запрос отделяет SQL программу от пользовательских данных. В PostgreSQL через pgx placeholder выглядит `$1`, `$2`; сами значения передаются отдельными аргументами, например `QueryRow(ctx, query, ownerID, slug)`. Не заменяйте placeholder форматированием строки (`fmt.Sprintf`) и не заключайте вход в кавычки самостоятельно. Правильная параметризация не позволяет значению стать новым SQL оператором.

Но placeholder предназначен для значения, не для имени столбца или ключевого слова. `ORDER BY $1` не означает «сортировать по столбцу, имя которого пришло аргументом»; база увидит обычное значение. Для динамического столбца или направления сортировки применяйте конечную таблицу вариантов в коде и выбирайте из заранее написанных фрагментов. Никогда не превращайте произвольную строку пользователя в SQL identifier.

Посмотрите ниже на самостоятельную SQL демонстрацию. В ней создаются временные таблицы, затем запрос проходит CRUD цикл и в конце транзакция откатывается. Поэтому запись не остаётся в рабочей схеме. В задаче Medium Go функция возвращает ровно строковый контракт запроса, но grading сравнивает строку и не запускает PostgreSQL.

### Разбор ошибок

PostgreSQL сообщает структурированный SQLSTATE. Например, `23505` означает нарушение уникальности, `23503` — ссылки на отсутствующую строку, `23514` — нарушение `CHECK`. Категория пригодна для стабильного отображения и тестов. Текст ошибки может зависеть от конкретного constraint и содержать детали схемы; его не следует отдавать клиенту или сопоставлять как единственный контрольный сигнал.

Слой repository должен переводить известные случаи в ограниченный набор ошибок приложения, например `ErrConflict` или `ErrNotFound`, сохраняя исходную причину внутри для безопасной диагностики. HTTP handler уже выбирает статус и публичный текст. Не смешивайте это с любым `error != nil`: потеря соединения, отмена контекста и дубликат требуют разных внутренних решений.

### Безопасное чтение и удаление

Права владения включаются в условие выборки или изменения: `WHERE owner_id = $1 AND slug = $2`. Если сначала прочитать запись по публичному slug, а потом проверить владельца в коде, легко забыть проверку в одной из операций. Для объекта без доступа часто полезно одинаковое внешнее поведение «не найдено», чтобы не выдавать существование чужого ресурса.

Проверьте, что `DELETE` или `UPDATE` учитывает и ключ, и владельца. RowsAffected может подсказать, была ли запись найдена, но это не всегда даёт право раскрыть её существование. Контракт определяется всей системой, а не одним запросом.

### Мини-практика с disposable средой

SQL-блок ниже — самостоятельная демонстрация для чтения и выполнения в disposable среде; обычный runner функций не принимает SQL и не подключается к базе. Для настоящей практики откройте в приложении раздел «Проекты» → P2 LinkHub: его отдельный project worker поднимает временную PostgreSQL для Go-тестов и проверки API. Перенесите идею запроса в свою миграцию или repository P2 и проверяйте через кнопки проекта; сам SQL fence нельзя отправить туда как произвольный текст. Не запускайте учебный SQL в личной production базе.

Вопросы перед запуском: какая строка уникальна? Какое ограничение не позволит создать ссылку без владельца? Что будет, если один и тот же alias одновременно создадут два запроса? Какие аргументы передаются драйверу отдельно? Попробуйте изменить одно значение, не меняя SQL текст, и затем нарушить constraint, чтобы увидеть разницу между допустимыми данными и отказом целостности.

## SQL-практика для P2 worker

Таблица, ключи, ограничения и CRUD. Следующий блок самодостаточен: все таблицы временные, входные строки заданы прямо, а изменения отменяются. Его следует отправлять SQL worker в проектном рабочем месте P2; обычный Go function runner не подключает базу и не выполняет этот блок. Здесь нет команд управления сервером, файловой системы или роли.

```sql
BEGIN;
CREATE TEMP TABLE demo_users (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE CHECK (position('@' IN email) > 1)
);
CREATE TEMP TABLE demo_links (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  owner_id integer NOT NULL REFERENCES demo_users(id),
  slug text NOT NULL UNIQUE,
  target_url text NOT NULL CHECK (length(target_url) BETWEEN 1 AND 2048)
);
INSERT INTO demo_users(email) VALUES ('a@example.test') RETURNING id, email;
-- $1, $2, $3 — placeholders драйвера, не текст для psql literal prompt.
PREPARE demo_create(integer, text, text) AS
  INSERT INTO demo_links(owner_id, slug, target_url) VALUES ($1, $2, $3) RETURNING id, slug;
EXECUTE demo_create(1, 'docs', 'https://example.test/docs');
SELECT id, slug, target_url FROM demo_links WHERE owner_id = 1;
UPDATE demo_links SET target_url = 'https://example.test/start' WHERE owner_id = 1 AND slug = 'docs';
DELETE FROM demo_links WHERE owner_id = 1 AND slug = 'docs';
ROLLBACK;
```

Предскажите вывод каждой команды, затем измените одно условие `WHERE` или JOIN и проверьте результат в disposable PostgreSQL, используя аналогичный запрос в P2 repository/migration. Если project worker недоступен, разберите блок как текст; не переносите его в общую базу.

## Практика E / M / H

- **Easy: Распознай категорию ограничения.** Верни stable категорию SQLSTATE: 23505 → unique_conflict; 23503 → missing_reference; 23514 → check_violation; всё остальное → storage_error. Сравнивай код, не текст сообщения PostgreSQL. Это функция классифицирует входную строку и не подключается к базе.
- **Medium: Оставь SQL значениям параметры.** Верни ровно INSERT INTO links(owner_id, slug, target_url) VALUES ($1, $2, $3) RETURNING id. Запрос фиксирован; не встраивай никакое значение пользователя в текст. Это проверяет только строковый контракт функции, не выполнение SQL.
- **Hard: Разрешай только известный столбец.** Разреши только owner_id, slug, target_url, enabled и created_at. Не пытайся экранировать произвольный SQL identifier. Значения фильтров идут параметрами; имя столбца выбирается из allowlist.

Три упражнения проверяются детерминированными примерами функции Go. Ни одно не запускает PostgreSQL, не проверяет план запроса и не доказывает навык написания исполняемого SQL. Самостоятельная практика с запросами — в P2 workspace: перенесите SQL в проектный файл и проверяйте через Go integration tests и project verification с disposable DB. В каждом упражнении сначала запишите ожидаемый результат для стандартного и граничного входа, затем добавьте минимальную проверку. Не маскируйте ошибку пустым значением, если контракт требует отдельную категорию.

## Типичные ошибки и самостоятельная диагностика

- Параметры заменены конкатенацией SQL. Выпишите query и args отдельно и убедитесь, что payload остаётся значением.
- Пользовательский identifier проходит напрямую. Проверьте allowlist и отказ для строки вроде `slug DESC`.
- Уникальность проверена только приложением. Смоделируйте два конкурирующих создания и оставьте решение constraint базе.
- SQLSTATE преобразован по тексту локализованного сообщения. Сопоставляйте устойчивый code и не публикуйте подробность.

При отладке записывайте вход, ожидаемую категорию, фактический результат и состояние disposable базы. Не сохраняйте DSN, токен, cookie или содержимое реального пользовательского payload в журнал примера. Повторяемость важнее большого лога: один владелец, один объект и короткий запрос дают лучший минимальный случай.

## Повторение и глоссарий

Вернитесь к трём опорам главы: модель данных должна иметь ограничения; SQL связывает текст запроса и параметры безопасно; результат требует правильного порядка и обработки ошибок/ресурсов. Свяжите их с предыдущими знаниями: ошибки и интерфейсы из Junior помогают отделить доменную категорию от драйвера, context и integration tests делают внешнюю зависимость наблюдаемой. Дальше P2 применит тему к коротким ссылкам и пользовательским данным.

- **SQL (язык запросов)** — Язык описания структуры, чтения и изменения реляционных данных.
- **table (таблица)** — Набор строк одной предметной сущности с общей схемой.
- **primary_key (первичный ключ)** — Ограничение, обеспечивающее уникальную идентичность каждой строки.
- **foreign_key (внешний ключ)** — Ограничение, связывающее строку с существующей строкой другой таблицы.
- **constraint (ограничение)** — Правило целостности, которое база проверяет при изменениях.
- **parameterized_query (параметризованный запрос)** — Запрос, в котором значения передаются драйверу отдельно от SQL текста.

Оцените доказательства отдельно: компилируемый Go пример подтверждает локальный контракт; SQL блок показывает исполняемый запрос при наличии реального worker; интеграционные проверки P2 подтверждают поведение с PostgreSQL; security review необходим для утверждений о доступе. Один слой не следует описывать как доказательство другого.
