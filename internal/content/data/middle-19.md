# Dead letter, backoff и предел попыток

## Что ты сделаешь

Ты напишешь три функции-политики для повторов: растущую задержку с верхним пределом, решение «повторить или отправить в dead-letter» по классу ошибки и номеру попытки, и переходы состояния с учётом подтверждения. Функции работают только с переданными числами и флагами, поэтому проверяют правило, но не доказывают поведение брокера или очереди.

## Повтор нужен не всегда

Повтор полезен только для ошибки, которая может исчезнуть: например, кратковременная недоступность базы. Невалидное сообщение не станет валидным от ожидания. Поэтому решение начинается с классификации ошибки, а не с таймера.

Номер попытки считают с единицы. Лимит попыток включает текущую попытку, поэтому при `attempt == maxAttempts` новой попытки уже не будет. Постоянная ошибка сразу направляется в dead-letter очередь (очередь сообщений с исчерпанной политикой), чтобы сохранить материал для разбора.

Пример показывает, как номер попытки сравнивается с лимитом. На каждом шаге видно, остаётся ли повтор:

```go
package main

import "fmt"

func main() {
    max := 3
    for attempt := 1; attempt <= 3; attempt++ {
        fmt.Println(attempt, attempt < max)
    }
}
```

Вывод: `1 true`, `2 true`, `3 false`. На третьей попытке повтора уже нет: сообщение уходит в dead-letter. Если сравнение написать через `<=`, лимит станет на одну попытку больше, чем задано.

## Экспоненциальная задержка и её предел

Экспоненциальная задержка (exponential backoff) увеличивает паузу между попытками. Обычно база удваивается на каждом шаге: первая пауза 10 миллисекунд, затем 20, 40, 80. Пример показывает такой рост:

```go
package main

import "fmt"

func main() {
    delay := 10
    for attempt := 1; attempt <= 4; attempt++ {
        fmt.Println(attempt, delay)
        delay *= 2
    }
}
```

Вывод: четыре строки `1 10`, `2 20`, `3 40`, `4 80`. Рост быстрый, и через несколько шагов пауза становится бессмысленной. Поэтому задержку всегда ограничивают верхним пределом (cap).

Без предела возникает опасность переполнения целого числа. Пример показывает, как максимальное значение `int64` при умножении обёртывается в отрицательное число:

```go
package main

import (
    "fmt"
    "math"
)

func main() {
    var d int64 = math.MaxInt64
    fmt.Println(d * 2)
}
```

Вывод: `-2`. Пауза стала отрицательной, и код, который её использует, поведёт себя непредсказуемо. Поэтому перед умножением проверяют, не превысит ли результат предел, а не полагаются на то, что число «и так большое».

> **Важно.** Верхний предел задержки и общий срок повторов — разные ограничения. Задержка ограничивает паузу, а срок ограничивает всю историю сообщения.

## Jitter и одновременные клиенты

Если все клиенты используют одинаковую задержку, они одновременно повторяют запрос. Это создаёт всплеск нагрузки на уже перегруженную зависимость. Случайный разброс (jitter) размазывает повторы по времени.

Jitter меняет распределение пауз, поэтому его проверяют на диапазоне значений с контролируемым источником случайности. В тестах не используют реальную случайную задержку и `time.Sleep`: тест станет медленным и хрупким.

## Решение о повторе

Решение принимается по трём фактам: была ли ошибка, является ли она временной и не исчерпан ли лимит. Постоянная ошибка и исчерпанный лимит ведут в dead-letter. Временная ошибка до лимита даёт повтор. Успех подтверждается.

Неверные входы — отдельная ветка. Лимит попыток должен быть положительным, а номер попытки тоже начинается с единицы. Если входы неверны, решение не принимается вовсе, иначе ошибка конфигурации станет незаметной.

На практике классы ошибок выбирают по контракту зависимости, а не по тексту ошибки. Таймаут и ограничение скорости обычно временные. Ошибка валидации, неизвестный тип события и несовместимая версия схемы — постоянные. Ответ «не найдено» зависит от смысла операции: в одном сценарии это окончательный результат, в другом — повод повторить позже, когда реплика догонит запись. Классификацию записывают в контракте, чтобы её можно было проверить тестом.

## Переходы состояния и подтверждение

Подтверждение исходного сообщения делают только после надёжной фиксации следующего маршрута: повтора или dead-letter. Если публикация в очередь повторов подтверждена, исходное сообщение можно безопасно подтвердить. Иначе сбой между публикацией и подтверждением может потерять или продублировать работу.

Таймаут публикации оставляет исход неизвестным. Сообщение могло уйти, а ответ потерялся. Поэтому обработчик должен быть идемпотентным, а повтор публикации должен сохранять исходный идентификатор.

## Типичные ошибки и исправление

Первая ошибка — повторять постоянную ошибку бесконечно. Исправление — классификация ошибки и предел попыток.

Вторая — не ограничивать рост задержки. Исправление — верхний предел и проверка перед умножением.

Третья — сбрасывать счётчик попыток при перезапуске worker. Тогда повторы станут бесконечными. Исправление — хранить номер попытки вместе с сообщением или в надёжной топологии повторов.

Четвёртая — отправлять в dead-letter без причины и идентификатора. Оператор не сможет разобрать сообщение. Исправление — сохранять исходный ID, безопасную причину и число попыток.

> **Типичная ошибка.** Возвращать клиенту внутренний текст ошибки. Наружу идёт стабильная безопасная категория, а подробности остаются во внутреннем журнале без секретов.

## Если что-то пошло не так

- Сообщения копятся в очереди повторов → лимит не применяется или задержка слишком мала; проверь номер попытки и предел.
- Одна и та же постоянная ошибка повторяется → классификация не отличает постоянную ошибку от временной.
- Бюджет повторов сбрасывается после рестарта → счётчик не сохраняется при повторной доставке.
- Задержка становится отрицательной → рост не ограничен и переполнил целое число.

## Конфигурация и единицы

Лимит попыток и границы задержки задают в одной единице измерения: миллисекунды или секунды, но не смесь. Значения проверяют при запуске сервиса, а не только в момент первой ошибки. Документ конфигурации должен сказать, включает ли лимит первоначальное исполнение. Если не сказал, одна и та же цифра может означать один повтор или два.

Подсчёт попыток должен сохраняться при повторной доставке. Если падение worker сбрасывает счётчик, сообщение получит полный бюджет заново, и цикл повторов станет бесконечным. Поэтому номер попытки хранят вместе с сообщением или в надёжной топологии очереди повторов.

Dead-letter очередь нужна владельцу: кто-то отвечает за её содержимое, срок хранения, процедуру повторного запуска и сигнал о росте. Повторный запуск должен сохранять исходный идентификатор события, чтобы дедупликация продолжала работать, но создавать контролируемую новую попытку. Иначе уже выполненный необратимый эффект повторится вслепую.

## Граница доказательства

Функции этой главы проверяют выбор локальной политики. Они не гарантируют, что публикация в очередь повторов завершилась до подтверждения исходного сообщения, что dead-letter очередь переживёт перезапуск или что потребитель не выполнит побочный эффект дважды. Эти свойства проверяются отдельным сценарием с брокером: соединение принудительно закрывают в точках между публикацией и подтверждением.

Повтор без наблюдения опасен, потому что он незаметно загружает систему. Растущая очередь повторов сначала выглядит как нормальный всплеск, а потом как инцидент. Поэтому политику повторов проверяют не только тестом, но и графиком: сколько сообщений находится в повторе, сколько ушло в dead-letter и как давно обрабатывалось самое старое сообщение.

Метрики помогают увидеть проблему до того, как она станет инцидентом. Нужны число временных и постоянных ошибок, текущая попытка, глубина очереди повторов, размер dead-letter и причина исчерпания лимита. Не включай в журнал полезную нагрузку и секретные поля: достаточно идентификатора и категории.

### Задание 1 · Delay — локальное правило

**Цель.** Вход — `attempt`, `baseMS`, `maximumMS`. Если `attempt` не положителен или любой предел отрицательный, верни `0`. Иначе задержка равна `baseMS`, удвоенному для каждой попытки после первой, но не больше `maximumMS`. Переполнения быть не должно.

**Ожидаемый вывод** — входы: `attempt = 1, baseMS = 10, maximumMS = 100`; `attempt = 4, baseMS = 10, maximumMS = 50`; `attempt = 2, baseMS = 80, maximumMS = 30`; `attempt = MaxInt64, baseMS = 0, maximumMS = 100`; `attempt = 2, baseMS = MaxInt64, maximumMS = MaxInt64`:


4. Начни с `baseMS` и на каждой следующей попытке удваивай, но не выше `maximumMS`.
5. Перед удвоением проверь, не превысит ли результат предел; если да, верни `maximumMS`.

- Отрицательное число при большом `baseMS` → удвоение переполнило `int64`.
- Долгий расчёт при огромном `attempt` → цикл не останавливается, когда задержка достигла предела.

> **Подсказка.** Цикл можно остановить, как только задержка достигла предела, и проверять переполнение до удвоения.

## Итог

- Повтор разрешён только для временной ошибки и только до лимита; постоянная ошибка и исчерпанный бюджет ведут в dead-letter.
- Растущая задержка имеет верхний предел и случайный разброс, а её расчёт не допускает переполнения.
- Подтверждение исходного сообщения идёт после фиксации следующего маршрута; счётчик попыток сохраняется при повторной доставке.
