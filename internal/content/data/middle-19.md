# Dead letter, backoff и предел попыток

## Зачем эта тема нужна

В backend-сервисе тема «Dead letter, backoff и предел попыток» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

В очереди retry (повтор) полезен только для ошибки, которая может исчезнуть: например, временно недоступна база. Невалидное сообщение обычно не станет валидным от ожидания. Поэтому решение начинается с классификации ошибки, а не с таймера. `attempt` в упражнениях нумеруется с единицы, `maxAttempts` включает текущую попытку; при `attempt == maxAttempts` новой попытки уже нет. Постоянная ошибка направляется в dead-letter queue (очередь сообщений с исчерпанной политикой), чтобы сохранить диагностируемый материал для разбора.

Exponential backoff (экспоненциальная задержка) увеличивает паузу между повторными обращениями, но она должна иметь cap (верхний предел). Без него задержка может переполнить целое число; без jitter (случайного разброса) одинаковые клиенты могут повторить запрос одновременно. Учебная Easy функция показывает только насыщение целого значения. Medium отдельно решает, разрешена ли следующая попытка, а Hard добавляет уже подтверждённое сообщение как терминальное состояние. Ни одна из них не планирует таймер, не хранит число попыток и не делает broker ack.

Практический worker должен сохранять attempt или получать её из надёжной retry-топологии, ограничивать общий бюджет времени и отличать retryable error от permanent error. Если публикация в retry queue подтверждена, только тогда исходное сообщение можно безопасно подтвердить в исходной очереди; иначе сбой между publish и ack способен потерять или продублировать работу. Потребитель поэтому должен быть идемпотентным. Эти координационные гарантии требуют теста брокера и восстановления после остановки, а не таблицы чисел.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «Dead letter, backoff и предел попыток». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-19-easy mode=run
package main
import "fmt"

func RetryDelayEasy(attempt, baseMS, maximumMS int64) int64 {
	if attempt <= 0 || baseMS < 0 || maximumMS < 0 { return 0 }; if baseMS == 0 { return 0 }; if baseMS > maximumMS { return maximumMS }; delay := baseMS; for i := int64(1); i < attempt && delay < maximumMS; i++ { if delay > maximumMS/2 { return maximumMS }; delay *= 2 }; return delay
}

func main() { fmt.Println(RetryDelayEasy(1, 10, 100)) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «Dead letter, backoff и предел попыток» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-19-medium mode=run
package main
import "fmt"

func RetryActionMedium(attempt, maxAttempts int64, failed, temporary bool) string {
	if attempt <= 0 || maxAttempts <= 0 { return "invalid" }; if !failed { return "ack" }; if temporary && attempt < maxAttempts { return "retry" }; return "dead_letter"
}

func main() { fmt.Println(RetryActionMedium(1, 4, true, true)) }
```

Второй пример меняет вход так, чтобы пересечь границу контракта. Прочитайте его вместе с первым: какой именно параметр изменился и почему результат должен измениться? Эти два запуска проверяют заданное правило, но не обращаются к внешней зависимости и не доказывают её конфигурацию.

## Ошибка, повтор и восстановление

При transient error верни retry только пока попытка ниже лимита; постоянная ошибка и исчерпанный лимит ведут в dead-letter. Подтверждай исходное сообщение только после надёжной фиксации следующего маршрута. Timeout публикации оставляет исход неизвестным.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-19-hard mode=run
package main
import "fmt"

func RetryTransitionHard(attempt, maxAttempts int64, failed, temporary, acknowledged bool) string {
	if attempt <= 0 || maxAttempts <= 0 { return "invalid" }; if acknowledged || !failed { return "ack" }; if temporary && attempt < maxAttempts { return "retry" }; return "dead_letter"
}

func main() { fmt.Println(RetryTransitionHard(2, 5, true, true, false)) }
```

Порядок ветвей hard-контракта для «Dead letter, backoff и предел попыток» задаёт приоритет при пересекающихся признаках. Зафиксируйте этот приоритет до реализации, а неожиданный ввод обрабатывайте отдельно от успешного результата. Тест-векторы проверяют только выбранные категории; внешний протокол требует отдельного сценария.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy ограничивает числовой backoff; Medium выбирает retry или dead-letter по временному характеру и бюджету; Hard добавляет уже подтверждённое состояние и приоритет ack. Проверь равенство лимиту, permanent failure, успех и invalid attempt. Для реального worker тест отдельно проверяет публикацию retry до ack исходного сообщения и восстановление после остановки.

## Итог и повторение

Теперь вы умеете описать ограниченную модель темы «Dead letter, backoff и предел попыток», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `middle-18`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **backoff (растущая задержка)** — Ожидание перед новой попыткой.

- **dead-letter queue (очередь отложенных ошибок)** — Место для сообщений, исчерпавших политику повторов.

- **retry budget (лимит повторов)** — Верхняя граница попыток для одной операции.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «Dead letter, backoff и предел попыток» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «если вход меняется с обычного на граничный, решение должно перейти в заранее названную категорию; если зависимость временно недоступна, состояние остаётся восстанавливаемым». Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Проверка retry-политики на отказах

Сделайте таблицу состояния сообщения, в которой `attempt` — уже совершённая попытка, а не число оставшихся повторов. При первой временной ошибке с лимитом пять действие должно быть `retry`; на пятой попытке оно становится `dead_letter`. При постоянной ошибке перевод в DLQ происходит сразу, даже если бюджет ещё велик. После успешной обработки сообщение подтверждается. Если confirm/ack исходного сообщения потерян в сети, повторная доставка возможна, поэтому обработчик должен быть идемпотентным.

Backoff проверяйте отдельно от решения retry: при base=10ms ожидаемая последовательность может быть 10, 20, 40, 80ms, но её надо ограничить cap и суммарным deadline. Добавленный jitter изменяет распределение, поэтому тестируйте диапазон с контролируемым источником случайности, а не случайную задержку в grader. Для теста времени используйте injectable clock или вычисляемое значение, не `time.Sleep`. Метрика должна различать число временных и постоянных ошибок, текущую попытку, DLQ backlog и причину исчерпания лимита. Не включайте payload или секретные поля в лог.

Граница доказательства: функции главы проверяют выбор локальной политики. Они не гарантируют, что публикация в retry queue завершилась до ack, что DLQ переживёт перезапуск или что consumer не выполнит side effect дважды. Эти свойства проверяются отдельным брокерным сценарием с принудительным закрытием соединения в точках между publish и ack.


Для эксплуатационной конфигурации задайте maxAttempts и base/cap в одной единице измерения, проверяйте их при запуске и документируйте, включает ли maxAttempts первоначальное исполнение. Подсчёт попыток должен сохраняться через redelivery, иначе падение worker может сбросить бюджет и создать бесконечные повторы. DLQ должна иметь владельца, срок хранения, процедуру повторного запуска и сигнал о росте backlog. Повторный запуск DLQ должен сохранять исходный correlation ID, но создавать контролируемую новую попытку, чтобы не повторить уже выполненный необратимый эффект.
