# 28. Сборка приложения и DI

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `middle-26`; предыдущая глава `middle-27`.  
**Планируемый порядок каталога:** 68.  
**Результат:** Собрать зависимости через конструкторы и проверяемые интерфейсы; избегать скрытого глобального состояния.

## Глоссарий

- **dependency injection (внедрение зависимостей (DI))** — Передача компоненту зависимостей, которые он использует, вместо поиска их в глобальном состоянии.
- **constructor (конструктор)** — Функция `New...`, которая проверяет обязательные зависимости и возвращает готовый объект либо ошибку.
- **interface (интерфейс)** — Небольшой набор методов, описывающий необходимое поведение зависимости.
- **composition root (точка сборки)** — Место приложения, где создаются реализации и связываются в работающий граф.
- **fake (тестовая реализация)** — Контролируемая реализация интерфейса для проверки поведения потребителя без внешней системы.

## Теория и границы применения

В Go зависимости часто передают обычными аргументами конструктора. Например, `NewTaskService(repo TaskRepository, clock Clock) (*TaskService, error)` ясно показывает, что нужно сервису. Конструктор может отклонить nil-зависимость или недопустимую конфигурацию до того, как приложение начнёт принимать запросы. Необязательно создавать интерфейс для каждого типа: интерфейс нужен у потребителя, когда он выражает маленький контракт или позволяет изолировать тест.

Рассмотрим путь TaskFlow: composition root создаёт `*sql.DB`, repository, service и HTTP handler. Handler зависит от сервиса, а сервис — от repository и clock. Направление зависимостей идёт к доменному контракту: реализация SQL удовлетворяет интерфейсу `TaskRepository`, который объявлен рядом с потребителем. Repository не должен импортировать HTTP handler. Это помогает заменять инфраструктуру и не смешивать перевод HTTP ошибок с SQL.

```go
package main

import (
    "context"
    "errors"
    "fmt"
)

type Task struct{}
type TaskRepository interface {
    Get(context.Context, string) (Task, error)
}
type TaskService struct { repo TaskRepository }
func NewTaskService(repo TaskRepository) (*TaskService, error) {
    if repo == nil { return nil, errors.New("task repository is required") }
    return &TaskService{repo: repo}, nil
}
func main() {
    _, err := NewTaskService(nil)
    fmt.Println(err != nil)
}
```

Этот код проверяет лишь отсутствие интерфейсной зависимости. Он не открывает БД, не проверяет схему и не гарантирует, что repository соблюдает семантику контракта. В Go интерфейсное значение может содержать typed nil pointer, поэтому простая `repo == nil` проверка не ловит любой некорректный граф. Не пытайтесь отражением проверять все возможные nil; лучше не передавать typed nil на composition root и проверить реальные конструкторы.

Порядок сборки делает ошибки понятными: разобрать конфигурацию; создать инфраструктуру; создать repository; создать service; создать handler; только затем запустить сервер и отметить его готовым. Ошибка должна подниматься с контекстом компонента (`create task repository: ...`), но не включать секрет из connection string. Если конструктор сам открывает соединение, определите владельца и кто закрывает его при ошибке следующего шага. Ресурс закрывается ровно владельцем, обычно через `defer` в composition root.

Unit test сервиса может передать fake repository и проверить, что сервис запросил конкретный ID и правильно преобразовал результат. Такой тест проверяет orchestration относительно fake-контракта. Он не доказывает корректность SQL, миграции, пулов соединений или реального error mapping. Для них нужны repository integration tests с тестовой БД. В свою очередь, тест композиции должен собрать минимальный граф и доказать, что отсутствующая обязательная зависимость останавливает запуск. Задание Hard уже проверяет настоящий service→repository вызов через fake; это по-прежнему не доказывает корректность SQL.

В Go интерфейсы реализуются неявно: конкретному типу не нужна декларация `implements`. Это снижает связность, но может скрыть несоответствие ожиданиям, если интерфейс слишком широкий или плохо назван. Держите интерфейс близко к использующему его пакету, ограничивайте методы фактическими потребностями и давайте ошибкам устойчивую семантику. Не выставляйте интерфейс только для каждой структуры по привычке; избыточная абстракция делает контракт сложнее.

Глобальный mutable singleton ухудшает изоляцию: параллельные тесты меняют общее состояние, порядок тестов начинает влиять на результат, а жизненный цикл ресурса становится неявным. Передача через поля/конструкторы позволяет тесту подставить fake и задаёт ownership. Однако DI сама по себе не гарантирует хорошую архитектуру или безопасный доступ. Она только делает связи явными и облегчает проверку.

Easy оставляет короткую разминку по конфигурационной строке, Medium — проверку приоритета отсутствующей зависимости. Hard уже собирает реальный объект `TaskService` вокруг переданного `TaskRepository`. Проверочный fake записывает точный ID и context, считает вызовы, возвращает результат либо собственную ошибку. Так оценивается граница service → repository без БД; SQL, миграции и сетевое соединение всё ещё требуют отдельного integration test.

При проектировании тестового seam зафиксируйте ожидаемые вызовы, ошибки и отмену context. Fake может считать число вызовов и возвращать заранее заданную ошибку. Не делайте fake более умным, чем production контракт, иначе тест закрепит поведение самого fake. Если важно, что при repository error service не вызывает второй эффект, проверьте этот порядок явно. Для SQL transaction semantics замените fake на БД.

Конструктор — обычная функция, поэтому ошибки остаются видимыми и компилируемыми. Не маскируйте их panic без крайней причины; application startup должен вернуть диагностируемую ошибку и закрыть созданные ресурсы. Не запускайте goroutine внутри конструктора без документированного lifecycle: кто ждёт её завершения, отменяет context и сообщает ошибку? Для фонового компонента лучше явные `Start(ctx)`/`Close(ctx)` и тесты остановки.

Удобно нарисовать граф как список стрелок: handler → service; service → repository, clock; repository → DB. Затем отметить владельца каждой конкретной реализации и порядок закрытия: сначала перестать принимать работу, потом остановить фоновые операции, затем закрыть repository/DB. Это обучающая схема; она ещё не доказывает, что конкретное приложение закрывает ресурсы правильно. Проверить её можно тестом composition root с контролируемыми зависимостями и проверкой cleanup при ошибке сборки.

## Разбор решения: один test seam

Пусть `TaskService.Get` должен загрузить задачу по ID и вернуть доменную модель. Интерфейс рядом с сервисом может быть минимальным: один метод `Get(context.Context, string) (Task, error)`. Сервис получает repository через `NewTaskService`. В тесте fake получает заранее заданный результат и записывает переданный ID. Тогда unit test может доказать две вещи: сервис передал требуемый идентификатор, а ошибка репозитория не была превращена в успешный пустой объект. Он не доказывает, что SQL использовал правильную таблицу или что Postgres вернул правильную строку.

Constructor errors лучше отличать от runtime dependency errors. Отсутствие обязательного repository — ошибка сборки и приложение не должно объявлять readiness. Таймаут БД во время чтения — runtime ошибка, которую handler переводит в безопасный ответ. Не возвращайте nil service и nil error, если объект не готов: такая пара откладывает сбой до первого запроса и затрудняет диагностику.

Composition root строит concrete object graph. Порядок закрытия обычно обратен созданию: перестать принимать запросы, дождаться handler-ов, остановить worker, закрыть repository-owned resources, затем DB. Но ownership важнее универсального рецепта: если repository заимствует DB, он не должен закрывать общий пул. Зафиксируйте владение прямо в API и в тесте cleanup. В примере helper с тремя booleans не может показать этот lifecycle; для него нужен реальный объект графа и controlled fake/DB.

## Три самостоятельных запускаемых примера

### Пример 1: `ConfigStatus`

Контракт: Пустой URL → missing_database; длина менее 8 → invalid_database; иначе configured.

```go
package main

import "fmt"

func ConfigStatus(dbURL string) string {
	if dbURL == "" { return "missing_database" }; if len(dbURL) < 8 { return "invalid_database" }; return "configured"
}

func main() {
	fmt.Println(ConfigStatus("postgres://local"))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `DependencyPlan`

Контракт: Проверить слои в порядке repository, service, handler; первое отсутствующее звено возвращает соответствующую метку, все есть → ready.

```go
package main

import "fmt"

func DependencyPlan(repositoryProvided, serviceProvided, handlerProvided bool) string {
	if !repositoryProvided { return "missing_repository" }; if !serviceProvided { return "missing_service" }; if !handlerProvided { return "missing_handler" }; return "ready"
}

func main() {
	fmt.Println(DependencyPlan(true, true, true))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: конструктор и fake repository

Здесь весь объектный граф мал и явен: вызывающий код владеет fake, передаёт его конструктору, а service делегирует запрос. Отдельный sentinel позволяет тесту отличить исходную ошибку repository от новой похожей ошибки.

```go
package main

import (
    "context"
    "errors"
    "fmt"
)

type Task struct { ID string }
type TaskRepository interface {
    Get(context.Context, string) (Task, error)
}
type RepositoryMissingError struct{}
func (RepositoryMissingError) Error() string { return "task repository is required" }
type TaskService struct { repo TaskRepository }
func NewTaskService(repo TaskRepository) (*TaskService, error) {
    if repo == nil { return nil, RepositoryMissingError{} }
    return &TaskService{repo: repo}, nil
}
func (s *TaskService) Get(ctx context.Context, id string) (Task, error) {
    return s.repo.Get(ctx, id)
}
type fakeRepository struct { calls int; id string; result Task; err error }
func (f *fakeRepository) Get(_ context.Context, id string) (Task, error) {
    f.calls++; f.id = id
    return f.result, f.err
}
func main() {
    sentinel := errors.New("database unavailable")
    fake := &fakeRepository{result: Task{ID: "task-17"}}
    service, err := NewTaskService(fake)
    if err != nil { panic(err) }
    task, err := service.Get(context.Background(), "task-17")
    fmt.Printf("%s calls=%d id=%s error=%t\n", task.ID, fake.calls, fake.id, err != nil)
    fake.err = sentinel
    _, err = service.Get(context.Background(), "task-18")
    fmt.Printf("calls=%d id=%s wrapped=%t\n", fake.calls, fake.id, errors.Is(err, sentinel))
}
```

Запуск: сохраните этот блок в `main.go` и выполните `go run .`; ожидается `task-17 calls=1 id=task-17 error=false` и `calls=2 id=task-18 wrapped=true`. Fake доказывает маршрутизацию вызова и сохранение исходной ошибки. Он не проверяет SQL и поведение реального хранилища.

## Практика Easy / Medium / Hard

**Easy — базовое правило.** Реализуйте `func ConfigStatus(dbURL string) string`. Контракт: Пустая строка → missing_database; длина менее 8 байт → invalid_database; иначе configured. Это не валидация URL и не соединение с БД. Скрытые и публичные vectors закреплены в grading spec.

**Medium — граничная политика.** Реализуйте `func DependencyPlan(repositoryProvided, serviceProvided, handlerProvided bool) string`. Контракт: Первое отсутствующее звено в порядке repository, service, handler возвращает свою метку; все присутствуют → ready. Это не реальный граф объектов. Скрытые и публичные vectors закреплены в grading spec.

**Hard — service и его граница.** Реализуйте `TaskService`, `NewTaskService(repo TaskRepository)` и `Get(ctx, id)`. Конструктор отклоняет отсутствующий repository; успешный объект сохраняет конкретную переданную реализацию. Метод ровно один раз передаёт исходные context и ID и не теряет ошибку repository. Публичные и закрытые проверки наблюдают fake, а не исполняют произвольный пользовательский код на хосте grader.

## Лабораторная карточка TaskFlow: композиция зависимостей

Нарисуйте граф для одного endpoint `GET /v1/tasks/{id}`: composition root → `*sql.DB` → `TaskRepository` → `TaskService` → handler. Добавьте clock только если он действительно нужен сервису. Для каждой стрелки подпишите интерфейс, кто создаёт конкретную реализацию, кто владеет lifecycle и кто её закрывает. Не добавляйте глобальные singleton для удобства теста.

Напишите маленький constructor `NewTaskService(repo TaskRepository) (*TaskService, error)` и fake repository в тесте. В unit test проверьте успешное чтение и распространение ошибки repository, а также что пустая обязательная зависимость возвращает startup error. Fake должен только реализовать методы интерфейса, а не повторять SQL/бизнес-логику. Если проверяете число вызовов, зафиксируйте ожидаемый call count и объясните, почему повторный вызов был бы ошибкой.

Соберите composition root через явные шаги. Смоделируйте сбой создания service после открытия БД и проверьте, что DB закрывается. Затем соберите успешный путь и проверьте, что handler получил именно созданный service. Не включайте настоящий DSN или пароль в сообщения ошибки. Укажите, где происходит health/readiness transition; отдельный fake-driven Hard проверяет только constructor и вызов service, не lifecycle сервера.

Отдельно запустите repository integration test с тестовой PostgreSQL: миграции, чтение известной записи и безопасное закрытие соединения. Такой тест проверяет конкретный adapter/схему; он не удостоверяет все транзакции production или долговечность среды. Запишите версию схемы, команду, cleanup и точную границу вывода.

В ревью ответьте: интерфейс объявлен рядом с потребителем? Методы минимальны? typed nil возможен ли в месте сборки? Есть ли goroutine, стартующая внутри constructor, и кто её ждёт? Ошибка конструктора сохраняет причину без секрета? Какие ресурсы нужно закрыть при каждом промежуточном отказе? Если реального integration test нет, явно оставьте SQL semantics непроверенной. Завершите карточку перечнем unit, composition и DB integration доказательств и не смешивайте их результаты.
