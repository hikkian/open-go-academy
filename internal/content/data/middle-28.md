# Сборка приложения и DI

## Что ты сделаешь

Ты напишешь три части сборки: проверку строки подключения при старте, решение о готовности набора зависимостей и конструктор сервиса с его методом чтения, который не меняет ответ хранилища. Для каждой части есть правило отказа, и локальные fake-реализации проверяют его без базы.

## Зависимости передаются явно

Сборка приложения — это место, где создаются объекты и связываются между собой: хранилище, сервис, обработчик. Главный вопрос сборки — откуда каждый объект берёт то, что ему нужно. Ответ «из глобальной переменной» скрывает зависимость. Ответ «через аргумент конструктора» делает её видимой и подменяемой. Разница заметна уже в первом тесте: с аргументом тест передаёт fake, с глобальной переменной приходится подменять её и потом возвращать обратно.

Слово «внедрение» здесь означает не магию фреймворка, а обычный порядок действий в коде. Внедрение зависимостей (dependency injection) означает именно это: объект получает зависимости снаружи, а не создаёт или ищет их сам. Тогда тест может передать fake вместо настоящего хранилища, и сценарий будет проверяться без сети и базы.

> **Важно.** Глобальный синглтон удобен в первый день и мешает на третий: тесты начинают влиять друг на друга, а порядок их запуска становится частью результата.

## Конфигурация при старте

Строка подключения — первая зависимость, которую проверяет сборка. Пустая строка означает, что база не настроена, и приложение не должно стартовать молча. Короткая строка — подозрительная: она задана, но вряд ли корректна. Это разные причины, и оператор должен получить разные сообщения.

Учебная проверка работает только с длиной строки. Она не разбирает URL и не подтверждает, что база доступна. Пример показывает три состояния конфигурации:

```go
package main

import "fmt"

func main() {
    for _, s := range []string{"", "x", "postgres"} {
        switch {
        case s == "":
            fmt.Println("missing_database")
        case len(s) < 8:
            fmt.Println("invalid_database")
        default:
            fmt.Println("configured")
        }
    }
}
```

Вывод: `missing_database`, `invalid_database`, `configured`. Строка из восьми байт уже проходит проверку длины, поэтому граница в восемь байт включена.

## Обязательные зависимости

Сборка перечисляет обязательные зависимости в фиксированном порядке: хранилище, сервис, обработчик. Если первая отсутствует, остальные не имеют смысла, и сборка сообщает именно о ней. Порядок важен для диагностики: оператор увидит первую недостающую часть, а не случайную.

Пример показывает такой план. Проверки идут по порядку, и первое отсутствие становится ответом:

```go
package main

import "fmt"

func plan(repo, service, handler bool) string {
    switch {
    case !repo:
        return "missing_repository"
    case !service:
        return "missing_service"
    case !handler:
        return "missing_handler"
    }
    return "ready"
}

func main() {
    fmt.Println(plan(true, true, true), plan(false, true, true))
}
```

Вывод: `ready missing_repository`. Отсутствие хранилища обнаруживается раньше остальных, поэтому сообщение однозначно.

## Конструктор, который отвергает nil

Конструктор сервиса получает хранилище аргументом. Если передан `nil`, сервис не может работать. Отказ лучше дать сразу при сборке, чем падение при первом запросе. Тогда ошибка видна при старте, когда её ещё можно исправить.

Конструктор также не должен подменять переданный объект. Если бы он создавал новое хранилище внутри себя, тест с fake проверил бы объект, которого в продакшене нет, и зелёный результат ничего бы не значил. Сервис сохраняет тот же экземпляр хранилища, а не создаёт собственный. Иначе тест с fake проверял бы не то, что работает в продакшене.

## Метод чтения без потерь

Метод чтения сервиса передаёт аргументы хранилищу без изменений: контекст и идентификатор. Ответ хранилища возвращается как есть, включая ошибку. Сервис не должен подставлять значение по умолчанию вместо ошибки и не должен обрезать идентификатор: пробелы и символы решает хранилище или валидация на границе.

Этот принцип проверяется сравнением журнала вызовов. Если сервис изменил идентификатор, журнал покажет другое значение, чем передал вызывающий код.

## Сборка как точка контроля

Сборка — единственное место, где видно все зависимости сразу. Поэтому именно здесь удобно проверять конфигурацию, пока приложение ещё не принимает запросы. Если отказ произошёл на сборке, оператор видит причину в журнале запуска и может исправить настройку до того, как клиенты столкнутся с ошибкой.

Чем раньше проверка, тем дешевле исправление. Пустой адрес базы, отсутствующий обработчик и `nil` в конструкторе — ошибки конфигурации, а не ошибки запроса. Их не нужно маскировать ответом клиенту, их нужно не допустить до запуска.

## Что проверяет fake-хранилище

Fake-хранилище повторяет интерфейс и возвращает заранее заданные ответы: задачу, ошибку или отсутствие записи. Через него сценарий проходит все ветки без сети. Такой fake проверяет, что сервис правильно обрабатывает ответы, но не проверяет, как хранилище отвечает на самом деле.

Поэтому fake держат простым и явным. Если fake начинает повторять логику базы — сортировку, фильтры, проверку прав — он перестаёт быть подменой и превращается во второй, непроверенный сервис. Для таких случаев нужен интеграционный тест с реальным хранилищем.

## Модель и механизм

Для сборки полезны три вопроса. Какие зависимости обязательны? В каком порядке их проверять? Что произойдёт, если одна из них отсутствует? Ответы записываются до написания конструкторов.

Синхронизация здесь не нужна. Сборка выполняется один раз при старте. Поэтому гонки между сборкой и запросами возможны только тогда, когда сборку повторяют в рабочем процессе, и это обычно признак ошибки в запуске сервиса. Цена подхода — конструкторы с длинными списками аргументов; её уменьшают группировкой по смыслу, а не скрытым глобальным состоянием.

## Типичные ошибки и исправление

Первая ошибка — создавать хранилище внутри сервиса. Исправление — передавать его аргументом.

Вторая — не проверять `nil` в конструкторе. Исправление — отказ при сборке с понятной ошибкой.

Третья — подменять ответ хранилища значением по умолчанию. Исправление — возвращать ответ и ошибку без изменений.

Четвёртая — считать короткую строку подключения корректной. Исправление — отдельная категория для подозрительной конфигурации и проверка доступности базы в интеграционном тесте.

> **Типичная ошибка.** Тестировать сервис с настоящей базой там, где хватило бы fake. Тест станет медленным, а причина ошибки станет неясной: непонятно, виновата логика или база. Для логики сборки достаточно знать, какие зависимости переданы и что на них было вызвано.

## Если что-то пошло не так

- Приложение стартует без базы и падает на первом запросе → конфигурация не проверяется при сборке; добавь проверку до запуска сервера.
- Тесты влияют друг на друга → сервис читает глобальное состояние; передай зависимости аргументами.
- Ошибка хранилища пропала в ответе → сервис заменил её значением по умолчанию.
- Идентификатор в журнале вызовов отличается от переданного → сервис изменил аргумент.

### Задание 3 · Hard: service с внедрённым repository

**Цель.** Реализуй `NewTaskService(repo)`: если `repo` равен `nil`, верни ошибку `RepositoryMissingError`, иначе сохрани тот же экземпляр. Метод `Get(ctx, id)` передаёт `ctx` и `id` хранилищу без изменений и возвращает его ответ и ошибку как есть. Ответ теста собирается из полей через вертикальную черту: `task:`, ID задачи, репозиторий, число вызовов `calls=`, переданный идентификатор `id=`, признак контекста `ctx=` и признак ошибки `error=`. При ошибке сборки ответ — `constructor_error|missing=true|calls=0`.

**Ожидаемый вывод** — входы: задача `task-17` в хранилище `repo-1` успешно; затем `task-18` с ошибкой хранилища:

```text
"task:task-17|repo-1|calls=1|id=task-17|ctx=true|error=false"
"task:||calls=1|id=task-18|ctx=true|error=true"
```

**Шаги.**
1. Выбери задание «Hard: service с внедрённым repository»: в файле есть `NewTaskService` и метод `Get` с `panic("TODO")`.
2. В конструкторе проверь `repo` на `nil`; при `nil` верни ошибку `RepositoryMissingError`.
3. Сохрани переданный экземпляр в поле `repo`.
4. В `Get` вызови `repo.Get` с тем же `ctx` и `id`.
5. Верни задачу и ошибку хранилища без изменений.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- Ошибка сборки отсутствует при `nil` → конструктор не проверяет хранилище.
- `id` в журнале отличается от переданного → сервис изменил аргумент.
- `error=false` при ошибке хранилища → ошибка проглочена.

> **Подсказка.** Конструктор только сохраняет зависимость; метод только передаёт аргументы и возвращает ответ.

## Воспроизводимая лабораторная: конструктор с fake-хранилищем

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. База и сеть не нужны: fake-хранилище работает в памяти программы.

Программа ниже собирает сервис с fake-хранилищем, выполняет чтение и проверяет отказ конструктора на `nil`. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import (
    "context"
    "errors"
    "fmt"
)

type fakeRepo struct{ calls int }

func (f *fakeRepo) Get(ctx context.Context, id string) (string, error) {
    f.calls++
    return "task:" + id, nil
}

type service struct{ repo *fakeRepo }

var errMissing = errors.New("repository missing")

func newService(repo *fakeRepo) (*service, error) {
    if repo == nil {
        return nil, errMissing
    }
    return &service{repo: repo}, nil
}

func main() {
    repo := &fakeRepo{}
    svc, err := newService(repo)
    fmt.Println("constructed:", err == nil, svc != nil)
    got, _ := svc.repo.Get(context.Background(), "task-17")
    fmt.Println("got:", got, "calls:", repo.calls)
    _, err = newService(nil)
    fmt.Println("nil repo:", err)
}
```

**Ожидайте:** строка `constructed: true true`, затем `got: task:task-17 calls: 1`, затем `nil repo: repository missing`. Конструктор сохраняет тот же экземпляр хранилища и отвергает `nil` при сборке.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- Зависимости передаются явно через конструкторы; глобальное состояние скрывает их и мешает тестам.
- Отсутствие обязательной зависимости обнаруживается при сборке, а не при первом запросе, и порядок проверок задаёт понятный ответ.
- Сервис передаёт аргументы хранилищу без изменений и возвращает его ответ как есть; это проверяется журналом вызовов на fake.
