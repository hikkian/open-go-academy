# Партиционирование и маршрутизация данных

## Что ты сделаешь

Ты разберёшься, какую именно задачу решает разбиение таблицы на разделы — отсечение разделов при чтении и дешёвое удаление старых данных — и какие обязательства оно накладывает: ключ, границы, уникальность, обслуживание. Три функции урока — `PartitionRoute`, `ValidPartitionRange`, `PartitionPrunes` — это арифметика границ в одномерной модели; маршрутизатор PostgreSQL и его планировщик они не моделируют.

## Что такое раздел и зачем он нужен

Декларативное партиционирование делит одну логическую таблицу на физические дочерние отношения по ключу: диапазону значений, списку или хешу. Два честных выигрыша: planировщик исключает разделы, чьи границы несовместимы с предикатом запроса (partition pruning), и старый сегмент удаляется одной командой `DETACH`/`DROP` вместо миллионов `DELETE`. Всё остальное — не гарантии, а возможности: запрос без фильтра по ключу посетит все разделы, а тысяча мелких разделов увеличивает стоимость планирования и обслуживания.

```go group=route mode=run
package main

import "fmt"

func route(day int) string {
    if day < 1 || day > 31 {
        return "invalid"
    }
    if day <= 10 {
        return "p1"
    }
    if day <= 20 {
        return "p2"
    }
    return "p3"
}

func main() {
    for _, d := range []int{1, 10, 11, 20, 21, 31, 0, 32} {
        fmt.Printf("day %2d -> %s\n", d, route(d))
    }
}
```

Вывод:

```text
day  1 -> p1
day 10 -> p1
day 11 -> p2
day 20 -> p2
day 21 -> p3
day 31 -> p3
day  0 -> invalid
day 32 -> invalid
```

Это условная схема трёх разделов по «дню» без месяца — модель, на которой удобно проверять границы. В PostgreSQL диапазон задаётся как `FROM (включительно) TO (исключительно)`, и именно на стыке `10/11` рождаются ошибки: строка попадает не в тот раздел, в раздел по умолчанию или никуда.

> **Важно.** Ключ разделения — обязательство схемы. Временной ключ удобен для хранения и удаления по сроку, но запросы по арендатору без времени не получат отсечения; хеш-ключ распределяет строки, но не делает запрос локальным по времени.

## Три вида разбиения и что каждый даёт

Диапазонное разбиение (`RANGE`) — по интервалам значений: месяцы дат, диапазоны идентификаторов. Оно даёт отсечение для запросов с условием по ключу и естественное удаление старых сегментов; цена — заведение будущих разделов заранее. Разбиение по списку (`LIST`) — по перечню значений: регион, тип события, арендатор при небольшом числе арендаторов. Оно удобно, когда сегменты обслуживаются по-разному, но список нужно поддерживать, а новый арендатор без раздела — это отказ записи или раздел по умолчанию. Хеш-разбиение (`HASH`) равномерно раскладывает строки по N разделам: оно сглаживает размер сегментов и помогает параллельному обслуживанию, но ни один диапазонный запрос не получает отсечения — чтобы найти строки за неделю, придётся посетить все разделы.

Выбор следует из двух вопросов: по какому предикату запросы должны отсекать разделы и какие сегменты будут удаляться целиком. Если ответа нет ни на один, разбиение преждевременно. Допустимо и вложенное разбиение — по арендатору, внутри по месяцу, — но каждая ступень умножает число отношений и стоимость планирования.

## Отсечение разделов: когда оно работает

Планировщик отсекает раздел, если из предиката запроса следует, что ни одна строка раздела не подойдёт. Для диапазонного ключа это пересечение интервалов: раздел с границами `[21, 31]` не пересекается с запросом `day BETWEEN 1 AND 10` — его можно не читать.

```go group=prune mode=run
package main

import "fmt"

func prunes(queryStart, queryEnd, partStart, partEnd int) bool {
    if queryStart > queryEnd || partStart > partEnd {
        return false
    }
    return queryEnd < partStart || partEnd < queryStart
}

func main() {
    parts := [][2]int{{1, 10}, {11, 20}, {21, 31}}
    for _, q := range [][2]int{{1, 10}, {8, 12}, {25, 25}} {
        kept := 0
        for _, p := range parts {
            if !prunes(q[0], q[1], p[0], p[1]) {
                kept++
            }
        }
        fmt.Printf("запрос %v: читаем %d из %d разделов\n", q, kept, len(parts))
    }
}
```

Вывод:

```text
запрос [1 10]: читаем 1 из 3 разделов
запрос [8 12]: читаем 2 из 3 разделов
запрос [25 25]: читаем 1 из 3 разделов
```

Касание границы — `queryEnd == partStart` — это пересечение, раздел читать нужно. Перевёрнутый интервал — некорректный вход, и функция честно отвечает «не отсекать»: безопаснее прочитать лишнее, чем пропустить данные. В реальном плане отсечение бывает на этапе планирования (константы) и во время выполнения (параметры, подзапросы); `EXPLAIN` с литералом и с параметром могут показать разное число разделов.

> **Типичная ошибка.** Проверить отсечение на демонстрационном запросе с константой и решить, что подготовленный запрос с параметром поведёт себя так же.

## Отсечение во время выполнения

Планировщик отсекает разделы на этапе планирования, когда границы запроса — константы. Если граница приходит параметром подготовленного выражения, значением из подзапроса или результатом соединения, решение откладывается до выполнения: планировщик строит план на все разделы, а исполнитель пропускает ненужные, когда значение становится известно. В `EXPLAIN ANALYZE` это видно по пометке о разделах, которые «никогда не выполнялись». Отсечение во время выполнения дешевле полного чтения, но дороже планировочного: метаданные всех разделов уже открыты.

Отсюда практическое правило: предикат по ключу должен быть выражен так, чтобы исполнитель мог сравнить его с границами напрямую. Функция над ключом (`date_trunc(created_at)`), приведение типа или `OR` с другим столбцом лишают планировщик возможности сопоставить условие с границами, и все разделы читаются целиком. Проверяй форму предиката в плане, а не доверяй тому, что ключ «упомянут» в запросе.

## Уникальность, внешние ключи и раздел по умолчанию

Уникальное ограничение на партиционированной таблице должно включать ключ разделения, иначе его не проверить без обхода всех разделов. Это меняет модель идентификаторов, `upsert` и внешние ключи, которые на таблицу ссылаются. Раздел по умолчанию ловит строки, для которых подходящего раздела нет: он снижает риск отказа записи, но прячет ошибку заведения разделов, а потом строки придётся перемещать. Решай заранее, что лучше для твоего сервиса — громкий отказ или тихое накопление.

```go group=range mode=run
package main

import "fmt"

func validRange(startDay, endDay int) bool {
    return startDay >= 1 && endDay <= 31 && startDay <= endDay
}

func main() {
    fmt.Println(validRange(1, 10), validRange(10, 10), validRange(10, 9), validRange(0, 5), validRange(25, 32))
}
```

Вывод:

```text
true true false false false
```

Раздел из одного дня допустим; перевёрнутый и выходящий за границы ключа — нет. Такую проверку стоит запускать на описании схемы до миграции, а не узнавать о дыре между разделами по первой потерянной строке.

## Миграция и обслуживание

Переход на разделы — последовательность: создать будущие сегменты; перенести или присоединить (`ATTACH`) существующие данные; обновить ограничения; проверить маршруты записи; только потом переключать читателя. Тесты проверяют ровно нижнюю и верхнюю границу каждого интервала — отсутствие пропусков и дублей. План обслуживания отвечает на три вопроса: кто и когда создаёт следующий раздел, как отслеживается заполнение, при каких условиях старый раздел отсоединяют и удаляют — только после проверки политики хранения и резервных копий и отсутствия зависимых запросов.

> **Зачем.** Партиционирование не ускоряет запросы само по себе. Оно меняет форму обслуживания: если ты не можешь назвать запрос с отсечением и сегмент, который будешь удалять, разбиение добавит сложность без выигрыша.

Отдельно запиши, как отсечение взаимодействует с индексами: у каждого раздела свои индексы, и запрос без отсечения обходит их все; глобального индекса по партиционированной таблице нет, поэтому поиск по неключевому столбцу без фильтра по ключу — это N индексных поисков вместо одного.

## Типичные ошибки

- Разбиение «для скорости» без запроса, который получает отсечение.
- Границы `FROM/TO` перепутаны включительно/исключительно: строки на стыке теряются или уходят в раздел по умолчанию.
- Уникальность без ключа разделения: ограничение невозможно или проверка обходит все разделы.
- Раздел по умолчанию как замена заведению разделов: ошибка копится тихо.
- Тысячи мелких разделов: планирование и мониторинг дороже выигрыша.
- Проверка отсечения только на константах, не на параметрах.

## Самостоятельная лаборатория

На одноразовом PostgreSQL создай таблицу событий, партиционированную по диапазону даты на три месяца, и заполни миллионом синтетических строк. Сними `EXPLAIN` для трёх запросов: с фильтром по дате внутри одного месяца, с фильтром по дате на стыке двух месяцев, без фильтра по дате. Запиши число посещённых разделов. Повтори первый запрос через подготовленное выражение с параметром и сравни. Затем вставь строку с датой за пределами разделов — без раздела по умолчанию и с ним — и зафиксируй поведение. Отсоедини самый старый раздел и измерь время операции. Запиши число разделов и размер каждого до и после отсоединения: это и есть доказательство дешёвого удаления. Удали стенд.

## Если что-то пошло не так

- `p2` для дня 10 или `p1` для дня 11 → границы интервалов: `<= 10`, `<= 20`, проверь обе стороны стыка.
- `invalid` для дня 31 → верхняя граница `> 31`, не `>= 31`.
- `true` для перевёрнутого интервала в задании 2 → условие `startDay <= endDay` отсутствует.
- `true` при касании границ в задании 3 → касание — пересечение; используй строгие `<`.
- `true` для перевёрнутого интервала в задании 3 → некорректные границы должны давать `false`, а не отсечение.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Модель одномерная: один упорядоченный ключ и включительные границы.

### Задание 1 · Easy: маршрутизируй день в учебный shard

**Цель.** Дни 1–10 → `p1`, 11–20 → `p2`, 21–31 → `p3`; остальное → `invalid`.

**Ожидаемый вывод** — для дней 1, 16, 31:

```text
"p1"
"p2"
"p3"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func PartitionRoute(day int) string`. Импорты запрещены.
2. `day < 1 || day > 31` → `"invalid"`.
3. `day <= 10` → `"p1"`, `day <= 20` → `"p2"`, иначе `"p3"`.
4. «Запустить», «Проверить» — закрытые примеры: день 0 и день 32 → `invalid`.

**Как проверить себя.** Стыки 10/11 и 20/21 попадают в разные разделы; 1 и 31 — допустимы; это условная схема без месяца, не календарный ключ.

**Если не принято.**
- Красный закрытый пример для 0 → нижняя граница не проверена.
- Сдвиг на стыке → перепутаны `<` и `<=`.

> **Подсказка.** Проверяй вход на диапазон первой строкой; остальные ветки тогда не нуждаются в нижних границах.

### Задание 2 · Medium: проверь диапазон partition key

**Цель.** Вернуть `true`, если включительный диапазон лежит в 1…31 и `start ≤ end`.

**Ожидаемый вывод** — для `(1, 10)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ValidPartitionRange(startDay, endDay int) bool`. Импорты запрещены.
2. Верни `startDay >= 1 && endDay <= 31 && startDay <= endDay`.
3. «Запустить», «Проверить» — закрытые примеры: `(10, 9)` → `false`, `(0, 5)` → `false`.

**Как проверить себя.** Раздел из одного дня допустим; это проверка описания схемы, а не отсечение планировщиком.

**Если не принято.**
- `true` для `(10, 9)` → нет проверки порядка границ.
- `false` для `(10, 10)` → порядок проверен строгим `<` вместо `<=`.

> **Подсказка.** Нижнюю границу проверяй у `start`, верхнюю — у `end`; порядок обеспечит, что обе внутри.

### Задание 3 · Hard: проверь пересечение диапазонов

**Цель.** Вернуть `true`, когда включительные диапазоны запроса и раздела не пересекаются и раздел можно исключить; перевёрнутые интервалы → `false`.

**Ожидаемый вывод** — для запроса `1…10` и раздела `11…20`:

```text
true
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func PartitionPrunes(queryStart, queryEnd, partStart, partEnd int) bool`. Импорты запрещены.
2. `queryStart > queryEnd || partStart > partEnd` → `false`.
3. Верни `queryEnd < partStart || partEnd < queryStart`.
4. «Запустить», «Проверить» — закрытые примеры: запрос `8…12` и раздел `10…20` пересекаются → `false`; запрос `1…3` внутри раздела `0…5` → `false`.

**Как проверить себя.** Касание границы — пересечение; «не отсекать» — безопасный ответ по умолчанию для любого сомнительного входа.

**Если не принято.**
- `true` при касании → нестрогие сравнения `<=`.
- `true` для перевёрнутого запроса → проверка порядка границ стоит после вычисления.
- `false` для явно разнесённых диапазонов → условие объединено через `&&` вместо `||`.

> **Подсказка.** Два интервала не пересекаются ровно тогда, когда один целиком левее другого.

## Проверь себя

- Какие два выигрыша даёт партиционирование и чего оно не гарантирует?
- Почему граница `FROM/TO` — самое опасное место миграции?
- Что требуется от уникального ограничения на партиционированной таблице?
- Чем опасен раздел по умолчанию?
- Почему отсечение на константе не доказывает отсечение на параметре?

## Итог

- Разделы дают отсечение при чтении по ключу и дешёвое удаление сегментов; скорость сама по себе не обещана.
- Ключ и границы — обязательство схемы: тестируй стыки интервалов, уникальность включает ключ, раздел по умолчанию решается осознанно.
- План обслуживания — кто создаёт следующий раздел, как следят за заполнением и когда удаляют старый — часть решения, а не примечание.
