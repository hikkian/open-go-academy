## Алгоритмы и рост затрат

Алгоритм (algorithm) — конечная последовательность действий, которая решает задачу. Его оценивают по корректности и затратам ресурсов. В этой главе главный ресурс — количество операций при росте входа. Асимптотическая сложность (complexity) описывает порядок роста, а не точное время на конкретном компьютере.

Линейный поиск (linear search) последовательно сравнивает элементы. Для n элементов в худшем случае будет n сравнений, поэтому рост обозначают O(n). Если вход удвоился, число сравнений примерно удваивается. Константы и реальные накладные расходы тоже влияют на время, поэтому Big O не является секундомером.

Вложенный цикл по всем парам часто выполняет порядка n² сравнений: квадратичный рост (quadratic). Удвоение входа примерно учетверяет число пар. Но сам вид вложенных циклов ещё не доказывает O(n²): внутренний диапазон может быть постоянным или уменьшаться. Считайте фактические итерации и определите, сколько зависит от n.

Бинарный поиск (binary search) на каждом шаге исключает половину отсортированного диапазона. Его сложность O(log n), но предусловие (precondition) критично: данные должны быть отсортированы в том же порядке, в котором сравниваются. Без него результат не имеет смысла. Алгоритм не сортирует вход самостоятельно.

Для диапазона [lo, hi) нижняя граница включена, верхняя исключена. Изначально lo=0, hi=len(values). Пока lo < hi, индекс середины равен lo+(hi-lo)/2; форма избегает потенциального переполнения суммы индексов. Если значение меньше цели, установить lo=mid+1; иначе hi=mid. В конце lo — место, где цель должна быть, а равенство проверяется отдельно.

Условия остановки важны: при [lo, hi) каждый шаг должен строго уменьшать диапазон. Если написать hi=mid-1 одновременно с полууточенной границей, легко пропустить элемент или зациклиться. Выберите один инвариант и проверьте его на длинах 0, 1 и 2. В нашем контракте возвращается индекс найденного значения, иначе -1.

Вектор входов упражнений намеренно проверяет поведение, но не измеряет скорость. Пять элементов не подтверждают Big O. Сложность аргументируют анализом циклов и числа шагов; benchmark сравнивает конкретные реализации на конкретной машине и не заменяет доказательство. Здесь требуется и корректная функция, и объяснение предпосылок алгоритма.

Иногда простой линейный поиск разумнее: вход короткий, уже отсортированность неизвестна, данные читаются один раз или сортировка стоит дороже одного поиска. Если нужно много запросов по одному набору, сортировка один раз и бинарные запросы могут окупиться. Если нужна частая вставка, поддерживать порядок тоже имеет стоимость. Сравнивайте полный сценарий, а не одну функцию.

Другой компромисс — память. Дополнительный map даёт быстрый поиск в среднем, но требует памяти и построения индекса; сортировка меняет порядок или требует копии. Не объявляйте один вариант «самым быстрым» без условий по размеру, частоте запросов, изменяемости и памяти. Оптимизация начинается с корректного простого решения и измеряемой цели.

Пограничные индексы — это -1, первый, последний, len и значение между существующими элементами. Не возвращайте позицию вставки, если контракт требует -1 для отсутствующего значения. Дубликаты тоже требуют политики: здесь допустим любой индекс равного элемента. Если продукт ожидает первый дубликат, это отдельное условие и иной поиск.

Для контроля итераций можно вручную записать lo, hi, mid и сравнение в таблице. Пример [2,5,8,12], цель 8: диапазон [0,4), mid=2, найдено. Для цели 7: mid=2 исключает правую часть, следующий mid=1 двигает lo=2, затем диапазон схлопывается в [2,2), отсутствует. Трассировка показывает корректность границ понятнее случайного принта.

Два указателя, хеширование и предварительная сортировка — другие техники, но выбирать их нужно под контракт. Уникальные значения и порядок результата могут менять допустимый алгоритм. На Junior этапе достаточно определить повторную работу, предпосылку упорядоченности и понятный trade-off. Не смешивайте учебный анализ с неподтверждёнными обещаниями производительности.

### Полная программа: бинарный поиск

Сохраните как `main.go`. Функция не меняет срез и предполагает сортировку по возрастанию.

```go
package main

import "fmt"

func binarySearch(sorted []int, target int) int {
    lo, hi := 0, len(sorted)
    for lo < hi {
        mid := lo + (hi-lo)/2
        if sorted[mid] < target { lo = mid + 1 } else { hi = mid }
    }
    if lo < len(sorted) && sorted[lo] == target { return lo }
    return -1
}
func main() {
    values := []int{2, 5, 8, 12, 17}
    fmt.Println(binarySearch(values, 12))
    fmt.Println(binarySearch(values, 9))
}
```

Вывод: `3`, затем `-1`. Каждая итерация сокращает оставшийся диапазон примерно вдвое; число итераций растёт логарифмически.

### Ошибки, тестирование и критерии

Частая ошибка — вызвать поиск на неотсортированном входе и затем обвинить середину. Другая — вычислить mid как (lo+hi)/2 без причины выбирать эту форму; в очень больших индексах сумма теоретически может переполниться. Проверьте пустой список, первый/последний элемент, пропуск между соседями, цель меньше минимума и больше максимума. Детерминированные проверки доказывают эти результаты, но не асимптотическую сложность.

Задание Easy на максимум проверяет один проход. Medium реализует бинарный поиск по заданной сигнатуре. Hard сравнивает полный процесс для одного/многих запросов и требует аргументировать сортировку, память, порядок и границы. Автоматическая часть проверяет функцию; ручная часть требует короткого доказательства предпосылки и оценки роста. Не выдавайте тестовые векторы за доказательство Big O.

### Самопроверка, словарь и самостоятельная помощь

1. Сколько проверок в худшем случае у линейного поиска? 2. Что означает O(n²)? 3. Каково предусловие бинарного поиска? 4. Почему нужен контракт для дубликатов? 5. Почему маленькие функциональные тесты не доказывают Big O? 6. Когда линейный способ разумнее? 7. Почему диапазон [lo,hi) упрощает длину? 8. Что проверяется после выхода цикла? Ответы: не более n; рост квадратично; отсортированный порядок; иначе результат не определён полностью; они проверяют конечные входы; короткие данные/нет сортировки/один проход; hi-lo; что lo указывает на цель или отсутствие.

Если не сходится индекс, вручную выпишите диапазон после каждой итерации. Сначала попробуйте length 0 и 1. Сравните `<` против `<=` только после определения инварианта. AI может предложить альтернативный код, но требуйте трассировку и контрпример. Не делайте вывод о сложности по одному времени запуска.

## Как читать оценку роста

Обозначение O(f(n)) описывает верхний порядок роста с точностью до постоянного множителя и членов меньшего порядка. Поэтому O(3n+8) упрощают до O(n), а O(n²+4n) — до O(n²). Для новичка важнее сравнить классы роста и назвать допущения, чем манипулировать формальными пределами. O(1) означает ограниченное число шагов относительно n, а не одинаковое время на каждом устройстве.

Считайте операции внутри цикла и число повторений отдельно. Один цикл, проходящий весь вход, выполняет n шагов; два последовательных прохода дают 2n, то есть всё ещё линейный рост. Вложенные полные проходы могут выполнить n×n проверок. Если внешний цикл идёт n раз, а внутренний — только 10 раз, рост O(10n), то есть линейный. Если внутренний счётчик каждый раз делится пополам, счёт операций будет другим. Название структуры кода не заменяет подсчёт.

Для бинарного поиска диапазон после k шагов не больше примерно n/2^k. Чтобы осталось не более одного кандидата, требуется около log₂(n) шагов. Для n=1024 это примерно десять делений пополам; линейный просмотр может потребовать 1024 сравнений. Это иллюстрация порядка, не измерение задержки. Доступ к памяти, размер кеша, запуск процесса и цена сравнения вносят реальные различия.

Big O для памяти тоже полезен. Цикл поиска использует постоянное число индексов — O(1) дополнительной памяти. Сортировка копии создаёт O(n) дополнительное хранилище, если алгоритм или способ копирования требует его. Хеш-индекс занимает память пропорционально числу записей. Иногда дополнительная память снижает повторную работу; иногда она создаёт лишний расход и обновление индекса.

Выбор алгоритма зависит от сценария. Для одного поиска в неотсортированном списке линейный просмотр проще и дешевле сортировки. Для тысяч запросов к неизменяемому набору сортировка один раз, затем бинарный поиск часто выгодна. Если набор меняется постоянно, поддержка сортированности может стоить дороже. Укажите число запросов, размер и модель изменений, прежде чем рекомендовать алгоритм.

## Дубликаты, порядок и семантика результата

Бинарный поиск в этом контракте может вернуть любой найденный индекс дубликата. Если интерфейс требует первый индекс, алгоритм ищет нижнюю границу и в конце проверяет равенство. Это небольшое изменение задачи меняет постусловие. Всегда выясняйте, что означает результат для повторяющихся ключей. Случайные функциональные векторы не должны подменять незаданное условие.

Вставка в отсортированный срез сохраняет порядок, но сдвигает элементы и занимает O(n). Двоичный поиск быстро находит позицию, но перемещение остаётся линейным. Это классический пример того, почему нельзя оценивать приложение только по поиску. Также важно понять, можно ли менять вход: сортировка на месте является наблюдаемым побочным эффектом. Наш поиск ничего не меняет.

Алгоритм должен иметь конечный прогресс. Для двоичного поиска инвариант — цель, если существует, остаётся внутри [lo,hi), а диапазон строго сокращается. Если обновление границ оставляет прежние lo/hi, цикл не завершится. Проверяйте длину 1: это быстро обнаруживает неверное сочетание `<=` и `mid-1`. Проверяйте пустой вход до индексации.

## Что значит доказать и что значит измерить

Функциональные тесты отвечают на вопрос «получили ли мы ожидаемый результат на этих входах?». Анализ цикла отвечает на вопрос «как растёт работа при общем n?». Benchmark отвечает «сколько времени заняла конкретная реализация в конкретном окружении при этих данных?». Ни один вид доказательства автоматически не заменяет два других.

Микробенчмарки чувствительны к прогреву, шуму машины, сборке мусора, оптимизациям компилятора и форме данных. Не публикуйте вывод о производительности по одному запуску. Для обучения достаточно оценить число сравнений вручную и корректно назвать предусловие. Реальный performance work включает профиль полного сценария, репрезентативную нагрузку и повторяемый метод.

Если вход может быть неверно отсортирован, следует ли функция проверять сортировку? Проверка сама требует O(n), что убирает преимущество бинарного поиска для одного вызова. Часто предусловие остаётся ответственностью вызывающего кода и документируется. В другом API может быть безопаснее принимать отсортированную обёртку, проверять при построении индекса или использовать другой тип. Архитектурный выбор зависит от частоты операций и доверия к источнику.

### Пример: линейный максимум

```go
package main

import "fmt"

func maximum(values []int) (int,bool) { if len(values)==0{return 0,false}; m:=values[0]; for _,v:=range values[1:] { if v>m { m=v } }; return m,true }
func main() { v,ok:=maximum([]int{4,-2,9,3}); fmt.Println(v,ok) }
```

Вывод: `9 true`. Цикл посещает каждый элемент не более одного раза: O(n) времени и O(1) дополнительной памяти.

### Пример: подсчитать попарную работу

```go
package main

import "fmt"

func pairCount(n int) int { count:=0; for i:=0;i<n;i++ { for j:=0;j<n;j++ { count++ } }; return count }
func main() { fmt.Println(pairCount(3)); fmt.Println(pairCount(6)) }
```

Вывод: `9`, затем `36`. При удвоении n число пар возрастает в четыре раза; это наглядная функциональная иллюстрация, а не доказательство свойств любой вложенной петли.
