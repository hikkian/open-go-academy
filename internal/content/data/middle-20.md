# RabbitMQ: exchange, queue и binding

## Зачем эта тема нужна

В backend-сервисе тема «RabbitMQ: exchange, queue и binding» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

RabbitMQ разделяет приём маршрута и хранение: publisher отправляет сообщение в exchange (обменник), exchange применяет binding (правило маршрутизации) к queue (очереди). Direct exchange сравнивает routing key и binding key как точные строки. Topic exchange имеет отдельные wildcard-правила; их нельзя имитировать сравнением строк из этого упражнения. Пустой ключ — ошибка выбранной локальной модели. Отсутствие совпавшего binding означает unrouted (не маршрутизировано), а не «сообщение сохранено».

Easy проверяет только наличие трёх элементов изолированной топологии. Medium моделирует точное совпадение direct key. Hard отличает подтверждённую публикацию от неопределённой: publisher confirm говорит о принятии брокером согласно протоколу, но не подтверждает, что consumer обработал сообщение; returned с mandatory публикацией сигнализирует, что маршрут не найден. При потере соединения до confirm результат unknown (неизвестен), поэтому слепой повтор может создать дубликат.

В реальном приложении тестовая топология должна иметь уникальный vhost или префикс ресурсов. Очистка обязана удалять только собственную очередь и exchange, никогда общую среду. Интеграционный тест поднимает закреплённую версию RabbitMQ, создаёт topology, отправляет сообщения с routed и unrouted key, проверяет confirm/return и затем чистит свои объекты. Три локальные функции не открывают сокет и не доказывают настройку durable queue, consumer ack или восстановление брокера.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «RabbitMQ: exchange, queue и binding». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-20-easy mode=run
package main
import "fmt"

func TopologyReadyEasy(exchange, queue, binding bool) bool {
	return exchange && queue && binding
}

func main() { fmt.Println(TopologyReadyEasy(true, true, true)) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «RabbitMQ: exchange, queue и binding» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-20-medium mode=run
package main
import "fmt"

func DirectRouteMedium(exchange, routingKey, bindingKey string) string {
	if routingKey == "" || bindingKey == "" { return "invalid" }; if exchange == "" { return "invalid" }; if routingKey == bindingKey { return "route" }; return "unrouted"
}

func main() { fmt.Println(DirectRouteMedium("orders", "created", "created")) }
```

Второй пример меняет вход так, чтобы пересечь границу контракта. Прочитайте его вместе с первым: какой именно параметр изменился и почему результат должен измениться? Эти два запуска проверяют заданное правило, но не обращаются к внешней зависимости и не доказывают её конфигурацию.

## Ошибка, повтор и восстановление

Разделяй unrouted return, отрицательный confirm и неизвестный исход канала. Confirm публикации не равен consumer ack. Используй изолированный vhost и не удаляй чужие очереди.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-20-hard mode=run
package main
import "fmt"

func PublishOutcomeHard(mandatory, brokerConfirm, returned bool) string {
	if returned { return "unrouted" }; if !brokerConfirm { return "unknown" }; return "confirmed"
}

func main() { fmt.Println(PublishOutcomeHard(true, true, false)) }
```

Порядок ветвей hard-контракта для «RabbitMQ: exchange, queue и binding» задаёт приоритет при пересекающихся признаках. Зафиксируйте этот приоритет до реализации, а неожиданный ввод обрабатывайте отдельно от успешного результата. Тест-векторы проверяют только выбранные категории; внешний протокол требует отдельного сценария.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy проверяет состав топологии; Medium различает точное совпадение direct routing key; Hard отделяет confirm, returned и unknown. Не трактуй topic wildcard как прямое равенство. Интеграционный сценарий должен использовать изолированный vhost и проверять routed/unrouted публикацию, confirm и очистку только собственных ресурсов.

### Термины

- **exchange (обменник)** — Получает сообщение и выбирает маршрут.

- **queue (очередь)** — Хранит сообщения до выдачи потребителю.

- **binding (связь маршрутизации)** — Правило связи exchange с queue.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «RabbitMQ: exchange, queue и binding» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «если вход меняется с обычного на граничный, решение должно перейти в заранее названную категорию; если зависимость временно недоступна, состояние остаётся восстанавливаемым». Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Проверка маршрута и подтверждения

Зафиксируйте topology как набор имён и типов: exchange, очередь назначения, binding key и тип exchange. Для direct exchange только точное совпадение ключа создаёт маршрут; для topic правила `*` и `#` имеют иной смысл и нуждаются в собственных тестах. Если используется alternate exchange, unrouted исходный маршрут может быть обработан дополнительной топологией, но это отдельная конфигурация, отсутствующая в данной функции.

Publisher confirm и consumer acknowledgement относятся к разным стадиям. Confirm сообщает о результате приёма публикации брокером; consumer ack отмечает обработку доставленного сообщения. Ни один не означает автоматически, что бизнес-операция внешней системы завершилась ровно один раз. При неизвестном исходе публикации сохраняйте идентификатор сообщения и используйте идемпотентный consumer. Метрики разделяют returned/unrouted, nack, timeout и consumer redelivery; объединённый счётчик скрывает различия.

Для повторяемого интеграционного теста выделите временный vhost или уникальный префикс, дождитесь готовности сервиса, объявите exchange/queue/binding и опубликуйте один routed и один unrouted fixture. Убедитесь, что confirm/return соответствуют настройке, затем удалите только свои ресурсы. В отчёте зафиксируйте версию RabbitMQ и конфигурацию durable/auto-delete. Успех теста не следует распространять на другой тип exchange или production topology.


При расследовании unrouted сообщения сопоставьте exchange, routing key, binding pattern и vhost из одного события; одного имени очереди в логе недостаточно. Устойчивый publisher ставит таймаут на подтверждение и сохраняет outcome, а канал при ошибке закрывает и пересоздаёт контролируемо. Не превращайте channel reconnect в молчаливый успех: если исход сообщения неизвестен, consumer должен выдержать повтор. Настройки auto-delete, exclusive queue и durable exchange относятся к разным жизненным циклам и не заменяют друг друга.


Проверяя ordering, включите в fixture сообщения с одинаковым routing key в разные очереди и два независимых binding. Наблюдайте фактическое потребление каждой очередью, потому что функция сравнения ключей не показывает fan-out и конкуренцию consumers. Зафиксируйте, какая очередь должна получить копию и какая получает её по умолчанию.
