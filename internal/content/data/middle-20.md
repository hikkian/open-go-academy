# RabbitMQ: exchange, queue и binding

## Что ты сделаешь

Ты напишешь три функции-модели для маршрутизации в RabbitMQ: проверку готовности топологии, выбор маршрута по точному ключу и исход публикации с учётом подтверждения и возврата. Функции работают с переданными значениями, поэтому проверяют правило, но не открывают соединение с брокером.

## Exchange, binding и queue

RabbitMQ разделяет приём маршрута и хранение. Публикующий отправляет сообщение в exchange (обменник). Exchange применяет binding (правило связи) к queue (очереди). Очередь хранит сообщения до выдачи потребителю.

Эти три элемента нельзя путать. Без exchange сообщение некуда отправить. Без binding exchange не знает, какой очереди передать сообщение. Без очереди сообщению негде лежать. Поэтому готовность топологии означает наличие всех трёх частей, а не одной из них.

Пример показывает простую связь: ключ маршрута сопоставляется с именем очереди через таблицу связей. Для ключа без связи результат пустой:

```go
package main

import "fmt"

func main() {
    bindings := map[string]string{"created": "orders.new"}
    fmt.Println(bindings["created"], bindings["cancelled"] == "")
}
```

Вывод: `orders.new true`. Ключ `created` связан с очередью, а ключ `cancelled` связи не имеет, поэтому сообщение с таким ключом не будет маршрутизировано.

## Точное совпадение ключа

Direct exchange сравнивает routing key (ключ маршрута сообщения) и binding key (ключ связи) как точные строки. Совпадение символ в символ создаёт маршрут. Пустой ключ считается ошибкой входа: ни маршрут, ни связь с ним не имеют смысла.

Topic exchange использует собственные правила с wildcard-символами `*` и `#`. Их нельзя имитировать сравнением строк из этой главы. Учебная модель поддерживает только именованный direct exchange и не включает default exchange RabbitMQ, у которого ключ маршрута совпадает с именем очереди.

Пример показывает проверку пустых значений, которая предшествует сравнению:

```go
package main

import "fmt"

func main() {
    names := []string{"orders", ""}
    for _, n := range names {
        fmt.Println(n != "")
    }
}
```

Вывод: `true` и затем `false`. Пустое имя отбрасывается до любой маршрутизации. Это важно потому, что пустой ключ может случайно совпасть с пустым ключом связи, и тогда сообщение окажется в чужой очереди без всякой ошибки.

На практике связей бывает много: один обменник связан с несколькими очередями разными ключами. Модель смотрит на одну пару ключей за раз, поэтому её результат относится только к этой паре.

> **Важно.** Отсутствие совпавшего binding означает unrouted (не маршрутизировано). Это не означает, что сообщение сохранено.

## Подтверждение публикации и возврат

Publisher confirm — подтверждение брокера о приёме публикации по протоколу. Оно не означает, что потребитель обработал сообщение. Consumer ack — отдельное подтверждение обработки. Эти два события происходят в разное время и на разных сторонах.

Флаг `mandatory` говорит брокеру вернуть publisher сообщение, если маршрут не найден. Возврат (returned) допустим только при `mandatory = true`. Сочетание «возврат без mandatory» противоречиво, и модель относит его к неверному входу.

Пример показывает порядок событий публикации в журнале. Подтверждение брокера идёт раньше подтверждения потребителя:

```go
package main

import "fmt"

func main() {
    events := []string{"publish", "broker confirm", "consumer ack"}
    for i, e := range events {
        fmt.Println(i+1, e)
    }
}
```

Вывод: три строки с номерами. Журнал показывает, что подтверждение брокера не заменяет подтверждение обработки.

## Модель и механизм

У RabbitMQ три разных объекта: обменник выбирает маршрут, связь задаёт правило, очередь хранит сообщение. Модель проверяет каждый объект отдельно, потому что ошибка в любом из них выглядит одинаково: сообщение не доходит до обработки.

Перед публикацией полезно проверить топологию целиком, а не по отдельным сообщениям. Один вызов публикации с удачным результатом ничего не говорит о том, что привязка на месте, а очередь переживёт перезапуск. Для маршрутизации полезны три вопроса. Существуют ли все элементы топологии? Совпадает ли ключ точно? Что известно о приёме публикации и что о её обработке? Ответы записываются до написания публикатора.

Что модель не описывает, важно назвать явно. Она не знает, сохраняется ли очередь на диске, сколько сообщений потребитель получает заранее, в каком режиме он подтверждает доставку и как брокер ведёт себя при перезапуске. Эти параметры меняют наблюдаемое поведение, поэтому выводы из учебной модели нельзя переносить на конкретную конфигурацию без проверки.

Синхронизация имеет цену. Подтверждения публикации добавляют ожидание, а постоянное переподключение канала создаёт нагрузку. Выбор между высокой надёжностью и скоростью — продуктовое решение, которое нужно измерять.

## Типичные ошибки и исправление

Первая ошибка — считать успешную отправку сохранением сообщения. Исправление — различать подтверждение брокера и подтверждение обработки.

Вторая — сравнивать ключи маршрута по шаблону, как для topic exchange. Исправление — точное сравнение для direct и отдельные тесты для wildcard.

Третья — удалять общие exchange или очереди при очистке теста. Исправление — изолированный vhost или уникальный префикс, и удаление только собственных ресурсов.

> **Типичная ошибка.** Закрывать канал при ошибке и молча считать публикацию успешной. Если исход неизвестен, сообщение может быть принято, и повтор без идентификатора создаст дубль.

## Если что-то пошло не так

- Сообщения исчезают без ошибки → ключ не совпадает с binding или binding отсутствует; проверь топологию и ключ.
- Публикация кажется успешной, а обработки нет → подтверждение брокера приняли за подтверждение потребителя; проверь ack потребителя.
- После переподключения сообщения дублируются → исход публикации был неизвестен; потребитель должен быть идемпотентным.
- Очистка тестов задела чужие очереди → ресурсы не изолированы; используй отдельный vhost.
- Очередь растёт, а потребители работают → обработка медленнее поступления, либо потребители не подтверждают сообщения; сравни скорость поступления и обработки и проверь подтверждения.
- Сообщения приходят в неверном порядке → несколько потребителей или несколько очередей обрабатывают один поток; порядок нужно задавать явно по ключу.

## Проверка маршрута и подтверждения

Топологию фиксируют как набор имён и типов: exchange, очередь назначения, ключ связи и тип обменника. Для direct exchange только точное совпадение ключа создаёт маршрут. Для topic правила `*` и `#` имеют иной смысл и требуют собственных тестов. Если настроен alternate exchange, непромаршрутизированное сообщение может уйти в другую топологию, но это отдельная конфигурация, которой нет в этой модели.

Подтверждение публикации и подтверждение потребителя относятся к разным стадиям. Первое сообщает о приёме публикации брокером. Второе отмечает обработку доставленного сообщения. Ни одно из них автоматически не означает, что бизнес-операция внешней системы выполнилась ровно один раз. Метрики стоит разделять: возвраты непромаршрутизированных сообщений, отрицательные подтверждения, таймауты и повторные доставки потребителю. Объединённый счётчик скрывает причину.

При расследовании непромаршрутизированного сообщения сопоставь обменник, ключ маршрута, шаблон связи и виртуальный хост из одного события. Одного имени очереди в журнале недостаточно.

## Повтор публикации и неизвестный исход

Если соединение оборвалось до подтверждения, исход публикации неизвестен: сообщение могло принять брокер, а ответ потерялся. Повтор без идентификатора создаст дубль. Поэтому каждому сообщению задают стабильный идентификатор, и потребитель должен быть идемпотентным.

Переподключение канала не должно превращаться в молчаливый успех. Публикатор ставит таймаут на подтверждение, сохраняет исход и только потом решает, повторять ли. Настройки автоудаления, эксклюзивной очереди и долговечного обменника относятся к разным жизненным циклам и не заменяют друг друга: долговечный обменник не делает сообщения долговечными.

## Порядок и несколько очередей

Если проверяется порядок сообщений, включай в набор данных сообщения с одинаковым ключом маршрута в разные очереди и два независимых связывания. Смотри, какая очередь получила каждую копию. Сравнение ключей не показывает ни рассылку, ни конкуренцию потребителей: при нескольких потребителях одной очереди порядок обработки может отличаться от порядка поступления.

> **Подсказка.** Здесь достаточно одной строки с логическим «и», но каждое условие должно быть именно флагом.

## Итог

- Exchange выбирает маршрут, binding связывает его с очередью, а очередь хранит сообщения до обработки.
- Подтверждение публикации и подтверждение потребителя — разные события; ни одно не заменяет другое.
- Очистка тестовой топологии касается только собственного изолированного vhost или префикса.
