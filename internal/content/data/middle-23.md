# Инвалидация кеша и устаревшее чтение

## Зачем эта тема нужна

В backend-сервисе тема «Инвалидация кеша и устаревшее чтение» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

Cache invalidation (инвалидация кеша) должна учитывать порядок событий. Представьте, что версия 12 обновила проекцию, а задержанное сообщение версии 10 пришло позже: простое «последнее полученное событие побеждает» воскресит старое значение. Версия — монотонный идентификатор изменения одной сущности; сравнивать версии разных сущностей нельзя. Для deleted entity (удалённой сущности) tombstone (метка удаления) тоже несёт версию, чтобы запоздалый upsert не восстановил удалённую запись.

Easy применяет только строго более новую версию и отвергает отрицательные/невалидные значения. Medium разделяет refresh и invalidate для нового upsert/delete. Hard добавляет повторную доставку через флаг alreadyApplied. В реальном потребителе этот флаг — не произвольная переменная: дедупликационный ключ и новая версия должны фиксироваться атомарно. Иначе crash между отметкой события и обновлением кеша либо пропустит изменение, либо повторит его.

Удаление ключа само по себе не всегда достаточно. Другой запрос может прочитать старую базу и вновь положить старое значение в кеш после invalidation. Возможные решения: version fence, чтение версии источника, write-through, короткий TTL или повторное подтверждение после загрузки. Выбор зависит от задержек событий и допустимой stale-политики. Тест функции проверяет порядок ветвей, а доказательство требует конкурентного integration test с переставленными, повторёнными и задержанными событиями.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «Инвалидация кеша и устаревшее чтение». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-23-easy mode=run
package main
import "fmt"

func CacheVersionActionEasy(current, incoming int64) string {
	if current < 0 || incoming < 0 { return "invalid" }; if incoming > current { return "apply" }; return "ignore"
}

func main() { fmt.Println(CacheVersionActionEasy(4, 5)) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «Инвалидация кеша и устаревшее чтение» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-23-medium mode=run
package main
import "fmt"

func CacheEventActionMedium(current, incoming int64, deleted bool) string {
	if current < 0 || incoming < 0 { return "invalid" }; if incoming <= current { return "ignore" }; if deleted { return "invalidate" }; return "refresh"
}

func main() { fmt.Println(CacheEventActionMedium(4, 5, false)) }
```

Второй пример меняет вход так, чтобы пересечь границу контракта. Прочитайте его вместе с первым: какой именно параметр изменился и почему результат должен измениться? Эти два запуска проверяют заданное правило, но не обращаются к внешней зависимости и не доказывают её конфигурацию.

## Ошибка, повтор и восстановление

Сравни version прежде чем обновлять projection; старое событие игнорируй, новый tombstone сохраняй как fence. Deduplication и update должны иметь атомарную границу.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-23-hard mode=run
package main
import "fmt"

func ProjectionEventActionHard(current, incoming int64, deleted, alreadyApplied bool) string {
	if current < 0 || incoming < 0 { return "invalid" }; if alreadyApplied { return "duplicate" }; if incoming <= current { return "ignore" }; if deleted { return "invalidate" }; return "refresh"
}

func main() { fmt.Println(ProjectionEventActionHard(4, 5, false, false)) }
```

Порядок ветвей hard-контракта для «Инвалидация кеша и устаревшее чтение» задаёт приоритет при пересекающихся признаках. Зафиксируйте этот приоритет до реализации, а неожиданный ввод обрабатывайте отдельно от успешного результата. Тест-векторы проверяют только выбранные категории; внешний протокол требует отдельного сценария.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy сравнивает версии; Medium отделяет обновление от tombstone; Hard добавляет duplicate delivery. Проверь старое событие после нового, равную версию, повтор и удаление. Сервисный тест должен атомарно сохранять version fence и projection при повторной и переставленной доставке.

## Итог и повторение

Теперь вы умеете описать ограниченную модель темы «Инвалидация кеша и устаревшее чтение», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `middle-11`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **invalidation (инвалидация)** — Удаление или признание значения кеша устаревшим.

- **stale read (устаревшее чтение)** — Результат, который отстаёт от подтверждённой записи.

- **version (версия)** — Монотонный номер для упорядочивания изменений.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «Инвалидация кеша и устаревшее чтение» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «если вход меняется с обычного на граничный, решение должно перейти в заранее названную категорию; если зависимость временно недоступна, состояние остаётся восстанавливаемым». Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Переставленные события, повтор и tombstone

Порядок выдачи сообщений может отличаться от порядка изменения данных. Пример: событие обновления версии 17 применилось, после чего пришёл задержанный upsert версии 15. Получатель должен сравнить версии и игнорировать старое событие. Для удаления зафиксируйте tombstone с версией 18; простое удаление ключа теряет сведения о последней версии, и поздняя версия 15 может воскресить запись.

Повторная доставка не обязательно означает повторный бизнес-эффект. Используйте стабильный event ID или sequence/version вместе с идентификатором сущности. Сохранение «уже применено» отдельно от изменения проекции уязвимо к остановке процесса между двумя записями. Запишите их атомарно в одной транзакции либо выберите протокол, который допускает повтор без побочного эффекта. В Redis-кеше версия может быть вытеснена; тогда нужно определить, откуда восстановить fence и какое окно stale допускается.

Тестовый набор должен переставлять события, повторять один ID, посылать равную версию с отличающимся содержимым и проверять delete/upsert sequence. Равная версия с разными payload — конфликт целостности, а не обычное обновление. Модель главы не содержит event ID/payload и потому не обнаружит такую коллизию. Integration test должен проверять атомарность версии и проекции, рестарт consumer и очистку созданных ключей.


Идентификатор версии должен быть монотонным для одной сущности и переживать удаление/создание, если старые события ещё могут прийти. Повторное создание объекта с версией 1 опасно, если tombstone со старой версией уже отброшен. Выберите retention tombstone не короче максимального окна доставки и восстановления либо храните отдельный sequence в источнике истины. Для каждого обработанного события фиксируйте безопасные метрики applied, ignored-old, duplicate и invalid-version, не записывая персональное содержимое события.


Если версии приходят из разных shard, их сравнимость должна быть определена заранее; случайный timestamp не всегда задаёт полный порядок при одинаковом времени. Выберите источник sequence и правило tie-breaker, добавьте его в event contract и тестируйте конкурирующие обновления. Слабая версия может привести к тихому откату проекции.
