# Инвалидация кеша и устаревшее чтение

## Что ты сделаешь

Ты напишешь три функции-модели для порядка событий в кеше: применить ли событие с версией, как обработать удаление и обновление и как не спутать повтор доставки с новым событием. Функции работают с числами версий и флагами и не обращаются к кешу или базе.

## Окно рассогласования после изменения

Источник истины — база — меняется в транзакции. Кеш меняется отдельно, в другой системе. Между коммитом в базу и обновлением или удалением ключа в кеше есть промежуток, в котором кеш держит старое значение. Этот промежуток существует даже тогда, когда инвалидация идёт сразу после commit: сетевой вызов тоже занимает время.

Поэтому инвалидация не гарантирует, что кеш сразу станет правильным. Она только сокращает окно. Если инвалидация доходит до кеша с задержкой, читатели успевают заново положить старое значение, и окно растягивается. Поэтому задержку доставки инвалидаций тоже нужно измерять и считать частью модели. Чтобы понять, что произойдёт в промежутке, нужно знать порядок событий, а не только факт удаления.

## Версия вместо времени

Время записи нельзя использовать для порядка: часы разных машин расходятся, и два события могут получить обратный порядок. Надёжнее версия, которую выдаёт источник истины и которая растёт при каждом изменении строки. Событие с версией, не большей уже применённой, не может быть новее состояния в кеше.

Пример показывает правило сравнения: версия применяется только тогда, когда она строго больше текущей.

```go
package main

import "fmt"

func main() {
    current := int64(4)
    for _, incoming := range []int64{5, 6, 4} {
        if incoming > current {
            fmt.Println(incoming, "apply")
            current = incoming
        } else {
            fmt.Println(incoming, "ignore")
        }
    }
}
```

Вывод: `5 apply`, `6 apply`, `4 ignore`. Событие с версией `4` пришло после более новых и не должно откатить кеш назад.

## Поздний ответ старого чтения

Самая неприятная ситуация — поздний ответ. Читатель прочитал значение версии 4 из базы, но его ответ задержался в сети. Тем временем источник стал версией 5, и кеш получил инвалидацию. Если читатель теперь положит свой старый ответ в кеш, устаревшее значение окажется там после инвалидации.

Защита — версия при записи в кеш. Запись проходит, только если версия в ней новее уже известной версии, даже после удаления. Для этого после удаления остаётся след с последней версией. Одного удаления ключа недостаточно: поздняя запись вернёт старое значение.

> **Важно.** Удаление ключа и проверка версии при записи решают разные проблемы. Удаление очищает известное устаревшее значение, а проверка версии не даёт старому ответу вернуться.

## След удаления

Удаление ключа оставляет пустое место, и именно поэтому поздний ответ так опасен. Пустое место ничего не знает о версии. Если запомнить версию удаления в отдельном следе, то запись с меньшей версией будет отвергнута даже тогда, когда ключа уже нет. Пример показывает, как старое событие пропускается по следу:

```go
package main

import "fmt"

func main() {
    events := []struct {
        version int
        deleted bool
    }{{5, true}, {4, false}}
    tomb := 0
    for _, e := range events {
        if e.version > tomb {
            tomb = e.version
            fmt.Println("apply", e.version, e.deleted)
        } else {
            fmt.Println("skip", e.version)
        }
    }
}
```

Вывод: `apply 5 true` и затем `skip 4`. Удаление версии 5 сохранило след, и запоздавшее обновление версии 4 не вернуло запись.

След нельзя хранить вечно. Срок его жизни должен быть не короче окна, в котором поздние ответы ещё возможны. Иначе очистка следа откроет дорогу старым записям, и защита пропадёт без предупреждения.

## Удаление и обновление

Событие может быть обновлением или удалением. Удаление говорит, что ключ надо убрать: следующий читатель пойдёт в источник. Обновление позволяет положить новое значение. Оба события сравниваются по версии. Старое удаление не должно удалить свежее значение, а старое обновление не должно вернуть удалённую запись.

Для модели важен порядок проверок: сначала некорректные версии, потом сравнение порядка, потом тип события. Такой порядок совпадает с тем, как устроен отказ: сначала отбрасываем заведомо неверный ввод, затем решаем, новее ли событие, и только потом выбираем действие над кешем. Иначе устаревшее удаление может стать причиной инвалидации свежих данных.

## Повтор доставки

Брокер может доставить одно событие дважды. Тогда версия совпадает с уже применённой, и событие не должно менять кеш второй раз. Если событие такое, что его повтор безопасен, достаточно сравнения версий. Если эффект не сводится к версии, нужен отдельный признак уже обработанного события.

Учебная функция различает повтор и старое событие. Повтор уже применённого события даёт отдельный результат `duplicate`, а не `ignore`: в журнале видно, что событие было, но не менялось.

## Что проверяет интеграционный сценарий

Учебные функции не видят одновременных обработчиков. Интеграционный сценарий должен запустить два обработчика, которые получают события в обратном порядке, и проверить итоговое состояние кеша. Итог проверяют не по порядку вызовов, а по значению и версии: кеш должен содержать либо свежее значение, либо быть пустым после свежего удаления.

Сценарий также проверяет, что повтор одного события не меняет состояние второй раз и что след удаления переживает перезапуск обработчика, если его срок ещё не истёк. Часы в тесте управляются явно: события продвигаются по версиям, без ожидания реального времени.

## Модель и механизм

Для кеша полезны три вопроса. Какая версия у текущего значения? Какая версия у входящего события? Что делает событие: обновляет, удаляет или повторяет уже сделанное? Ответы записываются в виде правил до реализации обработчика. Если на один из вопросов нет ответа, обработчик не готов: он будет угадывать порядок, а угадывание в кеше обычно обнаруживают пользователи, а не тесты.

Функции этой главы моделируют только решение. Атомарность записи версии, хранение признаков обработки и гонка двух обработчиков проверяются отдельным сценарием с реальным хранилищем.

Устаревание стоит измерять, а не угадывать. Полезны три числа: доля ответов, в которых версия кеша отстаёт от версии источника, число отвергнутых поздних записей и число повторов, распознанных как дубликаты. Рост первого числа при стабильной нагрузке обычно означает, что инвалидации теряются или приходят с задержкой. Рост второго показывает, что поздние ответы реально случаются и защита работает. Третье число помогает оценить, не перегружен ли брокер повторной доставкой.

## Типичные ошибки и исправление

Первая ошибка — сравнивать время записи вместо версии. Исправление — версия, выданная источником.

Вторая — удалять ключ и считать проблему решённой. Исправление — проверка версии при каждой записи в кеш.

Третья — применять старое удаление. Исправление — сравнение версии до выбора действия.

Четвёртая — обрабатывать повтор как новое событие. Исправление — отдельный признак обработанного события.

> **Типичная ошибка.** Полагаться на порядок прихода сообщений. Брокер и сеть могут доставить события в другом порядке, и только версия восстанавливает правильный ход.

## Если что-то пошло не так

- Кеш показывает значение старее базы после обновления → поздняя запись старого ответа; добавь проверку версии при записи.
- Свежие данные пропадают после удаления → старое удаление применено без сравнения версий.
- Одно событие меняет кеш дважды → повтор доставки не распознан; храни признак обработанных событий.
- Порядок событий в журнале не совпадает с версиями → версия не выдаётся источником; сравнивай только версии.

## Воспроизводимая лабораторная: версия против позднего ответа

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Docker не нужен: кеш моделируется картой в памяти программы.

Программа повторяет сценарий позднего ответа. Источник стал версией 5, инвалидация удалила ключ, и только потом приходит старый ответ версии 4. Сначала запись делается без проверки, затем с проверкой версии по следу удаления.

```go
package main

import "fmt"

type entry struct {
    value   string
    version int
}

func main() {
    cache := map[string]entry{"item:1": {value: "old", version: 4}}
    delete(cache, "item:1")
    late := entry{value: "old", version: 4}
    cache["item:1"] = late
    fmt.Println("without check:", cache["item:1"].value)

    delete(cache, "item:1")
    tombstone := 5
    if late.version > tombstone {
        cache["item:1"] = late
    }
    _, ok := cache["item:1"]
    fmt.Println("with check:", ok)
}
```

**Ожидайте:** первая строка `without check: old` — старое значение вернулось в кеш после инвалидации. Вторая строка `with check: false` — запись отвергнута, потому что версия 4 не новее следа версии 5.

**Очистка:** программа работает только в памяти процесса и ничего не создаёт на диске. Если запускал её через временный каталог в `/dev/shm`, удали этот каталог, например командой `rm -rf /dev/shm/<каталог>`.

## Итог

- Между коммитом в базу и обновлением кеша есть окно рассогласования; инвалидация его сокращает, но не отменяет.
- Порядок событий задаёт версия источника: событие применяется только тогда, когда версия строго новее.
- Повтор доставки распознаётся отдельно от старого события, а поздний ответ не возвращается в кеш поверх свежего значения.
