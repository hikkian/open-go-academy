# Граница Redis: данные не являются очередью

## Что ты сделаешь

Ты напишешь три функции-чеклиста: решение о роли Redis для данных, проверку предпосылок очереди и проверку отказного сценария с объявленной границей потери. Функции получают булевы заявления автора и возвращают метку. Они ничего не читают из Redis и не доказывают, что система работает.

## Кеш и очередь требуют разных гарантий

Обычное кешируемое значение можно получить заново из источника истины. Если Redis потерял ключ, приложение сходит в базу и продолжит работу медленнее. Поэтому потеря кеша допустима, если продукт это разрешает.

Очередь задач устроена иначе. Задача — это обещание сделать работу. Если она пропала после того, как producer получил подтверждение, никто не вспомнит о ней. Задача может стоить денег, письма клиенту или записи в отчёт. Такие данные требуют подтверждённой записи, повторной доставки и понятного владения незавершённой задачей.

Отсюда следует простое правило: возможность прочитать значение повторно ещё не делает его надёжной очередью. Чтение вернёт данные, но не скажет, потерялась ли задача и кто сейчас обязан её обработать.

> **Важно.** Redis может быть быстрым и полезным кешем и при этом не быть очередью задач. Решение о роли нельзя принимать по одному названию структуры данных.

## Какие вопросы задать примитиву

Перед тем как использовать конкретный примитив Redis как очередь, нужно уточнить несколько вещей. Сохраняются ли данные на диске, и в каком режиме. Что именно подтверждает ответ producer: приём командой или запись на диск. Как незавершённая задача возвращается потребителю после его падения. Что происходит при переключении на резервный узел и сколько последних записей может пропасть.

Эти вопросы относятся к конфигурации и топологии, а не к коду. Учебная функция получает ответы в виде булевых флагов, поэтому её результат — только чеклист. Он не заменяет проверку настоящей конфигурации.

## Окно потери и цель восстановления

Окно потери данных — это допустимое число последних подтверждённых записей, которые можно потерять при отказе. Оно задаётся продуктом, а не выводится из настроек Redis. Если продукт не может согласиться ни на одну потерю, такой примитив не подходит для очереди без дополнительных механизмов.

Цель восстановления задаёт, за какое время система должна вернуться к работе после отказа. Её тоже нужно записать в виде измеримого числа. Флаг «цель определена» без числа ничего не доказывает: он лишь сообщает, что кто-то сделал заявление.

## Предпосылки очереди

Предпосылки очереди — это заявления автора о том, что известно и согласовано. Режим сохранения задан. Подтверждение producer описано точно. Порядок возврата незавершённой задачи определён. Обработчик идемпотентен, то есть повтор доставки не дублирует эффект.

Пример показывает, как такой чеклист даёт метку. Метка `candidate_only` означает только то, что предпосылки заявлены. Она не означает, что очередь работает под нагрузкой:

```go
package main

import "fmt"

func main() {
    flags := []bool{true, true, true, false}
    ready := true
    for _, f := range flags {
        ready = ready && f
    }
    if ready {
        fmt.Println("candidate_only")
    } else {
        fmt.Println("needs_review")
    }
}
```

Вывод: `needs_review`. Одна непроверенная предпосылка достаточна, чтобы не считать конфигурацию пригодной для очереди.

## Порядок возврата незавершённой задачи

Незавершённая задача — та, которую потребитель взял, но не подтвердил. Если он упал, задача должна вернуться в очередь. Здесь важен порядок: сначала задача остаётся за потребителем с отметкой аренды, потом по истечении срока аренды её забирает другой потребитель. Без такой отметки задача либо теряется вместе с падением, либо обрабатывается дважды.

Пример показывает журнал обработки одной задачи при повторной доставке. Эффект выполняется один раз, потому что повтор узнаётся по идентификатору:

```go
package main

import "fmt"

func main() {
    done := map[string]bool{}
    for _, id := range []string{"job-7", "job-7"} {
        if done[id] {
            fmt.Println("skip", id)
            continue
        }
        done[id] = true
        fmt.Println("effect", id)
    }
}
```

Вывод: `effect job-7` и затем `skip job-7`. Повтор доставки не дал второго эффекта. Настоящая защита хранится рядом с эффектом и переживает перезапуск, а словарь в памяти процесса — только модель.

## Переключение узла и окно потери

При переключении на резервный узел часть последних записей может не попасть на новый узел, если репликация асинхронная. Эти записи уже были подтверждены producer, но не сохранились. Именно такие записи образуют окно потери. Его размер зависит от режима репликации и момента подтверждения, а не от желания команды.

Окно нужно также измерить на реальном отказе, а не вывести из настроек: один и тот же режим может терять разное число записей при разной нагрузке и задержке сети между узлами. Поэтому в журнал отказного теста пишут число подтверждённых записей до отказа и число записей, найденных после восстановления.

Поэтому окно нужно согласовать заранее. Если продукт допускает потерю нескольких последних записей, это записывают как число. Если не допускает, подтверждение должно ждать копии на другом узле, и это уже другая цена по задержке.

Пример показывает, как число потерянных записей сравнивается с согласованным окном:

```go
package main

import "fmt"

func main() {
    acknowledged, replicated := 12, 10
    lost := acknowledged - replicated
    budget := 2
    fmt.Println("lost", lost, "within budget", lost <= budget)
}
```

Вывод: `lost 2 within budget true`. Здесь потеря укладывается в окно, но это число даёт не Redis, а сравнение, которое команда должна провести на реальном отказе.

## Отказной сценарий

Отказной тест проверяет три вещи. Подтверждённая запись переживает отказ узла. Незавершённая задача после восстановления доставляется повторно, и потребитель не выполняет эффект второй раз. После восстановления состояние совпадает с ожидаемым в пределах объявленного окна потери.

Тест должен управлять отказом сам: остановить узел в заранее выбранной точке, например между подтверждением и обработкой. Случайный сон и надежда на удачное время не дают воспроизводимого результата. Журнал отказа нужно сохранить вместе с конфигурацией и версией Redis.

## Модель и механизм

Для роли Redis полезны три вопроса. Что потеряется, если значение пропадёт? Что должно быть подтверждено до ответа producer? Что произойдёт после отказа с каждой незавершённой задачей? Ответы записываются как предпосылки до реализации.

Учебные функции отвечают только на вопрос о заявлении. Они не выясняют, включено ли сохранение, и не измеряют окно потери. Поэтому их метки стоит читать как «требует проверки» или «кандидат», но не как «готово».

## Типичные ошибки и исправление

Первая ошибка — считать Redis очередью, потому что в нём есть списки. Исправление — отдельно проверить сохранение, подтверждение и возврат задачи.

Вторая — путать подтверждение приёма с подтверждением обработки. Исправление — назвать, какое подтверждение имеется в виду, и где оно записано.

Третья — объявлять окно потери нулевым без проверки. Нулевое окно требует синхронного подтверждения записи и отдельной цены за него. Исправление — записать согласованное число и проверить его отказным тестом.

Четвёртая — доверять флагу «проверено». Флаг — заявление. Исправление — хранить ссылку на результат проведённого отказного сценария.

> **Типичная ошибка.** Считать, что повторное чтение значения после отказа равно восстановлению задачи. Значение может быть на месте, а задача уже занята другим потребителем или потеряна при переключении узла.

## Если что-то пошло не так

- Задачи пропадают после перезапуска → режим сохранения не подтверждён; проверь конфигурацию узла и момент ответа producer.
- Один и тот же платёж выполнился дважды → обработчик не идемпотентен; повтор доставки дал второй эффект.
- После переключения узла часть задач не видна → окно потери больше согласованного или возврат незавершённой работы не определён.
- Отказной тест проходит нестабильно → точка отказа выбрана случайно; зафиксируй её и повтори.

## Воспроизводимая лабораторная: что сообщает конкретный Redis

**Предварительные условия:** локальный Docker или совместимый Podman CLI и свободный loopback-порт `16379`. Используй только имя контейнера `oga-middle24-redis` и тот же закреплённый образ, что в предыдущей главе.

```sh
docker run --rm -d --platform linux/amd64 --name oga-middle24-redis -p 127.0.0.1:16379:6379 docker.io/library/redis@sha256:cb1c6f8dc0251eb2b079d774f1dbf51536b216b5568545559b20cd949235dd28
docker exec oga-middle24-redis redis-cli CONFIG GET appendonly
docker exec oga-middle24-redis redis-cli CONFIG GET save
docker exec oga-middle24-redis redis-cli SET lesson:24:job pending
docker exec oga-middle24-redis redis-cli GET lesson:24:job
```

**Ожидайте:** `CONFIG GET` печатает имя параметра и его значение, которое сервер сообщил сам; ты не задавал их и не должен угадывать, какими они будут. Команда `SET` отвечает `OK`, а `GET` возвращает `pending`. Этот вывод говорит только о том, что значение записано в память этого контейнера. Он не доказывает, что запись переживёт перезапуск, и не описывает переключение узла.

**Очистка:** `docker stop oga-middle24-redis`. Контейнер запущен с `--rm`, поэтому ключи и настройки удалятся вместе с ним.

## Итог

- Кеш восстановим из источника, очередь задач — нет: для неё нужны подтверждённая запись, повторная доставка и понятное владение.
- Роль Redis и готовность очереди заявляются чеклистом, а подтверждаются конфигурацией и отказным сценарием с измеренным окном потери.
- Метки «candidate_only» и «needs_review» — заявления для проверки, а не доказательство работы системы.
