# Граница Redis (серверного хранилища ключей и структур данных): данные не являются очередью

## Зачем эта тема нужна

В backend-сервисе тема «Граница Redis: данные не являются очередью» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

Redis может быть быстрым кешем (`cache`) и может участвовать в обработке очередей, но слова «можно повторить» недостаточно, чтобы обещать очередь, которая переживёт отказ. Повторная доступность данных (`replayability`) описывает возможность снова увидеть запись, но не доказывает, что она пережила сбой, что обработчик-потребитель (`consumer`) восстановит владение задачей или что повтор обработки не создаст второй побочный эффект. В Redis потоковая структура (`Streams`) и другие примитивы имеют разные правила для ожидающих подтверждения сообщений (`pending`), захвата сообщения другим обработчиком (`claim`) и подтверждения обработки (`ack`). Не переноси правила одного механизма на другой.

При проектировании очереди (`queue design`) назовите: механизм сохранения данных (`persistence`) и окно возможной потери; смысл подтверждения отправителя (`producer acknowledgement`) — локальная запись или реплика; поведение репликации (`replication`) и переключения при отказе (`failover`); как сообщение возвращается в работу после падения потребителя — аренда владения (`lease`), период видимости (`visibility`), захват и защита от устаревшего владельца (`fencing`). Подтверждайте сообщение только после нужного эффекта; обеспечьте идемпотентность обработчика (`idempotency`), согласуйте допустимый бюджет потери (`loss budget`) и измеримый срок восстановления (`recovery target`). Конкретные свойства зависят от версии Redis, топологии, настроек и примитива. Булевы поля упражнения — только заявления автора о предпосылках; проверяющая программа не подключается к Redis и не верифицирует их.

Easy возвращает `needs_review`, когда продукт требует сохранности: replayable не меняет ответ. Medium требует объявить выбранный persistence режим, смысл producer ack, recovery владения задачей и идемпотентность эффекта. Hard добавляет декларацию failover drill, recovery target и согласованный loss budget с допустимым окном потери. `candidate_only` означает только «все поля checklist объявлены». Оно не означает, что конфигурация существует, тест пройден или Redis подходит для production. Для реального решения нужны тесты на точной конфигурации: подтвердить, что запись принята, аварийно остановить узел в заданных точках, проверить восстановление сообщения, повторную доставку, дедупликацию, failover и измеренное окно потери. Если продукт не может принять эти условия, используйте специализированный брокер либо постоянное хранилище с нужной моделью подтверждений.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «Граница Redis: данные не являются очередью». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-24-easy mode=run
package main
import "fmt"

func RedisRoleEasy(durabilityRequired, replayable bool) string {
	if durabilityRequired { return "needs_review" }; return "cache"
}

func main() { fmt.Println(RedisRoleEasy(false, false)) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «Граница Redis: данные не являются очередью» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-24-medium mode=run
package main
import "fmt"

func RedisQueuePrerequisitesMedium(persistenceConfigured, producerAckDefined, ownershipRecoveryDefined, idempotentHandler bool) string {
	if persistenceConfigured && producerAckDefined && ownershipRecoveryDefined && idempotentHandler { return "candidate_only" }; return "needs_review"
}

func main() {
	fmt.Println(RedisQueuePrerequisitesMedium(true, true, true, true)) // candidate_only: все заявления отмечены
	fmt.Println(RedisQueuePrerequisitesMedium(true, true, false, true)) // needs_review: не описано recovery владения
}
```

Во втором вызове изменён только ownershipRecoveryDefined. Ожидаемые строки — `candidate_only`, затем `needs_review`. Так проверяется конкретная граница локальной функции; Redis не запускается и его конфигурация не проверяется.

## Ошибка, повтор и восстановление

Не приравнивай replayability к persistence или ack. Producer ack и consumer ack — разные события: первое сообщает отправителю о принятии записи по конкретным правилам примитива; второе обычно сообщает, что consumer завершил обработку. Если процесс падает после эффекта, но до consumer ack, сообщение может прийти повторно. Нужны идемпотентная операция или deduplication, а также протокол возврата незавершённой работы из pending/lease состояния. В учебной модели это только заявленные входы. Проверь crash, failover, redelivery, recovery и loss window на точной конфигурации; candidate_only не является доказательством.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-24-hard mode=run
package main
import "fmt"

func RedisQueueReviewHard(persistenceConfigured, producerAckDefined, ownershipRecoveryDefined, idempotentHandler, failoverTestDefined, recoveryTargetDefined, lossBudgetDefined bool) string {
	if persistenceConfigured && producerAckDefined && ownershipRecoveryDefined && idempotentHandler && failoverTestDefined && recoveryTargetDefined && lossBudgetDefined { return "candidate_only" }; return "needs_review"
}

func main() {
	fmt.Println(RedisQueueReviewHard(true, true, true, true, true, true, true)) // candidate_only
	fmt.Println(RedisQueueReviewHard(true, true, false, true, true, true, true)) // needs_review
}
```

Hard добавляет к medium checklist три пункта: failover drill, измеримую цель восстановления и допустимое окно потери. Ожидаемый вывод примера: сначала `candidate_only`, затем `needs_review`, потому что во втором вызове не заявлен ownership recovery. Все аргументы — обычные bool, поэтому «invalid input» здесь нет; неизвестную или непроверенную гарантию следует передавать как false.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy отказывается объявлять durable queue по паре флагов. Medium проверяет заявленные persistence/loss window, producer ack, consumer ownership recovery и idempotency. Hard требует также failover drill, recovery target и согласованный loss budget. Каждый параметр bool — ручное заявление, не чтение из Redis; тест функции подтверждает только таблицу ветвлений. Для настоящего решения зафиксируй version, topology и конкретный primitive, а затем прогони crash/restart/failover сценарий с подсчётом потерянных и повторно доставленных сообщений.

## Итог и повторение

Теперь вы умеете описать ограниченную модель темы «Граница Redis: данные не являются очередью», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `middle-16`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **eviction (вытеснение)** — Удаление ключа из-за политики памяти.

- **durability (устойчивость хранения)** — Сохранение важного состояния после отказа.

- **queue (очередь сообщений)** — Система хранения работы с заданными правилами выдачи и подтверждения.


## Лабораторный сценарий: от гипотезы до восстановления

Перед тестом очереди зафиксируйте одну гипотезу, начальное состояние, команду и момент подтверждения. Изменяйте по одному параметру. Таблица должна включать успешную доставку, отказ до подтверждения, повтор после неопределённого результата и восстановление после падения consumer. Для каждой строки запишите состояние сообщения, ожидаемое число эффектов и очистку. Ограничьте тест локальной фикстурой либо явно выделенной инфраструктурой; случайная задержка сети не воспроизводит определённую точку отказа.

Разделяйте наблюдение и вывод: stdout модели подтверждает только напечатанный результат, unit test — только контракт функции и её входы. Проверка реального движка должна указывать версию, топологию, persistence-настройки, команду и состояние до/после сбоя. Не сохраняйте DSN, токены или пользовательские данные в отчёте.

### Разбор конкретной гипотезы

Для Redis queue проверьте два раздельных отказа: primary после producer acknowledgement и consumer после эффекта до ack. Зафиксируйте, может ли сообщение потеряться, будет ли оно доставлено повторно и как предотвращается повторный side effect. Если продукт требует нулевой потери, но опыт не проверил failover или окно persistence, результат остаётся неизвестным. Укажите, какое измерение или отдельный тест закроет этот пробел.

Выбор зависит от допустимого риска и стоимости поддержки. Cache можно восстановить из источника истины; потерянная очередь может означать потерянную работу. Если требования свежести, потери или восстановления меняются, пересмотрите выбранный примитив. Не заключайте, что очередь надёжна, по тесту числового helper.

## Матрица гарантий для Redis

Перед использованием Redis для очереди составьте проверяемую матрицу. Для persistence укажите выбранный механизм, расписание и подтверждённое окно возможной потери. Для записи определите, какое подтверждение наблюдает producer и что означает replica acknowledgement. Для consumer опишите, как незавершённая работа становится доступной после падения владельца. Для side effect укажите deduplication key или идемпотентную операцию. Для failover перечислите, какие узлы и данные переживают сценарий. Наконец, согласуйте loss budget и процедуру восстановления с владельцем продукта.

Значения в упражнениях — декларации автора модели, не сигналы, прочитанные из Redis. `candidate_only` означает, что пункты заполнены; ревьюер должен подтвердить их по конфигурации, документации используемой версии и испытанию. Если хотя бы одна предпосылка ложна или неизвестна, результат `needs_review`. Не следует превращать слово «candidate» в зелёный production badge. Для кеша допускаемая потеря часто равна «значение можно восстановить из БД»; для очереди потеря задания может быть недопустима.

Failure drill записывает новое сообщение, подтверждает producer, останавливает primary до и после выбранной точки persistence, затем восстанавливает топологию и считает сообщения. Повторите с отказом consumer после побочного эффекта, но до ack; проверьте дедупликацию. Зафиксируйте версию Redis, настройки persistence/replication, тип очередного примитива, время восстановления и реально потерянные/дублированные операции. Эта лаборатория не заменяет обзор актуальных гарантий конкретного Redis релиза.


Перед выбором Redis как очереди сравните требования продукта с механизмом, а не только пропускной способностью. Уточните, нужна ли потеря нуля сообщений или допустим небольшой интервал, какой объём backlog переживает восстановление, кто управляет consumer lease и как обнаруживается poison message. Простая list/stream-like структура может дать разные semantics: не переносите свойства одного примитива на другой. Проверяйте официальную документацию конкретной версии и топологии перед тем, как записать обещание в архитектурный документ.

## Воспроизводимая лабораторная: очередь outbox в P3 и граница Redis

**Prerequisites:** Go 1.27.2, Docker Compose v2, POSIX shell с `openssl`/`seq` и свободный loopback-порт 55433. Из корня репозитория поднимите только закреплённую disposable БД из P3; случайный пароль хранится лишь в текущей shell-сессии:

```sh
set -eu
cd content/projects/p3
export POSTGRES_USER=taskflow POSTGRES_PASSWORD="$(openssl rand -hex 24)" POSTGRES_DB=taskflow_test
docker compose -p oga-middle24 up -d db
for attempt in $(seq 1 30); do
  if docker compose -p oga-middle24 exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then break; fi
  sleep 1
done
docker compose -p oga-middle24 exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"
cd reference
TASKFLOW_TEST_DATABASE_URL="postgres://taskflow:${POSTGRES_PASSWORD}@127.0.0.1:55433/taskflow_test?sslmode=disable" go test -run '^TestPostgresTaskOutboxAndTenantIsolation$' -count=1 -v
```

**Ожидайте:** тест проверяет транзакционную запись TaskFlow/outbox и сценарии lease/retry из описания проекта. В этой реализации очередь — PostgreSQL outbox; Redis не запускается и не является очередью приложения. **Очистка:** из каталога `reference` выполните `cd .. && docker compose -p oga-middle24 down -v`; volume содержит только тестовую БД этого опыта.

## Необязательный Redis Streams эксперимент

Эта отдельная проверка показывает поведение самого Redis Streams; она не запускает код приложения и не меняет вывод P3 о PostgreSQL outbox. Нужны Docker или совместимый Podman CLI и свободный loopback-порт `16380`. Используйте изолированный контейнер с тем же закреплённым Redis 8.4.2 Alpine для Linux/amd64:

```sh
set -eu
container=oga-middle24-redis
cleanup() { docker stop "$container" >/dev/null 2>&1 || true; }
trap cleanup EXIT
docker run --rm -d --platform linux/amd64 --name "$container" -p 127.0.0.1:16380:6379 docker.io/library/redis@sha256:cb1c6f8dc0251eb2b079d774f1dbf51536b216b5568545559b20cd949235dd28
for attempt in $(seq 1 30); do if [ "$(docker exec "$container" redis-cli ping 2>/dev/null)" = PONG ]; then break; fi; sleep 1; done
docker exec "$container" redis-cli XGROUP CREATE lesson:24 events 0 MKSTREAM
id=$(docker exec "$container" redis-cli --raw XADD lesson:24 '*' type task-created)
docker exec "$container" redis-cli XREADGROUP GROUP events reader-a COUNT 1 STREAMS lesson:24 '>'
docker exec "$container" redis-cli XPENDING lesson:24 events
docker exec "$container" redis-cli XCLAIM lesson:24 events reader-b 0 "$id"
docker exec "$container" redis-cli XACK lesson:24 events "$id"
docker exec "$container" redis-cli XPENDING lesson:24 events
```

**Ожидайте:** первая проверка pending показывает одно неподтверждённое сообщение; `XCLAIM` возвращает его второму обработчику, `XACK` возвращает `1`, последняя проверка pending показывает `0`. Это проверяет выбранный протокол передачи и подтверждения сообщения. Оно не проверяет долговечность, failover, конфигурацию приложения или интеграцию Redis с P3. **Очистка:** trap останавливает контейнер; `--rm` удаляет его и временные данные.
