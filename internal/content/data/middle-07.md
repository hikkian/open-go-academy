# RWMutex, Once и атомарная операция

## Что ты сделаешь

Ты напишешь три функции-модели для разных задач синхронизации: проверку повтора попытки, сравнение с заменой и ограниченное сложение. Примеры главы покажут, какой примитив подходит к какому инварианту, и где простой атомарный счётчик перестаёт быть достаточным.

## Выбор начинается с инварианта

Прежде чем выбрать примитив, сформулируй инвариант словами. Что должно оставаться верным всегда? Сколько значений в это входит? Какие операции его меняют? Только после ответов имеет смысл решать, нужен mutex, атомарная операция, канал или однократная инициализация.

Полезный первый вопрос: сколько ячеек входит в инвариант. Если одна, подходит атомарная операция. Если несколько связанных полей, нужна критическая секция под mutex. Если значение вычисляется один раз при старте, подходит `Once`. Если чтений много, а записи редки, рассматривают `RWMutex`. Если нужна передача владения, выбирают канал. Этот список не правило, а отправная точка, которую проверяют тестом и измерением.

Эти вопросы важнее выбора по скорости. Самый быстрый примитив бесполезен, если он не обеспечивает нужный порядок событий. Поэтому в главе каждый пример начинается с инварианта, а потом показывает механизм.

## sync.Once — однократное выполнение

`sync.Once` вызывает функцию ровно один раз для конкретного значения `Once`. Повторные вызовы `Do` не выполняют функцию снова, а конкурентные вызовы ждут, пока первый вызов завершится.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var once sync.Once
    for i := 0; i < 3; i++ {
        once.Do(func() {
            fmt.Println("init")
        })
    }
    fmt.Println("done")
}
```

Вывод: `init`, затем `done`. Инициализация выполнилась один раз, хотя `Do` вызывали три раза.

Граница `Once` важна. Он привязан к конкретному экземпляру и не запоминает результат по ключу: для «один раз на каждый ключ» нужна таблица с собственной синхронизацией. Если инициализация может не удаться и её нужно повторить, `Once` не подходит: функция считается выполненной даже после ошибки.

Для повторяемой инициализации используют обычный mutex и флаг готовности. Участник берёт блокировку, проверяет флаг, выполняет инициализацию и выставляет флаг только при успехе. При ошибке флаг остаётся сброшенным, и следующий участник повторит попытку. Такой протокол медленнее `Once` на горячем пути, зато ошибку можно повторить явно и наблюдать.

## Атомарная операция над одной ячейкой

Атомарная операция выполняется неделимо над одной переменной. Счётчик из `sync/atomic` подходит для независимого инкремента, потому что другой участник не увидит половину операции.

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

func main() {
    var n atomic.Int64
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            n.Add(1)
        }()
    }
    wg.Wait()
    fmt.Println(n.Load())
}
```

Вывод: `100`. Каждый `Add` неделим, поэтому ни одно обновление не теряется.

Но атомарность относится только к одной ячейке. Если инвариант связывает два поля, например баланс и версию, атомарные операции над каждым полем по отдельности не дают согласованной пары. Для такого инварианта нужна одна критическая секция, как в предыдущей главе.

## compare-and-swap и повторные попытки

Операция compare-and-swap (CAS) записывает новое значение, только если текущее равно ожидаемому. Она возвращает успех или неуспех. Неуспех означает, что другой участник успел изменить значение. Вызывающий код обычно перечитывает значение и повторяет попытку.

Повторы нужно ограничивать. Если конкуренция постоянна, бесконечный цикл съедает процессорное время и никогда не завершается. Попытка также должна учитывать отмену контекста: отменённый запрос не должен крутиться в CAS-цикле.

В Go такая операция доступна как `CompareAndSwap` у атомарного типа. Пример показывает успешную замену при совпадении ожидаемого значения:

```go
package main

import (
    "fmt"
    "sync/atomic"
)

func main() {
    var v atomic.Int64
    v.Store(7)
    old := v.Load()
    ok := v.CompareAndSwap(old, 9)
    fmt.Println(ok, v.Load())
}
```

Вывод: `true 9`. Замена прошла, потому что текущее значение совпало с тем, что прочитали раньше. Если бы между `Load` и `CompareAndSwap` другой участник записал своё значение, результат был бы `false`, и код должен был бы повторить чтение.

## RWMutex — читатели и писатель

`sync.RWMutex` допускает несколько читателей одновременно, но писатель получает эксклюзивный доступ. Пример показывает базовый порядок: запись под `Lock`, чтение под `RLock`.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var rw sync.RWMutex
    value := 0
    rw.Lock()
    value = 42
    rw.Unlock()
    rw.RLock()
    fmt.Println(value)
    rw.RUnlock()
}
```

Вывод: `42`. Чтение видит значение, потому что `Unlock` писателя предшествует `RLock` читателя.

> **Важно.** Между `RUnlock` и `Lock` состояние может измениться. Если условие проверено под чтением, после получения записи его нужно проверить снова.

RWMutex оправдан, когда чтений много и они достаточно длинные для наблюдаемой конкуренции. Он сложнее обычного mutex и может работать медленнее на коротких секциях. Выбор делается после измерения.

Есть и неочевидное правило: когда писатель уже ждёт `Lock`, новые читатели не входят под `RLock`, пока писатель не отработает. Так писатель не голодает бесконечно. Но из этого следует, что читатель, который уже держит `RLock`, не должен брать `RLock` повторно в той же горутине: если между ними встал писатель, оба будут ждать друг друга.

## Типичные ошибки и исправление

Первая ошибка — считать атомарный счётчик защитой проверки лимита. Проверка `if n < limit` и последующий `Add` — два шага. Между ними другой участник может пройти ту же проверку. Исправление — CAS-цикл или mutex на весь переход.

Вторая — ожидать, что `Once` повторит инициализацию после ошибки. Исправление — хранить ошибку и использовать протокол повтора, а не `Once`.

Четвёртая — копировать структуру с `sync.RWMutex`, `sync.Once` или mutex по значению. Копия получает собственное состояние блокировки, и защита исчезает для обоих экземпляров. Передавай такие структуры по указателю. Команда `go vet` предупреждает о копировании блокировок, поэтому её вывод стоит смотреть до запуска тестов.

Третья — смешивать атомарный и обычный доступ к одной переменной. Конкурентное чтение без атомарной операции остаётся гонкой данных, даже если запись атомарна. Все доступы к такой переменной должны идти через атомарные операции.

> **Типичная ошибка.** Выбирать `atomic` потому, что он «быстрее», без измерения и без инварианта. Lock-free код труднее доказать, а на конкуренции он может работать хуже обычного mutex.

## Если что-то пошло не так

- Лимит превышен под нагрузкой → проверка и увеличение разделены; сделай переход атомарным или под mutex.
- Инициализация не повторилась после ошибки → `Once` уже отработал; используй протокол с повтором.
- CAS-цикл не завершается → нет ограничения на число попыток или отмены.
- Тест проходит, а race detector ругается → часть доступов идёт без синхронизации; найди все чтения.

## Лаборатория перед практикой

Возьми счётчик с лимитом пять и десять горутинами, каждая из которых проверяет `if n < 5` и затем делает `Add(1)`. Перед запуском запиши, может ли итог стать больше пяти, и на каком шаге появится превышение. Затем запусти программу несколько раз с флагом `-race` и сравни наблюдение с предсказанием.

Журнал эксперимента содержит версию Go, команду, число горутин, лимит, предсказание и наблюдение. Если превышение не появилось, это не доказывает корректность: расписание могло не совпасть. Запиши это как ограничение эксперимента, а потом перепиши проверку через CAS-цикл с ограничением попыток и сравни результат.

### Практический мост: выбор примитива синхронизации

Helper не использует `RWMutex`, `Once` или атомарные операции, поэтому результат не подтверждает синхронизацию памяти. Ближайший реальный сценарий P3 — один эффект при конкурентной доставке: тест `TestPostgresTaskOutboxAndTenantIsolation` в `content/projects/p3/reference/postgres_integration_test.go`. Для реального DB-сценария используй disposable PostgreSQL.

Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда поднимает только disposable PostgreSQL из P3 Compose на loopback-порту 55433; пароль существует только в окружении shell. Она ждёт healthcheck, запускает точный тест и удаляет контейнер и volume при завершении блока:

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle07 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидай один receipt при конкурентной доставке. Это не тест `RWMutex`, `sync.Once` или atomic. Векторы этой главы охватывают только чистые функции и не заменяют интеграционные проверки.

### Задание 1 · RWMutex, Once и атомарная операция — easy

**Цель.** Для `[номер попытки, максимум]` верни `[1]`, если следующая попытка с номером `номер + 1` не превышает максимум. Нумерация начинается с 1: номер меньше 1 означает, что ни одной попытки ещё не было, и повтор не разрешён.

**Ожидаемый вывод** — входы: `[2, 4]`, затем `[4, 4]`:

```text
[1]
[0]
```

4. Вычисли номер следующей попытки.

6. Нажми «Запустить» и сравни с блоком выше.

- `[1]` для номера ноль → номер меньше единицы не отброшен.

> **Подсказка.** Сначала проверка номера, потом сравнение следующей попытки с максимумом.

## Итог

- Примитив выбирается по инварианту: одна ячейка подходит для атомарной операции, а связанные поля требуют общей критической секции.
- `Once` выполняет функцию один раз для конкретного значения; `RWMutex` разделяет чтение и запись, но не делает переход атомарным.
- CAS-повторы ограничиваются и учитывают отмену; выбор lock-free механизма делается только после измерения.
