# Ошибки, wrapping, Is/As и defer

## Зачем нужна эта тема

В Go ошибки обычно представлены значениями, возвращаемыми последним результатом. Такой подход виден в сигнатуре `(value, err)`. Если `err != nil`, вызывающий код решает, как поступить. Ошибка сама по себе не обязана аварийно завершать программу; чаще вызывающая функция добавляет полезный контекст, возвращает ошибку дальше или преобразует её в понятный ответ на своей границе. Не игнорируйте ошибку через `_` без причины: это молча превращает сбой в успех. В этой главе мы будем рассуждать не о синтаксисе ради синтаксиса, а о наблюдаемом контракте: какие значения функция принимает, какие возвращает, что она вправе менять и как отличить отсутствие результата от нормального нуля. Взрослое инженерное решение начинается с таких вопросов до написания цикла. Контракт задаёт границы задачи, помогает подобрать тесты и предупреждает случайную зависимость от деталей реализации.

Ключевой пример из этой темы — **ошибки, wrapping, is/as и defer**. Разложите его на наблюдаемые шаги. Сначала назовите вход и его тип. Затем найдите место, где данные могут отсутствовать, быть пустыми либо выйти за границу. После этого проследите изменение состояния по одной итерации. В конце проверьте, что возвращаемое значение соответствует именно требованию, а не случайному результату конкретного запуска. Такой способ чтения пригодится и при разборе чужого кода, и при диагностике собственной ошибки.

## Пример 1: основной путь

Сохраните код как `main.go` и запустите его в редакторе курса. Он использует только стандартную библиотеку, не обращается к сети и не зависит от времени или случайных данных. Сначала предскажите каждую строку вывода, затем запускайте и сравните наблюдение с прогнозом. Если ответ отличается, проследите типы значений и точки изменения, а не исправляйте программу наугад.

```go
package main

import (
    "errors"
    "fmt"
    "strconv"
)

var errInvalid = errors.New("некорректная запись")

func parseID(text string) (int, error) {
    id, err := strconv.Atoi(text)
    if err != nil { return 0, fmt.Errorf("ID %q: %w", text, err) }
    if id <= 0 { return 0, fmt.Errorf("ID должен быть положительным: %w", errInvalid) }
    return id, nil
}

func main() {
    _, err := parseID("0")
    fmt.Println(errors.Is(err, errInvalid))
}
```

Этот пример специально показывает минимальный исполняемый контекст: `package main`, необходимые импорты, небольшие функции и `main`. Для повторного использования учебная задача ниже задаёт функцию, а проверяющая система вызывает её с несколькими наборами аргументов. Поэтому не копируйте `main` внутрь отправляемого решения. Разделение примера и упражнения помогает увидеть, что демонстрация объясняет концепцию, а функция упражнения отвечает на конкретный контракт.

## Пример 2: тот же принцип в прикладной функции

Прочитайте код сверху вниз. Обратите внимание на результат операции: если API возвращает новый срез или новый объект, вызывающая сторона должна сохранить именно возвращённое значение. Не делайте вывод о неизменности входа только по тому, что функция принимает его по значению: сложные значения могут содержать ссылки на общую память. Передайте небольшую последовательность и вручную отметьте, что меняется после каждого шага.

```go
package main

import (
    "errors"
    "fmt"
)

type FieldError struct { Field string }
func (e *FieldError) Error() string { return "неверное поле: " + e.Field }

func validate(name string) error {
    if name == "" { return &FieldError{Field: "name"} }
    return nil
}

func main() {
    err := validate("")
    var fieldErr *FieldError
    if errors.As(err, &fieldErr) { fmt.Println(fieldErr.Field) }
}
```

Практический выбор здесь не сводится к «короче или длиннее». Важны владение и ожидаемая видимость изменений. Если функция обещает чистое преобразование, тест должен подтвердить, что исходный объект остался прежним. Если интерфейс допускает изменение, это поведение следует назвать в документации. Явный договор снижает стоимость сопровождения, когда через месяц функцию вызывает другой пакет или другой человек.

## Пример 3: граница и диагностируемое поведение

Третий пример подчёркивает место, где часто появляется скрытое предположение. Прочитайте его с двумя входами: обычным и граничным. При необходимости добавьте третий случай самостоятельно, не меняя смысл программы. Хорошая проверка отвечает на один вопрос: например, различаются ли пустой и отсутствующий вход, корректна ли граница индекса или сохраняется ли порядок. Если тест одновременно проверяет много несвязанных свойств, падение сложнее объяснить.

```go
package main

import "fmt"

func work() {
    defer fmt.Println("закрытие ресурса")
    defer fmt.Println("вторая очистка")
    fmt.Println("работа")
}

func main() { work() }
```

## Разбор ошибок и отладка

**Ошибка компиляции** обычно сообщает, что программа нарушила правила языка: не тот тип, неверное число результатов или неизвестное имя. Начинайте с первой ошибки компилятора, проверьте сигнатуру и типы выражений рядом с указанной строкой. Не пытайтесь лечить последующие сообщения, пока не исправлена первая: они нередко являются следствием одной причины.

**Ошибка времени выполнения** возникает при исполнении, например при выходе за границы или разыменовании nil. Воспроизведите её минимальным входом и найдите условие, которое должно было защитить операцию. Если программа не падает, но выдаёт неправильное значение, это ошибка логики: составьте маленькую трассировку, сравнив ожидаемое и фактическое состояние после каждой операции.

Для этой темы полезно отдельно спросить: изменилась ли исходная коллекция; что функция делает при нулевой длине; зависит ли результат от порядка обхода; не переполняется ли арифметика; не смешаны ли байтовая позиция и позиция кодовой точки; проверен ли nil до обращения к полю; осталась ли ошибка распознаваемой после добавления контекста. Не каждый вопрос нужен каждой задаче. Выберите релевантные и превратите их в отдельные тест-кейсы.

## Как проектировать тесты

Для любой функции из главы составьте таблицу из четырёх типов примеров: обычный вход, пустое состояние, точная граница и значение, которое нарушает предварительное условие. Если повторяющиеся элементы или ключи имеют специальное правило, добавьте отдельный случай на повтор. Записывайте ожидаемый результат до запуска. Это предотвращает распространённую ловушку: подгонку ожиданий под ошибочный вывод программы.

Публичные примеры упражнения показывают контракт на знакомых данных; скрытые проверки охватывают другие значения того же правила. Поэтому решение, которое запоминает пример, не является решением. Оно должно вычислять ответ для любого входа в оговорённых пределах. Не нужно угадывать внутренности проверки: достаточно точно выполнить условие и покрыть его тестами, которые вы сами можете объяснить.

## Практика: три задачи

### Easy: Разбери положительный идентификатор

Разобрать десятичный int через strconv.Atoi и принять только значение >0. Пустая/нечисловая/нулевая/отрицательная/переполненная запись возвращает 0 и ненулевую ошибку. Успех возвращает число,nil.

Сначала перечислите варианты входа и ожидаемые результаты. Реализуйте функцию с сигнатурой `func parsePositiveID(text string) (int, error)` в отдельном `main.go` рядом с `package main`. Не добавляйте пользовательский ввод, сетевое обращение или собственный сериализатор: grader передаёт типизированные значения напрямую. После реализации проверьте обычный пример, как минимум одну границу и случай отсутствующего/пустого значения, если он применим.

### Medium: Разбери CSV-подобную строку с контекстом

Record имеет поля ID int и Name string. Вход ровно `id,name`: разделитель первая запятая; id должен быть положительным десятичным int, name после strings.TrimSpace непустое. Лишние запятые в имени запрещены. Ошибка любого поля должна сохранять исходную причину через %w; результат при ошибке — нулевая Record.

Сначала перечислите варианты входа и ожидаемые результаты. Реализуйте функцию с сигнатурой `func parseRecord(line string) (Record, error)` в отдельном `main.go` рядом с `package main`. Не добавляйте пользовательский ввод, сетевое обращение или собственный сериализатор: grader передаёт типизированные значения напрямую. После реализации проверьте обычный пример, как минимум одну границу и случай отсутствующего/пустого значения, если он применим.

### Hard: Сохрани типизированную ошибку и Is

Для code=1 обернуть предоставленный driver-сентинел ErrNotFound, для code=2 вернуть обёрнутую *InputError{Code:2}, иначе nil. Типы ErrNotFound и InputError определены в trusted boundary. Нельзя сравнивать текст; вызов errors.Is/errors.As на результате должен работать.

Сначала перечислите варианты входа и ожидаемые результаты. Реализуйте функцию с сигнатурой `func describeFailure(code int) error` в отдельном `main.go` рядом с `package main`. Не добавляйте пользовательский ввод, сетевое обращение или собственный сериализатор: grader передаёт типизированные значения напрямую. После реализации проверьте обычный пример, как минимум одну границу и случай отсутствующего/пустого значения, если он применим.

## Краткий глоссарий

- **error** — ошибка: Значение, описывающее невозможность штатно выполнить операцию.
- **wrapping** — оборачивание: Добавление контекста поверх исходной ошибки с сохранением цепочки причин.
- **sentinel error** — ошибка-сентинел: Заранее определённая ошибка, которую сравнивают через errors.Is.
- **errors.Is** — проверка цепочки: Проверяет, совпадает ли ошибка с целевой ошибкой в цепочке обёрток.
- **errors.As** — извлечение типа: Находит ошибку требуемого типа в цепочке и присваивает её указателю.
- **defer** — отложенный вызов: Вызов, выполняемый при выходе из текущей функции в порядке LIFO.

## Что запомнить

Прежде чем писать код, сформулируйте вход, результат, ограничения и поведение на границах. Во время реализации выбирайте типы и операции, которые делают контракт читаемым. После реализации проверьте независимость данных, устойчивость к пустому входу и фактические ошибки. Если поведение намеренно ограничено, например обработкой текста на уровне рун, назовите это ограничение честно. Так следующий участник курса сможет использовать решение без догадок.

Ошибки-сентинелы удобны для стабильной категории: вызывающий код спрашивает `errors.Is(err, ErrNotFound)`, а не ищет слова в сообщении. Текст может менять формулировку и содержать контекст. Если конкретная ошибка несёт поля, например имя поля и код, определите тип с методом Error и извлекайте его через errors.As.

Оператор `%w` означает, что исходная ошибка доступна через цепочку. `%v` лишь вставляет текст, теряя машинно проверяемую связь. Оборачивайте там, где добавляется полезная операция или поле, а не на каждом слое автоматически. Много повторяющихся фраз затрудняют чтение и могут случайно раскрывать внутренние данные пользователю.

Несколько defer выполняются в обратном порядке регистрации. Это удобно, если ресурс B должен закрыться раньше ресурса A: сначала открыть A и отложить его закрытие, потом открыть B и отложить его закрытие. Отложенные вызовы выполняются при выходе из функции, включая ранний return. Поэтому defer часто соседствует с проверкой успешного открытия ресурса.

Ошибка парсинга может быть связана с ошибкой strconv, а поверх неё — с контекстом записи или строки. Такая цепочка позволяет пользователю получить объяснение «поле ID записи 14», а программа всё ещё может спросить, была ли причина числовой ошибкой. Сохраняйте эту возможность, если контракт требует errors.Is/As; не сериализуйте произвольную ошибку напрямую.
