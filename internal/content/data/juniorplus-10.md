# Фильтрация, JOIN и индексы

## Что ты сделаешь

Ты напишешь три функции, которые описывают форму результата запроса: `PageLimit` ограничит размер страницы, `LinkSortColumn` выберет ключ сортировки из заранее известного списка, `LinkBelongsTo` проверит, что строка принадлежит владельцу. Ни одна функция не обращается к базе: проверяется правило, которое потом войдёт в запрос.

## Фильтр, порядок и предел

Запрос выбирает строки (`WHERE`), задаёт порядок (`ORDER BY`) и ограничивает количество (`LIMIT`). Эти три части не меняют данные: они описывают, какой кусок набора вернуть. Без `ORDER BY` порядок строк не определён: база может вернуть их в любом порядке, и страница будет прыгать между запросами.

Если размер страницы приходит от клиента, его ограничивают заранее. Отрицательный или слишком большой `LIMIT` — ошибка контракта, а не повод отдать всю таблицу:

```go
package main

import "fmt"

func main() {
    rows := []string{"a", "b", "c", "d"}
    page := rows[1:3]
    fmt.Println(page, len(rows))
}
```

Вывод: `[b c] 4`. Срез показывает страницу, исходный набор остаётся прежним.

> **Важно.** `LIMIT` без `ORDER BY` даёт случайный порядок. Страница, которую видит пользователь, должна иметь стабильный порядок.

## JOIN и кратность

`JOIN` соединяет строки двух таблиц по ключу. Если у одной строки слева несколько совпадений справа, результат получает несколько строк. Число строк после соединения задаётся кратностью: один владелец с тремя ссылками даёт три строки.

```go
package main

import "fmt"

func main() {
    owners := map[int]string{1: "ada"}
    links := []int{1, 1, 1}
    count := 0
    for _, o := range links {
        if _, ok := owners[o]; ok {
            count++
        }
    }
    fmt.Println(count)
}
```

Вывод: `3`. Каждая ссылка находит владельца, поэтому строк три.

> **Типичная ошибка.** Ожидать одну строку на пользователя после `JOIN` с ссылками. Дубли появляются из-за кратности, и `DISTINCT` или `GROUP BY` должны быть осознанным выбором.

## Индекс — компромисс

Индекс ускоряет поиск по столбцу, но замедляет запись: при каждой вставке обновляется ещё и индекс. Без индекса база просматривает строки подряд. Проход по срезу показывает ту же идею: поиск без структуры проверяет каждый элемент:

```go
package main

import "fmt"

func main() {
    rows := []string{"a", "b", "c"}
    found := -1
    for i, r := range rows {
        if r == "c" {
            found = i
            break
        }
    }
    fmt.Println(found)
}
```

Вывод: `2`. Выбор индекса — решение о том, что чаще читается и что чаще пишется.

## Если что-то пошло не так

- Страница меняется при каждом обновлении → нет `ORDER BY` или порядок неоднозначен.
- Строк больше, чем ссылок → `JOIN` дал кратность; проверь ключ соединения.
- `index out of range` при срезе страницы → границы страницы выходят за длину набора.
- `imported and not used: fmt` → пакет есть, а печать не вызвана.

## Итог

- Фильтр, порядок и предел описывают кусок набора, а не меняют данные; без `ORDER BY` страница нестабильна.
- Кратность `JOIN` определяет число строк; дубли — следствие связей, а не ошибка запроса.
- Индекс — компромисс между чтением и записью; ключ сортировки выбирается из списка.
