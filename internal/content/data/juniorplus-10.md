## От чтения строк к форме результата

Запрос часто не нужен в режиме «вернуть всё». `WHERE` (условие отбора) ограничивает строки, `ORDER BY` задаёт порядок, а `LIMIT` ограничивает объём ответа. API должен валидировать limit до передачи базе: отрицательная страница или число в миллионы строк превращаются в ненужную работу. Маленькая нормализующая функция может проверить числовое правило, но не доказывает, что запрос реально ограничен.

Порядок должен быть полным и предсказуемым. Если сортировать только по `created_at`, несколько ссылок с одинаковым временем могут меняться местами между запросами. Добавьте уникальный tie-breaker: например `ORDER BY created_at DESC, id DESC`. Это основа стабильной постраничной выдачи. OFFSET прост для первых примеров, но на больших смещениях серверу может понадобиться пройти много строк; keyset pagination использует последний ключ и требует точного контракта сравнения.

## JOIN и кратность

`JOIN` (соединение) собирает строки из связанных таблиц. Для каждой пары строк, подходящей условию `ON`, появляется строка результата. Важно считать не только смысл таблиц, но и cardinality (кратность/кардинальность). Если у пользователя четыре ссылки, соединение `users → links` обычно выдаст четыре строки пользователя. Если затем соединить ссылки с тремя тегами каждая, результат может содержать двенадцать строк. Это не обязательно ошибка базы; это структура отношения.

Условие соединения должно описывать правильные ключи. `owner_id` может соединять владельца и ссылку, но не делает каждый slug глобально безопасным. Условия ограничения доступа часто дополнительно присутствуют в `WHERE`. При агрегации используйте `GROUP BY` и подходящий `COUNT`, но сначала проверьте, не размножает ли другой JOIN строки. `COUNT(DISTINCT ...)` иногда помогает, однако способен скрыть неверную модель соединений.

Для LinkHub owner scoped запрос должен выбрать только строки текущего пользователя. Нельзя брать owner ID из тела JSON и считать его полномочием: authenticated principal приходит с серверной сессии. Даже если slug уникален, запрос на изменение включает owner как часть условия. Локальная функция в Hard лишь проверяет равенство двух уже полученных строк; реальный доступ подтверждает интеграционный тест с двумя пользователями.

## Индексы — это цена и выбор

Индекс (index, индекс) хранит вспомогательную структуру, чтобы находить строки по определённым ключам дешевле полного сканирования в подходящем запросе. Индекс не является магическим ускорителем любой выборки: база может сознательно выбрать sequential scan, особенно если таблица маленькая или условие возвращает большую долю данных. Каждый индекс занимает место и делает `INSERT`, `UPDATE`, `DELETE` дороже, поскольку структуру надо поддерживать.

Составной индекс помогает при подходящем порядке ключей и фильтрах. Например `(owner_id, created_at DESC, id DESC)` соответствует списку ссылок владельца по времени. Индекс с колонками в обратном порядке не обязательно даст тот же поиск. Не добавляйте индекс на каждый столбец «на всякий случай»; сформулируйте реальный запрос, измерьте на достаточном наборе данных и проверьте план.

## Читать EXPLAIN без гадания

`EXPLAIN` показывает план, а `EXPLAIN ANALYZE` ещё и выполняет запрос. В production осторожно с Analyze: это реальная работа, а modifying statement потребует дополнительной осторожности и rollback. На учебной временной базе можно посмотреть тип узла, estimated rows и условия scan. `Seq Scan` не синоним плохой работы; для пяти строк он может быть лучше индекса. `Index Scan` тоже не обещает малую задержку без контекста размера и I/O.

Важное различие — оценки и наблюдения. Planner прогнозирует число строк, а analyze сообщает фактическое. Большая разница между ними может указывать на недостаточную статистику или корреляцию значений, но сначала изучите данные и форму запроса. Не сообщайте «индекс сработал» только потому, что индекс существует.

### Что проверяют задачи

Easy проверяет числовую политику лимита, включая недопустимые границы. Medium возвращает известное имя сортировки и fallback; это демонстрирует allowlist, но безопасная интеграция должна выбирать один из неизменяемых SQL фрагментов, а параметры по-прежнему передавать отдельно. Hard сравнивает owner ID, уже полученные двумя сторонами. Набор тестов проверяет только функцию и не способен вызвать JOIN, подсчитать план или проверить пользовательские данные в PostgreSQL.

Для SQL навыка используйте самостоятельную демонстрацию: она создаёт временные таблицы, соединяет их, фильтрует, сортирует, создаёт индекс, показывает `EXPLAIN` и откатывает транзакцию. Результат worker можно воспроизвести без постоянного изменения схемы. Практический P2 отдельно проверяет запросы и доступ на disposable базе.

### Типичные ошибки

- Нет `ORDER BY`, но клиент предполагает стабильную последовательность.
- `JOIN` по неуникальному полю умножает строки.
- `LIMIT` контролирует ответ, но код не ограничил работу до выполнения.
- Индекс не совпадает с фильтром/порядком либо добавлен без запроса-основания.
- `EXPLAIN ANALYZE` запущен на операции, изменяющей данные.
- Параметр пытаются использовать вместо имени столбца.
- Проверка владельца стоит после выборки в забытом маршруте, а не в контракте репозитория.

Прежде чем объявить запрос хорошим, выпишите ожидаемую кратность результата, условие владельца, стабильный порядок и максимальный объём. Затем сравните план только на данных, похожих на рабочую нагрузку.

## SQL-практика для P2 worker

Фильтр, JOIN и план запроса. Следующий блок самодостаточен: все таблицы временные, входные строки заданы прямо, а изменения отменяются. Его следует отправлять SQL worker в проектном рабочем месте P2; обычный Go function runner не подключает базу и не выполняет этот блок. Здесь нет команд управления сервером, файловой системы или роли.

```sql
BEGIN;
CREATE TEMP TABLE demo_owners(id integer PRIMARY KEY, label text NOT NULL);
CREATE TEMP TABLE demo_links(id integer PRIMARY KEY, owner_id integer NOT NULL REFERENCES demo_owners(id), slug text NOT NULL, enabled boolean NOT NULL);
INSERT INTO demo_owners VALUES (1, 'Алия'), (2, 'Бек');
INSERT INTO demo_links VALUES (10, 1, 'docs', true), (11, 1, 'old', false), (20, 2, 'home', true);
SELECT l.id, l.slug, o.label
FROM demo_links AS l JOIN demo_owners AS o ON o.id = l.owner_id
WHERE l.owner_id = 1 AND l.enabled = true
ORDER BY l.id
LIMIT 20;
CREATE INDEX demo_links_owner_enabled_idx ON demo_links(owner_id, enabled);
EXPLAIN SELECT id, slug FROM demo_links WHERE owner_id = 1 AND enabled = true ORDER BY id LIMIT 20;
ROLLBACK;
```

Предскажите вывод каждой команды, затем измените одно условие `WHERE` или JOIN и проверьте результат в disposable PostgreSQL, используя аналогичный запрос в P2 repository/migration. Если project worker недоступен, разберите блок как текст; не переносите его в общую базу.

## Практика E / M / H

- **Easy: Ограничь размер страницы.** Если requested меньше 1, верни 20; если больше 100 — 100; иначе само requested. Такая функция нормализует число и ничего не говорит о плане базы.
- **Medium: Выбери безопасный ключ сортировки.** slug → slug; created → created_at; status → enabled; для любого другого значения верни created_at. Возвращаемое имя предназначено только для выбора из заранее известного фрагмента SQL, а пользовательский ввод всё равно нельзя напрямую конкатенировать.
- **Hard: Проверь принадлежность строки владельцу.** Верни true только когда оба идентификатора непусты и совпадают побайтно. Эта локальная проверка иллюстрирует предикат ownership; в работающем repository ограничение владельца должно быть также частью SQL WHERE и результата базы.

Три упражнения проверяются детерминированными примерами функции Go. Ни одно не запускает PostgreSQL, не проверяет план запроса и не доказывает навык написания исполняемого SQL. Самостоятельная практика с запросами — в P2 workspace: перенесите SQL в проектный файл и проверяйте через Go integration tests и project verification с disposable DB. В каждом упражнении сначала запишите ожидаемый результат для стандартного и граничного входа, затем добавьте минимальную проверку. Не маскируйте ошибку пустым значением, если контракт требует отдельную категорию.

## Типичные ошибки и самостоятельная диагностика

- Порядок не включает уникальный tie-breaker. Проверьте одинаковые timestamps на двух страницах.
- JOIN размножает агрегат. Выпишите уникальность ключа с каждой стороны до написания COUNT.
- Индекс добавлен по интуиции. Сначала назовите реальный WHERE и ORDER BY, потом изучите план на сопоставимых данных.
- LIMIT не ограничивает число входов всей работы. Проверьте стоимость offset и размер страницы отдельно.

При отладке записывайте вход, ожидаемую категорию, фактический результат и состояние disposable базы. Не сохраняйте DSN, токен, cookie или содержимое реального пользовательского payload в журнал примера. Повторяемость важнее большого лога: один владелец, один объект и короткий запрос дают лучший минимальный случай.

## Повторение и глоссарий

Вернитесь к трём опорам главы: модель данных должна иметь ограничения; SQL связывает текст запроса и параметры безопасно; результат требует правильного порядка и обработки ошибок/ресурсов. Свяжите их с предыдущими знаниями: ошибки и интерфейсы из Junior помогают отделить доменную категорию от драйвера, context и integration tests делают внешнюю зависимость наблюдаемой. Дальше P2 применит тему к коротким ссылкам и пользовательским данным.

- **WHERE (условие строки)** — Часть SELECT, исключающая строки, не удовлетворяющие предикату.
- **JOIN (соединение)** — Операция сопоставления строк по условию между наборами.
- **cardinality (кардинальность)** — Число строк на стороне связи и ожидаемое число результата.
- **index (индекс)** — Дополнительная структура для поиска/порядка, имеющая цену записи и хранения.
- **query_plan (план запроса)** — Выбранная PostgreSQL последовательность операций для выполнения SQL.
- **stable_order (устойчивый порядок)** — Полный порядок с дополнительным уникальным ключом при равенстве.

Оцените доказательства отдельно: компилируемый Go пример подтверждает локальный контракт; SQL блок показывает исполняемый запрос при наличии реального worker; интеграционные проверки P2 подтверждают поведение с PostgreSQL; security review необходим для утверждений о доступе. Один слой не следует описывать как доказательство другого.
