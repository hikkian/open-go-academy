# Буферизированные каналы и владение

## Что ты сделаешь

Ты напишешь три модели буфера: подсчёт отправок, которые поместятся в буфер, буфер с вытеснением старых значений и учёт принятого, отброшенного и прочитанного. Примеры урока покажут, какая отправка будет ждать при заданной ёмкости, и почему это зависит от числа чтений.

## Ёмкость задаёт место ожидания

Буферизированный канал создаётся с ёмкостью: `make(chan int, 2)`. Пока в буфере меньше двух значений, отправка проходит без получателя. Третья отправка ждёт, пока кто-нибудь не прочитает значение. Чтение из пустого буфера тоже ждёт.

Значит, буфер меняет точку ожидания, но не отменяет ожидание. Проверить это можно по `len` и `cap`: `len` показывает число значений в очереди, `cap` — ёмкость.

```go
package main

import "fmt"

func main() {
    ch := make(chan int, 2)
    ch <- 1
    ch <- 2
    fmt.Println(len(ch), cap(ch))
    v := <-ch
    fmt.Println(v, len(ch))
}
```

Вывод: `2 2` и затем `1 1`. После двух отправок очередь заполнена. Чтение забирает самое старое значение, и очередь уменьшается на один элемент.

> **Важно.** Ёмкость — это место ожидания, а не гарантия, что ожидания не будет. Полный буфер блокирует отправителя точно так же, как небуферизированный канал блокирует его без получателя.

## Как предсказать блокировку

Простое правило: из числа отправок вычти число чтений. Результат — текущее число значений в буфере. Если он уже равен ёмкости, следующая отправка будет ждать. Если буфер пуст, следующее чтение будет ждать.

Например, канал ёмкостью 1, в который подряд отправляют два значения без чтения. Первая отправка проходит, вычитание даёт 1, и буфер полон. Вторая отправка ждёт чтения. Если читателя в программе нет, она зависнет, и предсказание совпадает с поведением.

Правило работает только для последовательного сценария, в котором известен порядок действий. В конкурентном коде порядок чтений и отправок выбирает расписание, поэтому такая модель даёт диапазон, а не точный ответ. Для проверки реального кода нужна синхронизация через явные события, а не задержки.

## Ёмкость — не пропускная способность

Буфер сглаживает кратковременный всплеск: производитель может выдать несколько значений подряд, пока потребитель занят. Но если производство постоянно быстрее потребления, очередь рано или поздно заполнится, и ёмкость ничего не изменит.

Поэтому ёмкость выбирают из требования: сколько принятых задач допустимо ожидать без потребителя. Цифра из интуиции («пусть будет сто») не годится. Сначала определи допустимый backlog, потом выбирай ёмкость, и только потом измеряй нагрузку.

## Политика переполнения

Когда буфер полон, есть три явных варианта. Можно блокировать производителя, пока место не освободится. Можно отклонить задачу с ошибкой, чтобы вызывающий код узнал о перегрузке. Можно вытеснить самое старое значение, если старые данные теряют ценность.

Вариант с отказом выглядит иначе: отправка внутри `select` с веткой `default` не ждёт. Если буфер полон, `default` выполняется, и вызывающий код получает явный отказ. Это удобно для обработчика запроса: клиент получит ответ о перегрузке вместо бесконечного ожидания. Такой отказ нужно записать в контракте и проверить тестом, иначе задача потеряется без следа.

Третий вариант требует особой внимательности: вытеснение нельзя делать молча. Оно должно быть явным и подсчитываться. Пример показывает вытеснение самых старых значений в срезе фиксированной длины.

```go
package main

import "fmt"

func main() {
    buf := []int{}
    capacity := 2
    for _, v := range []int{1, 2, 3} {
        buf = append(buf, v)
        if len(buf) > capacity {
            buf = buf[1:]
        }
    }
    fmt.Println(buf)
}
```

Вывод: `[2 3]`. Значение `1` вытеснено, когда пришло `3`. Если потеря недопустима, вытеснять нельзя: нужен обратный сигнал производителю или устойчивое хранилище.

## Учёт принятого, отброшенного и прочитанного

Модель буфера полезна, когда считаешь три числа: сколько значений принято, сколько отброшено и сколько уже прочитано. Баланс должен сходиться: принятые минус прочитанные равно тому, что осталось в очереди. Эти числа помогают проверить логику, но не заменяют проверку реального канала.

```go
package main

import "fmt"

func main() {
    capacity, produced, consumed := 4, 3, 1
    accepted := min(capacity, produced)
    dropped := produced - accepted
    left := accepted - min(consumed, accepted)
    fmt.Println(left, dropped)
}
```

Вывод: `2 0`. Буфер ёмкостью 4 принял все три значения, никто не отброшен, и одно значение уже прочитано.

## Модель и механизм

Сначала различай состояние программы и расписание. Состояние — значения в буфере, владение ресурсами и открытые каналы. Расписание — чередование шагов, выбранное системой во время исполнения. Корректная программа должна давать допустимый результат при любом расписании, которое разрешено языком.

Для буферизированного канала полезны четыре вопроса. Кто владеет очередью? Кто отправляет и кто читает? Кто закрывает канал, когда новых значений не будет? Что происходит, когда буфер полон или пуст? Ответы пишутся рядом с кодом до того, как выбрана ёмкость.

Закрытие буферизированного канала не стирает очередь. Получатель сначала получит сохранённые значения, и только затем — признак закрытия. Поэтому закрытие нельзя использовать как способ «очистить» буфер.

## Типичные ошибки и исправление

Первая ошибка — считать буфер решением блокировки. Он лишь откладывает её. Если потребитель никогда не читает, буфер заполняется, и отправитель встаёт. Исправление — определить, кто читает, и что делать при переполнении.

Вторая — выбирать ёмкость «с запасом» без расчёта. Большой буфер удерживает память, увеличивает задержку и скрывает перегрузку, пока она не станет аварией. Исправление — записать допустимый backlog и проверить его измерением.

Третья — закрывать буферизированный канал несколькими участниками. Повторное закрытие и отправка в закрытый канал вызывают панику. Право закрытия принадлежит одному владельцу, который дождался всех отправителей.

Четвёртая — вытеснять старые значения без подсчёта. Тогда данные исчезают, а отчёт говорит, что всё обработано. Исправление — считать отброшенные значения и показывать их в наблюдаемой метрике или журнале.

> **Типичная ошибка.** Использовать канал как долговременную очередь. Значения живут только в памяти процесса: после падения процесса буфер пуст, и обещание «задача не потеряна» неверно.

## Если что-то пошло не так

- Программа зависла на отправке → буфер полон, а читатель не запущен или уже вышел; найди, где читается канал.
- Потерянные задачи без ошибки → вытеснение или отбрасывание не подсчитывается; добавь счётчик.
- `fatal error: all goroutines are asleep` → все стороны ждут; проверь, что хотя бы одна может продолжить.
- Баланс не сходится → модель пропускает чтение или порядок учёта; запиши принятые, отброшенные и прочитанные по шагам.
- Задачи пропадают при нагрузке, хотя ошибок нет → отправка в `select` с `default` молча отбрасывает значение; ветка `default` должна возвращать явный отказ или считать отброс.

## Лаборатория перед практикой

Возьми пример с `len` и `cap` и добавь третью отправку перед чтением. Перед запуском запиши, что произойдёт: программа напечатает значения или зависнет. Затем запусти её с таймаутом, например через `timeout 5s go run main.go`, и сравни. Если программа зависла, восстанови порядок: прочитай одно значение между отправками и предскажи, какие числа появятся в выводе.

Журнал эксперимента содержит версию Go, команду, ёмкость, число отправок и чтений, предсказание и наблюдение. Если предсказание не совпало, сначала объясни расхождение по модели буфера, и только потом меняй код. Иначе легко подогнать код под ожидаемый вывод и не понять, почему он был другим.

## Практика

### Практический мост: буфер и владение ресурсом

Helper моделирует число или распределение, но не создаёт буферизированный канал и не назначает владельца закрытия. Реальная очередь с ограничением есть в P3: worker в `content/projects/p3/reference/worker.go` выдаёт задачи из SQL-таблицы. Тест `TestPostgresTaskOutboxAndTenantIsolation` в `content/projects/p3/reference/postgres_integration_test.go` проверяет конкурентную выдачу, но не ёмкость Go-канала.

Для реального сценария нужен disposable PostgreSQL. Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда ниже поднимает только тестовую базу из P3 Compose на loopback-порту 55433, пароль живёт только в окружении shell, а контейнер и volume удаляются при выходе из блока:

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle04 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидайте один актуальный lease и один receipt. Это проверяет очередь SQL, а не ёмкость Go-канала. Векторы этой главы охватывают только чистые функции: они не запускают goroutine и не заменяют интеграционные проверки.

### Задание 1 · Буферизированные каналы и владение — easy

**Цель.** Вернуть срез из одного числа: сколько отправок поместится в пустой буфер. Отрицательная ёмкость даёт 0.

**Ожидаемый вывод** — входы: `[2, 5]`, затем `[5, 1]`:

```text
[2]
[1]
```

**Шаги.**
1. Выбери задание «Буферизированные каналы и владение — easy»: в файле есть `BufferAcceptCount` с `panic("TODO")`. Импорты не нужны.
2. Возьми первый элемент как ёмкость, второй — как число отправок.
3. Если ёмкость меньше нуля, считай её равной нулю.
4. Возьми меньшее из ёмкости и числа отправок.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два среза из одного числа; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[5]` для `[2, 5]` → взято число отправок вместо ёмкости.
- `[-1]` для отрицательной ёмкости → значение не ограничено нулём снизу.

> **Подсказка.** Сначала ёмкость, потом минимум из двух чисел.

### Задание 2 · Буферизированные каналы и владение — medium

**Цель.** Вернуть последние значения, которые помещаются в буфер. При переполнении старые значения вытесняются. Первый элемент — ёмкость.

**Ожидаемый вывод** — входы: `[2, 4, 5, 6, 7]`, затем `[4, 1, 2]`:

```text
[6,7]
[1,2]
```

**Шаги.**
1. Выбери задание «Буферизированные каналы и владение — medium»: в файле есть `BufferLatest` с `panic("TODO")`. Импорты не нужны.
2. Возьми первый элемент как ёмкость.
3. Если ёмкость меньше единицы, верни пустой список `[]`.
4. Возьми последние значения из остатка списка, не больше ёмкости.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два списка; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[4,5,6,7]` для первого входа → ёмкость не применена, вытеснение не произошло.
- `[7]` для первого входа → взято меньше, чем помещается в буфер.
- `null` вместо `[]` при нулевой ёмкости → результат остался nil-срезом; создай пустой срез.

> **Подсказка.** Срез последних `k` элементов получается выражением `values[len(values)-k:]`, где `k` уже ограничено ёмкостью.

### Задание 3 · Буферизированные каналы и владение — hard

**Цель.** Вход: `[ёмкость, произведено, потреблено]`. Если ёмкость меньше единицы, верни `[0,0]`. Иначе принятые — меньшее из ёмкости и произведённых, отброшенные — остальные. Потребитель забирает принятые значения, но не больше принятых. Верни `[оставлено в очереди, отброшено]`.

**Ожидаемый вывод** — входы: `[3, 5, 2]`, затем `[4, 2, 0]`:

```text
[1,2]
[2,0]
```

**Шаги.**
1. Выбери задание «Буферизированные каналы и владение — hard»: в файле есть `BufferAccounting` с `panic("TODO")`. Импорты не нужны.
2. Если ёмкость меньше единицы, сразу верни `[0,0]`.
3. Вычисли принятые: меньшее из ёмкости и произведённых.
4. Вычисли отброшенные: произведённые минус принятые.
5. Вычисли, сколько потребитель забрал: меньшее из потреблённых и принятых; остаток принятых — в очереди.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Два списка из двух чисел; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[3,2]` для `[3, 5, 2]` → чтения не вычтены из принятых.
- `[0,0]` для `[4, 2, 0]` → принятые значения потеряны в расчёте.
- Ненулевой отброшенный остаток при ёмкости меньше единицы → сначала проверь ветку ёмкости, потом остальное.

> **Подсказка.** Порядок такой же, как шаги карточки: ёмкость, принятые, отброшенные, остаток.

## Итог

- Буфер сдвигает точку ожидания: отправка ждёт, когда очередь заполнена, чтение — когда она пуста.
- Ёмкость выбирается из допустимого backlog; при переполнении политика должна быть явной и подсчитываться.
- Закрытие не очищает буфер; владение закрытием остаётся у одного участника, а долговременная очередь требует отдельного хранилища.
