## Зачем нужна эта проблема

select ждёт сразу несколько коммуникаций и выбирает одну из уже готовых ветвей; если готовы несколько, язык не обещает приоритет конкретной ветви. Ветка default делает select неблокирующим и способна превратить цикл в busy loop, если тут же повторять его без ожидания. Для срока ожидания применяйте context.WithTimeout: его отмена видна через Done, а CancelFunc освобождает таймерные ресурсы и должна вызываться.

Context передавайте первым аргументом вниз по цепочке вызовов. Не храните его в структуре сервиса и не создавайте Background внутри обработчика запроса: так отмена теряется. Ошибка `context.Canceled` отличается от `DeadlineExceeded`, хотя иногда обе преобразуются в общий статус на внешней границе. Внутри сохраняйте достаточно точную категорию, чтобы не повторять уже отменённый запрос.

Практическая цена ошибки — не абстрактная «гонка». Это потерянное обновление, зависший запрос, повторный платёж, медленный shutdown или очередь, которая растёт быстрее обработки. Полезно описывать отказ тремя фразами: какое состояние было до события; какие две операции пересеклись; какой неверный результат появился. Такой разбор удерживает внимание на проверяемом причинном механизме.

## Модель и механизм

Сначала различайте состояние программы и расписание. Состояние — значения, владение ресурсами и открытые каналы. Расписание — чередование шагов, выбранное системой во время исполнения. Корректная программа должна давать допустимый результат при любом расписании, которое разрешено языком и используемыми примитивами. Если ответ верен только при предположении «эта goroutine, наверное, выполнится первой», это не контракт.

Для механизма полезны четыре вопроса. **Кто владеет изменяемым состоянием?** **Какая операция передаёт владение или синхронизирует доступ?** **Кто сообщает об окончании?** **Что происходит при ошибке или отмене?** Пишите ответы рядом с кодом. Не добавляйте канал, mutex или транзакцию до того, как поняли, какую связь они обязаны обеспечить.

Синхронизация имеет цену: блокировки создают ожидание, копирование тратит память, round trip к БД увеличивает задержку, а более сильная изоляция повышает вероятность конфликта. Но преждевременно выбирать «самый быстрый» механизм обычно нельзя: у него может не быть нужной семантики. Сначала сохраните инвариант, затем измеряйте полный путь типичной нагрузки и ищите узкое место.

### Рабочий пример 1 — `main.go`

Файл целиком компилируется командой `go run main.go`. Вывод не зависит от порядка получения отдельных результатов: программа суммирует оба значения. В примере есть конкретное подтверждение завершения всех производителей до закрытия канала.

```go group=middle-05-example1 mode=run
package main
import ("fmt";"sync")
func main(){ var wg sync.WaitGroup; results:=make(chan int,2); for _,v:=range []int{2,3}{wg.Add(1);go func(n int){defer wg.Done();results<-n*n}(v)};go func(){wg.Wait();close(results)}(); total:=0;for n:=range results{total+=n};fmt.Println(total) }
```

Обратите внимание, какая строка синхронизирует завершение, кто закрывает канал и почему закрытие находится после отправок. Измените один вход так, чтобы добавить ещё одну работу, не меняя её жизненный цикл. Затем предскажите число вывода до запуска.

### Рабочий пример 2 — `main.go`

Это самостоятельная демонстрация центрального правила главы. Вызов можно воспроизвести без внешней базы, брокера, сети или случайных задержек. Он показывает локальный механизм и не подтверждает поведение сервиса в production окружении.

```go group=middle-05-example2 mode=run
package main
import ("fmt";"sync")
func main(){ var mu sync.Mutex; counts:=map[string]int{}; var wg sync.WaitGroup; for _,key:=range []string{"a","b","a"}{wg.Add(1);go func(k string){defer wg.Done();mu.Lock();counts[k]++;mu.Unlock()}(key)};wg.Wait();fmt.Println(counts["a"],counts["b"]) }
```

Составьте таблицу из двух колонок: «что гарантирует код» и «что остаётся за его пределами». Например, mutex защищает доступ только в тех местах, где участники используют тот же mutex; чистый snapshot пример моделирует лишь переданный аргумент. Такая таблица предотвращает сильные выводы из маленького фрагмента.

### Рабочий пример 3 — `main.go`

Третий вариант отделяет событие и результат. Он нужен, чтобы потренировать чтение границы отмены или конкурентного изменения и придумать отрицательный случай. Сначала выполните с текущими параметрами, потом измените ровно один параметр, который переключает ветвь.

```go group=middle-05-example3 mode=run
package main
import ("context";"fmt")
func work(ctx context.Context, result chan<- string){<-ctx.Done();result<-"cancelled";}
func main(){ctx,cancel:=context.WithCancel(context.Background());cancel();ch:=make(chan string,1);work(ctx,ch);fmt.Println(<-ch)}
```

## Типичные ошибки и исправление

Первая ошибка — считать `go f()` подтверждением выполнения `f`. Это лишь запуск. Добавьте канал результата или WaitGroup и отдельно продумайте отмену. Вторая — считать `time.Sleep` механизмом синхронизации. Задержка может сделать тест стабильным на одной машине, но она не задаёт отношение happens-before. Ждите событие, которое сообщает о нужном переходе.

Третья ошибка — защищать только запись, забывая чтение, либо держать lock только вокруг одной половины инварианта. Пройдите по всем обращениям к данным поиском; перечислите все владельцы. Четвёртая — считать, что буфер всегда лечит блокировку. Он лишь меняет порог, при котором она появится. Если потребитель никогда не прочитает, конечный буфер рано или поздно заполнится.

Пятая ошибка — закрыть канал там, где отправители ещё живы, или разрешить нескольким участникам закрывать его. Передайте одному владельцу право закрытия. Шестая — отменить ожидание родителя, но забыть дочернюю работу. Контекст кооперативен: код должен периодически читать `Done`, а драйвер или зависимость должны принимать переданный контекст.

Седьмая ошибка — принять зелёный race detector за доказательство всех расписаний. Он важен, но проверяет увиденные исполнения. Комбинируйте unit tests, разные входы, ручной аудит доступов и bounded нагрузку. В БД также не считайте один успешный тест сериализуемостью всех транзакций: используйте реальную версию PostgreSQL и сценарии конкурирующих соединений.

## Практика без AI

### Практический мост: отмена и ограниченное ожидание

Helper с флагом отмены вычисляет категорию; он не ждёт `context.Done()`, не прерывает I/O и не проверяет гонку timeout/cancel. P3 проверяет shutdown в `content/projects/p3/reference/reference_test.go`: `TestWaitForWorkerHonorsShutdownDeadline` и `TestRunWorkersJoinsInflightWork`. Запустите `cd content/projects/p3/reference && go test -run 'Test(WaitForWorkerHonorsShutdownDeadline|RunWorkersJoinsInflightWork)' -count=1`; база не нужна. Ожидайте возврат в пределах deadline и присоединение работы после сигнала. Для других вариантов `select` P3 не содержит отдельного теста: сделайте локальный bounded эксперимент с `context.WithTimeout` и context-aware ожиданием, проверьте `errors.Is(err, context.DeadlineExceeded)`.

Уровни проверяют разные алгоритмы по теме главы. Векторы охватывают только чистую функцию: они не запускают goroutine, не устанавливают happens-before и не заменяют интеграционные проверки.

**Easy — `MinDeadline`.** Для [родительскийСрок,локальныйСрок] в миллисекундах верните меньший положительный срок; некорректное значение даёт [0].

**Medium — `RemainingDeadline`.** Для [срокРодителя,локальныйБюджет,прошло] верните max(0,min(срокРодителя,локальныйБюджет)-прошло); отрицательный ввод даёт [0].

**Hard — `DeadlineChain`.** Для последовательности вложенных бюджетов верните накопленный минимум; неположительный бюджет становится нулём и ограничивает все последующие операции.

## Разбор границ и reasoning

### Бюджет времени и отмена

Deadline ограничивает полное время операции, а timeout отдельного шага должен оставаться внутри этого общего бюджета. Если у родителя осталось меньше времени, чем локальный лимит, дочерняя операция не должна продлевать запрос. Срок полезно вычислять один раз от текущего времени и передавать дальше через context, а не строить независимые таймеры в каждом слое. Иначе каскад вызовов может суммарно ждать дольше, чем обещано клиенту. Отмена не равна принудительному завершению: код проверяет сигнал и выходит в безопасной точке, освобождая ресурсы через defer. Для операции с побочным эффектом дополнительно решите, может ли она уже завершиться на сервере после отмены клиента; сетевой timeout не доказывает, что запись не произошла. Повтор запроса поэтому зависит от идемпотентности. В тестах используйте управляемые каналы или внедрённые часы, чтобы детерминированно пройти timeout и успех. Sleep лишь замедляет тест и не задаёт порядок событий.

## Самостоятельная лаборатория: конкретный сценарий

Ограничение времени должно наследовать родительский дедлайн. Локальный компонент может сократить оставшееся время, но не должен продлевать его. Поэтому полезно вычислять минимум parent и local budgets и не запускать работу при нулевом бюджете. Отмена сообщает о намерении прекратить работу; она не откатывает уже отправленный HTTP запрос и не отменяет commit, который сервер уже подтвердил. После отмены проверьте, не остаётся ли поздняя запись состояния.

Выполните лабораторию в отдельной временной копии файла. Сначала сохраните исходный вывод. Затем измените один параметр или одну строку и запишите: какое предположение проверяется, какой результат вы ожидаете, какой результат реально получили. Если результат отличается, откатите изменение и уменьшите пример до двух действий. После объяснения ошибки восстановите код и добавьте проверку, которая обнаружит именно этот сбой. Не используйте случайные sleep, чтобы «поймать» нужное расписание; тест должен синхронизировать события явно или использовать детерминированные данные.

Минимальный журнал эксперимента содержит дату/версию инструмента, команду, входные данные, ожидаемый результат и наблюдение. Для чистой функции достаточно публичных и дополнительных граничных векторов. Для конкурентного кода укажите число участников, реальную точку синхронизации и команду race detector; отсутствие найденного отчёта ограничено пройденными путями. Для PostgreSQL запишите версию, уровень изоляции, две транзакции и порядок statements. Такие заметки помогают другому человеку воспроизвести ваш вывод, но не превращают домашний эксперимент в универсальную гарантию.

После проверки объясните, какие случаи не покрыты. Хорошее резюме признаёт границу: например, локальный тест не измеряет нагрузку production; таблица результатов не проверяет восстановление после потери процесса; один запрос не проверяет поведение при нескольких соединениях. Следующим действием должно быть конкретное расширение теста или инструментированное измерение, а не расплывчатое обещание «проверить всё».

### Ещё один проход: что меняется при отказе

Проверьте отмену в самом медленном участке, а не только перед его началом. Функция может получить уже отменённый context и всё же выполнить побочный эффект, если игнорирует Done. Добавьте раннюю проверку и повторную проверку непосредственно перед необратимым действием, если операция допускает это. Для базы данных передавайте context в метод драйвера. Уточняйте, что отмена запроса не означает автоматический rollback уже завершённого commit.

## Итог, повторение и словарь

Главная мысль: определите владение и инвариант до выбора механизма; сделайте завершение явным; тестируйте отказной путь; отделяйте локальную демонстрацию от системного доказательства. Для повторения через день нарисуйте состояния и стрелки синхронизации без исходного кода, а затем объясните код коллеге. Через неделю самостоятельно воспроизведите один отказ с изменением одного условия.

- **select — выбор коммуникации:** Оператор ожидания готовой send/receive ветви канала или отмены.
- **deadline — срок завершения:** Верхняя временная граница операции, передаваемая через context.
- **cancellation — отмена:** Кооперативный сигнал прекратить работу и распространить причину завершения.

Следующая глава `middle-06` использует эти договорённости дальше. Если пример компилируется, но объяснение результата пока не получается, не переходите к более сложному варианту: сначала перескажите модель без терминов, затем добавьте термин и конкретный тест.
