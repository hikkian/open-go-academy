# select, таймаут и отмена

## Что ты сделаешь

Ты напишешь три функции-модели для бюджетов времени: выбор меньшего срока, остаток срока после уже прошедшего времени и накопленный минимум вложенных бюджетов. Примеры покажут, как `select` выбирает готовую ветку и как отмена через `context` приходит в работу.

## select выбирает готовое

`select` ждёт сразу несколько операций с каналами и выполняет одну из тех, что готовы. Если готовы сразу несколько, язык не обещает, какая будет выбрана. Значит, порядок приоритета нельзя строить на том, что ветка записана выше.

Пример: канал с результатом уже заполнен, а канал отмены ещё открыт. Готова только одна ветка, поэтому выбор определён.

```go
package main

import "fmt"

func main() {
    result := make(chan string, 1)
    done := make(chan struct{})
    result <- "ok"
    select {
    case r := <-result:
        fmt.Println("result:", r)
    case <-done:
        fmt.Println("cancelled")
    }
}
```

Вывод: `result: ok`. Если бы канал `done` тоже был закрыт, обе ветки стали бы готовы, и выбор был бы недетерминирован. Тогда код должен работать корректно в обоих случаях. Если бизнес-правило требует предпочесть результат отмене, его нужно записать явно: например, сначала неблокирующим `select` проверить `result`, и только потом ждать `done`.

## Ветка default и busy loop

Ветка `default` делает `select` неблокирующим: если ни одна операция не готова, выполняется `default`. Это полезно для проверки «есть ли сейчас значение», но опасно в цикле. Если повторять такой `select` без ожидания, цикл будет крутиться на процессоре и тратить ресурсы впустую.

Правило простое: `default` не заменяет ожидание. Если нужно подождать, используй блокирующий `select` с каналом отмены или таймером.

## Таймаут через context

`context.WithTimeout` создаёт контекст, отмена которого наступит по сроку. Канал `ctx.Done()` закрывается при отмене или по истечении срока. `CancelFunc` освобождает таймерные ресурсы, поэтому его вызывают через `defer`, даже если срок ещё не истёк.

Контекст передаётся первым аргументом вниз по цепочке вызовов. Его не хранят в структуре сервиса и не создают `context.Background()` внутри обработчика запроса: так отмена клиента теряется.

Ошибки различаются. `context.Canceled` означает явную отмену, `context.DeadlineExceeded` — истёкший срок. На внешней границе их часто превращают в общий статус, но внутри полезно сохранить точную причину и проверять её через `errors.Is`.

```go
package main

import (
    "context"
    "errors"
    "fmt"
)

func main() {
    err := context.Canceled
    fmt.Println(errors.Is(err, context.Canceled), errors.Is(err, context.DeadlineExceeded))
}
```

Вывод: `true false`. Проверка через `errors.Is` работает даже тогда, когда ошибку обернули через `%w`, поэтому сравнивать текст сообщения не нужно.

## Ожидание результата или отмены

Типичный шаблон ожидания содержит две ветки: получение результата и `ctx.Done()`. Если результат пришёл раньше, функция возвращает его. Если контекст отменён раньше, функция возвращает причину отмены и не ждёт дальше.

```go
package main

import (
    "context"
    "fmt"
)

func wait(ctx context.Context, result <-chan string) string {
    select {
    case r := <-result:
        return r
    case <-ctx.Done():
        return ctx.Err().Error()
    }
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    cancel()
    result := make(chan string)
    fmt.Println(wait(ctx, result))
}
```

Вывод: `context canceled`. Канал результата никто не отправляет, поэтому единственная готовая ветка — отмена, и вывод определён. Такой шаблон не даёт вызывающему коду ждать вечно, если работа зависла.

Ветка отмены должна стоять рядом с каждым ожиданием, а не только в начале функции. Если между двумя ожиданиями есть долгий шаг, отмена, пришедшая в середине, останется незамеченной до следующего `select`.

Если нужен и срок ожидания результата, добавь третью ветку с таймером. Для одного ожидания `time.After` достаточно. В цикле он создаёт новый таймер на каждой итерации, поэтому для повторяющегося ожидания лучше один `time.NewTimer` с вызовом `Stop` при выходе.

## Бюджет времени

Deadline ограничивает полное время операции, а таймаут отдельного шага должен оставаться внутри этого общего бюджета. Если у родителя осталось меньше времени, чем локальный лимит, дочерняя операция не должна продлевать запрос. Поэтому фактический срок равен минимуму родительского и локального бюджета.

Срок полезно вычислить один раз и передавать дальше через context, а не строить независимые таймеры в каждом слое. Иначе каскад вызовов суммарно ждёт дольше, чем обещано клиенту. Вычисление выглядит так: `deadline := start.Add(budget)`, а проверка — `time.Now().After(deadline)`.

Для тестов часы лучше передавать аргументом: функция получает текущее время и срок, а не вызывает `time.Now()` внутри. Тогда проверка «срок уже истёк» выполняется без ожидания в реальном времени, и результат одинаков при каждом запуске. Ниже пример вычисления минимума двух сроков:

```go
package main

import "fmt"

func main() {
    parent, local := 900, 300
    budget := min(parent, local)
    fmt.Println(budget)
}
```

Вывод: `300`. Локальный компонент сократил срок, но не продлил его: родительский бюджет всё ещё ограничивает работу.

## Отмена не откатывает уже сделанное

Отмена — это намерение прекратить работу, а не принудительное завершение. Код должен проверить сигнал и выйти в безопасной точке, освободив ресурсы через `defer`. Ресурс, открытый до отмены, освобождается через `defer` сразу после открытия. Тогда путь выхода по отмене совпадает с обычным: файл, соединение или таймер закрываются одинаково. Если освобождение разнесено по ветвям, отмена почти всегда пропустит одну из них. Функция, которая игнорирует `Done`, продолжит работу и может выполнить побочный эффект после отмены.

Для операции с записью решай отдельно: может ли она уже завершиться на сервере после отмены клиента. Сетевой таймаут не доказывает, что запись не произошла. Повтор запроса поэтому зависит от идемпотентности, а не от факта таймаута.

> **Важно.** Отмена запроса не означает автоматический откат уже подтверждённого commit. Если сервер подтвердил запись, клиентский таймаут её не отменит.

## Типичные ошибки

Первая ошибка — создать `context.Background()` внутри обработчика и тем самым отделить работу от отмены клиента. Передавай контекст запроса вниз по цепочке.

Вторая — забыть `cancel` у `WithTimeout`. Таймер продолжает жить до срока, а ресурсы держатся дольше, чем нужно. Вызов `defer cancel()` сразу после создания решает проблему.

Третья — проверять отмену только перед началом работы. Функция может получить отменённый контекст во время работы и всё равно выполнить запись. Проверяй `Done` перед необратимым действием.

Четвёртая — ждать в тесте через `time.Sleep`, чтобы «дать время» таймауту. Тест станет медленным и хрупким. Используй управляемые каналы или внедрённые часы, чтобы детерминированно пройти и таймаут, и успех.

Пятая — поставить `default` в `select` внутри цикла без паузы. Цикл станет busy loop: процессор занят проверками, которые ничего не ждут. Если нужно дождаться результата, убери `default` и добавь ветку отмены или таймер.

## Если что-то пошло не так

- Программа работает дольше срока клиента → дочерний шаг создал собственный таймер; передавай один срок вниз.
- Запрос отменён, но запись появилась → операция не проверяла `Done` перед побочным эффектом; добавь проверку и идемпотентность.
- Растёт число таймеров → не вызывается `cancel`; добавь `defer cancel()`.
- Тест нестабилен на медленной машине → тест ждёт время; замени `Sleep` на явный канал.

## Лаборатория перед практикой

Возьми пример с `wait` и поменяй две строки: сделай канал `result` буферизованным и отправь в него значение до вызова `wait`, при этом не отменяй контекст. Перед запуском запиши, какую ветку выберет `select` и почему. Затем запусти и сравни. Потом отмени контекст до отправки и предскажи вывод заново.

Журнал эксперимента содержит версию Go, команду запуска, состояние каналов и контекста в момент вызова, предсказание и наблюдение. Если предсказание не совпало, сначала объясни, какая ветка оказалась готовой. Только после этого меняй код. Так видно, что ошибка была в модели готовности, а не в случайном расписании.

## Практика

### Практический мост: отмена и ограниченное ожидание

Helper с флагом отмены вычисляет категорию. Он не ждёт `context.Done()`, не прерывает ввод-вывод и не проверяет гонку между таймаутом и отменой. Проверку shutdown ведёт P3: тесты `TestWaitForWorkerHonorsShutdownDeadline` и `TestRunWorkersJoinsInflightWork` в `content/projects/p3/reference/reference_test.go`. Запусти их командой `cd content/projects/p3/reference && go test -run 'Test(WaitForWorkerHonorsShutdownDeadline|RunWorkersJoinsInflightWork)' -count=1`. База не нужна.

Первый тест ожидает возврат в пределах срока, второй — присоединение работы после сигнала. Для других вариантов `select` отдельного теста в P3 нет: сделай локальный ограниченный эксперимент с `context.WithTimeout` и проверкой `errors.Is(err, context.DeadlineExceeded)`.

Уровни проверяют разные алгоритмы по теме главы. Векторы охватывают только чистую функцию: они не запускают goroutine и не заменяют интеграционные проверки.

### Задание 1 · select, таймаут и отмена — easy

**Цель.** Для пары `[родительский срок, локальный срок]` в миллисекундах вернуть меньший срок в виде среза из одного числа. Если любое значение не положительно, верни `[0]`.

**Ожидаемый вывод** — входы: `[900, 300]`, затем `[250, 700]`:

```text
[300]
[250]
```

**Шаги.**
1. Выбери задание «select, таймаут и отмена — easy»: в файле есть `MinDeadline` с `panic("TODO")`. Импорты не нужны.
2. Проверь, что оба значения больше нуля; если нет, верни `[0]`.
3. Иначе найди меньшее из двух значений.
4. Верни срез из одного числа.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два среза из одного числа; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[900]` для `[900, 300]` → взят родительский срок; сравнивай оба значения.
- `[-1]` или `[4]` для неположительного входа → проверка положительности пропущена.

> **Подсказка.** Сначала проверка двух значений на положительность, потом минимум.

### Задание 3 · select, таймаут и отмена — hard

**Цель.** Вход — последовательность вложенных бюджетов. Вычисли накопленный минимум: первый элемент остаётся как есть, каждый следующий становится минимумом с предыдущим накопленным. Неположительный бюджет становится нулём и ограничивает все последующие операции.

**Ожидаемый вывод** — входы: `[800, 500, 700, 100]`, затем `[50, 60]`:

```text
[800,500,500,100]
[50,50]
```

**Шаги.**
1. Выбери задание «select, таймаут и отмена — hard»: в файле есть `DeadlineChain` с `panic("TODO")`. Импорты не нужны.
2. Создай пустой срез результата.
3. Пройди по бюджетам по порядку и приведи каждый неположительный к нулю.
4. Для первого элемента запиши его значение; для каждого следующего — минимум с предыдущим накопленным.
5. Верни срез накопленных значений.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Два среза; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[800,500,700,100]` без изменений → накопленный минимум не считается.
- Ненулевые значения после нулевого бюджета → нулевой бюджет не ограничивает последующие элементы; после нуля все значения результата равны нулю.

> **Подсказка.** Один цикл с переменной «текущий минимум» и одной проверкой на неположительность.

## Итог

- `select` выбирает одну готовую ветку; если готовы несколько, приоритет нужно задавать явно.
- Срок операции — минимум родительского и локального бюджетов; контекст передаётся вниз и не создаётся заново.
- Отмена — кооперативный сигнал: она не откатывает подтверждённую запись, а функция должна сама проверять `Done`.
