# Retries, backoff и общий retry budget

## Что ты сделаешь

Ты разберёшь, когда повтор помогает, а когда усиливает сбой, зачем между попытками растущая пауза со случайным сдвигом, почему у повторов должен быть общий бюджет на весь сервис, а не только лимит на запрос, и почему неизвестный исход опаснее явной ошибки. Три функции урока — `RetryAction`, `RetryDelay`, `RetryDecision` — это решения о повторе по заданным полям; они не ждут, не планируют таймеры и не знают, завершилась ли операция.

## Зачем нужна эта граница

Повтор (retry) полезен, если ошибка временная и операция безопасна для повторного выполнения. Но каждая повторная попытка — дополнительная работа ровно в тот момент, когда система деградирует: сервис, отвечающий ошибками из-за перегрузки, получает от повторов ещё больше нагрузки. Увеличение паузы (backoff) раздвигает попытки, случайное смещение (jitter) не даёт тысяче клиентов повторить одновременно, а постоянную ошибку ни то ни другое не исправит — её надо распознать и остановиться.

Сначала классифицируй ошибку: постоянный отказ (неверный запрос, нет прав, не найдено) требует остановки; временный сбой (тайм-аут, 503, обрыв соединения) может допускать повтор. Затем проверь остаток срока, лимит попыток на запрос и общий бюджет повторов сервиса. Идемпотентность — одинаковый итог при повторном применении — должна быть обеспечена контрактом операции, а не предполагаться из-за того, что используется очередь или HTTP.

```go group=action mode=run
package main

import "fmt"

func retryAction(attempt, maxAttempts int, transient bool) string {
    if attempt < 0 || maxAttempts <= 0 {
        return "invalid"
    }
    if !transient {
        return "stop"
    }
    if attempt >= maxAttempts {
        return "exhausted"
    }
    return "retry"
}

func main() {
    fmt.Println(retryAction(0, 3, true), retryAction(2, 3, true), retryAction(3, 3, true), retryAction(0, 3, false), retryAction(0, 1, true))
}
```

Вывод:

```text
retry retry exhausted stop retry
```

`attempt` — число уже выполненных попыток: при лимите три и трёх сделанных попытках четвёртой не будет. Постоянная ошибка останавливает сразу, даже на нулевой попытке: повторять то, что заведомо не изменится, — тратить бюджет и время.

> **Важно.** Классификация ошибки — часть контракта зависимости. Если сервис отвечает одним кодом на всё, клиент не может отличить временное от постоянного и будет либо повторять ошибки валидации, либо сдаваться на тайм-аутах.

## Пауза: удвоение с потолком и без переполнения

Экспоненциальная пауза: первая попытка через базовое время, каждая следующая — вдвое дольше, но не дольше потолка. Удваивать нужно осторожно: после шестидесяти удвоений число не влезет в `int`. Поэтому цикл останавливается, как только текущая пауза больше половины потолка — следующее удвоение превысит его.

```go group=delay mode=run
package main

import "fmt"

func retryDelay(attempt, baseMillis, capMillis int) int {
    if attempt < 0 || baseMillis < 0 || capMillis < 0 {
        return 0
    }
    delay := baseMillis
    for n := 0; n < attempt && delay < capMillis; n++ {
        if delay > capMillis/2 {
            return capMillis
        }
        delay *= 2
    }
    if delay > capMillis {
        return capMillis
    }
    return delay
}

func main() {
    fmt.Println(retryDelay(0, 10, 100), retryDelay(1, 10, 100), retryDelay(4, 10, 100), retryDelay(100, 1, 100), retryDelay(0, 10, 5), retryDelay(0, 0, 100))
}
```

Вывод:

```text
10 20 100 100 5 0
```

Сотая попытка при базе в миллисекунду — потолок, а не переполнение; база выше потолка обрезается сразу; нулевая база остаётся нулевой. Jitter добавляют поверх: случайную долю паузы, чтобы клиенты, упавшие одновременно, не вернулись одновременно. Функция урока детерминирована и jitter не моделирует.

> **Типичная ошибка.** `base << attempt` или `base * 2^attempt` без потолка внутри цикла. На тестовых числах работает, на большой попытке даёт отрицательную паузу — и клиент повторяет мгновенно и бесконечно.

## Бюджет на сервис, а не только лимит на запрос

Лимит попыток на запрос не защищает систему: тысяча запросов по три попытки — три тысячи вызовов в деградирующую зависимость. Общий бюджет повторов (retry budget) ограничивает долю повторов от всех вызовов за окно — например, не больше десяти процентов, — и когда он исчерпан, новые ошибки не повторяются вовсе, пока бюджет не восстановится. Так повторы не превращаются в самоусиление сбоя.

```go group=decision mode=run
package main

import "fmt"

func decision(attempt, maxAttempts, budgetRemaining, delayMillis, deadlineRemainingMillis int, transient bool) string {
    if attempt < 0 || maxAttempts <= 0 || budgetRemaining < 0 || delayMillis < 0 || deadlineRemainingMillis < 0 {
        return "invalid"
    }
    if !transient {
        return "stop"
    }
    if attempt >= maxAttempts {
        return "exhausted"
    }
    if budgetRemaining == 0 {
        return "budget_exhausted"
    }
    if deadlineRemainingMillis == 0 || delayMillis >= deadlineRemainingMillis {
        return "deadline"
    }
    return "retry"
}

func main() {
    fmt.Println(decision(0, 3, 2, 10, 20, true), decision(3, 3, 2, 1, 20, true), decision(0, 3, 0, 1, 20, true))
    fmt.Println(decision(0, 3, 2, 20, 20, true), decision(0, 3, 2, 0, 0, true), decision(0, 3, 2, 1, 20, false))
}
```

Вывод:

```text
retry exhausted budget_exhausted
deadline deadline stop
```

Порядок правил — политика: сначала валидность, потом природа ошибки, потом лимит на запрос, потом общий бюджет, потом срок. Пауза, равная остатку срока, — уже `deadline`: пока клиент дождётся повтора, его срок истечёт, и повтор сделает работу для никого. Функция не резервирует бюджет и не ждёт — она только отвечает, что делать с этим снимком.

> **Зачем.** Бюджет восстанавливается со временем, лимит на запрос — нет. Первый защищает зависимость от волны, второй — вызывающего от бесконечного ожидания; нужны оба.

## Повторы в цепочке сервисов

Повторы умножаются по слоям. Если браузер повторяет три раза, шлюз — три раза, а сервис — три раза перед вызовом базы, один сбой базы превращается в двадцать семь запросов. Поэтому повторы размещают на одном уровне — обычно ближе всего к источнику сбоя, где известна природа ошибки, — а верхние уровни либо не повторяют вовсе, либо повторяют только то, что нижний объявил непереповторённым. Это тоже часть контракта зависимости: ответ «уже повторяли, бесполезно» (например, явный признак в ошибке) экономит бюджет всем, кто выше.

Второе умножение — веерные вызовы: запрос, который обращается к десяти зависимостям, при повторе целиком повторяет и девять успешных вызовов. Повторять нужно отказавший шаг, а не весь запрос, и это требует, чтобы шаги были разделимы, а их результаты — сохраняемы между попытками.

## Неизвестный исход

Самый опасный случай — тайм-аут: клиент не знает, выполнилась ли операция. Повтор без ключа идемпотентности может создать дубликат — второй заказ, второе списание. Перед повтором такой операции нужен либо ключ идемпотентности, по которому сервер распознает повтор, либо запрос состояния: «есть ли уже заказ с таким client-id?». Повтор чтения безопасен; повтор записи безопасен только по контракту, а не по умолчанию.

## Практическая процедура

Запиши таблицу правил в порядке приоритета: некорректные данные; постоянная ошибка; исчерпан лимит на запрос; исчерпан общий бюджет; не осталось времени; допустимая временная ошибка. Для каждой строки — одно ожидаемое решение. Затем подбери входы, где срабатывают два условия сразу — исчерпан лимит и постоянная ошибка, нулевой бюджет и нулевой срок, — и проверь, какое из них побеждает. Отдельно перечисли операции сервиса и для каждой отметь: идемпотентна ли, какой ключ это обеспечивает, что делать при тайм-ауте.

Наконец, повторы видны в метриках: доля повторных вызовов от всех вызовов, доля запросов, исчерпавших лимит, и доля отказов по бюджету. Первая показывает здоровье зависимости раньше её собственных алертов, вторая — что лимит мал или ошибка постоянная, третья — что бюджет работает и защищает. Без этих трёх цифр повторы невидимы до тех пор, пока не станут причиной инцидента, а не его следствием.

## Типичные ошибки

- Повтор постоянной ошибки: валидация не исправится от третьей попытки.
- Фиксированная пауза без удвоения и без jitter: синхронные волны повторов.
- Удвоение без потолка внутри цикла: переполнение и мгновенные повторы.
- Лимит на запрос без общего бюджета: тысяча запросов умножают нагрузку на зависимость.
- Пауза не сравнена с остатком срока: повтор завершается после истечения срока вызывающего.
- Повтор записи после тайм-аута без ключа идемпотентности: дубликаты.

## Самостоятельная лаборатория

Напиши клиент к учебному серверу, который первые N запросов отвечает 503, а затем 200, и реализуй повторы по функциям урока: классификация ошибки по коду, пауза с удвоением и потолком плюс случайный сдвиг, лимит на запрос, общий бюджет как доля повторов за минуту, срок из контекста. Запусти сто параллельных клиентов и посчитай, сколько вызовов получил сервер с бюджетом и без. Затем добавь к серверу «тайм-аут после выполнения» и покажи, как повтор без ключа идемпотентности создаёт дубликат, а с ключом — нет.

## Если что-то пошло не так

- `retry` при `attempt == maxAttempts` → `attempt` — уже выполненные попытки; сравнение `>=`.
- `exhausted` при постоянной ошибке → природа ошибки проверяется раньше лимита.
- Отрицательная пауза на большой попытке → потолок проверяется внутри цикла.
- `retry` при паузе, равной остатку срока → нужно строго меньше.
- `deadline` при нулевом бюджете → бюджет проверяется раньше срока.
- `import … is not allowed` → импорты запрещены: целые числа и флаги.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и числами. Все времена — в миллисекундах; функции детерминированы и ничего не ждут.

### Задание 1 · Easy: разрешение retry

**Цель.** `attempt < 0` или `maxAttempts ≤ 0` → `invalid`; постоянная ошибка → `stop`; `attempt ≥ maxAttempts` → `exhausted`; иначе `retry`.

**Ожидаемый вывод** — для `(attempt=0, maxAttempts=3, transient=true)`:

```text
"retry"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func RetryAction(attempt int, maxAttempts int, transient bool) string`. Импорты запрещены.
2. Валидность → `!transient` → `attempt >= maxAttempts` → `retry`.
3. «Запустить», «Проверить» — закрытые примеры: `(2,3)` → `retry`; `(3,3)` → `exhausted`; постоянная ошибка → `stop`; `(0,1)` → `retry`.

**Как проверить себя.** `attempt` — уже выполненные попытки; `stop` побеждает `exhausted`.

**Если не принято.**
- `retry` для `(3,3)` → строгое `>`.
- `exhausted` при `transient = false` → порядок правил.

> **Подсказка.** Четыре `return` в порядке условия.

### Задание 2 · Medium: capped exponential backoff

**Цель.** Отрицательный аргумент → `0`; иначе `min(base · 2^attempt, cap)` без переполнения; нулевая база остаётся нулевой.

**Ожидаемый вывод** — для `(attempt=0, baseMillis=10, capMillis=100)`:

```text
10
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func RetryDelay(attempt int, baseMillis int, capMillis int) int`. Импорты запрещены.
2. `delay := baseMillis`; цикл `attempt` раз, пока `delay < capMillis`: если `delay > capMillis/2` — верни `capMillis`, иначе удвой.
3. После цикла обрежь по потолку. «Запустить», «Проверить» — закрытые примеры: `(1,10,100)` → 20; `(4,10,100)` → 100; `(100,1,100)` → 100; `(0,10,5)` → 5; `(0,0,100)` → 0; `MaxInt` как база и потолок → `MaxInt`.

**Как проверить себя.** Сотая попытка не переполняется; база выше потолка обрезается на нулевой попытке.

**Если не принято.**
- Отрицательный результат → удвоение без проверки половины потолка.
- `10` для `(0,10,5)` → обрезка по потолку после цикла отсутствует.

> **Подсказка.** Условие `delay > capMillis/2` — единственная защита от переполнения; не заменяй его умножением.

### Задание 3 · Hard: retry budget и deadline

**Цель.** Некорректные поля → `invalid`; постоянная ошибка → `stop`; лимит → `exhausted`; бюджет 0 → `budget_exhausted`; срок 0 или пауза ≥ срока → `deadline`; иначе `retry`.

**Ожидаемый вывод** — для `(attempt=0, maxAttempts=3, budgetRemaining=2, delayMillis=10, deadlineRemainingMillis=20, transient=true)`:

```text
"retry"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func RetryDecision(attempt int, maxAttempts int, budgetRemaining int, delayMillis int, deadlineRemainingMillis int, transient bool) string`. Импорты запрещены.
2. Отрицательные счётчики или времена, `maxAttempts <= 0` → `"invalid"`.
3. Далее по порядку: `stop`, `exhausted`, `budget_exhausted`, `deadline`, `retry`.
4. «Запустить», «Проверить» — закрытые примеры: лимит → `exhausted`; бюджет 0 → `budget_exhausted`; пауза 20 при сроке 20 → `deadline`; срок 0 → `deadline`; постоянная ошибка → `stop`.

**Как проверить себя.** Повтор разрешён, только если пауза строго меньше остатка срока; функция не резервирует общий бюджет и не ждёт.

**Если не принято.**
- `retry` при паузе, равной сроку → нужно `<`.
- `deadline` при нулевом бюджете → бюджет раньше срока.
- `budget_exhausted` при постоянной ошибке → природа ошибки первая после валидности.

> **Подсказка.** Шесть правил — шесть строк; порядок и есть контракт.

- Чем общий бюджет повторов отличается от лимита попыток на запрос?
- Почему пауза, равная остатку срока, означает отказ от повтора?

## Итог

- Повторяют только временные ошибки, с растущей паузой и сдвигом; постоянную ошибку распознают и останавливаются.
- Лимит на запрос защищает вызывающего, общий бюджет — зависимость; пауза сравнивается с остатком срока.
- Тайм-аут — неизвестный исход: повтор записи безопасен только с ключом идемпотентности или запросом состояния.
