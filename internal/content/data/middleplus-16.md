# 16. Retries, backoff и общий retry budget

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-15`
**Цель:** Retry (повтор) помогает при временном сбое, но каждая повторная попытка добавляет нагрузку именно в момент деградации. Backoff (увеличение паузы) и jitter (случайное смещение) уменьшают синхронные волны, но не исправляют постоянную ошибку. Нужны deadline, лимит попыток и общий бюджет, согласованный с идемпотентностью операции.

## Термины и перевод

- **Повторы с бюджетом** — Retry (повтор) помогает при временном сбое, но каждая повторная попытка добавляет нагрузку именно в момент деградации. Backoff (увеличение паузы) и jitter (случайное смещение) уменьшают синхронные волны, но не исправляют постоянную ошибку. Нужны deadline, лимит попыток и общий бюджет, согласованный с идемпотентностью операции.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Повтор (retry) полезен, если ошибка временная и операция безопасна для повторного выполнения. Во время деградации каждая новая попытка создаёт дополнительную работу, поэтому повторы могут усилить исходную проблему. Backoff (увеличение паузы между попытками) раздвигает повторные вызовы; jitter (случайное смещение паузы) снижает вероятность, что много клиентов повторят одновременно.

Сначала классифицируйте ошибку: постоянный отказ обычно требует остановки, а временный сбой может допускать повтор. Затем проверьте остаток deadline (крайнего срока), лимит попыток и общий retry budget (бюджет повторов). Идемпотентность (одинаковый итог при повторном применении) должна быть обеспечена контрактом операции, а не предполагаться из-за того, что используется очередь или HTTP.

Функции урока классифицируют заданные поля. Они не ждут, не планируют таймеры, не обращаются к сервису и не могут узнать, завершилась ли операция до timeout. Этот неизвестный исход важен: перед повтором иногда требуется ключ идемпотентности или запрос состояния.

## Три запускаемых примера

### Пример 1: обычный путь

```go
package main

import "fmt"

func RetryAction(attempt int, maxAttempts int, transient bool) string {
	if attempt < 0 || maxAttempts <= 0 { return "invalid" }; if !transient { return "stop" }; if attempt >= maxAttempts { return "exhausted" }; return "retry"
}

func main() { fmt.Println(RetryAction(1, 3, true)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 2: решение с несколькими сигналами

```go
package main

import "fmt"

func RetryDelay(attempt int, baseMillis int, capMillis int) int {
	if attempt < 0 || baseMillis < 0 || capMillis < 0 { return 0 }; delay := baseMillis; for n:=0; n<attempt && delay<capMillis; n++ { if delay > capMillis/2 { return capMillis }; delay *= 2 }; if delay > capMillis { return capMillis }; return delay
}

func main() { fmt.Println(RetryDelay(4, 10, 100)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 3: проверка ограниченного инварианта

```go
package main

import "fmt"

func RetryDecision(attempt int, maxAttempts int, budgetRemaining int, delayMillis int, deadlineRemainingMillis int, transient bool) string {
	if attempt < 0 || maxAttempts <= 0 || budgetRemaining < 0 || delayMillis < 0 || deadlineRemainingMillis < 0 { return "invalid" }; if !transient { return "stop" }; if attempt >= maxAttempts { return "exhausted" }; if budgetRemaining == 0 { return "budget_exhausted" }; if deadlineRemainingMillis == 0 || delayMillis >= deadlineRemainingMillis { return "deadline" }; return "retry"
}

func main() { fmt.Println(RetryDecision(1, 3, 2, 100, 250, true)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.


## Практическая процедура

Запишите таблицу правил в порядке приоритета: некорректные данные; постоянная ошибка; нет остатка времени; исчерпан лимит или общий бюджет; допустимая временная ошибка. Для каждой строки определите одно ожидаемое решение. Затем подберите входы, где одновременно срабатывают два условия, чтобы проверить, какое из них имеет приоритет.

Для реального клиента добавьте ограниченное число попыток, верхний предел паузы, отмену по deadline и общий бюджет на процесс или операцию. Случайное смещение не должно делать тест недетерминированным: в учебном helper проверяйте решение, а расписание пауз тестируйте отдельно с контролируемыми часами и источником случайности.

Сохраните вход, ожидаемую и фактическую метку. Это проверяет политику классификации, но не гарантирует временную ошибку, безопасность побочного эффекта или корректность backoff на живом сервисе. Для этого нужны тесты интеграции и повторов на фиксированном поведении зависимости.

## Разбор сценария: Retries, backoff и общий retry budget

Возьмите одну операцию и проведите её через заданную последовательность: первая попытка завершается временной ошибкой; проверяется остаток времени; принимается решение о повторе; следующий результат либо завершает операцию, либо снова расходует бюджет. Запишите номер попытки и состояние бюджета после каждого шага.

Теперь измените по одному условию: ошибка становится постоянной, deadline истекает или общий бюджет исчерпан. Для каждого случая объясните, почему дальнейший вызов запрещён или нуждается в отдельном правиле. Если исход первой попытки неизвестен из-за timeout, укажите, как ключ идемпотентности или чтение состояния предотвращает двойной эффект.

Отчёт должен различать вычисленную helper-ом политику и фактическое выполнение повторов. Публичные/закрытые векторы подтверждают только заданные комбинации входов; они не измеряют лавину запросов и не реализуют ожидание. Следующий системный тест должен контролировать число вызовов зависимости и общий срок операции.

## Лаборатория: проследить бюджет попыток

### Численный сценарий

Задайте один запрос с общим deadline через десять секунд, максимумом трёх попыток и общим бюджетом двух повторов. Первая попытка заняла две секунды и вернулась с временной ошибкой; после backoff в одну секунду остаётся семь секунд. Повтор разрешён, если требуемое время следующего вызова помещается в остаток. Если вторая попытка занимает шесть секунд, остаётся одна секунда: третья попытка может быть запрещена даже при свободном счётчике попыток. Локальный лимит и общий срок — независимые ограничения.

Теперь замените временную ошибку на постоянную, например ошибку валидации. Повтор не исправит вход и только потратит ресурсы. Если же клиент получил timeout после возможного выполнения записи, неизвестно, изменилось ли состояние. Здесь идемпотентный ключ (стабильный идентификатор одной операции) или запрос состояния важнее числа повторов: иначе повтор может применить тот же эффект дважды.

### Разбор таблицы решений

Составьте столбцы: класс ошибки, номер попытки, оставшееся время, бюджет повторов, известность результата и ожидаемое решение. Сначала задайте правило для некорректного входа, затем постоянной ошибки, затем истёкшего deadline, исчерпанного бюджета и допустимого временного сбоя. Если несколько условий истинны, приоритет должен быть определён заранее.

Прогоните пять случаев вручную. В первом временный сбой имеет остаток и бюджет — ожидайте повтор. Во втором повторов уже два — остановитесь. В третьем нет остатка — не начинайте работу, которая не может закончиться вовремя. В четвёртом ошибка постоянна — верните её вызывающему коду. В пятом исход вызова неизвестен — сначала запросите состояние или повторите с тем же ключом, если операция поддерживает такую гарантию.

### Пауза и эксперимент

Экспоненциальная пауза увеличивает ожидание после каждой ошибки, но должна иметь верхний предел. Если много клиентов используют одинаковые значения без jitter (случайного смещения), их повторы могут синхронизироваться. Для воспроизводимого теста не полагайтесь на случайный сон: передайте источник времени и случайности как зависимости либо тестируйте классификацию решения отдельно от реального таймера.

Сделайте небольшой опыт с искусственной зависимостью, которая детерминированно ошибается заданное число раз и затем отвечает. Запишите число фактических вызовов, суммарное время и итог операции. Повторите с постоянной ошибкой и проверьте, что вызовов не больше предела. В этом репозитории helper возвращает решение по полям, но не совершает запросы и не реализует backoff. Его результат не доказывает, что зависимость действительно временная, побочный эффект безопасен или несколько клиентов делят бюджет корректно. Отчёт должен объяснить эти границы.

### Планирование пауз и джиттера

Пусть базовая пауза равна 200 миллисекундам, а каждый повтор удваивает задержку до верхнего предела двух секунд. При трёх попытках интервалы могут быть 200 и 400 миллисекунд; общее ожидание до третьего вызова равно 600 миллисекундам, без времени самих вызовов. Если каждая операция сама выполняется 3 секунды, deadline в 5 секунд оставляет слишком мало времени для полного цикла. Расчёт должен включать время запроса, паузы и резерв на возврат результата.

Jitter может случайно выбирать паузу внутри диапазона, например от половины до полной вычисленной задержки. Это помогает распределить конкурирующих клиентов по времени, но делает конкретный запуск изменчивым. Для повторяемых unit-тестов закрепите seed или внедрите псевдослучайный источник. В production источники не должны все использовать один фиксированный seed, иначе клиенты сохранят синхронность.

Общий budget отличается от локального максимума попыток. Тысяча запросов, каждый с тремя повторами, может породить до трёх тысяч дополнительных вызовов. Ограничение на долю повторов за окно или на их число у клиента защищает зависимость лучше, чем лимит отдельного запроса. Заранее определите, блокирует ли исчерпание общего бюджета все повторы или только менее важные операции.

### Посчитайте верхнюю границу усиления

При `N` исходных запросах и максимумe `R` повторов худший случай даёт до `N × (R + 1)` попыток, если каждый запрос использует весь лимит. Для тысячи запросов с тремя повторами это до четырёх тысяч вызовов зависимости. Именно поэтому per-request limit не равен общему retry budget. Рассчитайте усиление до включения повторов и сравните с запасом зависимости.

Общий budget может ограничивать долю повторов за интервал, но важно определить, как распределяется право на повтор между callers. Один шумный клиент не должен израсходовать все повторные попытки остальных без явного правила. В учебной функции нет общей памяти или распределённого счётчика; любое такое ограничение потребует отдельного механизма координации и теста гонок.

### Разделите retry и redelivery

Retry клиента и повторная доставка брокером — разные источники повторного исполнения. Клиент может послать новый запрос после timeout; брокер может повторно передать уже принятое сообщение после потери ack. У каждого свой лимит и история. Общий эффект может повториться, даже если код бизнес-операции содержит только один явный цикл повторов.

Составьте таблицу владельцев повтора: API client, worker или broker; число попыток; задержка; срок; идентификатор операции; условие окончательной остановки. Если все уровни по отдельности допускают три повтора, максимальное число вызовов может перемножиться. Считайте общий каскад, а не один локальный параметр. Идемпотентность должна покрывать конечную операцию и побочный эффект, а не только отдельный HTTP handler.

Пример этого урока не моделирует повторную доставку. В отчёте обозначьте это как открытый риск и не называйте локальный `retry budget` глобальным лимитом.

### Не повторяйте отменённую работу

Отмена контекста отличается от временной ошибки зависимости. Если вызывающая сторона перестала ждать, новые повторы обычно только тратят ресурс и могут произвести эффект, который никто не ожидает. Проверьте отмену до начала следующего вызова и перед каждым ожиданием backoff. При этом уже отправленная операция могла завершиться; не сообщайте «не выполнено», если результата нет. Сохраните состояние как неизвестное и определите способ сверки.

Повторите матрицу с указанной единицей времени и сохраните полную последовательность попыток, чтобы другой читатель проверил расчёт независимо.

## Практика Easy / Medium / Hard

**Easy — разрешение повторной попытки.** Реализуйте `RetryAction`, отличив постоянную ошибку, временную ошибку и исчерпанный per-request limit.

**Medium — backoff.** Реализуйте `RetryDelay` как min(base×2^attempt, cap) без переполнения; проверьте cap, нулевую базу, большую попытку и неверные диапазоны.

**Hard — совмещенная retry policy.** Реализуйте `RetryDecision`: попытка разрешена, только если ошибка временная, не достигнут предел запроса, остался общий budget и backoff строго помещается в остаток deadline. Проверьте приоритет каждой причины остановки. Чистая функция не резервирует конкурентный бюджет и не исполняет retry.
