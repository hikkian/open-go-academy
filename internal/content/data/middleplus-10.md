# Репликация и lag

## Что ты сделаешь

Ты научишься говорить о задержке репликации точно: чем отличаются lag по времени и по позиции журнала, почему подтверждённый commit на primary не означает видимость на реплике и какой путь чтения безопасен сразу после записи. Три функции урока — `ReadSource`, `ValidReplicaLag`, `ReadAfterWrite` — это политики выбора источника чтения по учебным сигналам; к базе они не подключаются и lag не измеряют.

## Что именно называют lag

В потоковой репликации PostgreSQL primary отправляет журнал упреждающей записи (WAL), standby получает его и применяет. «Lag» могут называть разные вещи: разницу во времени между commit на primary и применением на реплике; разницу позиций журнала — отправлено, получено, применено; оценку из мониторингового запроса, обновляемую раз в N секунд. Эти определения не взаимозаменяемы. Время, вычисленное из часов двух узлов, включает расхождение часов (clock skew); позиция журнала точна, но не переводится в секунды без контекста нагрузки.

```go group=lagkinds mode=run
package main

import "fmt"

func main() {
    const (
        sentLSN    = 1_000_000 // байт журнала, отправленных primary
        appliedLSN = 940_000   // байт, применённых репликой
        bytesPerSec = 20_000   // средняя скорость применения за последнюю минуту
    )
    byteLag := sentLSN - appliedLSN
    fmt.Println("lag по журналу:", byteLag, "байт")
    fmt.Println("оценка по времени:", byteLag/bytesPerSec, "с при текущей скорости")
    fmt.Println("при нулевой записи на primary lag по журналу остаётся", byteLag, "байт до применения")
}
```

Вывод:

```text
lag по журналу: 60000 байт
оценка по времени: 3 с при текущей скорости
при нулевой записи на primary lag по журналу остаётся 60000 байт до применения
```

Оценка в секундах зависит от скорости применения, которая меняется при всплеске записи, медленном диске или долгой транзакции на реплике. Сначала установи, какую метрику измеряет твоя система и как часто она обновляется, — иначе порог «не больше трёх секунд» сравнивает несравнимое.

> **Важно.** Если измеритель недоступен или вернул «неизвестно», это не ноль. Отсутствие данных о lag — повод для безопасного пути, а не для чтения с реплики.

## Как измерять lag в PostgreSQL

На primary представление `pg_stat_replication` показывает для каждой реплики четыре позиции журнала — отправлено, записано, сброшено на диск, применено — и, при включённой обратной связи, оценки задержек по каждому этапу. Разница между позицией primary и применённой позицией реплики — lag по журналу в байтах; оценка задержки в секундах считается из времени прохождения последних записей. На самой реплике доступны последняя применённая позиция и время последней применённой транзакции.

У временной оценки есть известная ловушка: если primary ничего не пишет, время последней применённой транзакции на реплике застывает, и наивная формула «сейчас минус это время» показывает растущий lag при полностью синхронной реплике. Поэтому мониторинг сравнивает позиции, а время использует как дополнение. Запиши для своего стенда, какой запрос даёт метрику, как часто он выполняется и что он показывает при простое primary.

## После commit запись видна не везде

Клиент получил подтверждение commit на primary, тут же читает с реплики и не видит своей записи. Данные не потеряны: запись ещё не применена, или снимок транзакции на реплике открыт раньше. Контракт чтения должен сказать, допустимо ли такое устаревание для этой операции. Экран «ваш заказ создан» — нет; список заказов за месяц в отчёте — да.

```go group=source mode=run
package main

import "fmt"

func readSource(lagSeconds, maxLag int) string {
    if lagSeconds < 0 || maxLag < 0 {
        return "invalid"
    }
    if lagSeconds <= maxLag {
        return "replica"
    }
    return "primary"
}

func main() {
    fmt.Println(readSource(1, 3), readSource(3, 3), readSource(5, 3), readSource(-1, 3))
}
```

Вывод:

```text
replica replica primary invalid
```

Порог включительный — три секунды при бюджете в три секунды ещё укладываются. Сам бюджет берётся из продуктовой семантики операции, а не из «обычно реплика успевает». Отрицательный lag — ошибка измерения или часов, и ответ на него — `invalid`, не `replica`.

> **Типичная ошибка.** «Подождать 100 мс и читать с реплики». Фиксированная пауза не гарантия: при всплеске lag превратится в неограниченное ожидание или в устаревшее чтение.

## Чтение своей записи

Read-your-writes — гарантия, что клиент видит собственные завершённые записи в последующих чтениях. Способы обеспечить: направить чтения этого клиента на primary на время после записи; дождаться, пока реплика применит позицию журнала не ниже позиции commit; передать токен согласованности, если архитектура его поддерживает. Самый простой механизм — primary после записи — дорог нагрузкой на primary и не защищает от переключения на новую primary, которая ожидаемой записи ещё не получила.

```go group=ryw mode=run
package main

import "fmt"

func readAfterWrite(wrote, replicaFresh bool) string {
    if wrote || !replicaFresh {
        return "primary"
    }
    return "replica"
}

func main() {
    fmt.Println(readAfterWrite(true, true), readAfterWrite(true, false), readAfterWrite(false, true), readAfterWrite(false, false))
}
```

Вывод:

```text
primary primary replica primary
```

В этой модели запись всегда ведёт на primary, даже если реплика «свежа» по флагу: флаг — утверждение мониторинга, а не доказательство видимости конкретной записи. Реплика разрешена только для чтения без предшествующей записи и с положительным сигналом свежести. Реальные системы используют позиции журнала и ограждение (fencing); булев флаг — учебное упрощение.

## Ожидание позиции вместо паузы

Если операция требует увидеть свою запись, а читать хочется с реплики, честный механизм — ожидание позиции. После commit клиент запоминает позицию журнала, которую вернул primary; перед чтением спрашивает реплику, применена ли позиция не ниже этой; если да — читает с реплики, если нет — ждёт с ограничением по времени и при истечении срока уходит на primary или возвращает ошибку. Ограничение обязательно: без него всплеск lag превращает чтение в бесконечное ожидание.

Такой протокол дороже булевого флага — две дополнительные операции на чтение, — поэтому применяют его к операциям, где устаревание недопустимо, а остальные чтения отправляют на реплику по бюджету lag. Выбор, какие операции какие, — продуктовый, и он записывается в контракт чтения рядом с порогом.

Есть и дешёвый компромисс между паузой и ожиданием позиции: после записи клиент получает короткий «маркер недавней записи» в сессии — например, на несколько секунд — и все чтения с маркером идут на primary без проверки позиций. Это та же привязка к primary, но ограниченная по времени и по клиенту, поэтому нагрузка на primary растёт только на долю недавно писавших. Срок маркера выбирают по наблюдаемому распределению lag с запасом и пересматривают, когда распределение меняется; ошибка здесь не катастрофична — после истечения маркера остаётся бюджет lag из задания 1.

## Здоровье реплики и режим подтверждения

Низкий lag в текущую секунду не делает реплику безопасной для любого класса чтения: нужны доступность соединения, состояние потока, ёмкость и возможность обслужить запрос. Синхронная репликация задерживает commit до подтверждения реплики и меняет доступность при её отказе; асинхронная допускает окно потери уже подтверждённых изменений при некоторых отказах. Конкретная гарантия следует из режима подтверждения и политики переключения, а не из слова «репликация».

Реплика — не резервная копия: удаление и повреждение данных реплицируются так же, как полезные изменения. Проверка восстановления и независимая копия решают другие задачи. План переключения (failover) отвечает: кто принимает решение, как выбирается новая primary, какие записи могли не попасть на неё.

> **Зачем.** Обещание «нулевой потери данных» имеет смысл только с названным режимом подтверждения, проверенной конфигурацией и записанным поведением при переключении.

Отдельно договорись о словах в отчётах и алертах: «lag 3 с» без указания способа измерения не сравним с порогом, а «реплика свежа» без интервала обновления метрики — не наблюдение, а мнение. Правило простое: каждая цифра lag в документе сопровождается видом метрики (время или позиция), источником (запрос или экспортер) и частотой обновления; каждое решение о чтении — названной операцией и её бюджетом. Тогда разбор инцидента «пользователь не увидел свой заказ» занимает минуты: смотрят, какой путь выбрала операция, какой lag показывала метрика и сколько ждал клиент до запасного пути.

## Типичные ошибки

- Сравнивать lag по времени с порогом, заданным для позиции журнала, или наоборот.
- Трактовать «неизвестно» как ноль и читать с реплики.
- Фиксированная пауза вместо ожидания позиции или маршрута на primary.
- Флаг свежести как доказательство видимости конкретной записи.
- Реплика как резервная копия.
- Обещание read-your-writes без плана на переключение primary.

## Самостоятельная лаборатория

На одноразовом стенде с primary и одной репликой (контейнеры, только локально) запиши строку на primary и сразу читай её с реплики в цикле с ограничением по времени, фиксируя момент появления. Затем приостанови применение журнала на реплике, повтори запись и чтение с тем же ограничением — чтение должно завершиться отказом по сроку, а не ожидать бесконечно. Сними метрики lag обоими способами — по времени и по позиции — до, во время и после паузы, запиши их рядом. Отчёт: какой метрике ты доверяешь для порога, что делает клиент при превышении, что произошло при неизвестном lag. Если стенда нет, так и запиши: поведение реплики не проверялось. Удали стенд.

## Если что-то пошло не так

- `replica` для `lag = 3, maxLag = 3` — верно; `primary` → порог должен быть включительным.
- `primary` для отрицательного lag → отрицательные значения — `invalid`, проверка стоит первой.
- `replica` после записи при свежей реплике → в модели запись всегда ведёт на primary; условие `wrote ||`.
- `true` в задании 2 при отрицательном пороге → оба числа должны быть неотрицательны.
- `import … is not allowed` → импорты запрещены: сравнения и флаги.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Входы — учебные сигналы, к базе функции не обращаются.

### Задание 1 · Easy: выбери replica по lag budget

**Цель.** Вернуть `replica`, если известный lag неотрицателен и не выше `maxLag`; при большем — `primary`; отрицательные данные → `invalid`.

**Ожидаемый вывод** — для `(lagSeconds=1, maxLag=3)`:

```text
"replica"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func ReadSource(lagSeconds, maxLag int) string`. Импорты запрещены.
2. `lagSeconds < 0 || maxLag < 0` → `"invalid"`.
3. `lagSeconds <= maxLag` → `"replica"`, иначе `"primary"`.
4. «Запустить», «Проверить» — закрытые примеры: `(5, 3)` → `primary`, `(-1, 3)` → `invalid`.

**Как проверить себя.** Порог включительный; порог — продуктовое решение об операции, функция лишь применяет его к числу.

**Если не принято.**
- `primary` для `(3, 3)` → сравнение строгое.
- `replica` для `(-1, 3)` → проверка знака отсутствует или стоит после сравнения.

> **Подсказка.** Сформулируй словами, что означает `maxLag` для этой операции, прежде чем писать условие.

### Задание 2 · Medium: проверь допускаемый replica lag

**Цель.** Вернуть `true` только для неотрицательных lag и порога, когда lag укладывается в порог включительно.

**Ожидаемый вывод** — для `(0, 5)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ValidReplicaLag(lagSeconds, maxLag int) bool`. Импорты запрещены.
2. Верни `lagSeconds >= 0 && maxLag >= 0 && lagSeconds <= maxLag`.
3. «Запустить», «Проверить» — закрытые примеры: `(6, 5)` → `false`, `(1, -1)` → `false`.

**Как проверить себя.** Нулевой lag допустим; отрицательный порог — ошибка; секунды lag не равны согласованности всех запросов.

**Если не принято.**
- `true` для `(1, -1)` → порог не проверен на знак.
- `false` для `(5, 5)` → сравнение строгое.

> **Подсказка.** Три условия через `&&`; это предусловие для задания 1.

### Задание 3 · Hard: сохрани read-your-writes

**Цель.** После записи читать с primary; при несвежей реплике — тоже primary; реплика — только без предшествующей записи и при `replicaFresh = true`.

**Ожидаемый вывод** — для `(wrote=true, replicaFresh=false)` и `(wrote=false, replicaFresh=true)`:

```text
"primary"
"replica"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func ReadAfterWrite(wrote, replicaFresh bool) string`. Импорты запрещены.
2. `wrote || !replicaFresh` → `"primary"`, иначе `"replica"`.
3. «Запустить», «Проверить» — закрытые примеры: запись при свежей реплике → `primary`; нет записи, реплика не свежа → `primary`.

**Как проверить себя.** Из четырёх комбинаций флагов только одна даёт `replica`; флаг свежести — входной сигнал, а не подтверждение от базы.

**Если не принято.**
- `replica` для `(true, true)` → условие учитывает только свежесть; запись должна вести на primary.
- `replica` для `(false, false)` → несвежая реплика не разрешена.

> **Подсказка.** Маршрут на primary — один из механизмов read-your-writes; позиции журнала и токены — другие, и функция о них не знает.

## Проверь себя

- Что видит клиент сразу после commit при чтении с реплики?
- Что делать, когда lag неизвестен?
- Почему фиксированная пауза перед чтением не гарантия?
- Почему реплика не резервная копия?

## Итог

- Lag бывает по времени и по позиции журнала; порог сравнивают только с метрикой того же вида, «неизвестно» — не ноль.
- Подтверждённый commit не означает видимость на реплике; допустимость устаревания задаёт операция, а не инфраструктура.
- Read-your-writes обеспечивают маршрутом на primary, ожиданием позиции или токеном; реплика — не резервная копия, гарантии следуют из режима подтверждения и плана переключения.
