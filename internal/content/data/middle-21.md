# Redis и кешируемая проекция

## Зачем эта тема нужна

В backend-сервисе тема «Redis и кешируемая проекция» появляется там, где одно решение меняет стоимость, корректность или возможность восстановления после сбоя. Новичку полезно начать не с названия технологии, а с вопроса: какие данные уже известны, кто ими владеет, что должно быть истинно после операции и что произойдёт, если процесс остановится в самый неудобный момент. Middle-инженер должен уметь назвать эти условия до того, как выберет библиотеку.

В этой главе мы строим небольшую модель и отделяем три вещи: правило приложения, гарантию конкретной зависимости и доказательство теста. Это различие помогает не делать слишком сильный вывод из маленького примера. Функция в упражнении может проверить границу чисел, но она не соединяется с PostgreSQL или Redis и поэтому не может подтвердить реальное поведение транзакции, доставки или кэша.

## Сначала определим границу

Кеш (cache) хранит копию результата, который можно получить из источника истины. Time to live (TTL, срок жизни) задаёт, когда запись считается устаревшей; это не гарантия точного момента удаления ключа. TTL должен отражать допустимую свежесть продукта. Нулевой срок в этой модели означает «не кешировать», а предел в час ограничивает случайно бесконечное хранение. Слишком длинный TTL увеличивает окно устаревания; слишком короткий повышает нагрузку на базу.

Medium вводит stale-while-error решение: свежий результат предпочтителен; stale (устаревший) допускается только если политика явно разрешает его; иначе при здоровом backend надо загрузить источник, а при его отказе вернуть unavailable. Hard различает staleData от самого разрешения: нельзя обслужить устаревшую запись, если записи уже нет. Для профиля пользователя устаревший ответ может быть приемлем, для прав доступа или остатка денег — обычно нет. Это бизнес-контракт, который нельзя выводить из технической доступности Redis.

Инвалидация не решается TTL полностью. Запись в базу и публикация события могут разойтись; локальный процесс может держать старое значение; Redis может вытеснить запись или стать недоступным. Реальная проверка включает прогрев/холодный старт, истечение TTL, отказ кеша, конкурентное обновление и наблюдение за stale rate. Учебная policy функция помогает зафиксировать выбор, но не знает времени записи, фактического возраста и конфигурации cache.

## Go-модель: детерминированная граница

Ниже три небольшие Go-функции показывают растущие контракты темы «Redis и кешируемая проекция». Это локальные модели, не интеграционный тест. Это учебная модель с явно ограниченным входом; она не заменяет EXPLAIN, SQL transaction, брокер, Redis или тест реального сервиса.

```go group=middle-21-easy mode=run
package main
import "fmt"

func CacheTTLEasy(seconds int64) int64 {
	if seconds <= 0 { return 0 }; if seconds > 3600 { return 3600 }; return seconds
}

func main() { fmt.Println(CacheTTLEasy(30)) }
```

Ожидаемый вывод зависит от выбранных входов и читается по одной строке на вызов. Сравните каждый результат с правилом функции. Для числовых лимитов сохраняйте целочисленные единицы; например, секунды и миллисекунды нельзя смешивать без явного преобразования.

## Маленький тест без внешней системы

Сравните средний контракт для темы «Redis и кешируемая проекция» с предыдущим: здесь добавлена отдельная ветвь policy, но scope всё ещё ограничен локальными входами. Тест на чистую функцию подтверждает только модель.

```go group=middle-21-medium mode=run
package main
import "fmt"

func CacheReadPolicyMedium(fresh, staleAllowed, backendAvailable bool) string {
	if fresh { return "serve_fresh" }; if staleAllowed { return "serve_stale" }; if backendAvailable { return "load" }; return "unavailable"
}

func main() { fmt.Println(CacheReadPolicyMedium(true, false, false)) }
```

Второй пример меняет вход так, чтобы пересечь границу контракта. Прочитайте его вместе с первым: какой именно параметр изменился и почему результат должен измениться? Эти два запуска проверяют заданное правило, но не обращаются к внешней зависимости и не доказывают её конфигурацию.

## Ошибка, повтор и восстановление

При ошибке Redis выбирай явный stale/fallback policy. Не делай неограниченный fan-out в базу при cache miss; ограничивай нагрузку и измеряй fallback.

## Пример обработки ошибок в Go

Код приложения должен переводить внутренний результат в устойчивые категории, не возвращая клиенту SQL-текст или stack trace. На границе HTTP handler назначает статус и безопасный ответ; service решает доменное правило; repository знает детали хранения. Это деление позволяет тестировать правило отдельно, а запрос к настоящей базе — отдельным интеграционным сценарием.

```go group=middle-21-hard mode=run
package main
import "fmt"

func CacheFailurePolicyHard(fresh, staleAllowed, backendAvailable, staleData bool) string {
	if fresh { return "serve_fresh" }; if staleAllowed && staleData { return "serve_stale" }; if backendAvailable { return "load" }; return "unavailable"
}

func main() { fmt.Println(CacheFailurePolicyHard(true, false, false, false)) }
```

Порядок ветвей hard-контракта для «Redis и кешируемая проекция» задаёт приоритет при пересекающихся признаках. Зафиксируйте этот приоритет до реализации, а неожиданный ввод обрабатывайте отдельно от успешного результата. Тест-векторы проверяют только выбранные категории; внешний протокол требует отдельного сценария.

## Типичные ошибки и диагностика

- Подменять наблюдаемое поведение обещанием: формулируйте, что именно проверяет тест.
- Игнорировать неизвестный исход после timeout: выясните, могла ли операция уже завершиться.
- Повторять бесконечно: добавьте максимальное число попыток, backoff и сигнал о постоянной ошибке.
- Считать кеш долговечным источником истины: определите пересчёт, срок жизни и fallback.
- Слишком рано внедрять сложную инфраструктуру: сначала измерьте проблему и обозначьте требуемую гарантию.
- Возвращать наружу внутренний текст ошибки: используйте стабильную безопасную категорию.

При отладке воспроизведите отказ одним контролируемым переключателем: зависимость возвращает временную ошибку, ответ задержан или запись уже зафиксирована. Сохраняйте минимальный fixture и проверяйте, какой переход произошёл. Не используйте случайные `time.Sleep` в тесте синхронизации; управляемые каналы или часы дают предсказуемый сценарий. Нагрузочный тест также должен иметь фиксированный объём и явно объявленный предел параллелизма.

## Практика и самопроверка

Easy ограничивает TTL; Medium выбирает между fresh, stale и загрузкой; Hard требует фактической stale записи и допускает безопасный отказ. Сопоставь stale-разрешение для разных доменов. В integration test зафиксируй время и проверь истечение, отказ cache, fallback на источник и отсутствие устаревания для критичных данных.

Теперь вы умеете описать ограниченную модель темы «Redis и кешируемая проекция», назвать её границы и не путать локальное правило с гарантией внешней системы. Повторите prerequisites `middle-13`: они дают базу для этого решения. Для следующего шага перенесите инвариант в маленький сервисный сценарий, добавьте измеряемую диагностику и выполните отказной тест на фактическом движке либо отдельной локальной зависимости. Успешный учебный пример — начало инженерного доказательства, а не его финал.

### Термины

- **cache (кеш)** — Быстрое временное представление данных.

- **TTL (срок жизни)** — Время до автоматического истечения ключа.

- **cache miss (промах кеша)** — Отсутствие пригодного значения в кеше.


## Лабораторный сценарий: от гипотезы до восстановления

Начните с небольшой гипотезы, которую можно опровергнуть. Для главы «Redis и кешируемая проекция» запишите исходное состояние и ожидаемый результат словами, прежде чем писать код. Выберите один параметр, меняйте только его и сохраняйте остальные значения неизменными. Это важно: если одновременно менять лимит, тайм-аут и число worker, успешный результат не объяснит, какой фактор повлиял на поведение. Укажите единицы каждого числа, порядок операций и точку, после которой действие считается подтверждённым.

Соберите таблицу минимум из четырёх строк: обычный успешный случай, нижняя или верхняя граница, временный отказ зависимости и повтор после неопределённого результата. Для каждой строки запишите вход, ожидаемую категорию, изменение состояния и ресурс, который нужно освободить. Не используйте текст исключения как продуктовый контракт. Если ошибка может содержать SQL, DSN, токен или данные клиента, наружу возвращайте безопасную категорию, а внутренний лог очищайте от секретов.

Проведите эксперимент в три прохода. В первом пройдите чистый успешный путь и проверьте, что система выполнила ожидаемое число операций. Во втором принудительно верните одну временную ошибку и проследите, появляется ли ограниченный повтор с задержкой. В третьем остановите или отмените работу после выбранной границы и проверьте, можно ли продолжить без потери подтверждённых данных и без повторного побочного эффекта. Для управляемого теста используйте fake, канал или специально подготовленный локальный fixture; не полагайтесь на случайную сетевую задержку.

После каждого прохода разделяйте наблюдения и выводы. Строка stdout показывает только напечатанный результат. Успешный unit test показывает только контракт функции и фикстуру, которую он запускал. Тест реальной интеграции должен проверить фактический движок и конфигурацию; race detector способен обнаружить часть data race в исполненном сценарии, но не доказывает отсутствие всех логических гонок. Для воспроизводимого отчёта сохраните версию Go, параметры запуска, исходные fixture, число повторов, длительность, ошибки и границы утверждения.

### Разбор конкретной гипотезы

Для этой темы сформулируйте проверяемое правило так: «если вход меняется с обычного на граничный, решение должно перейти в заранее названную категорию; если зависимость временно недоступна, состояние остаётся восстанавливаемым». Разложите операцию на подготовку, вызов зависимости, фиксацию результата и уведомление вызывающей стороны. Для каждого шага отметьте, что уже произошло при остановке процесса. Если изменение подтверждено до отправки ответа, повтор клиента должен быть распознан как повтор той же логической операции. Если подтверждения ещё не было, восстановление должно повторить работу ограниченное число раз и оставить диагностируемый след при исчерпании лимита.

Практический trade-off следует объяснить через стоимость и риск, а не через лозунг «быстрее» или «надёжнее». Ограничение ресурсов может увеличить очередь и latency, но уменьшить нагрузку на базу. Индекс может сократить чтение нужных строк, но увеличить запись и размер хранилища. Кеш может снизить повторные чтения, но добавить устаревание и операционную зависимость. Durable queue повышает восстановимость, но требует контроля backlog, подтверждений и dead-letter пути. Назовите условия, при которых выбор надо пересмотреть: профиль нагрузки изменился, ключевая зависимость стала источником ошибок или измеренная свежесть уже не соответствует продуктовой потребности.

В завершение напишите короткий протокол проверки: предпосылки, команда, fixture, ожидаемый результат, фактический результат и ограничение. Если проверяется функция из упражнения, перечислите только её входы и выходы. Если проверяется сервис, добавьте integration scenario с реальной базой или локальным брокером, очисткой созданных тестовых данных и подтверждением восстановления. Такой протокол позволяет другому разработчику повторить опыт и увидеть, какие новые наблюдения опровергнут ваше решение.


Перед тем как принять изменение, перечитайте исходное требование и проверьте каждый переход, а не только итоговый ответ. Запишите один отказ, который тест ещё не покрывает, и объясните, какой отдельный integration test способен его воспроизвести. Если результат зависит от нагрузки, сравните одинаковый фиксированный набор данных и сохраните параметры запуска. Не расширяйте утверждение за пределы наблюдений: числовой helper не показывает план PostgreSQL, а успешный локальный вывод не означает, что очередь переживёт перезапуск.


## Политика свежести и отказ cache

До выбора TTL договоритесь о freshness budget (допустимом возрасте данных) отдельно для каждой категории. Справочная карточка может пережить минуту устаревания; баланс или разрешение доступа может требовать чтения источника истины. Одно значение TTL для всех ключей обычно скрывает разницу продукта. Если запись cache отсутствует или вытеснена, поведение должно оставаться корректным без кеша, пусть и медленнее.

При недоступности Redis не повторяйте запрос бесконечно и не превращайте cache в единственный источник. Для некритичного чтения можно обратиться к базе с ограничением параллелизма; иначе отказ кеша создаст лавину запросов. Для stale response явно покажите владельцу продукта, какие поля допустимо отдавать старыми. Счётчики hit, miss, stale served, backend fallback и ошибки дают наблюдаемое основание менять политику. TTL и hit ratio сами по себе не доказывают свежесть.

Интеграционный сценарий использует управляемое время: положите значение, передвиньте fake clock за TTL, отключите cache, затем проверьте fallback. Повторите с политикой stale=true и без сохранённых данных. Проверьте, что данные с требованием свежести не возвращаются по stale ветке. Учебные bool не содержат timestamp, поэтому hard функция может только показать приоритет policy, а не вычислить возраст записи или подтвердить актуальность базы.


Ключ кеша включает только параметры, которые реально меняют результат, и имеет версионированную схему при несовместимом изменении. Иначе два tenant могут получить одно значение или старый формат останется после релиза. Добавьте предел размера и политику вытеснения, учитывая, что eviction допустима лишь если источник может восстановить значение. Включите защиту от stampede: несколько одновременных cache miss не должны без ограничений породить одинаковые дорогие запросы. Эти детали стоит закрепить в ADR и наблюдать после запуска.


Деплой схемы ключа должен учитывать старые экземпляры приложения, которые ещё пишут прежний формат. Используйте namespace версии, постепенную миграцию или очистку с безопасным fallback. Не вставляйте секреты пользователя в ключ, который может попасть в debug output. Измеряйте размер значения и отказы сериализации отдельно от cache miss.
