# Redis и кешируемая проекция

## Что ты сделаешь

Ты напишешь три функции-политики для кеша: ограничение срока жизни записи, выбор ответа при промахе кеша и решение при отказе кеша с учётом устаревших данных. Функции работают с переданными числами и флагами, поэтому проверяют правило, но не подключаются к Redis и не доказывают его состояние.

## Кеш — копия, а не источник истины

Кеш хранит копию результата, который можно получить заново из источника истины: базы, внешнего сервиса или расчёта. Поэтому кеш всегда подчинён источнику. Если кеш потерян, приложение должно остаться корректным и просто стать медленнее.

Данные подходят для кеша, если их можно пересчитать и если короткая устарелость допустима продуктом. Справочная карточка товара может пережить минуту без обновления. Баланс счёта или право доступа обычно нельзя отдавать из кеша без явного решения, потому что устаревшее значение может уже быть неверным в момент ответа.

> **Важно.** Наличие Redis не делает данные надёжнее. Redis — быстрое временное хранилище, и его недоступность — штатная ситуация, которую нужно описать заранее.

## Срок жизни записи

Time to live (TTL, срок жизни) задаёт, после какого времени запись считается устаревшей. Это не гарантия точного момента удаления ключа: Redis удаляет просроченные ключи лениво или фоново, поэтому ключ может существовать чуть дольше срока. Для приложения важен срок свежести, а не физическое удаление.

Учебная функция ограничивает TTL двумя правилами. Нулевой или отрицательный срок означает «не кешировать». Очень длинный срок ограничивается одним часом, чтобы случайно бесконечная запись не жила вечно. Пример показывает, как такой предел работает на нескольких значениях:

```go
package main

import "fmt"

func main() {
    for _, s := range []int64{30, 3600, 9000} {
        ttl := s
        if ttl > 3600 {
            ttl = 3600
        }
        fmt.Println(ttl)
    }
}
```

Вывод: `30`, `3600`, `3600`. Слишком длинный TTL расширяет окно устаревания, а слишком короткий увеличивает нагрузку на источник. Значение выбирают по требованию свежести, а не по удобству.

## Что делать при промахе кеша

Промах кеша (cache miss) — отсутствие пригодной записи. Его обработка определяет, выдержит ли система нагрузку. Есть три основных ответа: отдать свежее значение из кеша, отдать устаревшее значение, если продукт это разрешает, или загрузить источник истины. Если ни один вариант не возможен, ответ — недоступность.

Порядок проверки важен. Свежее значение выигрывает всегда. Устаревшее допускается только при явном разрешении политики. Загрузка из источника выполняется, если он доступен. Иначе приходит ответ «недоступно». Пример показывает такой выбор на трёх входах:

```go
package main

import "fmt"

func main() {
    fresh, staleAllowed, backendAvailable := false, true, false
    switch {
    case fresh:
        fmt.Println("serve_fresh")
    case staleAllowed:
        fmt.Println("serve_stale")
    case backendAvailable:
        fmt.Println("load")
    default:
        fmt.Println("unavailable")
    }
}
```

Вывод: `serve_stale`. Устаревшее значение отдано, потому что свежего нет, а политика его разрешает. Тот же порядок веток без разрешения дал бы `load` или `unavailable`.

## Инвалидация не решается TTL

TTL не заменяет инвалидацию. Запись в базу и публикация события могут разойтись: база уже обновлена, а кеш ещё хранит старое значение до истечения срока. Локальный процесс может держать копию в собственной памяти, а Redis может вытеснить запись по памяти. Поэтому TTL ограничивает ущерб от устаревания, но не гарантирует отсутствие устаревания.

Практические приёмы: удалять ключ сразу после успешной записи, учитывать версию записи при чтении и наблюдать долю устаревших ответов. Удаление ключа до записи в базу опасно: между удалением и записью другой читатель успеет заново положить старое значение.

## Лавина при промахе

Если тысяча запросов одновременно промахиваются по одному ключу, все они пойдут в базу. Это называют stampede или лавиной. Защита — ограничение параллелизма загрузки для одного ключа: один запрос загружает значение, остальные ждут его результата или получают устаревшее, если политика это позволяет.

Ключ кеша должен включать только параметры, которые меняют результат, и иметь версию схемы. Иначе два tenant получат одно значение, а старый формат переживёт релиз. Размер значения и число ключей тоже нужно ограничивать.

> **Типичная ошибка.** Ставить один TTL на все ключи. Справочные данные и права доступа требуют разной свежести, и единое значение почти всегда скрывает разницу продукта.

## Модель и механизм

Для кеша полезно отделять три вопроса. Насколько запись свежа? Разрешено ли отдать её, если она устарела? Что можно сделать, если источник недоступен? Ответы записываются как политика до написания кода, а не выводятся из текущей доступности Redis.

Учебные функции не знают времени записи и не видят реального возраста значения. Поэтому они проверяют только приоритет веток. Возраст и актуальность проверяются в интеграционном сценарии с управляемыми часами.

## Типичные ошибки и диагностика

- Считать кеш источником истины: при потере ключа данные не должны пропасть.
- Не различать свежесть по категориям: справочники и права доступа живут по разным правилам.
- Отдавать устаревшее без разрешения: политика должна назвать поля, которые можно показывать старыми.
- Повторять чтение источника бесконечно при отказе кеша: нужен лимит параллелизма.

При отладке воспроизводи отказ одним переключателем: ключ отсутствует, источник отвечает ошибкой или запись уже обновлена. Не используй случайные задержки; управляемые часы и явные состояния дают повторяемый сценарий.

## Ключ кеша и версия схемы

Ключ кеша — это контракт. Он должен включать всё, от чего зависит результат: идентификатор арендатора, идентификатор объекта и версию схемы представления. Если убрать арендатора, два клиента получат чужие данные под одним ключом. Если не менять версию при изменении формата, после релиза старые записи продолжат отдаваться в новом коде.

Пример показывает ключ с версией и арендатором. Версия стоит первой, поэтому миграция схемы просто использует новое пространство ключей:

```go
package main

import "fmt"

func cacheKey(tenant string, id int, version int) string {
    return fmt.Sprintf("v%d:tenant:%s:item:%d", version, tenant, id)
}

func main() {
    fmt.Println(cacheKey("acme", 42, 2))
}
```

Вывод: `v2:tenant:acme:item:42`. Старые записи с префиксом `v1` остаются в Redis до истечения TTL и не мешают новой версии. Миграция не требует очистки всего кеша.

Не вставляй в ключ личные данные: ключ может попасть в журнал отладки или в метрики. Для длинных составных частей используй хеш, а не исходные значения.

## Наблюдаемость кеша

Чтобы менять политику, нужны числа. Минимальный набор: доля попаданий (hit), промахи (miss), ответы устаревшими данными (stale served), обращения к источнику после отказа кеша (backend fallback) и ошибки сериализации. Долю попаданий одну не стоит считать признаком свежести: высокая доля может означать, что устаревшие данные отдаются слишком часто.

Размер значения и ошибки сериализации измеряй отдельно от промахов. Крупное значение может вытеснять соседние записи, а сбой декодирования выглядит как промах, если его не учитывать. Записывай версию схемы вместе с метриками, иначе после миграции графики смешают два формата.

## Сценарий с управляемыми часами

Интеграционный сценарий должен управлять временем, а не ждать его. Положи значение с TTL, переведи фальшивые часы за срок, отключи кеш и проверь, что ответ пришёл из источника. Затем повтори с политикой, которая разрешает устаревшие данные, и без сохранённой записи. Ответ с требованием свежести не должен уходить в ветку устаревших данных.

Учебные функции этой главы получают флаги, а не часы, поэтому они не вычисляют возраст. Возраст записи относится к интеграционной проверке, и результат такой проверки нельзя переносить на другую конфигурацию без повтора.

## Воспроизводимая лабораторная: TTL и чтение Redis

**Предварительные условия:** локальный Docker или совместимый Podman CLI и свободный loopback-порт `16379`. Отдельный Redis CLI на компьютере не нужен: команды выполняются внутри контейнера. Используй только имя контейнера `oga-middle21-redis`.

```sh
docker run --rm -d --platform linux/amd64 --name oga-middle21-redis -p 127.0.0.1:16379:6379 docker.io/library/redis@sha256:cb1c6f8dc0251eb2b079d774f1dbf51536b216b5568545559b20cd949235dd28
docker exec oga-middle21-redis redis-cli SET lesson:21:value fresh EX 2
docker exec oga-middle21-redis redis-cli TTL lesson:21:value
docker exec oga-middle21-redis redis-cli GET lesson:21:value
sleep 3
docker exec oga-middle21-redis redis-cli GET lesson:21:value
```

**Ожидайте:** `SET` отвечает `OK`, первый `TTL` — положительным числом не больше 2, первый `GET` — `fresh`, последний `GET` после ожидания ничего не печатает. TTL может быть меньше 2 из-за времени выполнения, и он не обещает точный момент физического удаления. Лаборатория проверяет команды конкретного Redis, но не политику приложения.

**Очистка:** `docker stop oga-middle21-redis`. Контейнер запущен с `--rm`, поэтому временные данные удалятся вместе с ним.

## Итог

- Кеш — копия источника истины: его потеря не должна ломать корректность, только скорость.
- TTL задаёт срок свежести, а не точный момент удаления; предел срока защищает от бесконечного хранения.
- Ответ при промахе выбирается политикой: свежее, устаревшее по разрешению, загрузка или недоступность.
