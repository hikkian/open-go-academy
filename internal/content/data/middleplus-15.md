# 15. Глубина очереди, возраст и задержка

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-14`
**Цель:** Queue depth (глубина очереди) показывает число ожидающих элементов, но одинаковое число может быть нормальным для короткой работы и катастрофическим для долгой. Важны время самого старого элемента, скорость входа и выхода, размер сообщений и ограничение памяти. Метрика очереди должна быть связана с ресурсным бюджетом и временем ожидания потребителя.

## Термины и перевод

- **Очередь и queue depth** — Queue depth (глубина очереди) показывает число ожидающих элементов, но одинаковое число может быть нормальным для короткой работы и катастрофическим для долгой. Важны время самого старого элемента, скорость входа и выхода, размер сообщений и ограничение памяти. Метрика очереди должна быть связана с ресурсным бюджетом и временем ожидания потребителя.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Глубина очереди — моментальный счёт ожидающих элементов; сама по себе она не говорит, как долго они ждут. Пять коротких задач и пять задач, заблокированных на внешней зависимости, создают разный опыт. Возраст старейшего элемента добавляет временной контекст, а входящая и завершаемая скорости помогают понять, растёт ли очередь.

До чтения метрики определите точку учёта: включаются ли задачи, уже взятые worker (обработчиком), и когда удаляется завершённая задача. Выберите единицы и поясните, относится ли размер очереди к памяти, числу элементов или обоим ограничениям. В примерах урока вычисляется только условное состояние по переданным значениям; они не подключены к реальной очереди и не собирают timestamps (временные отметки).

Полезный сигнал должен приводить к проверяемому вопросу: растёт ли возраст, падает ли скорость завершения, исчерпан ли лимит? Одна средняя глубина может скрыть краткий пик или давно зависший элемент, поэтому название метрики без определения границы и окна недостаточно.

## Три запускаемых примера

### Пример 1: обычный путь

```go
package main

import "fmt"

func QueueBand(depth int, capacity int) string {
	if depth < 0 || capacity <= 0 { return "invalid" }; if depth == 0 { return "empty" }; if depth >= capacity { return "full" }; return "queued"
}

func main() { fmt.Println(QueueBand(2, 4)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 2: решение с несколькими сигналами

```go
package main

import "fmt"

func QueuePressure(depth int, capacity int, oldestSeconds int, maxAgeSeconds int) string {
	if depth < 0 || capacity <= 0 || oldestSeconds < 0 || maxAgeSeconds <= 0 { return "invalid" }; if depth == 0 { return "empty" }; if depth >= capacity { return "full" }; if oldestSeconds >= maxAgeSeconds { return "stale" }; return "normal"
}

func main() { fmt.Println(QueuePressure(2, 4, 60, 60)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 3: проверка ограниченного инварианта


## Практическая процедура

Нарисуйте жизненный цикл одного элемента: поступил, принят, начал выполняться, завершился либо был отклонён. Выберите, какие состояния входят в глубину, а какие — в возраст ожидания. Для каждого счётчика запишите единицу, источник, окно и что происходит при отсутствии данных.

Постройте небольшую таблицу наблюдений для нескольких последовательных моментов: глубина, число новых задач, число завершённых и возраст старейшей. Сопоставьте изменения. Рост глубины вместе с растущим возрастом означает длительное накопление; стабильная глубина при равном входе и выходе не обязательно означает проблему. Не выводите причину только из совпадения метрик.

Если проверяете helper, используйте обычное значение и точные границы его контракта. Результат не подтверждает корректность инструментирования, фактическое использование памяти или задержку реального потребителя. Для этого потребовался бы отдельный тест очереди с измеряемым временем и известной работой.

## Разбор сценария: Глубина очереди, возраст и задержка

Возьмите сценарий с конечной последовательностью задач и явно задайте момент каждого поступления и завершения. На каждом шаге вычислите ожидающую глубину по выбранному определению и возраст самой старой ожидающей задачи. Проверьте, что задача, уже взятая исполнителем, не попадает в очередь, если именно таков ваш контракт.

Сравните две последовательности с одинаковой глубиной, но разным временем ожидания. Это показывает, почему размер очереди не заменяет возраст. Затем рассмотрите рост входа при неизменном выходе: объясните, какой сигнал первым покажет накопление и какой ресурс может быть ограничен. Не утверждайте, что число элементов равно памяти без размера каждого элемента.

В карточке отчёта сохраните определения метрик и таблицу шагов. Если helper классифицирует состояние, приложите вход и выход и назовите его границу. Фактические задержки, распределение размеров и точность телеметрии здесь не измеряются; следующим тестом может быть контролируемая очередь с фиксированными задержками исполнителя.

## Лаборатория: связать число, возраст и скорость потока

### Численный сценарий

Рассмотрите очередь из шести ожидающих сообщений. Если за секунду приходит четыре, а завершается два, при отсутствии других изменений глубина через секунду станет восемь. При одинаковой скорости выхода такой прирост будет повторяться. Но глубина шесть сама по себе ничего не говорит о сроке ожидания: при двух завершениях в секунду ожидание может быть коротким для быстрых сообщений и длинным для тяжёлых. Время старейшего элемента связывает текущий снимок с длительностью ожидания.

Сравните два набора с глубиной шесть. В первом все элементы поступили за последнюю секунду; во втором старейший ждёт уже минуту. Одинаковая метрика depth (глубины) маскирует принципиально различный риск. Если очередь содержит сообщения переменного размера, одинаковое число элементов также не означает одинаковое потребление памяти. Для оценки памяти нужны байты или ограничение размера, а не догадка по количеству.

### План ручного наблюдения

1. Определите, что именно учитывается: только ожидающие элементы или также работа, взятая обработчиком. Запишите событие добавления и удаления.
2. Для каждого шага фиксируйте время, число новых задач, число завершённых, глубину после изменений и возраст старейшей ожидающей задачи.
3. На одном шаге остановите завершение, не прекращая вход. Предскажите, как изменятся глубина и возраст. Затем остановите вход и проверьте, сокращается ли очередь.
4. Повторите с большим временем обработки, но тем же числом элементов. Отделите влияние ожидания от влияния размера сообщений.
5. Укажите, что должны показать метрики и при каких условиях результат стал бы тревожным. Порог нельзя выдумать без цели и допустимого окна.

### Интерпретация сигналов

Рост глубины вместе с ростом возраста говорит, что работа накапливается и стареет. Если глубина стабильна, но возраст увеличивается, проверьте, не завис ли один элемент при одновременном поступлении и завершении других. Если глубина падает, но ошибки растут, завершённые с ошибкой задачи могут создавать ложное ощущение восстановления. Считайте успехом только то завершение, которое соответствует заранее заданному критерию.

Среднее по окну сглаживает короткий всплеск. Максимум может преувеличить единичное событие; процентиль зависит от выборки и точного определения наблюдения. Поэтому отчёт должен включать длительность окна, число измерений, единицы и правило пустого окна. При отсутствующей телеметрии не подставляйте ноль: нулевая глубина и неизвестная глубина — разные состояния.

Публичные и закрытые helper-векторы проверяют лишь классификацию поданных чисел. Они не записывают время, не отслеживают память и не измеряют точность метрики. Для проверки сделайте отдельный тест очереди с управляемыми часами или фиксированной последовательностью временных отметок. Вопросы к себе: какая задача считается старейшей, когда возраст сбрасывается, учитывается ли занятый worker, и какую альтернативную причину может объяснить тот же график?

### От времени ожидания к решению

Ожидаемое ожидание иногда приближают как размер очереди, делённый на скорость обработки. Если впереди восемь элементов, а обработчик завершает четыре элемента в секунду, грубая оценка составляет две секунды. Это работает только при однородных задачах, постоянной скорости и известном числе исполнителей. При разных размерах очереди нужен прогноз объёма работы, а при нескольких обработчиках важно определить, какая часть уже выполняется.

Если возраст старейшего элемента уже превышает допустимый срок, очередь может быть глубокой по важной причине или просто содержать просроченную работу. Спросите, имеет ли смысл выполнять задачу после срока. Иногда безопаснее отменить или отправить её на отдельный разбор; иногда завершение всё ещё необходимо для сохранения согласованности. Не удаляйте старую работу автоматически только потому, что она старая.

Практически полезно связывать предупреждения с действием. Например, высокий возраст может вызвать ограничение новых низкоприоритетных задач, а рост памяти — ранний отказ. Порог должен иметь владельца и обоснование ресурсом. Если алерт основан только на глубине, может быть много ложных срабатываний при быстром потребителе или пропущена одна зависшая задача при небольшой очереди.

### Не перепутайте очередь с задержкой ответа

Полная задержка запроса может включать время до приёма, время в очереди, исполнение и ожидание ответа после работы. Урок рассматривает очередь, но график latency может суммировать все компоненты. При росте общей задержки измерьте участки отдельно, прежде чем обвинять очередь. Ошибка в точке старта таймера даст систематически неверное сравнение.

Если задача снимается с очереди, но не завершается, глубина падает, хотя пользовательский результат ещё не готов. Для такого случая полезны число активных работ, возраст выполняемой задачи и длительность выполнения. Для отменённой задачи определите, удаляется ли она сразу и остаётся ли подтверждённая запись. Нулевая глубина не значит, что вся работа завершилась успешно.

### Пример с расписанием событий

Пусть в момент 0 приходит задача A, в момент 1 — B и C, а завершение исполнителя происходит в моменты 2 и 4. При FIFO A начинает первой, затем B; C остаётся в очереди до следующего освобождения. Если B отменена до старта, очередь может уменьшиться, а C — начать раньше. Запишите точные переходы и убедитесь, что возраст C считается от поступления, а не от предыдущего завершения.

Теперь оставьте ту же глубину, но сдвиньте поступление C на несколько минут раньше. Если ваша метрика снимает только текущую глубину, график не изменится, хотя пользовательское ожидание станет намного хуже. Для обнаружения нужен возраст старейшего элемента или распределение задержки ожидания. Проверьте, какой источник времени это вычисляет и сбрасывается ли он при переносе задачи в другую очередь.

Проведите эксперимент с фиксированным расписанием и сравните ожидаемую таблицу с наблюдением. Не используйте реальные секунды сна там, где можно передать временные отметки: тест останется детерминированным и быстрым.

### Проверьте уход задачи из системы

При подсчёте важно не потерять задачу между очередью и worker. Если worker забрал элемент, глубина уменьшается; если процесс завершился до подтверждённого результата, задача может исчезнуть или вернуться после восстановления — зависит от типа очереди. Фиксируйте события `enqueued`, `started` и `completed` отдельно и проверяйте разность между ними. Для долговечной очереди уточните, когда запись удаляется и какое подтверждение означает завершение.

## Практика Easy / Medium / Hard

**Easy — снимок глубины.** Реализуйте `QueueBand`; проверьте пустую, частичную, полную и некорректную очередь.

**Medium — возраст старейшей работы.** Реализуйте `QueuePressure` с входным `maxAgeSeconds`; глубина и возраст независимо дают состояния `full` и `stale`. Проверьте порог прямо на границе и рядом с ней.

**Hard — политика потребителя.** Реализуйте `QueueAction` и добавьте `consumerPaused`; проверьте приоритет паузы над пустым снимком, а также порядок full и stale. Это не запускает consumer и не измеряет latency распределение.
