# Составные и частичные индексы

## Что ты сделаешь

Ты научишься выбирать порядок колонок в составном B-tree по форме запроса, а не по красоте схемы: равенства впереди, сортировка следом, левый префикс как единица использования. Разберёшь покрывающие и частичные индексы и их цену для записи. Три функции урока — `IndexOrder`, `ValidIndexShape`, `IndexSupportsQuery` — это правила формы индекса в учебной модели; решение планировщика они не предсказывают.

## Левый префикс: как устроен составной B-tree

Составной индекс упорядочивает записи сначала по первой колонке, внутри равных значений — по второй, и так далее. Для `(tenant_id, created_at)` все записи одного арендатора лежат рядом и внутри отсортированы по времени: фильтр по `tenant_id` и диапазон по `created_at` — непрерывный отрезок индекса. Запрос только по `created_at` такого отрезка не получает: нужные записи разбросаны по всем арендаторам.

```go group=prefix mode=run
package main

import "fmt"

type entry struct {
    tenant  int
    created int
}

func main() {
    // записи уже в порядке (tenant, created), как в B-tree
    index := []entry{{1, 10}, {1, 20}, {1, 30}, {2, 5}, {2, 25}, {3, 15}, {3, 35}}
    first, last := -1, -1
    for i, e := range index {
        if e.tenant == 2 && e.created >= 10 {
            if first < 0 {
                first = i
            }
            last = i
        }
    }
    fmt.Println("tenant=2, created>=10: отрезок индекса", first, "..", last)
    hits := 0
    for _, e := range index {
        if e.created >= 20 {
            hits++
        }
    }
    fmt.Println("только created>=20: совпадений", hits, "из", len(index), "— непрерывного отрезка нет")
}
```

Вывод:

```text
tenant=2, created>=10: отрезок индекса 4 .. 4
только created>=20: совпадений 4 из 7 — непрерывного отрезка нет
```

Порядок ключей следует из предикатов, сортировки и кардинальности. В нагрузке с обязательным фильтром по арендатору ведущая колонка `tenant_id` помогает и изоляции чтения, но это наблюдение о такой нагрузке, а не универсальное правило.

> **Важно.** Единица использования составного индекса — левый префикс. Индекс по `(a, b, c)` помогает запросам по `a`, по `a, b` и по `a, b, c`; запросу по `b` он помогает редко и дорого.

## Равенство, потом диапазон или сортировка

Частая форма: `WHERE status = ? AND created_at > ? ORDER BY created_at LIMIT 20`. Колонки с равенством идут первыми — они сужают отрезок, — затем колонка, по которой диапазон или сортировка: внутри равных `status` записи уже лежат в нужном порядке, и сортировать не надо. Если поставить `created_at` первой, равенство по `status` придётся проверять на каждой записи диапазона.

```go group=order mode=run
package main

import "fmt"

func indexOrder(equalityColumns, sortColumns int) string {
    if equalityColumns < 0 || sortColumns < 0 {
        return "invalid"
    }
    if equalityColumns == 0 {
        return "sort_only"
    }
    if sortColumns == 0 {
        return "equality_only"
    }
    return "equality_then_sort"
}

func main() {
    fmt.Println(indexOrder(2, 1), indexOrder(1, 0), indexOrder(0, 2), indexOrder(-1, 1))
}
```

Вывод:

```text
equality_then_sort equality_only sort_only invalid
```

Это правило формы для заданного запроса. Направление сортировки, `NULLS FIRST/LAST`, collation и операторы (`=`, `>`, `LIKE 'abc%'`) влияют на то, сможет ли планировщик применить индекс к конкретному `ORDER BY`; проверяй запрос целиком, включая фильтр арендатора и стабильный tie-breaker, чтобы пагинация не переставляла равные `created_at`.

> **Типичная ошибка.** Индекс `(created_at, status)` для запроса «последние pending»: диапазон впереди равенства, и отрезок индекса включает все статусы.

## Покрывающий индекс и INCLUDE

Если все нужные запросу поля есть в индексе, планировщик может обойтись без чтения таблицы — index-only scan. `INCLUDE (payload)` добавляет поля в листья индекса, не делая их ключами сортировки. Но «только индекс» возможен, лишь когда карта видимости (visibility map) подтверждает, что страницы таблицы не содержат невидимых версий строк; после массовых изменений до `VACUUM` сканирование всё равно обращается к таблице. Каждое добавленное поле увеличивает индекс и усиливает write amplification: узкий индекс дешевле обновлять и хранить.

## Частичный индекс и совпадение предиката

Частичный индекс содержит только строки, удовлетворяющие его предикату: `WHERE status = 'pending'` на таблице, где pending — два процента, даёт индекс в пятьдесят раз меньше полного. Планировщик использует его, только если докажет, что предикат запроса влечёт предикат индекса: `status = 'pending'` — да; `status IN ('pending', 'done')` — нет; параметр `status = $1` — нет, потому что значение неизвестно при планировании.

```go group=partial mode=run
package main

import "fmt"

func supports(equalityPrefix, indexSortColumns, querySortColumns int, partialPredicateMatches bool) bool {
    if equalityPrefix < 0 || indexSortColumns < 0 || querySortColumns < 0 {
        return false
    }
    if equalityPrefix == 0 && indexSortColumns == 0 {
        return false
    }
    return querySortColumns <= indexSortColumns && partialPredicateMatches
}

func main() {
    fmt.Println(supports(2, 2, 1, true), supports(1, 1, 2, true), supports(2, 1, 1, false), supports(0, 0, 0, true))
}
```

Вывод:

```text
true false false false
```

Второй случай — запрос сортирует по двум колонкам, а индекс даёт порядок только по одной; третий — частичный индекс с несовпавшим предикатом; четвёртый — пустой ключ. Уникальность частичного индекса распространяется только на охваченные строки: если бизнес-инвариант требует уникальности во всей таблице, частичный индекс его не обеспечит.

> **Зачем.** Прежде чем создавать частичный индекс, выпиши точные предикаты запросов, которые должны им пользоваться, и проверь каждый через `EXPLAIN`: логически похожее условие — ещё не эквивалентное.

## ORDER BY … LIMIT и стабильный порядок

Запрос «последние двадцать» — `ORDER BY created_at DESC LIMIT 20` — выигрывает от индекса с подходящим ключом и направлением: планировщик идёт по индексу с конца и останавливается после двадцати строк, не сортируя всю выборку. Но стоит добавить второй столбец сортировки, `NULLS FIRST` или другую collation, как соответствие пропадает, и в плане появляется `Sort` поверх полного отрезка.

Отдельная проблема — равные значения `created_at`: без tie-breaker (`ORDER BY created_at DESC, id DESC`) порядок равных строк не определён, и пагинация может показать одну запись дважды, а другую пропустить. Tie-breaker должен входить и в индекс — `(tenant_id, created_at, id)`, — иначе выигрыш от индекса теряется на досортировке. Проверяй запрос целиком, с фильтром арендатора и tie-breaker, а не абстрактный `ORDER BY`.

> **Зачем.** Индекс, построенный «под сортировку», проверяется одним вопросом: исчез ли узел `Sort` из плана при той же выборке.

## Цена записи и обслуживания

Каждый индекс обновляется при вставке, удалении и изменении ключевой колонки, занимает диск и участвует в `VACUUM`. Перед добавлением оцени: размер и ожидаемый рост, bloat, влияние построения (`CREATE INDEX CONCURRENTLY` на живой таблице), время миграции. Нельзя заключить, что индекс полезен, по наличию `Index Scan` в плане: сопоставь фактически прочитанные строки и блоки, фильтры после индекса, сортировку, общее время и результат для пользователя. Выбор — баланс между конкретными путями чтения и профилем изменений, и он пересматривается, когда меняется нагрузка.

Перед миграцией перечисли все запросы, которые должны пользоваться новым индексом, и те, которые заплатят за него записью. Индекс без списка потребителей через полгода никто не решится удалить, хотя его, возможно, никто не использует; отчёт с этим списком — часть схемы, а не примечание.

## Типичные ошибки

- Диапазон или сортировка впереди равенства: отрезок индекса включает лишние строки.
- Индекс по `(a, b)` в расчёте на запросы по `b`: левый префикс не совпадает.
- Частичный индекс для параметризованного запроса: планировщик не докажет предикат.
- `INCLUDE` всего подряд ради index-only scan: индекс растёт, а visibility map всё равно отправляет к таблице.
- Уникальный частичный индекс как инвариант всей таблицы.
- Вывод о пользе по слову `Index Scan`, а не по прочитанным блокам и времени.

## Самостоятельная лаборатория

На одноразовом PostgreSQL создай таблицу задач с колонками `tenant_id`, `status`, `created_at`, миллион синтетических строк, pending — два процента. Запрос: `WHERE tenant_id = ? AND status = 'pending' ORDER BY created_at DESC LIMIT 20`. Построй три индекса по очереди — `(created_at)`, `(tenant_id, status, created_at)`, частичный `(tenant_id, created_at) WHERE status = 'pending'` — и для каждого сними `EXPLAIN (ANALYZE, BUFFERS)`: тип доступа, прочитанные блоки, наличие `Sort`, время. Замени `'pending'` на параметр и проверь, что частичный индекс перестал использоваться. Запиши размер каждого индекса и вывод одним предложением. Удали стенд.

## Если что-то пошло не так

- `equality_only` для `(0, 0)` → в учебной модели проверка `equalityColumns == 0` идёт первой, и ответ — `sort_only`; порядок правил как в карточке.
- `true` для пустой формы в задании 2 → условие «хотя бы одна колонка» отсутствует.
- `true` при `querySortColumns > indexSortColumns` → сравнение перевёрнуто.
- `true` при несовпавшем предикате → флаг `partialPredicateMatches` не учтён.
- `import … is not allowed` → импорты запрещены: целые числа и `bool`.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Модель упрощена: направления сортировки, operator classes и решение планировщика не моделируются.

### Задание 1 · Easy: составь порядок колонок B-tree

**Цель.** По числу колонок с равенством и колонок сортировки вернуть `equality_then_sort`, `equality_only`, `sort_only` или `invalid`.

**Ожидаемый вывод** — для `(equalityColumns=2, sortColumns=1)`:

```text
"equality_then_sort"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func IndexOrder(equalityColumns, sortColumns int) string`. Импорты запрещены.
2. Отрицательное значение → `"invalid"`.
3. `equalityColumns == 0` → `"sort_only"`; затем `sortColumns == 0` → `"equality_only"`; иначе `"equality_then_sort"`.
4. «Запустить», «Проверить» — закрытые примеры: `(0, 2)` → `sort_only`, `(-1, 1)` → `invalid`.

**Как проверить себя.** Порядок правил фиксирован: сначала знак, затем отсутствие равенств, затем отсутствие сортировки; форма `(0, 0)` по этому порядку даёт `sort_only`.

**Если не принято.**
- `invalid` для `(0, 2)` → ноль принят за некорректное значение; недопустимы только отрицательные.
- Перепутаны `equality_only` и `sort_only` → проверь, какое число равно нулю.

> **Подсказка.** Это классификация формы, не рекомендация: даже `equality_then_sort` ничего не говорит о направлениях и операторах.

### Задание 2 · Medium: проверь непустую форму индекса

**Цель.** Вернуть `true`, если оба счётчика неотрицательны и хотя бы один больше нуля.

**Ожидаемый вывод** — для `(1, 1)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ValidIndexShape(equalityColumns, sortColumns int) bool`. Импорты запрещены.
2. Верни `equalityColumns >= 0 && sortColumns >= 0 && (equalityColumns > 0 || sortColumns > 0)`.
3. «Запустить», «Проверить» — закрытые примеры: `(-1, 0)` → `false`, `(0, 0)` → `false`.

**Как проверить себя.** Пустой ключ — не индекс; отрицательные счётчики — ошибка входа; тип колонок и operator class здесь не проверяются.

**Если не принято.**
- `true` для `(0, 0)` → нет условия «хотя бы одна колонка».
- `false` для `(0, 1)` → использовано `&&` вместо `||` во второй части.

> **Подсказка.** Скобки вокруг `||` обязательны: без них приоритет `&&` изменит смысл.

### Задание 3 · Hard: проверь equality prefix и порядок index

**Цель.** Вернуть `true`, если ключ индекса непуст, колонок сортировки в запросе не больше, чем в индексе, и предикат частичного индекса совпадает.

**Ожидаемый вывод** — для `(equalityPrefix=2, indexSortColumns=2, querySortColumns=1, partialPredicateMatches=true)`:

```text
true
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func IndexSupportsQuery(equalityPrefix, indexSortColumns, querySortColumns int, partialPredicateMatches bool) bool`. Импорты запрещены.
2. Все три числа неотрицательны, иначе `false`; ключ непуст: `equalityPrefix > 0 || indexSortColumns > 0`.
3. `querySortColumns <= indexSortColumns` и `partialPredicateMatches` — оба обязательны.
4. «Запустить», «Проверить» — закрытые примеры: запрос сортирует по двум колонкам при одной в индексе → `false`; предикат не совпал → `false`.

**Как проверить себя.** Запрос без сортировки (`querySortColumns = 0`) поддерживается любым непустым индексом с совпавшим предикатом; для полного индекса флаг предиката передают как `true`.

**Если не принято.**
- `true` при `querySortColumns > indexSortColumns` → неравенство перевёрнуто.
- `true` при пустом ключе → проверка «хотя бы одна колонка» отсутствует.
- `false` при `querySortColumns = 0` → ноль ошибочно принят за «нет поддержки».

> **Подсказка.** Пять условий через `&&`; модель не знает о направлениях сортировки и операторах — так и напиши в отчёте, когда применишь её к реальному запросу.

## Итог

- Составной B-tree используют по левому префиксу: равенства впереди, диапазон или сортировка следом, порядок — из формы запроса.
- Покрывающий индекс экономит чтение таблицы только при чистой карте видимости; частичный — только при доказуемом совпадении предиката.
- Каждый индекс — цена для записи и обслуживания; польза доказывается прочитанными блоками и временем, а не словом `Index Scan`.
