# Метрики, traces и request context

## Что ты сделаешь

Ты напишешь три проверки телеметрии: допустимость имени метки метрики, allowlist пар атрибутов трассировки и классификацию счётчиков запросов и ошибок. Функции проверяют имена, значения и числа по переданным данным. Они не создают метрики и не отправляют трассы.

## Три вида телеметрии

Метрики — это агрегаты: сколько запросов было, какая доля завершилась ошибкой, какая задержка у 95 процентов запросов. Они нужны для графиков и алертов, и хранятся компактно, потому что не хранят отдельные события. Журнал — это отдельные события с деталями. Трасса — путь одного запроса через несколько сервисов с временем на каждом шаге.

Каждый вид отвечает на свой вопрос. Метрика скажет, что ошибок стало больше. Журнал покажет, какая именно ошибка случилась. Трасса покажет, в каком сервисе запрос провёл больше всего времени. Смешивать их роли нельзя: например, метрика с детальными значениями быстро становится дорогой.

> **Важно.** Телеметрия тоже обрабатывает персональные данные, если в неё попадают идентификаторы пользователей или содержимое запросов. Её проектируют с той же осторожностью, что и основное хранилище.

## Метки метрик

Метка (label) — это измерение метрики, например операция или класс статуса. Каждое уникальное сочетание значений меток создаёт отдельный временной ряд. Если метка принимает конечное число значений, ряды ограничены. Если метка принимает значения без предела, рядов становится бесконечно много.

Поэтому метки выбирают с небольшим фиксированным набором значений. Для операции это список операций, для результата — успех или ошибка. Пример показывает, как такой набор задаётся явно и как проверяется имя метки:

```go
package main

import "fmt"

func main() {
    allowed := map[string]bool{"operation": true, "status_class": true, "result": true}
    for _, label := range []string{"operation", "user_id"} {
        fmt.Println(label, allowed[label])
    }
}
```

Вывод: `operation true` и `user_id false`. Ключ `user_id` отвергнут, потому что его значений слишком много.

## Почему нельзя использовать идентификатор

Идентификатор пользователя как метка метрики создаёт миллионы рядов, и хранилище метрик перестаёт справляться. Кроме того, такая метка раскрывает поведение конкретного человека в агрегатах, которые видят многие люди. Поэтому вместо идентификатора используют класс: например, тип клиента или сегмент.

То же касается путей HTTP. Путь `/v1/tasks/839274` содержит идентификатор задачи и порождает новый ряд для каждой задачи. Вместо этого используют шаблон маршрута `/v1/tasks/{taskID}`: значений конечно и они известны заранее.

## Атрибуты трассировки

Атрибуты трассы тоже не должны содержать сырые данные. Разрешённые пары задаются как allowlist: ключ и допустимые значения. Значение маршрута — только шаблон, метод — один из известных методов HTTP, код статуса — число в диапазоне 100–599. Всё остальное запрещено, включая query-строку, токены и неизвестные ключи.

Allowlist надёжнее запрета по той же причине, что и для журнала: новый атрибут не попадёт в трассу, пока его не разрешили. Пример показывает проверку маршрута и запрещённого пути:

```go
package main

import "fmt"

func main() {
    routes := map[string]bool{"/v1/tasks/{taskID}": true}
    for _, r := range []string{"/v1/tasks/{taskID}", "/v1/tasks/839274"} {
        fmt.Println(r, routes[r])
    }
}
```

Вывод: `/v1/tasks/{taskID} true` и `/v1/tasks/839274 false`. Сырой путь с идентификатором не совпадает с шаблоном и не попадает в атрибуты.

## Контекст трассировки

Контекст трассировки переносит идентификатор трассы от одного сервиса к другому. Он передаётся в заголовках запроса и затем в контексте обработчика. Проверка передачи контекста важна: если контекст не дошёл до downstream-вызова, трасса обрывается, и диагностика теряет нить.

Проверка передачи не должна записывать персональные данные. Удобный приём — маркер: в запрос кладут заметное значение, которое не должно появиться ни в одном атрибуте, метке или журнале. Если маркер найден в телеметрии, утечка есть. Тест проверяет и передачу контекста, и отсутствие маркера.

## Классификация счётчиков

Счётчики запросов и ошибок дают основу для сигналов. Если запросов не было, судить о надёжности нельзя: ноль ошибок при нуле запросов — это отсутствие данных, а не хорошая работа. Поэтому сначала проверяется выборка, и только потом доля ошибок. Ошибок больше запросов быть не может, и такой ввод считается некорректным.

Учебная функция делает только классификацию. Она не вычисляет SLO и не считает бюджет ошибок: это отдельная задача, которой нужны окна времени и цели.

## Частота и стоимость меток

Стоимость метрик растёт не с числом событий, а с числом рядов. Поэтому добавить одну метку с десятью значениями означает умножить число рядов на десять для каждой комбинации остальных меток. Новую метку обсуждают заранее: какой вопрос она отвечает, сколько значений у неё будет, и можно ли получить тот же ответ из уже существующих меток.

Гистограммы задержки тоже умножают ряды: каждая корзина — отдельный ряд. Поэтому их делают только для ключевых операций, а не для каждого маршрута. Для остальных достаточно счётчика и суммы.

## Выборки и шум

Доля ошибок на маленькой выборке шумит: один неудачный запрос из двух даёт пятьдесят процентов. Поэтому алерт по доле ставят только при достаточном числе запросов за окно. Классификатор в этой главе выделяет пустую выборку отдельно именно потому, что решение о тревоге на ней невозможно.

## Модель и механизм

Для телеметрии полезны три вопроса. Какой вопрос отвечает каждый сигнал? Какие метки и атрибуты конечны? Что означает отсутствие данных? Ответы записываются как контракт до добавления инструментирования.

Синхронизация здесь не нужна, потому что счётчики в этой главе уже агрегированы. Цена подхода — список допустимых меток и атрибутов требует сопровождения, и каждое новое измерение обсуждается как изменение схемы.

## Типичные ошибки и исправление

Первая ошибка — сделать идентификатор меткой метрики. Исправление — класс или сегмент вместо идентификатора.

Вторая — записывать сырой путь запроса. Исправление — шаблон маршрута.

Третья — считать пустую выборку хорошим результатом. Исправление — отдельное состояние «нет данных».

Четвёртая — проверять передачу контекста без маркера. Исправление — тест с заметным маркером, который не должен попасть в телеметрию.

> **Типичная ошибка.** Добавить заголовок авторизации в атрибуты трассы, чтобы «видеть пользователя в трассе». Токен попадает в систему трассировки и живёт там дольше самого токена.

## Если что-то пошло не так

- Хранилище метрик растёт без предела → в метке появился идентификатор; замени его классом.
- В трассе видны пути с идентификаторами → атрибут пишет сырой путь; используй шаблон маршрута.
- Трасса обрывается на границе сервисов → контекст не передан в downstream-вызов; проверь аргументы.
- Ноль ошибок в дашборде при нулевом трафике → выборка пустая, а не сервис надёжен; покажи отсутствие данных отдельно.

## Воспроизводимая лабораторная: allowlist атрибутов

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Внешний сборщик телеметрии не нужен: атрибуты формируются и проверяются в памяти программы.

Программа ниже собирает атрибуты запроса, оставляет только разрешённые пары и проверяет, что маркер персональных данных не попал в результат. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import (
    "fmt"
    "strings"
)

func main() {
    allowed := map[string]map[string]bool{
        "route":  {"/v1/tasks/{taskID}": true},
        "method": {"GET": true, "POST": true},
    }
    request := map[string]string{
        "route":         "/v1/tasks/839274?token=PII-MARKER",
        "method":        "GET",
        "authorization": "Bearer PII-MARKER",
    }
    kept := []string{}
    for key, value := range request {
        if values, ok := allowed[key]; ok && values[value] {
            kept = append(kept, key+"="+value)
        }
    }
    fmt.Println("kept:", len(kept))
    fmt.Println("marker leaked:", strings.Contains(strings.Join(kept, ","), "PII-MARKER"))
}
```

**Ожидайте:** строка `kept: 1` — маршрут с идентификатором и query-строкой отброшены, а метод `GET` сохранён. Затем `marker leaked: false`: маркер персональных данных не попал в телеметрию.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- Метрики дают агрегаты, журналы — отдельные события, трассы — путь запроса; каждый вид отвечает на свой вопрос.
- Метки и атрибуты выбирают из конечного списка: идентификаторы и сырые пути создают бесконечно много рядов и раскрывают данные.
- Пустая выборка означает отсутствие данных, а не надёжность; проверка передачи контекста использует маркер, которого не должно быть в телеметрии. Все три правила живут рядом с кодом инструментирования и меняются вместе с ним, а не в отдельном документе, который быстро устаревает.
