# 32. Метрики, traces и request context

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `middle-29`; предыдущая глава `middle-31`.  
**Планируемый порядок каталога:** 72.  
**Результат:** Выбирать низкокардинальные labels и проектировать проверку trace context propagation без записи PII. В P3 пока нет tracing-инструментации, поэтому курс учит составить проверяемый integration test, но не подтверждает propagation в работающем сервисе.

## Глоссарий

- **metric label (метка метрики)** — Измерение агрегированной серии; множество значений должно быть ограничено.
- **cardinality (кардинальность)** — Количество уникальных комбинаций label и, следовательно, временных рядов.
- **route template (шаблон маршрута)** — Нормализованный шаблон, возвращённый router, например `/v1/tasks/{taskID}`, без фактического ID.
- **trace attribute (атрибут трассировки)** — Пара ключ-значение, привязанная к span и подчинённая privacy policy.
- **SLI (индикатор уровня сервиса)** — Определённая измеримая выборка событий и её знаменатель.

## Теория и границы применения

Метрики отвечают на агрегированные вопросы: сколько запросов завершилось с ошибкой, как меняется задержка, сколько задач ожидают обработки. Их labels должны иметь конечный и контролируемый набор значений. Если добавить user ID, raw URL или task ID, каждый запрос может создавать новый ряд; кардинальность растёт вместе с трафиком и увеличивает память/стоимость хранения. Для HTTP обычно используют route template, method из ограниченного набора и status class, но конкретная схема зависит от метрики.

Route template должен приходить из router после сопоставления маршрута. Для `/v1/tasks/123` нормализованное имя может быть `/v1/tasks/{taskID}`. Нельзя подменять его исходным `URL.Path` и считать, что имя ключа `route` делает значение безопасным. Учебный checker может сравнить строку с allowlist известных templates, но сам по себе не доказывает происхождение значения из router. Интеграционный тест должен пройти запрос через реальный router, перехватить созданный span/metric и проверить, что template сохранён, а ID не появился.

Ключ и значение telemetry нужно проверять независимо. Allowlist `route`, `method`, `status_code` предотвращает неизвестные имена, но `route=/users/839274`, `route=/reset?token=secret` или `status_code=Bearer ...` всё равно раскрывают чувствительные данные и/или создают кардинальность. Поэтому контракт Medium проверяет допустимый key вместе с допустимым value: для route — только точные зарегистрированные templates; method — ограниченные HTTP methods; status_code — ограниченный формат/диапазон. Любое неожиданное значение отвергается. В приложении источник значения всё равно должен быть правильным — value validation не доказывает происхождение.

Trace связывает этапы одной операции и обычно имеет ограниченное число span attributes. Trace ID и span ID — технические identifiers для корреляции, но не замена пользовательскому principal. Не помещайте в span секрет, тело запроса, credential, личный ID или текст ошибки без необходимости и явной политики. Разрешённый key не является sanitizer. Context propagation переносит trace context между слоями; внешние trace headers считаются недоверенным входом, формат и размер нужно валидировать, а sampled flag не должен безусловно позволять клиенту включать дорогую трассировку.

Метрики, логи и traces имеют разные назначения и правила хранения. Metrics агрегируют, logs описывают события, traces связывают этапы запроса. Уникальный request ID может быть полезен в логах/trace, но как label метрики часто опасен из-за количества серий. Анонимизация должна учитывать возможность связывания данных между сигналами; один и тот же идентификатор в нескольких системах создаёт корреляцию. Выбирайте минимальные поля, необходимые для диагностики.

SLI начинается с точного знаменателя: какие запросы считаются подходящими, какое окно времени и что считается ошибкой. При нуле наблюдений процент не равен нулю; это `no_sample`, потому что нет основания утверждать ни успех, ни отказ. `SignalDecision` проверяет только целые счётчики и их допустимый порядок (`0 <= failures <= requests`). Он не вычисляет долю, не строит окно, не обнаруживает потерю telemetry и не подтверждает SLO.

Уровни упражнений узкие: Easy проверяет фиксированные названия metric labels; Medium проверяет key-value пары; Hard классифицирует два счётчика. Каждый contract нужен для одного локального правила и не измеряет реальную серию. В частности, Medium allowlist известных шаблонов лишь проверит совпадение со строковым набором. Чтобы доказать, что route получен от router, нужен integration путь. Чтобы доказать отсутствие secret в экспортируемом telemetry — нужно проверить сериализацию/экспорт на конкретной конфигурации.

Протестируйте границы: точный известный template принимается; один raw ID отвергается; неизвестный сегмент/route отвергается; query string и token отвергаются; `method` принимает только перечисленные методы; код статуса принимает только определённый диапазон; пустой или case-variant key отвергается. Добавьте collision: разрешённый key с недопустимым value. Такой вектор нужен именно потому, что проверка только имени поля пропускает важный риск. Не подменяйте route template на произвольный path для удобства теста.

Для реального instrumentation выберите тестовый HTTP route с параметром. Сделайте запрос с уникальным sentinel ID, снимите metric attributes и span events через in-memory exporter. Убедитесь, что template присутствует, а sentinel отсутствует во всех labels и attributes. Затем проверьте низкую кардинальность для нескольких разных ID: число серий должно оставаться постоянным. Тест с прямым вызовом `TraceAttributeAllowed` проверит только таблицу допустимых пар, а не соединение router с instrumentation.

Наблюдаемость — сигнал для диагностики, а не гарантия корректности. Наличие span не доказывает, что операция успешна; отсутствие ошибок в пустой или неполной выборке не доказывает надёжность. На review запишите, где были измерены значения, какое окно/экспортёр использовался, какая privacy policy применялась и что осталось непроверенным. Не используйте helper результат как подтверждение безопасности или доступности сервиса.

## Разбор решения: нормализация маршрута

Router знает, какой шаблон сопоставился с запросом. Событие instrumentation должно использовать этот результат, например `/v1/tasks/{taskID}`, вместо сырых `/v1/tasks/42` или `/v1/tasks/901`. Если взять `r.URL.Path`, метка может включить идентификатор. Если взять `r.URL.String()`, туда может попасть query token. Простая проверка имени `route` не меняет ни одну из этих строк.

Для учебного allowlist конкретных templates список намеренно закрытый и короткий. Добавление маршрута требует обновить схему и тесты. Более общий production вариант должен брать canonical route metadata у router, а не пытаться распознавать любой пользовательский путь регулярным выражением. Если unknown route получает label `unknown`, этот label остаётся низкокардинальным; нельзя помещать исходный путь в fallback.

Method и status также ограничиваются. HTTP method следует нормализовать по фактически поддерживаемому набору. Status code имеет конечный набор целых значений; часто metric использует status class вместо точного кода, чтобы уменьшить серии. Контракт Medium принимает лишь строки из формата 100..599, а не утверждает, что точный код лучше для каждого метрика. Выбор зависит от диагностики и cardinality budget.

Проверка значений не является полноценной защитой от секретов: известный template может быть передан вручную любым вызывающим кодом. Поэтому production wiring имеет два требования: источник — router, значение — канонический template, и exporter получает только scrubbed attributes. В отчёте отдельно укажите результаты unit pair-check и real-router integration test; не объединяйте их в один сильный claim.

## Три самостоятельных запускаемых примера

### Пример 1: `MetricLabelAllowed`

Контракт: Разрешены только фиксированные labels operation, status_class, result.

```go
package main

import "fmt"

func MetricLabelAllowed(label string) bool {
	switch label { case "operation", "status_class", "result": return true; default: return false }
}

func main() {
	fmt.Println(MetricLabelAllowed("operation"))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `TraceAttributeAllowed`

Контракт: Разрешены route, method, status_code; неизвестные и секретные атрибуты false.

```go
package main

import "fmt"

func TraceAttributeAllowed(key, value string) bool {
	switch key {
	case "route": return value == "/v1/tasks/{taskID}" || value == "/v1/projects/{projectID}/tasks/{taskID}"
	case "method": return value == "GET" || value == "POST" || value == "PATCH" || value == "DELETE"
	case "status_code": return len(value) == 3 && value[0] >= '1' && value[0] <= '5' && value[1] >= '0' && value[1] <= '9' && value[2] >= '0' && value[2] <= '9'
	default: return false
	}
}

func main() {
	fmt.Println(TraceAttributeAllowed("route", "/v1/tasks/{taskID}"))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `SignalDecision`

Контракт: Некорректные счётчики→invalid; нулевой знаменатель→no_sample; иначе есть сбои→errors_present, нет наблюдавшихся→no_errors_observed.

```go
package main

import "fmt"

func SignalDecision(requests, failures int) string {
	if requests < 0 || failures < 0 || failures > requests { return "invalid" }; if requests == 0 { return "no_sample" }; if failures > 0 { return "errors_present" }; return "no_errors_observed"
}

func main() {
	fmt.Println(SignalDecision(10, 0))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

## Практика Easy / Medium / Hard

**Easy — базовое правило.** Реализуйте `func MetricLabelAllowed(label string) bool`. Контракт: Разрешены только имена labels operation, status_class, result. Функция не проверяет instrumentation или значения. Скрытые и публичные vectors закреплены в grading spec.

**Medium — граничная политика.** Реализуйте `func TraceAttributeAllowed(key, value string) bool`. Контракт: Проверяется пара key/value: route только точный router-template `/v1/tasks/{taskID}` или `/v1/projects/{projectID}/tasks/{taskID}`; method только GET/POST/PATCH/DELETE; status_code — строка 100..599. Raw ID/path/query/secret отклоняются. Helper не подтверждает происхождение route из router. Скрытые и публичные vectors закреплены в grading spec.

**Hard — helper-проверка.** Реализуйте `func SignalDecision(requests, failures int) string`. Контракт: Некорректные счётчики → invalid; нулевой знаменатель → no_sample; есть сбои → errors_present; иначе no_errors_observed. Helper не вычисляет SLI/SLO. Скрытые и публичные vectors закреплены в grading spec.

## Лабораторная карточка TaskFlow: route templates, cardinality и privacy

Подключите in-memory router и test exporter для одной route `/v1/tasks/{taskID}`. Выполните запросы с несколькими разными ID и query token sentinel. Перехватите labels и span attributes для каждого запроса. Во всех записях должно быть одно и то же router-produced template, а не конкретный ID/path/query; число metric series должно оставаться постоянным. Убедитесь, что token и sentinel ID отсутствуют как в keys, так и values.

Сделайте отдельный прямой table-driven test `TraceAttributeAllowed`: допустимый известный template; другой известный template; raw ID path; неизвестный template; query string; секрет; неизвестный key; method вне allowlist; status value за пределами формата. Включите collision с допустимым key `route` и запрещённым value. Это доказывает поведение пары helper input, но не происхождение route. В integration test получайте значение непосредственно из router API; не передавайте строку из запроса как готовый template.

Для metric labels проверьте, что cardinality не растёт при смене `taskID`. User ID, email, request ID, сырая ошибка и URL не должны становиться labels. Trace attributes имеют отдельную privacy policy: низкая кардинальность metric label не гарантирует безопасное trace value. Проверьте сериализованные span events на чувствительные данные, а не только список ключей.

Для `SignalDecision` добавьте нулевой знаменатель, ноль ошибок, ненулевые ошибки, отрицательные счётчики и failures больше requests. Подчеркните, что helper не рассчитывает процент/error budget, не задаёт окно наблюдения и не проверяет потерю telemetry. Чтобы проверять SLI/SLO, нужен отдельный контракт с выборкой и временем.

В финальной карточке спроектированного теста укажите router/framework, exporter, запросы, метки, число серий до/после, privacy sentinel, команду и ограничения. В текущем P3 нет router instrumentation или exporter, поэтому фактический вывод о propagation здесь не подтверждён. Если значения проверялись только как строки, не называйте это доказательством instrumentation. Даже in-memory test не подтверждает production конфигурацию или хранение телеметрии.

## Воспроизводимая лабораторная: лейблы наблюдаемости в P3

**Prerequisites:** Go 1.27.2; исходники P3 доступны локально, база не нужна. Запустите фиксированные проверки ошибок и ограничения входа:

```sh
cd content/projects/p3/reference
go test -run '^(TestBoundedStrictJSON|TestErrorResponseDoesNotExposeInternalText)$' -count=1 -v
rg -n 'slog|trace|metric|request_id|requestID' --glob '*.go'
```

**Ожидайте:** тесты проходят по лимиту/строгому разбору JSON и отсутствию внутренних деталей в ответе; поиск показывает, какие сигналы реально присутствуют. В отчёте назовите один cardinality-риск (например, сырое значение ID как label) и отметьте, найден ли такой label; наличие `request_id` не доказывает распределённую трассировку. **Очистка:** внешние ресурсы не создаются.
