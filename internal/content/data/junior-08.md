## Тесты, таблицы и отладка

Тест (test) — исполняемая проверка ожидаемого поведения. В Go тестовый файл оканчивается на _test.go, пакет использует testing, а команда go test запускает проверки. Имя функции начинается с Test и принимает *testing.T. Тест должен сообщать, какое условие нарушено, и показывать вход, ожидаемое и фактическое значения.

Табличный тест (table-driven test) хранит набор входов и ожиданий в срезе структур, а цикл запускает одну проверку для каждой строки. Так обычный случай и границы используют одинаковую проверочную логику. Поля кейса должны объяснять сценарий. Не делайте таблицу такой абстрактной, что непонятно, почему значение ожидается.

Подтест (subtest) создаётся через t.Run с осмысленным названием. Он отделяет результаты и позволяет запустить конкретный сценарий флагом -run. Имена кейсов должны быть стабильными и безопасными для фильтрации. Не добавляйте в имена случайное время или идентификаторы.

Утверждение (assertion) — сравнение наблюдаемого результата с контрактом. В стандартном testing нет стороннего assert-пакета: условие и t.Fatalf достаточно. Сначала сравните весь результат, затем при необходимости покажите разницу полей. Тест должен завершаться сразу, если продолжение делает сравнение бессмысленным; t.Fatal прекращает текущий тест, t.Error записывает ошибку и продолжает.

Минимальное воспроизведение (minimal reproduction) — самый маленький вход, который показывает дефект. Сократите длинные данные, уберите нерелевантные вызовы, сохраните точное условие. Этот приём особенно полезен при off-by-one, nil/empty distinction и неверном порядке. Запускаемый тест превращает пример в повторяемое доказательство.

Регрессионный тест (regression test) фиксирует уже найденный дефект. Сначала создайте тест, который падает на старом поведении и проходит после исправления. Затем измените production-код. Так будущая правка не вернёт прежнюю ошибку незаметно. Само наличие теста не гарантирует полноту: он доказывает только те случаи, которые проверяет.

Тестируйте контракт, а не внутренние шаги. Если функция minMax возвращает два значения и флаг, сравните три результата; не требуйте, чтобы реализация использовала конкретное имя локальной переменной или цикл. Хороший тест переживает безопасный рефакторинг, но падает при изменении публичного поведения.

Для пустого среза minMax возвращает (0,0,false). Для непустого — реальные границы и true. Флаг отделяет отсутствие элементов от настоящего нуля. Таблица должна включать пустой и nil-срез, один элемент, отрицательные числа, одинаковые элементы и значения в разном порядке. Контракт одинаков для nil и пустого среза, потому что оба имеют длину ноль.

Отладка (debugging) — систематический поиск причины. Начните с точного сообщения и места, где наблюдаемое значение впервые расходится с ожиданием. Добавьте временный вывод или поставьте breakpoint в IDE, пройдите выполнение пошагово и проверьте гипотезу одним изменением. Удалите диагностический код после исправления или замените полезную проверку тестом.

Компиляторный сбой означает, что программа не прошла проверку синтаксиса или типов. Тестовый сбой означает, что программа собралась, но результат не совпал. Паника обычно указывает на нарушенный инвариант, например чтение values[0] без проверки длины. Не смешивайте эти классы: сначала добиться сборки, затем проверить поведение, затем исследовать панику.

Для запуска всех тестов проекта используется `go test ./...`; `-run TestMinMax/empty` выбирает конкретный тест и подтест. Флаг `-v` показывает подробности. `-count=1` отключает кеширование результата для диагностики. Не начинайте с десятков флагов: воспроизведите падение обычной командой, затем сузьте область.

Функциональная проверка платформы не подтверждает качество тестов студента. В упражнении автогрейдер вызывает функцию с детерминированными случаями. Чтобы практиковать сами тесты, в существующем P1 workspace откройте пакет проекта, создайте *_test.go и запустите go test ./.... Приёмка проверит итоговое поведение приложения, а ручное ревью оценивает, насколько тесты выражают границы и понятные ошибки.

Не проверяйте случайные детали: порядок обхода map не определён; сравнение ошибок по тексту хрупко; время и случайность нужно контролировать через передаваемую зависимость в более крупных программах. В этом уроке задача чистая и синхронная, поэтому никаких моков и часов нет. Каждый тест должен быть повторяемым.

Когда тест падает, прочитайте ожидаемое и фактическое значения до редактирования кода. Сформулируйте, какое правило нарушено, затем вручную посчитайте маленький пример. Проверьте границу до и после порога. Уменьшите вход, сохраните failing case и только потом меняйте алгоритм. Это экономит время и избегает случайного исправления симптома.

Три уровня задач тренируют разные навыки: написать таблицу тестов для маленькой функции; реализовать minMax и покрыть пустую границу; добавить регрессионную проверку к заданному дефекту. Оцениваются ответы функции, но ваши тесты выполняются только если вы сами добавили их в workspace. Не называйте автогрейдинг доказательством качества тестового набора.

### Полный тестовый пакет

Сохраните как `minmax_test.go` рядом с `minmax.go`. Он самодостаточен как пакет `main` в режиме тестирования.

```go mode=test
package main

import "testing"

func minMax(values []int) (int, int, bool) {
    if len(values) == 0 { return 0, 0, false }
    lo, hi := values[0], values[0]
    for _, v := range values[1:] { if v < lo { lo = v }; if v > hi { hi = v } }
    return lo, hi, true
}
func TestMinMax(t *testing.T) {
    cases := []struct { name string; in []int; wantLo, wantHi int; wantOK bool }{
        {"empty", nil, 0, 0, false}, {"one", []int{4}, 4, 4, true},
        {"negative", []int{-5, 2, -1}, -5, 2, true},
    }
    for _, tc := range cases { t.Run(tc.name, func(t *testing.T) {
        lo, hi, ok := minMax(tc.in)
        if lo != tc.wantLo || hi != tc.wantHi || ok != tc.wantOK { t.Fatalf("minMax(%v) = (%d,%d,%v), want (%d,%d,%v)", tc.in, lo, hi, ok, tc.wantLo, tc.wantHi, tc.wantOK) }
    }) }
}
```

Выполните `go test ./...`. Не превращайте отсутствие ошибки в единственное утверждение: сравните все части результата.

### Частые ошибки, самопроверка и помощь без ИИ

Типичная ошибка — использовать t.Errorf и затем обращаться к отсутствующему элементу: тест продолжает выполнение. Используйте Fatalf, когда дальше нельзя безопасно продолжить. Другая ошибка — одна строка теста на большой сложный сценарий: разделите его на имена, соответствующие бизнес-правилам. Не пишите тест, который дублирует реализацию построчно; иначе он может подтверждать тот же дефект.

Проверьте себя: 1) зачем table-driven формат? 2) чем t.Fatal отличается от t.Error? 3) какую роль играет имя subtest? 4) почему nil и пустой срез одинаковы здесь? 5) как тест фиксирует regression? 6) что доказывает passing test? 7) чем compile error отличается от failed assertion? Ответы: общая структура набора; первое останавливает текущий тест; позволяет понять/запустить сценарий; контракт смотрит len=0; воспроизводит найденный дефект; только проверенные случаи; сборка не завершилась против результата-контракта.

Если вы застряли, временно уберите лишние кейсы, оставив один падающий. Запустите `go test -run TestMinMax/empty -count=1`, выведите короткий вход и ожидаемое значение. Прочитайте тестовую строку целиком. AI Tutor может предложить гипотезу, но вы должны подтвердить её запуском теста; не копируйте непроверенную замену. Не передавайте приватные данные.

### Итог и словарь

Умение писать тесты — самостоятельный навык: сформулировать контракт, выбрать границы, назвать сценарий и показать полезное сообщение. Регрессионный набор растёт из реальных дефектов. Функциональный автогрейдер этого не заменяет. Практикуйте через P1 workspace и повторяйте запуск после каждой правки.

**Мини-глоссарий:** test — тест, исполняемая проверка; assertion — утверждение о результате; table-driven test — табличный тест; subtest — подтест; regression test — проверка от возврата дефекта; debugging — отладка; minimal reproduction — минимальное воспроизведение; boundary case — граничный случай.

## Как выбирать случаи, а не накапливать случайные тесты

Тестовый набор строится от контракта. Сначала перечислите состояния результата: успех, пустой вход, недопустимый вход и граница. Затем для каждого правила найдите вход, который отличает его от близкой неправильной реализации. Если правило говорит «не меньше порога», проверка ровно на границе отличает `>=` от `>`. Если функция допускает пустоту, пустой вход отличает безопасную реализацию от чтения первого элемента. Если порядок важен, переставьте элементы и проверьте сохранение порядка.

Не обязательно проверять все возможные списки. Для чистой функции область значений может быть бесконечной. Выбирайте классы эквивалентности: входы, которые проходят одинаковую ветвь. У каждой важной ветви должен быть хотя бы один пример; у предельной границы полезны значения сразу до, на границе и сразу после неё. Для сложной функции разделяйте тесты по правилу, чтобы имя показывало намерение.

Проверка всей структуры одним сравнением проще, когда тип сравним и диагностическое сообщение остаётся ясным. Для срезов `reflect.DeepEqual` не нужен в этой главе: циклом или `slices.Equal` можно сравнить значения, а при расхождении показать конкретные входы. В тестовом примере мы сравниваем несколько скалярных результатов напрямую. Зависимость добавляет собственные правила и не делает тест автоматически точнее.

Подтесты запускаются независимо, но тестовый код всё равно должен учитывать захват переменной цикла. В современных версиях Go семантика range-переменных для новых модулей отличается от старого поведения, однако переносимые примеры могут явно делать `tc := tc` перед `t.Run`. Понимайте версию модуля и не объясняйте сегодняшнюю ошибку устаревшим поведением. Здесь функции синхронны, поэтому параллельные тесты не нужны.

Если тест падает непостоянно, ищите зависимость от времени, случайности, глобального состояния, порядка map или внешнего сервиса. Эти проверки детерминированы: они используют конкретный ввод и не выходят в сеть. Для времени передавайте clock-функцию или время параметром в проектном коде; для случайности — источник с фиксированным seed, когда это допустимо. Не делайте тест «зелёным» увеличением sleep: это скрывает гонку, а не исправляет её.

### От дефекта к регрессионному кейсу

Представим, что прежняя реализация читает `values[0]` и падает на nil-срезе. Сохраните минимальный сценарий `minMax(nil)` в таблице с ожидаемым `(0,0,false)`. Убедитесь, что тест сначала падает паникой. Исправьте реализацию и запустите весь пакет. Теперь изменение контракта случайно нельзя вернуть без явного падения теста. Это ценность регрессионного теста: он сохраняет причину исправления рядом с кодом.

Если тест просто повторяет строки production-реализации, он может повторить ту же неверную предпосылку. Пишите ожидаемое независимо: вручную посчитайте минимум и максимум у короткого массива. Хороший тестовый oracle (эталон ожидания) проще проверяемой программы, а не её копия. Для больших проектов golden fixtures требуют ревью источника и обновлений, иначе ошибочные данные закрепятся.

### Самостоятельное исследование инструментов

В IDE можно ставить breakpoint в начале теста и выполнять шаги, наблюдая текущий кейс. Если интерфейс редактора не поддерживает debugger, используйте `t.Logf` только временно или запускайте узкий тест с `-v`. После нахождения причины уберите шумные логи и оставьте точное утверждение. Сообщение должно помогать следующему человеку без полного повторного запуска под отладчиком.

Для своего теста полезно прочитать стандартную документацию пакета testing и примеры `go help testflag`; это команды и документационные темы, а не код для вставки. Уточняйте синтаксис в установленной версии. Не воспринимайте тестовый отчёт как судью всего продукта: зелёный пакет говорит, что проверенные утверждения прошли.

### Пример: тест на ошибочный результат и минимальный кейс

```go mode=test
package main

import "testing"

func countPositive(values []int) int { n:=0; for _,v:=range values { if v>0 { n++ } }; return n }
func TestCountPositive(t *testing.T) {
    cases:=[]struct{name string; in []int; want int}{{"empty",nil,0},{"boundary",[]int{-1,0,1},1}}
    for _,tc:=range cases { t.Run(tc.name,func(t *testing.T){ if got:=countPositive(tc.in); got!=tc.want { t.Fatalf("countPositive(%v)=%d, want %d",tc.in,got,tc.want) } }) }
}
```

Это отдельный полный тестовый пакет: production-функция включена намеренно, чтобы пример запускался сам.

### Пример: регрессионная проверка пустой границы

```go mode=test
package main

import "testing"

func first(values []int) (int,bool) { if len(values)==0{return 0,false}; return values[0],true }
func TestFirstEmptyRegression(t *testing.T) { got,ok:=first(nil); if ok||got!=0 { t.Fatalf("first(nil)=(%d,%v), want (0,false)",got,ok) } }
```

Этот короткий тест фиксирует контракт, который защищает от panic при чтении индекса 0.
