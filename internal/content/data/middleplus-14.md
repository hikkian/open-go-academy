# 14. Обратное давление и управляемый отказ

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-13`
**Цель:** Backpressure (обратное давление) ограничивает передачу работы, когда downstream (нижестоящая зависимость) не успевает. Без обратного сигнала очередь лишь переносит перегрузку в память и увеличивает время ожидания. Политика должна заранее определять, ждать ли producer (производителю), отклонить ли задачу или применить shedding (сброс избыточной нагрузки), сохранив приоритет уже принятой работы.

## Термины и перевод

- **Backpressure** — механизм, который сообщает источнику о насыщении потребителя и ограничивает поступление новой работы.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Обратное давление (backpressure) — способ сообщить источнику работы, что принимающая сторона достигла своего предела. Без этого сигнала ожидание просто переносится в очередь: память расходуется, а время ответа растёт. Урок рассматривает конкретную точку решения — принять работу в ограниченную очередь, попросить подождать или отказать.

Сначала определите вместимость очереди и что означает её глубина: число ожидающих задач, без уже выполняемых. Затем опишите ответ при свободном месте и при полном лимите. Если политика возвращает «подождать», в реальном API всё равно нужен deadline (крайний срок ожидания); если отказывает — вызывающий код должен понимать, можно ли повторить запрос и когда. Наш helper не реализует ожидание, очередь, передачу сигнала или повтор.

Отказ должен быть виден вызывающей стороне и наблюдаем в самой системе. Молчаливое принятие сверх лимита нарушает границу, а безусловное повторение отказа способно усилить перегрузку. Эти последствия объясняют, почему решение о допуске — часть контракта, а не только условие в функции.

## Три запускаемых примера

### Пример 1: обычный путь

```go
package main

import "fmt"

func Admission(depth int, limit int) string {
	if depth < 0 || limit <= 0 { return "invalid" }; if depth >= limit { return "full" }; return "admit"
}

func main() { fmt.Println(Admission(4, 4)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 2: решение с несколькими сигналами

```go
package main

import "fmt"

func AdmissionReason(depth int, limit int, waitMillis int, deadlineMillis int, shed bool) string {
	if depth < 0 || limit <= 0 || waitMillis < 0 || deadlineMillis < 0 { return "invalid" }; if depth < limit { return "admit" }; if shed { return "shed" }; if deadlineMillis == 0 || waitMillis >= deadlineMillis { return "deadline" }; if waitMillis == 0 { return "reject" }; return "wait"
}

func main() { fmt.Println(AdmissionReason(4, 4, 100, 250, false)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 3: проверка ограниченного инварианта

```go
package main

import "fmt"

func AdmissionDecision(depth int, limit int, waitMillis int, deadlineMillis int, cancelled bool, shed bool) string {
	if depth < 0 || limit <= 0 || waitMillis < 0 || deadlineMillis < 0 { return "invalid" }; if cancelled { return "cancelled" }; if depth < limit { return "admit" }; if shed { return "shed" }; if deadlineMillis == 0 || waitMillis >= deadlineMillis { return "deadline" }; if waitMillis == 0 { return "reject" }; return "wait"
}

func main() { fmt.Println(AdmissionDecision(4, 4, 100, 250, true, false)) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.


## Практическая процедура

Сформулируйте три состояния: ниже предела, ровно на пределе и выше допустимого значения. Для каждого укажите ответ источнику и судьбу уже принятой работы. Проверьте границы публичных примеров: они подтверждают только порядок правил классификатора, а не реальную семантику HTTP или очереди.

Затем нарисуйте короткую последовательность: источник предлагает задачу; контроль допуска отвечает; приёмник либо сохраняет задачу, либо явно отказывает; источник соблюдает ответ. Для варианта ожидания укажите общий срок и отмену при его истечении. Для отказа укажите, не должна ли задача уже иметь побочный эффект, прежде чем вызывающая сторона решит повторить попытку.

Считайте отказ контролируемым исходом, а не автоматическим сбоем. В реальной интеграции понадобились бы метрики принятых/отклонённых задач и нагрузочный тест с изолированным исполнителем. Упражнение проверяет только заданные числа и приоритеты состояний; оно не вызывает downstream и не подтверждает безопасность публичного сервиса.

## Разбор сценария: Обратное давление и управляемый отказ

Представьте конечную очередь с заданной вместимостью. Подайте предложения последовательно до заполнения, затем ещё одно: запишите, что должен получить источник на каждом шаге. Отдельно проверьте нулевой лимит, если он допустим по контракту, и некорректные входы. Не смешивайте число ожидающих задач с числом уже выполняемых.

Сравните две возможные политики после заполнения: отказать немедленно или ждать ограниченное время. Для ожидания определите, что происходит при отмене вызывающей стороны; для отказа — какое условие делает повтор безопасным и ограниченным. Если helper возвращает имя состояния, это лишь согласованная метка, а не реализованный канал обратной связи.

Зафиксируйте, кто наблюдает насыщение и каким событием подтверждается освобождение места. Укажите неизвестные свойства, например фактическую память сообщения или поведение при остановке процесса. Следующий шаг для настоящей очереди — интеграционный тест producer/consumer с лимитом и отменой, а не вывод о работоспособности из одного классификатора.

## Лаборатория: определить поведение на заполненной очереди

### Численный сценарий

Пусть очередь вмещает три ожидающие задачи, а один обработчик уже занят. Пришли задачи A, B, C: после их принятия очередь заполнена, хотя суммарно система удерживает четыре задачи. Приходит D. Если контракт считает только ожидающие задачи, D не помещается. Если он считает одновременно выполняемую задачу частью общего лимита, то отказ наступил ещё при приёме C. До реализации обязательно выберите одно определение: две реализации с одинаковым числом «лимит три» могут вести себя по-разному.

Сравните ответ «отклонить» с ответом «ждать». Немедленный отказ освобождает вызывающую сторону, но ей нужно знать, когда и безопасно ли повторить запрос. Ожидание может сохранить работу, однако потребляет соединение и должно завершиться по deadline (крайнему сроку). Если запрос отменили, очередь должна удалить его или пометить отменённым; иначе исполнитель позднее выполнит работу, которую клиент уже считает отменённой.

### Пошаговый эксперимент

1. Определите единицу лимита, вместимость и входит ли активная задача. Запишите поведение для пустой очереди, последнего свободного места и первой сверхлимитной заявки.
2. Вручную разыграйте A, B, C, D и освобождение одного места. Укажите, кто получает освободившийся слот: уже ожидающий caller, новая заявка или элемент очереди.
3. Повторите сценарий с отменой B до её начала. Решите, возвращается ли место немедленно и как подтверждается отмена.
4. Задайте конечное время ожидания и ответ при его истечении. Не добавляйте автоматический retry без проверки повторного эффекта и общего бюджета попыток.
5. Проверьте helper на точной границе. Зафиксируйте вход, ожидаемую метку, фактическую метку и объяснение, почему соседнее значение даёт другое решение.

### Наблюдения и ловушки

Если глубина очереди равна лимиту, этого ещё недостаточно, чтобы узнать сколько задач система удерживает: часть могла быть захвачена обработчиками. Проверьте выбранное определение на каждом переходе. Ещё одна ловушка — считать отказ бесплатным. Для клиента, отправившего запрос, timeout не всегда сообщает, выполнилась ли операция; повтор изменения может создать дубликат. Ответ о перегрузке полезен только вместе с ясным результатом и правилом безопасного повторения.

Измерьте отдельно число предложенных, принятых, ожидающих, начатых, отменённых и завершённых задач. Эти счётчики должны описывать один и тот же сценарий и не дублировать элементы между состояниями. Если метрика не поступила, обозначьте её как неизвестную, а не как ноль. На локальных примерах не моделируются сетевые задержки, память сообщений, состояние нескольких реплик и поведение настоящей очереди. Они проверяют только политику решения для входных чисел.

В отчёте ответьте, на какой границе система сказала «нет», что получил caller (вызывающий код), и что будет, если тот повторит запрос. Какая часть решения вычислена helper-функцией, а какая требует теста реального канала? Для следующего шага достаточно небольшого producer/consumer теста с ограниченной очередью, управляемой отменой и проверкой фактической максимальной глубины.

### Отказы, повторы и справедливость

Backpressure может возвращаться как ожидание, временный отказ или явное снижение приоритета. У каждого ответа разные последствия. Ожидание удерживает клиента и может расходовать соединение; отказ переносит решение повторить на клиента; shedding (сброс нагрузки) может сохранить ресурс для важной работы, но требует прозрачного критерия выбора. Ошибка `429` сама по себе не ограничивает повторный поток, если клиент игнорирует `Retry-After` или получает одинаковое указание от сотен запросов.

Ограничьте время ожидания и число повторных обращений. Если система сообщает, что запрос не принят, это должно означать отсутствие побочного эффекта. Если она сообщает об ошибке уже после возможного выполнения, клиент не знает, нужно ли повторять. Для изменения состояния используйте идемпотентный ключ или чтение результата. В этой главе чистый helper не различает сетевой timeout до обработки и после неё; не приписывайте ему такого знания.

При приоритетном отказе проверьте, не создаёт ли политика постоянную несправедливость. Можно зарезервировать часть ресурса для низкого класса или учитывать возраст запроса. Но резерв также может простаивать, если критическая работа исчерпывает остальной бюджет. Поэтому соберите долю отказов и время ожидания отдельно по классам и определите допустимое правило до опыта.

### Запишите контракт отказа

Для каждого класса ответа напишите короткое сообщение вызывающему коду: принято; отказано до выполнения; ожидание истекло; исход неизвестен. Эти состояния нельзя объединять в одну метку `error`. Caller может безопасно повторить только часть из них. Если отказ произошёл до принятия, повтор после короткой задержки может быть возможен; если ответ потерялся после выполнения, нужна проверка результата либо ключ операции.

Проверьте также перегрузку самого канала обратной связи. Когда клиенты одновременно получают отказ и мгновенно повторяют, поток возрастает. Укажите задержку повторного предложения и jitter, если он используется. В этом упражнении не реализуется такой протокол, поэтому отчёт должен показать только решение policy-функции и отдельно предложить тест клиент-серверной последовательности.

### Проверьте отказ под повторной нагрузкой

Один отказ на границе может вызвать серию повторов, если клиент воспринимает любой ответ как временный. Разыграйте пять клиентов, которые получают отказ одновременно и повторяют без задержки. Сравните с клиентами, которые применяют ограниченную экспоненциальную паузу с jitter. Не требуется подключаться к сети: последовательность может быть задана как таблица времени и числа запросов. Запишите, возрастает ли число предложений после каждого раунда.

Сформулируйте желаемое поведение ответа: запрос явно не принят, повтор ограничен, а после восстановления клиент может попробовать снова. Если результат неизвестен, это отдельное состояние. Не смешивайте его с «не принято». Helper урока классифицирует состояние очереди, но не устанавливает эти протокольные гарантии.

## Практика Easy / Medium / Hard

**Easy — предел очереди.** Реализуйте `Admission` и проверьте состояние до лимита, на лимите и некорректные значения.

**Medium — ограниченное ожидание.** Реализуйте `AdmissionReason`: на полной очереди сравните предполагаемое wait window с остатком deadline, применяя shed policy в указанном порядке. Различите `wait`, `deadline`, `reject` и `shed`.

**Hard — отмена caller.** Реализуйте `AdmissionDecision`, где cancellation имеет приоритет над доступным слотом, а invalid ranges по-прежнему отклоняются первыми. Проверьте одновременные условия. Функция только выбирает действие; таймер и отмену контекста должна выполнять отдельная система.

### Рабочий вопрос 1: границы backpressure

Сопоставьте backpressure с владельцем источника истины и назовите событие, после которого повтор становится безопасным. Запишите сначала ожидаемое состояние, затем вход, действие и наблюдаемый исход. Не выводите причинность из одного совпадения; сохраните команду, версию среды, количество повторов и ошибочные варианты. Если данных недостаточно, итогом должна быть отметка «неизвестно» и план следующего измерения, а не уверенная оценка.
