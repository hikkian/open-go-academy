# Обратное давление и управляемый отказ

## Что ты сделаешь

Ты разберёшь точку, в которой система решает судьбу новой задачи при полной очереди: принять, попросить подождать, отказать или сбросить — и почему это решение принадлежит контракту, а не условию в коде. Три функции урока — `Admission`, `AdmissionReason`, `AdmissionDecision` — это политика допуска по снимку очереди с приоритетом правил; ожидание, таймеры и отмену горутин они не реализуют.

## Зачем нужна эта граница

Обратное давление (backpressure) — сигнал источнику работы о том, что принимающая сторона достигла предела. Без этого сигнала перегрузка не исчезает, а переезжает в очередь: память расходуется, время ответа растёт, а источник продолжает слать работу, которую некому выполнять. Ограниченная очередь и явное решение на её границе возвращают перегрузку туда, где её можно увидеть и на неё отреагировать.

Сначала определи вместимость очереди и что считается её глубиной: число ожидающих задач, без уже выполняемых. Потом опиши ответ при свободном месте и при полном лимите. «Подождать» в реальном API всегда ограничено крайним сроком (deadline); «отказать» сопровождается информацией, можно ли повторить и когда. Молчаливое принятие сверх лимита нарушает границу, а безусловный повтор отказа усиливает перегрузку.

```go group=admission mode=run
package main

import "fmt"

func admission(depth, limit int) string {
    if depth < 0 || limit <= 0 {
        return "invalid"
    }
    if depth >= limit {
        return "full"
    }
    return "admit"
}

func main() {
    fmt.Println(admission(0, 1), admission(1, 1), admission(3, 4), admission(-1, 1), admission(0, 0))
}
```

Вывод:

```text
admit full admit invalid invalid
```

Глубина, равная лимиту, — уже `full`: лимит задаёт, сколько задач могут ждать, а не «сколько плюс одна». Нулевой лимит — некорректная конфигурация, а не «очередь без ожидания».

> **Важно.** `full` — состояние снимка, а не действие. Что делать при `full` — ждать, отказать, сбросить — решает политика, записанная рядом с лимитом.

## Четыре ответа на полную очередь

Когда места нет, у вызывающей стороны четыре исхода. Сброс (shed): задачу отбрасывают по приоритету, даже не ставя в очередь, — так защищают критическую работу. Крайний срок (deadline): ждать нечего, потому что у вызывающего не осталось времени или ожидание заведомо его превысит. Отказ (reject): вызывающий не готов ждать вовсе и просит мгновенный ответ. Ожидание (wait): есть и время, и готовность ждать. Порядок проверок важен: сброс раньше оценки ожидания, потому что сбрасываемую задачу бессмысленно ставить в очередь даже на секунду.

```go group=reason mode=run
package main

import "fmt"

func reason(depth, limit, waitMillis, deadlineMillis int, shed bool) string {
    if depth < 0 || limit <= 0 || waitMillis < 0 || deadlineMillis < 0 {
        return "invalid"
    }
    if depth < limit {
        return "admit"
    }
    if shed {
        return "shed"
    }
    if deadlineMillis == 0 || waitMillis >= deadlineMillis {
        return "deadline"
    }
    if waitMillis == 0 {
        return "reject"
    }
    return "wait"
}

func main() {
    fmt.Println(reason(0, 1, 5, 10, false), reason(1, 1, 5, 10, false), reason(1, 1, 5, 5, false))
    fmt.Println(reason(1, 1, 0, 10, false), reason(1, 1, 5, 10, true), reason(1, 1, 11, 10, false))
}
```

Вывод:

```text
admit wait deadline
reject shed deadline
```

Ожидание, равное оставшемуся сроку, — уже `deadline`: пока задача дождётся места, срок истечёт, и работа будет сделана впустую. Нулевой остаток срока — то же самое, независимо от готовности ждать.

> **Типичная ошибка.** Проверять `waitMillis == 0` раньше срока. Вызывающий, не готовый ждать, но с истёкшим сроком, получит `reject` с намёком «повтори позже», хотя повторять уже нечего.

## Отмена важнее допуска

Если вызывающий уже отменил запрос — закрыл соединение, истёк его контекст — любое решение о допуске бессмысленно: работа не нужна никому. Поэтому отмена проверяется сразу после валидности входа, раньше свободного места. Но не раньше валидности: некорректные числа в снимке — ошибка измерения, и её нельзя маскировать словом «отменено».

```go group=decision mode=run
package main

import "fmt"

func decision(depth, limit, waitMillis, deadlineMillis int, cancelled, shed bool) string {
    if depth < 0 || limit <= 0 || waitMillis < 0 || deadlineMillis < 0 {
        return "invalid"
    }
    if cancelled {
        return "cancelled"
    }
    if depth < limit {
        return "admit"
    }
    if shed {
        return "shed"
    }
    if deadlineMillis == 0 || waitMillis >= deadlineMillis {
        return "deadline"
    }
    if waitMillis == 0 {
        return "reject"
    }
    return "wait"
}

func main() {
    fmt.Println(decision(0, 1, 5, 10, true, false), decision(-1, 1, 5, 10, true, false), decision(1, 1, 1, 10, true, false))
    fmt.Println(decision(0, 1, 5, 10, false, false), decision(1, 1, 5, 10, false, true))
}
```

Вывод:

```text
cancelled invalid cancelled
admit shed
```

Отмена при свободном месте всё равно `cancelled`: принять работу, которую никто не ждёт, — тратить ресурс впустую. В настоящем коде это проверка `ctx.Err()` перед постановкой в очередь и ещё раз перед началом выполнения — задача могла быть отменена, пока ждала.

## Что видит вызывающая сторона

Отказ должен быть виден снаружи и наблюдаем внутри. Снаружи — код ответа и подсказка: можно ли повторить, через сколько, какой был лимит. HTTP 429 с `Retry-After` или 503 с тем же заголовком, ошибка gRPC `RESOURCE_EXHAUSTED` — а не 500 и не тихое принятие. Внутри — счётчики по каждому исходу: сколько задач принято, сколько ждали и сколько, сколько сброшено, сколько отказано по сроку. Без этих счётчиков перегрузка выглядит как «иногда медленно».

Повтор отказа — отдельный контракт. Клиент, повторяющий сразу и бесконечно, превращает обратное давление в самоусиление перегрузки; об этом урок о повторах и бюджете. Здесь важно одно: ответ при `full` сообщает, имеет ли повтор смысл.

> **Зачем.** Решение о допуске принимается до того, как задача заняла дорогой ресурс — соединение, память, горутину. Чем раньше точка решения, тем дешевле отказ.

## Лимит и срок: откуда берутся числа

Лимит очереди не выбирают «побольше, чтобы не отказывать». Его выводят из бюджета ёмкости прошлого урока и допустимого времени ожидания: если воркеры завершают сто задач в секунду, а контракт разрешает ждать не дольше двух секунд, в очереди осмысленно держать не больше двухсот задач — всё сверх этого дождётся места уже после истечения срока. Лимит больше — очередь хранит заведомо просроченную работу; лимит меньше — отказы при всплесках, которые система могла бы переварить.

Срок ожидания приходит от вызывающего, а не назначается очередью: у пользовательского запроса он задан контекстом запроса, у фоновой задачи — её расписанием. Очередь лишь сравнивает свою оценку времени ожидания с оставшимся сроком. Оценка — это глубина, делённая на скорость завершения, и она честна только при однородных задачах; для разнородных берут худший реалистичный случай.

Справедливость — отдельный вопрос: при сбросе по приоритету низкоприоритетный класс может не получить обслуживания никогда. Если это недопустимо, политика резервирует ему долю мест, и правило «сброс» применяется только к работе сверх этой доли.

## Практическая процедура

Выпиши для одной очереди: что входит в глубину; лимит и его обоснование (из ёмкости и резерва прошлого урока); ответ при `full` для каждого класса вызывающих — внутренние задачи, пользовательские запросы, фоновые; срок ожидания по умолчанию; как выражается отказ снаружи и какой счётчик растёт внутри. Таблица и есть спецификация политики; код функций — её исполнение.

## Типичные ошибки

- Неограниченная очередь: перегрузка переезжает в память и задержку.
- `full` без политики: что делать — решают по месту, каждый раз по-разному.
- Ожидание без срока или срок, не сравнённый с ожидаемым временем.
- Отказ как 500: клиент не знает, можно ли повторить.
- Отмена проверена после постановки в очередь или не проверена перед выполнением.
- Нет счётчиков по исходам: перегрузка невидима до инцидента.

## Если что-то пошло не так

- `admit` при `depth == limit` → граница: `>=` даёт `full`.
- `reject` при истёкшем сроке → срок проверяется раньше готовности ждать.
- `wait` при `shed = true` → сброс стоит раньше оценки ожидания.
- `cancelled` при отрицательной глубине → валидность проверяется первой.
- `admit` при `cancelled = true` → отмена важнее свободного места.
- `import … is not allowed` → импорты запрещены: сравнения и флаги.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках. Входы — снимок очереди; функции не ждут, не ставят в очередь и не отменяют горутин.

### Задание 1 · Easy: admission limit

**Цель.** `depth < 0` или `limit ≤ 0` → `invalid`; `depth ≥ limit` → `full`; иначе `admit`.

**Ожидаемый вывод** — для `(depth=0, limit=1)`:

```text
"admit"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func Admission(depth int, limit int) string`. Импорты запрещены.
2. Валидность, затем `depth >= limit` → `"full"`, иначе `"admit"`.
3. «Запустить», «Проверить» — закрытые примеры: `(1, 1)` → `full`; `(-1, 1)` и `(0, 0)` → `invalid`; `(0, 2)` → `admit`.

**Как проверить себя.** Равенство глубины и лимита — `full`; это синхронное решение по снимку, ожидание и отмену реализует отдельный код.

**Если не принято.**
- `admit` для `(1, 1)` → строгое `>` вместо `>=`.
- `full` для `(0, 0)` → нулевой лимит — `invalid`.

> **Подсказка.** `full` — не отказ и не ожидание, а состояние; политика — в заданиях 2 и 3.

### Задание 2 · Medium: backpressure и caller deadline

**Цель.** Некорректные входы → `invalid`; есть место → `admit`; при полной очереди: `shed` → `shed`; `deadline ≤ 0` или `wait ≥ deadline` → `deadline`; `wait ≤ 0` → `reject`; иначе `wait`.

**Ожидаемый вывод** — для `(depth=0, limit=1, waitMillis=5, deadlineMillis=10, shed=false)`:

```text
"admit"
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func AdmissionReason(depth int, limit int, waitMillis int, deadlineMillis int, shed bool) string`. Импорты запрещены.
2. Отрицательные числа или `limit <= 0` → `"invalid"`; `depth < limit` → `"admit"`.
3. На полной очереди по порядку: `shed` → `"shed"`; `deadlineMillis == 0 || waitMillis >= deadlineMillis` → `"deadline"`; `waitMillis == 0` → `"reject"`; иначе `"wait"`.
4. «Запустить», «Проверить» — закрытые примеры: `(1,1,5,10)` → `wait`; `(1,1,5,5)` → `deadline`; `(1,1,0,10)` → `reject`; `shed` → `shed`; нулевой срок → `deadline`.

**Как проверить себя.** Ожидание, равное сроку, — `deadline`; сброс проверяется до срока и ожидания; это решение политики, не таймер.

**Если не принято.**
- `reject` для `(1,1,0,0)` → нулевой срок должен дать `deadline` раньше проверки ожидания.
- `wait` при `shed = true` → порядок правил нарушен.

> **Подсказка.** Запиши пять правил в столбик в порядке приоритета — код повторит их построчно.

### Задание 3 · Hard: cancellation и admission policy

**Цель.** Как в задании 2, плюс `cancelled` → `cancelled` сразу после проверки валидности и раньше `admit`.

**Ожидаемый вывод** — для `(depth=0, limit=1, waitMillis=5, deadlineMillis=10, cancelled=false, shed=false)`:

```text
"admit"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func AdmissionDecision(depth int, limit int, waitMillis int, deadlineMillis int, cancelled bool, shed bool) string`. Импорты запрещены.
2. Валидность → `"invalid"`; `cancelled` → `"cancelled"`; дальше правила задания 2.
3. «Запустить», «Проверить» — закрытые примеры: отмена при свободном месте → `cancelled`; отмена при отрицательной глубине → `invalid`; остальные как в задании 2.

**Как проверить себя.** Отмена важнее допуска, но не важнее валидности входа; функция выбирает метку и не управляет таймером, контекстом или горутиной.

**Если не принято.**
- `admit` при `cancelled = true` → отмена проверяется после свободного места.
- `cancelled` при `depth = -1` → валидность должна быть первой.

> **Подсказка.** Единственное отличие от задания 2 — одна проверка на втором месте.

## Итог

- Ограниченная очередь и явное решение на границе возвращают перегрузку туда, где её видно.
- Порядок правил — политика: валидность, отмена, место, сброс, срок, готовность ждать.
- Отказ виден снаружи (код и подсказка о повторе) и считается внутри; ожидание всегда ограничено сроком.
