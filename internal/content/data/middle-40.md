# 40. TaskFlow: acceptance и защита решения

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `middle-39`; предыдущая глава `middle-39`.  
**Планируемый порядок каталога:** 80.  
**Результат:** Собирать версионированный acceptance record из воспроизводимых тестовых артефактов.; Связывать rollback plan и независимое review с конкретной версией артефакта.; Ограничивать выводы по учебным тестам и явно фиксировать остаточные риски.

## Глоссарий

- **acceptance evidence (доказательство приёмки)** — Версионированные результаты тестов, миграций, проверок отказа и ограничений.
- **rollback (откат)** — Проверенная процедура возврата совместимого состояния после неудачного выпуска.
- **residual risk (остаточный риск)** — Известная угроза, которую принятые меры полностью не устраняют.
- **review decision (решение рецензента)** — Отдельная запись решения с автором, временем и связью с проверяемым артефактом.
- **claim boundary (граница утверждения)** — Точная формулировка того, что конкретный тест доказывает и чего не доказывает.

## Теория и границы применения

Acceptance record связывает решение о готовности с конкретной версией продукта и проверяемыми доказательствами. Укажите commit или digest артефакта, Go/toolchain и версии инфраструктуры, миграции, точные команды, exit codes, входы теста, окружение и известные ограничения. Одного счётчика «6 из 8» недостаточно: читатель должен иметь возможность определить, какие именно критерии выполнены и кем измерены.

Разделите критерии на автоматические и требующие оценки человека. Unit/integration tests, миграции, race/failure checks и bounded workload должны ссылаться на реальные результаты. Рубрика архитектурного review должна содержать вопросы, требуемые артефакты, допустимые ответы, критические блокеры и критерий решения. Запись reviewer decision связывается с этой версией артефакта и сохраняет reviewer identity/время в доверенном контексте; параметр `reviewerApproved bool` из функции не является независимым подтверждением.

Используйте состояния с ясным порядком: некорректная спецификация → invalid; открытый критический риск → hold; обязательный критерий без доказательства → incomplete; только после проверки всех обязательных пунктов можно передавать результат на review. «Ready for review» не равно «выпуск разрешён». Решение о выпуске учитывает совместимость миграций, наблюдаемость, owner дежурства и возможность остановки, но не должно маскировать известный риск арифметикой баллов.

Rollback plan описывает триггер отката, владельца, точную процедуру, совместимость схемы и способ убедиться, что система восстановилась. Для destructive миграции может не существовать безопасного обратного SQL: тогда планом бывает forward fix и восстановление из проверенной резервной копии. Само наличие текстового файла не доказывает, что восстановление когда-либо репетировали. Отдельно запишите условия, когда rollout приостанавливается и кто может продолжить его.

Review должен зафиксировать принятие, отказ или запрос изменений, конкретную причину, оставшиеся риски и требуемое следующее действие. Расхождение reviewer не стирается флагом: сохраните разные аргументы и владельца разрешения. Учебный отчёт оценивает качество инженерных доказательств и не подтверждает должность, аккредитацию или production readiness без соответствующей независимой проверки.

`EvidenceCount`, `AcceptanceStatus` и `ReleaseDecision` проверяют арифметику и приоритет на заданных входах. Они не читают acceptance record и не знают, существовали ли артефакты или человеческое решение. Эта глава формулирует желаемый пакет evidence; реальное присвоение ранга требует отдельной серверной интеграции, версии рубрики, сохранённого артефакта и ручного review там, где критерий субъективен.

Сделайте acceptance record читаемым без устного объяснения автора. Каждая строка критерия должна содержать идентификатор, требуемое свидетельство, путь к сохранённому выводу, pass/fail/unknown и причину. Храните незаполненные пункты как unknown, не превращая их в ноль или pass. Если команда не запускалась из-за отсутствующей инфраструктуры, это явный блокер, а не отрицательный результат теста. Для ручной рубрики запишите вопросы, наблюдаемые признаки ответа и оценку reviewer; для спорного критерия оставьте комментарий и требуемое исправление. Свяжите snapshot артефакта и ревью так, чтобы последующий commit не наследовал одобрение старой версии. Повторная приёмка после существенного изменения запускает затронутые проверки заново. Для rollback заранее проверьте права доступа, владельца процедуры, совместимость формата данных и критерий возвращения readiness. Если rollback рискован или невозможен, остановите продвижение и согласуйте forward recovery. Эти правила позволяют отличить административную отметку от реальных оснований для решения.

## Три самостоятельных запускаемых примера

### Пример 1: `EvidenceCount`

Контракт: Отрицательные значения→0; passed не может превысить required; иначе вернуть passed.

```go
package main

import "fmt"

func EvidenceCount(required, passed int) int {
	if required < 0 || passed < 0 { return 0 }; if passed > required { return required }; return passed
}

func main() {
	fmt.Println(EvidenceCount(8, 6))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `AcceptanceStatus`

Контракт: Плохие счётчики→invalid; критический риск→hold_risk; незакрытые требования→incomplete; иначе ready_for_review.

```go
package main

import "fmt"

func AcceptanceStatus(required, passed int, openCriticalRisk bool) string {
	if required <= 0 || passed < 0 || passed > required { return "invalid" }; if openCriticalRisk { return "hold_risk" }; if passed < required { return "incomplete" }; return "ready_for_review"
}

func main() {
	fmt.Println(AcceptanceStatus(8, 8, false))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `ReleaseDecision`

Контракт: true только если acceptance, rollback plan и отдельное reviewer approval подтверждены.

```go
package main

import "fmt"

func ReleaseDecision(acceptancePassed, rollbackReady, reviewerApproved bool) bool {
	return acceptancePassed && rollbackReady && reviewerApproved
}

func main() {
	fmt.Println(ReleaseDecision(true, true, true))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

## Лабораторная карточка TaskFlow: TaskFlow: acceptance и защита решения

Определите конкретный сценарий с одной пользовательской операцией. Укажите principal, объект, tenant, действие и ожидаемое состояние. Перечислите trust boundary (границу доверия), где вход считается недоверенным, где аутентификация проверена, и какой сервис принимает окончательное решение. Затем перечислите наблюдения: ответ HTTP, доменное событие, запись данных, лог и trace. Если одно из наблюдений отсутствует или запаздывает, результат должен оставаться неопределённым, а не автоматически считаться успешным.

До запуска теста зафиксируйте начальное состояние и независимые данные для двух владельцев. Включите положительный случай и минимум две отрицательные комбинации: неверный tenant, неверная роль, отменённый context, истёкший deadline, закрытие сервера или повторное событие — выберите те, которые относятся к теме главы. Подтвердите, что отрицательный сценарий не меняет данные и не пишет секрет в лог. Если чистый helper не может показать этот эффект, обозначьте интеграционную проверку как отдельное обязательное доказательство.

Наблюдение следует отделить от интерпретации. «Ответ вернул 404» — факт теста; «IDOR невозможен» — слишком сильный вывод. Чтобы обосновать более узкое утверждение, проверьте конкретный endpoint с authenticated principal, запустите запрос с чужим ID и подтвердите отсутствие утечки тела и побочного изменения. Аналогично, один `go test -race` на небольшой набор не гарантирует отсутствия data race при другой последовательности. Укажите точные пути, которые тест фактически исполнил.

Для operational readiness перечислите владельцев процедур: кто меняет readiness, кто наблюдает drain, кто смотрит saturation, кто останавливает нагрузочный тест и кто принимает rollback решение. Пороговые значения должны быть определены владельцами проекта и измерены на сопоставимой среде. Эта программа не задаёт production SLA. Если у учебной системы пока нет измеренных данных, запишите только ожидаемые проверки и назовите статус как непроверенный.

Для failure case определите инъекцию только в тестовой среде и ограничьте воздействие числом запросов, временем либо тестовой очередью. До старта проверьте cleanup и состояние ресурса. После эксперимента подтвердите, что соединения закрыты, временные записи очищены и service вернулся к ready только после проверки обязательной зависимости. При неожиданном результате немедленно прекратите эксперимент и сохраните логи с очищенными секретами. Не расширяйте нагрузку, пока не объяснили расхождение и не повторили исходный контрольный прогон.

На review передайте короткую карточку: код/commit, версия Go, команда, входные vectors, результат каждого теста, окружение, риски и пробелы. Попросите рецензента указать альтернативное объяснение результата. Если независимый читатель трактует сообщение сильнее, чем измерения, уточните claim. Назначьте конкретное следующее действие только при ясной проверке завершения; общие призывы «улучшить мониторинг» не являются завершённым пунктом.
