# TaskFlow: acceptance и защита решения

## Что ты сделаешь

Ты напишешь три проверки финального шага TaskFlow: подсчёт подтверждённых признаков приёмки, статус приёмки с приоритетом риска и решение о выпуске из трёх условий. Функции получают числа и флаги и возвращают ответ. Они не запускают тесты, не читают отчёты и не решают, достаточно ли аргументов для защиты. Эти вопросы решают люди на ревью, а функции показывают только то, что записано в вход.

## Что входит в release evidence

Приёмка — это не одно зелёное значение. Для выпуска TaskFlow нужен набор артефактов, и каждый из них привязан к конкретной версии кода. Модульные тесты дают результат прогона с номером коммита. Детектор гонок дает отчёт по нагрузочному пути. Тест отказа фиксирует ожидаемое поведение при сбое зависимости. Отчёт нагрузки содержит параметры и распределение времени ответа. План отката описывает шаги и проверен на стенде. Отдельный reviewer оставляет запись о согласии или несогласии.

Версионирование здесь главное. Артефакт без версии нельзя связать с релизом: через неделю неясно, проверялся ли именно этот код. Поэтому каждая строка приёмки содержит имя артефакта и версию, а пустая версия означает, что артефакт не засчитан, даже если файл существует.

Пример 2 показывает такую запись: имя и версия соединяются в одну строку, а отсутствие версии отмечается явно.

```go
package main

import "fmt"

type record struct {
	artifact string
	version  string
}

func stamp(r record) string {
	if r.version == "" {
		return r.artifact + ": unversioned"
	}
	return r.artifact + "@" + r.version
}

func main() {
	fmt.Println(stamp(record{"load-report", "v1.4.0"}))
	fmt.Println(stamp(record{"rollback-plan", ""}))
}
```

Вывод: `load-report@v1.4.0` и `rollback-plan: unversioned`. Вторая строка не ломает отчёт: она просто показывает, что план отката не привязан к версии и не может быть засчитан.

## Подсчёт признаков

Пример 1 показывает подсчёт подтверждённых признаков. Каждый артефакт имеет поле `ok`, и итог считается по нему. Такой подсчёт прост, но важно, что он не превращает неизвестное в подтверждённое: элемент без результата считается непройденным.

```go
package main

import "fmt"

type evidence struct {
	name string
	ok   bool
}

func countPassed(items []evidence) int {
	n := 0
	for _, e := range items {
		if e.ok {
			n++
		}
	}
	return n
}

func main() {
	items := []evidence{
		{"unit", true},
		{"race", true},
		{"rollback drill", false},
	}
	fmt.Printf("%d of %d passed\n", countPassed(items), len(items))
}
```

Вывод: `2 of 3 passed`. Итог «2 из 3» сам по себе не решает судьбу релиза, но он честно показывает, что одна проверка не пройдена. Решение о выпуске принимается по статусу приёмки, а не по доле зелёных пунктов.

Функция `EvidenceCount` из задания Easy устроена похоже, но с ограничением: число подтверждённых признаков не может превышать требуемое, а отрицательные значения считаются ошибкой и дают ноль.

## Статус приёмки и приоритет риска

Статус приёмки выбирается по порядку. Сначала проверяется корректность счётчиков: требуемое число положительно, подтверждённое не отрицательно и не больше требуемого. Некорректные данные не могут дать ни один из статусов. Затем открытый критический риск останавливает релиз, даже если все требования подтверждены. Последним проверяется полнота: незакрытые требования дают `incomplete`, а полностью закрытый набор без риска даёт `ready_for_review`.

Порядок важен потому, что статус `ready_for_review` не означает «можно выпускать». Он означает, что пакет готов к ревью человеком. Выпуск решается отдельно, и это видно в функции решения ниже. Статус `hold_risk` стоит выше статуса `incomplete` намеренно: если критический риск открыт, незакрытые требования уже не главная проблема, и команда должна заниматься риском, а не списком галочек.

## Защита архитектурного решения

Защита решения перед reviewer — это не спор о том, кто прав. Цель — показать, какие варианты рассматривались, почему выбран этот, какие ограничения он принимает и что не проверено. Хорошая защита называет цену: например, что отложенная очередь даёт задержку публикации, а синхронная запись увеличивает время ответа и нагрузку на базу.

Защита должна честно перечислять остаточные риски. Остаточный риск — то, что осталось после всех мер и о чём известно. Он записывается с владельцем и сроком пересмотра. Фраза «рисков нет» почти всегда означает, что риски не искали, и на ревью её не принимают.

## Фиксация несогласия

Reviewer может не согласиться. Такое несогласие фиксируют как отдельную запись с именем, статусом и владельцем. Статусы простые: принято (изменение внесено), отклонено (с обоснованием), отложено (с датой возврата). Несогласие без владельца не закрыто и не отложено: о нём просто забыли. Владелец нужен даже для отклонённого несогласия, потому что кто-то должен подтвердить обоснование и поставить подпись. Если возражение касается сразу нескольких решений, каждое получает собственную строку: так видно, какие из них приняты, а какие нет, и защита не превращается в общий спор.

Пример 3 показывает такую запись. Если владелец не назначен, строка явно говорит, что несогласие не зафиксировано, а не молча исчезает из отчёта.

```go
package main

import "fmt"

type objection struct {
	reviewer string
	status   string
	owner    string
}

func describe(o objection) string {
	if o.owner == "" {
		return o.reviewer + ": not recorded, no owner"
	}
	return fmt.Sprintf("%s: %s, owner %s", o.reviewer, o.status, o.owner)
}

func main() {
	fmt.Println(describe(objection{"reviewer A", "deferred", "team lead"}))
	fmt.Println(describe(objection{"reviewer B", "", ""}))
}
```

Вывод: `reviewer A: deferred, owner team lead` и `reviewer B: not recorded, no owner`. Вторая строка — не ошибка программы, а сигнал: ревью нельзя закрывать, пока такие строки есть.

## Решение о выпуске

Выпуск требует трёх условий: приёмка пройдена, план отката готов и отдельный reviewer подтвердил пакет. Отдельный reviewer означает человека, который не писал изменение. Подтверждение автора собственной работы не считается. Если хотя бы одно условие не выполнено, решение отрицательное.

Функция из задания Hard собирает эти три флага логическим «и». Она ничего не проверяет сама: флаги приходят из процесса приёмки. Поэтому её результат отражает записанные факты и не заменяет ни тесты, ни ревью. Если в процессе появляется четвёртое условие, например согласование с безопасностью, его добавляют в функцию и в описание процесса одновременно. Иначе решение и процедура разойдутся, и через месяц никто не вспомнит, почему выпуск прошёл без нужной подписи.

## Что сказать в защите

Защита заканчивается перечнем того, что доказано и что не доказано. Полезно заранее подготовить короткий ответ на вопрос «что изменится, если предположение окажется неверным». Если ответ требует переделки архитектуры, это тоже стоит назвать: reviewer должен понимать, какую цену несёт решение при ошибке в допущении. Доказано то, что прошло в стенде с версией кода. Не доказано то, что не запускалось: продакшен-нагрузка, реальная база с другими данными, отказ сети между регионами. Учебные тесты этой главы проверяют логику функций, а не систему в целом, и это нужно написать явно, а не надеяться, что reviewer поймёт сам.

## Типичные ошибки и исправление

> **Типичная ошибка.** Выдавать ответ функции за доказательство качества. Функция проверяет переданные флаги, но не то, как они были получены.

Ошибки на этом этапе связаны с потерей контекста. Чаще всего они появляются перед самым выпуском, когда все торопятся и каждый надеется, что другой проверил деталь. Артефакт приложен без версии. Статус «ready_for_review» принимают за разрешение выпустить. Несогласие reviewer пропадает из отчёта. Остаточные риски не записаны, поэтому защита звучит уверенно, но не честно.

## Если что-то пошло не так

- Приёмка зелёная, а релиз всё равно нельзя выпускать → не записан план отката или нет независимого reviewer; проверь все три условия.
- Отчёт нагрузки нельзя связать с версией кода → артефакт без версии; пересними прогон с номером коммита.
- Reviewer не согласился, и это нигде не записано → создай запись с владельцем и статусом до защиты.
- Защита обещает отсутствие гонок → признак гонок проверяет детектор на пройденных путях; сформулируй вывод осторожнее.

## Практика

Эти задания проверяют только логику решений. Они не читают отчёты, не запускают тесты и не принимают решение о выпуске. Закрытые примеры видны только в «Проверить».

### Задание 1 · Easy: taskflow: acceptance и защита решения — базовое правило

**Цель.** Реализуй `EvidenceCount(required, passed int) int`. Отрицательное требуемое или подтверждённое число даёт `0`. Подтверждённых признаков не может быть больше требуемых: в этом случае верни требуемое число. Иначе верни подтверждённое число.

**Ожидаемый вывод** — вход: требуется 8, подтверждено 6:

```text
6
```

**Шаги.**
1. Выбери задание «Easy: taskflow: acceptance и защита решения — базовое правило»: в файле есть `EvidenceCount` с `panic("TODO")`. Импорты не нужны.
2. Проверь отрицательные значения и верни `0`.
3. Если подтверждено больше требуемого, верни требуемое число.
4. Иначе верни подтверждённое число.
5. Нажми «Запустить» и сравни вывод с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Вывод — `6` без кавычек; семь проверочных случаев совпадают с контрактом, включая ноль требуемых и подтверждённых признаков.

**Если не принято.**
- `9` вместо `8` при избытке подтверждённых → ограничение сверху не применено.
- `6` вместо `0` при отрицательном требуемом → проверка знака пропущена.
- `1` при нуле требуемых и одном подтверждённом → ограничение сверху не применено.

> **Подсказка.** Сначала знак, потом сравнение с требуемым, потом возврат подтверждённого числа.

### Задание 2 · Medium: taskflow: acceptance и защита решения — граничная политика

**Цель.** Реализуй `AcceptanceStatus(required, passed int, openCriticalRisk bool) string`. Некорректные счётчики дают `"invalid"`: требуемое число не положительно, подтверждённое отрицательно или больше требуемого. Открытый критический риск даёт `"hold_risk"`. Незакрытые требования дают `"incomplete"`. Иначе верни `"ready_for_review"`.

**Ожидаемый вывод** — вход: все восемь требований подтверждены, критического риска нет:

```text
"ready_for_review"
```

**Шаги.**
1. Выбери задание «Medium: taskflow: acceptance и защита решения — граничная политика»: в файле есть `AcceptanceStatus` с `panic("TODO")`.
2. Проверь корректность счётчиков и верни `"invalid"`, если она нарушена.
3. Проверь открытый критический риск и верни `"hold_risk"`.
4. Проверь полноту и верни `"incomplete"`, если подтверждено меньше требуемого.
5. Иначе верни `"ready_for_review"`.
6. Нажми «Запустить» и сравни вывод с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Вывод — одна строка в кавычках; восемь проверочных случаев совпадают с контрактом, включая риск при неполном наборе.

**Если не принято.**
- `"ready_for_review"` при открытом риске → проверка риска стоит после проверки полноты.
- `"incomplete"` при восьми из восьми → сравнение с требуемым записано строго.
- `"ready_for_review"` при нулевом требуемом → проверка положительности требуемого пропущена.

> **Подсказка.** Порядок такой же, как в тексте: корректность, риск, полнота, остальное. Меняя его, меняешь смысл статуса.

## Итог

- Release evidence версионируется: каждый артефакт привязан к коммиту, а артефакт без версии не засчитывается, даже если файл существует.
- Открытый критический риск удерживает релиз, а решение о выпуске требует трёх условий: приёмки, плана отката и отдельного подтверждения reviewer.
- Защита называет цену решения, остаточные риски и то, что не проверено; учебные тесты показывают логику функций и не доказывают качество системы.
