# pprof: гипотеза, изменение и повтор

## Что ты сделаешь

Ты замкнёшь цикл, начатый в первом уроке модуля: наблюдение в профиле → проверяемая гипотеза → одно изменение → повторный профиль и benchmark на неизменном стенде → честный вывод, в том числе отрицательный. Три функции урока — `ProfileDelta`, `SameProfileWindow`, `OptimizationEvidence` — это арифметика и правила сопоставления двух профилей и двух прогонов benchmark, без которых сравнение «до» и «после» превращается в рассказ.

## Наблюдение — ещё не гипотеза

«Доля CPU у `parse` велика» — наблюдение. «Каждый запрос заново разбирает неизменный шаблон, поэтому кеширование разобранного шаблона сократит вызовы `parse`, а `ns/op` обработчика снизится; риск — рост удерживаемой памяти на размер кеша» — гипотеза (hypothesis): у неё есть причина, прогноз на выигрывающий показатель, прогноз на риск и наблюдение, которое её опровергнет. Запиши все четыре пункта до правки.

```go group=card mode=run
package main

import "fmt"

type hypothesis struct {
    observation string
    cause       string
    prediction  string
    risk        string
    refutedBy   string
}

func (h hypothesis) complete() bool {
    return h.observation != "" && h.cause != "" && h.prediction != "" && h.risk != "" && h.refutedBy != ""
}

func main() {
    h := hypothesis{
        observation: "parse — 25 % flat samples под нагрузкой read-heavy",
        cause:       "шаблон разбирается на каждом запросе",
        prediction:  "flat parse < 5 %, ns/op обработчика ниже",
        risk:        "inuse_space растёт на размер кеша",
        refutedBy:   "flat parse не снизился или ns/op не изменился",
    }
    fmt.Println("гипотеза полная:", h.complete())
    fmt.Println("опровергнет:", h.refutedBy)
}
```

Вывод:

```text
гипотеза полная: true
опровергнет: flat parse не снизился или ns/op не изменился
```

Прогноз на риск нужен не меньше прогноза на выигрыш: без него изменение примут только потому, что один график стал красивее.

> **Важно.** Если ты не можешь назвать результат, который опровергнет гипотезу, это не гипотеза, а намерение что-то переписать.

## Артефакты «до» неприкосновенны

Сохрани байты профиля, бинарник, которым он собран, revision и команду. Символизация должна указывать на ту версию исходников, с которой снят профиль, иначе `pprof` покажет не те строки. Профиль «до» — неизменяемый артефакт: не перезаписывай его результатом «после» под тем же именем. После правки собери профиль той же командой, того же типа, под той же нагрузкой и сравни через `go tool pprof -base до.out после.out`: разность профилей (profile diff) покажет, какие стеки изменились. Но и она зависит от сопоставимости прогонов: разные окна сбора или разная нагрузка дают разность, в которой нет смысла.

```go group=window mode=run
package main

import "fmt"

func sameWindow(beforeSeconds, afterSeconds int, sameWorkload bool) bool {
    return beforeSeconds > 0 && beforeSeconds == afterSeconds && sameWorkload
}

func delta(before, after int64) int64 { return before - after }

func main() {
    fmt.Println("окна сопоставимы:", sameWindow(30, 30, true), sameWindow(30, 60, true), sameWindow(30, 30, false))
    fmt.Println("изменение flat samples:", delta(100, 75), delta(75, 100), delta(10, 10))
}
```

Вывод:

```text
окна сопоставимы: true false false
изменение flat samples: 25 -25 0
```

Положительная разность означает, что сэмплов стало меньше. Но равная длительность окон не гарантирует равного числа событий: если во втором окне нагрузка была вдвое меньше, сэмплов тоже будет меньше без всякой оптимизации. Сопоставимость проверяют по нагрузке, среде, сборке и настройкам сэмплирования — флаг `sameWorkload` в функции лишь напоминает об этом.

> **Типичная ошибка.** Сравнить профиль, снятый за 30 секунд прогрева, с профилем за 30 секунд установившейся нагрузки. Окна равны, события — нет.

## Одно изменение за раз

Несколько независимых правок делают атрибуцию невозможной: выигрыш (или проигрыш) нельзя приписать ни одной из них. Меняй одну причину, повторяй сбор, записывай. После каждого шага проверяй, не переехала ли работа на другой ресурс: меньше сэмплов CPU при росте аллокаций или блокировок; пул горутин убрал накладные расходы на запуск, но добавил очередь и ожидание; предвычисление снизило цену запроса, но увеличило стартовую задержку и heap. Назови конкретный компромисс и объясни, почему для твоего требования он приемлем.

Профиль локализует, benchmark измеряет: это два разных наблюдения, и подтверждение нужно от обоих. Снижение `flat` у функции при неизменном `ns/op` пути означает, что дорогая часть переместилась или доля функции была мала.

```go group=evidence mode=run
package main

import "fmt"

func evidence(beforeFlat, afterFlat, beforeNs, afterNs int64) string {
    if beforeFlat < 0 || afterFlat < 0 || beforeNs <= 0 || afterNs <= 0 {
        return "invalid"
    }
    if afterFlat < beforeFlat && afterNs < beforeNs {
        return "consistent_candidate"
    }
    if afterFlat > beforeFlat || afterNs > beforeNs {
        return "conflicting_signals"
    }
    return "no_change"
}

func main() {
    fmt.Println(evidence(60, 40, 100, 90))
    fmt.Println(evidence(60, 40, 110, 120))
    fmt.Println(evidence(60, 60, 100, 100))
}
```

Вывод:

```text
consistent_candidate
conflicting_signals
no_change
```

`consistent_candidate` — оба сигнала согласны, можно переходить к повторам и проверке корректности; `conflicting_signals` — профиль и benchmark разошлись, и это самый информативный исход: работа переехала, или гипотеза была о не том пути.

## Закон Амдала: почему маленькая доля не ускоряет путь

Если функция занимает 25 % пути и ты ускорил её вдвое, путь ускорится лишь примерно в 1,14 раза; если бесконечно — не более чем в 1,33. Закон Амдала (Amdahl) ограничивает выигрыш всего пути долей, которую удалось ускорить. Это модель для рассуждения: при меняющейся нагрузке и конкуренции доли плавают, и точного прогноза она не даёт. Но она объясняет, почему верно локализованная дорогая функция иногда не меняет полное время: её доля мала относительно пользовательского сценария, который ты на самом деле измеряешь.

> **Зачем.** Прежде чем оптимизировать функцию с долей 3 %, посчитай потолок: даже исчезнув целиком, она ускорит путь на три процента, что часто меньше размаха повторов.

## Отрицательный результат — тоже результат

Если после правки профиль не показывает ожидаемого движения, не выбирай удобный участок постфактум и не объявляй успех по другому показателю. Пересмотри гипотезу: профиль был не под тот путь; узкое место сместилось; доля слишком мала; измерение слишком шумное. Запиши исход: «гипотеза не подтвердилась», «стоимость переместилась», «разброс превышал эффект». Это предотвращает повторение той же идеи через месяц и делает ход мысли проверяемым. Для P4 неудачные попытки фиксируются, если они чему-то учат и не маскируют результат; финальный отчёт должен позволить рецензенту повторить процесс и увидеть, где кончается свидетельство и начинается интерпретация.

## Что записать в журнал эксперимента

Одна запись — один цикл: дата и revision; команда сбора профиля и команда benchmark с флагами; гипотеза из четырёх пунктов; что именно изменено, одним предложением; имена артефактов «до» и «после»; итог сравнения через `-base` в двух-трёх строках; медианы и размахи benchmark; классификация исхода; следующий шаг. Такой журнал читается за минуту, и по нему другой инженер повторит эксперимент, не спрашивая автора. Если записей несколько, нумеруй циклы: ссылка «см. цикл 3» короче пересказа и не теряет деталей.

Записывай числа с единицами и долями, а не прилагательными: «flat parse 25 % → 4 % при 3 100 сэмплах; медиана ns/op 612 → 540, размах 20 → 23» говорит больше, чем «стало заметно быстрее». Если какой-то пункт пуст — например, нет прогноза на риск, — это сигнал, что цикл не завершён, а не повод пропустить строку.

Перед тем как закрыть цикл, перечитай первую запись: гипотеза, записанная до правки, и вывод, записанный после, должны говорить об одном и том же показателе. Если показатель незаметно сменился, цикл не завершён, а подменён.

## Типичные ошибки

- Гипотеза без опровергающего наблюдения: любое число будет «подтверждением».
- Профиль «до» перезаписан профилем «после»: сравнивать не с чем.
- Разные окна, нагрузка или сборка у двух профилей: разность не имеет смысла.
- Несколько правок в одном шаге: выигрыш не атрибутирован.
- Успех по профилю без benchmark или наоборот: нужны оба сигнала.
- Оптимизация функции с долей в три процента: потолок выигрыша меньше шума.

## Если что-то пошло не так

- `-25` вместо `25` → порядок вычитания: нужно `before - after`.
- `true` для разных окон → условие сравнивает только знак, а нужно равенство длительностей.
- `true` при нулевых окнах → проверка `beforeSeconds > 0` отсутствует.
- `no_change` при ухудшении одной метрики → ветка `conflicting_signals` проверяет только одну метрику; нужны обе через `||`.
- `consistent_candidate` при `afterNs = 0` → диапазоны не проверены: время должно быть строго положительным.

## Практика

Три функции без `main` и печати; среда показывает результаты числами, `bool` и строками в кавычках. Никакая из них не читает профили: это правила сравнения над учебными числами.

### Задание 1 · Easy: вычисли изменение flat samples

**Цель.** Вернуть `before − after` для счётчика одного и того же типа сэмплов на сопоставимых профилях.

**Ожидаемый вывод** — для `(before=100, after=75)`:

```text
25
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func ProfileDelta(before, after int64) int64`. Импорты запрещены.
2. Верни `before - after`.
3. «Запустить», «Проверить» — закрытые примеры: `(75, 100)` → `-25`, `(10, 10)` → `0`.

**Как проверить себя.** Положительное число — сэмплов стало меньше; ноль — изменений нет; знак сохраняется, модуль не берётся.

**Если не принято.**
- Знак перевёрнут → вычитание в другом порядке.
- Всегда неотрицательно → взят модуль; знак — часть контракта.

> **Подсказка.** Одна строка; вся сложность задания — в предусловиях, которые функция не проверяет: одинаковый тип сэмплов и одинаковая нагрузка.

### Задание 2 · Medium: проверь сопоставимость profile pair

**Цель.** Вернуть `true`, если оба окна сбора одинаковой положительной длительности и нагрузка помечена одинаковой.

**Ожидаемый вывод** — для `(30, 30, true)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func SameProfileWindow(beforeSeconds, afterSeconds int, sameWorkload bool) bool`. Импорты запрещены.
2. Верни `beforeSeconds > 0 && beforeSeconds == afterSeconds && sameWorkload`.
3. «Запустить», «Проверить» — закрытые примеры: `(30, 60, true)` → `false`, `(30, 30, false)` → `false`.

**Как проверить себя.** Равная длительность не означает равного числа событий — функция проверяет форму пары, а не настоящую сопоставимость нагрузки, среды и сборки.

**Если не принято.**
- `true` для `(30, 60, true)` → окна должны быть равны, а не просто положительны.
- `true` для `(0, 0, true)` → нужна строгая положительность.

> **Подсказка.** Три условия через `&&`; второе — равенство, не `<=`.

### Задание 3 · Hard: сопоставь профиль и benchmark

**Цель.** По `flat` «до/после» и `ns/op` «до/после» вернуть `invalid`, `consistent_candidate`, `conflicting_signals` или `no_change`.

**Ожидаемый вывод** — для `(beforeFlat=60, afterFlat=40, beforeNs=100, afterNs=90)`:

```text
"consistent_candidate"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func OptimizationEvidence(beforeFlat, afterFlat, beforeNs, afterNs int64) string`. Импорты запрещены.
2. Первой проверкой: `flat < 0` или `ns <= 0` у любой стороны → `"invalid"`.
3. Оба снизились (`afterFlat < beforeFlat && afterNs < beforeNs`) → `"consistent_candidate"`.
4. Хотя бы одно выросло (`afterFlat > beforeFlat || afterNs > beforeNs`) → `"conflicting_signals"`.
5. Иначе → `"no_change"`. «Запустить», «Проверить» — закрытые примеры: flat упал, время выросло → `conflicting_signals`; flat вырос, время упало → `conflicting_signals`; нулевое время → `invalid`.

**Как проверить себя.** Равные числа по обеим метрикам — `no_change`; улучшение по одной и неизменность по другой — тоже `no_change` (не кандидат и не конфликт); любое ухудшение — конфликт.

**Если не принято.**
- `consistent_candidate` при равном времени → во втором правиле нужны строгие `<` по обеим метрикам.
- `no_change` при росте одной метрики → в третьем правиле `&&` вместо `||`.
- `invalid` не срабатывает для `beforeNs = 0` → время проверяется как `<= 0`, не `< 0`.

> **Подсказка.** Порядок правил: валидность → согласие обоих сигналов → любое ухудшение → остальное.

## Итог

- Гипотеза — причина, прогноз на выигрыш, прогноз на риск и опровергающее наблюдение, записанные до правки.
- Профиль «до» неприкосновенен; сравнение через `-base` имеет смысл только при одинаковых окне, нагрузке и сборке.
- Одно изменение за раз, два сигнала — профиль и benchmark; отрицательный результат записывается, а не прячется.
