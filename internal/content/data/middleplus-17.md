# 17. Outbox, атомарность записи и публикация

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-16`
**Цель:** Transactional outbox (транзакционный исходящий журнал) записывает бизнес-изменение и намерение отправить событие в одной транзакции базы. Отдельный publisher (издатель) может повторно прочесть запись после сбоя. Это закрывает окно «изменение committed, событие потеряно», но не обеспечивает exactly-once обработку; повторная публикация и идемпотентный consumer остаются частью контракта.

## Термины и перевод

- **Transactional outbox** — паттерн, сохраняющий доменное изменение и запись о намерении публикации в одной транзакции.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Проблема outbox возникает, когда приложение меняет данные в базе и должно опубликовать соответствующее событие. Если сначала зафиксировать изменение, а затем процесс упадёт до публикации, событие потеряется. Если публиковать первым, а транзакция базы откатится, потребитель увидит событие о несуществующем изменении.

Транзакционный outbox записывает бизнес-изменение и намерение публикации в одной транзакции базы. Отдельный publisher (издатель) читает ожидающие записи и отправляет их брокеру. Это закрывает именно разрыв между commit изменения и сохранением намерения отправить событие. Публикация в брокер и commit базы при этом не становятся одной транзакцией; publisher может отправить повторно.

Поэтому контракт потребителя тоже важен: если эффект выполнен, но ack (подтверждение) потерялось, сообщение может прийти снова. Идемпотентная обработка или дедупликация должны учитывать устойчивый идентификатор. Учебные функции проверяют описанное состояние и порядок шагов, но не подключены ни к базе, ни к брокеру.

## Три запускаемых примера

### Пример 1: обычный путь

```go
package main

import "fmt"

func OutboxTransition(state string, event string) string {
	if state == "absent" && event == "persist" { return "pending" }; if state == "absent" && event == "rollback" { return "absent" }; if state == "pending" && event == "publish" { return "delivered" }; if state == "pending" && event == "crash" { return "pending" }; if state == "delivered" && event == "ack" { return "acked" }; if state == "delivered" && event == "crash" { return "pending" }; if state == "acked" && event == "publish" { return "acked" }; return "invalid"
}

func main() { fmt.Println(OutboxTransition("delivered", "crash")) }
```

Скомпилируйте сохранённый блок как `go run main.go`. Значения — фиксированные учебные входы; результат не измеряет внешнюю систему. Измените один аргумент на граничный и объясните, какая ветка меняется.

### Пример 2: решение с несколькими сигналами

```go
package main

import "fmt"

func OutboxAttempt(state string, event string, attempts int, maxAttempts int) string {
	if attempts < 0 || maxAttempts <= 0 || attempts > maxAttempts { return "invalid" }; if state == "pending" && event == "publish" { if attempts >= maxAttempts { return "dead_letter" }; return "delivered" }; if (state == "pending" && event == "retry") || (state == "delivered" && event == "crash") { if attempts >= maxAttempts { return "dead_letter" }; return "pending" }; return OutboxTransition(state,event)
}

func OutboxTransition(state string, event string) string {
	if state == "absent" && event == "persist" { return "pending" }; if state == "absent" && event == "rollback" { return "absent" }; if state == "pending" && event == "publish" { return "delivered" }; if state == "pending" && event == "crash" { return "pending" }; if state == "delivered" && event == "ack" { return "acked" }; if state == "delivered" && event == "crash" { return "pending" }; if state == "acked" && event == "publish" { return "acked" }; return "invalid"
}

func main() { fmt.Println(OutboxAttempt("pending", "retry", 3, 3)) }
```

### Пример 3: проверка ограниченного инварианта

```go
package main

import "fmt"

func OutboxRecovery(state string, event string, attempts int, maxAttempts int, effectApplied bool) string {
	if attempts < 0 || maxAttempts <= 0 || attempts > maxAttempts { return "invalid" }; if state == "delivered" && event == "crash" { if effectApplied { return "deduplicate" }; if attempts >= maxAttempts { return "dead_letter" }; return "retry_publish" }; if state == "acked" && event == "publish" { return "deduplicate" }; if state == "pending" && event == "publish" { if attempts >= maxAttempts { return "dead_letter" }; return "delivered" }; if (state == "pending" && event == "retry") || (state == "delivered" && event == "crash") { if attempts >= maxAttempts { return "dead_letter" }; return "pending" }; return OutboxTransition(state,event)
}

func OutboxTransition(state string, event string) string {
	if state == "absent" && event == "persist" { return "pending" }; if state == "absent" && event == "rollback" { return "absent" }; if state == "pending" && event == "publish" { return "delivered" }; if state == "pending" && event == "crash" { return "pending" }; if state == "delivered" && event == "ack" { return "acked" }; if state == "delivered" && event == "crash" { return "pending" }; if state == "acked" && event == "publish" { return "acked" }; return "invalid"
}

func main() { fmt.Println(OutboxRecovery("delivered", "crash", 1, 3, true)) }
```

## Практическая процедура

Нарисуйте две независимые стороны: транзакцию базы и доставку брокеру. Отметьте точки сбоя до commit, после commit и после публикации, но до отметки outbox как отправленного. Для каждой точки укажите, что можно восстановить из сохранённого состояния и какая операция может повториться.

Затем задайте поля модели: изменение зафиксировано, outbox-запись сохранена, публикация наблюдалась, статус записи обновлён, потребитель применил эффект, ack принят. Не объединяйте «опубликовано» и «обработано». Проверьте очередность условий примерами урока и объясните, какие поля отсутствуют в упрощённой модели.

Для реальной реализации понадобились бы транзакционные тесты с аварийным завершением на каждой границе, проверка повторной доставки и стратегия дедупликации. Helper подтверждает только логику заданного вектора; он не доказывает атомарность базы или брокера и не предоставляет exactly-once семантику.

## Разбор сценария: Outbox, атомарность записи и публикация

Проследите одно изменение по шагам. В одной транзакции сохраните изменение и outbox-запись; только после commit publisher может подобрать запись. После успешной отправки он отмечает её обработанной. Для каждого перехода задайте, что произойдёт, если процесс остановится прямо перед ним или сразу после него.

Особенно проверьте окно «брокер принял событие, но publisher не сохранил отметку». При перезапуске публикация может повториться. Опишите, как consumer обнаруживает повтор и когда сохраняет собственный эффект относительно ack. Не называйте поток exactly-once, если не описали атомарность этих операций и дедупликацию.

Сохраните диаграмму состояний, конкретный сценарий отказа и ожидаемое восстановление. Примеры урока проверяют только упрощённые boolean/enum входы и не моделируют сеть, транзакции или долговременное хранилище. Для проверки реальной гарантии нужен интеграционный стенд с управляемыми сбоями между переходами.

## Лаборатория: пройти точки сбоя вокруг outbox

### Численный сценарий

Возьмём бизнес-операцию «создать заказ и сообщить о создании». Без outbox возможна потеря сообщения: база сохранила заказ, процесс упал до публикации. Возможна и обратная ошибка: брокер получил сообщение, но транзакция базы откатилась. Outbox меняет порядок гарантий: транзакция сохраняет заказ и запись о намерении отправить событие вместе. Например, таблица содержит `event_id`, `order_id`, полезную нагрузку и состояние публикации. После commit отдельный publisher ищет незавершённые строки.

Здесь ещё не гарантировано, что consumer (потребитель) применит эффект ровно один раз. Publisher может отправить сообщение, затем упасть до отметки «отправлено». После перезапуска он увидит строку снова и повторит публикацию. Если consumer сохранил эффект, но ack (подтверждение) не дошло, сообщение тоже может быть доставлено повторно. Стабильный event ID позволяет обнаружить дубликат, только если consumer хранит факт обработки атомарно с собственным эффектом.

### Матрица точек отказа

1. Сбой до транзакции: не должно быть ни заказа, ни намерения публикации.
2. Ошибка при вставке outbox-записи: транзакция целиком откатывает и заказ, и событие.
3. Сбой после commit, до чтения publisher: обе записи сохранены, публикацию можно продолжить позже.
4. Брокер принял сообщение, но ответ не дошёл publisher: результат неизвестен, поэтому допустим повтор.
5. Consumer выполнил эффект и упал до ack: доставка может повториться; проверьте дедупликацию.
6. Ошибка обновления статуса outbox после отправки: строка остаётся кандидатом для повторной публикации.

Для каждой строки запишите наблюдаемый источник истины: транзакционную таблицу, broker acknowledgement или журнал consumer. Не делайте вывод из одного лога, если соответствующее состояние могло измениться без записи. Полезно различать «запись опубликована», «потребитель получил» и «эффект потребителя сохранён».

### Вопросы восстановления и предел модели

Продумайте очистку старых строк, повтор после длительного простоя и обработку события, которое всегда отвергает consumer. Удаление записи слишком рано может потерять возможность повторной публикации; бесконечный повтор постоянной ошибки может блокировать очередь. Эти политики требуют владельца, лимитов и аудита. Они не следуют автоматически из транзакционного outbox.

Нарисуйте state machine (машину состояний): `pending`, `publishing`, `published`, `failed` — если такие состояния действительно есть в реализации. Для каждого перехода назовите транзакционную границу и условие повторного захвата. Примеры lesson helper работают только с предоставленными полями и не подключают базу или брокер. Чтобы проверить реальные гарантии, нужен тест с транзакционной базой, тестовым брокером и остановкой процесса между шагами. Результат такого стенда всё равно относится только к выбранной версии, конфигурации и сценарию отказа.

### Схема хранения и конкурентные издатели

В таблице outbox обычно нужны стабильный идентификатор события, тип, полезная нагрузка, время создания и состояние доставки. Точный набор зависит от протокола. Храните только необходимые данные и определите срок удаления: слишком короткий срок теряет возможность восстановления, а бесконечное хранение растит таблицу и может замедлять publisher. Полезная нагрузка должна быть совместима с версией consumer или иметь явную версию схемы.

Если несколько издателей выбирают pending-записи одновременно, оба могут отправить один event. Реализация может атомарно резервировать запись, применять lease (аренду с ограниченным сроком) или допускать дубликаты с безопасным consumer. Lease уменьшает конкуренцию, но истечение аренды во время медленной отправки может привести к двум владельцам. Одного флага `processing` недостаточно, если процесс упал и флаг никогда не очищается; нужны сроки и восстановление зависших заявок.

Практикуйте отдельно очистку и повтор. После обработки consumer-ом удаление dedupe marker слишком рано позволяет поздней доставке выполнить эффект снова. Слишком долгий marker может потреблять хранилище. Выберите период, соотнесённый с возможным повтором брокера, и явно документируйте гарантию. Эти архитектурные варианты не проверяются helper примерами данного урока.

### Проверьте порядок транзакции

Транзакция должна фиксировать доменное изменение и outbox-запись вместе. Проверьте, что ошибка сериализации события происходит до commit или корректно откатывает обе записи. Если событие формируется после commit из уже изменившихся данных, повторное чтение может дать другой payload; сохранённая запись обычно нужна именно для стабильного намерения публикации.

Также задайте порядок доставки между связанными событиями. Два издателя могут обработать записи не по времени создания, если выборка и захват не сохраняют порядок. Если порядок важен для агрегата, нужен ключ партиционирования или версия события и правило consumer. Базовые helper-векторы этого не моделируют; отметьте это как отдельное требование протокола.

## Практика Easy / Medium / Hard

**Easy — переходы outbox.** Реализуйте `OutboxTransition` между absent, pending, delivered и acked для persist, rollback, publish, ack и crash. Отдельно проверьте crash до ack и повторную доставку после ack.

**Medium — retry limit.** Реализуйте `OutboxAttempt`; добавьте повтор из pending и dead_letter на границе maxAttempts. Убедитесь, что исходные переходы Easy сохраняются.

**Hard — восстановление и дедупликация.** Реализуйте `OutboxRecovery`. После delivered+crash результат зависит от того, применил ли consumer эффект; уже примененный эффект и публикация acked состояния дают `deduplicate`. Проверьте rollback, publish, ack, crash обеих ветвей, retry boundary и invalid. Это state-machine модель, не DB transaction, broker integration или exactly-once гарантия.
