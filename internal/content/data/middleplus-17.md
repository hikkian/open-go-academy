# Outbox, атомарность записи и публикация

## Что ты сделаешь

Ты разберёшь, почему «записать в базу и отправить событие» нельзя сделать атомарно напрямую, как транзакционный outbox закрывает окно между commit и публикацией, и почему он не отменяет повторных доставок и идемпотентного потребителя. Три функции урока — `OutboxTransition`, `OutboxAttempt`, `OutboxRecovery` — это конечный автомат записи outbox: состояния, события, лимит попыток и правила восстановления после сбоя. К базе и брокеру они не подключены.

## Зачем нужна эта граница

Приложение меняет данные в базе и должно опубликовать событие об этом в брокер. Если сначала зафиксировать изменение, а процесс упадёт до публикации — событие потеряно, потребители никогда не узнают. Если сначала опубликовать, а транзакция базы откатится — потребители получили событие о несуществующем изменении. База и брокер — два разных хранилища, и общей транзакции у них нет.

Транзакционный outbox (transactional outbox) записывает бизнес-изменение и намерение опубликовать событие в одной транзакции базы: событие становится строкой в таблице outbox рядом с данными. Отдельный издатель (publisher) читает ожидающие строки и отправляет их в брокер, а после подтверждения помечает отправленными. Это закрывает ровно один разрыв — между commit изменения и сохранением намерения. Публикация в брокер и commit базы по-прежнему не одна транзакция: издатель может отправить дважды.

```go group=transition mode=run
package main

import "fmt"

func transition(state, event string) string {
    switch state + "+" + event {
    case "absent+persist":
        return "pending"
    case "absent+rollback":
        return "absent"
    case "pending+publish":
        return "delivered"
    case "pending+crash":
        return "pending"
    case "delivered+ack":
        return "acked"
    case "delivered+crash":
        return "pending"
    case "acked+publish":
        return "acked"
    }
    return "invalid"
}

func main() {
    fmt.Println(transition("absent", "persist"), transition("pending", "publish"), transition("delivered", "ack"))
    fmt.Println(transition("pending", "crash"), transition("delivered", "crash"), transition("acked", "publish"), transition("unknown", "publish"))
}
```

Вывод:

```text
pending delivered acked
pending pending acked invalid
```

Четыре состояния: `absent` — строки нет; `pending` — записана, не отправлена; `delivered` — отправлена, подтверждение не получено; `acked` — подтверждена. Два сбоя: `pending+crash` ничего не меняет — строка переживёт перезапуск; `delivered+crash` возвращает в `pending`, потому что подтверждение потеряно и отправку придётся повторить. `acked+publish` остаётся `acked`: повторная доставка уже подтверждённого не меняет состояние.

> **Важно.** Outbox гарантирует «хотя бы один раз», а не «ровно один раз». Повторная публикация — нормальный путь, а не ошибка; с ней работает потребитель.

## Лимит попыток и мёртвая очередь

Издатель, который повторяет бесконечно, при постоянной ошибке брокера или отравленном сообщении будет крутиться вечно и блокировать остальные строки. Поэтому у каждой записи есть счётчик попыток и лимит: на лимите строка уходит в мёртвую очередь (dead letter) — отдельное состояние для ручного разбора, а не удаление.

```go group=attempt mode=run
package main

import "fmt"

func attempt(state, event string, attempts, maxAttempts int) string {
    if attempts < 0 || maxAttempts <= 0 || attempts > maxAttempts {
        return "invalid"
    }
    if state == "pending" && event == "publish" {
        if attempts >= maxAttempts {
            return "dead_letter"
        }
        return "delivered"
    }
    if (state == "pending" && event == "retry") || (state == "delivered" && event == "crash") {
        if attempts >= maxAttempts {
            return "dead_letter"
        }
        return "pending"
    }
    return "invalid" // остальные переходы — по таблице первого примера
}

func main() {
    fmt.Println(attempt("pending", "publish", 0, 3), attempt("pending", "retry", 2, 3), attempt("pending", "retry", 3, 3))
    fmt.Println(attempt("delivered", "crash", 3, 3), attempt("pending", "retry", 4, 3))
}
```

Вывод:

```text
delivered pending dead_letter
dead_letter invalid
```

`attempts` — уже сделанные попытки: три из трёх означают, что четвёртой не будет. Больше лимита — противоречие в данных, `invalid`. В заданиях оставшиеся переходы берутся из таблицы первого примера; здесь они заменены `invalid` только ради краткости.

> **Типичная ошибка.** Удалять строку на лимите попыток. Событие теряется молча — ровно та потеря, ради которой outbox вводили.

## Восстановление после сбоя и дедупликация

Самый тонкий случай — `delivered+crash`: издатель отправил событие, упал до записи подтверждения, и теперь не знает, дошло ли оно и обработал ли его потребитель. Если известно, что потребитель уже применил эффект (`effectApplied`), повторная отправка должна быть подавлена ключом идемпотентности — `deduplicate`; если нет — отправить снова, `retry_publish`, с учётом лимита.

```go group=recovery mode=run
package main

import "fmt"

func recovery(state, event string, attempts, maxAttempts int, effectApplied bool) string {
    if attempts < 0 || maxAttempts <= 0 || attempts > maxAttempts {
        return "invalid"
    }
    if state == "delivered" && event == "crash" {
        if effectApplied {
            return "deduplicate"
        }
        if attempts >= maxAttempts {
            return "dead_letter"
        }
        return "retry_publish"
    }
    if state == "acked" && event == "publish" {
        return "deduplicate"
    }
    return "other"
}

func main() {
    fmt.Println(recovery("delivered", "crash", 1, 3, false), recovery("delivered", "crash", 1, 3, true))
    fmt.Println(recovery("delivered", "crash", 3, 3, false), recovery("delivered", "crash", 3, 3, true), recovery("acked", "publish", 3, 3, true))
}
```

Вывод:

```text
retry_publish deduplicate
dead_letter deduplicate deduplicate
```

Дедупликация побеждает лимит: если эффект применён, повторная отправка не нужна независимо от счётчика. Откуда издатель узнаёт про `effectApplied`? Только из контракта с потребителем: устойчивый идентификатор события в сообщении и таблица обработанных идентификаторов у потребителя. Без этого флаг — предположение.

> **Зачем.** Потребитель, который хранит идентификаторы обработанных событий и пропускает повторы, — вторая половина outbox. Без него «хотя бы один раз» означает «иногда дважды» для пользователя.

## Что ещё входит в контракт

Порядок событий одного объекта: издатель, отправляющий строки outbox несколькими потоками, может доставить обновление раньше создания; порядок сохраняют, отправляя события одного ключа последовательно. Задержка: издатель опрашивает таблицу или слушает уведомления — это окно между commit и видимостью события, и оно тоже часть контракта. Уборка: подтверждённые строки удаляют или архивируют по сроку, иначе таблица растёт бесконечно. Наблюдаемость: возраст старейшей `pending` строки и число `dead_letter` — два обязательных сигнала.

## Издатель: опрос или уведомление

Издатель узнаёт о новых строках двумя способами. Опрос таблицы раз в N миллисекунд прост и надёжен, но добавляет задержку до N и нагрузку на базу пустыми запросами; его смягчают индексом по состоянию и времени и выборкой пачками. Уведомление базы (`LISTEN/NOTIFY` в PostgreSQL) будит издателя сразу, но не гарантирует доставку сигнала при перезапуске — поэтому его всегда сочетают с редким опросом как страховкой. В обоих случаях издатель берёт строки с блокировкой пропуска занятых (`FOR UPDATE SKIP LOCKED`), чтобы несколько экземпляров не отправляли одну строку дважды, — но два экземпляра на один ключ объекта всё равно ломают порядок, и ключ закрепляют за экземпляром.

## Практическая процедура

Нарисуй таблицу переходов: строки — состояния, столбцы — события, в ячейках — новое состояние или `invalid`. Добавь столбец со счётчиком попыток и отметь, в каких ячейках он проверяется. Затем для каждого сбоя — до commit, после commit, после отправки, после подтверждения — запиши, что увидит издатель при перезапуске и что сделает. Отдельно для `delivered+crash` опиши, как издатель узнаёт, применил ли потребитель эффект. Таблица и есть спецификация; функции урока — её проверка.

## Типичные ошибки

- Публиковать до commit: событие о несуществующем изменении.
- Публиковать после commit без outbox: событие теряется при падении между шагами.
- Считать outbox гарантией «ровно один раз».
- Удалять строку на лимите попыток вместо мёртвой очереди.
- Потребитель без таблицы обработанных идентификаторов.
- Несколько издателей на один ключ без сохранения порядка.

## Самостоятельная лаборатория

На одноразовом PostgreSQL создай таблицу данных и таблицу outbox; напиши транзакцию, которая меняет данные и вставляет событие, и издателя, который читает `pending` строки, «отправляет» их (печатает) и помечает `acked`. Убей издателя между отправкой и пометкой, перезапусти и покажи повторную отправку. Добавь потребителя с таблицей обработанных идентификаторов и покажи, что повтор не применяется дважды. Запиши задержку между commit и первой отправкой при опросе раз в секунду. Проект P3 курса содержит такой outbox с интеграционным тестом — сравни свою таблицу переходов с его состояниями. Удали стенд.

## Если что-то пошло не так

- `invalid` для `pending+crash` → этот переход допустим и возвращает `pending`.
- `pending` для `acked+publish` → подтверждённое состояние не меняется повторной доставкой.
- `delivered` при `attempts == maxAttempts` → лимит достигнут, нужен `dead_letter`.
- `retry_publish` при `effectApplied = true` → дедупликация проверяется раньше лимита.
- `invalid` для `attempts == maxAttempts` → равенство допустимо; `invalid` только при `attempts > maxAttempts`.
- `import … is not allowed` → импорты запрещены: сравнения строк и чисел.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках. Это конечный учебный автомат; атомарность базы и дедупликация потребителя требуют отдельной интеграции.

### Задание 1 · Easy: outbox state transitions

**Цель.** По состоянию и событию вернуть новое состояние по таблице урока; неизвестная пара → `invalid`.

**Ожидаемый вывод** — для `("absent", "persist")`:

```text
"pending"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func OutboxTransition(state string, event string) string`. Импорты запрещены.
2. Семь переходов: `absent+persist→pending`, `absent+rollback→absent`, `pending+publish→delivered`, `pending+crash→pending`, `delivered+ack→acked`, `delivered+crash→pending`, `acked+publish→acked`.
3. Всё остальное → `"invalid"`. «Запустить», «Проверить» — закрытые примеры: каждый из переходов и неизвестное состояние.

**Как проверить себя.** Сбой до отправки состояние не меняет; сбой после отправки возвращает в `pending`; повтор после подтверждения ничего не меняет.

**Если не принято.**
- `invalid` для `delivered+crash` → переход пропущен.
- `delivered` для `acked+publish` → подтверждённое состояние неизменно.

> **Подсказка.** Семь `if` или `switch` по паре состояние+событие; порядок не важен, пары не пересекаются.

### Задание 2 · Medium: лимит повторной публикации

**Цель.** Как задание 1, плюс лимит попыток: `pending+publish` и обе ветви восстановления на лимите → `dead_letter`; `attempts < 0`, `maxAttempts ≤ 0` или `attempts > maxAttempts` → `invalid`.

**Ожидаемый вывод** — для `("pending", "publish", attempts=0, maxAttempts=3)`:

```text
"delivered"
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func OutboxAttempt(state string, event string, attempts int, maxAttempts int) string`. Импорты запрещены.
2. Валидность счётчиков; `pending+publish` → `delivered` до лимита, `dead_letter` на лимите.
3. `pending+retry` и `delivered+crash` → `pending` до лимита, `dead_letter` на лимите.
4. Остальные пары — по таблице задания 1 (реализуй её рядом). «Запустить», «Проверить» — закрытые примеры: `retry` на 2 из 3 → `pending`, на 3 из 3 → `dead_letter`; `delivered+ack` → `acked`; `attempts = 4` при лимите 3 → `invalid`.

**Как проверить себя.** Лимит проверяется в трёх ветвях — публикации и двух восстановлениях; равенство `attempts == maxAttempts` — лимит достигнут.

**Если не принято.**
- `pending` на лимите → `>=` вместо `>`.
- `invalid` для `delivered+ack` с попытками → для прочих переходов нужна таблица задания 1.

> **Подсказка.** Напиши `OutboxTransition` в том же файле и вызови её в конце — так делает эталон.

### Задание 3 · Hard: crash recovery и дедупликация

**Цель.** Как задание 2, плюс `delivered+crash`: `effectApplied` → `deduplicate`, иначе `retry_publish` до лимита и `dead_letter` на нём; `acked+publish` → `deduplicate`.

**Ожидаемый вывод** — для `("absent", "persist", 0, 3, false)`:

```text
"pending"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func OutboxRecovery(state string, event string, attempts int, maxAttempts int, effectApplied bool) string`. Импорты запрещены.
2. Валидность счётчиков как в задании 2.
3. `delivered+crash`: сначала `effectApplied` → `"deduplicate"`; затем лимит → `"dead_letter"`; иначе `"retry_publish"`.
4. `acked+publish` → `"deduplicate"`; `pending+publish` и `pending+retry` — как в задании 2; остальное — таблица задания 1.
5. «Запустить», «Проверить» — закрытые примеры: `delivered+crash` с эффектом и без, на лимите и до него; `acked+publish`; отрицательные попытки → `invalid`.

**Как проверить себя.** Дедупликация побеждает лимит; `delivered+crash` без эффекта на лимите — `dead_letter`, с эффектом — `deduplicate` даже на лимите.

**Если не принято.**
- `retry_publish` при `effectApplied = true` → порядок: эффект проверяется первым.
- `pending` для `delivered+crash` → в этой модели восстановление после отправки — `retry_publish`, не `pending`.

> **Подсказка.** Единственные новые ветки — `delivered+crash` и `acked+publish`; остальное — задание 2.

## Проверь себя

- Какой разрыв закрывает транзакционный outbox, а какой — нет?
- Почему `delivered+crash` возвращает в `pending`, а `pending+crash` ничего не меняет?
- Зачем мёртвая очередь и почему не удаление?
- Откуда издатель узнаёт, что потребитель уже применил эффект?
- Что обязан делать потребитель, чтобы «хотя бы один раз» не стало «дважды»?

## Итог

- Outbox записывает событие в той же транзакции, что и данные, и закрывает окно между commit и публикацией; «ровно один раз» он не даёт.
- Записи живут в четырёх состояниях со счётчиком попыток; лимит ведёт в мёртвую очередь, а не в удаление.
- Повторная доставка — нормальный путь: потребитель хранит обработанные идентификаторы, издатель сохраняет порядок по ключу и следит за возрастом `pending`.
