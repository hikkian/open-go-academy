# 29. HTTP middleware и context

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `juniorplus-08`; предыдущая глава `middle-28`.  
**Планируемый порядок каталога:** 69.  
**Результат:** Ограничить body, сохранять request context, задавать deadline и не терять cancellation.

## Глоссарий

- **middleware (промежуточный обработчик)** — Обёртка вокруг HTTP handler, которая применяет общую политику к запросу.
- **request context (контекст запроса)** — Носитель отмены, deadline и request-scoped значений между вызовами.
- **deadline (предельный срок)** — Момент, после которого операция должна прекратить работу.
- **body limit (лимит тела запроса)** — Ограничение байт, которые могут быть прочитаны/обработаны из HTTP body.

## Теория и границы применения

HTTP middleware располагается до или вокруг handler: оно может проверить размер тела, добавить request-scoped данные, измерить длительность и передать управление следующему слою. Порядок обёрток имеет значение. Если логирование считывает body до ограничителя, то ограничение может оказаться слишком поздним. Ограничитель должен действовать до декодирования и полной буферизации. При streaming-чтении учитывайте, что проверка `Content-Length` не достаточна: клиент может передать chunked body или неверное значение заголовка.

В Go `http.Request` уже содержит context. Downstream-вызовы должны получать `r.Context()`, чтобы отмена клиента и deadline могли дойти до repository/внешнего клиента. Если заменить его на `context.Background()`, связь с жизненным циклом запроса теряется. Если нужно ограничить работу handler, используйте дочерний `context.WithTimeout` и вызовите cancel через `defer`. Короткий timeout не должен превышать родительский deadline: операция не может продлить время, которого ей не дали.

Context cancellation кооперативен. Он закрывает `Done()` и задаёт `Err()`, но не останавливает произвольную функцию, которая игнорирует context. Каждая потенциально блокирующая операция должна передавать context и проверять его через API зависимости. Горутинный код обязан определить, кто ждёт завершения и что произойдёт с результатом после отмены. Не запускайте goroutine на каждый запрос, если нет bounded concurrency и пути завершения.

Для body limit решите, что считать размером: фактически прочитанные байты, а не только заголовок. В стандартном `net/http` есть `http.MaxBytesReader`; при превышении чтение возвращает ошибку. Не делайте `io.ReadAll` до установки лимита. В тесте проверьте размер ровно на границе, на один байт больше, отрицательные параметры чистой политики, неизвестный Content-Length и закрытие/отмену потока. Учитывайте, что JSON decoder может прочитать больше ожидаемого логического объекта; ограничение относится ко всему телу запроса.

`EffectiveTimeout` в этом наборе возвращает меньший из положительных parent/handler значений. Эта функция не создаёт `context.Context`, не устанавливает системный deadline и не измеряет время. `RequestDecision` моделирует только приоритет cancellation и решения по заданной длине. Чтобы проверить реальный middleware, создайте `httptest` запрос и downstream handler: проверьте, что oversized body отклонён до вызова downstream, отменённый context доходит до dependency, а deadline отменяется при выходе. Эти тесты подтверждают конкретный middleware, но не всю нагрузочную устойчивость сервиса.

Перед чтением body можно отклонить очевидно слишком большой `Content-Length`, но нельзя доверять ему как единственному контролю. Лимит должен применяться к reader. Для ответов и streaming есть отдельные пределы и правила: request body limit не ограничивает ответ внешнего сервиса. Не смешивайте лимит тела с таймаутом; медленный маленький body всё ещё может занимать соединение слишком долго. Используйте server read timeout и context с подходящей политикой.

Middleware должно сохранять исходную семантику ответа и заголовков. Если handler уже отправил заголовок, поздняя ошибка не всегда может заменить код ответа. Для middleware, которое пишет ответ самостоятельно, задайте стабильный JSON error и не раскрывайте внутреннюю ошибку чтения. Обязательно проверьте поведение на пустом body и на уже отменённом context. Внешнее соединение может закрыться до ответа, поэтому тест ожидаемого кода должен учитывать слой, который его наблюдает.

Не помещайте в context произвольную конфигурацию или optional parameters. Он подходит для отмены/deadline и небольших данных, привязанных к одному запросу. Используйте типизированный ключ, не строку, если кладёте principal или trace state. Параметр функции лучше context value для обязательной бизнес-зависимости: так сигнатура явно показывает requirement.

Уровни упражнений здесь — helper-проверки с разным фокусом: Easy проверяет допустимость byte count и лимита; Medium выбирает эффективное положительное время; Hard задаёт порядок между отменой, ошибочными пределами, превышением и продолжением. Это не реализация HTTP middleware, не тест передачи cancellation и не подтверждение, что сервер закрывает соединение. Практическая лаборатория должна отдельно подтвердить эти свойства через `httptest` и интеграционный dependency.

При проверке deadline используйте короткие управляемые интервалы и синхронизацию, а не произвольный `time.Sleep`, который делает тест нестабильным. Отмена может произойти до того, как worker начал работу; тест должен иметь handshake каналом. Всегда вызывать cancel, даже если тест завершился раньше. Если нужна проверка утечки goroutine, сравнивайте наблюдения осторожно и добавляйте конкретный сигнал завершения, а не полагайтесь только на глобальное число goroutine.

## Разбор решения: пределы и отмена — разные механизмы

Предел тела отвечает на вопрос о размере работы; timeout — сколько времени запрос может занимать. Клиент может отправлять маленькое тело очень медленно: байтовый лимит не спасёт от медленного соединения. Быстро отправленное огромное тело может превысить лимит прежде, чем timeout сработает. Поэтому middleware может применять оба ограничения, а HTTP server — иметь read deadline. Их тесты должны различать источник отказа.

`http.MaxBytesReader` оборачивает body так, чтобы чтение сообщало об overflow. Установка его после `json.Decoder.Decode` ничего не защищает. Обработчик может увидеть ошибку decoder и ответить `413`, но обязан следить, что клиентский запрос не был уже частично обработан. Обычно сначала полностью валидируется и декодируется ограниченное тело, а затем вызывается изменение состояния. Транзакционный порядок зависит от endpoint.

Deadline дочернего контекста равен минимуму родительского и локального ограничения. Функция Medium возвращает числовое значение только для этой политики; она не учитывает абсолютное время, monotonic clock или отмену на практике. В Go передавайте context в методы `QueryContext`/`ExecContext`; это просит driver остановить работу, но поведение конкретного driver следует проверить. Если он не реагирует, приложение может зависнуть несмотря на отмену.

Тесты должны иметь явные события: dependency сообщила «начал», тест вызывает cancel, dependency сообщает «завершил». Такая последовательность делает отмену наблюдаемой. Нельзя выводить корректное завершение лишь из факта, что `ctx.Err()` стал `context.Canceled`; обработчик может игнорировать сигнал и продолжить менять данные.

## Review middleware before merge

Проверьте порядок композиции middleware в самом сервере, потому что отдельные unit tests не показывают фактическую последовательность обёрток. Убедитесь, что лимитер стоит перед decode, trace/context middleware не теряет исходный request, а error writer остаётся доступен нужному слою. Назовите owner каждого ресурса и убедитесь, что тело закрывается в соответствии с правилами HTTP server.

Добавьте тест, где middleware обёрнуто в обратном порядке, чтобы понять, какой регресс выявляет проверка. Не оставляйте такой вариант как production config; он служит контрольным отрицательным случаем. Для deadline теста используйте context сигнал и ограниченный test timeout, чтобы зависший тест завершился предсказуемо. Любой timeout в тесте должен быть существенно больше ожидаемой длительности успешного пути и достаточно коротким для сбоя.

В отчёте разделите: чистую арифметическую политику; поведение `net/http` ограничения; передачу cancellation в fake; реакцию реального driver. Это четыре разные утверждения с разными тестами. Команда `go test -race` может помочь найти конкретные data races при исполненной последовательности, но не доказывает отсутствия всех гонок.

## Три самостоятельных запускаемых примера

### Пример 1: `BodyAllowed`

Контракт: Допустимо только при bodyBytes>=0, maxBytes>0 и размере не выше лимита.

```go
package main

import "fmt"

func BodyAllowed(bodyBytes, maxBytes int64) bool {
	return bodyBytes >= 0 && maxBytes > 0 && bodyBytes <= maxBytes
}

func main() {
	fmt.Println(BodyAllowed(12, 16))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `EffectiveTimeout`

Контракт: Некорректный неположительный timeout →0; иначе минимум parent/handler timeout.

```go
package main

import "fmt"

func EffectiveTimeout(parentMillis, handlerMillis int64) int64 {
	if parentMillis <= 0 || handlerMillis <= 0 { return 0 }; if parentMillis < handlerMillis { return parentMillis }; return handlerMillis
}

func main() {
	fmt.Println(EffectiveTimeout(3000, 5000))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `RequestDecision`

Контракт: Сначала canceled → canceled; затем некорректные пределы → invalid; превышение → too_large; иначе continue.

```go
package main

import "fmt"

func RequestDecision(bodyBytes, maxBytes int64, canceled bool) string {
	if canceled { return "canceled" }; if bodyBytes < 0 || maxBytes <= 0 { return "invalid" }; if bodyBytes > maxBytes { return "too_large" }; return "continue"
}

func main() {
	fmt.Println(RequestDecision(12, 16, false))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

## Практика Easy / Medium / Hard

**Easy — базовое правило.** Реализуйте `func BodyAllowed(bodyBytes, maxBytes int64) bool`. Контракт: Допустимый размер: bodyBytes >= 0, maxBytes > 0 и bodyBytes <= maxBytes. Функция не ограничивает HTTP reader. Скрытые и публичные vectors закреплены в grading spec.

**Medium — граничная политика.** Реализуйте `func EffectiveTimeout(parentMillis, handlerMillis int64) int64`. Контракт: Если любой timeout неположителен, вернуть 0; иначе вернуть минимум parent/handler. Функция не создаёт deadline. Скрытые и публичные vectors закреплены в grading spec.

**Hard — helper-проверка.** Реализуйте `func RequestDecision(bodyBytes, maxBytes int64, canceled bool) string`. Контракт: Приоритет: canceled → canceled; некорректные пределы → invalid; превышение → too_large; иначе continue. Это helper-решение, не middleware. Скрытые и публичные vectors закреплены в grading spec.

## Лабораторная карточка TaskFlow: middleware и request context

Соберите `httptest` endpoint, который читает тело через ограничитель и передаёт `r.Context()` fake dependency. До теста выберите небольшой лимит, например 16 байт. Проверьте body размером 0, ровно 16, 17 байт, пустой `Content-Length`/streaming input и тело с ошибкой чтения. Установите ограничитель до JSON decoder и отметьте, был ли downstream handler вызван. Отдельно проверьте ответ на превышение и что он не содержит внутреннюю ошибку.

Создайте запрос с отменяемым context. Fake dependency должен сигнализировать о старте через канал и завершаться при `ctx.Done()`. Сначала дождитесь сигнала, затем отмените parent; подтвердите, что зависимость получила отмену и handler завершился. Не используйте случайный `time.Sleep` вместо handshake. В отдельном тесте создайте handler timeout короче parent deadline и подтвердите, что эффективный срок не увеличился. Всегда вызывайте cancel и дожидайтесь фоновой работы.

Unit test `BodyAllowed`, `EffectiveTimeout` и `RequestDecision` прогоняет чистые границы и precedence. Он не устанавливает ограничитель и не распространяет context. Integration test через `httptest` подтверждает middleware-путь в выбранной конфигурации. Тест с fake не доказывает, что реальный SQL driver соблюдает отмену; для этого нужен отдельный тест с тестовой БД/driver и конкретной операцией.

Проверьте, что body читается максимум на лимит плюс диагностический байт, что oversized request не вызывает неограниченную буферизацию и что middleware не заменяет исходный context на `Background`. Для slow client дополнительно понадобится настройка server read timeout; числовой helper миллисекунд эту защиту не включает.

В отчёте перечислите тестовые случаи, лимит, Go version, таймауты и наблюдённое событие отмены. Если тест прошёл только с fake, укажите это прямо. Не делайте вывод о нагрузочной устойчивости или предотвращении DoS из одного маломерного `httptest`; этот эксперимент подтверждает только заданный размер и цепочку middleware.
