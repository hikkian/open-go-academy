# HTTP middleware и context

## Что ты сделаешь

Ты напишешь три проверки для границ HTTP-запроса: допустимость размера тела, итоговый срок обработки с учётом срока родителя и решение о продолжении с учётом отмены и размера тела. Функции проверяют числа и флаги, а сам HTTP-сервер и его чтение тела они не запускают.

## Middleware как граница

Middleware — это обёртка вокруг обработчика. Название пришло из систем, где одна и та же обёртка стоит между сетью и приложением, и каждый запрос проходит через неё одинаково. Она видит запрос раньше обработчика и может решить, пропустить его дальше или ответить сама. Здесь удобно держать общие границы: максимальный размер тела, срок обработки, проверку отмены. Обработчик тогда отвечает только за своё правило.

Граница полезна, если все обработчики получают её одинаково. Порядок подключения тоже важен: граница размера тела должна стоять раньше того кода, который тело читает, иначе чтение уже случилось до проверки. Иначе один забытый лимит на одном маршруте становится дырой, через которую приходит огромное тело или висящий запрос.

> **Важно.** Middleware не заменяет проверку ввода в обработчике. Он ограничивает объём и время, а смысл данных проверяется дальше по цепочке.

## Размер тела

Тело запроса может быть очень большим. Если читать его без предела, память растёт вместе с размером, а сервис становится уязвимым для простого отказа. Поэтому чтение ограничивают: тело читается не дальше заданного предела, а если клиент прислал больше, чтение заканчивается ошибкой.

Учебная функция проверяет допустимость размера по числам. Она не читает поток. Пример показывает проверку, которая отвергает отрицательный размер и нулевой предел до сравнения:

```go
package main

import "fmt"

func main() {
    for _, c := range [][2]int64{{16, 16}, {17, 16}, {0, 0}} {
        ok := c[0] >= 0 && c[1] > 0 && c[0] <= c[1]
        fmt.Println(ok)
    }
}
```

Вывод: `true`, `false`, `false`. Граница включена: тело ровно в шестнадцать байт проходит, семнадцать — нет. Нулевой предел не пропускает ничего, поэтому он считается ошибкой конфигурации.

## Срок обработки и родитель

Срок обработки задаёт общий бюджет запроса. Если клиент или прокси уже ограничили запрос трёхсекундным сроком, обработчик не может продлить его собственным пятисекундным таймаутом. Эффективный срок — меньший из родительского и локального. Нулевой или отрицательный срок означает ошибку настройки, а не бесконечное ожидание.

Пример показывает такое сравнение. Родительский срок короче локального, поэтому действует он:

```go
package main

import "fmt"

func main() {
    parent, handler := int64(1200), int64(5000)
    if parent < handler {
        fmt.Println(parent)
    } else {
        fmt.Println(handler)
    }
}
```

Вывод: `1200`. Локальный таймаут не расширил запрос, а родительский срок остался общим бюджетом.

## Дочерний контекст и отмена

Обработчик получает дочерний контекст запроса. Дочерний контекст наследует отмену и срок родителя и может добавить собственный срок. Если клиент закрыл соединение, отмена доходит до обработчика и дальше до хранилища. Поэтому работа прекращается вместе с запросом, а не продолжается в фоне.

Важно понимать, что отмена — это сообщение, а не принудительная остановка. Функция, которая не читает `Done`, продолжит выполняться. Это касается и библиотечных вызовов: если библиотека не принимает контекст, отмена до неё не дойдёт, и это нужно зафиксировать как ограничение. Поэтому каждая долгая операция должна проверять контекст сама и передавать его дальше.

## Решение о продолжении

Решение о продолжении собирает вместе три факта: отменён ли запрос, корректны ли границы, и умещается ли тело в предел. Порядок важен. Отменённый запрос не нужно читать вовсе, даже если тело маленькое. Некорректные границы — ошибка конфигурации, и её нужно видеть раньше, чем размер тела.

Пример показывает такой порядок. Отмена проверяется первой, и её результат не зависит от размера тела:

```go
package main

import "fmt"

func decide(body, max int64, canceled bool) string {
    switch {
    case canceled:
        return "canceled"
    case body < 0 || max <= 0:
        return "invalid"
    case body > max:
        return "too_large"
    }
    return "continue"
}

func main() {
    fmt.Println(decide(12, 16, false), decide(99, 16, true))
}
```

Вывод: `continue canceled`. Отменённый запрос с большим телом ответил `canceled`, а не `too_large`: клиент уже не ждёт ответа на размер.

## Как проверить распространение отмены

Чистая функция не доказывает, что отмена дошла до хранилища. Для этого нужен интеграционный сценарий: запрос с медленным хранилищем, отмена клиентского соединения во время ожидания и проверка, что запрос к базе прерван. Наблюдение сохраняют в журнале: время отмены, момент прерывания и число запросов, которые реально выполнились.

Такой тест важнее модульного: он проверяет цепочку от middleware до драйвера, где отмена чаще всего теряется.

## Серверный срок и срок обработчика

Срок на уровне сервера защищает от медленных клиентов: если соединение открыто, но запрос не дочитан, сервер не должен ждать бесконечно. Это отдельная граница, которая действует до middleware. Срок обработчика работает внутри неё и не может её отменить. Поэтому при настройке полезно знать оба значения и сравнивать их явно, а не полагаться на умолчания библиотеки.

Если серверный срок короче срока обработчика, длинная работа оборвётся раньше, чем вернёт ответ. Клиент получит обрыв вместо понятной ошибки. Поэтому обработчик с большим бюджетом обязан проверять, укладывается ли он в серверный срок, и возвращать категорию заранее.

## Журнал отказов границ

Отказы по размеру тела, сроку и отмене полезно записывать в журнал с категорией. Журнал не должен содержать тело запроса: оно может быть большим или личным. Достаточно размера, предела, категории и идентификатора запроса. По этим данным видно, клиенты ли отправляют слишком большие тела или предел выбран слишком маленьким.

Частые отмены одного маршрута говорят о медленном хранилище или о таймауте, который короче обычной работы. Такой сигнал полезнее единичного отказа, потому что он показывает причину, а не отдельный случай.

## Модель и механизм

Для границ запроса полезны три вопроса. Какой размер тела допустим? Какой срок у запроса и кто его задал? Что произойдёт при отмене на каждом шаге? Ответы записываются как границы middleware до написания обработчиков.

Синхронизация здесь косвенная: отмена распространяется через канал `Done`, и её проверяют так же, как любой канал. Цена подхода — каждый слой должен передавать контекст дальше, и один забытый аргумент разрывает цепочку.

## Типичные ошибки и исправление

Первая ошибка — читать тело без предела. Исправление — ограничить чтение и вернуть понятную категорию при превышении.

Вторая — продлевать срок локальным таймаутом. Исправление — эффективный срок равен меньшему из родительского и локального.

Третья — создавать новый контекст в обработчике. Исправление — передавать дочерний контекст от входящего запроса.

Четвёртая — считать отмену остановкой. Исправление — долгие операции проверяют `Done` сами.

> **Типичная ошибка.** Передавать в хранилище `context.Background()` вместо контекста запроса. Тогда отмена клиента не дойдёт до базы, и работа продолжится впустую.

## Если что-то пошло не так

- Большие тела съедают память → чтение не ограничено пределом; добавь ограничение в middleware.
- Запрос выполняется после закрытия соединения → контекст не передан дальше; проверь аргументы.
- Срок обработчика больше срока клиента → локальный таймаут не сравнивается с родительским.
- Отмена не прерывает запрос к базе → драйвер не получил контекст; передай контекст в вызов.

## Воспроизводимая лабораторная: предел тела и отмена

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Сеть и сервер не нужны: запрос создаётся в памяти пакетом `httptest`.

Программа ниже ограничивает тело запроса пределом шестнадцать байт и читает его. Она также проверяет, что контекст запроса не отменён. Запусти её во временном каталоге и сравни вывод с ожидаемым.

```go
package main

import (
    "fmt"
    "io"
    "net/http"
    "net/http/httptest"
    "strings"
)

func main() {
    req := httptest.NewRequest(http.MethodPost, "/", strings.NewReader(strings.Repeat("x", 20)))
    rec := httptest.NewRecorder()
    req.Body = http.MaxBytesReader(rec, req.Body, 16)
    _, err := io.ReadAll(req.Body)
    fmt.Println("too large:", err != nil)
    fmt.Println("context alive:", req.Context().Err() == nil)
}
```

**Ожидайте:** первая строка `too large: true` — тело в двадцать байт не прочитано полностью при пределе шестнадцать. Вторая строка `context alive: true` — контекст запроса не отменён.

**Очистка:** программа работает в памяти процесса и ничего не создаёт на диске. Если запускал её во временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- Middleware задаёт общие границы запроса: предел тела и срок обработки, которые обработчики не могут расширить.
- Отмена передаётся через дочерний контекст и работает как сообщение, а не как принудительная остановка; её проверяет интеграционный тест. Вместе с тестом отмены стоит держать тест срока: один и тот же сценарий с коротким сроком покажет, что ответ приходит именно от границы, а не от случайного обрыва соединения.
- Решение о продолжении проверяет отмену раньше размера тела, а некорректные границы выносит как ошибку конфигурации.
