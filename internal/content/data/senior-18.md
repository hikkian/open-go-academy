# P5: наблюдаемость и причинная связь

## Что ты сделаешь

Ты свяжешь показатели, журналы и трассировки с конкретным вопросом расследования: назовёшь сигнал, источник и окно наблюдения, выберешь допустимые атрибуты и не примешь пустую телеметрию за отсутствие проблемы. Три функции урока проверяют покрытие сигнала, разрешённые атрибуты и значимость окна. Они не собирают метрики и не доказывают причинную связь.

## Разбор темы

Общий разбор P5 дан в senior-13. Здесь речь о том, как телеметрия отвечает на вопрос расследования и где её ответ заканчивается.

## Вопрос раньше данных

Телеметрии много, и она легко создаёт иллюзию ответа. Графики, журналы и трассировки показывают, что происходило, но не говорят, почему. Поэтому расследование начинается с вопроса в одной фразе: «почему платежи этим утром ждут дольше двух секунд» или «какие клиенты получили дублирующие письма». Вопрос определяет нужный сигнал, источник и окно. Без этого инженер листает панели без цели и находит совпадения, которые ничего не доказывают.

Сигнал — это измеримая величина, отвечающая на вопрос: доля ответов дольше порога, число повторных отправок, глубина очереди. Источник — место, где величина записывается: метрика сервиса, журнал приложения, трасса запроса. Окно — интервал времени, за который берётся величина. Одно и то же событие может выглядеть по-разному в минутном и в часовом окне, и выбор окна меняет ответ.

Хороший вопрос расследования проверяем: из него видно, какой ответ был бы «да», а какой «нет». Вопрос «стало ли хуже» не годится, потому что любое колебание величины можно назвать ухудшением. Вопрос «выросла ли доля ответов дольше двух секунд с 9 до 10 утра по сравнению с прошлой неделей» допускает измерение и отрицательный ответ. Формулировка, которую нельзя опровергнуть, обычно не стоит проверки.

## Журналы, метрики и трассировки

Журналы хранят отдельные события с подробностями, метрики хранят агрегаты с ограниченным набором меток, трассировки связывают шаги одного запроса через несколько сервисов. Каждый вид отвечает на свой класс вопросов. Метрика быстро показывает, что задержка выросла. Трасса показывает, на каком шаге она выросла. Журнал объясняет, почему шаг завершился ошибкой. Пытаться заменить один вид другим — типичная ошибка: по журналу нельзя восстановить распределение задержек, а по метрике — путь конкретного запроса.

Важна связь между видами. Идентификатор запроса, который попадает и в журнал, и в трассу, позволяет перейти от агрегата к конкретному случаю. Если его нет, расследование превращается в ручной поиск по времени.

Стоимость вида телеметрии тоже важна при выборе. Журналы дороги при большом объёме, метрики дёшевы, но ограничены по меткам, трассы зависят от выборки. Решение о том, что записывать постоянно, а что только по требованию, принимается заранее: иначе в момент инцидента выясняется, что нужного журнала нет, потому что его не включали.

## Выборка и её границы

Трассировки обычно записываются не для всех запросов, а для доли, заданной выборкой. Значит, отсутствие трассы не означает отсутствие ошибки. Возможно, запрос просто не попал в выборку. Выборка может быть головной (решение принимается в начале запроса) или хвостовой (решение после завершения). Хвостовая выборка лучше сохраняет медленные и ошибочные запросы, но требует буфера и дороже в эксплуатации. Запишите выбранную стратегию и её долю рядом с вопросом расследования: иначе отчёт о «нулевом количестве трасс» будет принят за доказательство.

Стратегия выборки меняется во время инцидента: при всплеске ошибок имеет смысл поднять долю записываемых трасс на время расследования. Это решение тоже записывается вместе с временем начала и конца, иначе после инцидента нельзя понять, почему трасс стало больше, и сравнение с прошлой неделей окажется некорректным.

## Кардинальность меток

Каждая уникальная комбинация значений меток — отдельный временной ряд, который система хранит и считает. Метка с идентификатором пользователя создаёт миллионы рядов и быстро перегружает систему хранения. Поэтому метки выбирают из ограниченного набора: шаблон маршрута вместо полного пути, класс статуса вместо точного кода, название операции вместо текста запроса. Полный идентификатор остаётся в журнале или трассе, где его можно искать точечно.

Ограничение кардинальности стоит проверять автоматически: при выпуске сравнивается число рядов до и после изменения. Резкий рост почти всегда означает новую метку с нестабильным значением, и такую ошибку лучше поймать на стенде, чем счетом за хранение в конце месяца.

## Приватность в телеметрии

Телеметрия копирует данные из продукта в систему наблюдения, и эта копия живёт дольше и доступна большему числу людей. Персональные данные в журналах, адреса электронной почты в метках и секреты в заголовках — частые источники утечек. Фильтр нужен на входе: список разрешённых атрибутов задаётся явно, а не запрещённых. Удаление уже записанного значения из архива обычно невозможно, поэтому проверка до записи важнее любой очистки после.

Отдельный риск — текст запроса, который попадает в шаблон маршрута или в название операции по ошибке. Если маршрут содержит идентификатор в пути, он будет записан в каждую метрику. Поэтому шаблоны маршрутов проверяют на реальных путях до выпуска, а не полагаются на то, что разработчик вспомнит.

## Причина и корреляция

Два сигнала, которые растут вместе, не доказывают, что один вызывает другой. Для проверки причины нужно изменить один фактор при прочих равных и увидеть ожидаемый эффект. Если изменить условие нельзя, фиксируется, какие альтернативные объяснения исключены и какие остались. Расследование, которое честно пишет «вероятно, причина в X, проверено Y, не проверено Z», полезнее уверенного вывода по корреляции.

Иногда изменить фактор невозможно, например когда сбой случился у внешнего поставщика. Тогда причина устанавливается косвенно: по совпадению времени начала с событием поставщика, по воспроизведению на стенде с имитацией задержки, по отсутствию сбоя в тех же условиях без внешнего вызова. Каждое такое свидетельство записывается с его слабостью, а не выдаётся за доказательство.

## Покрытие сигнала

Пример 1 проверяет, отвечает ли выбранный сигнал на вопрос расследования. Сначала должен быть назван сам вопрос, затем источник и окно наблюдения; без любого из них данные не отвечают на вопрос.

```go
package main

import "fmt"

func signalCoverage(question, source, window string) string {
	if question == "" {
		return "missing_question"
	}
	if source == "" {
		return "missing_source"
	}
	if window == "" {
		return "missing_window"
	}
	return "defined"
}

func main() {
	fmt.Println(signalCoverage("latency", "histogram", "5m"))
	fmt.Println(signalCoverage("latency", "histogram", ""))
	fmt.Println(signalCoverage("", "", ""))
}
```

Вывод: `defined`, `missing_window`, `missing_question`. Наличие данных ещё не означает, что они относятся к вопросу: сигнал нужно сопоставить с конкретным источником и окном.

## Разрешённые атрибуты

Пример 2 проверяет, можно ли использовать атрибут в telemetry. Разрешён короткий список измерений с ограниченной кардинальностью; всё остальное, включая персональные и пустые ключи, отклоняется.

```go
package main

import "fmt"

func attributeAllowed(key string) bool {
	switch key {
	case "route_template", "status_class", "operation":
		return true
	default:
		return false
	}
}

func main() {
	fmt.Println(attributeAllowed("route_template"))
	fmt.Println(attributeAllowed("user_email"))
	fmt.Println(attributeAllowed(""))
}
```

Вывод: `true`, `false`, `false`. Фильтр на входе важнее удаления после записи: персональное значение, попавшее в журнал, уже скопировано.

## Значимость окна наблюдения

Пример 3 классифицирует окно наблюдения инцидента. Некорректные счётчики не обсуждаются; отсутствие выборок означает неизвестность, а не отсутствие сбоя; сбои в выборке фиксируются как наблюдённые.

```go
package main

import "fmt"

func incidentSignal(samples, failed int) string {
	if samples < 0 || failed < 0 || failed > samples {
		return "invalid"
	}
	if samples == 0 {
		return "unknown"
	}
	if failed > 0 {
		return "observed_failure"
	}
	return "no_failure_observed"
}

func main() {
	fmt.Println(incidentSignal(10, 1))
	fmt.Println(incidentSignal(0, 0))
	fmt.Println(incidentSignal(10, 0))
	fmt.Println(incidentSignal(10, 11))
}
```

Вывод: `observed_failure`, `unknown`, `no_failure_observed`, `invalid`. Пустое окно нельзя превращать в зелёный статус: тишина в телеметрии может означать отсутствие выборки.

## Если что-то пошло не так

- Вопрос расследования не назван → сформулируй его и подбери сигнал с источником и окном.
- Персональное значение попало в атрибут → отфильтруй его на входе и проверь список разрешённых ключей.
- Пустое окно выглядит как зелёный статус → помечай его как unknown и выясни причину отсутствия данных.
- Корреляцию выдаёшь за причину → измени один фактор контролируемо и проверь ожидаемый эффект.

## Типичные ошибки расследования

Начинать с панелей без вопроса и выбирать сигнал по тому, что уже нарисовано. Считать отсутствие трассы доказательством отсутствия ошибки, не зная стратегии выборки. Использовать идентификатор пользователя как метку метрики, потому что так «удобнее искать». Считать одно совпадение по времени причиной. Сравнивать величины из разных окон и делать вывод о росте.

## Итог

- Телеметрия отвечает на вопрос только тогда, когда сигнал, источник и окно названы для конкретного вопроса расследования.
- Отсутствие данных означает неизвестность: без выборки нельзя утверждать ни наличие сбоя, ни его отсутствие.
- Атрибуты ограничиваются на входе по списку с низкой кардинальностью, а причинная связь проверяется контролируемым изменением.
