# Race detector и упорядочивание памяти

## Что ты сделаешь

Ты напишешь три функции-модели, которые оценивают наблюдения: совпадение пары значений, монотонность счётчика и первое уменьшение. Главная часть урока — не сами функции, а то, как читать результат `go test -race` и что он доказывает.

## Что такое гонка данных

Гонка данных возникает, когда несколько горутин обращаются к одной ячейке памяти одновременно, хотя бы один доступ является записью, и между ними нет нужной синхронизации. Программа при этом может работать правильно сегодня и неправильно завтра, потому что результат зависит от расписания.

Гонка часто не проявляется на ноутбуке разработчика и проявляется в продакшене. Причина в том, что число ядер, частота переключений и нагрузка меняют расписание. Поэтому отсутствие сбоя на одной машине не говорит о безопасности кода. Оно говорит только о том, что конкретное расписание не привело к ошибке.

Пример того же счётчика, но защищённого mutex. Каждое увеличение находится внутри критической секции, поэтому детектор не видит конфликтующих доступов:

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var mu sync.Mutex
    var wg sync.WaitGroup
    n := 0
    for i := 0; i < 50; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()
            n++
            mu.Unlock()
        }()
    }
    wg.Wait()
    fmt.Println(n)
}
```

Вывод: `50`. Итог совпадает при любом расписании, потому что каждый доступ к `n` синхронизирован mutex-ом. Без mutex тот же код мог бы дать отчёт детектора, а итог — меньше пятидесяти, но не в каждом запуске.

Не путай гонку данных с логической гонкой. Логическая гонка — это неверный бизнес-порядок: два запроса по очереди читают и пишут корректно с точки зрения памяти, но теряют обновление, потому что проверили старое условие. Race detector находит только первую разновидность.

## Happens-before — порядок, который можно обосновать

Happens-before — отношение гарантированного порядка. Если операция `A` синхронизирована с операцией `B`, всё, что было записано до `A`, видно после `B`. Канал, mutex и корректно применённые атомики создают такие связи.

Пример: горутина записывает значение и отправляет сигнал в канал, а `main` получает сигнал и только потом читает значение. Отправка happens-before завершения получения, поэтому чтение безопасно.

```go
package main

import "fmt"

func main() {
    data := 0
    done := make(chan bool)
    go func() {
        data = 42
        done <- true
    }()
    <-done
    fmt.Println(data)
}
```

Вывод: `42`. Запись `data` стоит до отправки в канал, а чтение — после получения. Эта связь видна в коде и объясняется без расписания.

Атомики дают похожую связь, но только для тех операций, которые ими выполнены. Запись обычного поля до `Store` атомика и чтение того же поля после `Load`, который увидел значение, безопасны. Если часть доступов идёт мимо атомика, связь теряется, и детектор снова может сообщить о гонке.

```go
package main

import (
    "fmt"
    "sync"
    "sync/atomic"
)

func main() {
    var hits atomic.Int64
    var wg sync.WaitGroup
    for i := 0; i < 20; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            hits.Add(2)
        }()
    }
    wg.Wait()
    fmt.Println(hits.Load())
}
```

Вывод: `40`. Атомарный `Add` неделим, поэтому двадцать увеличений на два дают сорок при любом расписании. Атомик здесь не защищает другой инвариант: он гарантирует только целостность одной ячейки.

## Почему sleep не создаёт порядок

`time.Sleep` измеряет время, а не порядок операций. Если горутина обычно успевает за десять миллисекунд, тест может пройти на одной машине и упасть на другой. С точки зрения модели памяти задержка не создаёт happens-before: она не связывает запись и чтение.

Поэтому вместо «подождать 10 мс» используй получение результата, закрытие канала или `WaitGroup`. Тогда связь между событиями выражена синхронизацией, и её можно проверить.

## Что означает отчёт детектора

Race detector отслеживает реально выполненные обращения к памяти и сообщает о конфликтующих доступах без happens-before. Отчёт указывает два места: где был доступ и с чем он конфликтовал. Это свидетельство о конкретном исполнении.

Отсутствие отчёта означает, что в этом запуске конфликтов не наблюдалось. Оно не означает, что конфликтов нет вообще: непройденные ветки, другие входы и другие расписания остаются вне проверки. Поэтому зелёный `-race` — важный сигнал, но не доказательство.

Пример отчёта выглядит примерно так. Это фрагмент вывода, а не программа, поэтому он не запускается как пример:

```text
WARNING: DATA RACE
Write at 0x00c0000140a8 by goroutine 7:
  main.main.func1()
Previous read at 0x00c0000140a8 by main goroutine:
  main.main()
```

Такой отчёт говорит, какая строка писала, какая читала и в какой горутине. Обычно в отчёте есть и строки «Goroutine ... created at», которые показывают, где создана конфликтующая горутина. Это помогает понять, кто запустил работу и с какими данными. Дальше нужно найти общий объект и выяснить, какой синхронизации не хватает.

> **Важно.** Детектор видит только исполненные пути. Если защищённая ветка не запускалась в тесте, гонка в ней останется незамеченной.

## Как читать отчёт шаг за шагом

Отчёт нужно разбирать по порядку, а не просто переписывать в исправление. Сначала найди два доступа, которые указал детектор: какая горутина писала и какая читала. Затем определи общий объект: переменная, поле структуры, элемент `map` или срез. Только после этого спрашивай, какой порядок должен быть между этими доступами.

Исправление выбирается по требуемому порядку. Если нужна передача значения, подойдёт канал. Если нужна защита общего состояния, подойдёт mutex. Если нужна однократная публикация, подойдёт атомик или `Once`. Каждое исправление должно сопровождаться тестом, который воспроизводит прежний отчёт, и запуском с `-race`.

Когда исправление внесено, запусти тест несколько раз, например с `-count=20`. Один зелёный прогон после исправления ничего не доказывает: отчёт мог не появиться по случайности.

## Что делать после чистого запуска

Чистый запуск — не финиш, а начало проверки. Расширь входы, чтобы пройти все ветки кода с общими данными. Запусти тест многократно с `-count`, чтобы увидеть разные расписания. Проведи ручной аудит: найди все обращения к разделяемым объектам и проверь, что у каждого есть протокол.

Обрати внимание на копирование структур с mutex, а также на ссылки внутри `map`, `slice` и интерфейсов: копия структуры или общий срез могут обходить защиту. Взаимодействие с внешним процессом или базой требует отдельной модели синхронизации, которую детектор не проверит.

## Модель и механизм

Сначала различай состояние программы и расписание. Состояние — значения, владение ресурсами и открытые каналы. Расписание — чередование шагов, выбранное системой во время исполнения. Корректная программа должна давать допустимый результат при любом расписании, которое разрешено языком.

Для проверки полезны три вопроса. Какой объект разделяется между горутинами? Какая операция задаёт порядок доступов к нему? Что видит читатель, если запись произошла, но синхронизация не завершилась? Ответы записываются до запуска детектора.

Синхронизация имеет цену: ожидание, память и сложность кода. Устранять гонку следует правильной синхронизацией, а не удалением теста или добавлением задержки.

## Типичные ошибки и исправление

Первая ошибка — считать зелёный `-race` доказательством отсутствия гонок. Исправление — записать, какие ветки и входы проверены, и назвать непроверенные.

Вторая — добавлять `time.Sleep` в тест, чтобы убрать отчёт. Это скрывает проблему, а не исправляет её. Исправление — заменить задержку явным событием.

Третья — проверять только итоговое значение. Итог может совпасть, а промежуточное состояние остаться противоречивым. Исправление — проверять инвариант напрямую в конце и во время работы.

> **Типичная ошибка.** Отключать `-race` в CI, потому что он «медленный». Так исчезает единственный динамический сигнал о гонках, а баг остаётся до первого продакшен-расписания.

## Если что-то пошло не так

- Отчёт детектора появляется только под нагрузкой → расписание редкое; добавь управляемые барьеры и повтори тест.
- Отчёт пропадает после добавления `Sleep` → задержка изменила расписание, но не синхронизацию; верни тест к явным событиям.
- Тест зелёный, а результат неверный → возможна логическая гонка без data race; проверь бизнес-порядок операций.
- `WARNING: DATA RACE` в другом пакете → общий объект передан по ссылке; найди, кто его изменяет.

## Лаборатория перед практикой

Возьми счётчик, который десять горутин увеличивают через обычное `n++` без mutex, и запусти его с `go run -race main.go`. Перед запуском запиши, появится ли отчёт, и какие две строки он укажет. Затем добавь mutex вокруг инкремента и повтори запуск. Сравни результат с предсказанием и запиши, что изменилось в отчёте.

Журнал эксперимента содержит версию Go, команду с `-race`, число горутин, предсказание, наблюдение и текст отчёта, если он появился. Если отчёт не появился в первом запуске, повтори эксперимент с большим числом запусков и запиши это как ограничение: отсутствие отчёта в одном запуске не доказывает корректность.

## Практика

### Практический мост: границы race detector

Helper-векторы не создают конкурирующих доступов и не проверяют data race. Реальная конкурентная доставка проверяется в проекте P3: тест `TestPostgresTaskOutboxAndTenantIsolation` в `content/projects/p3/reference/postgres_integration_test.go`. Для реального DB-сценария используй disposable PostgreSQL.

Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда поднимает только disposable PostgreSQL из P3 Compose на loopback-порту 55433; пароль существует только в окружении shell. Она ждёт healthcheck, запускает точный тест с детектором и удаляет контейнер и volume при завершении блока:

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle08 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -race -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидай отсутствие сообщения race detector в этом запуске. Результат не доказывает все расписания и не проверяет SQL-изоляцию. Векторы этой главы охватывают только чистые функции.

### Задание 1 · Race detector и упорядочивание памяти — easy

**Цель.** Для пары наблюдений верни `[1]`, если значения совпадают, иначе `[0]`. Если наблюдений не два, верни `[0]`.

**Ожидаемый вывод** — входы: `[4, 4]`, затем `[4, 5]`:

```text
[1]
[0]
```

**Шаги.**
1. Выбери задание «Race detector и упорядочивание памяти — easy»: в файле есть `ConsistentPair` с `panic("TODO")`. Импорты не нужны.
2. Проверь, что во входе ровно два значения; если нет, верни `[0]`.
3. Сравни два значения.
4. Если они равны, верни `[1]`; иначе `[0]`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два среза из одного числа; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[1]` для входа из одного значения → длина входа не проверена.
- `[0]` для равных значений → сравнение выполнено неверно.

> **Подсказка.** Сначала длина списка, потом сравнение.

## Итог

- Race detector сообщает о конфликтах в реально выполненных путях; отсутствие отчёта ограничено пройденным.
- Порядок доступов обосновывается синхронизацией, а не задержкой; happens-before связывает запись и чтение.
- После чистого запуска нужны новые входы, аудит общих объектов и интеграционный сценарий по теме кода.
