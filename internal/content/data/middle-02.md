# Создание goroutine и завершение

## Что ты сделаешь

Ты напишешь три функции-модели для задач со статусами «выполняется», «завершена» и «отменена». Примеры урока покажут, почему вызов `go` сам по себе не доказывает, что работа выполнена, и как сделать завершение наблюдаемым.

## Вызов go — это только старт

Оператор `go f()` запускает функцию в отдельной goroutine (горутине, лёгкой задаче Go) и сразу возвращает управление. Он не ждёт результата и не гарантирует, что функция успеет начать работу. Если `main` завершится раньше, процесс остановится, даже когда дочерняя задача ещё печатает.

Поэтому у каждого запуска должна быть точка завершения: канал результата, `sync.WaitGroup` или другой протокол. В примере два производителя отправляют квадраты в буферизованный канал, а отдельная горутина закрывает канал только после `wg.Wait()`.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup
    results := make(chan int, 2)
    for _, v := range []int{2, 3} {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            results <- n * n
        }(v)
    }
    go func() {
        wg.Wait()
        close(results)
    }()
    total := 0
    for n := range results {
        total += n
    }
    fmt.Println(total)
}
```

Вывод: `13`. Сумма `4` и `9` не зависит от того, какая горутина отправила значение первой. Закрытие канала стоит после `wg.Wait()`, поэтому цикл `range` не выйдет раньше последней отправки.

## Кто владеет завершением

Каждый запуск нужно описать четырьмя вопросами: кто создаёт работу, кто ждёт результат, кто может её отменить и кто освобождает ресурсы. Если на последний вопрос ответ «никто», код требует пересмотра: горутина может зависнуть на отправке в канал, который никто не читает.

Буфер канала не решает эту проблему. Он лишь откладывает момент, когда отправитель заблокируется. Если читателя нет, буфер рано или поздно заполнится, и горутина встанет.

Право закрытия канала должно быть у одного владельца, который знает, что отправителей больше нет. Повторное закрытие и отправка в закрытый канал вызывают панику. Поэтому закрытие ставят в одном месте, после ожидания всех отправителей.

У `sync.WaitGroup` есть своё правило порядка: `Add` вызывают до `go`, а не внутри горутины. Если `Add` отстаёт от `Wait`, ожидание может вернуться раньше, чем появятся все участники. `Done` вызывают через `defer`, чтобы он сработал и при панике внутри работы.

## Передача данных в горутину

Аргументы функции вычисляются до запуска горутины, поэтому значение лучше передавать явным параметром. В Go 1.22 и новее переменная цикла создаётся заново на каждой итерации, и старый сбой с общей переменной не повторится. Явный параметр всё равно делает владение видимым: из сигнатуры понятно, какое значение получила горутина.

Если горутины пишут в общий срез, каждая должна занимать свой индекс. Тогда запись не конкурирует с другими записями, а ожидание через `WaitGroup` даёт безопасное чтение после завершения.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    values := []int{1, 2, 3}
    squares := make([]int, len(values))
    var wg sync.WaitGroup
    for i, v := range values {
        wg.Add(1)
        go func(i, v int) {
            defer wg.Done()
            squares[i] = v * v
        }(i, v)
    }
    wg.Wait()
    fmt.Println(squares)
}
```

Вывод: `[1 4 9]`. Каждая горутина пишет только в свой индекс, поэтому мьютекс здесь не нужен. Если заменить срез на `map`, запись уже требует синхронизации: одновременная запись в `map` из нескольких горутин недопустима.

## Отмена — сигнал сотрудничества

Context не останавливает горутину принудительно. Функция сама должна читать `ctx.Done()`, а зависимость — принимать контекст и уважать его. Иначе вызывающий код перестанет ждать, а фоновая работа продолжит занимать ресурсы.

```go
package main

import (
    "context"
    "fmt"
)

func work(ctx context.Context, result chan<- string) {
    <-ctx.Done()
    result <- "cancelled"
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    cancel()
    ch := make(chan string, 1)
    work(ctx, ch)
    fmt.Println(<-ch)
}
```

Вывод: `cancelled`. Пример вызывает `work` синхронно, поэтому он показывает только реакцию на `Done`, а не настоящую фоновую работу. В реальном коде вызов идёт через `go`, а ожидание результата — через канал или `WaitGroup`.

> **Важно.** Отмена сообщает, что работу пора остановить. Она не гарантирует, что работа уже остановилась. Для этого нужно дождаться завершения горутины.

## Два способа ждать результат

`sync.WaitGroup` отвечает на вопрос «все ли участники закончились». Он считает действия, но не возвращает значения и не передаёт ошибку. Подходит, когда результат пишется в общее место, которое защищено или не делится между участниками.

Канал результата передаёт значение или ошибку напрямую. Он удобен, когда вызывающий код должен получить ответ от одной работы. Если результатов много, нужен владелец закрытия канала, и поэтому чаще используют комбинацию: `WaitGroup` ждёт всех, а отдельная горутина закрывает канал, как в первом примере.

Передача указателя на общий изменяемый объект оставляет доступ обеим сторонам. Горутина, получившая указатель, может менять объект в любой момент, пока вызывающий код считает его своим. Поэтому в сигнатуре и в комментарии нужно написать, кто владеет объектом после старта.

## Как проверить завершение

Тест, который ждёт горутину через `time.Sleep(100 * time.Millisecond)`, зависит от скорости машины. Лучше дать горутине явную точку: канал готовности, который она закрывает после старта, и канал результата, который тест читает с ограничением по времени. Тогда тест знает, что событие произошло, а не угадывает момент.

Для каждой горутины проверь три исхода: успешное завершение, ошибку и отмену. В каждом исходе вызывающий код должен получить сигнал, а ресурсы должны освободиться. Если хотя бы один исход не покрыт, это место остаётся непроверенным, даже когда основной путь зелёный.

Удали строку ожидания из первого примера и запусти его несколько раз. Результат может совпасть случайно, но код уже неверен: программа потеряет вывод, если `main` завершится раньше отправок. Такой эксперимент показывает, что без явного ожидания тест не наблюдает завершение.

## Что доказывают примеры

Примеры урока работают без сети, базы и случайных задержек. Они показывают локальный механизм и не доказывают поведение сервиса под нагрузкой. Честная запись о результате выглядит так:

- Гарантирует код: сумма в первом примере не зависит от порядка отправок, а срез во втором получает каждое значение по своему индексу.
- Остаётся за пределами: поведение при аварийном завершении процесса, загрузка планировщика и порядок вывода на другой машине.
- Не проверяется: отмена реальной фоновой работы. Для неё нужен тест с настоящей горутиной и ожиданием через канал.

Такой список предотвращает сильные выводы из маленького фрагмента. Если в отчёте написано «код корректен», без уточнения границ такое утверждение не принимается.

## Типичные ошибки

Ошибки обычно выглядят как правильный код.

- `go f()` принимают за подтверждение выполнения `f`. Это только запуск: добавь канал результата или `WaitGroup`.
- `time.Sleep` используют как синхронизацию. Задержка может пройти на одной машине и упасть на другой, и она не задаёт порядок событий. Жди событие, а не время.
- Защищают только запись, забывая чтение. Мьютекс должен покрывать все обращения к общим данным.
- Закрывают канал там, где отправители ещё живы. Право закрытия принадлежит одному владельцу.
- Отменяют ожидание родителя, но забывают дочернюю работу. Контекст кооперативен: код должен читать `Done`.

> **Типичная ошибка.** Считать зелёный `-race` доказательством всех расписаний. Детектор проверяет только те исполнения, которые реально произошли во время запуска. Комбинируй тесты, разные входы и ручной аудит доступов.

## Если что-то пошло не так

- Программа завершается без вывода из горутины → `main` вышел раньше; добавь ожидание через `WaitGroup` или канал.
- Результат меняется от запуска к запуску → порядок не входил в контракт; сравнивай набор значений или сортируй его.
- Паника `send on closed channel` → канал закрыт при живых отправителях; закрывай его один раз после `wg.Wait()`.
- Тест зависает на чтении из канала → результат никто не отправил; проверь пути ошибки и отмены.

## Лаборатория перед практикой

Возьми первый пример и добавь третьего производителя со значением 4. Перед запуском запиши ожидаемую сумму, затем запусти программу и сравни. Если сумма совпала, но ты не можешь объяснить, почему `close` стоит после `wg.Wait()`, перенеси `close` в `main` до запуска горутин. Программа упадёт с паникой. Запиши, что именно произошло, и почему: владение закрытием здесь не стиль, а условие корректности.

Журнал эксперимента содержит версию Go, команду запуска, входные значения, ожидаемый результат и наблюдение. Без такого журнала другой человек не сможет повторить вывод, а сам эксперимент не станет доказательством.

## Практика

### Практический мост: запуск и завершение работы

Функции этой практики — модель статусов. Они не создают горутины и не проверяют расписание выполнения, поэтому их векторы не доказывают happens-before. Настоящий жизненный цикл задач есть в проекте P3: `runWorkers` в `content/projects/p3/reference/worker.go` присоединяет работу, которая уже выполняется, когда начинается отмена. Тест `TestRunWorkersJoinsInflightWork` в `reference_test.go` проверяет именно это. Запусти его из каталога `content/projects/p3/reference` командой `go test -run TestRunWorkersJoinsInflightWork -count=1`. База не нужна.

Все три задания ниже работают с чистыми функциями. Вход и ожидаемый результат каждой функции указаны в карточке; закрытые примеры видны только в «Проверить».

### Задание 1 · Создание goroutine и завершение — easy

**Цель.** Вернуть срез из одного числа: сколько элементов имеют статус 1.

**Ожидаемый вывод** — входы: `[1, 0, 1, -1]`, затем `[0, 0]`:

```text
[2]
[0]
```

**Шаги.**
1. Выбери задание «Создание goroutine и завершение — easy»: в файле есть `CompletedCount` с `panic("TODO")`. Импорты не нужны.
2. Пройди по `values` и подсчитай элементы, равные 1.
3. Верни срез из одного числа — счётчика.
4. Нажми «Запустить» и сравни с блоком выше.
5. Нажми «Проверить».

**Как проверить себя.** Два результата в квадратных скобках; все три критерия зелёные.

**Если не принято.**
- `[3]` для первого входа → учитываются и статусы 0 или -1; сравнивай со статусом 1 точно.
- `[0]` для первого входа → цикл не находит совпадений; проверь, что счётчик растёт.

> **Подсказка.** Одна переменная-счётчик и одно сравнение `== 1`.

### Задание 2 · Создание goroutine и завершение — medium

**Цель.** Вернуть значения со статусом 1 из пар `[значение, статус]`, сохранив порядок.

**Ожидаемый вывод** — входы: `[7, 1, 8, 0, 9, 1]`, затем `[3, -1]`:

```text
[7,9]
[]
```

**Шаги.**
1. Выбери задание «Создание goroutine и завершение — medium»: в файле есть `JoinCompleted` с `panic("TODO")`. Импорты не нужны.
2. Иди по `values` парами: сначала значение, затем статус.
3. Если последняя пара неполная, пропусти её.
4. Добавь значение в результат, только если статус равен 1.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два среза в квадратных скобках; оба вывода совпадают буква в букву; все три критерия зелёные.

**Если не принято.**
- `null` вместо `[]` → результат остался nil-срезом; создай пустой срез перед циклом.
- `[7,8,9]` → статус проверяется у значения, а не у пары; сравнивай второй элемент пары.

> **Подсказка.** Шаг цикла по парам — два, а не один.

### Задание 3 · Создание goroutine и завершение — hard

**Цель.** Вернуть срез с индексом первой отменённой задачи (статус -1) или срез `[-1]`, если отмен нет.

**Ожидаемый вывод** — входы: `[0, 1, -1, 1]`, затем `[1, 1]`:

```text
[2]
[-1]
```

**Шаги.**
1. Выбери задание «Создание goroutine и завершение — hard»: в файле есть `FirstCancelledIndex` с `panic("TODO")`. Импорты не нужны.
2. Пройди по `values`, сохраняя индекс текущего элемента.
3. На первом элементе со статусом -1 верни срез с его индексом.
4. Если отмен нет, верни срез `[-1]`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два среза; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- Индекс последней отмены вместо первой → цикл не остановился на первом совпадении; верни результат сразу.
- `[-1]` при наличии отмены → сравнение со статусом -1 не сработало; проверь знак.

> **Подсказка.** Возврат из функции внутри цикла останавливает поиск на первом совпадении.

## Проверь себя

- Что произойдёт с горутиной, если `main` вернётся раньше её завершения?
- Почему буферизованный канал не заменяет владельца, который ждёт результат?
- Почему закрывать канал должен один участник?
- Почему аргумент горутине лучше передавать явно?
- Почему отмена через context требует, чтобы код читал `Done`?
- Почему зелёный `-race` не доказывает все расписания?

## Итог

- `go` запускает работу, но не подтверждает её выполнение: нужна явная точка завершения.
- Владелец канала и общих данных назван в коде; закрывает канал один участник после последней отправки.
- Тесты проверяют отмену и ошибку, а не только успешный путь; зелёный `-race` — лишь часть доказательства.
