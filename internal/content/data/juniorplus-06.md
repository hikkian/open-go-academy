# Маршруты, методы и перенаправления

## Маршрут выбирает ответственность

Маршрут (route) связывает метод и цель запроса с обработчиком. Два запроса к одному пути с `GET` и `DELETE` могут вести к разным операциям. Сначала mux определяет, существует ли подходящая комбинация метода и пути; handler затем применяет контракт к конкретному ресурсу. Различайте три ответа: путь не известен (`404`), путь известен, метод не разрешён (`405`), ресурс на допустимом маршруте не найден (`404` от логики handler).

`http.ServeMux` Go умеет method-aware шаблоны вида `GET /health` и именованные части пути. Сопоставление учитывает более точный шаблон. Этот синтаксис доступен в современном Go; в этом курсе версия указана в metadata. Если запускаете пример более старой версией, ошибка компиляции или поведение маршрута — сигнал проверить версию, а не переписать проект на случайный сторонний router.

Некоторые методы имеют специальные свойства. `HEAD` обычно возвращает те же headers и status, что `GET`, но без тела. `OPTIONS` часто сообщает допустимые возможности. `Allow` полезен при `405`. Не возвращайте `200` для неизвестного метода, если клиент рассчитывает, что сервер отказал.

## Redirect не означает CRUD

Перенаправление (redirect, ответ перейти к другому URI) сообщает клиенту новый `Location`. Оно не заменяет создание или изменение ресурса и не гарантирует, что браузер последует ответу. `301` и `308` обозначают постоянное перенаправление; `302` и `307` — временное. При `307` метод и тело запроса сохраняются, а старые клиенты исторически могли менять POST на GET после `302`. Выбирайте статус согласно маршруту и тестируйте точное поведение клиента.

Redirect должен иметь `3xx` status и заголовок `Location`. Go предоставляет `http.Redirect`, который устанавливает оба и при необходимости пишет небольшое HTML тело. Для стабильного API не сравнивайте это тело, если контракт его не задаёт. Проверяйте статус и Location. Цель может быть относительной, например `/articles/go`, или абсолютной.

### Неожиданное перенаправление — риск

Если клиент принимает target из пользовательского ввода, атакующий может предложить `https://evil.example`, `//evil.example` или схему вроде `javascript:`. При создании короткой ссылки это может быть допустимо, но при возврате редиректа нужно ясно понимать политику. Open redirect может использовать доверенный домен для фишинга. В простом внутреннем учебном роутере ниже разрешается только фиксированная относительная цель, начинающаяся одним `/`.

URL — синтаксис со scheme, authority, path, query и fragment. Проверка `strings.HasPrefix(target, "/")` недостаточна, если разрешает `//host`: браузер трактует это как абсолютную network-path reference. Также исключайте обратный слэш, схемы, CR/LF и пустые назначения согласно политике. Разбирайте URL стандартной библиотекой и проверяйте отдельные компоненты.

## Пример 1. Методный health route и Allow

```go group=method-route mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) { w.WriteHeader(http.StatusNoContent) })
	request := httptest.NewRequest(http.MethodPost, "/health", nil)
	recorder := httptest.NewRecorder()
	mux.ServeHTTP(recorder, request)
	fmt.Println(recorder.Code, recorder.Header().Get("Allow"))
}
```

Результат показывает отказ метода; точное значение `Allow` зависит от зарегистрированных pattern. При собственном router задайте стабильный header явно. Всегда проверяйте `GET` и неверный метод разными входами.

## Пример 2. Redirect внутри приложения

```go group=safe-relative-redirect mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	h := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if r.URL.Path != "/go" { http.NotFound(w, r); return }
		http.Redirect(w, r, "/articles/go", http.StatusFound)
	})
	recorder := httptest.NewRecorder()
	h.ServeHTTP(recorder, httptest.NewRequest(http.MethodGet, "/go", nil))
	fmt.Println(recorder.Code, recorder.Header().Get("Location"))
}
```

В тесте браузер не следует за redirect, так что recorder позволяет рассмотреть исходный ответ. Автоматически не делайте второй запрос к адресу `Location`: в реальном учебном тесте redirect цель остаётся относительной фикстурой.

## Пример 3. Защитить пользовательский target

```go group=redirect-target-policy mode=run
package main

import (
	"fmt"
	"net/url"
)

func isLocalPath(raw string) bool {
	u, err := url.Parse(raw)
	return err == nil && u.Scheme == "" && u.Host == "" && len(u.Path) > 1 && u.Path[0] == '/' && u.Path[1] != '/' && u.Fragment == ""
}

func main() {
	fmt.Println(isLocalPath("/articles/go"), isLocalPath("//evil.example"), isLocalPath("https://evil.example"))
}
```

Результат `true false false` демонстрирует узкую политику. Реальный API может разрешать абсолютные URL, но тогда требует иных правил и информированного продукта. Эта проверка не создаёт редирект и не является общей sanitizer для любого URL контекста.

## Сопоставление и HTTP ошибки

Для небольшой программы можно зарегистрировать маршруты через `ServeMux`, а для параметров работать с `r.PathValue("code")`. Не извлекайте идентификатор наивным `strings.Split` всего URL: в path segments могут быть экранированные символы, а query не является частью route path. Предпочитайте штатный matcher. В тесте посмотрите `r.URL.Path`, `r.URL.Query()` и `r.Method` раздельно.

Маршрут и ресурс — разные уровни. `GET /links/unknown` может совпасть с маршрутом чтения одной ссылки, после чего репозиторий сообщит «нет записи». А `GET /nonsense` не совпал с маршрутом. Внешний статус часто одинаков (`404`), но внутренние логи и метрики должны различать причину без выдачи чувствительных данных клиенту.

### Идентификаторы в пути

Именованная часть шаблона вроде `/links/{alias}` извлекается стандартным mux как `r.PathValue("alias")`. Прежде чем использовать её в SQL, нужно определить правила кодирования, проверку alias и отношение к отсутствующей записи. Значение route parameter не является автоматически валидным или авторизованным: пользователь сам выбирает URL.

Статический `/health` и динамический `/links/{alias}` — разные маршруты; тестируйте path, близкие к границе (`/links/`, `/links/a/b`, URL encoded slash), и не делайте неоговорённых предположений про decode. Выбирая ID в пути, зафиксируйте длину и алфавит так, чтобы один ID оставался одним сегментом. Query-параметр не заменяет path identifier автоматически: это отдельный контракт.

`http.ServeMux` понимает не только exact route, но и subtree patterns с завершающим slash. Pattern `/links/` способен принять неизвестное число под-путей, а не только `/links/{alias}`. Для ресурсов используйте точные шаблоны и дополнительные тесты на trailing slash. Случайная регистрация широкого префикса может перехватить маршрут, который задумывался иначе.

При маршрутизации нескольких patterns узкий path обычно имеет приоритет над широким; конфликтующие patterns могут быть отвергнуты при регистрации или выбрать более специфичный. Не угадывайте порядок: запустите тесты на пересечениях (`/links`, `/links/{alias}`, `/links/{alias}/stats`) и прочитайте ошибку регистрации. Изменение одного pattern способно изменить поведение многих запросов.

## Типичные ошибки

- **Считать redirect обычным ответом страницы.** Браузер может послать следующий запрос и показать уже другую страницу. API клиент может вообще не follow redirect.
- **Игнорировать `Location`.** Без целевого URI клиенту некуда идти; тест должен проверить именно заголовок.
- **Разрешать абсолютный внешний URL незаметно.** Зафиксируйте, может ли ресурс перенаправить на внешний домен и кто контролирует цель.
- **Ставить `405` для отсутствующего URL.** Сначала определите, распознан ли ресурсный путь, и отдельно разрешён ли метод.
- **Считать 301/302/307 взаимозаменяемыми.** Они задают разное постоянство и историческое поведение повторной отправки метода.
- **Сравнивать тело ответа `http.Redirect`.** Оно не обязательно часть API контракта. Проверяйте статус и Location.

Если клиент неожиданно попал на внешний сайт, сохраните исходный Location в локальной фикстуре, проверьте его компоненты, найдите источник target и проверьте правило доверия. Не открывайте подозрительную ссылку в браузере ради «проверки». Если неверный метод дал 404, выясните версию Go и поведение ServeMux, затем зафиксируйте требуемые `405` и `Allow` тестом.

Для разделения handler ветвей ведите компактную таблицу маршрутов: pattern, допустимые methods, целевой handler, нормальный status, ошибка неизвестного ID. Таблица полезна при code review, потому что URL контракты часто оказываются распределены по нескольких регистрациям. Если регистрация зависит от конфигурации, тестируйте с фиксированным конфигом, иначе неизвестно, какую поверхность вы проверяете.

Redirect status влияет и на клиента. При `307` тело POST нужно направить повторно по Location; такой повтор может вызвать нежелательный эффект, если endpoint меняет данные. Поэтому redirect после mutation требует особенно ясного решения. Для перехода после создания браузерного ресурса можно выбрать корректный redirect pattern, но он не устраняет дублирование и не заменяет idempotency logic. В данной API главе предпочитайте `201` с Location, если клиентский контракт не требует навигации.

### Нормализация и граница сегмента

Не пытайтесь автоматически «починить» любой путь, подставив slash или обрезав лишнюю часть. Такое исправление может превратить одну цель в другую. Сначала определите, хотите ли API различать `/links/green` и `/links/green/`; затем добавьте два fixture. Если канонический URI возвращается сервером, используйте `Location` и не меняйте состояние в процессе такого ответа.

Параметр маршрута — всё ещё пользовательский ввод. Для alias `a%2Fb` проверьте, какое значение получает handler в используемой версии Go. Не считайте percent-encoding разрешением на slash внутри одного идентификатора. Корректный URL syntax и разрешённое приложением значение — две отдельные проверки.

`httptest.NewRecorder` сохраняет redirect response, но не выполняет follow. Это хорошая изоляция: можно проверить Location и случайно не запросить внешний адрес. Если когда-нибудь нужно проверить цепочку переходов, используйте второй локальный test handler и client, который разрешает лишь тестовые адреса. Не давайте ему автоматически следовать URI из произвольной строки.

## Практика

- **Easy:** реализуйте `GET /health` и ответ на другой метод. Проверьте body/status/Allow, не меняя проверку неизвестного пути.
- **Medium:** создайте короткий маршрут `GET /go/{code}` с заранее заданной локальной целью. Известный код выдаёт `302` и ожидаемый Location; неизвестный — `404`.
- **Hard:** обработайте redirect без open redirect: пропускайте только абсолютный внутренний path без authority/scheme, отклоняйте пустой target, `//host`, URL scheme, обратный слэш и CR/LF; неверный метод — `405`.

Тесты должны проверять конечную цель как заголовок и не переходить по ней. Для безопасного результата составьте таблицу допустимых и отклонённых цели и включите границы. Не исправляйте заголовок `Location` после `http.Redirect`, не проверив исходную ошибку политики. Полезная таблица проверяет normal path, encoded slash, пустую строку, `//authority`, absolute URL, query, fragment и обратный slash. Для каждого fixture запишите ожидаемый status и Location.

## Мини-глоссарий

- **route (маршрут)** — связь HTTP метода и пути с обработчиком.
- **method mismatch** — путь известен, но метод не допускается.
- **redirect (перенаправление)** — ответ 3xx с инструкцией перейти по Location.
- **Location** — заголовок URI ресурса или цели перехода.
- **open redirect** — возможность отправить пользователя на контролируемый атакующим адрес.
- **`Allow`** — список методов, поддерживаемых выбранным ресурсом.
- **path segment** — отдельная часть пути между `/`.
- **authority** — часть URL с хостом и иногда портом.
