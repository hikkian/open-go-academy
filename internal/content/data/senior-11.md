# Изоляция арендаторов и безопасность межклиентских границ

**Senior · модуль 2 · занятие 5 из 6 · 270 минут.** Зависимость: `senior-10`. Tenant isolation (изоляция арендаторов) означает, что клиент организации не может читать или менять ресурсы другой организации, а их нагрузка и администрирование не должны случайно сливаться. Tenant-ом может быть команда, организация, проект или отдельный аккаунт — понятие должно соответствовать модели доступа. Эта глава не сертифицирует multi-tenant продукт; она помогает сформулировать угрозы и тесты.

## Tenant как часть модели доступа

Начните с субъектов: пользователь, service account, оператор support, background worker, администратор и публичный клиент. У каждого есть идентичность и scope полномочий. Tenant ID в браузерном запросе является вводом, а не доказательством принадлежности. Сервер должен получить principal из доверенного authentication path, проверить membership и разрешение на конкретное действие и ресурс.

**Authorization** (авторизация) — решение, имеет ли субъект право выполнить действие над объектом в данном контексте. Проверка роли без проверки tenant может разрешить доступ не к той организации. Проверка tenant без действия может позволить участнику читать закрытые billing сведения. Для критичных операций задайте tuple: principal, tenant, resource, operation, context. Context включает состояние ресурса, роль, срок, delegation и дополнительные условия.

Сделайте scope частью типизированного запроса, насколько это помогает избежать ошибок. Например, repository method принимает `TenantID` явно, а не опциональный string, который иногда пуст. Но наличие типа не является контролем: вызывающий код может передать tenant из пользовательского body. Источник идентификатора должен быть проверен относительно server-owned membership. Не предоставляйте функцию «get by ID» без видимого tenant scope для обычного пути.

IDOR (insecure direct object reference — небезопасная прямая ссылка на объект) возникает, когда знание ID позволяет обратиться к чужому объекту. Случайные UUID уменьшают угадываемость, но не заменяют авторизацию. Тестируйте запрос с валидным ID соседнего tenant-а, несуществующим ID и собственным ресурсом. Если ответы для чужого и отсутствующего объекта различаются, это может раскрывать существование. Выберите безопасную семантику ответа согласно продукту.

## Где применять проверку

Проверка должна быть на серверной доверенной границе и охватывать все пути. HTTP handler получает principal и передаёт service method контекст, который нельзя потерять. Worker извлекает tenant identity из durable event, сверяет её с ресурсом, и ограничивает свою DB role. Административный task должен логировать основание доступа и scope. GraphQL resolver, экспорт, поиск и WebSocket требуют того же контроля, что обычный REST route.

SQL query должен ограничивать tenant в самом выборе/изменении, если это возможно. Отдельный read-by-ID, затем проверка tenant в коде может открывать race или случайно вернуть данные в логе/ошибке. Transaction и DB constraints способны помочь обеспечить инвариант, но точный механизм зависит от схемы. Если используется row-level security, проверьте роль приложения, настройку session context, pool reuse и поведение при сбросе контекста.

Connection pool создаёт важную опасность: session state от одного tenant-а может пережить возврат соединения в пул. Используйте transaction-scoped настройку и проверяйте, что reset гарантирован при error, panic и cancellation. Тест на последовательные запросы A→B→A на одном connection выявляет часть утечек состояния. Не полагайтесь на то, что пул обычно выдаёт другое соединение.

Cache key обязан включать все параметры, влияющие на доступ и содержимое: tenant, resource ID, locale, role-sensitive view, version. Если ключ использует только resource ID, кэш может смешать арендаторов. Cache invalidation также scoped: изменение организации не должно очистить или показать другой tenant snapshot. Для shared public content нужна явная классификация, а не предположение «кэш виден всем».

Search index, object storage, logs и analytics — отдельные data paths. Фильтр tenant в SQL не защищает autocomplete endpoint, экспорт CSV, object URL или telemetry. Signed URL имеет срок действия и scope; его нельзя публиковать в логах. Background export требует повторной проверки actor и tenant, ограничений размера, контрольного статуса и удаления временного файла. Результаты analytics могут быть агрегированы, но нужно оценить возможность восстановления личности по малой группе.

## Модель разделения

Изоляцию можно обеспечить логически через общие таблицы с tenant column, схемами на арендатора или отдельными базами/аккаунтами. У каждого подхода разные trade-offs. Shared tables упрощают schema update и стоимость, но повышают зависимость от корректной фильтрации и shared resource limits. Schema-per-tenant может дать управление namespace, но усложняет миграции и пул. Database-per-tenant увеличивает изоляцию и гибкость backup, но повышает операционную цену, connection count, provisioning и агрегированное наблюдение.

Не выбирайте изоляцию только по числу строк или моде. Уточните требования: возможность data residency, отдельный encryption key, restore одного tenant-а, noisy neighbor protection, deletion, аудит, размер клиентов, RPO/RTO и ограничения команды. Слово «enterprise» не является измерением. Выведите конкретный риск и сформулируйте, что изменение модели реально улучшит.

Noisy neighbor — tenant, который потребляет непропорциональную долю CPU, соединений, очереди или storage. Fairness требует политики quotas, rate limit и приоритетов. Лимит на API по IP может объединить множество честных пользователей за NAT; лимит по tenant ID полезнее, но требует доверенного principal и контроля создания бесплатных tenant-ов. Отказ одного tenant-а не должен захватывать shared queue.

Административный доступ к данным арендатора — отдельная privilege boundary. Support-пользователь может временно смотреть содержимое для решения обращения, но основание, scope, срок и аудит должны быть определены. Break-glass доступ должен быть ограничен, наблюдаем и отзывать полномочия. Пометка «admin» не снимает необходимость проверки данных и logging. Пользователь должен понимать, если конкретный администраторский доступ включён в продуктовую модель.

Политика membership должна учитывать lifecycle приглашения, удаление участника и смену владельца. Приглашение может быть просрочено, переслано или принято пользователем с другой идентичностью. Session, созданная до отзыва роли, может жить дольше, чем ожидает оператор. Определите, проверяется ли полномочие на каждом критическом действии, как инвалидируются сессии и что видно в аудите после изменения.

## Утечки через ошибки и побочные каналы

Response body — не единственный канал. В логах, трассах, метриках, URL, referrer, кэше браузера и ошибках может оказаться чужой ID, имя или токен. Ошибка `resource belongs to tenant X` раскрывает существование и идентификатор соседа. Безопасная ошибка должна помогать клиенту действовать, не раскрывая внутренний scope. Диагностические детали ограничьте правами и сроком хранения.

Номер последовательности, размер ответа, время и различие в поведении иногда позволяют выводить сведения о соседнем tenant-е. Для обычной угрозы можно приоритизировать прямую утечку и SQL scope; для чувствительных клиентов учитывайте timing/aggregation attacks. Не обещайте защиту от side-channel, который не анализировался. Укажите уровень adversary и доступ к endpoint-ам.

Удаление tenant-а требует пути через все системы: primary data, search, cache, queue, object files, analytics, backup retention. «Soft delete» может блокировать доступ, но сохранять запись. «Hard delete» может быть отложен, пока сообщение не обработано. Требуются tracking status, cancellation и срок очистки. Персональные данные не копируйте в event payload без необходимости, иначе удаление усложнится.

## Тестирование матрицей

Создайте fixture минимум из tenant A и B, пользователя member и viewer, ресурсов разных владельцев и несуществующего ID. Проверяйте read, update, delete, list, search, export и background job. Для каждого объекта протестируйте свой tenant, чужой tenant, отозванную роль и некорректную связь. Не ограничивайтесь unit тестом policy; хотя бы один integration путь должен включать API и реальную границу хранилища в disposable environment.

Property-like проверка может генерировать случайное распределение tenant IDs и убеждаться, что результат каждого запроса является подмножеством разрешённого tenant-а. Убедитесь, что generator сам не повторяет только один удобный паттерн. Race-тестировать надо и смену membership во время запроса. Сохраняйте seed для воспроизведения. При отсутствии рабочей БД обозначьте интеграционную проверку как pending.

Проверяйте с пулом соединений при минимальном числе connections, чтобы принудительно повторно использовать состояние. Выполните A, возврат, B и снова A; добавьте ошибку и cancellation, прежде чем соединение вернётся. Тестируйте кэш с совпадающими resource ID для двух tenants. Для exporter убедитесь, что background job получает неизменяемый, авторизованный scope, а не читает текущую случайную session.

## Примеры Go

Функции моделируют классификацию контекста, но не security middleware. Каждый пример автономный и запускается как `go run main.go`.

### Проверка совпадения tenant scope
```go group=scope mode=run
package main
import "fmt"
func sameTenantScope(principalTenant, resourceTenant string) bool { return principalTenant != "" && resourceTenant != "" && principalTenant == resourceTenant }
func main() { fmt.Println(sameTenantScope("tenant-a", "tenant-a"), sameTenantScope("tenant-a", "tenant-b"), sameTenantScope("", "tenant-a")) }
```
Это только необходимая проверка совпадения явно названных областей tenant-а, а не решение об авторизации. Реальный principal должен быть получен из доверенной сессии, иметь membership, а ресурс должен принадлежать известному tenant-у; затем отдельно проверяются разрешение на действие и контекст. Равенство любых двух идентификаторов само по себе ничего из этого не доказывает.

### Классификация обращения по rate key
```go group=limit mode=run
package main
import "fmt"
func rateScope(authenticated, tenantKnown bool) string { if !authenticated { return "anonymous" }; if !tenantKnown { return "invalid-scope" }; return "tenant" }
func main() { fmt.Println(rateScope(false, false), rateScope(true, false), rateScope(true, true)) }
```
Выбор ключа должен учитывать abuse и справедливость. IP, account и tenant имеют разные свойства.

### Результат удаления
```go group=delete mode=run
package main
import "fmt"
func deletionState(active, pendingCopies bool) string { if active { return "active" }; if pendingCopies { return "cleanup-pending" }; return "deleted" }
func main() { fmt.Println(deletionState(true, false), deletionState(false, true), deletionState(false, false)) }
```
Статус не очищает данные. Реальный deletion workflow должен быть повторяемым, auditable и проверять каждую систему хранения.

## Практика E / M / H

**Easy — необходимое совпадение tenant scope.** Реализуйте `func SameTenantScope(principalTenant, resourceTenant string) bool`: верните `true`, только если оба явно переданных значения tenant scope непустые и равны. Имена `principalTenant` и `resourceTenant` обозначают уже полученные scope, а не ID пользователя и ID ресурса. `true` подтверждает лишь совпадение областей и никогда само по себе не разрешает доступ: требуются доверенная аутентификация, membership, принадлежность ресурса, действие и контекст.

**Medium — ключ квоты.** Реализуйте `func RateScope(authenticated, tenantKnown bool) string`: anonymous при отсутствии аутентификации; invalid-scope если tenant неизвестен; иначе tenant. Функция только выбирает класс, не реализует rate limiter.

**Hard — статус удаления.** Реализуйте `func DeletionState(active, pendingCopies bool) string`: active → `active`; inactive и pending copies → `cleanup-pending`; иначе `deleted`. Задайте owner и критерий завершения для каждого места хранения.

Private/public vectors покрывают совпадающие/различающиеся tenant scope, пустые значения, неизвестный scope и отложенную очистку. Grader не проверяет SQL, middleware, connection pool, membership или реальные права. Успех не доказывает tenant isolation приложения.

## Частые ошибки

- Доверять tenant ID из body. Связывайте его с серверной идентичностью и membership.
- Использовать непредсказуемость UUID как авторизацию. Любой валидный чужой ID должен отказать.
- Считать общий connection pool нейтральным. Тестируйте повторное использование session context.
- Забывать tenant в cache key, export или analytics. Пройдите весь data flow.
- Проверять роль только на list, но не на download или background worker. Постройте полную матрицу операций.
- Возвращать разные ответы для foreign/missing resources без причины. Обдумайте information disclosure.
- Удалить primary record и считать tenant удалённым. Отслеживайте все copies и retention.
- Вводить DB-per-tenant без операционного плана. Посчитайте миграции, backup, connections и provisioning.

## Самостоятельная лаборатория

Постройте тестовую матрицу TaskFlow для двух синтетических workspace. Включите CRUD, поиск, export и фоновое уведомление. Для каждого endpoint укажите principal, tenant source, server check, SQL/data scope, response/error и логируемые поля. Придумайте IDOR отрицательный сценарий для объекта B, запрошенного из session A, и проверьте, что output и лог не раскрывают данные соседа.

Добавьте сценарий смены роли при занятом connection pool, кэш с одинаковым ключом и удаление workspace с pending event. Укажите, какой сценарий требует реальной интеграционной среды. Не используйте реальные аккаунты или клиентские данные. Запишите остаточный риск, который не проверяется локальным harness.

## Итог и вопросы

Вы должны уметь отличать tenant selector от доверенного scope; проверять principal-resource-action; учитывать все хранилища и worker-ы; сравнивать logical и physical separation; защищать shared resource fairness; тестировать foreign-resource отрицательными cases; и отслеживать deletion lifecycle.

1. Откуда сервер получил авторитетный tenant scope?
2. Есть ли альтернативный путь к ресурсу через search/export/worker?
3. Какие данные могут остаться в pooled session или cache?
4. Как доказать, что удаление завершилось в каждой копии?
5. Какое integration proof нужно перед public multi-tenant use?

**Глоссарий:** tenant — изолируемая организация/клиент; IDOR — доступ к объекту по прямой ссылке без должной авторизации; noisy neighbor — tenant, чрезмерно расходующий shared resource; row-level security — ограничение строк политикой БД; break-glass — ограниченный аварийный административный доступ; cache key — ключ, определяющий область и вариант кэшированных данных.
