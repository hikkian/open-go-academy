# Блокировки строк и конкурентное обновление

**ID:** `middle-12` · **Уровень:** Middle · **Модуль:** PostgreSQL и транзакции · **Время:** 150 минут · **Зависимость:** `middle-11` · **Go:** 1.27.2 · **Учебная версия:** 2026.10

## Результат и маршрут

Защищать инвариант конкурентного изменения условным UPDATE или транзакционной блокировкой и проверять конфликт. После занятия вы должны уметь сформулировать инвариант словами, выбрать пример, который его нарушает, и объяснить, какая операция восстанавливает ожидаемый ход. Это глава для тех, кто уже написал программы на Go, знает функции, структуры, ошибки, тесты и базовые SQL-транзакции. Перед началом назовите одну конкретную ситуацию из своего проекта, где два действия могут пересечься или где чтение и изменение должны согласоваться.

Ориентируйтесь на последовательность: наблюдение → модель состояния → механизм → проверяемая реализация → ограничения доказательства. Сначала запустите примеры ниже. Не угадывайте порядок goroutine и не переносите поведение конкретной машины на все запуски. В вопросах БД уточняйте, какой именно statement и snapshot обсуждаются. Если термин незнаком, выпишите его своими словами до продолжения.

## Зачем нужна эта проблема

Операция «прочитать значение, вычислить новое, записать» содержит окно гонки: два запроса могут прочитать одно старое значение и оба решить, что обновление допустимо. Для простого счётчика выразите проверку прямо в SQL: `UPDATE accounts SET balance=balance-$1 WHERE id=$2 AND balance >= $1 RETURNING balance`. Ноль строк означает, что условие не выполнилось; это не обязательно инфраструктурная ошибка.

Для более сложного инварианта блокируйте нужные строки внутри транзакции и держите транзакцию короткой. Все конкурирующие пути должны брать блокировки в согласованном порядке. Следите за ошибками deadlock и serialization failure: повтор безопасен лишь тогда, когда вся операция идемпотентна или повторяется с новым transaction scope. Уникальный индекс остаётся важным последним гарантом уникальности, даже если приложение перед этим делает SELECT.

Практическая цена ошибки — не абстрактная «гонка». Это потерянное обновление, зависший запрос, повторный платёж, медленный shutdown или очередь, которая растёт быстрее обработки. Полезно описывать отказ тремя фразами: какое состояние было до события; какие две операции пересеклись; какой неверный результат появился. Такой разбор удерживает внимание на проверяемом причинном механизме.

## Модель и механизм

Сначала различайте состояние программы и расписание. Состояние — значения, владение ресурсами и открытые каналы. Расписание — чередование шагов, выбранное системой во время исполнения. Корректная программа должна давать допустимый результат при любом расписании, которое разрешено языком и используемыми примитивами. Если ответ верен только при предположении «эта goroutine, наверное, выполнится первой», это не контракт.

Для механизма полезны четыре вопроса. **Кто владеет изменяемым состоянием?** **Какая операция передаёт владение или синхронизирует доступ?** **Кто сообщает об окончании?** **Что происходит при ошибке или отмене?** Пишите ответы рядом с кодом. Не добавляйте канал, mutex или транзакцию до того, как поняли, какую связь они обязаны обеспечить.

Синхронизация имеет цену: блокировки создают ожидание, копирование тратит память, round trip к БД увеличивает задержку, а более сильная изоляция повышает вероятность конфликта. Но преждевременно выбирать «самый быстрый» механизм обычно нельзя: у него может не быть нужной семантики. Сначала сохраните инвариант, затем измеряйте полный путь типичной нагрузки и ищите узкое место.

### Рабочий пример 1 — `main.go`

Файл целиком компилируется командой `go run main.go`. Вывод не зависит от порядка получения отдельных результатов: программа суммирует оба значения. В примере есть конкретное подтверждение завершения всех производителей до закрытия канала.

```go group=middle-12-example1 mode=run
package main
import "fmt"
func update(balance, debit int64) (int64,bool) { if debit<0||balance<debit{return balance,false};return balance-debit,true }
func main(){next,ok:=update(40,12);fmt.Println(next,ok);same,ok:=update(5,8);fmt.Println(same,ok)}
```

Обратите внимание, какая строка синхронизирует завершение, кто закрывает канал и почему закрытие находится после отправок. Измените один вход так, чтобы добавить ещё одну работу, не меняя её жизненный цикл. Затем предскажите число вывода до запуска.

### Рабочий пример 2 — `main.go`

Это самостоятельная демонстрация центрального правила главы. Вызов можно воспроизвести без внешней базы, брокера, сети или случайных задержек. Он показывает локальный механизм и не подтверждает поведение сервиса в production окружении.

```go group=middle-12-example2 mode=run
package main
import "fmt"
func snapshot(readValue, laterCommit int64) int64 { _=laterCommit;return readValue }
func main(){fmt.Println(snapshot(10,11));fmt.Println(snapshot(0,5))}
```

Составьте таблицу из двух колонок: «что гарантирует код» и «что остаётся за его пределами». Например, mutex защищает доступ только в тех местах, где участники используют тот же mutex; чистый snapshot пример моделирует лишь переданный аргумент. Такая таблица предотвращает сильные выводы из маленького фрагмента.

### Рабочий пример 3 — `main.go`

Третий вариант отделяет событие и результат. Он нужен, чтобы потренировать чтение границы отмены или конкурентного изменения и придумать отрицательный случай. Сначала выполните с текущими параметрами, потом измените ровно один параметр, который переключает ветвь.

```go group=middle-12-example3 mode=run
package main
import "fmt"
type Versioned struct{ Value int64; Version int64 }
func compareAndSet(x Versioned, expected, next int64)(Versioned,bool){if x.Version!=expected{return x,false};x.Value=next;x.Version++;return x,true}
func main(){x,ok:=compareAndSet(Versioned{Value:7,Version:3},3,9);fmt.Println(x.Value,x.Version,ok)}
```

### Таблица диагностики

| Наблюдение | Проверяемое предположение | Маленький эксперимент |
|---|---|---|
| Прогресс остановился | Есть операция ожидания без возможного отправителя/разблокировки | Найдите все send/receive/Lock/Wait и владельца каждого |
| Иногда неверный результат | Конкурирующий путь обходит общий протокол | Повторите тест с `-race`, затем проверьте каждый доступ вручную |
| Результат есть, но порядок другой | Контракт обещал набор, а вы ожидали порядок | Зафиксируйте, требуется ли порядок и где он создаётся |
| Ошибка возникает после отмены | Отмена не прошла через зависимость или позднюю запись | Передайте context и проверьте каждую точку побочного эффекта |
| Транзакция видит неожиданное значение | Не определены уровень и граница снимка | Запишите порядок commit/statement и повторите на PostgreSQL |

## Типичные ошибки и исправление

Первая ошибка — считать `go f()` подтверждением выполнения `f`. Это лишь запуск. Добавьте канал результата или WaitGroup и отдельно продумайте отмену. Вторая — считать `time.Sleep` механизмом синхронизации. Задержка может сделать тест стабильным на одной машине, но она не задаёт отношение happens-before. Ждите событие, которое сообщает о нужном переходе.

Третья ошибка — защищать только запись, забывая чтение, либо держать lock только вокруг одной половины инварианта. Пройдите по всем обращениям к данным поиском; перечислите все владельцы. Четвёртая — считать, что буфер всегда лечит блокировку. Он лишь меняет порог, при котором она появится. Если потребитель никогда не прочитает, конечный буфер рано или поздно заполнится.

Пятая ошибка — закрыть канал там, где отправители ещё живы, или разрешить нескольким участникам закрывать его. Передайте одному владельцу право закрытия. Шестая — отменить ожидание родителя, но забыть дочернюю работу. Контекст кооперативен: код должен периодически читать `Done`, а драйвер или зависимость должны принимать переданный контекст.

Седьмая ошибка — принять зелёный race detector за доказательство всех расписаний. Он важен, но проверяет увиденные исполнения. Комбинируйте unit tests, разные входы, ручной аудит доступов и bounded нагрузку. В БД также не считайте один успешный тест сериализуемостью всех транзакций: используйте реальную версию PostgreSQL и сценарии конкурирующих соединений.

## Практика без AI

### Практический мост: блокировка строки и версия

Helper не выполняет `SELECT FOR UPDATE`/`UPDATE` и не создаёт конфликт транзакций. P3 применяет атомарное условие версии в `content/projects/p3/reference/store.go` (`UpdateTaskState`) и согласование членства; интеграционный тест проверяет role-revocation race и HTTP обновление в `content/projects/p3/reference/postgres_integration_test.go`, `TestPostgresTaskOutboxAndTenantIsolation`. Для реального DB-сценария используйте disposable PostgreSQL:

Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда поднимает только disposable PostgreSQL из P3 Compose на loopback-порту 55433; пароль существует только в окружении shell. Она ждёт healthcheck, запускает точный тест и удаляет контейнер и volume при завершении блока:

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle12 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидайте сериализованный результат отзыва роли и отказ устаревшей версии через условный UPDATE. Это сценарные свидетельства, не общий тест всех блокировок.

Уровни проверяют разные алгоритмы по теме главы. Векторы охватывают только чистую функцию: они не запускают goroutine, не устанавливают happens-before и не заменяют интеграционные проверки.

**Easy — `VersionMatch`.** Для [версияВХранилище,ожидаемаяВерсия] верните [1] при совпадении и [0] при конфликте.

**Medium — `ConditionalUpdate`.** Для [значение,версия,ожидаемаяВерсия,новоеЗначение] обновите строку только при совпадении версии; верните [значение,версия,обновлено(0/1)].

**Hard — `ApplyVersionedEdits`.** Вход — [значение,версия,ожидаемаяВерсия,новоеЗначение,...]. По порядку применяйте пары с совпадающей версией, повышая её после каждого успеха; конфликт пропускается. Верните [значение,версия,числоУспехов].

## Разбор границ и reasoning

### Условное обновление и конфликт версии

Оптимистическая версия помогает обнаружить, что строку изменили после чтения. В SQL это обычно условие в UPDATE по идентификатору и ожидаемой версии, после чего приложение проверяет число изменённых строк. Ноль строк может означать конфликт версии или отсутствие записи; различать эти случаи следует в соответствии с API и моделью доступа. Проверка версии и запись должны быть одной операцией базы или частью корректной транзакции. Нельзя сначала выполнить SELECT, сравнить версию в Go, а затем без условия обновить запись: между этими шагами конкурентная транзакция может победить. После конфликта не повторяйте слепо старое значение: перечитайте актуальное состояние и заново примените бизнес-решение, если это безопасно. Ограничьте переполнение версии и определите представление ошибки для вызывающего кода. Чистая функция задания упражняет переход состояния, но не проверяет SQL row count, блокировки или атомарность. Для этого нужен тест с двумя соединениями PostgreSQL, где один из конкурентов гарантированно получает конфликт.

## Самостоятельная лаборатория: конкретный сценарий

Условное обновление удобно, когда инвариант помещается в один SQL statement. Проверяйте `RowsAffected`: ноль строк означает конфликт версии, отсутствие строки или непройденное условие — трактуйте это в соответствии с API. В транзакции полезно различать ожидаемый конфликт и временную ошибку. Не повторяйте произвольный внешний side effect внутри retry. Идемпотентный ключ или outbox могут понадобиться при выходе за пределы транзакции, но это следующая тема, не свойство этого примера.

Выполните лабораторию в отдельной временной копии файла. Сначала сохраните исходный вывод. Затем измените один параметр или одну строку и запишите: какое предположение проверяется, какой результат вы ожидаете, какой результат реально получили. Если результат отличается, откатите изменение и уменьшите пример до двух действий. После объяснения ошибки восстановите код и добавьте проверку, которая обнаружит именно этот сбой. Не используйте случайные sleep, чтобы «поймать» нужное расписание; тест должен синхронизировать события явно или использовать детерминированные данные.

Минимальный журнал эксперимента содержит дату/версию инструмента, команду, входные данные, ожидаемый результат и наблюдение. Для чистой функции достаточно публичных и дополнительных граничных векторов. Для конкурентного кода укажите число участников, реальную точку синхронизации и команду race detector; отсутствие найденного отчёта ограничено пройденными путями. Для PostgreSQL запишите версию, уровень изоляции, две транзакции и порядок statements. Такие заметки помогают другому человеку воспроизвести ваш вывод, но не превращают домашний эксперимент в универсальную гарантию.

После проверки объясните, какие случаи не покрыты. Хорошее резюме признаёт границу: например, локальный тест не измеряет нагрузку production; таблица результатов не проверяет восстановление после потери процесса; один запрос не проверяет поведение при нескольких соединениях. Следующим действием должно быть конкретное расширение теста или инструментированное измерение, а не расплывчатое обещание «проверить всё».

### Ещё один проход: что меняется при отказе

Для конкурентного обновления сохраните ответ `RETURNING` и число затронутых строк. При retry заново прочитайте нужные данные и пересчитайте решение внутри новой транзакции; нельзя повторно отправлять старый SQL с устаревшим значением. Если действие после commit отправляет событие, две операции не становятся атомарными автоматически. Именно этот разрыв позже требует outbox-подхода. Пока важно не скрывать границу: SQL инвариант защищает строку, но не внешний брокер или отправку письма.

## Итог, повторение и словарь

Главная мысль: определите владение и инвариант до выбора механизма; сделайте завершение явным; тестируйте отказной путь; отделяйте локальную демонстрацию от системного доказательства. Для повторения через день нарисуйте состояния и стрелки синхронизации без исходного кода, а затем объясните код коллеге. Через неделю самостоятельно воспроизведите один отказ с изменением одного условия.

- **row lock — блокировка строки:** Синхронизация изменений выбранной строки до завершения транзакции.
- **optimistic concurrency — оптимистическая конкурентность:** Проверка версии или предиката при записи вместо ранней блокировки.
- **conditional UPDATE — условное обновление:** SQL изменение, которое применяет предикат и запись в одном statement.

Следующая глава `middle-13` использует эти договорённости дальше. Если пример компилируется, но объяснение результата пока не получается, не переходите к более сложному варианту: сначала перескажите модель без терминов, затем добавьте термин и конкретный тест.
