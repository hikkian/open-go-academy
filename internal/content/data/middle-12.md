# Блокировки строк и конкурентное обновление

## Что ты сделаешь

Ты напишешь три функции-модели для конкурентного обновления строки: проверку версии, условное обновление и применение последовательности правок с пропуском конфликтов. Примеры главы покажут, почему проверку и запись нужно делать одной операцией, и как блокировки строк связаны с порядком захвата.

## Окно гонки между чтением и записью

Операция «прочитать значение, вычислить новое, записать» содержит окно гонки. Два запроса могут прочитать одно старое значение, и оба решат, что обновление допустимо. Итог окажется неверным, хотя каждый запрос по отдельности выглядел корректно.

Самый простой способ закрыть окно — выразить проверку прямо в SQL. Условие записывается в `WHERE` того же `UPDATE`, поэтому проверка и изменение выполняются над одной актуальной версией строки:

```text
UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1 RETURNING balance
```

Если строка вернулась, операция прошла. Если не вернулась, условие не выполнилось: баланса не хватило или строки уже нет. Ноль затронутых строк — это сигнал, а не диагноз. Причину нужно уточнить отдельным чтением, если ответ важен пользователю.

## Версия строки как условие

Чаще строка хранит номер версии. Обновление проходит, только если версия в базе совпала с той, которую клиент читал. После успешной записи версия увеличивается. Так конфликт выявляется без блокировок: устаревший клиент просто не попадает в условие.

Чистая модель ниже повторяет это правило. Если версия совпала, значение заменяется и версия растёт. Если не совпала, строка остаётся прежней.

```go
package main

import "fmt"

func applyUpdate(version, expected int) (rows int) {
    if version == expected {
        return 1
    }
    return 0
}

func main() {
    fmt.Println(applyUpdate(3, 3), applyUpdate(3, 2))
}
```

Вывод: `1 0`. Первый вызов соответствует затронутой строке, второй — конфликту. В реальном коде число затронутых строк возвращает драйвер, и его проверяют сразу после `UPDATE`.

> **Важно.** Модель описывает правило версии, но не доказывает атомарность SQL-операции. Атомарность проверяет только реальная база, и такой тест должен работать с двумя соединениями.

## Блокировки строк и порядок захвата

Для более сложного инварианта строки блокируют внутри транзакции через `SELECT ... FOR UPDATE` или аналог. Блокировка держится до конца транзакции, поэтому транзакция должна быть короткой. Сетевой вызов или долгий расчёт внутри неё удерживают строку и мешают другим участникам.

Если транзакция блокирует несколько строк, все конкурирующие пути должны брать их в одном порядке. Иначе два участника могут взять одни и те же строки в разном порядке и ждать друг друга. Простое правило: блокировать по возрастанию идентификатора. Функция ниже показывает, как получить такой порядок из набора идентификаторов.

```go
package main

import (
    "fmt"
    "sort"
)

func lockOrder(ids ...int) []int {
    sorted := append([]int(nil), ids...)
    sort.Ints(sorted)
    return sorted
}

func main() {
    fmt.Println(lockOrder(7, 3, 5))
}
```

Вывод: `[3 5 7]`. Все пути берут блокировки в этом порядке, поэтому циклического ожидания не возникает. Сам порядок — соглашение, которое нужно записать и соблюдать везде.

## Повтор и уникальность

Ошибки deadlock и serialization failure означают, что база отменила конкурирующую транзакцию. Повтор безопасен только тогда, когда вся операция идемпотентна или выполняется заново в новой транзакции с новым чтением. Повторять один запрос из середины транзакции нельзя: предыдущие чтения устарели.

Попытки нужно ограничивать. Пример ниже моделирует повтор с новым чтением: первое ожидаемое значение не совпало, второе совпало, и операция прошла на второй попытке.

```go
package main

import "fmt"

func main() {
    version := 3
    attempts := 0
    for _, expected := range []int{2, 3} {
        attempts++
        if version == expected {
            version++
            break
        }
    }
    fmt.Println(version, attempts)
}
```

Вывод: `4 2`. Первая попытка видела устаревшую версию и не прошла, вторая прочитала актуальную и прошла. Цикл завершился по успеху, а не по бесконечному повтору.

Уникальный индекс остаётся последним гарантом уникальности. Даже если приложение перед вставкой делает `SELECT`, между проверкой и вставкой может появиться другой участник. Индекс отклонит дубликат в любом случае.

## Модель и механизм

Условный UPDATE проверяет условие и меняет строку в одном шаге, поэтому конкурент видит либо старую, либо новую версию строки. Модель здесь — версия строки и ожидаемая версия. Сравнивай их перед записью и считай ноль затронутых строк сигналом, а не диагнозом.

Для конкурентного обновления полезны три вопроса. Какой инвариант должен сохраняться? Какое условие проверяется вместе с записью? Что происходит с конкурентом, которого отклонили? Ответы записываются до написания запроса.

Блокировки имеют цену: ожидание, нагрузку на конкурентные пути и риск deadlock. Условный `UPDATE` дешевле, но выражает только простые инварианты. Для сложного инварианта нужна транзакция с блокировками и короткими границами.

## Типичные ошибки и исправление

Первая ошибка — читать строку, проверять условие в коде и только потом обновлять. Между чтением и записью другой участник успевает изменить строку. Исправление — условие в `WHERE` или блокировка на время проверки.

Вторая — считать ноль затронутых строк доказательством конкретной причины. Ноль означает, что условие не выполнилось, но причин несколько. Исправление — отдельно уточнить состояние строки, если ответ важен.

Третья — брать блокировки в разном порядке в разных путях. Исправление — единый порядок, например по возрастанию идентификатора, и проверка тестом с конкурентными соединениями.

> **Типичная ошибка.** Считать, что повтор после ошибки сериализации безопасен всегда. Если внутри транзакции был внешний платёж, повтор отправит его второй раз. Сначала определи идемпотентность.

## Если что-то пошло не так

- Баланс уходит в минус под нагрузкой → проверка и списание разделены; перенеси условие в `WHERE` и проверяй затронутые строки.
- Два запроса зависают друг за другом → блокировки взяты в разном порядке; задай единый порядок.
- Повтор создаёт дубликат → операция не идемпотентна; добавь ключ операции или уникальный индекс.
- Конфликт не виден в ответе → число затронутых строк не проверено; проверь его сразу после `UPDATE`.

## Лаборатория перед практикой

Создай в disposable базе строку с версией, например `version = 3`. Открой две сессии. В первой прочитай строку и запомни версию. Во второй выполни условный `UPDATE` с текущей версией и commit. Затем в первой сессии выполни условный `UPDATE` с той версией, которую она прочитала. Перед запуском запиши предсказание: сколько строк затронет первая сессия и почему.

Журнал эксперимента содержит версию сервера, текст обоих `UPDATE`, прочитанную версию, число затронутых строк в каждой сессии и итоговое значение. Если результат совпал с предсказанием, повтори эксперимент с блокировкой `SELECT ... FOR UPDATE` в первой сессии и запиши, что изменилось: вторая сессия будет ждать commit первой.

## Практика

### Практический мост: блокировка строки и версия

Функции этой практики не выполняют `SELECT FOR UPDATE` и `UPDATE` и не создают конфликт транзакций. Они показывают правило версии и правило повтора на переданных числах. P3 применяет условие версии в `content/projects/p3/reference/store.go`, в функции `UpdateTaskState`. Интеграционный тест `TestPostgresTaskOutboxAndTenantIsolation` в `content/projects/p3/reference/postgres_integration_test.go` проверяет конкурентные сценарии с отзывом роли и обновлением по версии. Для реального DB-сценария используй disposable PostgreSQL:

Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда поднимает только disposable PostgreSQL из P3 Compose на loopback-порту 55433; пароль существует только в окружении shell. Она ждёт healthcheck, запускает точный тест и удаляет контейнер и volume при завершении блока:

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle12 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидай сериализованный результат отзыва роли и отказ устаревшей версии через условный `UPDATE`. Это сценарные свидетельства, а не общий тест всех блокировок. Векторы этой главы охватывают только чистые функции.

### Задание 1 · Блокировки строк и конкурентное обновление — easy

**Цель.** Вход — `[версия в хранилище, ожидаемая версия]`. Верни `[1]`, если версии совпали, и `[0]` при конфликте. Если входа не два значения, верни `[0]`.

**Ожидаемый вывод** — входы: `[4, 4]`, затем `[4, 5]`:

```text
[1]
[0]
```

**Шаги.**
1. Выбери задание «Блокировки строк и конкурентное обновление — easy»: в файле есть `VersionMatch` с `panic("TODO")`. Импорты не нужны.
2. Если во входе не два значения, верни `[0]`.
3. Сравни версию в хранилище с ожидаемой.
4. Если они равны, верни `[1]`; иначе `[0]`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два среза из одного числа; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[1]` для входа из одного значения → длина входа не проверена.
- `[1]` при разных версиях → сравнение выполнено неточно.

> **Подсказка.** Сначала длина входа, потом равенство.

### Задание 2 · Блокировки строк и конкурентное обновление — medium

**Цель.** Вход — `[значение, версия, ожидаемая версия, новое значение]`. Если версия совпала с ожидаемой, замени значение и увеличь версию на единицу. Верни `[значение, версия, обновлено]`, где флаг равен `1` или `0`. При неполном входе или отрицательной версии верни `[0, 0, 0]`.

**Ожидаемый вывод** — входы: `[10, 3, 3, 12]`, затем `[10, 3, 2, 12]`:

```text
[12,4,1]
[10,3,0]
```

**Шаги.**
1. Выбери задание «Блокировки строк и конкурентное обновление — medium»: в файле есть `ConditionalUpdate` с `panic("TODO")`. Импорты не нужны.
2. Если входа не четыре значения или версия либо ожидаемая версия отрицательны, верни `[0,0,0]`.
3. Сравни версию с ожидаемой.
4. Если совпала, запиши новое значение, увеличь версию и верни флаг `1`.
5. Если не совпала, верни значение и версию без изменений и флаг `0`.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Два списка из трёх чисел; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[12,3,1]` для `[10, 3, 3, 12]` → версия не увеличена после успешной записи.
- `[12,4,1]` при несовпавшей версии → запись выполнена без проверки условия.
- Значения при отрицательной версии не обнулены → проверка входа пропущена.

> **Подсказка.** Сначала проверка входа, потом сравнение версий, потом запись.

### Задание 3 · Блокировки строк и конкурентное обновление — hard

**Цель.** Вход: `[значение, версия, ожидаемая версия, новое значение, ...]`. По порядку применяй пары с совпадающей версией; после каждого успеха версия растёт на единицу. Конфликтующую пару пропускай. Верни `[значение, версия, число успехов]`. Если входа меньше двух значений или версия отрицательна, верни `[0,0,0]`. Неполную последнюю пару пропусти.

**Ожидаемый вывод** — входы: `[10, 2, 2, 11, 3, 12, 3, 13]`, затем `[5, 0, 0, 6]`:

```text
[12,4,2]
[6,1,1]
```

**Шаги.**
1. Выбери задание «Блокировки строк и конкурентное обновление — hard»: в файле есть `ApplyVersionedEdits` с `panic("TODO")`. Импорты не нужны.
2. Если входа меньше двух значений или версия отрицательна, верни `[0,0,0]`.
3. Возьми значение и версию из первых двух элементов.
4. Иди по парам правок: ожидаемая версия и новое значение.
5. Если ожидаемая версия совпала с текущей, примени правку, увеличь версию и число успехов.
6. Иначе пропусти правку.
7. Верни `[значение, версия, успехи]`.
8. Нажми «Запустить» и сравни с блоком выше.
9. Нажми «Проверить».

**Как проверить себя.** Два списка из трёх чисел; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- Все правки применены, хотя версия устарела → проверка совпадения версии после первой успешной правки пропущена.
- Число успехов не совпадает с числом изменений версии → счётчик успехов не увеличен.
- Результат при входе с отрицательной версией не нулевой → проверка входа стоит после правок.

> **Подсказка.** Текущая версия меняется после каждой удачной правки, поэтому сравнивай с ней, а не с версией из входа.

## Итог

- Проверка версии и запись делаются одной операцией: условие в `WHERE` или блокировка на время проверки.
- Ноль затронутых строк сообщает, что условие не выполнилось, но не называет причину; её уточняют отдельно.
- Блокировки берут в едином порядке, а повтор после конфликта выполняют заново в новой транзакции и только для идемпотентной операции.
