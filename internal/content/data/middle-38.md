# TaskFlow: outbox и ограниченный worker

## Что ты сделаешь

Ты напишешь три проверки второго слоя TaskFlow: решение о действии с записью outbox, правило обработки повторной доставки события и ограниченную выборку пакета для worker. Функции получают значения и возвращают ответ. Они не пишут в базу, не отправляют события в брокер и не доказывают, что эффект случился ровно один раз. Это задача интеграционного теста с настоящей транзакцией.

## Порядок записи и публикации

Порядок шагов в worker важнее, чем кажется. Сначала worker читает пакет строк без публикации, затем отправляет каждое событие, и только после подтверждения брокера отмечает строку как опубликованную. Если отметить строку до отправки, сбой после отметки потеряет событие навсегда: строка выглядит опубликованной, а брокер её не видел.

Отметку тоже делают отдельной транзакцией с условием. Запись обновляется, только если она всё ещё находится в состоянии «не опубликовано». Тогда два параллельных worker не перепишут друг другу результат, а второй просто не найдёт строку среди непубликованных. Эту проверку нельзя заменить чтением в памяти процесса, потому что процессов несколько.

## Зачем outbox рядом с изменением

Когда задача TaskFlow создана, нужно сообщить остальным системам, что это произошло. Самый простой путь — отправить событие в брокер сразу после записи в базу. Он ломается на первом же сбое между двумя шагами. Запись в базе прошла, брокер недоступен, событие потеряно. Или наоборот: брокер принял событие, а транзакция откатилась, и подписчики получили то, чего в системе нет.

Outbox решает это записью намерения в ту же транзакцию, что и доменное изменение. В таблице `outbox` появляется строка, описывающая событие. Либо коммитятся обе записи, либо ни одна. Отдельный worker читает строки и публикует их в брокер. Так публикация отделена от запроса пользователя, и сбой брокера не отменяет созданную задачу.

Важно, что outbox не делает публикацию мгновенной. Событие появится у подписчиков позже, после следующего прохода worker. Если это недопустимо, задержку нужно измерить и записать в требования, а не надеяться на порядок вызовов.

## Решение по записи outbox

Для одной строки outbox есть три состояния. Если доменная транзакция не закоммичена, публиковать нечего: строки в outbox тоже нет, и действие называется `not_committed`. Если строка закоммичена и ещё не опубликована, нужна публикация. Если строка уже отмечена как опубликованная, worker подтверждает её и переходит к следующей.

Пример 1 показывает, как строка outbox создаётся вместе с изменением и попадает в лог только при коммите. Ошибка в середине транзакции откатывает оба изменения.

```go
package main

import "fmt"

type tx struct {
	tasks  []string
	outbox []string
}

func (t *tx) createTask(title string) {
	t.tasks = append(t.tasks, title)
	t.outbox = append(t.outbox, "task_created:"+title)
}

func main() {
	t := &tx{}
	t.createTask("Ship release")
	fmt.Println(len(t.tasks), len(t.outbox))
	fmt.Println(t.outbox[0])
}
```

Вывод: `1 1` и `task_created:Ship release`. В примере нет настоящей транзакции: в реальной базе обе записи попадают в одну транзакцию, и `commit` либо применяет их вместе, либо откатывает вместе. Пример показывает форму связи, а не механизм атомарности.

## Повторная доставка и идемпотентность

Worker публикует событие и может не получить подтверждение: сеть оборвалась, процесс упал после отправки, но до отметки в базе. При следующем проходе он отправит то же событие снова. Поэтому гарантия, которую даёт outbox, называется at-least-once: событие доставляется хотя бы один раз, возможно, больше.

Защита от повторного эффекта ставится на подписчика. Каждое событие имеет ключ, и обработчик запоминает, что по этому ключу эффект уже применён. Повторный ключ не меняет данные второй раз; он подтверждается как дубликат. Пример 2 показывает такой обработчик на словаре применённых ключей.

```go
package main

import "fmt"

var applied = map[string]bool{}

func apply(key string) string {
	if key == "" {
		return "missing_key"
	}
	if applied[key] {
		return "duplicate_ack"
	}
	applied[key] = true
	return "apply_once"
}

func main() {
	fmt.Println(apply("evt-1"))
	fmt.Println(apply("evt-1"))
	fmt.Println(apply(""))
}
```

Вывод: `apply_once`, `duplicate_ack`, `missing_key`. Пустой ключ проверяется первым: событие без ключа нельзя дедуплицировать, и его нужно отклонить, а не применять.

Словарь в памяти работает только в одном процессе и исчезает при перезапуске. Для сравнения: настоящая база переживает перезапуск, а словарь — нет, поэтому пример годится только для объяснения формы проверки. В TaskFlow ключ записывают вместе с эффектом в одну транзакцию, чтобы после падения эффект и отметка совпадали. Булева проверка в памяти этого не доказывает. Поэтому в разборе главы такой помощник назван warm-up проверкой.

## Лимит попыток и мёртвая очередь

Повторы нужны, но без предела они превращаются в бесконечный цикл. Каждое сообщение получает общий бюджет попыток. Временная ошибка даёт повтор, пока бюджет не исчерпан. Постоянная ошибка, например неверный формат события, не даёт повтора вовсе. Исчерпанное или постоянно сломанное сообщение переносят в отдельную очередь мёртвых писем. Там его смотрит человек или отдельный процесс, а основной поток идёт дальше.

Правило порядка здесь тоже важно. Если эффект уже применён, сообщение подтверждается, даже когда попытки исчерпаны: повторять нечего. Некорректный счётчик, например отрицательная попытка, означает ошибку в самом worker, и решение о сообщении не принимается.

## Ограниченная выборка

Worker не должен забирать из outbox все строки сразу. Большой пакет удлиняет транзакцию, держит блокировки и даёт всплеск нагрузки на брокер после перезапуска. Поэтому выборка ограничена размером пакета. Пример 3 показывает такую функцию: она возвращает не больше заданного числа строк и не падает на пустой очереди.

```go
package main

import "fmt"

func nextBatch(pending []string, limit int) []string {
	if limit <= 0 {
		return nil
	}
	if len(pending) < limit {
		return pending
	}
	return pending[:limit]
}

func main() {
	fmt.Println(nextBatch([]string{"a", "b", "c"}, 2))
	fmt.Println(nextBatch(nil, 2))
	fmt.Println(nextBatch([]string{"a", "b", "c"}, 5))
}
```

Вывод: `[a b]`, `[]`, `[a b c]`. Размер пакета задаётся настройкой, а не длиной очереди. Выбирать значение стоит по измерению: сколько строк worker успевает опубликовать за один проход и сколько держит транзакция без заметного роста задержки. Слишком маленький пакет тоже плох, потому что очередь начинает расти быстрее, чем уменьшается. При пустой очереди worker просто выходит из прохода и ждёт следующего.

## Что доказывает проверка повторного worker

Повторный worker проверяют запуском двух экземпляров над одной тестовой базой. Оба берут одни и те же строки, публикуют и пытаются отметить. Проверка проходит, если эффект на подписчике один, даже когда отметка выполнена дважды. Булева функция в этом не участвует: она не видит блокировок, гонок и перезапусков.

Поэтому выводы о exactly-once записаны осторожно. Outbox с дедупликацией даёт эффект ровно один раз только при условии, что эффект и ключ записываются атомарно на стороне подписчика. Если эффект идёт во внешний сервис без ключа, гарантии нет, и это нужно признать в описании системы.

## Типичные ошибки и исправление

> **Типичная ошибка.** Публиковать событие до коммита доменной транзакции. Подписчик получит событие о задаче, которой в базе нет.

Ошибки в этом слое часто выглядят безобидно. Чаще всего их замечают только под нагрузкой или после перезапуска, поэтому тест на одном процессе ничего не покажет. Строку outbox пишут после коммита отдельным запросом, и сбой между ними теряет событие. Повтор делают без лимита, и сообщение крутится вечно. Выборку берут без ограничения, и после паузы брокер получает сотни сообщений разом. Дедупликацию держат только в памяти процесса.

## Если что-то пошло не так

- Событие есть у подписчика, а задачи в базе нет → публикация стоит до коммита; перенеси запись outbox в транзакцию.
- Одно сообщение публикуется каждые несколько секунд навсегда → лимит попыток не задан; добавь общий бюджет и dead-letter.
- После перезапуска брокер получает всплеск → выборка без ограничения; задай размер пакета.
- Подписчик применил эффект дважды → ключ не записан вместе с эффектом; сделай запись атомарной.

## Итог

- Строка outbox коммитится вместе с доменным изменением, а worker публикует её позже; так сбой брокера не теряет событие и не отменяет задачу.
- Повторная доставка защищается ключом события на стороне подписчика, общим лимитом попыток и мёртвой очередью для сообщений, которые не удаётся обработать.
- Булевы помощники проверяют решения, но exactly-once и восстановление после перезапуска доказываются интеграционным тестом с настоящими транзакциями.
