# 38. TaskFlow: outbox и ограниченный worker

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `middle-37`; предыдущая глава `middle-37`.  
**Планируемый порядок каталога:** 78.  
**Результат:** Связывать изменение домена и outbox intent одной транзакцией.; Обрабатывать повторную доставку через устойчивую идемпотентность, retry budget и dead-letter policy.; Понимать, что булевый helper не доказывает долговечное хранение или exactly-once effect.

## Глоссарий

- **outbox (исходящий журнал)** — Запись события в той же транзакции, что и доменное изменение.
- **at-least-once delivery (доставка минимум один раз)** — Модель доставки, допускающая повтор события после потери подтверждения.
- **idempotency (идемпотентность)** — Повтор одной команды не создаёт повторного бизнес-эффекта.
- **dead-letter queue (очередь необрабатываемых сообщений)** — Отдельное место для событий, исчерпавших политику повторов.
- **worker lease (аренда задачи worker)** — Временное владение задачей с восстановлением после истечения срока.

## Теория и границы применения

Outbox решает разрыв между сохранением доменного изменения и отправкой сообщения. Если сервис сначала фиксирует задачу в базе, а затем отдельно публикует событие, процесс может упасть между этими действиями. Записывайте бизнес-изменение и outbox intent в одной транзакции. Worker позже читает ожидающие записи и публикует их. Это гарантирует сохранённое намерение при успешном commit, но не exactly-once доставку через базу и брокер.

Worker должен иметь bounded batch, ограниченный параллелизм и срок аренды записи. При захвате пометьте запись владельцем/lease до публикации так, чтобы другой worker не забрал её одновременно; после истечения lease просроченная работа может восстановиться. Конкретное SQL зависит от базы: для PostgreSQL часто используют транзакционный выбор строк с `FOR UPDATE SKIP LOCKED`, но корректность требует проверить уровень изоляции и длительность транзакции. Не удерживайте транзакцию открытой на время медленного сетевого вызова.

После публикации подтвердите outbox запись отдельным переходом. Если сообщение ушло, а процесс упал до ack, запись будет отправлена повторно. Consumer должен хранить уникальный event key рядом с изменением эффекта, используя транзакцию и ограничение уникальности. Переданный параметр `alreadyApplied` в `IdempotencyResult` не доказывает, что состояние дедупликации долговечно или атомарно прочитано. Повторное сообщение должно завершаться без второго эффекта, в том числе при конкурентной обработке.

Ошибки классифицируйте: transient допускает ограниченный retry с backoff, permanent или исчерпанный бюджет переводит событие в dead-letter состояние с безопасным диагностическим контекстом. Не удаляйте событие после первой ошибки. Не храните секреты, полные payload или персональные данные в логах и метках. Для ручного replay предусмотрите аудит, права и защиту от произвольного изменения ключа или содержимого.

Проектная проверка должна воспроизвести crash boundaries: rollback до commit оставляет ни доменного изменения, ни события; commit до publish сохраняет событие; publish до ack допускает повтор; повтор consumer не дублирует эффект. Проверьте два worker одновременно, истечение lease, остановку во время обработки, retry exhaustion и cleanup временных данных на изолированной базе и тестовом брокере.

Малые helpers `OutboxAction`, `WorkerDisposition` и `IdempotencyResult` подтверждают лишь заданные таблицы решений. Они не выполняют транзакцию, аренду, доставку, дедупликацию либо восстановление worker. Сохраняйте эти distinctions в отчёте теста и не заявляйте exactly-once как свойство системы без гораздо более точного определения границы эффекта.

Таблица отказов помогает решить, кто владеет восстановлением: ошибка до commit оставляет исходное состояние; ошибка после commit оставляет событие доступным; timeout публикации имеет неопределённый исход и требует безопасного повтора; ошибка подтверждения после успешной доставки также допускает duplicate. Запишите статус строки outbox и ожидаемое число бизнес-эффектов после каждой точки. Retry должен иметь предел и постепенно растущую задержку; иначе постоянная ошибка образует горячий цикл. Dead-letter запись сохраняет причину и ссылку для диагностики с ограниченным сроком хранения. Replay выполняет уполномоченный оператор после исправления причины и повторно использует тот же event key. Приёмочное интеграционное испытание временно блокирует тестовый брокер, перезапускает worker и сверяет количество записей до/после. Окружение и broker образ должны быть закреплены, а cleanup удаляет только изолированные тестовые данные. Такие проверки дают доказательство для конкретного сценария, но не доказывают отсутствие всех точек отказа.

## Три самостоятельных запускаемых примера

### Пример 1: `OutboxAction`

Контракт: Нет commit→not_committed; уже published→ack; иначе publish.

```go
package main

import "fmt"

func OutboxAction(committed, published bool) string {
	if !committed { return "not_committed" }; if published { return "ack" }; return "publish"
}

func main() {
	fmt.Println(OutboxAction(true, false))
}
```

### Пример 2: `WorkerDisposition`

Контракт: Некорректный счётчик→invalid; уже применён эффект→ack; постоянный сбой или лимит→dead_letter; иначе retry.

```go
package main

import "fmt"

func WorkerDisposition(attempt, maxAttempts int, transient, effectApplied bool) string {
	if attempt < 0 || maxAttempts <= 0 { return "invalid" }; if effectApplied { return "ack" }; if !transient { return "dead_letter" }; if attempt >= maxAttempts { return "dead_letter" }; return "retry"
}

func main() {
	fmt.Println(WorkerDisposition(1, 5, true, false))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `IdempotencyResult`

Контракт: Пустой ключ→missing_key; повтор уже применённого события→duplicate_ack; иначе apply_once.

```go
package main

import "fmt"

func IdempotencyResult(key string, alreadyApplied bool) string {
	if key == "" { return "missing_key" }; if alreadyApplied { return "duplicate_ack" }; return "apply_once"
}

func main() {
	fmt.Println(IdempotencyResult("evt-1", true))
}
```
