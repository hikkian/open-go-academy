# Authn, authz и границы tenant

## Что ты сделаешь

Ты напишешь три функции решений доступа: сравнение границ арендатора (tenant), выбор между отказом и разрешением по владельцу и таблицу решений для задачи, где учитываются вход, роль, операция, арендатор и владелец. Все функции чистые: они решают по переданным значениям и не обращаются к сессиям или базе.

## Authentication и authorization

Аутентификация (authentication) отвечает на вопрос, кто перед нами: по cookie, токену или сертификату. Авторизация (authorization) отвечает на другой вопрос: что этот клиент может сделать с конкретным ресурсом. Первое решается один раз на запрос, второе — для каждой операции и каждого ресурса.

Ошибка возникает, когда успешный вход принимают за разрешение на всё. Клиент вошёл, но задача принадлежит другому арендатору или другому пользователю. Поэтому решение доступа включает и субъекта, и ресурс, и операцию.

> **Важно.** Вход в систему не даёт права на чужой ресурс. Каждое действие проверяется отдельно, даже если клиент уже прошёл аутентификацию в этом же запросе.

## Граница арендатора

Арендатор (tenant) — это граница данных между клиентами системы. Если идентификатор арендатора пришёл из запроса, его нельзя считать доказательством: клиент может подставить любой. Надёжный источник — сессия или токен, а сравнение с арендатором ресурса решает, допустим ли доступ.

Пустой идентификатор арендатора означает, что граница не определена. Если сравнить две пустые строки, получится ложное совпадение, и чужие данные окажутся доступны. Поэтому пустой арендатор — это ошибка входа, а не значение по умолчанию.

Пример показывает, почему пустую строку нельзя считать совпадением:

```go
package main

import "fmt"

func main() {
    principal, resource := "", ""
    fmt.Println(principal == resource, principal != "" && principal == resource)
}
```

Вывод: `true false`. Прямое сравнение дало бы совпадение для двух пустых арендаторов. Правильная проверка сначала отбрасывает пустые значения.

## Владелец ресурса

Внутри одного арендатора доступ обычно ограничивает владелец ресурса. Пользователь видит свою задачу, но не задачу коллеги, даже если оба работают в одной организации. Сравнение идёт по идентификатору пользователя из сессии, а не по полю из тела запроса.

Отказ по владельцу отличается от отказа по аутентификации. Не вошедший клиент получает ответ «неаутентифицирован». Вошедший, но чужой, получает «запрещено». Смешивание этих ответов мешает клиенту понять, что исправить: войти или запросить доступ.

## Таблица решений

Решение по задаче зависит от пяти входов: вход в систему, роль, операция, арендатор и владелец. Удобно записать допустимые пары роли и операции отдельно и проверять их после границ. Например, владелец может читать и менять свою задачу, соавтор может менять, наблюдатель — читать. Во всех случаях задача должна принадлежать тому же арендатору и тому же владельцу.

Пример показывает такую таблицу. Допустимые пары перечислены явно, и неизвестная роль не получает доступа:

```go
package main

import "fmt"

func allowed(role, operation string) bool {
    table := map[string][]string{
        "owner":  {"read", "write"},
        "editor": {"write"},
        "viewer": {"read"},
    }
    for _, op := range table[role] {
        if op == operation {
            return true
        }
    }
    return false
}

func main() {
    fmt.Println(allowed("viewer", "read"), allowed("viewer", "write"), allowed("admin", "read"))
}
```

Вывод: `true false false`. Наблюдатель читает, но не пишет. Роль `admin` в таблице отсутствует, поэтому доступа у неё нет, пока таблицу не расширят.

## Чистые векторы и их границы

Чистые функции главы проверяют таблицу решений на выбранных входах. Они не доказывают, что cookie защищена, что токен не подделан и что база возвращает задачу только своему арендатору. Эти свойства проверяются интеграционными тестами с реальным маршрутом и данными двух арендаторов.

Отрицательные тесты важнее позитивных. Нужно добавить сценарий чужого арендатора, сценарий чужого владельца и роль вне таблицы. Во всех трёх проверяется отсутствие доступа и отсутствие побочных изменений, например записи в журнал аудита о чужом действии.

## Сессия как источник личности

Личность клиента и его арендатор берутся из сессии или подписанного токена, который выдал сервер при входе. Сессия имеет срок жизни и может быть отозвана. Поэтому решение доступа должно учитывать не только факт входа, но и то, что сессия ещё действительна. Просроченный токен с правильными полями не даёт доступа.

Идентификаторы из тела запроса используются только как указание, какой ресурс нужен. Право на него проверяется сравнением с данными сессии и хранилища. Если клиент прислал чужой идентификатор задачи, сравнение владельца отвергнет его, даже при полностью корректной сессии.

## Аудит отказов

Отказ в доступе тоже событие, которое нужно записать. Журнал должен содержать идентификатор клиента, арендатора, операцию и категорию отказа, но не содержимое задачи. Частые отказы одного клиента по разным арендаторам — признак перебора идентификаторов, и такой сигнал полезнее, чем единичный отказ.

Запись отказа не должна менять данные ресурса. Побочные изменения при отказе — отдельная ошибка: например, отказ после частичной записи может оставить задачу в промежуточном состоянии. Поэтому проверка доступа выполняется до первой записи, а не посередине операции.

## Что не делает таблица

Таблица решений не отвечает на вопрос, правильно ли заведены роли и кто их назначил. Если администратор выдал роль редактора не тому пользователю, функция проконтролирует только саму пару роли и операции. Права назначения ролей проверяются отдельно, и их проверка тоже требует отрицательного теста.

## Модель и механизм

Для решения доступа полезны четыре вопроса. Кто клиент и откуда известна его личность? Какой арендатор владеет ресурсом? Кто владелец ресурса? Что разрешено роли для этой операции? Ответы записываются как таблица до написания обработчика.

Синхронизация здесь не нужна: решение чистое. Если таблицу правят несколько людей, её изменения нужно проводить через обычный ревью, как любой код, потому что одно лишнее слово в ней меняет то, кто видит чужие данные. Цена подхода — таблица растёт вместе с ролями, и её нужно хранить рядом с кодом, а не в голове разработчика.

## Типичные ошибки и исправление

Первая ошибка — брать арендатора из тела запроса. Исправление — арендатор из сессии или токена.

Вторая — сравнивать пустые арендаторы. Исправление — пустое значение отвергается до сравнения.

Третья — отвечать «запрещено» неаутентифицированному клиенту. Исправление — отдельный ответ «неаутентифицирован».

Четвёртая — выдавать роли доступ по умолчанию. Исправление — неизвестная роль и операция дают отказ.

> **Типичная ошибка.** Проверять только арендатора и забывать владельца внутри него. Тогда любой сотрудник организации читает задачи коллег.

## Если что-то пошло не так

- Клиент видит задачу другого арендатора → сравнение арендатора не выполняется или берёт значение из запроса.
- Пустой арендатор проходит проверку → пустое значение не отвергнуто до сравнения.
- Пользователь меняет чужую задачу → проверка владельца отсутствует для записи.
- Новая роль получает доступ без изменения таблицы → доступ выдан по умолчанию, а не по таблице.

## Практика

Эти задания моделируют решения доступа по переданным значениям. Функции не читают сессию и не обращаются к базе. Закрытые примеры видны только в «Проверить».

### Задание 1 · Easy: authn, authz и границы tenant — базовое правило

**Цель.** Реализуй `AccessDecision(principalTenant, resourceTenant string) string`. Если любой арендатор пустой, верни `"invalid"`. Если арендаторы равны и непусты, верни `"tenant_match"`. Иначе верни `"deny"`. Сравнение точное, с учётом регистра.

**Ожидаемый вывод** — входы: `t1, t1`; затем `"", t1`; затем `t1, ""`:

```text
"tenant_match"
"invalid"
"invalid"
```

4. Иначе верни `"deny"`.

**Как проверить себя.** Три строки в кавычках; вывод совпадает; все три критерия зелёные.

**Если не принято.**
- `"tenant_match"` для пустых арендаторов → пустое значение не отвергнуто до сравнения.
- `"tenant_match"` для `T1` и `t1` → сравнение выполнено без учёта регистра.
- `"deny"` при пустом арендаторе → пустое значение отнесено к отказу, а не к ошибке входа.

> **Подсказка.** Сначала пустые значения, потом точное сравнение.

- `"allow"` для чужого владельца → сравнение идентификаторов не выполнено.

> **Подсказка.** Порядок такой: вход, пустые значения, совпадение владельца.

**Ожидаемый вывод** — входы по порядку: владелец читает свою задачу; владелец пишет свою задачу; редактор пишет свою задачу; наблюдатель читает свою задачу:

**Если не принято.**
- `true` для наблюдателя при записи → таблица пар не применяется.
- `true` для чужого владельца → сравнение владельца пропущено.
- `true` при пустом арендаторе → пустое значение не отвергнуто.

> **Подсказка.** Вход, арендатор, владелец и только потом таблица ролей.

## Воспроизводимая лабораторная: отрицательные сценарии доступа

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Сервер и база не нужны: таблица решений проверяется в памяти программы.

Программа ниже проверяет три отрицательных случая: чужой арендатор, чужой владелец и роль вне таблицы. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import "fmt"

func authorize(authenticated bool, role, op, pTenant, tTenant, pID, oID string) bool {
    if !authenticated || pTenant == "" || tTenant == "" || pTenant != tTenant {
        return false
    }
    if pID != oID {
        return false
    }
    table := map[string][]string{"owner": {"read", "write"}, "editor": {"write"}, "viewer": {"read"}}
    for _, allowedOp := range table[role] {
        if allowedOp == op {
            return true
        }
    }
    return false
}

func main() {
    fmt.Println("other tenant:", authorize(true, "owner", "read", "t1", "t2", "u1", "u1"))
    fmt.Println("other owner:", authorize(true, "editor", "write", "t1", "t1", "u1", "u2"))
    fmt.Println("unknown role:", authorize(true, "admin", "read", "t1", "t1", "u1", "u1"))
}
```

**Ожидайте:** три строки `other tenant: false`, `other owner: false` и `unknown role: false`. Каждый отрицательный случай закрыт своей проверкой, и ни один не даёт доступа по умолчанию.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/<каталог>`.

## Итог

- Аутентификация отвечает, кто клиент; авторизация решает, что ему разрешено с конкретным ресурсом, и проверяется для каждой операции.
- Граница арендатора берётся из сессии, а не из запроса; пустой арендатор отвергается до сравнения.
- Таблица пар роли и операции явная; неизвестная роль и чужой владелец дают отказ, а не доступ по умолчанию.
