# 27. Authn, authz и границы tenant

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `juniorplus-16`; предыдущая глава `middle-26`.  
**Планируемый порядок каталога:** 67.  
**Результат:** Проверить principal, tenant и владельца ресурса в одной роли; отрицательные IDOR случаи.

## Глоссарий

- **authentication (аутентификация)** — Проверка credential и получение доверенного principal.
- **authorization (авторизация)** — Решение, может ли principal выполнить операцию над объектом.
- **tenant (граница tenant)** — Изолированная область данных; tenant из тела запроса сам по себе не является доверенным.
- **IDOR (ошибка прямого доступа к объекту)** — Доступ к чужому ресурсу через подменённый или угадываемый идентификатор.

## Теория и границы применения

В TaskFlow пользователь вызывает `GET /v1/tasks/{id}`. HTTP-слой разбирает запрос, но principal должен поступить из проверенного механизма аутентификации. Клиент может прислать любой task ID и tenant в query/body; эти значения описывают запрос, но не доказывают владение. На стороне service извлекается задача, а затем сравниваются доверенный principal, tenant задачи и разрешённое действие. Repository должен ограничивать выборку tenant’ом из principal либо возвращать запись для явной проверки — выбор зависит от модели данных, и его нужно проверить на реальном запросе.

Authentication отвечает «кто действует?», authorization — «может ли он выполнить это действие над этим объектом?». Эти решения связаны, но не взаимозаменяемы. Валидный principal не означает право на любую задачу. Совпадение tenant тоже не означает, что любой участник tenant может менять объект. Поэтому модель доступа включает действие, роль, tenant и владение. В примерах роли owner/editor/viewer условны: в реальном продукте матрица должна быть утверждена владельцем продукта, а не выведена из имени роли.

Для каждого endpoint зафиксируйте доверенные источники. Например: middleware валидирует сессию и помещает principal в context; service получает именно этот principal; route ID считается недоверенным; найденная задача содержит tenant и owner из базы; проверка выполняется до изменения. Не читайте principal из заголовка, который может без проверки прислать клиент. Не принимайте `tenant_id` из тела как замену scope principal. Запрос с чужим ID должен дать выбранный публичный ответ без чтения или изменения чужого состояния. Возврат 404 вместо 403 может скрывать существование объекта, но не исправляет отсутствие проверки доступа.

Задания этой главы — три чистых helper-контракта. `AccessDecision` сравнивает два значения tenant; `OwnerDecision` задаёт приоритет authentication над сравнением ID; `AuthorizeTask` проверяет ограниченную таблицу role × operation × tenant × owner. Они полезны, чтобы формализовать правило и проверить ветви на таблице решений. Они не создают principal, не читают HTTP, не обращаются к базе и не проверяют транзакционную гонку. Даже полный набор векторов подтверждает только возвращаемое значение helper на этих входах.

Для проверки приложения добавьте handler/service integration tests на настоящем тестовом хранилище: собственная задача разрешена; другой владелец того же tenant отклонён; другой tenant отклонён; изменённый ID не раскрывает данные; отказ не меняет запись. Если чтение и изменение должны быть атомарны, проверьте конкурентный сценарий и SQL-условие/транзакцию. Поддельный repository полезен для проверки orchestration, но не доказывает поведение PostgreSQL. Отдельно проверяется, что principal создаёт доверенная auth middleware, а не тестовый заголовок без подписи.

Думайте о `ownerID` как о поле авторитетной записи, а не о произвольном втором аргументе. В чистой функции два ID сравнимы, но функция не может установить их происхождение. Интеграционная проверка должна подтвердить, что owner ID поступает из загруженного ресурса и что загрузка ограничена нужным tenant. Нельзя считать систему защищённой от IDOR, пока не пройден конкретный путь от сетевого запроса к данным.

Перед изменением политики составьте decision table: authenticated?; tenant пуст?; tenant совпал?; principal равен owner?; role поддерживается?; действие допустимо? Зафиксируйте порядок отказов там, где результат различается. `OwnerDecision` сначала отклоняет неаутентифицированный запрос даже при пустых ID. Это удобная чистая политика, но публичный HTTP код и текст ошибки остаются решением handler. Добавьте несовпадающие значения, пустые значения и одновременные нарушения, иначе тест может пропустить изменение приоритета.

Наконец, разграничьте доказательства. Unit tests подтверждают чистые правила. Integration tests подтверждают связку middleware, handler, service и хранилища в заданной конфигурации. Threat model описывает то, чего эти тесты не покрывают: компрометацию сессии, ошибку настройки, обходной endpoint, межсервисные полномочия и конкурентное изменение. В этой учебной главе нет проверки production-изоляции, криптографии, полноты всех маршрутов или публичной multi-tenant безопасности.

## Разбор решения: запрос на чтение задачи

Пусть проверенный principal равен `(user-7, tenant-a)`, а маршрут содержит `/v1/tasks/42`. Route parameter — лишь selector записи, не полномочие. Handler получает principal из доверенного request context, затем вызывает сервис с principal и task ID. Клиент может послать `tenant=b` в body, но сервис не должен использовать это поле, чтобы расширить scope. При `tenant-a` и owner `user-7` чтение допускается, если политика разрешает read этой роли. При той же задаче и principal `user-8` tenant совпадает, но владение может не совпасть — один tenant check недостаточен. При задаче tenant-b должны быть отклонены и владелец user-7, и подставленный body tenant-a.

При чтении из repository полезно ограничить запрос одновременно task ID и доверенным tenant, если схема/индексы это позволяют. Тогда запись другого tenant не попадёт сервису как обычный результат. Но это решение зависит от схемы и должно быть подтверждено SQL test. Если repository возвращает объект до проверки, service обязан корректно обработать его и не сериализовать данные при отказе. Добавьте assertion на response body и состояние базы.

`AuthorizeTask` не моделирует lookup и потому принимает `taskTenant` и `ownerID` как вход. Проверка всех векторов не делает эти аргументы доверенными. В реальном обработчике подставьте только значения, прочитанные из авторитетного источника, и отдельно тестируйте входное преобразование. Эта разница между policy input и source-of-truth — ключ к тому, чтобы таблица решений не превращалась в ложное обещание защиты.

## Порядок решений и тестовые случаи

При проверке нескольких условий заранее выберите приоритет и сохраните его в контракте. Например, unauthenticated должен отклоняться до сравнения owner ID; пустой идентификатор не должен случайно совпасть с другим пустым значением; неизвестная роль должна быть deny-by-default. Табличные vectors должны содержать случаи, где одновременно нарушены два условия, потому что такая пара проверяет порядок, а не только каждое условие отдельно. Решение публичного кода ответа принимается HTTP-слоем и не выводится напрямую из helper-метки.

## Три самостоятельных запускаемых примера

### Пример 1: `AccessDecision`

Контракт: Пустой tenant → invalid; разные tenant → deny; совпадение → tenant_match.

```go
package main

import "fmt"

func AccessDecision(principalTenant, resourceTenant string) string {
	if principalTenant == "" || resourceTenant == "" { return "invalid" }; if principalTenant != resourceTenant { return "deny" }; return "tenant_match"
}

func main() {
	fmt.Println(AccessDecision("tenant-a", "tenant-a"))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `OwnerDecision`

Контракт: Порядок: unauthenticated; затем пустые ID → invalid; несовпавший владелец → forbidden; иначе allow.

```go
package main

import "fmt"

func OwnerDecision(principalID, ownerID string, authenticated bool) string {
	if !authenticated { return "unauthenticated" }; if principalID == "" || ownerID == "" { return "invalid" }; if principalID != ownerID { return "forbidden" }; return "allow"
}

func main() {
	fmt.Println(OwnerDecision("u1", "u1", true))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `AuthorizeTask` — ограниченная helper-matrix

Матрица использует owner/editor для read и write, viewer — только для read; все остальные условия см. в Hard-контракте ниже.

```go
package main

import "fmt"

func AuthorizeTask(authenticated bool, role, operation, principalTenant, taskTenant, principalID, ownerID string) bool {
	if !authenticated { return false }
	if principalTenant == "" || taskTenant == "" || principalTenant != taskTenant { return false }
	if principalID == "" || ownerID == "" || principalID != ownerID { return false }
	if operation != "read" && operation != "write" { return false }
	switch role {
	case "owner", "editor": return true
	case "viewer": return operation == "read"
	default: return false
	}
}

func main() {
	fmt.Println(AuthorizeTask(true, "owner", "write", "t1", "t1", "u1", "u1"))
}
```

`go run .` запускает только helper.

## Практика Easy / Medium / Hard

**Easy — базовое правило.** Реализуйте `func AccessDecision(principalTenant, resourceTenant string) string`. Контракт: Пустой tenant → invalid; равные непустые → tenant_match; разные → deny. Helper не знает источника tenant. Скрытые и публичные vectors закреплены в grading spec.

**Medium — граничная политика.** Реализуйте `func OwnerDecision(principalID, ownerID string, authenticated bool) string`. Контракт: Порядок: неаутентифицированный → unauthenticated; затем пустые ID → invalid; несовпавшие ID → forbidden; иначе allow. Это решение по аргументам, не проверка происхождения ID. Скрытые и публичные vectors закреплены в grading spec.

**Hard — helper-проверка.** Реализуйте `func AuthorizeTask(authenticated bool, role, operation, principalTenant, taskTenant, principalID, ownerID string) bool`. Контракт: Helper-матрица: true только при authenticated, совпавших непустых tenant и owner, поддерживаемой роли и операции. owner/editor: read/write; viewer: read. Не доказывает защиту endpoint или SQL от IDOR. Скрытые и публичные vectors закреплены в grading spec.

## Лабораторная карточка TaskFlow: tenant и владелец задачи

Подготовьте изолированное тестовое хранилище с двумя tenant (`tenant-a`, `tenant-b`) и тремя пользователями. В `tenant-a` создайте задачу владельца `user-1`, а пользователя `user-2` оставьте участником без владения. В `tenant-b` создайте задачу `user-3`. Запишите seed IDs, чтобы тест не зависел от порядка предыдущих запусков. Укажите, какой auth middleware устанавливает principal и почему значения `tenant_id`/`owner_id` из HTTP body не считаются доверенными.

Проверьте таблицу access: анонимный запрос; authenticated owner read/write; другой пользователь того же tenant; владелец другого tenant; неизвестная роль; неизвестное действие; отсутствующая задача. Для каждого отказа проверьте код/форму ответа и отсутствие изменения данных. Если API намеренно возвращает одинаковый 404 для чужого и отсутствующего объекта, зафиксируйте это как продуктовую политику. Не считайте одинаковый ответ доказательством, пока не проверили отсутствие утечки содержимого и побочного эффекта.

Добавьте два уровня тестов. В unit test передайте все строки прямо в `AuthorizeTask` и подтвердите роль/operation matrix. В integration test пройдите настоящую цепочку HTTP → middleware → handler → service → test database. Проверьте, что task tenant и owner загружены из authoritative row, а client не может подменить principal через query/body/header. Напишите, какой именно SQL запрос/условие исполнялось и как тест изолирует состояние.

Для update определите гонку между проверкой доступа и изменением. Если владение или tenant могут измениться параллельно, используйте транзакцию/условное обновление согласно модели хранения и добавьте конкурентный тест. Один helper или последовательный тест не проверяет TOCTOU. Не утверждайте, что вся система защищена от IDOR: вывод ограничивается конкретным endpoint, политикой ролей, схемой и выполненными запросами.

Завершите заметку: commit, команда, Go version, база/схема, набор IDs, ожидаемые/фактические результаты и ограничения. Избегайте реальных пользовательских данных. При сбое cleanup восстановите тестовую базу перед повтором; не оставляйте тестовую роль или запись в общем development окружении.

## Воспроизводимая лабораторная: tenant и роль на реальном SQL-пути

**Prerequisites:** Go 1.27.2, Docker Compose v2, POSIX shell с `openssl`/`seq` и свободный loopback-порт 55433. Из корня репозитория поднимите только закреплённую disposable БД из P3; случайный пароль хранится лишь в текущей shell-сессии:

```sh
set -eu
cd content/projects/p3
export POSTGRES_USER=taskflow POSTGRES_PASSWORD="$(openssl rand -hex 24)" POSTGRES_DB=taskflow_test
docker compose -p oga-middle27 up -d db
for attempt in $(seq 1 30); do
  if docker compose -p oga-middle27 exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then break; fi
  sleep 1
done
docker compose -p oga-middle27 exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"
cd reference
TASKFLOW_TEST_DATABASE_URL="postgres://taskflow:${POSTGRES_PASSWORD}@127.0.0.1:55433/taskflow_test?sslmode=disable" go test -run '^TestPostgresTaskOutboxAndTenantIsolation$' -count=1 -v
```



**Ожидайте:** тест проходит и включает проверки tenant isolation из своего описания. Для одного негативного случая запишите ожидаемые статус/отсутствие чтения или изменения и найдите соответствующую SQL-проверку членства; не подменяйте principal заголовком. Этот тест не является доказательством безопасности произвольного приложения. **Очистка:** `cd .. && docker compose -p oga-middle27 down -v`; volume содержит только тестовую БД этого опыта.
