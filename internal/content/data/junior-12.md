## Generics, обзор и проект P1 CLI Toolkit

Обобщённая функция (generic function) принимает параметр типа, а не только параметр-значение. Объявление `func Identity[T any](v T) T` позволяет компилятору вывести T из аргумента. Параметр типа — имя типа внутри объявления; constraint (ограничение) задаёт, какие операции и типы допустимы.

Пустое ограничение any означает множество всех типов. Для сложения можно ограничить T множеством типов, поддерживающих операцию +. Type set (множество типов) задаётся элементами и объединением через `|`; приближённый тип `~int` включает типы, чей underlying type — int. Ограничение должно разрешать каждую операцию функции, а не просто перечислять «похожие» типы.

Сигнатура проекта ApplyDiscount[T interface{ ~int | ~int64 }] принимает только int/int64 и их определённые типы с таким underlying type. Процент в условии лежит от 0 до 100; вычисление price*(100-percent)/100 нужно проверять на переполнение, либо сначала делить и умножать аккуратно с чётко описанным округлением. Для учебного контракта устанавливаем проверку диапазона и целочисленное усечение вниз; большие значения требуют защиты от overflow.

Generics не делают функцию автоматически лучше. Если операция одна и типы два с разным контрактом, две небольшие функции понятнее. Если структура данных или алгоритм естественно повторяются для любого T, параметр типа сокращает дублирование, сохраняя статическую проверку. Не используйте any и type switch внутри generic функции, если constraint способен выразить нужный контракт.

Компилятор выводит параметр типа по аргументам, когда это возможно. Иногда его нужно указать явно: `Identity[string]("Go")`. Constraint может включать методы, тогда внутри функции разрешены только эти методы. Type set с `~` относится к underlying type, но не означает, что можно выполнять любую операцию; разрешённые операции определяются правилами языка для всего множества.

Проверяйте точную сигнатуру: имена параметров не важны для вызова, но форма и constraint важны для grader. Не переопределяйте predeclared имена и не добавляйте алиасы типов в решении. Если parser принимает только точный контракт, альтернативная запись constraint может быть семантически близкой, но должна соответствовать ABI задания.

Проект P1 — CLI Toolkit, небольшая локальная утилита для разбора аргументов, чтения JSON-файла и вывода проверенной сводки. Он собирает функции, ошибки, пакеты, тесты, документацию и Git. Используются только stdlib и пользовательский файл, созданный самим проектом/тестом. Сеть и аккаунт не нужны. Это не production CLI и не гарантия квалификации.

Этап первый — зафиксировать контракт: допустимые аргументы, путь к данным, формат JSON, поведение на ошибках, коды завершения и вывод. Запишите обычный пример и malformed input. Затем определите данные и границы: ParseArgs отделяет синтаксис CLI; ReadItems отделяет JSON и validation; main соединяет стадии и владеет файлами; пакеты группируются по ответственности.

Этап второй — ошибки. Неправильные аргументы должны завершаться ясным usage, повреждённый JSON — сообщать категорию, не печатая внутренний stack. На успех stdout содержит документированный результат, на ошибку stderr и ненулевой exit code. Не смешивайте диагностический текст с машиночитаемым успешным выводом. Не принимайте неоговорённые флаги молча.

Этап третий — тесты. Чистые функции проверяются таблицами и subtests; интеграционный CLI запускается с временной папкой и fixture, если тестовый harness это поддерживает. Acceptance-проверки сравнивают exit/stdout/stderr и побочные эффекты по контракту. Автоматическая проверка не оценивает, насколько README доступен новичку, насколько история коммитов сфокусирована и почему выбрана архитектура.

Этап четвёртый — документация и Git. README объясняет назначение, запуск, формат входа, ошибочные случаи и версию Go. Перед commit просмотрите status, diff и staged diff. Секреты и локальные файлы данных не добавляйте. Выпустите артефакт только после чистых `go test ./...` и `go build ./...`; release в данном уроке означает локальный воспроизводимый результат, не публикацию в интернет.

Этот учебный план разделяет автоматическое и ручное evidence. Функциональные задачи используют trusted driver, который вызывает функцию на конечных публичных и скрытых входах. Они проверяют значения, не качество студентских тестов. Для P1 отдельно требуется student-authored tests, понятные ошибки, README и Git history. Ручная рубрика оценивает эти качества и объяснение решения; автоматический pass не означает, что они проверены.

Проектный рубрикатор оценивает пять областей: соблюдение контракта; валидация и полезность ошибок; тесты границ/регрессий; README и воспроизводимый запуск; история изменений и чистое состояние. По каждой области фиксируются наблюдаемые доказательства и пробелы. Нельзя выводить статус Junior или профессиональное звание из одного задания. Это учебный проект и обратная связь по перечисленным критериям.

### Полная программа: ограничение типа и скидка

Сохраните как `main.go`. Поддерживаются int/int64 и defined types на их основе; проверка умножения защищает overflow перед вычислением.

```go
package main

import "fmt"

func ApplyDiscount[T interface{ ~int | ~int64 }](price, percent T) (T, error) {
    var zero T
    if price < 0 || percent < 0 || percent > 100 { return zero, fmt.Errorf("price and percent are outside the allowed range") }
    // Делим до умножения, сохраняя усечение вниз и ограничивая промежуточный рост.
    whole := price / 100 * (100 - percent)
    remainder := price % 100 * (100 - percent) / 100
    return whole + remainder, nil
}
func main() {
    result, err := ApplyDiscount[int64](1250, 20)
    if err != nil { fmt.Println("error:", err); return }
    fmt.Println(result)
}
```

Вывод: `1000`. Остаток вычисляется до деления, поэтому для крайних целых типов multiplication там тоже нуждается в отдельном overflow-контракте; production версия должна использовать проверяемую арифметику. Учебная функция ограничивает доменный ввод, но не утверждает, что произвольный MaxInt64 безопасен.

## Как generic код проверяется компилятором

Generic функция описывает семейство вызовов, но создаёт статически типизированный результат. При `identity(7)` компилятор выводит T как int; результат снова int, а не any. Параметры типа входят в объявление функции в квадратных скобках, а значения передаются обычными круглыми скобками. Это не runtime-reflection и не динамический dispatch, если constraint не требует конкретных интерфейсных методов.

В constraint с `~int | ~int64` каждая ветвь должна разрешать сравнения и арифметику, используемые телом. Объединение означает альтернативные типы; пересечение интерфейсов требует удовлетворить всем методам/условиям. Если операция отсутствует хотя бы в одном допустимом типе, компилятор отвергнет тело. Добавление `comparable` разрешило бы сравнение на равенство, но не было бы нужно для скидки.

Типы с underlying int могут иметь собственное имя: `type Cents int64`. Generic функция может принять Cents, если constraint включает ~int64. Возвращаемое значение останется Cents, так как T сохраняет точный исходный тип. Это полезно для доменных типов, но также позволяет случайно смешать понятия, если constraint слишком широк. Специализированная функция `ApplyDiscountCents` может лучше выражать правила денег.

## Числовой контракт и overflow

Проверка price>=0 и percent от 0 до 100 задаёт доменную область, но сама по себе не исключает переполнение промежуточного `price*(100-percent)`. Деление до умножения меняет округление для некоторых величин. Если требуется точное floor от произведения, нужно безопасно разложить вычисление или проверить overflow до умножения. В главе мы показываем один подход для обычных значений и прямо называем его предел; не переносите код на произвольный MaxInt64 без дополнительной проверки.

Ещё одна политика — ограничить максимальную цену доменным максимумом, выбранным предметной областью, и проверить этот предел. Другой подход — умножение с проверкой переполнения или более широкая арифметика. Поскольку разрешены только стандартные типы, решение должно быть понятным и тестируемым. Для денежного продукта важно определить точность, округление, валюту и правила скидки вместе, а не выбирать их по умолчанию.

Округление вниз к целому создаёт наблюдаемое поведение: цена 99 и скидка 10% даст 89 в этой формуле. Округление к ближайшему дало бы другое значение. Тесты должны фиксировать выбранное правило. Значение percent=0 возвращает исходную цену, 100 возвращает ноль, а значение 101 должно дать ошибку. Пустой generic вход здесь отсутствует; границы принадлежат числовому контракту.

## P1: собрать проверяемый продукт

Начните с пользовательской истории: «Я запускаю утилиту с аргументами и файлом и получаю предсказуемую сводку». Переведите её в примеры запуска, включая неверные аргументы, отсутствующий файл, malformed JSON и пустой список. Каждый пример должен сообщать ожидаемый exit code, stdout, stderr и изменения файлов. Это acceptance contract, независимый от внутренней структуры пакетов.

Разложите логику на стадии. ParseArgs превращает []string в типизированную Config и не читает process-global os.Args. Загрузка файла преобразует байты в JSON-структуры. Валидация проверяет доменные правила. Форматирование готовит пользовательский результат. `main` связывает стадии и управляет потоками/файлами. Такая декомпозиция позволяет тестировать чистую функцию без запуска отдельного процесса.

Надёжная CLI-программа различает ошибки пользователя и внутренние ошибки. Usage появляется при некорректных аргументах; ошибка чтения объясняет, какой шаг не удался, без стека; код завершения отличает неуспех от успешного пустого результата. Успешный stdout остаётся пригоден для следующего инструмента. Не печатайте и структурированный JSON, и случайные debug-строки в один поток.

Добавьте student-authored tests. Table-driven тесты проверяют parsing, обязательные поля и malformed ввод. Регрессионный тест фиксирует найденную ошибку. Integration тест создаёт собственную временную директорию, вызывает приложение с fixture и сравнивает наблюдаемое поведение. Пишите комментарий к тесту только когда имя кейса не объясняет намерение. Запускайте весь набор после изменения общего helper.

README должен объяснить минимальные требования, запуск, JSON schema, пример, ошибки и тесты. Проверьте инструкции на чистой копии или в новом каталоге. Уберите локальный fixture из коммита, если он не является публичным тестовым примером. Проверьте лицензии используемых исходников и зависимостей, не добавляйте чужой код без условий использования.

## Релиз и рубрика

Локальный релиз начинается с чистого состояния: форматирование, тесты, сборка, проверка статуса и просмотр полного diff. Артефакт имеет версию и заметки о поведении, но его не нужно публиковать в сеть. Релизная проверка подтверждает воспроизводимые команды на текущей платформе. Она не означает, что приложение прошло аудит безопасности или готово к работе с любыми файлами.

Рубрика P1 разделяет поведение, обработку ошибок, тесты, документацию и историю Git. Для каждого критерия записывайте конкретное наблюдение: например, «bad JSON даёт ненулевой код и диагностическое сообщение в stderr», а не «ошибки хорошие». Автоматическая acceptance-проверка подтверждает только машинно-наблюдаемые критерии. Тестовая стратегия, читаемость и история требуют ручного просмотра. Учебная оценка сообщает освоение критериев этого проекта, а не должность или стаж.

Если какой-либо milestone не проходит, не перепрыгивайте к публикации. Сохраните точную команду и вывод, исправьте один класс проблемы и повторите необходимые проверки. Приёмочный дефект должен получить regression test. Успешный запуск на вашем компьютере не заменяет воспроизводимую инструкцию. Чистый Git status в конце показывает, что все намеренные файлы учтены.

### Пример: компилятор выводит параметр типа

```go
package main

import "fmt"

func identity[T any](value T) T { return value }
func main() { n:=identity(7); s:=identity("Go"); fmt.Printf("%T %v; %T %v\n",n,n,s,s) }
```

Вывод показывает `int 7; string Go`: каждый вызов сохраняет исходный статический тип.

### Пример: ограничение множества типов

```go
package main

import "fmt"

type Number interface { ~int | ~int64 }
func larger[T Number](a,b T) T { if a>b { return a }; return b }
type Cents int64
func main() { fmt.Println(larger(Cents(40),Cents(75))) }
```

Вывод: `75`. Определённый тип Cents удовлетворяет ограничению через underlying int64 и остаётся Cents в результате.
