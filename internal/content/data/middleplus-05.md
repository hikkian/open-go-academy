# Heap profile и жизненный цикл памяти

## Что ты сделаешь

Ты разберёшься, чем выделенная память отличается от удерживаемой, что показывает heap-профиль Go и чего он не показывает, и почему один снимок никогда не доказывает утечку. Три функции урока — `MemoryBudget`, `ValidHeapProfile`, `HeapChange` — это простые правила чтения счётчиков памяти: лимит, непротиворечивость двух метрик и сравнение двух снимков после сборки мусора.

## Два вопроса о памяти

Heap-профиль отвечает на разные вопросы в зависимости от режима. `alloc_space` — накопленный объём выделений за период наблюдения: сколько байт вообще просили у аллокатора. `inuse_space` — объём объектов, живых на момент снимка (snapshot). Буфер, который создаётся и освобождается на каждом запросе, даёт огромный `alloc_space` и крошечный `inuse_space`; кеш, выделенный один раз и живущий вечно, — наоборот.

Сначала назови, что расследуешь: нагрузку на аллокатор и сборщик мусора (тогда смотри `alloc_space`, `allocs/op` и `B/op` из benchmark) или рост живой памяти (тогда `inuse_space` и повторные снимки). Один профиль на оба вопроса не отвечает, и отчёт, в котором режим не назван, прочитают двумя противоположными способами.

```go group=metrics mode=run
package main

import "fmt"

func main() {
    // учебные счётчики в байтах, не чтение runtime
    inuse := int64(64 << 20)
    alloc := int64(5 << 30)
    fmt.Println("живая память:", inuse>>20, "MiB")
    fmt.Println("выделено за период:", alloc>>30, "GiB")
    fmt.Println("inuse <= alloc:", inuse <= alloc)
}
```

Вывод:

```text
живая память: 64 MiB
выделено за период: 5 GiB
inuse <= alloc: true
```

Здесь неравенство случайно верно. В общем случае оно не обязано выполняться: `inuse_space` включает объекты, выделенные до начала окна, за которое считается `alloc_space`. У двух метрик разные временные границы, и универсального порядка между ними нет.

> **Важно.** Heap-профиль группирует живые байты по стекам выделения. Он не строит граф ссылок и сам по себе не показывает путь удержания (retaining path): крупный стек говорит, где объекты были созданы, а не кто их держит.

## Место выделения — не владелец ссылки

В `go tool pprof -inuse_space` самый толстый стек — например, `newRecord` — показывает, где родились объекты, которые всё ещё живы. Владельцем же может быть `cache[key]`, глобальная map, замыкание в долгоживущей горутине или хвост backing array. Чтобы найти владельца, иди от долгоживущих корней по коду и напиши тест жизненного цикла: положи значение в кеш, удали запись, обнули ссылки и убедись, что сценарий освобождения соответствует контракту.

```go group=retain mode=run
package main

import "fmt"

type record struct{ payload [1 << 10]byte }

func main() {
    items := make([]*record, 0, 4)
    for i := 0; i < 4; i++ {
        items = append(items, &record{})
    }
    tail := items[3]
    items = items[:2] // длина уменьшилась, backing array всё ещё хранит 4 указателя
    fmt.Println("len:", len(items), "cap:", cap(items), "хвост достижим через массив:", items[:4][3] == tail)
    for i := range items[:cap(items)] {
        if i >= len(items) {
            items[:cap(items)][i] = nil // обнуление хвоста отпускает объекты
        }
    }
    fmt.Println("после обнуления:", items[:4][3] == nil)
}
```

Вывод:

```text
len: 2 cap: 4 хвост достижим через массив: true
после обнуления: true
```

Удаление элемента из пользовательской структуры не гарантирует, что backing array перестал на него ссылаться: срез указателей после сокращения длины удерживает хвост, пока ссылки не обнулены. Семантика профиля описана в [официальной документации `runtime/pprof`](https://pkg.go.dev/runtime/pprof); путь удержания из неё не следует — его доказывают кодом и тестом.

> **Типичная ошибка.** Принять allocation stack за retaining path и «оптимизировать» место выделения, хотя объекты держит кеш в другом пакете.

## Момент снимка и сборщик мусора

Снимок зависит от того, когда прошёл последний цикл GC, сколько процесс прогревался и в какой фазе жизненного цикла он находится. Принудительный `runtime.GC()` перед снимком полезен для контролируемого сравнения удерживаемой памяти «до» и «после», но не соответствует обычному поведению в production. Запиши: вызывал ли ты GC вручную, какой был интервал, сколько времени прошло после прогрева. Снимки в разных фазах без пояснения несравнимы.

```go group=change mode=run
package main

import "fmt"

func heapChange(before, after int64, gcCompleted bool) string {
    if before < 0 || after < 0 {
        return "invalid"
    }
    if !gcCompleted {
        return "gc_not_completed"
    }
    switch {
    case after < before:
        return "lower_after_gc"
    case after > before:
        return "higher_after_gc"
    }
    return "unchanged"
}

func main() {
    fmt.Println(heapChange(100, 80, true), heapChange(100, 120, true), heapChange(100, 100, true))
    fmt.Println(heapChange(100, 80, false), heapChange(-1, 0, true))
}
```

Вывод:

```text
lower_after_gc higher_after_gc unchanged
gc_not_completed invalid
```

Рост после GC — наблюдение, не диагноз: утечка доказывается серией снимков под одинаковой нагрузкой, в которых живая память растёт монотонно, и найденным путём удержания. Снижение тоже ничего не обещает, если нагрузка между снимками изменилась.

> **Зачем.** Единственный снимок отвечает только на вопрос «сколько живой памяти было в этот момент». Чтобы говорить о тенденции, нужны минимум два снимка с записанными условиями — а чтобы говорить о причине, нужен владелец ссылки.

## Как читать pprof для памяти

Heap-профиль хранит четыре вида сэмплов, и `go tool pprof` переключается между ними ключом `-sample_index`: `inuse_space` и `inuse_objects` — живые байты и объекты, `alloc_space` и `alloc_objects` — накопленные. По умолчанию показывается `inuse_space`, поэтому в отчёте всегда называй режим явно. Дальше те же команды, что для CPU: `-top` по стекам выделения, `-list имя` по строкам исходника, `-cum` для структуры вызовов.

Для сравнения двух снимков есть ключ `-base старый.out`: pprof показывает разность, и рост живой памяти виден по стекам, а не по общему числу. Это удобно для серии снимков из лаборатории ниже: три профиля под одинаковой нагрузкой, два сравнения через `-base`, и уже видно, какой стек выделения растёт монотонно. Кто держит эти объекты — по-прежнему вопрос к коду.

> **Зачем.** Без указания режима и базы отчёт о памяти нельзя повторить: число «120 MiB» без слова `inuse` или `alloc` и без момента снимка ничего не значит.

## Benchmark, escape analysis и пулы

`allocs/op` и `B/op` из benchmark показывают краткосрочную цену выделений; heap-профиль помогает найти, кто выделяет или удерживает. Escape analysis (`go build -gcflags=-m`) объясняет, почему значение ушло в кучу: интерфейсное значение, захват замыканием, возврат указателя, динамический размер, отсутствие inlining. Но сообщение компилятора не доказывает, что правка ускорит код — проверяй измерением именно собранной конфигурации, вывод зависит от версии Go и формы кода.

Переиспользование буферов и `sync.Pool` требуют оценки удержания, очистки ссылок, конкуренции и поведения GC. Пул — оптимизация для временных объектов, которые безопасно использовать повторно, а не постоянное хранилище: сборщик вправе очистить его. Большой объект может удерживать связанные данные через указатель, даже если поле выглядит маленьким. Любой вариант сначала проходит тесты корректности, включая гонки, и только потом измеряется отдельно по выделениям, задержке и удерживаемой памяти.

## Типичные ошибки

- Один снимок как доказательство утечки: нужна серия под одинаковой нагрузкой и владелец ссылки.
- `alloc_space` и `inuse_space` в одном выводе как одна «память»: разные вопросы и разные временные границы.
- Allocation stack как retaining path: место рождения объекта не говорит, кто его держит.
- Сравнение снимков до и после прогрева или с разным режимом GC без пояснения.
- `sync.Pool` как кеш: содержимое пула может исчезнуть в любой цикл сборки.
- Правка по сообщению escape analysis без измерения: компилятор объясняет, но не обещает выигрыш.

## Самостоятельная лаборатория

Возьми программу, которая кладёт записи в map и удаляет их по ключу. Сними heap-профиль в режиме `-inuse_space` трижды: после прогрева, после вставки десяти тысяч записей, после удаления всех записей и ручного `runtime.GC()`. Запиши три значения живой памяти и условия каждого снимка. Если после удаления память не вернулась к первому значению, найди путь удержания в коде: хвост среза, второй индекс, замыкание. Напиши тест жизненного цикла, который воспроизводит удержание, затем исправь и повтори три снимка. Удали файлы профилей после работы.

## Если что-то пошло не так

- `true` для `limit = 0` в задании 1 → лимит должен быть строго положительным.
- `false` для `inuse > alloc` в задании 2 → ты требуешь `inuse <= alloc`, а такого порядка нет; проверяются только знаки.
- `lower_after_gc` при `gcCompleted = false` → проверка завершения GC стоит после сравнения.
- `invalid` не срабатывает для отрицательных байт → проверка диапазонов должна быть первой.
- `import … is not allowed` → импорты запрещены: это сравнения чисел и флаг.

## Практика

Три функции без `main` и печати; среда показывает результаты `bool` и строками в кавычках. Все числа — учебные счётчики, функции не читают `runtime` и `pprof`.

### Задание 1 · Easy: проверь memory budget

**Цель.** Вернуть `true` при неотрицательном `used`, положительном `limit` и `used <= limit`.

**Ожидаемый вывод** — для `(used=80, limit=100)`:

```text
true
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func MemoryBudget(used, limit int64) bool`. Импорты запрещены.
2. Верни `used >= 0 && limit > 0 && used <= limit`.
3. «Запустить», «Проверить» — закрытые примеры: `(101, 100)` → `false`, `(0, 0)` → `false`.

**Как проверить себя.** Превышение лимита и нулевой лимит дают `false`; равенство `used == limit` — ещё `true`; это проверка пары чисел, не измерение памяти приложения.

**Если не принято.**
- `true` для `(0, 0)` → условие `limit >= 0` вместо `limit > 0`.
- `false` для `used == limit` → сравнение строгое, а нужно `<=`.

> **Подсказка.** Три условия через `&&`; какая метрика стоит за `used` — in-use или накопленные выделения — функция не знает, и это надо помнить при её применении.

### Задание 2 · Medium: проверь heap counters без смешения метрик

**Цель.** Вернуть `true`, если `inuse_space` и `alloc_space` неотрицательны — и только это.

**Ожидаемый вывод** — для `(64, 128)` и `(256, 128)`:

```text
true
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ValidHeapProfile(inuseBytes, allocBytes int64) bool`. Импорты запрещены.
2. Верни `inuseBytes >= 0 && allocBytes >= 0`.
3. «Запустить»: второй пример с `inuse > alloc` обязан дать `true`. «Проверить» — закрытые примеры: отрицательное значение любой метрики → `false`.

**Как проверить себя.** Нет условия `inuse <= alloc`: живая память может включать объекты, выделенные до окна накопления.

**Если не принято.**
- `false` для `(256, 128)` → добавлено неравенство между метриками; убери его.
- `true` при отрицательном `allocBytes` → проверяется только одна метрика.

> **Подсказка.** Задание специально тонкое: правильный ответ короче, чем кажется.

### Задание 3 · Hard: классифицируй retained heap после GC

**Цель.** Для неотрицательных снимков «до» и «после» при завершённом GC вернуть `lower_after_gc`, `higher_after_gc` или `unchanged`; при незавершённом GC — `gc_not_completed`; отрицательные значения → `invalid`.

**Ожидаемый вывод** — для `(before=100, after=80, gcCompleted=true)`:

```text
"lower_after_gc"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func HeapChange(before, after int64, gcCompleted bool) string`. Импорты запрещены.
2. Первой проверкой: `before < 0 || after < 0` → `"invalid"`.
3. Затем `!gcCompleted` → `"gc_not_completed"`.
4. Сравни: `after < before` → `"lower_after_gc"`, `after > before` → `"higher_after_gc"`, иначе `"unchanged"`. «Запустить», «Проверить» — закрытые примеры: рост → `higher_after_gc`; GC не завершён → `gc_not_completed`; отрицательное → `invalid`.

**Как проверить себя.** Порядок веток: диапазон, завершение GC, сравнение; результат — наблюдение об одной паре снимков, а не диагноз утечки.

**Если не принято.**
- `lower_after_gc` для `(100, 80, false)` → проверка GC стоит после сравнения.
- `gc_not_completed` для `(-1, 0, true)` → порядок проверок перепутан: диапазон первым.
- `unchanged` не возвращается при равенстве → нет последнего `return`.

> **Подсказка.** Четыре `return` подряд; `switch` без условия читается здесь лучше цепочки `if`.

## Итог

- `alloc_space` — что просили у аллокатора, `inuse_space` — что живо сейчас; у них разные временные границы и нет общего порядка.
- Профиль показывает место выделения, а не владельца ссылки; путь удержания ищут в коде от долгоживущих корней и доказывают тестом жизненного цикла.
- Утечку доказывают серией снимков под одинаковой нагрузкой с записанным режимом GC, а не одним числом.
