# Ограниченный worker pool

## Что ты сделаешь

Ты напишешь три функции-модели для пула исполнителей: расчёт числа пакетов, назначение задачи наименее загруженному исполнителю и сборка результатов по индексам задач. Примеры главы покажут настоящий пул с фиксированным числом горутин и то, как вернуть результаты в исходном порядке.

## Что ограничивает пул

Worker pool состоит из очереди задач, фиксированного числа исполнителей (workers) и коллектора результатов. Лимит задаёт число горутин, которые читают очередь одновременно. Он не зависит от того, сколько задач ждёт в очереди.

Поэтому пул ограничивает параллельную работу, но не ограничивает память, если входная очередь неограниченна. Если производитель читает вход без остановки, очередь растёт быстрее, чем исполнители её разбирают. Ограничение входа — отдельное решение, которое рассматривается в конце главы.

## Пул с фиксированным числом исполнителей

Исполнители запускаются один раз и читают общий канал задач, пока он не закроется. Пример ниже запускает два исполнителя, которые возводят числа в квадрат. Задачи отправляются в канал, затем канал закрывается, и ожидание завершения делает владелец через `WaitGroup`.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    jobs := make(chan int)
    results := make(chan int, 4)
    var wg sync.WaitGroup
    for w := 0; w < 2; w++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := range jobs {
                results <- j * j
            }
        }()
    }
    for j := 1; j <= 4; j++ {
        jobs <- j
    }
    close(jobs)
    wg.Wait()
    close(results)
    total := 0
    for r := range results {
        total += r
    }
    fmt.Println(total)
}
```

Вывод: `30`. Сумма квадратов от 1 до 4 не зависит от того, какой исполнитель обработал задачу. Порядок результатов в канале при этом не гарантирован, поэтому сравнивается сумма, а не последовательность.

## Сохрани связь результата с задачей

Если результат нужно вернуть в исходном порядке, каждая задача должна нести индекс. Исполнитель записывает результат по этому индексу в заранее выделенный срез. Тогда порядок завершения не влияет на итог, а запись разных индексов не конкурирует с другими записями.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    jobs := []int{1, 2, 3}
    results := make([]int, len(jobs))
    var wg sync.WaitGroup
    for i, j := range jobs {
        wg.Add(1)
        go func(i, j int) {
            defer wg.Done()
            results[i] = j * 10
        }(i, j)
    }
    wg.Wait()
    fmt.Println(results)
}
```

Вывод: `[10 20 30]`. Индекс задачи стал индексом результата. Если задача может завершиться ошибкой, результат должен нести и значение, и ошибку, иначе вызывающий код не узнает о сбое.

> **Важно.** Нельзя полагаться на порядок, в котором пришли результаты, если API обещает порядок задач. Либо сохраняй индекс, либо явно документируй, что порядок произвольный.

## Остановка исполнителей

Исполнитель должен завершиться в двух случаях: очередь закрыта или пришёл сигнал отмены. Цикл `for range` по каналу выходит сам, когда владелец закрывает очередь. Для отмены используется `select` с веткой `ctx.Done()`.

Пример исполнителя, который выходит по отмене, даже когда задач нет:

```go
package main

import (
    "context"
    "fmt"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    jobs := make(chan int)
    done := make(chan string)
    go func() {
        for {
            select {
            case <-ctx.Done():
                done <- "stopped"
                return
            case j := <-jobs:
                _ = j
            }
        }
    }()
    cancel()
    fmt.Println(<-done)
}
```

Вывод: `stopped`. Исполнитель ждёт задачу или отмену. Здесь задач нет, и отмена — единственная готовая ветка, поэтому вывод определён. Если бы выход по отмене отсутствовал, исполнитель висел бы на `jobs` вечно.

Выбор семантики отмены определяет порядок закрытия. Можно прекратить брать новые задачи, отменить активные или дать им закончиться. От этого зависит, когда закрывается входной канал и в каком порядке вызывается `Wait`. Обычно создатель закрывает `jobs` после последней отправки, исполнители завершают цикл, а владелец ждёт `WaitGroup`.

Не используй `len(ch)` как механизм синхронизации. Это мгновенный снимок: значение меняется сразу после чтения, и решение, принятое по нему, устаревает до следующей инструкции.

## Назначение задачи наименее загруженному исполнителю

Если задачи различаются по длительности, разумно назначать каждую исполнителю с наименьшей накопленной нагрузкой. При равенстве выбирается меньший индекс, чтобы результат был детерминированным. Такой выбор — чистая арифметика, поэтому его удобно проверить без горутин.

Сумма длительностей может переполниться на больших значениях. Поэтому накопление ограничивают максимальным значением `int`, а не позволяют числу стать отрицательным.

## Очередь и backpressure

Число исполнителей ограничивает одновременно выполняемую работу, но не число задач, которые ждут запуска. Если производитель читает вход без остановки, а очередь растёт без границ, память расходуется быстрее, чем исполнители её освобождают. Этот эффект виден не сразу: сервис работает, пока очередь не займёт всю доступную память.

Backpressure — обратное давление — решает проблему на границе. Когда допустимый буфер заполнен, производитель ждёт или отклоняет новую работу. Выбор между ожиданием, отказом и сбросом зависит от контракта: потеря телеметрии может быть приемлема, потеря платёжного изменения — нет.

Для любого пула полезно записать три отдельных числа: сколько обработчиков активно, какой максимальный размер очереди и сколько можно ждать одну задачу. Буфер на двадцать элементов не означает, что сервис выдержит двадцать запросов в секунду. Скорость зависит от длительности обработки, а не от размера буфера.

## Модель и механизм

У пула два параметра, и оба надо назвать: сколько исполнителей работают одновременно и сколько задач ждут в очереди. Без второго параметра ограничение незаметно превращается в очередь без предела, и память растёт быстрее, чем исполнители её освобождают.

Для пула полезны четыре вопроса. Кто владеет очередью? Кто её закрывает? Кто ждёт исполнителей? Что происходит с задачей, если исполнитель вышел по ошибке? Ответы записываются до написания исполнителей.

Синхронизация имеет цену. Каждый исполнитель занимает память и место в планировщике. Лимит нужно выбирать по измерению нагрузки, а не по ощущению.

## Типичные ошибки и исправление

Первая ошибка — запустить горутину на каждую задачу и назвать это пулом. Такой код не ограничивает параллелизм. Исправление — фиксированное число исполнителей, читающих общий канал.

Вторая — закрыть канал результатов до того, как все исполнители отправили результат. Следующая отправка вызовет панику. Исправление — закрывать канал результатов после `wg.Wait()` у владельца.

Третья — исполнитель ждёт задачи бесконечно, даже когда отмена уже пришла. Исправление — `select` с веткой `ctx.Done()` в месте ожидания задачи.

> **Типичная ошибка.** Считать, что буфер на двадцать элементов ограничивает нагрузку. Буфер ограничивает только число задач в очереди, а скорость обработки зависит от длительности каждой задачи.

## Если что-то пошло не так

- Число активных горутин растёт с числом задач → исполнители запускаются на каждую задачу; вынеси запуск из цикла задач.
- Результаты приходят не по порядку → индекс не передан с задачей; добавь его в структуру задачи.
- Программа зависла на завершении → владелец не закрыл `jobs`; закрой его после последней отправки.
- Паника `send on closed channel` → канал результатов закрыт раньше последнего исполнителя; закрывай после `Wait`.

## Практика

### Практический мост: ограниченный пул и реальная очередь

Функции этой практики распределяют и собирают индексы арифметически. Они не запускают исполнители и не ограничивают число горутин. Реальный SQL worker есть в `content/projects/p3/reference/worker.go`: его функция `runWorkers` принимает число исполнителей и ограничивает их работу. Конкурентный захват и подтверждение задач проверяет тест `TestPostgresTaskOutboxAndTenantIsolation` в `content/projects/p3/reference/postgres_integration_test.go`. Для реального DB-сценария используй disposable PostgreSQL.

Перед запуском нужны Go, Docker Compose v2 и OpenSSL. Команда поднимает только disposable PostgreSQL из P3 Compose на loopback-порту 55433; пароль существует только в окружении shell. Она ждёт healthcheck, запускает точный тест и удаляет контейнер и volume при завершении блока:

```sh
(
cd content/projects/p3/reference
set -eu
export POSTGRES_USER=taskflow POSTGRES_DB=taskflow_test
export POSTGRES_PASSWORD="$(openssl rand -hex 24)"
export TASKFLOW_TEST_DATABASE_URL="postgres://$POSTGRES_USER:$POSTGRES_PASSWORD@127.0.0.1:55433/$POSTGRES_DB?sslmode=disable"
compose() { docker compose -f ../compose.yaml -p oga-middle10 "$@"; }
trap 'compose down -v' EXIT
compose up -d db
ready=0
for attempt in $(seq 1 60); do
  if compose exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then ready=1; break; fi
  sleep 1
done
test "$ready" -eq 1
go test -run TestPostgresTaskOutboxAndTenantIsolation -count=1
)
```

Ожидай, что параллельные исполнители не применят один эффект дважды. Лимит горутин подтверждается кодом и конфигурацией, а не функциями этой главы. Векторы охватывают только чистые функции: они не запускают горутины и не заменяют интеграционные проверки.

### Задание 1 · Ограниченный worker pool — easy

**Цель.** Для `[число задач, лимит на пакет]` верни срез из одного числа: сколько непустых пакетов получится при округлении вверх. Пустой или некорректный ввод (задач не больше нуля или лимит не положителен) даёт `[0]`.

**Ожидаемый вывод** — входы: `[10, 3]`, затем `[4, 4]`:

```text
[4]
[1]
```

**Шаги.**
1. Выбери задание «Ограниченный worker pool — easy»: в файле есть `BatchCount` с `panic("TODO")`. Импорты не нужны.
2. Если число задач или лимит не больше нуля, верни `[0]`.
3. Раздели число задач на лимит.
4. Если остался неполный пакет, добавь один.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Два среза из одного числа; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `[3]` для `[10, 3]` → неполный пакет не учтён.
- `[0]` для `[4, 4]` → проверка на нулевой лимит сработала неверно.

> **Подсказка.** Деление с остатком: если остаток не нулевой, пакет один лишний.

### Задание 2 · Ограниченный worker pool — medium

**Цель.** Вход: `[число исполнителей, длительности задач...]`. Назначай каждую задачу исполнителю с наименьшей накопленной длительностью; при равенстве выбирай меньший индекс. Верни срез индексов исполнителей по порядку задач. Если исполнителей нет или длительность отрицательна, верни пустой результат.

**Ожидаемый вывод** — входы: `[3, 4, 2, 5, 1]`, затем `[2, 3, 1]`:

```text
[0,1,2,1]
[0,1]
```

**Шаги.**
1. Выбери задание «Ограниченный worker pool — medium»: в файле есть `LeastLoadedWorker` с `panic("TODO")`. Импорты не нужны.
2. Если исполнителей нет или задача отрицательная, верни пустой срез.
3. Создай срез накопленных нагрузок из нулей по числу исполнителей.
4. Для каждой задачи найди исполнителя с наименьшей нагрузкой; при равенстве бери меньший индекс.
5. Прибавь длительность к его нагрузке и запиши индекс в результат.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Два среза; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- Все задачи уходят одному исполнителю → выбор по наименьшей нагрузке не выполнен.
- Индекс исполнителя при равенстве нагрузок больше меньшего → сравнение при равенстве сделано неверно.
- `null` вместо `[]` → результат остался nil-срезом; создай пустой срез.

> **Подсказка.** Поиск минимума — один проход по нагрузкам с запоминанием индекса.

### Задание 3 · Ограниченный worker pool — hard

**Цель.** Вход — пары `[индекс задачи, результат]` в порядке завершения. Число задач равно числу пар. Верни результаты по индексам задач. Повторный индекс игнорируй, учитывая первое вхождение. Индекс вне диапазона `0..число пар − 1` игнорируй. Отсутствующие индексы пропускай.

**Ожидаемый вывод** — входы: `[2, 30, 0, 10, 1, 20]`, затем `[1, 8, 0, 7]`:

```text
[10,20,30]
[7,8]
```

**Шаги.**
1. Выбери задание «Ограниченный worker pool — hard»: в файле есть `OrderedResults` с `panic("TODO")`. Импорты не нужны.
2. Определи число задач: это число пар.
3. Создай срез результатов по этому числу и отметь, какие индексы заполнены.
4. Иди по парам по порядку: если индекс в диапазоне и ещё не заполнен, запиши результат.
5. Собери заполненные результаты по порядку индексов.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Два списка; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- Результаты идут в порядке завершения, а не по индексам → сборка по индексам не выполнена.
- Повторный результат перезаписывает первый → проверка «уже заполнено» пропущена.
- Индекс вне диапазона попал в результат → граница диапазона не проверена.

> **Подсказка.** Срез с отметками «заполнено» и итоговая сборка по порядку индексов.

## Итог

- Фиксированное число исполнителей ограничивает параллельную работу; очередь задач при этом отдельно ограничивается контрактом.
- Индекс задачи передаётся вместе с результатом, поэтому порядок результатов восстанавливается независимо от порядка завершения.
- Исполнитель выходит по закрытой очереди или по сигналу отмены; канал результатов закрывает владелец после ожидания всех исполнителей.
