# Пулы соединений и время ожидания

## Что ты сделаешь

Ты напишешь три функции-политики для пула соединений: состояние лимита, решение об ожидании и полную политику получения соединения с отменой. Они работают с переданными счётчиками и сроком, поэтому проверяют правила отдельно от реального пула, базы и сети.

## Пул ограничивает соединения, а не запросы

Пул соединений — это лимит одновременно открытых сессий к базе. Он не равен очереди запросов и не равен числу goroutine. Если пришло десять HTTP-запросов, а лимит равен четырём, четыре запроса выполняют SQL, остальные ждут свободный слот или завершаются по сроку.

Без пула каждый запрос открывал бы собственное соединение, и лимит перестал бы защищать базу. Слишком маленький пул, наоборот, создаёт очередь даже при исправной базе. Поэтому различай три величины: число входящих запросов, занятые соединения и число ожидающих получения соединения.

## Состояние лимита

Параметр `maximum` — конфигурационная верхняя граница. `inUse` — наблюдение в конкретный момент. Равенство `inUse == maximum` означает, что новый запрос сейчас не получит слот. Оно не говорит, что слот освободится скоро.

Значение `inUse > maximum` — противоречивое состояние. Его лучше обнаружить и вернуть как ошибку, чем маскировать ожиданием. Отрицательные счётчики и нулевой максимум — ошибки входа.

Буферизованный канал удобно представить как семафор. Ёмкость равна лимиту, заполненный канал означает занятый пул:

```go
package main

import "fmt"

func main() {
    slots := make(chan struct{}, 2)
    slots <- struct{}{}
    slots <- struct{}{}
    fmt.Println(len(slots), cap(slots))
}
```

Вывод: `2 2`. Оба слота заняты, и следующая отправка в `slots` будет ждать. Так же устроено ожидание получения соединения: запрос встаёт в очередь, пока кто-то не освободит слот.

## Ожидание и срок

При насыщении вызывающий код должен иметь ограниченный бюджет ожидания. В Go его передают через `context.Context` с дедлайном: тогда отмена или истёкший срок доходят до ожидания соединения. Время полного запроса и время ожидания пула — разные величины. Если до дедлайна осталось 20 миллисекунд, ожидание ещё на 100 миллисекунд бесполезно.

Сроки разных слоёв складываются плохо. Если общий дедлайн HTTP-запроса равен 300 миллисекундам, а авторизация и разбор JSON уже заняли 280, пулу не нужно добавлять ещё 300 миллисекунд ожидания. Оставшиеся 20 миллисекунд ограничивают и ожидание соединения, и SQL. Если каждый слой задаёт свой таймаут независимо, на деле ожидание может растянуться на секунды. Поэтому общий срок передаётся вниз, а локальные лимиты задаются явно.

Отмена контекста должна освобождать место в очереди ожидания. Пример показывает, что отменённый контекст сообщает о причине:

```go
package main

import (
    "context"
    "fmt"
)

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    cancel()
    fmt.Println(ctx.Err())
}
```

Вывод: `context canceled`. Ожидающий запрос видит эту ошибку и не должен продолжать занимать очередь. Проверка такой отмены требует интеграционного теста с реальным пулом, а не чистой функции.

## Очередь ожидания тоже ограничена

Очередь ожидания сама должна иметь предел. Без предела система принимает больше запросов, чем способна обслужить. Память растёт, а затем запросы массово отклоняются по таймауту. Лимит ожидающих — отдельная политика от `maximum`: одно регулирует соединения, второе — очередь.

Справедливость очереди, например FIFO, отмена ожидающего и реакция на закрытие пула — детали реализации. Их нельзя вывести из одного значения `inUse`.

## Сколько соединений на самом деле

Лимит на процесс умножается на число экземпляров приложения. Если каждая из двенадцати реплик держит пул на восемь соединений, база может получить до девяноста шести соединений. Пример показывает это умножение:

```go
package main

import "fmt"

func main() {
    perReplica, replicas := 8, 12
    fmt.Println(perReplica * replicas)
}
```

Вывод: `96`. Этот расчёт нужно сверять с `max_connections` базы, соединениями фоновых задач и всеми экземплярами сервиса. Увеличение лимита в одном процессе может перегрузить базу, даже если локально всё выглядит спокойно.

## Сценарий: почему проверка перед запросом не работает

Представь сервис каталога с лимитом восемь. Семь соединений заняты медленными запросами. Новый обработчик получает от пула снимок `inUse = 7` и решает, что слот свободен. Но до фактического получения другой обработчик может занять восьмой слот.

Значит, код не может сначала посмотреть статистику, а потом считать слот зарезервированным. Пул должен атомарно выдать ресурс или поставить вызывающую горутину в очередь. Проверка перед запросом годится для наблюдения, но не для решения.

> **Важно.** Счётчики из `Stats()` — снимок, который устаревает сразу после чтения. Решение о выдаче соединения принимает только атомарный механизм самого пула.

## Модель и механизм

Для пула соединений важны три величины: занятые слоты, очередь ожидания и оставшийся срок. Решение о слоте принимает сам пул атомарно; снимок счётчиков лишь подсказывает, что ситуация может измениться к моменту запроса.

Для пула полезны три вопроса. Какой лимит защищает базу? Что делает запрос, когда слота нет? Что происходит с ожиданием, когда срок истёк или запрос отменён? Ответы записываются до написания политики.

Синхронизация имеет цену. Ожидание занимает горутину и память, а отказ передаёт восстановление вызывающему коду. Выбор между ожиданием и отказом — продуктовое решение, которое нужно измерять.

## Типичные ошибки и исправление

Первая ошибка — путать число запросов с числом соединений. Исправление — измерять отдельно входящие запросы, занятые соединения и очередь ожидания.

Вторая — увеличивать лимит пула при медленных запросах. Тогда нагрузка растёт, а база получает больше параллельных запросов. Исправление — сначала измерить длительность запросов и лимиты базы.

Третья — ждать соединение без срока. Исправление — передавать контекст с дедлайном и проверять отмену.

> **Типичная ошибка.** Считать `inUse == maximum` сигналом, что слот скоро освободится. Это только состояние в момент наблюдения.

## Если что-то пошло не так

- Запросы зависают на получении соединения → лимит мал или соединения не возвращаются; проверь закрытие транзакций и результатов.
- Ошибки таймаута растут при высокой нагрузке → очередь переполнена или срок слишком короткий; сравни ожидание с длительностью SQL.
- База отказывает в соединениях → суммарный лимит по репликам превышает `max_connections`; пересчитай умножение.
- Отменённые запросы всё равно занимают очередь → отмена не передана в ожидание; проверь контекст.

## Лаборатория перед практикой

Возьми пример с семафором и добавь третью отправку в `slots` перед выводом. Перед запуском запиши, что произойдёт: программа напечатает значения, или отправка будет ждать. Затем запусти её с таймаутом, например `timeout 5s go run main.go`, и сравни. Если программа зависла, назови, кто должен освободить слот: в примере никто, потому что чтения из `slots` нет. Добавь чтение одного значения перед третьей отправкой и предскажи вывод заново.

Журнал эксперимента содержит версию Go, команду с таймаутом, число слотов, предсказание и наблюдение. Такой опыт переносится на пул соединений: ожидание без освободителя совпадает с запросом, который никогда не получит соединение. Если пул в реальном коде не отдаёт слот при ошибке, это та же ситуация.

## Практика

### Практический мост: настоящий лимит соединений

Функции этой практики моделируют решение по переданным счётчикам. Они не получают соединение атомарно, не ждут в очереди и не исполняют SQL. Реальный пул с ограничением проверяется в интеграционном тесте. Для его ручной проверки запусти disposable PostgreSQL из проекта P3. В первой из двух `psql`-сессий выполни `BEGIN; SELECT pg_sleep(5);`. Во второй выполни `SELECT count(*) FROM pg_stat_activity WHERE datname = current_database();` и посмотри число серверных сессий. Затем заверши первую транзакцию. Это показывает серверные сессии, но не измеряет ожидание пула в Go.

Для ожидания в Go нужен отдельный тест: пул с одним соединением, удержание этого соединения и второй запрос с коротким дедлайном. Такой тест в проекте P3 пока не написан, и его стоит добавить отдельной задачей.

### Задание 1 · Состояние лимита

**Цель.** Для `inUse` и `maximum` верни `invalid`, если `inUse < 0`, `maximum <= 0` или `inUse > maximum`. Если `inUse == maximum`, верни `wait`. Иначе верни `available`.

**Ожидаемый вывод** — входы: `inUse = 2, maximum = 8`, затем `inUse = 7, maximum = 8`, затем `inUse = 8, maximum = 8`:

```text

"available"
"wait"
```

2. Проверь, что `inUse` не отрицательный, `maximum` положительный и `inUse` не больше `maximum`; при нарушении верни `invalid`.
3. Если `inUse` равен `maximum`, верни `wait`.
4. Иначе верни `available`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Три строки в кавычках; оба вывода совпадают; все три критерия зелёные.

**Если не принято.**
- `available` при полном пуле → сравнение с `maximum` выполнено неверно.
- `invalid` при `inUse = maximum` → строгое неравенство поставлено вместо нестрогого.
- `available` при нулевом `maximum` → проверка границы пула пропущена.

> **Подсказка.** Сначала проверка корректности, потом полный пул, потом всё остальное.

## Итог

- Пул ограничивает открытые соединения; запросы ждут слот или отказываются по сроку.
- Решение о соединении принимает атомарный механизм пула, а проверка счётчиков даёт только снимок.
- Лимит очереди и срок ожидания защищают память и базу; суммарный лимит считается по всем экземплярам приложения.
