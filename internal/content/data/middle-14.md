# Пулы соединений и время ожидания

## Почему эта тема важна

Пул соединений — это лимит одновременных открытых сессий к базе, а не очередь запросов и не число goroutine. При десяти HTTP-запросах и лимите в четыре соединения четыре запроса могут выполнять SQL, остальные ждут или завершаются по deadline. Если каждый запрос создаёт собственный connection, лимит перестаёт ограничивать нагрузку и база получает лавину соединений. Если пул мал, очередь растит latency даже при исправной базе. Поэтому сначала разделите три измерения: число входящих запросов, занятые соединения и число ожидающих acquisition (получения соединения).

`maximum` — конфигурационная верхняя граница, `inUse` — наблюдение в момент времени. Равенство `inUse == maximum` означает, что новый запрос не может получить слот сейчас; оно не говорит, что слот освободится скоро. Значение `inUse > maximum` — противоречивое состояние модели, которое полезно обнаружить как invalid, а не маскировать ожиданием. Отрицательное число и нулевой максимум также являются ошибкой входа. Эти проверки создают аккуратную границу до вызова драйвера.

При насыщении вызывающий код должен иметь ограниченный бюджет ожидания. В Go обычно передают `context.Context` с deadline в `QueryContext` или другой метод acquisition, чтобы отмена запроса могла распространиться к драйверу. Различайте время полного запроса и время ожидания пула: если осталось 20 миллисекунд до deadline, ожидание ещё 100 миллисекунд заведомо бесполезно. Отмена должна освобождать место в очереди; в реальном драйвере это проверяют конкурентным integration test, а не чистой функцией.

Очередь ожидания сама должна быть ограничена. При неограниченном накоплении система может принять больше запросов, чем способна обслужить, увеличить память и затем массово отклонить их по timeout. Лимит ожидающих — отдельная политика от `maximum` соединений. Справедливость очереди (например FIFO), отмена waiter и реакция на закрытие пула — детали реализации, которые нельзя заключить из количества `inUse`.

Уровни упражнений образуют три ограниченные модели. Easy проверяет границы счётчиков и состояния available/wait. Medium добавляет предел очереди, бюджет времени и решение acquire/reject/timeout. Hard добавляет отмену и фиксирует приоритет: отменённый запрос не должен ждать даже при свободном слоте. Ни одна функция не захватывает mutex, не создаёт соединение и не выдерживает гонку между двумя acquisition. В реальном пуле два запроса могут одновременно увидеть свободный слот; только синхронизированный пул вправе выдать его одному.

Посмотрите метрики, а не только ошибки SQL: открытые соединения, занятые соединения, acquisition latency и число ожиданий. Если ожидание стабильно высокое, увеличение лимита не всегда решение: можно перегрузить базу. Сначала измерьте пропускную способность, распределение длительности запросов и лимиты самой базы. Пул приложения не заменяет серверный лимит и не обещает отказоустойчивость.

## Практика трёх уровней

**Easy — middle-14-easy.** Реализуйте самый узкий контракт. Перед кодом выпишите таблицу вход → результат, отдельно нормальный случай, границу и некорректное состояние. Не добавляйте состояние, которого нет в сигнатуре. Проверьте, что каждый выход имеет конкретное значение для вызывающего слоя.

**Medium — middle-14-medium.** Добавьте независимый сигнал или состояние из условия. Решайте ветви в заданном порядке: сначала невалидное состояние, затем уже совершённый эффект/отмена, затем доступность ресурса, затем временной лимит и только после этого повтор или отказ. Этот порядок важен там, где две причины истинны одновременно. Проверьте конфликтующие входы из public/private vectors.

**Hard — middle-14-hard.** Разберите окно сбоя, неизвестный результат либо ограниченный отказ. Запишите, что система знает до сбоя и что может подтвердить после перезапуска. Не выводите «ровно один раз» из локальной категории: при неопределённом подтверждении реальная система должна повторить безопасно либо запросить сверку. Решение из функции — лишь политика для заданных фактов.

## Три исполняемых примера

```go group=middle-14-easy mode=run
package main
import "fmt"


func PoolStateEasy(inUse int64, maximum int64) string {
	if inUse < 0 || maximum <= 0 || inUse > maximum { return "invalid" }
	if inUse == maximum { return "wait" }
	return "available"
}

func main() { fmt.Println(PoolStateEasy(2, 8)) }
```

```go group=middle-14-medium mode=run
package main
import "fmt"


func PoolAcquireMedium(inUse int64, maximum int64, waiters int64, maxWaiters int64, remainingMs int64) string {
	if inUse < 0 || maximum <= 0 || inUse > maximum || waiters < 0 || maxWaiters < 0 || remainingMs < 0 { return "invalid" }
	if inUse < maximum { return "acquire" }
	if remainingMs == 0 { return "timeout" }
	if waiters >= maxWaiters { return "reject" }
	return "wait"
}

func main() { fmt.Println(PoolAcquireMedium(7, 8, 0, 4, 500)) }
```

```go group=middle-14-hard mode=run
package main
import "fmt"


func PoolAcquireHard(inUse int64, maximum int64, waiters int64, maxWaiters int64, remainingMs int64, canceled bool) string {
	if inUse < 0 || maximum <= 0 || inUse > maximum || waiters < 0 || maxWaiters < 0 || remainingMs < 0 { return "invalid" }
	if canceled { return "canceled" }
	if inUse < maximum { return "acquire" }
	if remainingMs == 0 { return "timeout" }
	if waiters >= maxWaiters { return "reject" }
	return "wait"
}

func main() { fmt.Println(PoolAcquireHard(7, 8, 4, 4, 0, true)) }
```

## Как читать примеры и проверять выводы

Примеры ниже компилируются как небольшие программы и показывают публичный reference для упражнения. Каждый запускает только чистую функцию: в нём нет сетевого клиента, локальной БД, goroutine, таймера, брокера или настоящей конфигурации сервера. Вывод показывает результат контракта на названном input. Он не означает, что внешняя зависимость выдала такой исход, сохранила данные или соблюла порядок. Если пример и формулировка расходятся, исправлять нужно контракт или reference вместе, а не подгонять hidden tests под один частный ответ.

Табличный тест должен называть смысл каждой строки. Укажите входы, ожидаемую категорию и инвариант, который проверяется. Одного «happy path» недостаточно: добавьте точную границу, значение за границей и пересечение двух сигналов, когда приоритет важен. Private vectors должны ловить реализацию, которая всегда возвращает один удобный ответ, игнорирует отдельный аргумент, путает `>=` и `>` или не замечает некорректный счётчик. Случаи должны быть компактны и детерминированы, чтобы ученик мог воспроизвести их локально.

## Что потребуется для реальной проверки

Переход от helper к работающему backend потребует другого набора доказательств. Зафиксируйте версии runtime и зависимости, конфигурацию, лимиты, время ожидания, политику подтверждений и порядок фиксации. Для отказного теста отметьте точку, где процесс останавливается, перезапустите компонент и посчитайте итоговый эффект. Проверяйте, что отмена освобождает ресурсы, повтор не умножает изменение, а постоянная ошибка не крутится бесконечно. Снимайте метрики задержки, backlog и повторов. Unit test не может заменить такие проверки.

Если в системе участвует PostgreSQL, проверьте миграцию, уникальные ограничения, транзакционные границы и конкурентный сценарий на реальном закреплённом движке. Если участвует брокер, тест должен включать его фактический ack/confirm режим и рестарт consumer или relay. Если результат зависит от сети, используйте контролируемый локальный контейнер или fault proxy, а не случайную задержку. Очистка должна быть изолирована от пользовательских данных. Повторяемая команда и зафиксированный fixture позволяют другому разработчику независимо подтвердить результат.

## Диагностика и проектное решение

Начинайте расследование с наблюдаемого состояния: счётчики до операции, момент commit/ack, возвращённая категория, число повторов и конечный эффект. Сверьте часы, единицы измерения и идентификатор операции. Не делайте вывод по одному лог-сообщению, если его могло создать несколько попыток. Корреляционный ID должен быть безопасен и одинаков для повтора; payload, токены, DSN и личные сведения не следует без необходимости писать в лог.

При выборе политики опишите цену обеих сторон. Увеличить ожидание — значит дать системе больше времени, но занять запрос и ресурсы дольше. Быстро отказать — значит сохранить capacity, но передать восстановление вызывающему коду. Повтор — шанс пережить transient сбой и вероятность дублирования. Dead-letter — остановка автоматического шума ценой необходимости диагностики и replay. Хороший middle-level ответ называет условие переключения политики и метрику, которая это условие обнаружит.

Устойчивое решение имеет владельца каждого инварианта. Handler отвечает за решение и контекст; repository — за транзакционное состояние; адаптер брокера — за mapping ack/nack; операторская политика — за лимиты, очередь повторов и восстановление. Не размывайте ответственность между слоями. Наблюдаемая функция из grader помогает изолировать одно правило, а интеграционная система проверяет взаимодействие владельцев. Это разные масштабы доказательства, и оба могут понадобиться.

### Самопроверка

1. Какой вход пересекает границу контракта и меняет решение?
2. Какой отказ может произойти после внешнего эффекта, но до локального подтверждения?
3. Какая часть поведения проверена чистой функцией, а какая требует конкретной инфраструктуры?
4. Какой тест способен обнаружить дубликат, потерю эффекта или утечку ожидающего ресурса?

Перед завершением назовите один непокрытый отказ и один конкретный тест, который мог бы опровергнуть ваше решение. Сохраните команду, fixture, версии и фактическое число эффектов. Не расширяйте утверждение за пределы наблюдений: правильный результат helper — необходимая проверка правила, но не сертификат поведения всей системы.

## Практический мост: настоящий лимит соединений

Helper `PoolState*`/`PoolAcquire*` моделирует решение по переданным счётчикам; он не приобретает соединение атомарно, не ждёт waiter-а и не исполняет SQL. P3 использует pgx pool, но `TestPostgresTaskOutboxAndTenantIsolation` не проверяет исчерпание или ожидание пула. После запуска локального disposable PostgreSQL по `content/projects/p3/README.md`, в первой из двух `psql`-сессий выполните `BEGIN; SELECT pg_sleep(5);`, во второй — `SELECT count(*) FROM pg_stat_activity WHERE datname=current_database();`; наблюдайте серверные сессии и затем завершите первую транзакцию. Это не измеряет Go pool wait. Пробел P3: отдельного теста pgx acquisition timeout/cancel нет; для него нужен тест с `pgxpool.Config.MaxConns=1`, удержанием первого соединения и вторым `Acquire(ctx)` с коротким deadline.

## Сценарий: API запросил соединение

Представьте сервис каталога с `maximum=8`. Семь соединений выполняют медленные запросы. Новый HTTP handler хочет прочитать строку и получает от пула решение `available`, поскольку `inUse=7`. Это лишь снимок: до фактического acquisition другой handler может занять восьмой слот. Значит, код не может сначала вызвать helper, затем считать слот зарезервированным. Сам пул должен атомарно выдать ресурс или поставить вызывающую goroutine в очередь. В примере Easy полезно обсуждать предельное состояние, но не переносить его в production как «проверку перед Query».

Если все восемь соединений заняты, Medium рассматривает очередь. При `waiters=3`, `maxWaiters=4` и `remainingMs=200` разрешено ожидание. При `waiters=4` вход в очередь отклоняется, даже если время ещё осталось. Такая политика защищает память и позволяет быстро вернуть контролируемый overload ответ. При `remainingMs=0` запрос уже исчерпал свой budget; ожидание не должно продлевать общий deadline. Упражнение использует целые миллисекунды только как модель. Реальное время следует передавать через monotonic deadline `context.Context`, а не вручную декрементировать счётчик в каждом слое.

Hard проверяет canceled перед наличием слота. Такое правило выбрано явно: отменённому HTTP запросу не нужно получать соединение для ответа, который клиент больше не ждёт. Если реализация имеет иной продуктовый контракт, его надо назвать и доказать отдельно. Внутри реального пула отмена может состязаться с выдачей: соединение либо передано waiter, либо waiter удалён из очереди, но оно не должно потеряться. Тест на утечку может создать ограниченный пул, заполнить его, отменить ожидающего, освободить слот и убедиться, что следующий клиент получает ресурс.

### Что измерять при насыщении

Наблюдайте текущие open/in-use значения, длительность ожидания, число waiter-ов, число отмен и acquisition timeout. Сравните это с длительностью SQL и latency endpoint. Если SQL быстрое, а ожидание длинное, возможна конкуренция или узкий лимит; если сами запросы медленные, простое увеличение pool size может усилить нагрузку. Проверьте max connections базы, соединения фоновых задач и всех экземпляров приложения: локальный лимит на процесс умножается на реплики. Например, 8 соединений на каждую из 12 реплик потенциально даёт 96 соединений.

### Контрпримеры к модели

Попробуйте мутанты: вернуть `available` при `inUse == maximum`; не проверять `inUse > maximum`; проверять очередь раньше свободного слота; игнорировать `remainingMs`; игнорировать `canceled`. Векторы Easy должны ловить первые два, Medium — полный waiter limit и нулевой budget, Hard — отмену и приоритет. Если private case не отличает мутант, это пробел проверки, а не «сложность для ученика». Также добавьте мысленный сценарий гонки двух acquisition: helper выдаст обоим один ответ, потому что в функции нет состояния, которое менялось бы между вызовами.

### План реального теста

Для integration test настройте `MaxOpenConns` на малое число, например два. Откройте две транзакции и удерживайте их управляемыми каналами; третий запрос запускайте с коротким deadline. Проверьте, что он ожидает, затем завершается по deadline. Отдельно отмените waiter и освободите соединение: отменённый вызов должен завершиться, а новый запрос — успешно получить освободившийся слот. Не используйте `time.Sleep` как синхронизацию; каналы сообщают, что соединение действительно занято. После теста закройте транзакции и пул, иначе утечка тестового ресурса исказит следующие проверки.

### Разбор конкретных решений

Сравните три request-а. Первый приходит при `inUse=7`, `maximum=8`, waiter-ов нет и context жив: модель говорит acquire, но только операция самого пула может выдать слот без гонки. Второй приходит при заполненном пуле, свободном месте в очереди и положительном оставшемся времени: он ждёт, пока драйвер или semaphore пробудит его. Третий приходит с отменённым context: продолжать ждать не следует. В реальном коде не делайте отдельный `if Stats().InUse < max` перед `Query`; между проверкой и запросом состояние изменится. Используйте атомарный API acquisition и передавайте context.

Сравните timeout endpoint с acquisition timeout. Если HTTP request имеет общий deadline 300 ms и уже потратил 280 ms на авторизацию и JSON parsing, пул не должен добавлять ещё 300 ms ожидания. Оставшийся budget около 20 ms может дать timeout раньше; downstream SQL тоже должен использовать тот же deadline. Тайм-аут каждого слоя, сложенный независимо, превращает ожидаемые 300 ms в секунды. Явно описывайте общий deadline и локальные лимиты.

Сигналы overload должны быть предсказуемыми: очередь заполнена — быстро вернуть retryable status или продуктовую ошибку, а не оставить горутину навсегда. Ограниченный retry на клиенте должен иметь jitter, чтобы все клиенты не пришли одновременно. На сервере лимит waiter-ов защищает capacity, но его настройку надо наблюдать вместе с отказами: слишком низкое значение даст всплеск ошибок, слишком высокое — длинную очередь. Экспериментируйте на фиксированной нагрузке, увеличивая только один параметр за раз.

### Дополнительный контроль

Проведите отдельный нагрузочный эксперимент с фиксированным профилем: число запросов, длительность удержания соединения, число реплик и максимальное число соединений. Сначала зафиксируйте baseline, затем изменяйте только одно значение. Сравните p50/p95 ожидания acquisition и latency SQL; среднее может скрыть хвост очереди. Запишите число таймаутов и отмен. Нагрузка должна иметь конечный срок, а после теста пул и транзакции обязаны закрыться. Этот эксперимент измеряет данную среду, он не доказывает универсально оптимальный размер пула.

### Термины

- **connection pool (пул соединений)** — Ограниченный набор повторно используемых соединений.

- **deadline (срок выполнения)** — Момент, после которого работа должна прекратиться.

- **pool wait (ожидание пула)** — Время запроса в очереди за соединением.
