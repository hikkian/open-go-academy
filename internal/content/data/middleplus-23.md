# 23. Postmortem, временная шкала и системные меры

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-22`  
**Цель:** Postmortem (разбор инцидента после события) помогает восстановить временную линию, условия возникновения и эффективность защит. Blameless (без обвинения) означает, что анализирует систему решений и обратной связи, а не ищет удобного виноватого. Практические действия должны снижать риск повторения, иметь владельца, проверяемый результат и срок; список общих пожеланий не меняет надёжность.

## Термины и перевод

- **Postmortem** — Postmortem (разбор инцидента после события) помогает восстановить временную линию, условия возникновения и эффективность защит. Blameless (без обвинения) означает, что анализирует систему решений и обратной связи, а не ищет удобного виноватого. Практические действия должны снижать риск повторения, иметь владельца, проверяемый результат и срок; список общих пожеланий не меняет надёжность.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Разбор инцидента после события (postmortem) восстанавливает, что наблюдалось, когда принимались решения и какие защитные меры сработали. Временная шкала полезна только при различении факта и предположения: отметка времени и источник подтверждают событие, а причинное объяснение требует отдельной проверки.

Сначала оцените, продолжается ли воздействие; если да, приоритет — безопасное смягчение. После стабилизации соберите доступные факты в порядке времени и укажите пробелы доказательств. Затем сформулируйте действия, которые меняют систему или процесс: у каждого должен быть владелец, срок и проверяемое условие завершения. Blameless (без обвинения) значит исследовать условия принятия решений, а не назначать виноватого вместо исправления барьеров.

Функции урока проверяют порядок временных отметок, наличие evidence (доказательств) и формальные поля action item (пункта действия). Они не читают реальные журналы, не устанавливают причинность и не подтверждают, что исправление внедрено. Качество вывода и точность описания требуют человеческой проверки.

## Три запускаемых примера


### Пример 1: Postmortem facts: ordered timestamps, evidence presence and active incident response

```go
package main

import "fmt"

func IncidentPriority(impact int, ongoing bool, eventTimes []int, observed []bool) string { if impact<0||len(eventTimes)==0||len(eventTimes)!=len(observed){return "invalid"}; for i,t:=range eventTimes {if t<0||(i>0&&t<eventTimes[i-1]){return "invalid"}}; if ongoing{return "respond"}; for _,ok:=range observed{if !ok{return "review_gaps"}}; return "review" }

func main() { fmt.Println(IncidentPriority(2, true, []int{0, 5}, []bool{true, true})) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 2: Postmortem actions: mitigation first, then evidence, ownership and due date

```go
package main

import "fmt"

func IncidentAction(impact int, ongoing bool, mitigationReady bool, evidenceCount int, ownerAssigned bool, dueDay int) string { if impact<0||evidenceCount<0||dueDay<0{return "invalid"}; if ongoing{return "mitigate"}; if evidenceCount<2{return "collect_evidence"}; if mitigationReady{return "verify"}; if ownerAssigned&&dueDay>0{return "track_action"}; return "assign_action" }

func main() { fmt.Println(IncidentAction(2, true, false, 2, true, 4)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 3: Postmortem completion invariant: factual ordered evidence and verified owned action item

```go
package main

import "fmt"

func PostmortemReady(eventTimes []int, observed []bool, actionStatus string, ownerAssigned bool, dueDay int, verified bool) bool { if len(eventTimes)<2||len(eventTimes)!=len(observed)||dueDay<0{return false}; for i,t:=range eventTimes {if t<0||(i>0&&t<eventTimes[i-1])||!observed[i]{return false}}; return actionStatus=="closed"&&ownerAssigned&&dueDay>0&&verified }

func main() { fmt.Println(PostmortemReady([]int{0, 5, 9}, []bool{true, true, true}, "closed", true, 10, true)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.

## Практическая процедура

Соберите временную шкалу из проверяемых событий: время, источник, наблюдаемый факт и уровень уверенности. Сохраните неизвестные интервалы как пробелы; не заполняйте их догадкой. Проверьте, упорядочены ли события и достаточно ли доказательств для вопроса, на который вы отвечаете.

Отдельно перечислите непосредственное смягчение и последующие действия. У каждого действия укажите изменение, владельца, срок и способ проверить результат. «Улучшить мониторинг» слишком расплывчато без названной метрики или условия приёмки. Перед закрытием подтвердите выполненное действие наблюдаемым артефактом, а не одним статусом `closed`.

Прогоните helper на корректной шкале, пропущенном доказательстве и незавершённом действии. Это проверяет структуру и приоритеты, но не достоверность источников или причинный анализ. Нужен независимый review, который сверит выводы с фактами и отделит технические меры от гипотез.

## Разбор сценария: Postmortem, временная шкала и системные меры

Рассмотрите учебную временную шкалу из нескольких событий с известными отметками и источниками. Сначала отметьте, продолжается ли воздействие: если да, действие по смягчению предшествует оформлению отчёта. После стабилизации упорядочьте факты и пометьте отсутствующее доказательство как пробел, а не как событие, которое «наверняка произошло».

Выберите один системный барьер, который можно изменить, и превратите его в action item: конкретное изменение, владелец, срок, критерий приёмки и evidence после выполнения. Проверьте, что критерий показывает эффект, а не только факт закрытия задачи. Если причина пока не установлена, укажите конкурирующие гипотезы и следующий сбор данных.

Сопоставьте эти поля с результатом helper. Он подтверждает лишь структурные условия для данного набора входов; не устанавливает виновность, полноту рассказа, причинность или фактическое внедрение меры. Итоговый разбор должен быть проверен человеком по исходным источникам.

## Лаборатория: превратить временную шкалу в меры

### Учебный сценарий и факты

Рассмотрим условный сбой: запросы стали завершаться медленнее, затем очередь выросла, дежурный снизил входящий поток, после чего задержка вернулась в обычный диапазон. Это лишь порядок наблюдений, он сам по себе не устанавливает причину. Рост очереди мог быть причиной замедления, следствием медленной базы или совпасть с отдельным изменением. Сначала запишите источники и время каждого сигнала, включая точность часов и возможные задержки доставки.

Разделите временную шкалу на факт, интерпретацию и неизвестное. «В метрике глубина равна 80 в 10:05» — факт при известном источнике. «Очередь вызвала инцидент» — гипотеза, требующая связи с другими наблюдениями. «Дежурный не заметил алерт» требует проверки маршрута доставки и того, какой сигнал был доступен человеку. Не превращайте последовательность событий в причинную историю без проверки.

### Последовательность разбора

1. Сначала укажите, продолжается ли воздействие и нужна ли немедленная мера смягчения. В активном инциденте защита пользователя важнее полного текста отчёта.
2. После стабилизации зафиксируйте временную зону, источники, точность отметок, пропуски и дубли событий.
3. Для каждого решения запишите, какая информация была доступна в тот момент, какие альтернативы рассматривались и что изменилось после действия.
4. Сформулируйте несколько объяснений, совместимых с фактами. Для каждого укажите следующее наблюдение, которое отличило бы его от альтернатив.
5. Превратите подтверждённую системную причину в проверяемую меру с владельцем, сроком и доказательством завершения.

### Как писать действие

«Команда должна быть внимательнее» не меняет интерфейс или защиту. Более конкретный пункт может обязать систему отклонять работу до исчерпания памяти, показать старейший возраст задачи в алерте или провести репетицию переключения. Но даже такие предложения пока гипотезы: укажите критерий проверки, например тест, показывающий, что лимит не превышается, или запись успешной репетиции. Владелец отвечает за доведение меры, а независимый reviewer (проверяющий) подтверждает доказательство.

Статус `closed` не равен внедрённому и эффективному изменению. Спросите, какой артефакт демонстрирует результат: ссылка на изменение, отчёт теста, график после выпуска или подписанная процедура. Если мера не сработала, оставьте её незакрытой или откройте следующую работу. Срок помогает планировать, но сам по себе не доказывает риск снижен.

### Blameless анализ и его границы

Blameless (без обвинения) не означает, что действия людей исключены из временной шкалы. Записывайте, какие данные, инструкции, доступ и ограничения сформировали решение, не подменяя системный анализ персональным ярлыком. Фактические ошибки и решения могут иметь значение для обучения; намерения нельзя вывести из одной телеметрии. Сохраняйте точные наблюдения и обозначайте неопределённость.

Helper проверяет порядок временных отметок, наличие булевых подтверждений и формальные поля действия. Он не подтверждает подлинность журналов, полноту шкалы, человеческое понимание или причинность. Проведите независимое чтение отчёта по первичным источникам. Вопросы для итоговой проверки: какой факт опроверг бы главную гипотезу, почему выбрано именно это действие, как измерить его эффект и что остаётся неизвестным?

### Проверить действие после закрытия

Эффект меры может проявиться только при повторении исходных условий. Если добавили ограничение размера очереди, проверьте его на тесте, который раньше превышал предел. Если изменили алерт, воспроизведите сигнал и подтвердите доставку до правильного владельца. Если обновили процедуру, проведите тренировку и запишите, смогли ли участники выполнить шаги. Простое слияние кода или закрытие задачи доказывает изменение артефакта, но не обязательно уменьшение риска.

Планируйте проверку до выполнения: сохраните исходный результат, выберите измеримый критерий и укажите окно после внедрения. Если показатель не изменился, это не автоматически означает провал; возможно, инцидентный сценарий редок или тест не воспроизвёл нужное условие. Тогда пересмотрите связь между мерой и гипотезой, не подменяя метрику постфактум.

При повторном инциденте обновите временную шкалу и отметьте, сработала ли новая защита. Не переписывайте старый отчёт так, будто неопределённость никогда не существовала. История решений полезна для оценки того, какие меры были разумны с известными тогда данными. Это поддерживает обучение и ответственность без обвинительного упрощения.

### Проверьте доказательство до закрытия

Для временной шкалы попросите второго читателя связать каждый важный вывод с первичным источником. Если источник недоступен, обозначьте утверждение как неподтверждённое. Порядок отметок не доказывает, что часы были синхронизированы; источники могут иметь разные задержки и точность. Укажите используемую временную зону и известные расхождения.

Для действия попросите владельца показать фактический артефакт и reviewer-а проверить критерий приёмки. Это не формальность: задача может быть закрыта после изменения кода, который не включён в релиз. Если внедрение невозможно, перепишите действие или эскалируйте блокер с конкретной причиной. Не заменяйте проверяемый критерий устным заверением.

### Сверьте хронологию с решениями

Для каждого важного действия отметьте входной сигнал, который человек видел до принятия решения. Не используйте метрику, опубликованную позже, как будто она была доступна в момент инцидента. Это позволяет оценить не только технический эффект, но и качество инструментов поддержки решения.

Если временные метки различаются между системами, укажите погрешность или порядок, который можно подтвердить без точных часов. Не стройте причинный вывод на разнице в несколько секунд, когда синхронизация неизвестна. Попросите участника подтвердить свой контекст и отделите его воспоминание от сохранённого события.

После публикации отчёта определите дату пересмотра действий. Меры с долгим сроком могут потерять владельца; переназначение и проверка блокеров должны быть видимы. Это процессная рекомендация, а не поле, проверяемое helper-функцией.

## Практика Easy / Medium / Hard

**Easy — классификация.** Реализуйте первую функцию из контракта и проверьте корректный обычный случай, пустую/нулевую границу и явно невозможное значение. Результат должен точно совпасть с контрактом.

**Medium — политика с приоритетом.** Реализуйте вторую функцию. Сначала перечислите правила сверху вниз; при нескольких одновременно истинных условиях применяется первое. Добавьте тесты обычного состояния, насыщения, неизвестного значения и некорректной комбинации. Для числа/boolean не преобразуйте выход в произвольную строку.

**Hard — инвариант.** Реализуйте третью функцию, которая подтверждает только безопасную комбинацию предусловий. Граничный и противоречивый векторы обязаны отклоняться. Объясните, почему успешный результат helper не является реальным benchmark, fault test, безопасным rollout или гарантией доступности. Public и private cases находятся в JSON specs соответствующих exercise ID.

### Рабочий вопрос 1: границы postmortem

Сопоставьте postmortem с владельцем источника истины и назовите событие, после которого повтор становится безопасным. Запишите сначала ожидаемое состояние, затем вход, действие и наблюдаемый исход. Не выводите причинность из одного совпадения; сохраните команду, версию среды, количество повторов и ошибочные варианты. Если данных недостаточно, итогом должна быть отметка «неизвестно» и план следующего измерения, а не уверенная оценка. Укажите, какая часть ответа проверяется функцией, а какая потребовала бы отдельного интеграционного теста или человеческого review.
