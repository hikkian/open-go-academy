# Postmortem, временная шкала и системные меры

## Что ты сделаешь

Ты разберёшь, как после инцидента восстановить временную шкалу из фактов, а не предположений, почему разбор без обвинения — это метод, а не вежливость, и что отличает действие, которое снижает риск повторения, от пожелания в списке. Три функции урока — `IncidentPriority`, `IncidentAction`, `PostmortemReady` — проверяют порядок отметок времени, наличие свидетельств и формальные поля пунктов действий; реальные журналы они не читают и причинность не устанавливают.

## Зачем нужна эта граница

Разбор инцидента после события (postmortem) восстанавливает, что наблюдалось, когда принимались решения и какие защиты сработали. Временная шкала (timeline) полезна только при различении факта и предположения: отметка времени с источником — журнал, метрика, сообщение в чате — подтверждает событие; причинное объяснение «это случилось из-за того» требует отдельной проверки и помечается как гипотеза, пока не подтверждено.

Первое правило — порядок. Пока воздействие продолжается, приоритет у безопасного смягчения, а не у разбора: собирать шкалу во время пожара — тратить людей, которые тушат. После стабилизации собирают факты в порядке времени и явно отмечают пробелы: «между 10:04 и 10:11 наблюдений нет». Пробел — тоже факт, и он часто важнее заполненных строк: там, где нет наблюдений, не было и защит.

```go group=priority mode=run
package main

import "fmt"

func incidentPriority(impact int, ongoing bool, eventTimes []int, observed []bool) string {
    if impact < 0 || len(eventTimes) == 0 || len(eventTimes) != len(observed) {
        return "invalid"
    }
    for i, t := range eventTimes {
        if t < 0 || (i > 0 && t < eventTimes[i-1]) {
            return "invalid"
        }
    }
    if ongoing {
        return "respond"
    }
    for _, ok := range observed {
        if !ok {
            return "review_gaps"
        }
    }
    return "review"
}

func main() {
    fmt.Println(incidentPriority(2, true, []int{0, 5}, []bool{true, true}), incidentPriority(2, false, []int{0, 5}, []bool{true, true}), incidentPriority(2, false, []int{0, 5}, []bool{true, false}))
    fmt.Println(incidentPriority(2, false, []int{5, 4}, []bool{true, true}), incidentPriority(0, false, []int{0, 0}, []bool{true, true}), incidentPriority(2, false, []int{0}, []bool{}))
}
```

Вывод:

```text
respond review review_gaps
invalid review invalid
```

Шкала с убывающими отметками — некорректна: события не могут идти назад, и такой список чинят до разбора. Равные отметки допустимы — события в одну секунду. Продолжающийся инцидент — `respond` независимо от полноты шкалы; закрытый с неподтверждёнными событиями — `review_gaps`: сначала закрыть пробелы наблюдений.

> **Важно.** `ongoing` проверяется раньше пробелов: во время инцидента вопрос «полна ли шкала» неуместен, уместен вопрос «что мы делаем сейчас».

## Без обвинения — значит про систему

Blameless означает, что разбор исследует условия, в которых принимались решения: какая информация была доступна, какие сигналы отсутствовали, какие защиты не сработали, — а не ищет, кто нажал кнопку. Назначить виноватого проще, чем починить барьер, и ровно поэтому бесполезно: тот же барьер пропустит следующего. Вопрос разбора — не «почему он это сделал», а «почему это казалось разумным и что должно было остановить».

Из этого следует и структура пунктов действий: они меняют систему или процесс, а не людей. «Быть внимательнее» — не действие. «Добавить проверку совместимости миграции в конвейер выпуска, владелец — команда платформы, срок — две недели, критерий — конвейер блокирует несовместимую миграцию в тестовом прогоне» — действие.

```go group=action mode=run
package main

import "fmt"

func incidentAction(impact int, ongoing, mitigationReady bool, evidenceCount int, ownerAssigned bool, dueDay int) string {
    if impact < 0 || evidenceCount < 0 || dueDay < 0 {
        return "invalid"
    }
    if ongoing {
        return "mitigate"
    }
    if evidenceCount < 2 {
        return "collect_evidence"
    }
    if mitigationReady {
        return "verify"
    }
    if ownerAssigned && dueDay > 0 {
        return "track_action"
    }
    return "assign_action"
}

func main() {
    fmt.Println(incidentAction(2, true, false, 2, true, 4), incidentAction(2, false, true, 2, true, 4), incidentAction(2, false, false, 1, false, 0))
    fmt.Println(incidentAction(2, false, false, 2, true, 4), incidentAction(2, false, false, 2, false, 0), incidentAction(2, false, false, 2, true, 0))
}
```

Вывод:

```text
mitigate verify collect_evidence
track_action assign_action assign_action
```

Порядок шагов: смягчить, пока продолжается; собрать не меньше двух независимых свидетельств, прежде чем что-то утверждать; если мера готова — проверить её; если нет — следить за пунктом действия с владельцем и сроком, а без них — назначить. Владелец без срока — не отслеживание: пункт без даты живёт в списке годами.

> **Типичная ошибка.** Одно свидетельство как основание для вывода. Сообщение в чате «кажется, упала база» — наблюдение, а не факт; факт — метрика базы с отметкой времени и запись в журнале приложения, совпадающие между собой.

## Когда разбор готов

Разбор закрывают по формальным признакам, которые можно проверить: шкала из двух и более событий, упорядоченных и подтверждённых; пункты действий закрыты, у них были владелец и срок; результат проверен — мера действительно блокирует сценарий инцидента. Формальная готовность не оценивает качество текста и правильность причинного объяснения — это делает человек, читающий разбор.

```go group=ready mode=run
package main

import "fmt"

func postmortemReady(eventTimes []int, observed []bool, actionStatus string, ownerAssigned bool, dueDay int, verified bool) bool {
    if len(eventTimes) < 2 || len(eventTimes) != len(observed) {
        return false
    }
    for i, t := range eventTimes {
        if t < 0 || (i > 0 && t < eventTimes[i-1]) || !observed[i] {
            return false
        }
    }
    return actionStatus == "closed" && ownerAssigned && dueDay > 0 && verified
}

func main() {
    fmt.Println(postmortemReady([]int{0, 5, 9}, []bool{true, true, true}, "closed", true, 10, true), postmortemReady([]int{0, 5}, []bool{true, true}, "open", true, 10, false))
    fmt.Println(postmortemReady([]int{0, 5, 9}, []bool{true, true, true}, "closed", true, 10, false), postmortemReady([]int{0, 1}, []bool{true, true}, "Closed", true, 1, true), postmortemReady([]int{0, 0}, []bool{true, true}, "closed", true, 1, true))
}
```

Вывод:

```text
true false
false false true
```

Статус сравнивается точно: `Closed` с заглавной — не `closed`, потому что статус — машинное поле, а не текст для человека. Пункт закрыт, но не проверен — разбор не готов: закрытие без проверки означает, что мера внедрена на словах. Шкала из одного события — не шкала: нужны хотя бы начало и конец.

> **Зачем.** Формальные признаки нужны, чтобы разбор нельзя было закрыть «устали обсуждать»: пока нет проверенной меры с владельцем и сроком, он открыт.

## Из чего состоит шкала

Каждая строка: отметка времени (единый часовой пояс, источник часов назван), событие (что наблюдалось, не что подумали), источник (метрика, журнал, сообщение, действие оператора), кто или что это заметило, и пометка «факт/гипотеза». Отдельно — моменты решений: что знали, что выбрали, что из этого следовало. Между строками — пробелы с вопросом «почему здесь не было наблюдения». Шкала с метками обнаружения, смягчения и восстановления даёт три числа — время до обнаружения, до смягчения, до восстановления, — и именно их улучшают меры, а не «надёжность вообще».

## Практическая процедура

Возьми любой инцидент — реальный или из лаборатории прошлых уроков — и восстанови шкалу из пяти и более строк с источниками. Отметь пробелы и гипотезы. Сформулируй два пункта действий по форме «что меняем в системе, владелец, срок, критерий проверки»; для каждого запиши, какой пробел шкалы он закрывает. Прогони шкалу и пункты через функции урока: шкала упорядочена и подтверждена? у пункта есть владелец и срок? проверен ли результат? Расхождение с ожиданием — повод уточнить запись, а не функцию.

## Типичные ошибки

- Разбор во время инцидента: люди тушат и пишут одновременно, плохо и то, и другое.
- Гипотезы в шкале без пометки: «из-за» вместо «после».
- Одно свидетельство как факт.
- Поиск виноватого вместо починки барьера.
- Пункт действия без владельца, срока или критерия проверки.
- Закрытие разбора без проверки, что мера блокирует сценарий.

## Самостоятельная лаборатория

Воспроизведи инцидент на стенде из урока об инъекции отказов: отказ зависимости на три минуты под нагрузкой. Собери шкалу только из машинных источников — метрик и журналов — с отметками обнаружения, смягчения и восстановления, и посчитай три времени. Найди пробел: интервал, где по журналам ничего нет, и предложи наблюдение, которое его закроет. Оформи один пункт действия по форме и внедри его на стенде; повтори инцидент и покажи, какое из трёх времён уменьшилось. Удали стенд.

## Если что-то пошло не так

- `review` при пробелах наблюдений → проверка `observed` отсутствует.
- `respond` не возвращается при продолжающемся инциденте → `ongoing` проверяется после шкалы; должен быть после валидности и до пробелов.
- `track_action` без срока → нужно `dueDay > 0`.
- `verify` при одном свидетельстве → свидетельства проверяются раньше готовности меры.
- `true` при `Closed` → статус сравнивается точно.
- `import … is not allowed` → импорты запрещены.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Входы — формальные поля разбора; функции не читают журналы и не устанавливают причинность.

### Задание 1 · Easy: postmortem, временная шкала и системные меры — классификация

**Цель.** `impact < 0`, пустые или разной длины массивы, отрицательные или убывающие отметки → `invalid`; `ongoing` → `respond`; любое `observed = false` → `review_gaps`; иначе `review`.

**Ожидаемый вывод** — для `(2, true, [0,5], [true,true])` и `(2, false, [0,5], [true,true])`:

```text
"respond"
"review"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func IncidentPriority(impact int, ongoing bool, eventTimes []int, observed []bool) string`. Импорты запрещены.
2. Валидность: воздействие, длины, отметки неотрицательны и не убывают.
3. `ongoing` → `respond`; затем поиск `false` в `observed` → `review_gaps`; иначе `review`.
4. «Запустить», «Проверить» — закрытые примеры: пробел при закрытом инциденте → `review_gaps`; продолжающийся с пробелом → `respond`; убывающие отметки → `invalid`; равные отметки → допустимо.

**Как проверить себя.** Равные отметки допустимы, убывающие нет; продолжающийся инцидент побеждает пробелы.

**Если не принято.**
- `invalid` для `[0, 0]` → нестрогое сравнение `<=` вместо `<`.
- `review_gaps` при `ongoing = true` → порядок правил.

> **Подсказка.** Два цикла: один по отметкам для валидности, другой по `observed` после проверки `ongoing`.

### Задание 2 · Medium: postmortem, временная шкала и системные меры — политика

**Цель.** Отрицательные `impact`, `evidenceCount` или `dueDay` → `invalid`; `ongoing` → `mitigate`; меньше двух свидетельств → `collect_evidence`; `mitigationReady` → `verify`; владелец и срок > 0 → `track_action`; иначе `assign_action`.

**Ожидаемый вывод** — для `(2, true, false, 2, true, 4)` и `(2, false, true, 2, true, 4)`:

```text
"mitigate"
"verify"
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func IncidentAction(impact int, ongoing bool, mitigationReady bool, evidenceCount int, ownerAssigned bool, dueDay int) string`. Импорты запрещены.
2. Шесть правил в порядке цели.
3. «Запустить», «Проверить» — закрытые примеры: одно свидетельство → `collect_evidence` даже при готовой мере; владелец без срока → `assign_action`; нулевое воздействие с владельцем и сроком → `track_action`.

**Как проверить себя.** Свидетельства проверяются раньше готовности меры; срок обязателен для отслеживания.

**Если не принято.**
- `verify` при одном свидетельстве → порядок правил.
- `track_action` при `dueDay = 0` → срок должен быть положительным.

> **Подсказка.** Шесть `return` подряд; `impact` участвует только в валидности.

### Задание 3 · Hard: postmortem, временная шкала и системные меры — проверка инварианта

**Цель.** `true` только если отметок не меньше двух, массивы согласованы, отметки неотрицательны и не убывают, все наблюдения подтверждены, статус ровно `closed`, владелец назначен, срок > 0 и результат проверен.

**Ожидаемый вывод** — для `([0,5,9], [true,true,true], "closed", true, 10, true)` и `([0,5], [true,true], "open", true, 10, false)`:

```text
true
false
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func PostmortemReady(eventTimes []int, observed []bool, actionStatus string, ownerAssigned bool, dueDay int, verified bool) bool`. Импорты запрещены.
2. Длина ≥ 2 и равные длины; цикл по отметкам: неотрицательны, не убывают, каждое наблюдение подтверждено.
3. Верни `actionStatus == "closed" && ownerAssigned && dueDay > 0 && verified`.
4. «Запустить», «Проверить» — закрытые примеры: не проверено → `false`; пробел → `false`; `Closed` → `false`; срок 0 или −1 → `false`; две равные отметки → `true`; массивы разной длины → `false`.

**Как проверить себя.** Статус — точная строка; одна отметка — не шкала; закрытый, но непроверенный пункт не закрывает разбор.

**Если не принято.**
- `true` для `Closed` → сравнение без учёта регистра.
- `true` при одной отметке → проверка `len >= 2` отсутствует.

> **Подсказка.** Один цикл проверяет три условия на каждую отметку; остальное — одно выражение.

## Проверь себя

- Чем факт на шкале отличается от гипотезы?
- Почему разбор не начинают, пока инцидент продолжается?
- Что означает «без обвинения» на практике?
- Что делает пункт действия действием, а не пожеланием?
- Какие три времени показывает шкала и как их улучшают?

## Итог

- Шкала — упорядоченные факты с источниками и помеченными пробелами; гипотезы отделены от наблюдений.
- Порядок: смягчить, собрать не меньше двух свидетельств, проверить меру, назначить владельца и срок.
- Разбор закрыт, когда мера проверена и блокирует сценарий; «без обвинения» значит чинить барьеры, а не людей.
