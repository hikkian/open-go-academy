# 35. Fault injection и postmortem

**Ранг:** Middle · **Время:** 150–180 минут · **Предварительные требования:** `middle-34`; предыдущая глава `middle-34`.  
**Планируемый порядок каталога:** 75.  
**Результат:** Планировать fault injection только с изолированной областью и измеримым stop condition.; Отделять наблюдаемые факты инцидента от гипотез и назначать проверяемые действия.; Не считать enum helper доказательством восстановления реальной зависимости.

## Глоссарий

- **fault injection (инъекция отказа)** — Заранее ограниченное внесение сбоя в изолированной тестовой среде.
- **stop condition (условие остановки)** — Измеримое событие или предел, после которого эксперимент немедленно прекращается.
- **postmortem (разбор инцидента)** — Хронология, влияние, факты, неизвестные и проверяемые действия после восстановления.
- **blameless (без поиска виноватого)** — Анализ условий системы и защит, не обвинение отдельного человека.
- **action item (корректирующее действие)** — Назначенное изменение с владельцем, сроком и проверяемым критерием завершения.

## Теория и границы применения

Fault injection (инъекция отказа) проверяет заранее сформулированную гипотезу о реакции системы на отказ. Это эксперимент, а не произвольное выключение зависимости. До запуска определите тестовую среду, точку инъекции, начальное состояние, ожидаемые наблюдения, предел времени/запросов и условие немедленной остановки. Запрещено использовать production данные или направлять учебный сбой в чужую среду. У теста должен быть cleanup, который выполняется и после ошибки самого теста.

Для TaskFlow полезно разделять точки сбоя относительно commit. До commit транзакция должна откатить доменное изменение и outbox запись вместе. После commit публикация может быть ещё не выполнена, поэтому worker обязан обнаружить сохранённое событие позже. Если брокер принял сообщение, а подтверждение потерялось, возможна повторная публикация; consumer должен переносить повтор без второго бизнес-эффекта. Переключение enum `before_commit` в helper не останавливает базу или брокер и не проверяет эти границы.

Проводите эксперимент малыми шагами. Сначала выполните контрольный сценарий без инъекции и зафиксируйте baseline. Затем внесите один сбой, наблюдайте ограниченный эффект, остановите нагрузку при нарушении stop condition и проверьте восстановление зависимости и очистку временных ресурсов. Не объединяйте одновременно задержку, потерю сети и нехватку места: если исход неожиданен, одна переменная облегчает поиск причины. Повторяйте эксперимент только после восстановления исходного состояния.

Postmortem — разбор после восстановления, который сохраняет факты, а не оправдывает заранее выбранную версию. Запишите время событий, затронутый путь и пользователей, обнаружившие сигналы, длительность и масштаб влияния, действия во время инцидента, пробелы telemetry и момент восстановления. Различайте «что наблюдалось» и «почему это произошло»: первое подтверждается логом или метрикой, второе остаётся гипотезой до проверки.

Blameless подход не означает отсутствие ответственности. Он ищет условия, при которых разумное действие привело к плохому результату: неясный интерфейс, неограниченный retry, отсутствие stop condition или недоступный сигнал. Корректирующее действие должно иметь владельца, конкретный срок и проверяемый результат — например, тест, который воспроизводит ошибку, либо alert с проверенным порогом. Формулировка «улучшить мониторинг» сама по себе не задаёт критерий завершения.

Не публикуйте секреты и персональные данные в постмортеме. Сохраняйте очищенные логи, точные команды и версии, контрольные идентификаторы эксперимента и ограничения среды. После выполнения отдельно подтвердите остановку инъектора, закрытие соединений, очистку временной очереди и возвращение зависимости в ожидаемое состояние. Одно значение `SafeExperiment` лишь классифицирует заданные флаги и не подтверждает безопасность либо восстановление реального эксперимента.

Для упражнения по incident action используйте короткий сценарий: публикация сообщения задержалась, очередь растёт, но доменные записи фиксируются. Зафиксируйте временную шкалу по единому времени, объём ожидающих событий и момент, когда рост остановился. Отдельно пометьте, что подтверждено метрикой, что известно из логов, а что участники лишь предполагают. Действие «увеличить worker» должно иметь проверку побочного эффекта: не перегрузит ли оно базу и не начнёт ли повторять события без idempotency. Хороший postmortem также указывает, какие сигналы отсутствовали и как отличить потерю telemetry от здорового состояния. Сохраните решение об остановке эксперимента и очистке тестовых сообщений. Не публикуйте имена пользователей, ключи, токены и полный request body в отчёте. Рецензент должен иметь возможность оспорить вывод по указанным доказательствам, а не по авторитету автора.

## Три самостоятельных запускаемых примера

### Пример 1: `FaultStage`

Контракт: before_commit→rollback; after_commit→reconcile; publish→republish_idempotently; неизвестное→unknown.

```go
package main

import "fmt"

func FaultStage(stage string) string {
	switch stage { case "before_commit": return "rollback"; case "after_commit": return "reconcile"; case "publish": return "republish_idempotently"; default: return "unknown" }
}

func main() {
	fmt.Println(FaultStage("publish"))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 2: `IncidentAction`

Контракт: Отрицательный impact→invalid; ongoing→mitigate; завершён без меры→assign_action; иначе verify.

```go
package main

import "fmt"

func IncidentAction(ongoing bool, impact int, mitigationReady bool) string {
	if impact < 0 { return "invalid" }; if ongoing { return "mitigate" }; if !mitigationReady { return "assign_action" }; return "verify"
}

func main() {
	fmt.Println(IncidentAction(true, 2, false))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

### Пример 3: `SafeExperiment`

Контракт: true только при известном условии остановки, ограниченном охвате и отсутствии production data.

```go
package main

import "fmt"

func SafeExperiment(hasStopCondition, boundedScope, usesProductionData bool) bool {
	return hasStopCondition && boundedScope && !usesProductionData
}

func main() {
	fmt.Println(SafeExperiment(true, true, false))
}
```

Запуск: сохраните только этот блок в `main.go` и выполните `go run .`. Значения заданы в программе, поэтому результат детерминирован; программа не подключается к приложению и не проверяет внешние гарантии.

## Лабораторная карточка TaskFlow: Fault injection и postmortem

Определите конкретный сценарий с одной пользовательской операцией. Укажите principal, объект, tenant, действие и ожидаемое состояние. Перечислите trust boundary (границу доверия), где вход считается недоверенным, где аутентификация проверена, и какой сервис принимает окончательное решение. Затем перечислите наблюдения: ответ HTTP, доменное событие, запись данных, лог и trace. Если одно из наблюдений отсутствует или запаздывает, результат должен оставаться неопределённым, а не автоматически считаться успешным.

До запуска теста зафиксируйте начальное состояние и независимые данные для двух владельцев. Включите положительный случай и минимум две отрицательные комбинации: неверный tenant, неверная роль, отменённый context, истёкший deadline, закрытие сервера или повторное событие — выберите те, которые относятся к теме главы. Подтвердите, что отрицательный сценарий не меняет данные и не пишет секрет в лог. Если чистый helper не может показать этот эффект, обозначьте интеграционную проверку как отдельное обязательное доказательство.

Наблюдение следует отделить от интерпретации. «Ответ вернул 404» — факт теста; «IDOR невозможен» — слишком сильный вывод. Чтобы обосновать более узкое утверждение, проверьте конкретный endpoint с authenticated principal, запустите запрос с чужим ID и подтвердите отсутствие утечки тела и побочного изменения. Аналогично, один `go test -race` на небольшой набор не гарантирует отсутствия data race при другой последовательности. Укажите точные пути, которые тест фактически исполнил.

Для operational readiness перечислите владельцев процедур: кто меняет readiness, кто наблюдает drain, кто смотрит saturation, кто останавливает нагрузочный тест и кто принимает rollback решение. Пороговые значения должны быть определены владельцами проекта и измерены на сопоставимой среде. Эта программа не задаёт production SLA. Если у учебной системы пока нет измеренных данных, запишите только ожидаемые проверки и назовите статус как непроверенный.

Для failure case определите инъекцию только в тестовой среде и ограничьте воздействие числом запросов, временем либо тестовой очередью. До старта проверьте cleanup и состояние ресурса. После эксперимента подтвердите, что соединения закрыты, временные записи очищены и service вернулся к ready только после проверки обязательной зависимости. При неожиданном результате немедленно прекратите эксперимент и сохраните логи с очищенными секретами. Не расширяйте нагрузку, пока не объяснили расхождение и не повторили исходный контрольный прогон.

На review передайте короткую карточку: код/commit, версия Go, команда, входные vectors, результат каждого теста, окружение, риски и пробелы. Попросите рецензента указать альтернативное объяснение результата. Если независимый читатель трактует сообщение сильнее, чем измерения, уточните claim. Назначьте конкретное следующее действие только при ясной проверке завершения; общие призывы «улучшить мониторинг» не являются завершённым пунктом.

## Воспроизводимая лабораторная: отказ worker на тестовой БД

**Prerequisites:** Go 1.27.2, Docker Compose v2, POSIX shell с `openssl`/`seq` и свободный loopback-порт 55433. Из корня репозитория поднимите только закреплённую disposable БД из P3; случайный пароль хранится лишь в текущей shell-сессии:

```sh
set -eu
cd content/projects/p3
export POSTGRES_USER=taskflow POSTGRES_PASSWORD="$(openssl rand -hex 24)" POSTGRES_DB=taskflow_test
docker compose -p oga-middle35 up -d db
for attempt in $(seq 1 30); do
  if docker compose -p oga-middle35 exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB" >/dev/null 2>&1; then break; fi
  sleep 1
done
docker compose -p oga-middle35 exec -T db pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"
cd reference
TASKFLOW_TEST_DATABASE_URL="postgres://taskflow:${POSTGRES_PASSWORD}@127.0.0.1:55433/taskflow_test?sslmode=disable" go test -run '^TestPostgresTaskOutboxAndTenantIsolation$' -count=1 -v
```



**Ожидайте:** один тестовый прогон на случайных строках/схеме; сверяйте фактически перечисленные retry/lease assertions с выводом. Это контролируемый integration test, а не нагрузка и не доказательство восстановления после произвольного production-сбоя. Сохраните только команду и PASS/FAIL, не секрет URL. **Очистка:** `cd .. && docker compose -p oga-middle35 down -v`; volume содержит только тестовую БД этого опыта.
