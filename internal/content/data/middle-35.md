# Fault injection и postmortem

## Что ты сделаешь

Ты напишешь три проверки, которые помогают спланировать эксперимент с отказом и разобрать инцидент: выбор действия восстановления по стадии сбоя, решение о допустимом действии во время инцидента и проверку, что эксперимент ограничен по охвату и имеет условие остановки. Функции работают только с переданными значениями. Они не обращаются к базе, сети или реальным сервисам.

## Что такое fault injection

Fault injection — намеренное внесение сбоя, чтобы проверить, как система ведёт себя в ситуации, которую иначе трудно воспроизвести. Сбоем может быть падение процесса, ошибка соединения с базой, задержка ответа или потеря сообщения. Цель не в том, чтобы сломать систему ради интереса. Цель — убедиться, что повтор, откат, сверка и оповещение работают так, как записано в документации.

Эксперимент допустим только тогда, когда выполнены три условия. Известно, что именно ломается. Ограничена область: сбой касается одного тестового экземпляра или одного маршрута. Заранее записано условие остановки: число ошибок, время или порог метрики, после которого эксперимент прекращается без обсуждения. Без последнего пункта тест превращается в проверку того, насколько долго команда готова терпеть последствия.

## Область и условие остановки

Область эксперимента задаётся явно. Тестовая база, отдельная очередь или одна реплика сервиса — хорошие границы. Общий production-кластер и реальные данные клиентов — нет. Если область нельзя ограничить, эксперимент не начинается, даже если сам сбой выглядит безобидным.

Условие остановки должно измеряться. Фраза «остановить, если станет плохо» не работает, потому что в ней нет момента, в который принимается решение. Фраза «остановить после трёх ошибок записи или через десять минут» работает: как только условие выполнено, решение уже принято заранее, и спорить не о чем.

Пример 1 показывает, как функция сопоставляет стадию сбоя с действием восстановления. Она возвращает строку, а не выполняет откат, поэтому её легко проверить.

```go
package main

import "fmt"

func FaultStage(stage string) string {
	switch stage {
	case "before_commit":
		return "rollback"
	case "after_commit":
		return "reconcile"
	case "publish":
		return "republish_idempotently"
	default:
		return "unknown"
	}
}

func main() {
	fmt.Printf("%q\n", FaultStage("before_commit"))
	fmt.Printf("%q\n", FaultStage("publish"))
	fmt.Printf("%q\n", FaultStage(""))
}
```

Вывод: `"rollback"`, `"republish_idempotently"`, `"unknown"`. Пустая стадия попадает в `unknown`, а не в действие по умолчанию: неизвестный сбой не должен молча получать лечение, которое никто не проверял.

Пример 2 показывает условие остановки в виде функции. Счётчик ошибок и прошедшее время сравниваются с порогами, которые записаны до запуска.

```go
package main

import "fmt"

func shouldStop(failedWrites, elapsedMinutes int) bool {
	return failedWrites >= 3 || elapsedMinutes >= 10
}

func main() {
	fmt.Println(shouldStop(2, 5))
	fmt.Println(shouldStop(3, 5))
	fmt.Println(shouldStop(0, 10))
}
```

Вывод: `false`, `true`, `true`. Порог задан числом, поэтому два человека получат один и тот же ответ, не сверяясь друг с другом.

## Действие во время инцидента

Во время реального инцидента порядок решений важен. Сначала выясняют, продолжается ли сбой. Если да, главная задача — смягчить последствия, а не искать причину. Когда сбой закончился, но мера не применена, назначают действие по исправлению. Если мера уже готова, остаётся проверить, что она работает на реальном трафике.

Отрицательное число затронутых заказов означает ошибку входных данных. В этом случае решение не принимается вообще: сначала исправляют данные инцидента. Поэтому проверка входа стоит первой, раньше любой ветки о действии.

## Постмортем без поиска виноватых

Postmortem — письменный разбор инцидента после того, как сервис восстановлен. Blameless-формат ищет причины в процессах, инструментах и системе, а не в человеке, который нажал кнопку. Это не отменяет ответственности за решения, но делает факты доступными: люди рассказывают, что видели, только если не боятся наказания за свой рассказ.

Разбор разделяет три вещи. Наблюдаемый факт — «за четыре минуты 37 запросов получили ответ 503». Гипотеза — «вероятно, пул соединений был исчерпан». Действие — «добавить метрику занятых соединений и проверить её алертом на тестовом стенде». Гипотеза не превращается в факт, пока её не проверили. Действие без владельца, срока и критерия закрытия остаётся пожеланием.

## План эксперимента до запуска

Письменный план занимает полстраницы и экономит часы. В нём пять пунктов: что ломается, где это происходит, кто наблюдает, какой признак означает остановку и как проверяется восстановление. Если хотя бы один пункт пуст, запуск откладывается.

Наблюдатель назначается заранее и имеет право остановить эксперимент сам, не спрашивая никого. Так решение не зависит от того, насколько уверенно звучит тот, кто хочет продолжить. Кнопка остановки или команда отката проверяются до начала, а не в момент, когда они понадобились.

## Что доказывает симуляция

Симуляция доказывает только то, что симуляция делает. Если тест заменяет брокер ответом «ok», он проверяет логику обработки этого ответа, а не то, что брокер восстанавливает доставку. Поэтому в разборе обязательно пишут, какая часть реальности не была затронута. Задание Hard этой главы проверяет только три логических условия эксперимента. Этого достаточно для warm-up проверки, но недостаточно для вывода о безопасности системы.

Восстановление проверяют реальным отказом в тестовом стенде: измеряют время до восстановления и сверяют данные после него. Для этого заранее выбирают метрику времени, например секунды от первого сбоя до первого успешного ответа, и записывают её в план. Если сверка не сходится, восстановление не засчитывается, сколько бы зелёных тестов ни прошло.

## Типичные ошибки и исправление

> **Типичная ошибка.** Запускать эксперимент без условия остановки, потому что «всё под контролем». Контроль заканчивается в тот момент, когда метрика уходит дальше ожидаемого, а решение о прекращении нигде не записано.

Ошибки повторяются от проекта к проекту. Сбой запускают в общем окружении, потому что стенд занят. Условие остановки описано словами, а не числом. В разборе факты смешаны с догадками, и потом по ним принимают решения. Action item записан без способа проверки, поэтому его никто не закрывает. Полезная привычка — перечитать разбор через неделю и спросить, изменилось ли поведение системы, а не только текст документа.

## Если что-то пошло не так

- Сбой затронул пользователей, которых не было в плане → эксперимент вышел за область; останови его по условию и уменьши охват.
- Эксперимент продолжился, хотя метрика превысила порог → условие остановки не автоматизировано; добавь таймер или счётчик в сам стенд.
- В разборе появилась уверенная причина без данных → перенеси её в список гипотез и назначь проверку.
- Action item закрыт словами «сделано» → проверь критерий из карточки действия, а не память участников.

## Практика

Эти задания проверяют только логику функций. Они не запускают сбой, не обращаются к базе и не измеряют восстановление. Закрытые примеры видны только в «Проверить».

### Задание 1 · Easy: fault injection и postmortem — базовое правило

**Цель.** Реализуй `FaultStage(stage string) string`. Стадия `before_commit` даёт `"rollback"`, `after_commit` даёт `"reconcile"`, `publish` даёт `"republish_idempotently"`. Любое другое значение, включая пустую строку, даёт `"unknown"`.

**Ожидаемый вывод** — вход `publish`:

```text
"republish_idempotently"
```

**Шаги.**
1. Выбери задание «Easy: fault injection и postmortem — базовое правило»: в файле есть `FaultStage` с `panic("TODO")`. Импорты не нужны.
2. Опиши ветки `switch` для трёх известных стадий.
3. Верни `"unknown"` для всех остальных значений через ветку по умолчанию.
4. Нажми «Запустить» и сравни вывод с блоком выше.
5. Нажми «Проверить».

**Как проверить себя.** Вывод — одна строка в кавычках; все три критерия зелёные, включая пустую стадию.

**Если не принято.**
- `"unknown"` вместо `"rollback"` для `before_commit` → ветка написана с ошибкой в строке стадии.
- Пустая строка даёт пустой ответ → ветка по умолчанию не записана.
- Ответ отличается по регистру → сверь написание с контрактом.

> **Подсказка.** Все значения контракта записаны строками, поэтому сравнение идёт точно, без приведения к нижнему регистру.

### Задание 2 · Medium: fault injection и postmortem — граничная политика

**Цель.** Реализуй `IncidentAction(ongoing bool, impact int, mitigationReady bool) string`. Отрицательный `impact` даёт `"invalid"` раньше всех остальных проверок. Активный инцидент даёт `"mitigate"`. Завершённый инцидент без готовой меры даёт `"assign_action"`. Во всех остальных случаях верни `"verify"`.

**Ожидаемый вывод** — вход: инцидент активен, затронуто 2, мера не готова:

```text
"mitigate"
```

**Шаги.**
1. Выбери задание «Medium: fault injection и postmortem — граничная политика»: в файле есть `IncidentAction` с `panic("TODO")`.
2. Проверь `impact < 0` первой и верни `"invalid"`.
3. Проверь `ongoing` и верни `"mitigate"`.
4. Проверь `mitigationReady` и верни `"assign_action"`, если меры нет.
5. Иначе верни `"verify"`.
6. Нажми «Запустить» и сравни вывод с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Вывод — одна строка в кавычках; шесть проверочных случаев совпадают с контрактом, включая нулевой `impact` с готовой мерой.

**Если не принято.**
- `"mitigate"` при отрицательном `impact` → проверка входа стоит после ветки активного инцидента.
- `"assign_action"` для завершённого инцидента с готовой мерой → условие по `mitigationReady` инвертировано.
- `"verify"` для активного инцидента → порядок веток перепутан.

> **Подсказка.** Порядок веток: вход, активность, мера, остальное.

### Задание 3 · Hard: fault injection и postmortem — helper-проверка (не доказательство безопасности)

**Цель.** Реализуй `SafeExperiment(hasStopCondition, boundedScope, usesProductionData bool) bool`. Результат `true` только тогда, когда есть условие остановки, охват ограничен и production-данные не используются. Во всех остальных случаях верни `false`.

**Ожидаемый вывод** — вход: условие остановки есть, охват ограничен, production-данных нет:

```text
true
```

**Шаги.**
1. Выбери задание «Hard: fault injection и postmortem — helper-проверка (не доказательство безопасности)»: в файле есть `SafeExperiment` с `panic("TODO")`.
2. Верни `false`, если нет условия остановки.
3. Верни `false`, если охват не ограничен.
4. Верни `false`, если используются production-данные.
5. Иначе верни `true`.
6. Нажми «Запустить» и сравни вывод с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Вывод — `true` или `false` без кавычек; пять проверочных случаев совпадают с контрактом.

**Если не принято.**
- `true` при использовании production-данных → условие по `usesProductionData` не записано.
- `true` без условия остановки → проверка `hasStopCondition` пропущена.
- Функция читает что-то из сети или файлов → задача требует только логики по трём флагам.

> **Подсказка.** Все три условия важны, поэтому их удобно выразить одним выражением с `&&`.

## Воспроизводимая лабораторная: отказ worker на тестовой БД

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Настоящая база и сеть не нужны: лаборатория моделирует тестовую БД в памяти процесса.

Программа ниже обрабатывает шесть заданий. Начиная с третьего задания, имитация отказа возвращает ошибку записи. Условие остановки записано в коде: после двух ошибок worker прекращает работу. Запусти программу во временном каталоге и сравни вывод с ожидаемым.

```go
package main

import "fmt"

type fakeDB struct {
	rows     map[int]string
	failFrom int
	attempts int
}

func (db *fakeDB) save(id int, value string) error {
	db.attempts++
	if id >= db.failFrom {
		return fmt.Errorf("injected fault on %d", id)
	}
	db.rows[id] = value
	return nil
}

func main() {
	db := &fakeDB{rows: map[int]string{}, failFrom: 3}
	errs := 0
	for id := 1; id <= 6; id++ {
		if err := db.save(id, fmt.Sprintf("job-%d", id)); err != nil {
			errs++
			fmt.Println("error:", err)
			if errs == 2 {
				fmt.Println("stop after", errs, "errors")
				break
			}
			continue
		}
		fmt.Println("saved", id)
	}
	fmt.Println("rows", len(db.rows), "attempts", db.attempts)
}
```

**Ожидайте:** строки `saved 1` и `saved 2`, затем `error: injected fault on 3`, `error: injected fault on 4`, `stop after 2 errors` и итог `rows 2 attempts 4`. Задания 5 и 6 не выполняются, потому что условие остановки сработало раньше.

**Очистка:** программа ничего не создаёт на диске и работает только в памяти процесса. Если запускал её во временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Проверь себя

- Что нужно определить до запуска fault injection?
- Почему симуляция статуса не доказывает восстановление брокера?
- Как blameless postmortem удерживает точность записей?
- Каким должен быть action item, чтобы его можно было закрыть?
- Почему условие остановки задаётся числом или таймером?
- Что делать, если эксперимент затронул больше области, чем разрешено?

## Итог

- Fault injection допустим только в ограниченной области с измеримым условием остановки, заданным до запуска.
- Разбор инцидента разделяет факты, гипотезы и действия; действие закрывается по проверяемому критерию, а не по словам.
- Симуляция проверяет логику, но восстановление зависимости доказывается только реальным отказом в стенде и сверкой данных.
