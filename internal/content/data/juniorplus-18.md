## Повторяемая локальная среда

Docker image (образ) содержит программу и её среду; container (контейнер) — запущенный процесс. Compose описывает набор связанных сервисов как одно приложение. Для LinkHub это API и PostgreSQL. Между контейнерами есть внутренняя сеть Compose, а имя сервиса `db` становится DNS hostname. `localhost` внутри контейнера приложения означает этот же контейнер, а не соседнюю DB. На host компьютере браузер, напротив, использует опубликованный loopback порт.

Образ с тегом `postgres:18.6-bookworm` сообщает версию, а digest `sha256` закрепляет конкретное содержимое. P2 уже указывает конкретный digest PostgreSQL 18.6. Тег `latest` меняется и нарушает воспроизводимость. Go version и pgx dependency закреплены отдельно в go.mod/go.sum. Не редактируйте pin при обычной отладке; deliberate upgrade требует тестов совместимости и обновлённого evidence.

Compose полезен для разработки, потому что упрощает старт приложения с базой и сохранение состояния. Но этот local stack не становится от этого production deployment. За пределами курса остаются защита hosts, backups, key rotation, доступы, мониторинг, upgrades и распределённая устойчивость. Не публикуйте учебный API в открытую сеть и не переносите этот Compose без отдельного threat model.

## Порт на host и порт внутри контейнера

Внутренний API слушает `0.0.0.0:8097`, чтобы быть достижимым от соседей в container network. Compose map задаёт внешний bind только `127.0.0.1:8097:8097`; PostgreSQL так же доступен с host через `127.0.0.1:55432`. Эти две стороны не противоречат друг другу: адрес listener нужен внутри контейнера, а первая часть port mapping ограничивает host interface. Подстановка `0.0.0.0:8097:8097` открыла бы порт на все интерфейсы машины.

`ports` публикует сетевой endpoint; объявленный container port сам по себе не обязан быть доступен вне Compose сети. App container обращается к `db:5432`, потому что service DNS работает внутри проекта. Клиент на host обращается к loopback адресам и опубликованным port. Смешение этих namespace — частая причина connection refused. Не решайте её заменой `db` на localhost в app DSN.

## Volume и жизненный цикл данных

Named volume хранит состояние вне container filesystem. Удаление и повторное создание DB container не теряет данные, когда volume остаётся. Так persistence участвует в локальной разработке. Обычный stop не очищает его; флаг `down -v` удаляет данные. Команда общего `volume prune` может затронуть совершенно другой проект и пользовательские данные.

Прежде чем reset, установите точное имя project volume и убедитесь, что данные можно потерять. Работайте на отдельном учебном проекте, а не на машине с общей базой. Если проверка нужна с нуля, сначала примените migrations к disposable среде и зафиксируйте результат; затем адресно удалите созданное состояние. В Academy P2 worker база disposable на один job, но локальный Compose сохраняет её между запусками. Это два разных режима.

В P2 Compose закреплён PostgreSQL image `postgres:18.6-bookworm@sha256:9551dd5bf356409a21b31248f49b33bba9bb1877365f3a7e933aecd9af3cf52d`. В reference сборке используется Go 1.27.2 и pgx/v5 5.11.0; версия приложения зафиксирована go.mod. В P2 compose файл закрепляет volume как `linkhub-data`. Host ports связаны только с loopback. Сервисы имеют ограничения capabilities и read-only filesystem. Утилитарное послабление для developer среды не следует переносить в cloud. Знание границ запуска важнее количества опций, которые можно скопировать.

## Порядок запуска и readiness

Healthcheck у db запускает `pg_isready` с user и database из окружения. `depends_on: condition: service_healthy` заставляет Compose ждать успешной проверки перед запуском API. Простой depends_on обычно контролирует порядок старта, а не подтверждает готовность сервера. Даже `pg_isready` не доказывает что миграция прошла и API может обработать пользовательский запрос.

P2 reference дополнительно вызывает migration при startup и начинает HTTP server после открытия DB. Успешная readiness — последовательность наблюдений: база отвечает; миграция завершилась; API поднялся; нужный endpoint отвечает. Эти сигналы имеют разный смысл. Несколько секунд `sleep` не является готовностью: машина под нагрузкой может стартовать дольше, а неверный пароль не исправится ожиданием.

Когда приложение закрывается из-за раннего старта, посмотрите status и безопасную часть журналов. Не печатайте полный DSN. Исправьте именно зависимость или migration race и добавьте воспроизводимую проверку. Не создавайте бесконечный retry, скрывающий ошибочный конфиг. Понятный отказ при неправильной настройке позволяет человеку быстро понять причину.

Они не читают Compose YAML, не запускают контейнер и не проверяют сохранность реального volume. ## Пошаговая диагностика и повторение

Проверьте наличие Docker Compose v2 и локального `.env`; удостоверьтесь, что placeholder заменён без печати значения; сверьте закреплённый image; посмотрите, стал ли db healthy; затем проверяйте migration и HTTP health. Сравните адреса: `db:5432` только для app container, `127.0.0.1:55432` для host psql и `127.0.0.1:8097` для browser. Порт публикации должен остаться loopback.

Запустите два цикла: создание schema на пустом disposable volume, затем остановка без его удаления и повторное включение. Проверьте, что записи сохранились и migration не создала дубли. В конце если очистка нужна, адресуйте имя только этого project volume и проверьте из документации, что он содержит учебные данные. При сомнении не удаляйте.

Compose manifest P2 закрепляет image postgres:18.6-bookworm@sha256:9551dd5bf356409a21b31248f49b33bba9bb1877365f3a7e933aecd9af3cf52d. Точную ссылку копируйте из проекта, не пересказывайте сокращённым sha в собственной конфигурации. При обновлении образа зафиксируйте новый digest и снова примените миграции и тесты. Здесь мы не создаём публичный ingress, managed database или платную инфраструктуру: задача — понять безопасный локальный startup.

Составьте маленькую схему browser → host loopback → app → db service DNS → volume. Отдельно пометьте healthcheck DB и проверку API. Если DB healthy, но migration failed, причина находится после проверки readiness, а не в host networking. Не добавляйте публичный ingress или платную инфраструктуру: задача главы — безопасный локальный проект.


При смене компьютера или Docker runtime сначала проверьте доступность уже закреплённого image. Не обновляйте зависимость автоматически до latest ради быстрого старта. Обновление Go, PostgreSQL image и pgx — три связанные, но отдельные изменения; каждому нужны воспроизводимые tests и обновлённая инструкция. Compose в этом уроке служит безопасной local developer средой, а не конфигурацией для публичной эксплуатации.

## Три законченных запускаемых Go-примера

### Loopback

```go group=loopback mode=run
package main

import ("fmt";"net")

func loopback(host string) bool { ip:=net.ParseIP(host);return ip!=nil&&ip.IsLoopback() }
func main(){fmt.Println(loopback("127.0.0.1"),loopback("0.0.0.0"))}
```

Это полная программа со стандартным импортом, package main и main. Она использует только фиксированные локальные значения: не читает секреты окружения, не соединяется с сетью и не утверждает, что проверила сервис. Запустите пример и измените ровно одну входную величину.

### Service Dns

```go group=service-dns mode=run
package main

import "fmt"

type Service struct{Name string;Port int}
func main(){db:=Service{Name:"db",Port:5432};api:=Service{Name:"api",Port:8097};fmt.Printf("container uses %s:%d; browser uses 127.0.0.1:%d\n",db.Name,db.Port,api.Port)}
```

Это полная программа со стандартным импортом, package main и main. Она использует только фиксированные локальные значения: не читает секреты окружения, не соединяется с сетью и не утверждает, что проверила сервис. Запустите пример и измените ровно одну входную величину.

### Startup

```go group=startup mode=run
package main

import "fmt"

func state(db,schema,api bool) string {if !db{return "wait_database"};if !schema{return "migration_failed"};if !api{return "api_unhealthy"};return "ready"}
func main(){fmt.Println(state(false,false,false),state(true,false,false),state(true,true,true))}
```

Это полная программа со стандартным импортом, package main и main. Она использует только фиксированные локальные значения: не читает секреты окружения, не соединяется с сетью и не утверждает, что проверила сервис. Запустите пример и измените ровно одну входную величину.

## E / M / H: практика функции

- **Easy: Оставь host bind на loopback.** Разреши ровно hostname localhost или loopback IP. Отклони 0.0.0.0 и обычные интерфейсы. Helper классифицирует host и не читает весь Compose manifest.
- **Medium: Ограничь cleanup именованным disposable volume.** Верни true только при явно disposable проекте и выборе ровно его volume. В остальных случаях false. Это policy helper, не запускающий Docker. Не вызывай общий volume prune для очистки учебных данных.
- **Hard: Разбери последовательность старта.** DB unhealthy → wait_database; иначе миграция не завершилась → migration_failed; затем unhealthy API → api_unhealthy; ready только при всех true. Функция классифицирует signals, но не проверяет Compose, migration или endpoint.

Function grader компилирует доверенный код и сравнивает JSON для public/hidden cases. Он запускает только helper и не исполняет PostgreSQL, Compose, HTTP API или review rubric. Названия ready, allow и reviewed_evidence принадлежат малой таблице решений этой функции; не выдавайте их за полный security pass.

## Типичные ошибки и диагностика

- App подключается к localhost из другого контейнера. Внутренний адрес — DNS имя Compose service.
- API host bind открыт на все интерфейсы. Для курса оставьте 127.0.0.1.
- Считают depends_on достаточным health signal. Нужен condition service_healthy и отдельная schema/API проверка.
- Volume удаляют командой общего prune. Определите точный disposable project volume.
- Floating image tag заменяет digest и окружение перестаёт повторяться. Сверьте конкретный P2 pin.

## Повторение и глоссарий

Проследите полный путь проекта от публичного HTTP ответа назад к handler, context, repository, transaction и configuration. Для каждого участка назовите файл, команду или test, который даёт evidence. Отдельно назовите неизвестное, требующее человека, и boundary, которая не проверялась. Не расширяйте claim за пределы наблюдаемого результата.

- **image (образ)** — Шаблон контейнерной среды и запуска.
- **container (контейнер)** — Изолированный процесс, запущенный из образа.
- **volume (том)** — Отдельное хранилище состояния контейнера.
- **Compose (Compose)** — Описание связанных локальных сервисов и их окружения.
- **readiness_probe (проверка готовности)** — Проверка того, что сервис готов принять зависимый запрос.
- **loopback (петлевой адрес)** — Сетевой интерфейс, доступный текущей машине.

Оценка главы означает только самостоятельное evidence по критериям курса. Automatic tests, human review и внешнее профессиональное подтверждение являются отдельными процессами.
