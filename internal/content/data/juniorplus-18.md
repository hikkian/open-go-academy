# Docker Compose для разработки

## Что ты сделаешь

Ты напишешь три проверки, которые относятся к локальному запуску P2 в Compose: `IsLoopbackBind` разрешит публикацию порта только на loopback, `MayRemoveVolume` решит, можно ли удалить том, `ComposeStartupState` выберет причину, по которой старт ещё не готов. Функции получают уже известные значения: они не читают `compose.yaml`, не вызывают Docker и не обращаются к сети.

## Повторяемая локальная среда

Образ (image) содержит программу и её окружение, а контейнер (container) — запущенный процесс. Compose описывает набор связанных сервисов как одно приложение. Для LinkHub это API и PostgreSQL. Между контейнерами есть внутренняя сеть Compose, и имя сервиса `db` становится DNS-именем.

`localhost` внутри контейнера приложения означает сам этот контейнер, а не соседнюю базу. Браузер на host-компьютере, напротив, обращается к опубликованному порту на loopback.

Образ с тегом `postgres:18.6-bookworm` сообщает версию, а digest `sha256` закрепляет конкретное содержимое. Тег можно переназначить, поэтому воспроизводимость держится на digest. P2 уже указывает digest PostgreSQL 18.6. Не меняй pin при обычной отладке: обновление требует тестов совместимости и нового evidence.

## Порт на host и порт внутри контейнера

Внутренний API слушает `0.0.0.0:8097`, чтобы быть достижимым от соседних контейнеров. Публикация на host задаёт `127.0.0.1:8097:8097`, а PostgreSQL доступна с host через `127.0.0.1:55432`. Адрес listener и адрес публикации — разные вещи: первая часть port mapping ограничивает интерфейс host.

Пример проверки, что публикация идёт только на loopback:

```go
package main

import (
    "fmt"
    "strings"
)

func main() {
    ports := []string{"127.0.0.1:55432:5432", "0.0.0.0:8097:8097"}
    for _, p := range ports {
        fmt.Println(strings.HasPrefix(p, "127.0.0.1:"))
    }
}
```

Вывод: `true` и `false` на отдельных строках. Запись `0.0.0.0:8097:8097` открыла бы порт на все интерфейсы машины.

> **Типичная ошибка.** Написать `8097:8097` без адреса. Docker опубликует порт на все интерфейсы, и учебный API окажется доступен из локальной сети.

## Volume и жизненный цикл данных

Данные PostgreSQL лежат в именованном томе `linkhub-data`. Он переживает остановку контейнера, но не переживает удаление тома. Очистка учебной среды должна удалять только собственный disposable volume проекта.

Общий `docker volume prune` удаляет неиспользуемые тома без разбора. Он может стереть чужие данные, поэтому в инструкциях курса его не используют. Перед удалением проверь, что проект явно помечен как disposable и выбран ровно его том.

## Порядок запуска и readiness

В P2 `api` ждёт базу через `depends_on` с условием `service_healthy`. Healthcheck базы вызывает `pg_isready`. Это проверяет только готовность PostgreSQL принимать соединения. Миграции и HTTP API проверяются отдельно: зелёный healthcheck базы не гарантирует, что схема применена и API отвечает.

Порядок проверок при диагностике одинаков: база, миграции, API. Пример того, как шаги следуют друг за другом:

```go
package main

import "fmt"

func main() {
    steps := []string{"db healthy", "migrations applied", "api healthy"}
    for i, s := range steps {
        fmt.Println(i+1, s)
    }
}
```

Вывод: три строки с номерами `1 db healthy`, `2 migrations applied`, `3 api healthy`. Номер показывает, что второй шаг не начнётся, пока не готов первый.

> **Важно.** Этот локальный стек не становится production deployment. Защита host, backups, управление ключами, мониторинг и распределённая устойчивость остаются за пределами курса.

## Если что-то пошло не так

- API не отвечает на host → проверь публикацию `127.0.0.1:8097:8097` и то, что контейнер действительно запущен.
- Данные исчезли после очистки → удалён том проекта; общий prune или чужой volume не нужны для учебной среды.
- `connection refused` при обращении к `localhost:5432` из контейнера API → `localhost` указывает на сам контейнер; адрес базы — `db:5432`.
- Старт падает без подробностей → проверь, что `.env` создан из `.env.example`, а пароль задан локально.

## Практика

Три задания. Функции проверяются на входах из блока «Ожидаемый вывод»; закрытые примеры видны только в «Проверить». Docker, Compose и сеть не используются.

### Задание 1 · Оставь host bind на loopback

**Цель.** Вернуть `true` для `localhost` и loopback IP, например `127.0.0.1` или `::1`. Для `0.0.0.0`, обычных интерфейсов и других адресов вернуть `false`.

**Ожидаемый вывод** — входы: `127.0.0.1`, затем `0.0.0.0`:

```text
true
false
```

**Шаги.**
1. Выбери задание «Оставь host bind на loopback»: в файле есть `IsLoopbackBind` с `panic("TODO")`. Добавь импорты, которые используешь: `"net"` и, при необходимости, `"strings"`.
2. Сравни `host` с именем `localhost` точно.
3. Разбери `host` как IP-адрес и проверь, что адрес loopback.
4. Верни `true`, если выполнено одно из условий; иначе `false`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** `true` и `false`; все три критерия зелёные.

**Если не принято.**
- `0.0.0.0` принят → этот адрес слушает все интерфейсы и не является loopback.
- `192.168.1.10` принят → обычный адрес сети не разрешён.
- `::1` отклонён → IPv6 loopback тоже разрешён.

> **Подсказка.** Сначала `localhost`, потом разбор IP и проверка loopback.

**Если не принято.**

> **Подсказка.** Оба условия обязательны, поэтому достаточно одной проверки на каждое.

### Задание 3 · Разбери последовательность старта

**Цель.** Вернуть `"wait_database"`, если база нездорова. Иначе `"migration_failed"`, если миграции не применены. Иначе `"api_unhealthy"`, если API не отвечает. Только при всех трёх `true` — `"ready"`.

**Ожидаемый вывод** — входы: база нездорова, затем база здорова и миграции не применены, затем миграции применены и API не отвечает, затем всё в порядке:

```text

"migration_failed"
"api_unhealthy"
"ready"
```

**Шаги.**
1. Выбери задание «Разбери последовательность старта»: в файле есть `ComposeStartupState` с `panic("TODO")`. Импорты не нужны.
2. Если `dbHealthy` равно `false`, верни `"wait_database"`.
3. Если `migrationsApplied` равно `false`, верни `"migration_failed"`.
4. Если `apiHealthy` равно `false`, верни `"api_unhealthy"`.
5. Иначе верни `"ready"`.
6. Нажми «Запустить» и сравни с блоком выше.
7. Нажми «Проверить».

**Как проверить себя.** Четыре строки в кавычках; все три критерия зелёные.

**Если не принято.**
- База нездорова, миграции применены, API здоров, даёт `"ready"` → состояние базы проверяется первым.
- Миграции не применены при здоровой базе даёт `"api_unhealthy"` → миграции проверяются раньше API.

> **Подсказка.** Порядок такой же, как порядок шагов старта: база, миграции, API.

## Итог

- Compose описывает сервисы API и PostgreSQL; имя `db` доступно внутри сети, а `localhost` — только сам контейнер.
- Публикация портов ограничивается loopback, а очистка данных — собственным disposable volume.
- Healthcheck базы подтверждает только готовность PostgreSQL; миграции и API проверяются отдельно.
- Оценка главы — это только самостоятельное evidence по критериям курса; автоматические тесты, human review и внешнее подтверждение — отдельные процессы.
