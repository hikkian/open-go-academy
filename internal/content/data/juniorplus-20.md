# Защита P2 и Junior+ assessment

## Что ты сделаешь

Ты напишешь три функции, которые разбирают результат защиты P2: `FailureCategory` сгруппирует сбой по категории, `EvidenceStage` определит стадию пакета evidence, `AssessmentDisposition` выберет решение по проверкам и ручному review. Каждая функция описывает правило: она не запускает тесты, не читает отчёты и не выдаёт никакой статус сверх того, что передано аргументами.

## Цель — показать evidence, а не громкий титул

Защита проекта отвечает на один вопрос: что проверено, как воспроизведено и что осталось неизвестным. Итог курса — это самостоятельное evidence по критериям, а не ранг, публичный credential или профессиональная квалификация. Слова «готов к работе» или «сертифицирован» в пакете не используются, если для них нет отдельного процесса.

Чистая установка нужна, чтобы повторить результат без старого состояния машины: тот же commit, те же команды, свежая база, без забытых переменных окружения. Если проверка работает только на одном компьютере с особыми настройками, это тоже нужно написать в отчёте.

## Seeded failure — сначала наблюдение, потом исправление

В курсе есть намеренно внесённое расхождение между HTTP-контрактом и поведением SQL. Порядок работы такой: сначала воспроизведи расхождение, зафиксируй наблюдаемый ответ и результат запроса, затем добавь regression test, который падает на текущем коде, и только после этого исправляй.

Пример того, как расхождение видно из сравнения ожидания и факта:

```go
package main

import "fmt"

func main() {
    spec := map[string]int{"create": 201}
    actual := 200
    if spec["create"] != actual {
        fmt.Println("mismatch: spec", spec["create"], "actual", actual)
    }
}
```

Вывод: `mismatch: spec 201 actual 200`. Такая строка уже даёт факт для отчёта: что ожидал контракт и что вернул сервер.

> **Важно.** Regression test, написанный после исправления, не докажет, что исходная ошибка была воспроизведена. Сначала падение, потом исправление.

## Threat review по явным границам

Threat model P2 лежит в `content/projects/p2/threat-model.md`. Он перечисляет активы, участников, меры защиты и явные ограничения курса. Review проходит по этим границам: что защищено, что вынесено за пределы учебного проекта и что требует отдельного решения.

Ограничения так же важны, как меры. Учебный стек не содержит backups, управления ключами, мониторинга и защиты публичного периметра. Если отчёт молчит о них, он создаёт ложное впечатление полноты.

## Security acceptance и работа команды

Security gate — отдельная стадия. Непройденный gate блокирует решение независимо от того, насколько хорошо написан отчёт. Причина простая: уязвимость не компенсируется аккуратной документацией.

Работа команды видна по следам: кто проводил review, какие замечания закрыты, какие остались открытыми и почему. Записывай решения и их основание. Фраза «проверено вручную» без имени проверки, даты и результата не является evidence.

## Короткая защита проекта

Защита занимает несколько минут и строится вокруг фактов: что сделано, как проверено, что не проверено. Для каждого утверждения назови файл, команду или тест. Если ответа нет, скажи, что это неизвестно, и назови способ проверить.

Вопрос «почему так?» часто важнее демонстрации. Ответ должен опираться на контракт, threat model или результат теста, а не на общее впечатление.

## Итоговый evidence пакет

Пакет собирают из нескольких частей: clean setup с командами и результатом, список автоматических проверок, regression test для seeded failure, threat review с открытыми пунктами и записка о ручном review. Пакет не должен содержать секреты, реальные пароли и выводы без источника.

> **Типичная ошибка.** Смешать автоматический pass и ручное решение в одну строку «проект принят». Это разные стадии, и они записываются отдельно.

### Задание 1 · Сгруппируй failure без заявления о pass

**Цель.** Сопоставить точные ключи проверок с категориями: `http_contract` — `"http"`, `auth_session` — `"authentication"`, `owner_scope` — `"ownership"`, `postgres_integrity` — `"database"`, `redirect_boundary` — `"redirect"`. Любой другой ключ — `"unknown"`.

**Ожидаемый вывод** — входы: `http_contract`, затем `owner_scope`:

```text
"http"
"ownership"
```

**Шаги.**
1. Выбери задание «Сгруппируй failure без заявления о pass»: в файле есть `FailureCategory` с `panic("TODO")`. Импорты не нужны.
2. Сравни `check` с каждым из пяти ключей точно, с учётом регистра.
3. Для совпавшего ключа верни его категорию.
4. Иначе верни `"unknown"`.
5. Нажми «Запустить» и сравни с блоком выше.
6. Нажми «Проверить».

**Как проверить себя.** Две строки в кавычках; все три критерия зелёные.

**Если не принято.**
- `made_up` даёт категорию `"database"` → неизвестный ключ не сопоставляется ни с чем.
- `HTTP_CONTRACT` даёт `"http"` → ключи сравниваются точно.

> **Подсказка.** Один `switch` с пятью ветками и веткой `default`.

## Проверь себя

- Что доказывает зелёный automated acceptance, а что нет?
- Зачем сначала наблюдать seeded failure, а потом исправлять?
- Почему security gate стоит раньше ручного review?
- Что означает `reviewed_evidence`?
- Что должно оставаться ручным после автоматических проверок?
- Как безопасно повторить проверку?

> **Важно.** Оценка главы — это только самостоятельное evidence по критериям курса; автоматические тесты, human review и внешнее подтверждение — отдельные процессы.

- Защита P2 показывает evidence: что проверено, как воспроизведено и что осталось неизвестным.
- Security gate и автоматические проверки записываются отдельно от ручного review.
- `reviewed_evidence` означает только просмотренный evidence курса; это не ранг, публичный credential или профессиональная квалификация.
