# Модели согласованности для чтения

## Что ты сделаешь

Ты научишься называть гарантию чтения точным словом — eventual, read-your-writes, monotonic reads, linearizability — и связывать её с продуктовым контрактом операции: что пользователь вправе увидеть после нажатия «сохранить», что допустимо в отчёте и что недопустимо в проверке прав. Три функции урока — `ReadPolicy`, `ReplicaSafeForRead`, `ConsistencySource` — это таблицы выбора источника чтения по учебным сигналам; распределённых гарантий они не доказывают.

## Четыре гарантии и что они обещают

Модель согласованности (consistency model) описывает, какие значения клиент вправе наблюдать при чтении. Eventual consistency обещает, что копии сойдутся, когда прекратятся изменения и доставка завершится, — но не говорит когда. Read-your-writes: клиент видит собственную завершённую запись в последующих чтениях. Monotonic reads: один клиент не «перепрыгивает назад» к более старому состоянию, чем уже видел. Linearizability сильнее всех: каждая операция выглядит атомарной в единой последовательности, согласованной с реальным временем. Слово «репликация» само по себе не даёт ни одной из них.

```go group=models mode=run
package main

import "fmt"

type observation struct {
    client string
    saw    int
}

func monotonic(obs []observation) bool {
    last := map[string]int{}
    for _, o := range obs {
        if o.saw < last[o.client] {
            return false
        }
        last[o.client] = o.saw
    }
    return true
}

func main() {
    ok := []observation{{"A", 1}, {"A", 2}, {"B", 1}, {"A", 2}}
    bad := []observation{{"A", 2}, {"A", 1}}
    fmt.Println("монотонно:", monotonic(ok), monotonic(bad))
}
```

Вывод:

```text
монотонно: true false
```

Вторая последовательность нарушает monotonic reads: клиент A видел версию 2, потом версию 1 — так бывает, когда два чтения ушли на разные реплики с разным отставанием. Заметь, что гарантия локальна клиенту: B вправе видеть версию 1, пока A видит 2.

> **Важно.** Гарантии бывают сессионными и системными. Read-your-writes защищает одного клиента; она ничего не обещает другому пользователю, который смотрит тот же объект.

## Что обещает каждая операция

Один глобальный режим чтения игнорирует разницу в цене ошибки. Составь матрицу по пользовательским потокам: операция записи; последующее чтение; источник; допустимое устаревание; поведение при отставании; поведение при недоступности primary или реплики. Экран подтверждения заказа требует read-your-writes; отчёт за месяц допускает минуту отставания; проверка прав доступа требует актуальности, потому что устаревшее «разрешено» — дыра в безопасности.

```go group=policy mode=run
package main

import "fmt"

func source(wrote, needsLatest, replicaFresh bool) string {
    if wrote || needsLatest || !replicaFresh {
        return "primary"
    }
    return "replica"
}

func main() {
    fmt.Println("подтверждение заказа:", source(true, false, true))
    fmt.Println("проверка прав:", source(false, true, true))
    fmt.Println("отчёт, реплика свежа:", source(false, false, true))
    fmt.Println("отчёт, реплика отстаёт:", source(false, false, false))
}
```

Вывод:

```text
подтверждение заказа: primary
проверка прав: primary
отчёт, реплика свежа: replica
отчёт, реплика отстаёт: primary
```

Три сигнала — «была запись», «нужно самое свежее», «реплика свежа» — задаются операцией и мониторингом; функция лишь применяет приоритет: любой из первых двух или отрицание третьего ведёт на primary. В таблице должен быть и столбец «что при недоступности primary»: ошибка, деградация до устаревшего чтения или отказ операции — это продуктовый выбор, который нельзя делать молча в коде.

> **Типичная ошибка.** Назвать систему «согласованной», потому что чтения идут через один primary. Переключение на новую primary, не получившую ожидаемую запись, ломает гарантию, если план переключения её не учитывает.

## Чем платят за каждую гарантию

У гарантий разная цена. Eventual consistency почти бесплатна: чтения идут на любую копию, запись подтверждается одним узлом, зато приложение обязано переживать устаревшие ответы — и повторные обработки, если устаревшее состояние ведёт к повторному действию. Read-your-writes стоит нагрузки на primary или хранения позиции в сессии клиента: нужно где-то помнить, что этот клиент писал и какую позицию получил. Monotonic reads требуют либо привязки клиента к одной реплике, либо передачи последней увиденной позиции с каждым чтением. Linearizability дороже всех: каждая операция ждёт согласования, задержка растёт с расстоянием между узлами, а доступность при разделении сети падает.

Поэтому выбор модели — это выбор, за что платить: задержкой записи, нагрузкой на primary, сложностью клиента или допустимостью устаревания. Правильный ответ для сервиса — несколько моделей по операциям, записанных в матрице, а не одна «самая сильная» для всего.

## Когда гарантия тихо ломается

Три места, где заявленная модель расходится с реальностью. Переключение primary: клиент читал свою запись с primary, primary упал, новая не получила последнюю запись — read-your-writes нарушен, хотя код маршрутизации не менялся; план переключения должен либо дождаться применения журнала, либо честно вернуть ошибку на это окно. Повтор запроса: клиент повторил запись после тайм-аута, вторая попытка создала дубликат, и «свою запись» он теперь видит дважды — модель согласованности не заменяет идемпотентность. Кеш перед базой: даже при чтении с primary кеш вернёт старое значение, если его инвалидация отстала, — следующий урок про это.

Каждое из этих мест проверяется сценарием, а не чтением кода: запись, отказ, повтор, чтение — и список наблюдений, которые модель разрешает.

## Механизмы и их пределы

Привязка клиента к primary (sticky routing) даёт read-your-writes простейшим способом, но нагружает primary и не защищает от переключения. Токен или позиция журнала, передаваемые с запросом, работают барьером, только если путь чтения действительно дожидается этой позиции. Тайм-аут ожидания требует явного запасного пути: ошибка, переход на primary или ослабление свежести — любой из них должен быть записан, а не выбран скрыто.

```go group=safe mode=run
package main

import "fmt"

func replicaSafe(wrote, replicaFresh, staleTolerant bool) bool {
    return !wrote && replicaFresh && staleTolerant
}

func main() {
    fmt.Println(replicaSafe(false, true, true), replicaSafe(true, true, true), replicaSafe(false, false, false), replicaSafe(false, true, false))
}
```

Вывод:

```text
true false false false
```

Реплика безопасна только при трёх условиях сразу: нет обязательства read-your-writes, реплика свежа по сигналу, операция терпит устаревание. Последний случай показывает, что свежая реплика не спасает операцию, которой нужен последний результат по контракту: свежесть — наблюдение мониторинга с задержкой, а не гарантия.

## Согласованность и кеш, очередь, поиск

Копии данных живут не только в репликах базы. Кеш перед сервисом, очередь событий для другого сервиса, поисковый индекс, обновляемый асинхронно, — каждая копия имеет свою задержку и свою модель. Пользователь создал объект, увидел его на экране подтверждения (read-your-writes через primary), открыл поиск — и не нашёл: индекс обновится через минуту. Это не ошибка, если контракт поиска — eventual с названным окном, и ошибка, если интерфейс обещает «найдите только что созданное».

Поэтому матрица операций включает все источники, из которых операция читает, а не только базу. Для каждой копии — кто её владелец, как она узнаёт об изменении, какое окно устаревания допустимо и что показывает интерфейс в этом окне: «индексируется», старое значение или ничего. Сервис, который держит три копии с тремя разными окнами, честно описывает три модели вместо одной.

## Как проверять модель

Проверка согласованности — это сценарии с порядком во времени, а не статические значения. Запиши последовательность: клиент A пишет v2; A читает; B читает; реплика отстаёт; primary переключается. Для каждого шага укажи разрешённые и запрещённые наблюдения. Маленькая функция-политика проверяет таблицу выбора, но не доказывает распределённую гарантию: для этого нужны протокол, интеграционная среда, инъекция отказов и анализ восстановления.

Согласованность формулируется на языке пользователя: после «сохранено» видит ли он новый объект на другой странице? Если несколько сервисов читают копии, кто координирует версию? Что видит оператор поддержки? Контракт должен переживать повтор запроса, тайм-аут и retry, и в нём явно сказано, к чему относится гарантия: к сессии, арендатору или объекту.

> **Зачем.** Название модели в документе обещает ровно столько, сколько обеспечивает архитектура; лишнее обещание всплывёт в первом инциденте с переключением primary.

Последний тест матрицы — прочитать её глазами оператора поддержки: по каждой операции он должен понять, что пользователь мог увидеть в окне устаревания и считается ли это дефектом; если на какой-то строке ответа нет, модель для операции не выбрана, а только названа.

## Типичные ошибки

- Один режим чтения для всех операций: отчёт и проверка прав платят одинаково.
- «Репликация есть — значит, согласовано»: без названной модели обещания нет.
- Сессионная гарантия, выданная за системную.
- Тайм-аут ожидания позиции без записанного запасного пути.
- Флаг свежести как доказательство видимости конкретной записи.
- Проверка статическими значениями вместо сценариев с порядком событий.

## Самостоятельная лаборатория

Возьми три операции своего сервиса — запись с подтверждением, список, проверку доступа — и заполни матрицу из раздела «Что обещает каждая операция» для каждой. Затем напиши сценарий из пяти шагов с двумя клиентами и отстающей репликой и отметь, какие наблюдения допустимы по выбранной модели. Прогони сценарий через функцию `source` из примера и проверь, что её ответы согласуются с матрицей; расхождение — повод уточнить матрицу, а не функцию. Если есть стенд с репликой, воспроизведи шаг «реплика отстаёт» паузой применения журнала и зафиксируй, что увидел каждый клиент.

## Если что-то пошло не так

- `replica` после записи → условие учитывает только свежесть; `wrote` должен вести на primary.
- `replica` при `needsLatest = true` → третий сигнал не проверен.
- `true` в задании 2 при `staleTolerant = false` → все три условия обязательны, объединяй через `&&`.
- `primary` при всех благоприятных сигналах → отрицание `replicaFresh` перепутано.
- `import … is not allowed` → импорты запрещены: только логика над флагами.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Все входы — предпосылки учебной модели, не запросы к базе.

### Задание 1 · Easy: выбери источник чтения

**Цель.** После записи или при несвежей реплике → `primary`; иначе → `replica`.

**Ожидаемый вывод** — для `(wrote=true, replicaFresh=false)`:

```text
"primary"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func ReadPolicy(wrote, replicaFresh bool) string`. Импорты запрещены.
2. `wrote || !replicaFresh` → `"primary"`, иначе `"replica"`.
3. «Запустить», «Проверить» — закрытые примеры: `(false, true)` → `replica`, `(false, false)` → `primary`.

**Как проверить себя.** Из четырёх комбинаций только одна даёт `replica`; флаг свежести — утверждение мониторинга, не подтверждение базы.

**Если не принято.**
- `replica` для `(true, true)` → запись не учтена.
- `replica` для `(false, false)` → несвежая реплика разрешена по ошибке.

> **Подсказка.** Та же политика, что в уроке о репликации, — здесь она названа гарантией read-your-writes.

### Задание 2 · Medium: проверь условия чтения с replica

**Цель.** Вернуть `true`, только если нет предшествующей записи, реплика свежа и операция терпит устаревшие данные.

**Ожидаемый вывод** — для `(wrote=false, replicaFresh=true, staleTolerant=true)`:

```text
true
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ReplicaSafeForRead(wrote, replicaFresh, staleTolerant bool) bool`. Импорты запрещены.
2. Верни `!wrote && replicaFresh && staleTolerant`.
3. «Запустить», «Проверить» — закрытые примеры: запись была → `false`; реплика не свежа и операция не терпит устаревания → `false`.

**Как проверить себя.** Три условия обязательны одновременно; модель задаёт допустимую наблюдаемость записи, а не только физическое отставание.

**Если не принято.**
- `true` при `wrote = true` → забыто отрицание.
- `true` при `staleTolerant = false` → условие пропущено.

> **Подсказка.** Переведи каждое условие в вопрос контракта: «нужна ли своя запись?», «свежа ли копия?», «терпит ли операция старое?».

### Задание 3 · Hard: маршрутизируй запрос по требованиям consistency

**Цель.** `primary`, если была запись, требуется самое свежее состояние или реплика несвежа; во всех прочих случаях — `replica`.

**Ожидаемый вывод** — для `(wrote=false, needsLatest=false, replicaFresh=true)`:

```text
"replica"
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func ConsistencySource(wrote, needsLatest, replicaFresh bool) string`. Импорты запрещены.
2. `wrote || needsLatest || !replicaFresh` → `"primary"`, иначе `"replica"`.
3. «Запустить», «Проверить» — закрытые примеры: запись → `primary`; `needsLatest` → `primary`; несвежая реплика → `primary`.

**Как проверить себя.** Из восьми комбинаций только одна даёт `replica`; маршрутизация — не доказательство линеаризуемости.

**Если не принято.**
- `replica` при `needsLatest = true` → сигнал не учтён.
- `primary` при единственно благоприятной комбинации → перепутано отрицание свежести.

> **Подсказка.** Любой из трёх сигналов «за primary» достаточен; `||` между ними.

## Проверь себя

- Какая гарантия относится к одному клиенту, а какая — к системе?
- Как поведёт себя чтение после переключения primary?
- При каком сроке ожидания будет ошибка или запасной путь?
- Какая устаревшая версия недопустима для этой операции?
- Что доказывает функция-политика и чего не доказывает?

## Итог

- Модель согласованности — обещание о наблюдениях; её выбирают для операции, а не для системы целиком.
- Read-your-writes и monotonic reads — сессионные гарантии; linearizability — системная и дорогая; «репликация» не гарантия.
- Механизм — привязка к primary, позиция журнала или токен — с явным запасным путём на тайм-аут и планом на переключение.
