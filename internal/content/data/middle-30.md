# Shutdown, readiness и drain

## Что ты сделаешь

Ты напишешь три функции жизненного цикла: решение о приёме новых запросов при остановке, срок остановки с защитой от переполнения и выбор действия для активной работы с учётом срока. Функции решают по переданным значениям и не останавливают сервер.

## Порядок остановки

Graceful shutdown — остановка, при которой уже принятые запросы успевают завершиться. Порядок шагов важен. Сначала сервис снимает готовность, чтобы балансировщик перестал направлять ему новые запросы. Затем прекращает приём новой работы. После этого ограниченное время ждёт активные задачи. Остаток отменяет, и только потом закрывает зависимости: базу, очереди, файлы.

Нарушение порядка даёт известные сбои. Если закрыть базу раньше, чем завершились запросы, они упадут с ошибкой. Если не снять готовность, балансировщик продолжит слать запросы остановленному процессу, и клиенты увидят обрывы.

> **Важно.** Закрытие зависимостей — последний шаг. Пока хотя бы одна задача может к ним обратиться, закрывать их нельзя.

## Готовность и приём запросов

Готовность (readiness) отвечает на вопрос, может ли сервис принять запрос прямо сейчас. Остановка и готовность связаны, но не совпадают. Во время остановки готовности нет, но активные запросы ещё обрабатываются. Поэтому состояние допуска различает три ответа: сервис принимает работу, не готов, или останавливается и принимает только уже начатое.

Пример показывает такой выбор. Остановка важнее готовности: остановившийся сервис не принимает новую работу, даже если готов технически:

```go
package main

import "fmt"

func admission(stopping, ready bool) string {
    if stopping {
        return "draining"
    }
    if !ready {
        return "not_ready"
    }
    return "accepting"
}

func main() {
    fmt.Println(admission(false, true), admission(false, false), admission(true, true))
}
```

Вывод: `accepting not_ready draining`. Один и тот же сервис получает разные ответы в зависимости от того, что с ним происходит.

## Срок остановки

Срок остановки — общий бюджет всего процесса. Он начинается в момент сигнала и заканчивается в момент, когда сервис должен был завершиться. Если каждый шаг задаёт собственный таймаут, суммарное время может вырасти сильно больше обещанного. Поэтому срок вычисляют один раз, а шаги получают остаток.

Сложение сроков в миллисекундах может переполнить целое число. Пример показывает проверку переполнения до сложения. Большое значение времени и большой срок в сумме дают отрицательный результат, поэтому сравнение делается заранее:

```go
package main

import (
    "fmt"
    "math"
)

func deadline(now, grace int64) int64 {
    if now < 0 || grace < 0 || now > math.MaxInt64-grace {
        return -1
    }
    return now + grace
}

func main() {
    fmt.Println(deadline(1000, 500), deadline(math.MaxInt64, 1))
}
```

Вывод: `1500 -1`. Срок вычислен в миллисекундах, а переполнение дало ответ «ошибка», а не отрицательный срок в прошлом.

## Активная работа и отмена остатка

Активные задачи во время остановки делятся на три группы. Если их нет, сервис останавливается сразу. Если они есть и срок не истёк, сервис ждёт. Если срок истёк, остаток получает отмену. Отрицательное число активных задач — ошибка счётчика, и её нужно видеть, а не прятать.

Отменённая задача должна дать наблюдаемый исход: клиент получает категорию, а журнал — причину. Бесконечно ждать такую задачу нельзя, иначе остановка не закончится никогда.

## Очередь и producer

Закрывать очередь можно только тогда, когда все отправители закончили писать. Иначе отправка в закрытый канал вызывает панику. Поэтому остановка сначала прекращает приём, потом ждёт отправителей, и только после этого закрывает очередь. Закрывает тот, кто знает, что отправителей больше нет.

Тот же принцип касается базы: её закрывают после того, как последний запрос вернул ответ, а не в момент сигнала.

## Сигнал остановки

Сигнал остановки приходит от оркестратора или оператора. В контейнерной среде это почти всегда оркестратор: он сначала просит остановиться, а если процесс не вышел за отведённое время, останавливает его принудительно. Поэтому срок в сервисе должен быть короче срока оркестратора, иначе сервис не успеет закончить порядок шагов. Самый распространённый — `SIGTERM`: он просит процесс завершиться. Сервис не должен реагировать на него немедленным выходом, потому что это прерывает активные запросы. Вместо этого сигнал переводит сервис в режим остановки и запускает весь порядок шагов.

Повторный сигнал обычно означает, что оператор торопится. Тогда разумно сократить оставшийся срок или отменить остаток сразу, но не пропускать шаги с закрытием зависимостей. Двойной сигнал не должен приводить к паническим закрытиям: каждый шаг выполняется ровно один раз.

## Наблюдаемость остановки

Во время остановки полезно видеть три числа: сколько задач активно, сколько времени осталось до срока и сколько задач получили отмену. Эти числа пишут в журнал в начале остановки и по её завершении. Если журнал показывает отмену, а клиенты жалуются на обрывы, порядок шагов нарушен или срок короче, чем нужно.

Метрика длительности остановки помогает подобрать срок. Срок подбирают по наихудшему случаю, а не по средней длительности: редкая длинная задача определяет, успеет ли сервис завершиться, даже если обычно всё проходит быстро. Если остановка всегда укладывается в десять секунд, срок в тридцать секунд скрывает проблему. Если она всегда упирается в срок, часть работы стоит перенести или ускорить.

## Параллельная работа при остановке

Остановка и новые запросы идут параллельно, поэтому счётчик активной работы меняется из многих горутин одновременно. Если сервис проверяет счётчик без защиты, он может решить, что работы нет, хотя один запрос только что начался. Правило простое: приём новой работы и запись в счётчик выполняются под одной защитой, и только после снятия приёма счётчик считается окончательным.

Пример показывает, что число активных задач меняется по каждому запросу, а ответ остановки зависит от финального значения. Счётчик должен вернуться к нулю до того, как остановка решит, что работы нет:

```go
package main

import "fmt"

func main() {
    active := 0
    for _, ev := range []string{"start", "start", "done", "done"} {
        if ev == "start" {
            active++
        } else {
            active--
        }
    }
    fmt.Println("active:", active)
}
```

Вывод: `active: 0`. Счётчик вернулся к нулю, и только тогда остановка может считаться завершённой. Если бы одно из событий «done» потерялось, счётчик остался бы ненулевым, и остановка ждала бы задачу, которой уже нет. Поэтому потерянное событие завершения — тоже ошибка, которую нужно ловить тестом.

## Модель и механизм

Для остановки полезны три вопроса. Что известно балансировщику о готовности? Сколько работы ещё активно? Сколько времени осталось до срока? Ответы определяют, какое действие выбирает сервис на каждом шаге.

Синхронизация здесь главная тема: счётчик активной работы меняется из многих горутин. Его нужно защищать атомарно или под мьютексом, иначе остановка может решить, что работы нет, когда она ещё идёт.

## Типичные ошибки и исправление

Первая ошибка — закрывать базу сразу после сигнала. Исправление — закрывать зависимости последним шагом.

Вторая — не снимать готовность. Исправление — снимать готовность первым шагом и дать балансировщику время.

Третья — складывать таймауты шагов. Исправление — один общий срок, который уменьшается по мере работы.

Четвёртая — ждать активные задачи без предела. Исправление — срок и отмена остатка.

> **Типичная ошибка.** Закрыть очередь, пока обработчик ещё может отправить в неё событие. Отправка в закрытый канал вызывает панику во время остановки, когда её труднее всего диагностировать.

## Если что-то пошло не так

- Клиенты получают обрывы при перезапуске → готовность не снята до остановки приёма; добавь паузу после снятия готовности.
- Остановка занимает больше обещанного времени → шаги используют собственные таймауты; вычисли общий срок один раз.
- Паника при остановке очереди → закрытие выполнено раньше последней отправки; перенеси его после ожидания отправителей.
- Счётчик активной работы уходит в минус → декремент выполнен дважды; проверь пути завершения.

## Воспроизводимая лабораторная: срок остановки с активной работой

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Сервер и сеть не нужны: активная работа моделируется счётчиком в памяти программы.

Программа ниже запускает три задачи, одна из которых не успевает за срок. Она считает активные задачи, по истечении срока отменяет остаток и печатает итог. Запусти её в временном каталоге и сравни вывод с ожидаемым.

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var mu sync.Mutex
    active := 3
    done := make(chan struct{})
    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            mu.Lock()
            active--
            mu.Unlock()
        }()
    }
    wg.Wait()
    close(done)
    mu.Lock()
    remaining := active
    mu.Unlock()
    if remaining == 0 {
        fmt.Println("stopped", remaining)
    } else {
        fmt.Println("cancel_remaining", remaining)
    }
}
```

**Ожидайте:** строка `cancel_remaining 1`. Две задачи завершились, одна осталась активной, и срок истёк, поэтому остаток должен получить отмену. Счётчик защищён мьютексом, и его итог не зависит от порядка завершения.

**Очистка:** программа ничего не создаёт на диске. Если запускал её в временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- Остановка идёт по порядку: снимается готовность, прекращается приём, ограниченно ждут активные задачи, отменяют остаток, закрывают зависимости.
- Срок остановки — общий бюджет процесса; переполнение при сложении миллисекунд проверяется до вычисления.
- Задача, пережившая срок, получает отмену и наблюдаемый исход; очередь закрывает тот, кто знает, что отправителей больше нет.
