# ScaleLab: SLI/SLO, отказ, выпуск и защита решения

## Что ты сделаешь

Ты соберёшь всё, что было в модуле, в один воспроизводимый эксперимент: baseline и кандидат на одинаковых входах, повторы, сценарий отказа, критерии продолжения и отката — и защитишь решение о выпуске перед рецензентом, опираясь на записанные свидетельства, а не на один график. Три функции урока — `ScaleLabDecision`, `ScaleLabGate`, `ReleaseEvidence` — формальные ворота отчёта: считают прогоны и флаг теста отказа; версии, входы и сами результаты они не видят.

## Зачем нужна эта граница

Лаборатория масштабирования (ScaleLab) объединяет измерение, ограниченный отказ и решение о выпуске. Автор фиксирует baseline и кандидата, одинаковые входы, версии среды, команду, число повторов и сценарий отказа; критерии «продолжить», «остановить», «откатить» записывает до прогонов. Все результаты сохраняются, включая неудачные, с указанием, какие выводы они поддерживают и какие ограничения остаются. Учебная лаборатория помогает записать эксперимент; она не принимает production-запросы и не выдаёт допуск к выпуску.

Защита решения — это не презентация, а ответы на вопросы рецензента: что измеряли и в каких единицах; чем baseline отличается от кандидата, кроме изменения; сколько повторов и какой разброс; что сломали и что наблюдали; что произойдёт при откате; чего эксперимент не проверил. Если на какой-то вопрос ответа нет, это записывают как ограничение, а не прячут.

```go group=decision mode=run
package main

import "fmt"

func scaleLabDecision(baselineRuns, candidateRuns int) string {
    if baselineRuns <= 0 || candidateRuns <= 0 {
        return "incomplete"
    }
    return "compare"
}

func main() {
    fmt.Println(scaleLabDecision(3, 3), scaleLabDecision(1, 8), scaleLabDecision(0, 3), scaleLabDecision(3, -1))
}
```

Вывод:

```text
compare compare incomplete incomplete
```

Первые ворота — есть ли что сравнивать: без прогонов хотя бы одной стороны сравнения нет. Один прогон уже даёт `compare` — но не даёт вывода: следующие ворота требуют повторов.

> **Важно.** Функция видит два счётчика. Версию Go, хеш набора данных, одинаковость входов и сами результаты она не проверяет — это записывают отдельно, и рецензент спрашивает именно о них.

## Повторы и тест отказа как условие сравнения

Три прогона на сторону — минимум, при котором виден разброс; меньше — сравнение двух случайных чисел. Тест отказа — ограниченная инъекция из урока об отказах: кандидат под той же нагрузкой при отказе зависимости должен сохранять инварианты — ограниченную очередь, сроки, идемпотентность. Кандидат, который быстрее в норме и ломается при отказе, — не кандидат.

```go group=gate mode=run
package main

import "fmt"

func scaleLabGate(baselineRuns, candidateRuns int, faultTested bool) string {
    if baselineRuns < 3 || candidateRuns < 3 {
        return "repeat"
    }
    if !faultTested {
        return "fault_test"
    }
    return "review"
}

func main() {
    fmt.Println(scaleLabGate(3, 3, true), scaleLabGate(2, 4, true), scaleLabGate(4, 2, true), scaleLabGate(3, 3, false), scaleLabGate(0, 0, false))
}
```

Вывод:

```text
review repeat repeat fault_test repeat
```

Порядок ворот: сначала повторы, потом отказ, потом рецензия. Отрицательные счётчики тоже `repeat` — модель не выделяет ошибку входа: любые прогоны меньше трёх требуют прогонов. Флаг `faultTested` — утверждение автора; что тест действительно выполнялся и что именно ломали, проверяет рецензент по записи.

> **Типичная ошибка.** Тест отказа «был когда-то» на другой версии. Кандидат меняет поведение под отказом так же, как под нагрузкой; тест повторяют на той сборке, которую выпускают.

## Свидетельства для выпуска

Выпуск разрешают только при полном наборе: не меньше трёх прогонов на сторону и выполненный тест отказа. Это инвариант ворот, и он сознательно неполон: версия среды, одинаковость входов, корректность результата, совместимость отката — за пределами сигнатуры и фиксируются в записи свидетельств (evidence record), которую читает человек.

```go group=evidence mode=run
package main

import "fmt"

func releaseEvidence(baselineRuns, candidateRuns int, faultTested bool) bool {
    return baselineRuns >= 3 && candidateRuns >= 3 && faultTested
}

func main() {
    fmt.Println(releaseEvidence(3, 3, true), releaseEvidence(4, 3, true), releaseEvidence(3, 3, false), releaseEvidence(2, 3, true), releaseEvidence(0, 0, true))
}
```

Вывод:

```text
true true false false false
```

`true` здесь означает «формальные ворота пройдены», а не «выпускать». Решение принимает рецензент по полной записи; функция лишь не даёт поставить вопрос о выпуске раньше времени.

> **Зачем.** Формальные ворота защищают от самого частого провала: решения «на глаз» по одному удачному прогону без теста отказа.

## Запись свидетельств

Запись — один документ на эксперимент: вопрос и гипотеза с прогнозом на выигрыш и на риск; манифест baseline и кандидата — revision, версия Go, ОС и CPU, набор данных и его хеш, команды, флаги, число повторов; результаты всех прогонов сырыми значениями, медианы и размахи; сценарий отказа — что, как долго, какой инвариант, что наблюдали; план отката и его проверка; выводы и ограничения — что не проверено, на каком стенде, при каком составе нагрузки. Рецензент читает запись без автора; если ему нужно что-то спросить, это пробел записи.

## Манифест: что именно сравниваем

Самая частая причина несопоставимости — не изменение, а стенд. Между прогонами baseline и кандидата успевают поменяться версия Go после обновления инструментов, набор данных после «небольшой чистки», параметры контейнера, фоновая нагрузка на машине. Поэтому манифест записывают до первого прогона и проверяют перед каждым: revision обеих сторон, вывод `go version`, хеш набора данных, команды и флаги буквально, лимиты ресурсов стенда, время суток и что ещё работало на машине. Если что-то из этого отличается между сторонами, разница результатов объясняется стендом не хуже, чем изменением, и сравнение повторяют.

Манифест — часть записи свидетельств, а не отдельный файл «на всякий случай»: рецензент начинает с него, и первый вопрос защиты — «чем ещё отличались стороны?» — должен иметь ответ «ничем, вот манифест».

## Как защищать решение

Начни с вопроса, который проверяли, и с заранее записанного критерия. Покажи сравнение медиан с размахом — не средние и не лучший прогон. Назови, чем baseline и кандидат отличаются помимо изменения, и почему это не объясняет разницу. Опиши отказ и наблюдение инвариантов. Скажи, что произойдёт при откате и как это проверено. Закончи ограничениями: чего эксперимент не проверил и что для этого нужно. Рецензент не ищет подвох — он ищет, где заканчиваются свидетельства и начинается интерпретация; защита, которая сама проводит эту границу, проходит быстро.

Отрицательный исход защищают так же: гипотеза не подтвердилась, вот запись, вот что узнали, вот следующий эксперимент. Для курса это равноценный результат.

## Критерии до прогонов

Критерий продолжения — что должно быть верно, чтобы изменение пошло дальше: например, медиана кандидата ниже медианы baseline больше, чем на размах, при тех же `allocs/op` и сохранённых инвариантах под отказом. Критерий остановки — что останавливает эксперимент досрочно: рост ошибок выше порога, нарушение инварианта, исчерпание времени. Критерий отката — при каком наблюдении после выпуска возвращают baseline. Все три записывают до прогонов, потому что после них любой критерий можно подогнать под результат — и это будет незаметно даже для автора.

## Что объединяет модуль

Ёмкость и запас — чтобы знать границу; обратное давление и допуск — чтобы её держать; очередь, повторы, outbox — чтобы работа не терялась и не удваивалась; инъекция отказов — чтобы проверить это до инцидента; SLI и бюджет — чтобы измерять последствия; канареечный выпуск и разбор — чтобы менять систему, не ломая её, и учиться, когда сломалась. ScaleLab — место, где эти инструменты применяют к одному изменению разом; на экзамене и в проекте P4 спрашивают именно о связях между ними.

## Практическая процедура

Выбери одно изменение производительности в своём сервисе. Заполни запись свидетельств по разделу выше до прогонов: гипотеза, манифест, критерии. Сделай три прогона на сторону, тест отказа на кандидате, проверку отката. Прогони счётчики через функции урока — они должны дать `compare`, `review`, `true` — и затем ответь на шесть вопросов защиты письменно. Отдай запись коллеге без комментариев; каждый его вопрос — пробел, который нужно закрыть в записи, а не в разговоре.

Записанные критерии ещё и экономят время защиты: рецензент сравнивает результат с критерием, а не спорит о том, каким он должен был быть, и обсуждение сводится к одному вопросу — выполнен ли критерий по записи.

## Типичные ошибки

- Решение по одному прогону и одному графику.
- Baseline и кандидат на разных входах, версиях или машинах.
- Тест отказа на другой сборке или «когда-то».
- Откат не проверен; миграция необратима.
- Ограничения не записаны: рецензент узнаёт о них из вопросов.
- Отрицательный результат не оформлен: следующий эксперимент повторит ошибку.

## Самостоятельная лаборатория

Возьми любой эксперимент из уроков модуля — benchmark, профиль, очередь, повторы — и оформи его как запись свидетельств целиком: гипотеза, манифест, три прогона на сторону, тест отказа, откат, ограничения. Проведи его через три функции урока и затем защити перед коллегой или перед собой через день по шести вопросам. Запиши, какие вопросы не имели ответа в записи, и дополни её. Это и есть заготовка отчёта для проекта P4.

## Если что-то пошло не так

- `compare` при нуле прогонов → граница `<= 0`.
- `review` при двух прогонах → минимум три на каждую сторону.
- `fault_test` раньше `repeat` → порядок ворот: сначала повторы.
- `true` без теста отказа → все три условия обязательны.
- `incomplete` для отрицательных в задании 2 → там модель отвечает `repeat`.
- `import … is not allowed` → импорты запрещены.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Функции видят только счётчики и флаг; версии, входы и результаты фиксируются в записи свидетельств.

### Задание 1 · Easy: scalelab: sli/slo, отказ, выпуск и защита решения — классификация

**Цель.** `incomplete`, если число прогонов хотя бы одной стороны `≤ 0`; иначе `compare`.

**Ожидаемый вывод** — для `(3, 3)` и `(1, 8)`:

```text
"compare"
"compare"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func ScaleLabDecision(baselineRuns int, candidateRuns int) string`. Импорты запрещены.
2. `baselineRuns <= 0 || candidateRuns <= 0` → `"incomplete"`, иначе `"compare"`.
3. «Запустить», «Проверить» — закрытые примеры: ноль или отрицательное у любой стороны → `incomplete`.

**Как проверить себя.** Один прогон на сторону — уже `compare`; это первые ворота, не разрешение на вывод.

**Если не принято.**
- `compare` при нуле → граница нестрогая.
- `incomplete` при `(1, 8)` → один прогон допустим на этих воротах.

> **Подсказка.** Одно условие; вся суть — в том, чего функция не видит.

### Задание 2 · Medium: scalelab: sli/slo, отказ, выпуск и защита решения — политика

**Цель.** Меньше трёх прогонов у любой стороны → `repeat`; иначе без теста отказа → `fault_test`; с ним → `review`.

**Ожидаемый вывод** — для `(3, 3, true)`, `(2, 4, true)`, `(4, 2, true)`, `(3, 3, false)`:

```text
"review"
"repeat"
"repeat"
"fault_test"
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func ScaleLabGate(baselineRuns int, candidateRuns int, faultTested bool) string`. Импорты запрещены.
2. Повторы → отказ → рецензия, в этом порядке.
3. «Запустить», «Проверить» — закрытые примеры: нули и отрицательные → `repeat`.

**Как проверить себя.** Отрицательные счётчики — `repeat`, а не ошибка: модель не выделяет некорректный вход; флаг отказа — утверждение автора.

**Если не принято.**
- `fault_test` при двух прогонах → повторы проверяются первыми.
- `review` без флага → флаг обязателен.

> **Подсказка.** Три `return`; порядок — политика ворот.

### Задание 3 · Hard: scalelab: sli/slo, отказ, выпуск и защита решения — проверка инварианта

**Цель.** `true` ровно когда оба счётчика `≥ 3` и `faultTested`.

**Ожидаемый вывод** — для `(3, 3, true)`, `(4, 3, true)`, `(3, 3, false)`:

```text
true
true
false
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func ReleaseEvidence(baselineRuns int, candidateRuns int, faultTested bool) bool`. Импорты запрещены.
2. Верни `baselineRuns >= 3 && candidateRuns >= 3 && faultTested`.
3. «Запустить», «Проверить» — закрытые примеры: два прогона у любой стороны → `false`; нули → `false`.

**Как проверить себя.** `true` — формальные ворота пройдены; версия Go, хеш данных и одинаковость входов остаются в записи свидетельств.

**Если не принято.**
- `true` при двух прогонах → граница `>= 3`.
- `true` без теста отказа → третье условие пропущено.

> **Подсказка.** Одно выражение; его неполнота — осознанная и записанная.

## Итог

- ScaleLab — один воспроизводимый эксперимент: манифест, повторы, отказ, откат, критерии до прогонов, запись свидетельств для рецензента.
- Формальные ворота — повторы и тест отказа — не дают поставить вопрос о выпуске раньше времени; решение принимает человек по записи.
- Защита решения — ответы на вопросы рецензента с явной границей между свидетельством и интерпретацией; отрицательный результат защищают так же.
