# TaskFlow: границы и схема

## Что ты сделаешь

Ты напишешь три проверки, из которых складывается первый слой TaskFlow: валидацию входа задачи с порядком проверок и лимитом в байтах, таблицу допустимых переходов статуса и помощника, который сравнивает проект задачи с проектом запроса. Все функции получают значения и возвращают ответ. Они не обращаются к базе, не читают заголовки HTTP и не решают, имеет ли пользователь право на действие.

## Владелец данных и границы проекта

Каждая задача TaskFlow принадлежит проекту. Это основной факт, из которого следуют остальные правила. Поэтому `project_id` обязателен при создании и не может быть пустым даже тогда, когда заголовок задачи в порядке. Если проекта нет, ошибка относится к адресу записи, и разбирать заголовок бессмысленно.

Порядок проверок входа важен, потому что клиент получает один код ответа. Сначала проверяется владелец, потом содержимое. Если бы заголовок проверялся раньше, пустой проект остался бы незамеченным, пока клиент не исправит название. Это неудобно и не отражает реальную причину отказа.

Граница владельца проверяется дважды: в коде приложения и в схеме базы. В коде она даёт понятный код ответа. В схеме она защищает данные, если запись сделана мимо приложения, например скриптом миграции. Внешний ключ на таблицу проектов и запрет `NULL` в колонке проекта выражают то же правило, что и проверка функции. При удалении проекта та же граница решает судьбу его задач: либо запрет удаления, пока есть задачи, либо каскад с явным решением в документации. Молчаливое удаление задач без записи в журнал — самая тяжёлая ошибка этого слоя, потому что её нельзя заметить по ответу API. Поэтому правило о судьбе задач записывают до реализации обработчика удаления, а не после первого инцидента.

## Границы текста: лимит в байтах

Лимит заголовка в TaskFlow задан в байтах UTF-8, а не в символах. Для латиницы разница не видна: одна буква занимает один байт. Для кириллицы одна буква занимает два байта, поэтому шестьдесят букв весят сто двадцать байт, а шестьдесят одна буква уже сто двадцать два. Если считать символы, пользователь с русским названием получит ограничение, которое не совпадает с тем, что хранит база.

Пример 1 показывает, чем отличаются символы и байты. Функция `len` возвращает байты, а `utf8.RuneCountInString` возвращает символы.

```go
package main

import (
	"fmt"
	"unicode/utf8"
)

func main() {
	title := "яяя"
	fmt.Println(utf8.RuneCountInString(title), len(title))
	fmt.Println(len(title) > 4)
}
```

Вывод: `3 6` и `true`. Три буквы дают шесть байт, поэтому при лимите четыре байта такое название отклоняется, хотя символов меньше лимита.

В SQL та же мысль выражается функцией `octet_length`, которая считает байты, а не `length`, который считает символы. Ограничение в схеме и проверка в приложении должны использовать одну единицу измерения. Иначе одна и та же строка пройдёт проверку в одном месте и упадёт в другом.

## Переходы состояния в явной таблице

Статус задачи меняется не произвольно. `open` может стать `in_progress` или `cancelled`. `in_progress` может стать `done` или `cancelled`. Из `done` и `cancelled` переходов нет. Такое правило лучше записать одной таблицей, чем разбросать по обработчикам: тогда видно все разрешённые пары, и добавление нового перехода требует изменения в одном месте.

Пример 2 показывает таблицу разрешённых переходов в виде словаря. Функция проверяет список целевых состояний для текущего статуса.

```go
package main

import "fmt"

var allowed = map[string][]string{
	"open":        {"in_progress", "cancelled"},
	"in_progress": {"done", "cancelled"},
}

func canMove(from, to string) bool {
	for _, next := range allowed[from] {
		if next == to {
			return true
		}
	}
	return false
}

func main() {
	fmt.Println(canMove("open", "in_progress"))
	fmt.Println(canMove("done", "open"))
}
```

Вывод: `true` и `false`. Статус `done` не имеет записи в таблице, поэтому для него срез пуст и любой переход отклоняется. Отсутствие записи — тоже решение: неизвестный статус не должен проходить проверку по умолчанию.

Таблица не заменяет проверку в базе. Если статус хранится как строка без ограничения, запись `done` в обход приложения пройдёт. Поэтому допустимые значения статуса записывают и в схему, например через `CHECK (status IN ('open', 'in_progress', 'done', 'cancelled'))`.

## Схема как часть контракта

Схема таблицы `tasks` описывает то, что гарантирует база независимо от приложения. Колонки `project_id` и `title` объявлены `NOT NULL`. Внешний ключ указывает на таблицу проектов. Ограничение на статус перечисляет допустимые значения. Ограничение на длину заголовка проверяет `octet_length`. Каждое из них дублирует правило приложения и защищает от записи, которая обошла код.

Дублирование кажется лишним, но оно дешёвое. Проверка в приложении даёт понятный ответ клиенту. Ограничение в схеме не даёт испортить данные. Если убрать одно из них, второе перестаёт быть достаточным: приложение может ошибиться в ветке, а скрипт миграции может не знать о правилах приложения.

## Готова ли схема к миграции

Изменение схемы с данными делают в несколько шагов. Сначала добавляют новую колонку без ограничения. Затем заполняют её для существующих строк. Потом проверяют, что старые строки подходят под ограничение. Только после этого включают ограничение `NOT NULL` или `CHECK`. Если сделать всё одним шагом, миграция упадёт на первой же строке, которая не подходит под новое правило, и откатить её будет сложно.

Перед миграцией спрашивают три вещи. Есть ли строки, которые нарушают новое правило. Можно ли заполнить значение по умолчанию без потери смысла. Понадобится ли блокировка таблицы на время изменения. Если хотя бы на один вопрос ответа нет, миграция ещё не готова.

## Типичные ошибки и исправление

> **Типичная ошибка.** Считать, что лимит в байтах и лимит в символах совпадают для текста на любом языке. Так проверка в приложении пропускает строку, которую схема потом отвергает, или наоборот.

Ошибки в этом слое обычно простые. Порядок проверок перепутан, и клиент получает не ту причину отказа. Таблица переходов дополнена прямо в обработчике, и правило нигде не видно целиком. Схема описана одним комментарием, а ограничения в ней не созданы. Миграция с данными делается одним шагом без проверки старых строк.

## Если что-то пошло не так

- Клиент получает `missing_title` при пустом проекте → порядок проверок перепутан; проверь владельца первым.
- Русский заголовок в 61 букву отклоняется, хотя кажется коротким → лимит считается в символах; переведи проверку на байты.
- Задача переходит из `done` в `open` → таблица не запрещает переход или проверка идёт в обход таблицы.
- Миграция падает на середине → новое ограничение включено до заполнения и проверки старых строк.

## Воспроизводимая лабораторная: схема и ограничения TaskFlow

**Предварительные условия:** установленный Go нужной версии из `go.mod` проекта. Настоящая база не нужна: лаборатория собирает те же проверки в памяти процесса и печатает результат.

Программа ниже проверяет три задачи, длинный заголовок и два перехода статуса. Она использует ту же логику, что и задания, и печатает ответы в фиксированном порядке. Запусти её во временном каталоге и сравни вывод с ожидаемым.

```go
package main

import (
	"fmt"
	"strings"
	"unicode/utf8"
)

const maxTitleBytes = 120

type task struct {
	project string
	title   string
}

var moves = map[string][]string{
	"open":        {"in_progress", "cancelled"},
	"in_progress": {"done", "cancelled"},
}

func validate(t task) string {
	if t.project == "" {
		return "missing_project"
	}
	if t.title == "" {
		return "missing_title"
	}
	if len(t.title) > maxTitleBytes {
		return "title_too_long"
	}
	return "valid"
}

func canMove(from, to string) bool {
	for _, next := range moves[from] {
		if next == to {
			return true
		}
	}
	return false
}

func main() {
	tasks := []task{
		{"p1", "Ship release"},
		{"", "Orphan"},
		{"p1", ""},
	}
	for i, t := range tasks {
		fmt.Println(i+1, validate(t))
	}
	title := strings.Repeat("я", 61)
	fmt.Println("bytes", len(title), "runes", utf8.RuneCountInString(title), validate(task{"p1", title}))
	fmt.Println("open->in_progress", canMove("open", "in_progress"))
	fmt.Println("done->open", canMove("done", "open"))
}
```

**Ожидайте:** строки `1 valid`, `2 missing_project`, `3 missing_title`, затем `bytes 122 runes 61 title_too_long`, `open->in_progress true` и `done->open false`. Шестьдесят одна буква занимает сто двадцать две единицы байтового лимита, поэтому проверка отклоняет заголовок, хотя символов немного.

**Очистка:** программа ничего не создаёт на диске и работает только в памяти процесса. Если запускал её во временном каталоге, удали каталог, например командой `rm -rf /dev/shm/каталог_лаборатории`.

## Итог

- Задача принадлежит проекту, поэтому проверка владельца идёт первой, а схема дублирует это правило ограничением `NOT NULL` и внешним ключом.
- Лимит заголовка задан в байтах UTF-8: проверка в приложении и ограничение в схеме используют одну единицу измерения.
- Переходы статуса записаны явной таблицей и продублированы в схеме; миграция с данными идёт в несколько шагов с проверкой старых строк.
