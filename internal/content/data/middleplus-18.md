# Перегрузка, admission control и load shedding

## Что ты сделаешь

Ты разберёшь, что такое перегрузка в терминах предложенной и устойчиво обрабатываемой работы, где именно стоит решение о допуске — до дорогих ресурсов — и как сбрасывать нагрузку так, чтобы критическая работа выживала, а вызывающий понимал, что произошло. Три функции урока — `LoadMode`, `LoadDecision`, `ProtectCritical` — классифицируют снимок нагрузки и применяют приоритет; ресурсов они не резервируют и очередей не ведут.

## Зачем нужна эта граница

Перегрузка (overload) начинается, когда предложенная работа (offered load) требует больше ресурса, чем система может устойчиво выделить. Устойчиво — ключевое слово: на секунду можно принять и вдвое больше, но тогда вырастут очередь, задержка и расход памяти, и через минуту откажет всё. Контроль допуска (admission control) решает до дорогой работы, есть ли место новому запросу. Сброс нагрузки (load shedding) выбирает, какие запросы отклонить, если принять всё нельзя.

Сначала выбери ресурсную границу: число одновременно исполняемых задач, память очереди, соединения или общий бюджет. Потом задай порядок решения: некорректный вход; продолжающаяся критическая работа; исчерпание ресурса; допустимость нового запроса. Приоритет должен быть явным, иначе критическую задачу вытеснит фоновый поток — или фоновый поток никогда не получит обслуживания.

```go group=mode mode=run
package main

import "fmt"

func loadMode(offered, capacity int) string {
    if offered < 0 || capacity <= 0 {
        return "invalid"
    }
    if offered <= capacity {
        return "normal"
    }
    return "overloaded"
}

func main() {
    fmt.Println(loadMode(4, 5), loadMode(5, 5), loadMode(6, 5), loadMode(0, 5), loadMode(-1, 5), loadMode(1, 0))
}
```

Вывод:

```text
normal normal overloaded normal invalid invalid
```

Предложенная нагрузка, равная ёмкости, — ещё `normal`: модель считает границу включительной. Ноль запросов — тоже норма. Нулевая ёмкость — некорректная конфигурация, а не «всё перегружено».

> **Важно.** `offered` — это всё, что хотят выполнить, включая повторы и фоновые задачи; `capacity` — то, что система завершает устойчиво. Сравнивать нужно их, а не «запросов в секунду» с «числом подов».

## Решение о допуске: где и когда

Чем раньше принято решение, тем дешевле отказ. Отказать на входе — потратить микросекунды; принять, открыть соединение с базой, занять горутину и память, а потом сорвать срок — потратить всё это впустую и ещё замедлить тех, кого можно было обслужить. Поэтому контроль допуска стоит на границе сервиса, до аутентификации и десериализации тела, если это возможно, и опирается на дешёвые счётчики: число задач в работе, глубину очереди, остаток бюджета.

```go group=decision mode=run
package main

import "fmt"

func loadDecision(offered, capacity int, critical bool) string {
    if offered < 0 || capacity <= 0 {
        return "invalid"
    }
    if offered <= capacity {
        return "accept"
    }
    if critical {
        return "prioritize"
    }
    return "shed"
}

func main() {
    fmt.Println(loadDecision(5, 5, false), loadDecision(8, 5, true), loadDecision(8, 5, false), loadDecision(6, 5, true))
}
```

Вывод:

```text
accept prioritize shed prioritize
```

В норме принимают всех; при перегрузке критический запрос получает приоритет, остальные сбрасываются. «Приоритет» здесь — метка для дальнейшей обработки: место ему найдут за счёт сброшенных; это не «выполнить немедленно».

> **Типичная ошибка.** Проверять приоритет раньше нагрузки. Тогда в норме критические запросы идут по отдельному пути, а обычные — по общему, и две очереди ведут себя по-разному без всякой причины.

## Сброс: кого и по какому правилу

Сброс по приоритету требует, чтобы приоритет был известен на входе: по типу операции (оплата важнее рекомендаций), по вызывающему (внутренняя проверка здоровья важнее отчёта), по стоимости (дешёвые запросы сбрасывать бессмысленно). Критерии записывают заранее и проверяют на таблице входов. Ещё два правила: сбрасывают ту работу, которая без сброса всё равно не успеет к сроку, и не сбрасывают уже начатую — её завершение дешевле повтора.

```go group=protect mode=run
package main

import "fmt"

func protectCritical(offered, capacity int, critical, deadlineOK bool, queueAge, maxQueueAge int) bool {
    if offered < 0 || capacity <= 0 || queueAge < 0 || maxQueueAge < 0 {
        return false
    }
    if offered <= capacity {
        return true
    }
    return critical && deadlineOK && queueAge <= maxQueueAge
}

func main() {
    fmt.Println(protectCritical(4, 5, false, true, 0, 60), protectCritical(8, 5, true, true, 30, 60))
    fmt.Println(protectCritical(8, 5, false, true, 30, 60), protectCritical(8, 5, true, false, 30, 60), protectCritical(8, 5, true, true, 61, 60))
}
```

Вывод:

```text
true true
false false false
```

При перегрузке пропускают только критическую задачу, у которой не истёк срок и которая не простояла в очереди дольше допустимого: критическая, но уже бесполезная работа тоже сбрасывается. Граница возраста включительная — шестьдесят секунд при пределе шестьдесят ещё проходит.

> **Зачем.** Сброс без условия по сроку сохраняет «важные» запросы, результат которых никому не нужен, и тратит на них ёмкость, которой не хватило обычным.

## Что видит вызывающий и что видит оператор

Отклонённый запрос получает понятный ответ: статус, по которому ясно, что это не ошибка клиента и не сбой сервера, а временный отказ; подсказку, можно ли повторить и когда; и обязательно ограничение на повтор со стороны самого клиента — иначе сброс превращается в волну повторов. Внутри растут счётчики: принято, приоритизировано, сброшено — по классам запросов. Если сброшенных нет никогда, порог либо слишком высок, либо перегрузки не было; если сброшены все обычные, а критические всё равно не успевают, граница ёмкости выбрана неверно.

Справедливость — отдельный инвариант: класс, который сбрасывают первым, при длительной перегрузке не обслуживается вовсе. Если это недопустимо, ему резервируют долю ёмкости, и сброс применяется только к работе сверх доли.

## Измерить предложенную нагрузку

Контроль допуска опирается на счётчики, и они должны быть дешёвыми и честными. Число задач в работе — атомарный счётчик, который увеличивают при допуске и уменьшают при завершении, включая завершение с ошибкой и по отмене: утечка на одном пути ведёт к ложной перегрузке через час. Глубина очереди — из прошлых уроков. Предложенная нагрузка за короткое окно — счётчик входящих за последнюю секунду, а не за минуту: минутное среднее прячет всплеск, который уже положил сервис.

Отдельно измеряй нагрузку по классам: если критические запросы — один процент, а сбрасывают их первыми из-за ошибки в приоритете, общий график этого не покажет. И помни про повторы: клиент, повторяющий сброшенный запрос немедленно, удваивает предложенную нагрузку ровно в момент перегрузки — ответ со сроком повтора и бюджет повторов из прошлого урока здесь не роскошь, а часть защиты.

## Сброс и деградация — не одно и то же

Сброс отклоняет запрос целиком. Деградация (graceful degradation) выполняет его дешевле: без персонализации, из кеша, с меньшим числом результатов. Деградация сохраняет пользователю ответ ценой качества и часто предпочтительнее сброса для некритичных функций; но она должна быть заранее спроектирована, измерена по ёмкости и видна в метриках как отдельный режим. Политика допуска может сочетать оба: сначала деградировать обычные запросы, затем сбрасывать их, и лишь потом трогать критические.

## Практическая процедура

Выпиши классы запросов сервиса и для каждого — приоритет, срок, допустимый возраст в очереди и источник этих чисел. Затем определи ресурсную границу и способ измерения предложенной нагрузки за короткое окно. Составь таблицу входов, где срабатывают два правила сразу: перегрузка и критический запрос с истёкшим сроком; норма и некритический запрос; перегрузка и критический, простоявший в очереди дольше предела. Проверь по таблице функции урока и запиши для каждого класса, что получит вызывающий при сбросе.

Последний вопрос перед включением контроля допуска в бой — что произойдёт при его собственном сбое: если счётчик задач в работе «утёк» и показывает перегрузку всегда, сервис откажет всем при пустой очереди. Поэтому у политики есть предохранитель: если доля сброшенных превышает заранее заданный потолок дольше заданного времени при низкой реальной утилизации ресурса, сброс отключается и поднимается алерт. Защита, которая не умеет сомневаться в себе, становится источником инцидентов.

## Типичные ошибки

- Сравнение «запросов в секунду» с числом экземпляров вместо устойчивой ёмкости.
- Решение о допуске после дорогой работы: отказ стоит столько же, сколько обслуживание.
- Приоритет раньше нагрузки: разные пути в норме без причины.
- Сброс критической работы с истёкшим сроком не выполняется: ёмкость уходит в никуда.
- Отказ как 500 без подсказки о повторе: клиенты повторяют немедленно.
- Низкий приоритет без резервной доли: голодание при долгой перегрузке.

## Самостоятельная лаборатория

Собери сервис с двумя классами запросов — критическим и обычным — и ограничением на число одновременно исполняемых задач. Подай нагрузку втрое выше ёмкости со смесью классов и реализуй допуск по функциям урока: в норме всех, при перегрузке критические с живым сроком. Считай исходы по классам и измерь задержку критических запросов с защитой и без. Затем убери условие по сроку и покажи, как ёмкость уходит на просроченную критическую работу. Удали стенд.

## Если что-то пошло не так

- `overloaded` при `offered == capacity` → граница включительная, нужно `<=`.
- `invalid` при `offered = 0` → ноль — допустимая нагрузка; недопустимы отрицательные.
- `prioritize` в норме → приоритет проверяется только при перегрузке.
- `true` при истёкшем сроке → при перегрузке нужны все три условия.
- `false` при `queueAge == maxQueueAge` → граница возраста включительная.
- `import … is not allowed` → импорты запрещены.

## Практика

Три функции без `main` и печати; среда показывает результаты строками в кавычках и `bool`. Входы — снимок нагрузки; функции не резервируют ресурс и не ведут очередь.

### Задание 1 · Easy: перегрузка, admission control и load shedding — классификация

**Цель.** `offered < 0` или `capacity ≤ 0` → `invalid`; `offered ≤ capacity` → `normal`; иначе `overloaded`.

**Ожидаемый вывод** — для `(4, 5)` и `(5, 5)`:

```text
"normal"
"normal"
```

**Шаги.**
1. Выбери задание «Easy»: сигнатура `func LoadMode(offered int, capacity int) string`. Импорты запрещены.
2. Валидность, затем сравнение `<=`.
3. «Запустить», «Проверить» — закрытые примеры: `(6, 5)` → `overloaded`; `(0, 5)` → `normal`; `(-1, 5)` и `(1, 0)` → `invalid`.

**Как проверить себя.** Равенство — норма; ноль запросов — норма; нулевая ёмкость — ошибка конфигурации.

**Если не принято.**
- `overloaded` при равенстве → строгое сравнение.
- `invalid` для нуля запросов → проверка `offered <= 0` вместо `< 0`.

> **Подсказка.** Три `return` в порядке условия.

### Задание 2 · Medium: перегрузка, admission control и load shedding — политика

**Цель.** Валидность как в задании 1; `offered ≤ capacity` → `accept`; при перегрузке `critical` → `prioritize`, иначе `shed`.

**Ожидаемый вывод** — для `(5, 5, false)` и `(8, 5, true)`:

```text
"accept"
"prioritize"
```

**Шаги.**
1. Выбери задание «Medium»: сигнатура `func LoadDecision(offered int, capacity int, critical bool) string`. Импорты запрещены.
2. `invalid` → `accept` → `prioritize` → `shed`, в этом порядке.
3. «Запустить», «Проверить» — закрытые примеры: `(8, 5, false)` → `shed`; `(6, 5, true)` → `prioritize`; некорректные → `invalid`.

**Как проверить себя.** Приоритет проверяется только при перегрузке; в норме принимают всех независимо от флага.

**Если не принято.**
- `prioritize` при `offered <= capacity` → приоритет проверен раньше нагрузки.
- `accept` при перегрузке некритического → порядок правил.

> **Подсказка.** Задание 1 плюс одна развилка по флагу.

### Задание 3 · Hard: перегрузка, admission control и load shedding — проверка инварианта

**Цель.** Некорректные входы → `false`; `offered ≤ capacity` → `true`; при перегрузке — только `critical`, `deadlineOK` и `queueAge ≤ maxQueueAge`.

**Ожидаемый вывод** — для `(4, 5, false, true, 0, 60)` и `(8, 5, true, true, 30, 60)`:

```text
true
true
```

**Шаги.**
1. Выбери задание «Hard»: сигнатура `func ProtectCritical(offered int, capacity int, critical bool, deadlineOK bool, queueAge int, maxQueueAge int) bool`. Импорты запрещены.
2. `offered < 0`, `capacity <= 0`, `queueAge < 0` или `maxQueueAge < 0` → `false`.
3. `offered <= capacity` → `true`; иначе `critical && deadlineOK && queueAge <= maxQueueAge`.
4. «Запустить», «Проверить» — закрытые примеры: некритический при перегрузке → `false`; истёкший срок → `false`; возраст 61 при пределе 60 → `false`, 60 → `true`; в норме — `true` даже с истёкшим сроком и большим возрастом.

**Как проверить себя.** В норме функция не смотрит на флаги; при перегрузке нужны все три условия; граница возраста включительная.

**Если не принято.**
- `false` в норме при `deadlineOK = false` → условия применены вне перегрузки.
- `true` при `queueAge = 61` → строгое `<` нужно заменить на `<=`.

> **Подсказка.** Срок и возраст — разные вещи: срок задаёт вызывающий, возраст считает очередь; при перегрузке важны оба.

## Итог

- Перегрузка — предложенная работа сверх устойчивой ёмкости; решение о допуске стоит на входе и опирается на дешёвые счётчики.
- Порядок правил: валидность, норма, приоритет, сброс; при перегрузке выживает критическое с живым сроком и допустимым возрастом.
