# 18. Перегрузка, admission control и load shedding

**Ранг:** Middle+ · **Модуль:** ScaleLab reliability · **Время:** 180 минут · **Предварительное требование:** `middleplus-17`  
**Цель:** Overload (перегрузка) возникает, когда запросы требуют больше ресурсов, чем доступно в устойчивом режиме. Admission control (контроль допуска) защищает границу до выделения дорогих ресурсов; load shedding (сброс нагрузки) может отклонять менее важную работу. Необходимо сохранять ограничение очереди, deadline, справедливость и понятный ответ вызывающей стороне.

## Термины и перевод

- **Перегрузка и admission control** — Overload (перегрузка) возникает, когда запросы требуют больше ресурсов, чем доступно в устойчивом режиме. Admission control (контроль допуска) защищает границу до выделения дорогих ресурсов; load shedding (сброс нагрузки) может отклонять менее важную работу. Необходимо сохранять ограничение очереди, deadline, справедливость и понятный ответ вызывающей стороне.
- **capacity** — ёмкость: полезная работа за определённое время при заданной конфигурации.
- **backpressure** — обратное давление: сигнал производителю ограничить входящую работу.
- **queue depth** — глубина очереди: число ожидающих задач в определённой точке.
- **retry budget** — бюджет повторов: общий ограниченный объём повторных попыток.
- **outbox** — исходящий журнал: записи о публикации, атомарно сохранённые вместе с изменением.
- **overload** — перегрузка: поступление работы, превышающее устойчивый ресурсный предел.
- **fault injection** — инъекция отказа: контролируемое моделирование выбранной ошибки.
- **SLI/SLO** — индикатор/цель уровня сервиса: определённая метрика и цель по её окну.
- **rollout/rollback** — постепенный выпуск/откат версии.
- **baseline** — исходный уровень для повторяемого сравнения.

## Зачем нужна эта граница

Перегрузка начинается, когда запрошенная работа требует больше доступного ресурса, чем система может устойчиво выделить. Контроль допуска (admission control) решает до дорогостоящей работы, есть ли место новому запросу. Сброс нагрузки (load shedding) задаёт, какие запросы отклонить, если принять всё нельзя.

Сначала выберите ресурсную границу: число одновременно выполняемых задач, память очереди, соединения или общий бюджет. Затем задайте порядок решения: некорректный вход; продолжающаяся критическая работа; исчерпание ресурса; допустимость нового запроса. Приоритет должен быть явным, иначе критичная задача может быть вытеснена низкоприоритетным потоком или, наоборот, низкий приоритет никогда не получит обслуживания.

Модель этого урока принимает уже измеренные поля и возвращает состояние. Она не резервирует ресурс, не ставит запрос в очередь и не гарантирует справедливость. Отказ должен иметь понятную семантику для клиента, включая безопасный повтор и ограничение по времени.

## Три запускаемых примера


### Пример 1: Перегрузка: граница нормального допуска

```go
package main

import "fmt"

func LoadMode(offered int, capacity int) string { if offered<0||capacity<=0{return "invalid"}; if offered<=capacity{return "normal"}; return "overloaded" }

func main() { fmt.Println(LoadMode(4, 5)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 2: Политика перегрузки: приоритет и сброс

```go
package main

import "fmt"

func LoadDecision(offered int, capacity int, critical bool) string { if offered<0||capacity<=0{return "invalid"}; if offered<=capacity{return "accept"}; if critical{return "prioritize"}; return "shed" }

func main() { fmt.Println(LoadDecision(5, 5, false)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.


### Пример 3: Защита критической работы с deadline и возрастом очереди

```go
package main

import "fmt"

func ProtectCritical(offered int, capacity int, critical bool, deadlineOK bool, queueAge int, maxQueueAge int) bool { if offered<0||capacity<=0||queueAge<0||maxQueueAge<0{return false}; if offered<=capacity{return true}; return critical&&deadlineOK&&queueAge<=maxQueueAge }

func main() { fmt.Println(ProtectCritical(4, 5, false, true, 0, 60)) }
```

Пример проверяет только эту детерминированную модель; он не обращается к внешней системе.

## Практическая процедура

Перечислите доступные состояния модели и расставьте их по приоритету. Выберите вход, где одновременно нарушены две границы, и проверьте, какой ответ должен победить. Проверяйте приоритет, допустимое значение и предельное значение раздельно; иначе непонятно, какое правило определило результат.

Составьте политику для нормальной, перегруженной и деградированной зависимости. Для каждого решения укажите, что видит вызывающая сторона и сохраняется ли уже принятая работа. Если вводите приоритеты, определите starvation (голодание) — ситуацию, когда низкоприоритетный класс бесконечно ждёт — и способ ограничить её.

Результат helper не подтверждает текущую загрузку или фактическое ограничение ресурсов. Интеграционная проверка должна измерять одновременно активные задачи и память на ограниченном стенде. Публичные и закрытые векторы проверяют только переданные комбинации входов и контракт классификации.

## Разбор сценария: Перегрузка, admission control и load shedding

Представьте, что ограниченный ресурс почти исчерпан. Пропустите через правила сначала обычный запрос, затем запрос с высоким приоритетом и затем запрос, который не помещается в оставшийся бюджет. Запишите для каждого решение и основание: лимит, приоритет, deadline или недопустимый ввод.

Проверьте опасный случай: приоритетная работа постоянно приходит и вытесняет остальные. Укажите, ограничивает ли политика ожидание или допускает starvation. Также проверьте ответ клиенту при отказе: не утверждайте, что повтор безопасен, если неизвестно, успел ли запрос изменить состояние.

В выводе сформулируйте, какую одну границу подтверждает тест, и какие величины не измеряются. Helper может показать, что заданный `remaining` меньше стоимости работы и выбирается `reject`; он не выделяет память и не останавливает реальные запросы. Следующая проверка системы должна вызвать ограниченный исполнитель и подтвердить фактический предел параллелизма.

## Лаборатория: выбрать, кого допустить при перегрузке

### Численный сценарий

Пусть доступно восемь условных единиц ресурса, а запросы имеют стоимость 3, 2 и 4. Если сначала принять запросы стоимостью 3 и 2, остаётся три единицы; следующий запрос стоимостью 4 не помещается. Если запросы имеют приоритет, политика может сохранить бюджет для критичной работы, но должна заранее сказать, какие уже принятые запросы вытеснять нельзя. Функция этого урока может сравнить переданный остаток со стоимостью и выдать метку. Она не резервирует ресурс и не предотвращает гонку между двумя параллельными решениями.

Подумайте о ситуации, когда два запроса одновременно читают остаток 4 и оба стоят по 3. Оба helper-вызова по отдельности могут сказать `admit`, хотя вместе запросы расходуют 6. Реальная система должна атомарно резервировать ресурс или выполнять проверку под синхронизацией. Это ключевое различие между правильной чистой политикой и безопасным admission control.

### Построение таблицы приоритетов

Создайте таблицу для нормального, деградированного и перегруженного режима. В строках укажите вид работы, стоимость, класс важности, deadline и результат. Сначала решите, какие входы недопустимы. Затем проверьте, что уже выполняемая критичная операция не отменяется неожиданно. После этого задайте условия для новой обычной работы и для сброса нагрузки.

Добавьте два запроса с одинаковым приоритетом и слишком малым оставшимся бюджетом. Определите, кому достанется свободный ресурс: первому пришедшему, самому старому или запросу с ближайшим сроком. Если нет правила, результат будет зависеть от случайного порядка исполнения. Проверьте и обратный риск: высокий приоритет может постоянно вытеснять низкий класс, создавая starvation (голодание). Можно ограничить долю ресурса, резервировать минимум для класса или повышать приоритет с возрастом, но любое правило нужно явно выразить и проверить.

### Шаги испытания и наблюдения

1. Запишите начальный бюджет и точку, где он уменьшается: при решении, при постановке в очередь или при фактическом старте.
2. Рассчитайте последовательность запросов вручную; после каждого приёма обновляйте остаток.
3. Проверьте границы: ровно хватает, на единицу не хватает, нулевой остаток, некорректная стоимость.
4. Введите конкурентный пример и объясните, почему локальный helper не видит параллельное резервирование.
5. Запишите число принятых и отклонённых задач по классу, причину отказа и известный ресурс. Не включайте идентификаторы пользователей в метки метрик.

### Вывод и вопросы

Отказ может быть правильным действием защиты, но клиенту нужен понятный ответ. Если предлагается повторить запрос позже, укажите срок или событие, после которого это допустимо. При неизвестном исходе операции повтор без ключа идемпотентности может создать второй эффект. Не называйте политику справедливой только потому, что она уважает приоритет: измерьте максимальное ожидание и проверьте, не голодает ли класс.

Набор векторов подтверждает лишь результат функции для фиксированного снимка. Он не измеряет текущий бюджет, конкуренцию, память или фактическое число одновременно активных запросов. Следующий интеграционный тест должен синхронизировать несколько callers у одной границы, доказать, что общий бюджет не расходуется дважды, и проверить понятный отказ при исчерпании.

### Разделяйте допуск и исполнение

Контроль допуска принимает решение до начала дорогой работы, тогда как лимит параллелизма ограничивает уже запущенные операции. Очередь может иметь свободное место, но все соединения к базе уже заняты; или соединения свободны, но память очереди исчерпана. Для каждой границы определите, какой ресурс резервируется и как он освобождается при отмене или ошибке. Освобождение должно происходить ровно один раз; иначе утечка слотов постепенно откажет здоровым запросам.

Проверьте гонку между решением и резервированием. Два потока могут одновременно прочитать свободный бюджет и оба принять работу. В простой функции каждый отдельный вызов корректен относительно своего входа, но система в целом нарушает общий лимит. Нужна атомарная операция: semaphore (семафор), транзакция, lock или иной механизм, выбранный под ресурс. Проверяйте, что увеличение доступного бюджета синхронизировано с завершением задачи.

Пользовательский отказ должен сообщать стабильный класс причины, но не раскрывать секреты или внутренние адреса. При внешнем API также определите, может ли клиент повторить запрос и как избежать повтора эффекта. Эта деталь входит в эксплуатационный контракт, даже если демонстрационный helper возвращает только строку `reject`.

### Разберите отказ от допуска глазами клиента

Клиенту желательно различать временную перегрузку и постоянную ошибку контракта. Первая иногда допускает повтор с задержкой; вторая требует исправить запрос. Ответ может включать класс причины и ориентир времени, но не должен обещать точное освобождение ресурса, если оно неизвестно. Проверьте, что повтор не обходит приоритеты, создавая больше нагрузки.

Сервер должен учитывать и стоимость проверки самого запроса. Если expensive validation (дорогая проверка) выполняется до контроля допуска, отказ всё равно расходует ресурс. Расположите дешёвые проверки перед дорогими, но не выделяйте большой объём памяти до подтверждения бюджета. Измерьте, на каком шаге принимается решение и какие ресурсы уже затрачены; helper только определяет символический исход.

### Два независимых ограничения

Пусть очередь допускает десять элементов, но пул соединений к базе содержит только четыре. Если десять задач одновременно начнут выполнение, шесть могут ждать соединение, удерживая память и слоты. Если же ограничить активные worker четырьмя, очередь всё ещё может заполниться при длительном отказе базы. Эти лимиты защищают разные ресурсы и требуют отдельных сигналов.

Запишите бюджет по компонентам: ожидающая память, активные исполнения, соединения и срок удержания. Проверьте сценарий, где исчерпан один ресурс, но остальные свободны. Политика может вернуть разные причины или один общий отказ, но внутренний оператор должен понимать, какая граница сработала. Не подставляйте число worker вместо доступных соединений.

Упрощённый пример со стоимостью ресурса не резервирует несколько бюджетов атомарно. Для реального кода потребуется определить порядок захвата и освобождения, чтобы ошибка между двумя резервированиями не оставила утечку одного лимита.

## Практика Easy / Medium / Hard

**Easy — классификация.** Реализуйте первую функцию из контракта и проверьте корректный обычный случай, пустую/нулевую границу и явно невозможное значение. Результат должен точно совпасть с контрактом.

**Medium — политика с приоритетом.** Реализуйте вторую функцию. Сначала перечислите правила сверху вниз; при нескольких одновременно истинных условиях применяется первое. Добавьте тесты обычного состояния, насыщения, неизвестного значения и некорректной комбинации. Для числа/boolean не преобразуйте выход в произвольную строку.

**Hard — инвариант.** Реализуйте третью функцию, которая подтверждает только безопасную комбинацию предусловий. Граничный и противоречивый векторы обязаны отклоняться. Объясните, почему успешный результат helper не является реальным benchmark, fault test, безопасным rollout или гарантией доступности. Public и private cases находятся в JSON specs соответствующих exercise ID.

### Рабочий вопрос 1: границы overload

Сопоставьте overload с владельцем источника истины и назовите событие, после которого повтор становится безопасным. Запишите сначала ожидаемое состояние, затем вход, действие и наблюдаемый исход. Не выводите причинность из одного совпадения; сохраните команду, версию среды, количество повторов и ошибочные варианты. Если данных недостаточно, итогом должна быть отметка «неизвестно» и план следующего измерения, а не уверенная оценка. Укажите, какая часть ответа проверяется функцией, а какая потребовала бы отдельного интеграционного теста или человеческого review.
