# Клиент, сервер и путь HTTP

## Зачем разбирать обмен по частям

Когда браузер показывает ошибку или Go-программа получает неожиданный ответ, полезно спросить не «почему сломан интернет», а на каком шаге изменилось наблюдаемое поведение. HTTP — это формат обмена сообщениями между клиентом (client, сторона, которая начинает запрос) и сервером (server, сторона, которая принимает запрос и выбирает ответ). Эти роли относятся к одному обмену: программа, которая сегодня сервер, может сама быть клиентом другого сервиса.

Например, в LinkHub пользователь отправляет форму создания короткой ссылки. Браузер собирает запрос, сервер разбирает его и решает, можно ли создать ресурс, а затем возвращает результат. Пока мы рассматриваем только один такой обмен. База данных, вход в аккаунт и публичный сетевой запуск в этом уроке не нужны.

```text
клиент                         сервер
  | -- запрос -----------------> |
  | <- ответ ------------------ |
```

Стрелки показывают порядок сообщений, но не обещают доставку: соединение может оборваться. Клиент может не узнать, успел ли сервер выполнить операцию. TCP подтверждает доставку байтов между сетевыми концами при работающем соединении, но не доказывает, что приложение выполнило бизнес-действие ровно один раз. Повтор запроса после тайм-аута иногда создаёт дубликат — это отдельный контракт, к которому мы вернёмся.

## Из чего состоит HTTP-сообщение

Запрос (request, сообщение клиента) имеет метод, цель, заголовки и, иногда, тело. Метод — короткое слово о намерении: `GET` обычно читает представление, `POST` обычно просит создать или обработать данные. Цель указывает путь ресурса, например `/links`. Заголовки (headers) — именованные метаданные: `Content-Type` описывает формат тела, `Accept` сообщает предпочтительный формат ответа. Тело (body) — байты с данными; у `GET` оно часто пустое, но не следует определять наличие данных только по методу.

Ответ (response, сообщение сервера) содержит код состояния (status code), заголовки и тело. Код `201 Created` сообщает, что ресурс создан; `404 Not Found` — что запрошенный ресурс не найден; `500 Internal Server Error` — что сервер не смог корректно выполнить внутреннюю работу. Заголовок `Location` может указывать созданный ресурс или цель перенаправления. `Content-Type: application/json` говорит, что тело — JSON.

Упрощённый обмен выглядит так:

```text
POST /links HTTP/1.1
Host: example.test
Content-Type: application/json

{"alias":"go","target":"https://go.dev/"}

HTTP/1.1 201 Created
Content-Type: application/json
Location: /links/go

{"alias":"go","target":"https://go.dev/"}
```

Запись показана для чтения человеком. В реальной сети сообщение кодируется байтами, границы сообщений задаёт протокол, а соединение может обслуживать несколько запросов. Не нужно вручную собирать такую строку в серверном коде: `net/http` разбирает протокол и даёт структурированные значения.

### Контракт — это наблюдаемое поведение

Клиент и сервер должны совпадать по контракту (contract, согласованным правилам): допустимые методы и пути, значения заголовков, формат тела и значения кодов. Если сервер вернул JSON, но без `Content-Type`, многие клиенты всё равно разберут его, однако контракт станет неясным. Если вместо `201` пришёл `200`, тело может быть тем же, но клиенту труднее понять, создан ли ресурс.

Статусы делятся на пять семейств: `1xx` — промежуточные сообщения; `2xx` — успех; `3xx` — перенаправление; `4xx` — проблема запроса или прав клиента; `5xx` — сбой на стороне сервера. Семейство помогает ориентироваться, но конкретный код важен. Не сообщайте `500` о неверном JSON: клиент может исправить запрос. И наоборот, не выдавайте `200` при сбое и не кладите `"error"` в тело успешного ответа без чёткого контракта.

Заголовки нечувствительны к регистру по правилам HTTP, но значения и формат тела остаются значимыми. Заголовки не заменяют тело: большой объект удобно передавать в теле, а небольшие метаданные — в заголовках. Не помещайте секреты в URL: URL нередко попадает в историю браузера, access log и диагностические системы.

## Пример 1. Классификация статуса без сети

Путь `main.go`, стандартная библиотека не нужна. Функция классифицирует код; она не «отправляет HTTP».

```go group=status-classification mode=run
package main

import "fmt"

func ClassifyStatus(code int) string {
	switch {
	case code >= 200 && code < 300:
		return "success"
	case code >= 300 && code < 400:
		return "redirect"
	case code >= 400 && code < 500:
		return "client-error"
	case code >= 500 && code < 600:
		return "server-error"
	default:
		return "other"
	}
}

func main() { fmt.Println(ClassifyStatus(201), ClassifyStatus(404)) }
```

Здесь намеренно не принят диапазон `100..599` как единственная проверка валидности: задача классифицирует семействo, а не валидирует протокол. Вывод `success client-error` — локальный, детерминированный результат.

## Пример 2. Прочитать запрос через httptest

`httptest` создаёт запрос и запись ответа в памяти. Это не открывает порт и не требует браузера или интернета.

```go group=inspect-request mode=run
package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
)

func main() {
	handler := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/plain; charset=utf-8")
		w.WriteHeader(http.StatusCreated)
		fmt.Fprintf(w, "%s %s", r.Method, r.URL.Path)
	})
	request := httptest.NewRequest(http.MethodPost, "/links", nil)
	recorder := httptest.NewRecorder()
	handler.ServeHTTP(recorder, request)
	fmt.Println(recorder.Code)
	fmt.Println(recorder.Header().Get("Content-Type"))
	fmt.Println(recorder.Body.String())
}
```

Сначала тест создал вход, потом передал его handler (обработчику), после чего проверил то, что увидел бы клиент: статус, заголовок и текст. Важно вызвать `WriteHeader` до записи тела. Если сначала вызвать `Write`, пакет автоматически отправит успешный статус. В настоящем сервере handler получает уже разобранный запрос; он отвечает в `ResponseWriter`, а не возвращает готовый объект ответа.

## Пример 3. Проверить JSON-ответ по полям

Клиентский контракт проверяется по смыслу структуры, а не по пробелам или порядку ключей в JSON. В примере фиксированный тестовый ответ декодируется в структуру; сеть не используется.

```go group=decode-response mode=run
package main

import (
	"encoding/json"
	"fmt"
)

type Link struct {
	Alias  string `json:"alias"`
	Target string `json:"target"`
}

func main() {
	body := []byte(`{"target":"https://go.dev/","alias":"go"}`)
	var link Link
	if err := json.Unmarshal(body, &link); err != nil {
		panic(err)
	}
	fmt.Println(link.Alias, link.Target)
}
```

Ключи в ответе расположены не так, как поля структуры. JSON-объект не обещает определённый порядок ключей, поэтому клиенту следует проверять поля, значения и требуемое присутствие. Вывод `go https://go.dev/` подтверждает только декодирование этого fixture. Он не подтверждает, что URL безопасен, сервер сохранил ссылку или сетевой обмен завершился.

## Таблица диагностики обмена

Этот пример полезен для ручной диагностики. Он не является parser сетевых байтов: для протокольного разбора используйте `net/http`.

| Наблюдение | Где искать | Что из него нельзя заключить |
|---|---|---|
| Метод `POST` | строка запроса или `r.Method` | Что сервер сохранил запись |
| Путь `/links` | URL или `r.URL.Path` | Что идентификатор пользователя проверен |
| `Content-Type` | заголовок запроса | Что JSON валиден |
| `201` | код ответа | Что ответ дошёл до браузера |
| JSON в теле | декодер клиента | Что поля безопасны или принадлежат клиенту |

Полезный порядок проверки: сначала определите, кто отправлял сообщение; затем зафиксируйте метод и путь; потом сравните требуемые и фактические заголовки; только после этого разбирайте тело и статус. Такая последовательность не лечит ошибку сама, зато не смешивает транспорт, синтаксис и бизнес-правила.

Постройте таблицу воспроизведения до исправления. В столбце «ожидание» укажите, какое поведение было обещано; в «факт» положите данные от тестового recorder или клиента; в «переменная» назовите ровно один отличающийся вход. Например, для ошибки создания можно сравнить `POST /links` с корректным JSON и тот же запрос с пустым body. Если одновременно менять метод, путь, заголовки и JSON, результат не покажет причину. Для повторяющегося сбоя запишите fixture в тест, а не в личную заметку: так будущий рефакторинг проверит тот же контракт.

Разделяйте точную и семантическую проверку. Число статуса и значения `Location` часто должны совпадать точно. JSON разумнее декодировать и сравнивать по полям. Если заголовок допускает несколько представлений согласно контракту, сравнивайте семантику, а не случайное форматирование. При этом нельзя ослаблять проверку до «не пусто»: тест должен заметить неправильный статус или утечку чувствительного поля.

## Типичные ошибки и самостоятельная диагностика

1. **Считать любой `2xx` одинаковым.** Клиент может различать тело отсутствующего `204` и созданный ресурс при `201`. Сверьте точный контракт и тело ответа.
2. **Путать тело и заголовки.** Если JSON помещён в строковый заголовок, найдите, какой пакет его устанавливает. JSON-объект обычно живёт в body.
3. **Считать запрос доказательством выполнения.** Тайм-аут означает, что клиент не получил своевременный ответ, а не что сервер точно ничего не сделал. Для безопасных повторов нужны правила идемпотентности и, иногда, ключ запроса.
4. **Игнорировать метод.** `GET /links` и `POST /links` адресуют один путь, но описывают разные действия. Проверьте `r.Method` и явный ответ на неподдерживаемый метод.
5. **Отлаживать по одной только строке ошибки.** Запишите конкретные поля запроса и ответа без секретов; воспроизведите сообщение через `httptest`; меняйте один вход за раз.

Для ответа `404` различите два сценария: handler не выбран для пути или выбран, но ресурс отсутствует. Проверяйте конфигурацию маршрутов отдельно от поиска в хранилище. При `500` смотрите локальную причину в диагностике сервера, а клиенту оставляйте стабильное сообщение без пути к файлу, stack trace, SQL и значения токена.

## Практика

Попробуйте задания по порядку. В каждом сначала прочитайте функцию и вход, затем предскажите ответ, а уже потом запускайте проверку. Эталонное решение остаётся отдельным артефактом и не требуется для прохождения.

- **Easy:** классифицируйте статус по семейству. Проверьте обычный `200`, границу `300`, `599` и значение за пределами диапазона.
- **Medium:** по методу, пути, числу заголовков и размеру тела составьте краткое описание request snapshot. Не выводите тело и секретные заголовки; пустые значения остаются наблюдаемыми.
- **Hard:** для набора фикстур укажите категорию ответа и ожидаемый смысл: создано, не найдено, метод не поддержан или внутренняя ошибка. Не делайте вывод о сохранении данных только по статусу.

Критерии приёмки — это точная функция из условия, корректный ответ для каждого входа и обработка пустых/граничных значений. Если тест не совпал, сравните по полям: число случаев, код, заголовок и семантику тела. Не поправляйте expected под решение, пока не проверили исходный контракт.

## Проверка понимания и повторение

1. Какие четыре части запроса вы будете искать при разборе?
2. Чем статус `404` отличается от `500` с точки зрения ожидаемого действия клиента?
3. Почему факт отправки `POST` ещё не доказывает, что создание завершилось?
4. Какими тремя наблюдениями из `httptest.ResponseRecorder` подтверждается ответ?
5. Почему JSON-тело не становится валидным только из-за заголовка `Content-Type`?
6. Как отделить отсутствие маршрута от отсутствия записи по существующему маршруту?

Перед следующей главой нарисуйте последовательность «клиент — request — server — response» и подпишите метод, путь, один заголовок, статус и body. Затем объясните вслух границу знания: сообщение показывает, что наблюдал тест, но не все внутренние шаги. Вернитесь к Junior-12, если неудобно работать с функцией, аргументами и тестовыми фикстурами.

## Мини-глоссарий

- **client (клиент)** — участник, начинающий конкретный запрос.
- **server (сервер)** — участник, принимающий запрос и формирующий ответ.
- **request (запрос)** — метод, цель, заголовки и необязательное тело.
- **response (ответ)** — статус, заголовки и необязательное тело.
- **header (заголовок)** — метаданные HTTP-сообщения.
- **status code (код состояния)** — число, сообщающее результат обмена.
- **body (тело)** — байты с полезными данными сообщения.
- **contract (контракт)** — проверяемые правила формы и смысла обмена.
