# P5: migration и cutover

## Что ты сделаешь

Ты разобьёшь миграцию схемы на совместимые шаги expand, backfill, cutover и contract, опишешь путь отката и условие, которое разрешает переключение. Три функции урока выбирают фазу миграции, оценивают окно отката и собирают отметки для переключения. Они не выполняют миграцию и не заменяют проверку на копии данных.

## Разбор темы

Общий разбор P5 дан в senior-13. Здесь речь о том, как менять схему и переключать трафик так, чтобы в любой момент можно было остановиться и вернуться назад.

## Почему миграцию разбивают на шаги

Одна команда, которая переименовывает колонку и переписывает все строки, выглядит простой, но сочетает три риска: блокировку таблицы на время работы, несовместимость со старым кодом, который ещё работает, и невозможность откатить уже записанные данные. Разбиение на шаги убирает каждый из этих рисков в отдельности. Сначала добавляется новая форма, которую старый код игнорирует. Затем код учится писать в обе формы. Затем заполняются старые строки. Затем чтение переключается на новую форму. И только в конце старая форма удаляется. На каждом шаге можно остановиться, и система продолжает работать.

Порядок шагов важнее скорости. Удаление старой формы до переключения всех читателей — самая дорогая ошибка, потому что данные уже не вернуть без резервной копии.

## Двойная запись и её подводные камни

На этапе, когда код пишет в старую и новую форму одновременно, возникает риск расхождения: одна запись прошла, вторая упала, и данные разошлись. Простая мера — порядок записи с понятной обработкой ошибки: если вторая запись не прошла, первая откатывается или ставится в очередь повторной сверки. Без такой обработки расхождение накапливается незаметно, и обнаруживается только при переключении чтения.

Сверка нужна не только при двойной записи. Сравнение количеств строк и выборки контрольных записей между старой и новой формой показывает, что backfill действительно перенёс данные. Счётчики совпали, но значения в одном поле отличаются — это тоже расхождение, и только выборочное сравнение его поймает.

Backfill, который работает параллельно с двойной записью, требует отдельного правила: если строка записана новым кодом позже, backfill не должен перезаписать её старым значением. Обычно это решается условием обновления по версии строки или по времени изменения. Без такого условия фоновая работа тихо откатывает свежие данные, и ошибка видна только в отчётах через неделю.

## Теневое чтение

Перед переключением чтения удобно запустить новый путь параллельно и сравнивать ответы, не отдавая их пользователю. Такое теневое чтение показывает, совпадает ли поведение на реальном трафике, а не на тестовых данных. Расхождения собирают и разбирают: часть окажется ошибкой нового кода, часть — различием в порядке строк или в округлении, которое не важно для пользователя. Переключение разрешается, когда расхождения объяснены, а не когда их число стало маленьким.

Теневое чтение не должно удваивать нагрузку на базу. Если новый путь тяжёлый, его включают на доле трафика и увеличивают постепенно.

Теневое сравнение полезно не только для успеха, но и для тихих расхождений: например, когда новый путь возвращает те же данные, но в другом порядке, и клиент, который сортировал по старому порядку, видит другой список. Такие различия фиксируют правилами сравнения, которые знают о порядке и округлении, иначе каждый отчёт будет полон ложных тревог.

## Откат и окно отката

Откат кода возвращает старое поведение приложения, но не данные. Если новая версия уже записала строки в новой форме, старая версия может их не понимать. Поэтому окно отката определяется совместимостью записей: до какого момента старый код способен работать с данными, записанными новым. Это окно записывают заранее и проверяют на копии, а не выясняют во время инцидента.

Когда окно закрыто, остаётся исправление вперёд: новая версия исправляет данные и поведение, а не возвращается к старой. Такое решение принимает владелец данных, и заранее должен быть понятен критерий, при котором оно допустимо.

Окно отката стоит проверить не только техническим прогоном, но и по бизнес-процессам. Если в окне отката выставляются счета или отправляются письма на основе новой формы, откат на старую версию меняет уже отправленные документы. Такие места перечисляют заранее и решают, допустим ли откат для каждого из них.

Откат данных иногда возможен только через резервную копию, и это почти всегда дорогое решение: придётся восстанавливать и потерять всё, что записано после копии. Поэтому перед миграцией, которая меняет данные необратимо, делают отдельный снимок нужных таблиц и проверяют, что его можно восстановить на копии. Снимок не заменяет обратимой миграции, но даёт последний путь назад, когда остальные исчерпаны.

## Фаза миграции

Пример 1 показывает, на какой фазе находится миграция по текущим отметкам. Пока расширение не выполнено, начинается expand; затем backfill; затем переключение потребителей; только после этого допустим шаг contract.

```go
package main

import "fmt"

func migrationPhase(expanded, backfillVerified, consumersMoved bool) string {
	if !expanded {
		return "expand"
	}
	if !backfillVerified {
		return "backfill"
	}
	if !consumersMoved {
		return "cutover_ready"
	}
	return "contract_candidate"
}

func main() {
	fmt.Println(migrationPhase(false, false, false))
	fmt.Println(migrationPhase(true, false, false))
	fmt.Println(migrationPhase(true, true, false))
	fmt.Println(migrationPhase(true, true, true))
}
```

Вывод: `expand`, `backfill`, `cutover_ready`, `contract_candidate`. Порядок фаз защищает от удаления старой формы до того, как все потребители перешли на новую.

## Окно отката

Пример 2 оценивает, можно ли откатиться. Без старого бинарного файла откат кода невозможен; если новые записи несовместимы со старой версией, откат заблокирован данными; иначе откат доступен.

```go
package main

import "fmt"

func rollbackWindow(dataCompatible, oldVersionAvailable bool) string {
	if !oldVersionAvailable {
		return "no_binary_rollback"
	}
	if !dataCompatible {
		return "data_blocked"
	}
	return "rollback_available"
}

func main() {
	fmt.Println(rollbackWindow(true, true))
	fmt.Println(rollbackWindow(false, true))
	fmt.Println(rollbackWindow(true, false))
}
```

Вывод: `rollback_available`, `data_blocked`, `no_binary_rollback`. Откат бинарного файла не возвращает уже изменённую схему: данные, записанные новой версией, остаются в новом виде.

## Разрешение переключения

Пример 3 собирает три отметки для переключения: shadow-результаты сопоставлены, откат проверен на копии, владелец одобрил. Отсутствие любой отметки означает, что переключение не разрешено.

```go
package main

import "fmt"

func cutoverAllowed(shadowMatched, rollbackTested, ownerApproved bool) bool {
	return shadowMatched && rollbackTested && ownerApproved
}

func main() {
	fmt.Println(cutoverAllowed(true, true, true))
	fmt.Println(cutoverAllowed(true, false, true))
}
```

Вывод: `true`, `false`. Отметки фиксируют наличие подтверждений; проверка на копии не отражает данные, записанные в продуктиве после переключения.

## Если что-то пошло не так

- Удаляешь старую колонку до переключения всех потребителей → сначала выполни cutover и подтверди отсутствие чтений старой формы.
- Считаешь откат бинарного файла возвратом данных → проверь, что новая версия записала совместимо.
- Backfill без сверки количеств → сравни счётчики и выборочные контрольные записи до переключения.
- Переключаешь по одной проверке на копии → добавь shadow-сравнение и одобрение владельца.

## Типичные ошибки миграции

Удалять старую колонку в том же релизе, где впервые включается новая. Запускать backfill одним огромным запросом, который держит блокировку на всю таблицу. Считать совпадение количеств строк доказательством корректности значений. Откатывать код, не проверив, что старая версия поймёт записанные данные. Переключать чтение без теневого сравнения, полагаясь на тесты, которые построены на синтетических данных.

## Порог для переключения

Переключение чтения разрешается не по ощущению готовности, а по записанному порогу. Например: расхождение в выборке ниже одной сотой процента, все расхождения объяснены, откат проверен на копии в пределах окна отката. Если порог не выполнен, переключение откладывается, и это решение записывают вместе с причиной. Такой документ нужен не для бюрократии: через месяц он объяснит, почему миграция шла дольше плана.

## Роли при переключении

Переключение требует трёх ролей, и один человек не должен совмещать их. Владелец данных отвечает за критерии сверки и решает, что считается расхождением. Дежурный инженер выполняет переключение и отвечает за откат, если критерий нарушен. Тот, кто пишет код миграции, проверяет сверку, но не подтверждает переключение: иначе проверка становится самопроверкой. Роли записывают в плане миграции с именами, и план заранее согласуется с теми, кто будет на дежурстве в день переключения.

## Порядок шагов и контрольные точки

Для каждого шага миграции записываются вход, действие, критерий перехода и откат. Вход — состояние, с которого шаг начинается. Критерий перехода — наблюдаемое условие, например «backfill завершён, расхождение на выборке из тысячи строк равно нулю». Откат — действие, которое возвращает систему к входному состоянию. Если откат шага невозможен, это записывается явно, и переход на такой шаг требует отдельного одобрения владельца данных. Так список шагов становится инструкцией, которую можно выполнить ночью без автора.

Контрольные точки имеет смысл ставить не только после шагов, но и внутри долгого backfill. Курсор, на котором остановилась обработка, сохраняется, и после сбоя работа продолжается с него, а не с начала. Иначе перезапуск на большой таблице займёт часы и создаст нагрузку, которой никто не планировал.

## Итог

- Миграция разбивается на фазы, каждая из которых совместима с соседними версиями и имеет точку остановки.
- Откат кода не возвращает схему и данные, записанные новой версией, поэтому окно отката определяется совместимостью данных.
- Переключение разрешается по трём отметкам: сопоставленные shadow-результаты, проверенный откат и одобрение владельца.
