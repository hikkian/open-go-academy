# IP, TCP, DNS и порты

## Зачем приложению имена и адреса

HTTP описывает смысл запроса и ответа, но до HTTP программе нужно найти компьютер и установить путь к нему. DNS (Domain Name System, система доменных имён) связывает имя, например `api.example.test`, с одним или несколькими IP-адресами. IP (Internet Protocol, интернет-протокол) адресует сетевые узлы и помогает маршрутизаторам передавать пакеты. TCP (Transmission Control Protocol, протокол управления передачей) создаёт поток байтов между двумя сетевыми концами. Порт выбирает процесс или службу на конкретном узле.

Эти понятия отвечают на разные вопросы: «во что преобразовалось имя?», «куда маршрутизировать пакеты?», «с каким процессом соединиться?» и «какой HTTP ответило?». Смешивание уровней приводит к случайной диагностике. Если DNS вернул адрес, это не означает, что порт слушает. Если TCP соединился, это не означает, что на порту есть HTTP. Если сервер вернул `404`, значит приложение уже ответило: причину следует искать выше транспортного уровня.

Пример адреса: `https://api.example.test:8443/links`. Здесь схема `https` задаёт ожидаемый защищённый HTTP; имя — `api.example.test`; порт — `8443`; путь — `/links`. Порт `443` обычно используется HTTPS по умолчанию, а `80` — HTTP, но это соглашения. Служба может работать на другом порту. В URL со стандартным портом его иногда опускают.

## Путь диагностики

```text
имя → DNS lookup → IP-адрес → TCP к порту → TLS при HTTPS → HTTP → логика приложения
```

Это учебная последовательность, а реальные библиотеки могут кэшировать ответы и переиспользовать соединения. Она помогает выбрать следующий вопрос, а не описывает каждую оптимизацию. Ошибка «не удалось разрешить имя» указывает на этап до TCP. «Connection refused» обычно означает, что адрес достижим, но на порту никто не принимает соединение либо система активно его отклонила. Тайм-аут не различает все возможные причины: фильтрация, маршрут и перегрузка могут выглядеть похоже.

`localhost` — специальное имя для локальной машины. Оно может разрешаться в IPv4 (`127.0.0.1`) и IPv6 (`::1`). Приложение может слушать только одно семейство адресов, поэтому соединение к IPv6 localhost способно отличаться от соединения к IPv4. `0.0.0.0` обычно означает «слушать все локальные IPv4 интерфейсы» при bind; это не публичный адрес назначения для клиента. IPv6 wildcard записывается как `::`.

### IP — это адрес, а не имя человека

IPv4 записывает четыре десятичных октета, например `192.0.2.10`. Октет хранит значение `0..255`. IPv6 использует восемь групп шестнадцатеричных значений; нули можно сжимать по правилам записи. Адрес может принадлежать интерфейсу, loopback, частной сети или публичному пространству. Адрес сам по себе не сообщает, какой HTTP путь доступен, какое имя предъявить сертификату или кто владеет компьютером.

В одном DNS-имени может быть несколько адресов, а ответы меняются со временем. Клиент, прокси или операционная система могут сохранять ответ в кэше. При обновлении записи часть клиентов некоторое время использует старый адрес. Поэтому «DNS сейчас вернул X» — наблюдение, но не доказательство того, что каждый клиент получил X.

### TCP, соединение и поток

TCP обеспечивает упорядоченный поток байтов и повторную передачу при части потерь, пока соединение поддерживается. Он не сохраняет границы прикладных сообщений: две записи `Write` могут прийти как одна порция данных или одна запись — частями. HTTP-библиотека разбирает протокол поверх потока.

Соединение идентифицируется сетевыми концами, включая IP и порт клиента и сервера. Клиент обычно получает временный исходящий порт; сервер слушает стабильный порт. Одно приложение может иметь несколько открытых TCP-соединений. Современный HTTP способен обслуживать несколько запросов на одном соединении, поэтому «один HTTP-запрос — одно TCP-соединение» не является надёжным правилом.

Порт — 16-битное число `0..65535`, но значения `0` и специальные диапазоны имеют особый смысл при назначении. Порты помогают операционной системе доставить данные правильному процессу. Они не открывают firewall автоматически и не гарантируют, что процесс готов принять запрос.

## Пример 1. Разобрать host:port локально

Файл `main.go`; `net.SplitHostPort` разбирает форму endpoint, а `net.ParseIP` проверяет синтаксис IP. Проверять, существует ли адрес в сети, этот код не пытается.

```go group=parse-host-port mode=run
package main

import (
	"fmt"
	"net"
)

func main() {
	host, port, err := net.SplitHostPort("[::1]:8080")
	if err != nil { panic(err) }
	fmt.Println(net.ParseIP(host) != nil, port)
}
```

Квадратные скобки нужны вокруг IPv6 при записи host:port. У строки `::1:8080` без скобок невозможно однозначно отделить адрес от порта. Для построения такого адреса используйте `net.JoinHostPort`, чтобы не реализовать правила скобок самостоятельно.

## Пример 2. Собрать адрес без предположения о семействе

```go group=join-host-port mode=run
package main

import (
	"fmt"
	"net"
)

func main() {
	fmt.Println(net.JoinHostPort("2001:db8::7", "443"))
	fmt.Println(net.JoinHostPort("api.example.test", "8443"))
}
```

Результат соответственно `[2001:db8::7]:443` и `api.example.test:8443`. Для документационных адресов `2001:db8::/32` зарезервирован для примеров; код не подключается к ним. Склеивание `host + ":" + port` сломало бы IPv6.

## Пример 3. Отделить синтаксис имени от сетевого ответа

Для детерминированного учебного теста держите ожидаемое DNS-соответствие как fixture. Следующий код не выполняет DNS lookup.

```go group=dns-fixture mode=run
package main

import "fmt"

func main() {
	records := map[string][]string{
		"api.example.test": {"192.0.2.4", "2001:db8::4"},
	}
	addresses, ok := records["api.example.test"]
	fmt.Println(ok, len(addresses), records["missing.example.test"] == nil)
}
```

Вывод `true 2 true` говорит только о фикстуре. Он не говорит о DNS сервере, маршруте или доступности процессов. Такой тест хорошо проверяет преобразование и выбор адреса; реальный resolver требует отдельного integration test и контролируемой сетевой среды. Эти задания не требуют внешнего DNS.

## Последовательность расследования сбоя

1. Проверьте, что URL разбирается: схема, имя, порт и путь не перепутаны.
2. Различите имя и адрес. Если имя не разрешается, проверка HTTP handler пока преждевременна.
3. Зафиксируйте адрес и семейство IP. Если A и AAAA записи отличаются, проверьте какой путь реально выбрал клиент.
4. Проверьте, что нужный процесс слушает правильный IP и порт. Listen только на loopback не доступен из другой машины.
5. После установления TCP исследуйте TLS, если используется `https`; затем разбирайте HTTP статус и тело.

Эта последовательность не означает, что каждый шаг можно проверить простой командой или что результат однозначен. Наблюдайте точное сообщение библиотеки, время ожидания и выбранный адрес. Не публикуйте секреты, токены и персональные данные вместе с сетевыми диагностическими журналами.

### Чтение endpoint глазами программы

Разделите адрес на поля, прежде чем обсуждать его доступность. У `https://[2001:db8::2]:9443/health` схема — `https`, host — `2001:db8::2`, порт — `9443`, path — `/health`. Если убрать скобки, parser не знает, какое из восьми двоеточий разделяет порт. URI parser и `net.SplitHostPort` решают разные задачи: первый понимает компоненты URL, второй — endpoint формы `host:port`. Не передавайте в `SplitHostPort` всю URL строку и не используйте `URL.Host` как уже отделённый hostname: он может включать порт.

Номер порта в URL приходит текстом. Прежде чем преобразовать его к `int`, проверьте ошибку преобразования и диапазон. Строка `abc`, отрицательное значение и `70000` не становятся допустимым listener просто потому, что `Atoi` выполнился. Пустой порт также может означать «используй стандартный порт для схемы» в URL, но произвольный `host:` в вашей функции может быть признан ошибкой. Решение должно следовать сигнатуре и контракту, а не скрытой эвристике.

### Маршрутизатор между двумя узлами

Маршрутизатор пересылает пакет к следующему узлу на основании IP маршрутов. Он не читает смысл HTTP body и не выбирает функцию Go. Firewall и сетевые политики способны запретить порт даже при корректном адресе. NAT может преобразовать частный адрес и исходный порт при выходе из сети. Поэтому видимый публичный адрес клиента не всегда равен IP интерфейса его процесса.

`127.0.0.1` и `::1` — loopback: пакет возвращается в ту же машину. Если сервер слушает loopback, соседний контейнер или компьютер не обращается к нему как к собственному `localhost`; у него другой network namespace или узел. В контейнерах имя службы может резолвиться внутренним DNS Compose, а `localhost` внутри приложения указывает на сам контейнер. Изучите то пространство имён, в котором действительно работает клиент.

Для локальной практики избегайте выводов о firewall по тесту handler в памяти: тест вообще не открыл порт. Если нужен socket integration test, bind только на loopback, динамически назначьте порт через стандартный тестовый helper, используйте deadline и гарантированно остановите listener. Эти задачи ограничены чистыми parsers и фикстурами, поэтому не требуют подобного теста.

## Типичные ошибки

- **Проверять HTTP после ошибки DNS.** На этом запуске клиент не получил IP-адрес; server handler, скорее всего, ещё не участвовал.
- **Считать `localhost` одним адресом.** Настройки машины и семейство IPv4/IPv6 могут менять результат. Привяжите тестовый listener к конкретному локальному адресу или проверяйте оба.
- **Удалять порт из IPv6 endpoint.** Используйте `SplitHostPort`/`JoinHostPort`; не считайте двоеточия разделителем ровно один раз.
- **Считать открытый порт живым API.** TCP accept ничего не говорит о маршруте `/links` или допустимом методе.
- **Считать DNS запись гарантией сервера.** Кэш, несколько записей, балансировщик и состояние приложения находятся на других границах.
- **Диагностировать тайм-аут как отказ сервера.** Тайм-аут показывает, что операция не завершилась в установленный срок. Он не указывает единственную первопричину.

## Практика

Каждое задание моделирует только локальные данные. Не запускайте DNS-запросы и не подключайтесь к реальному адресу.

- **Easy:** распарсите endpoint `host:port`, включая IPv4, hostname, bracketed IPv6 и испорченную форму. Верните адресные части и признак успешного разбора; порт должен состоять из допустимых десятичных цифр и попадать в `1..65535`.
- **Medium:** по наблюдениям этапов выберите первую ещё не пройденную границу: разрешение имени, TCP connect, TLS или HTTP. Успех предыдущего этапа не объявляет следующий успешным.
- **Hard:** безопасно соберите endpoint из hostname/IP и порта; корректно оформите IPv6, отклоните пустые значения, разделители в имени и некорректный порт. Не пытайтесь подтвердить достижимость сети.

Критерии: одинаковый ввод даёт одинаковый вывод; обрабатываются обе версии IP и граничные порты; результат не утверждает, что сетевой узел существует. Для проверки составьте список входов с ожидаемой границей и прогоните их как таблицу. После ошибки сначала уменьшите пример до одной строки address или одного симптома, затем сформулируйте, какой уровень оно измеряет.

Для повторения нарисуйте цепочку «имя → адрес → порт → протокол приложения» и приведите по одному сбою на каждом переходе. Сверяйте мысленный диагноз с наблюдаемой стадией, а не с догадкой о сервере. Следующий урок добавляет TLS между транспортным соединением и прикладным HTTP; глава 01 остаётся опорой для разделения HTTP и сетевой доставки.

## Мини-глоссарий

- **DNS** — система поиска IP-адресов по именам.
- **IP** — протокол адресации и маршрутизации пакетов.
- **TCP** — транспортный упорядоченный поток байтов между двумя концами.
- **port (порт)** — номер службы внутри сетевого узла.
- **localhost** — имя для локальной машины.
- **endpoint (конечная точка)** — сочетание адреса и порта подключения.
- **resolver (резолвер)** — компонент, выполняющий поиск DNS имени.
- **timeout (тайм-аут)** — предел времени ожидания операции.
