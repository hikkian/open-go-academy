# P1 — Go CLI Toolkit

## Цель

Соберите небольшую командную программу `toolkit`. В проекте вы потренируетесь читать аргументы процесса, проверять ошибки, работать с файлами и декодировать JSON в типизированные данные.

## Функциональное задание

Сделайте две команды:

- `toolkit sum N...` принимает один или несколько целых десятичных чисел в диапазоне `int64`, в том числе отрицательных, и печатает сумму с переводом строки. При переполнении сообщите об ошибке.
- `toolkit inspect path` читает файл, содержащий JSON-массив строк, например `["Ada", "Lin", "Go"]`, и печатает количество строк с переводом строки. Пустой массив допустим.
- Представьте ошибки команды отдельной структурой (например, `ToolError` с полем `Message` и методом `Error() string`), чтобы вызывающий код мог единообразно показать короткое сообщение без стека вызовов.

При отсутствии аргументов, неизвестной команде, неверном числе, неверном количестве аргументов, ошибке чтения или некорректном JSON напечатайте короткое описание в stderr и завершите программу с кодом 2. Успешный запуск завершается кодом 0. Не выводите стек вызовов.

## Ограничения проекта

Для воспроизводимого запуска используйте только стандартную библиотеку Go и сохраните `go.mod` с модулем `cli-toolkit` и версией языка Go `1.27.2`; дополнительные зависимости не принимаются. Файлы проекта лежат в корне: исходники `.go` и JSON-файлы имеют имена вида `name.go` / `name.json` (ASCII-буква в начале, затем буквы, цифры, `_` или `-`), а также допускаются `README.md` и `go.mod`. Включая тесты, допускается не более 16 файлов, 64 KiB Go-исходников суммарно, 8 JSON-файлов суммарно до 64 KiB и 128 KiB содержимого всего. Нужны непустой README и хотя бы один `.go` файл не с суффиксом `_test.go`.

## Автоматически проверяемые функциональные критерии

1. Пример `sum 4 -1 9` печатает ровно `12` и перевод строки.
2. Суммы, выходящие за границы `int64`, отклоняются; граничные допустимые суммы работают.
3. `inspect` принимает только JSON-массив строк и печатает его длину; файл и декодирование проверяются.
4. Все ошибки CLI дают пустой stdout, полезное сообщение в stderr и код 2.
5. Автоматические тесты охватывают успех, неверный ввод, переполнение, граничные значения int64, пустой массив, неверные JSON-типы и отсутствующий файл.
6. Ошибка представлена типом, реализующим `error`, и отображается в одном контролируемом сообщении.
7. Ограничения файлов, размеров, зависимостей и фиксированный `go.mod` соблюдаются.

## Критерии ручной оценки

- README ясно объясняет назначение, build/run/tests, примеры и выпуск; оцените полноту и понятность по обсуждению на review.
- Git история показывает небольшие осмысленные коммиты; преподаватель проверяет историю и обсуждает решения. Автотесты не подтверждают качество истории или защиту проекта.
- Выпуск `v1.0.0` подготовлен только после ручной проверки чистого состояния, заметок выпуска и команд проверки.

## Рекомендуемые этапы

1. Создайте модуль и минимальную точку входа; разберите форму команды.
2. Реализуйте `sum`, затем тесты на отрицательные числа и границы `int64`.
3. Реализуйте `inspect` с `os.ReadFile` и `encoding/json`; проверьте пустой и некорректный файл.
4. Проверьте точные stdout/stderr и коды завершения через собранный бинарный файл.
5. Запустите форматирование, тесты и `go vet`; проверьте команды из этого README.
6. Подготовьте выпуск `v1.0.0`: чистый Git status, аннотированный тег и заметки выпуска с командами проверки.

## Запуск

В каталоге проекта:

```sh
go test ./...
go vet ./...
go build -o toolkit .
./toolkit sum 4 -1 9
./toolkit inspect names.json
```

Пример `names.json`:

```json
["Ada", "Lin", "Go"]
```

Ожидаемый вывод последней команды — `3`. Для ошибки проверьте код завершения и stderr отдельно, например `./toolkit sum not-a-number`. До создания релизного тега сначала убедитесь, что все тесты проходят и документация соответствует текущей программе.
