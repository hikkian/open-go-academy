# Участие в Open Go Academy

Проект находится в активной разработке. Перед изменениями прочитайте [AGENTS.md](AGENTS.md), [спецификацию](docs/MASTER_SPEC.md), [план](docs/EXECUTION_PLAN.md) и [текущий handoff](AGENT_HANDOFF.md). Спецификация задаёт продукт, план — порядок этапов, handoff — подтверждённое состояние. Не считайте черновики, локальные проверки или проектные симуляции опубликованной функциональностью.

## Подготовка и проверки

Нужны Linux, Go 1.27.2 (либо доступ к этому toolchain через `scripts/go.sh`), Node.js 24.18.0, npm и make. Для локального исполнения кода дополнительно нужен rootless Podman с cgroup v2/systemd и seccomp. Сборка без AI и без контейнерного runtime возможна; выполнение Go-кода без runtime должно оставаться отключённым.

```sh
make bootstrap
make test
```

`make test` запускает Go unit-тесты, тесты и vet P1 reference, общий vet и race detector, затем frontend typecheck/build. Для отдельных проверок используйте команды из [Makefile](Makefile): `make sandbox-test`, `make build`, `make e2e`. `make e2e` ожидает работающие процессы API и runner; подробности — в [руководстве запуска](GETTING_STARTED.md). Негативные sandbox-тесты запускайте только на disposable окружении и после чтения [модели угроз](docs/architecture/THREAT_MODEL.md).

Перед отправкой изменений:

- выполните проверки, относящиеся к затронутым пакетам, и укажите фактический результат;
- не меняйте pinned Go/npm зависимости без обновления lockfiles и объяснения совместимости;
- для пользовательского кода сохраняйте fail-closed поведение и проверяйте реальные границы исполнения;
- учебный текст, стартер и reference должны соответствовать закреплённой версии Go и иметь воспроизводимые проверки;
- не включайте ключи, пользовательские данные, `.data/`, `artifacts/` или локальные сборочные файлы;
- обновляйте traceability и handoff только по подтверждённым результатам.

## Дизайн изменений

Для учебных глав используйте [руководство автора курса](docs/COURSE_AUTHORING.md): оно описывает контракт задания, эталоны, скрытые проверки, проверку неправильных решений и порядок приёмки черновика.

Сначала обсудите контракт и критерий приёмки в issue/изменении, если задача затрагивает API, миграции, ранги, доказательства, credentials или runner boundary. Для миграций проверьте пустую базу, повторный запуск и сохранённые данные. Для UI проверяйте desktop/mobile и состояния ошибки, пустого результата и отключённой возможности. AI Tutor остаётся необязательным; AI не может определять оценки, ранги или выдачу credentials.

## Лицензирование

Лицензия кода и учебных материалов пока не выбрана владельцем. Не добавляйте SPDX/лицензионные заявления и не распространяйте сторонние материалы без проверки прав. Решение о лицензии и публикации остаётся за владельцем проекта.
